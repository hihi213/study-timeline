# **1) 키 입력~에디터 메모리까지 (유저 공간)**

1. 키보드 인터럽트 → OS 입력 스택(IME/Wayland·X/Win32) → **에디터 프로세스 이벤트 루프**로 문자 전달
2. 에디터는 **자신의 가상 메모리(힙/버퍼)** 에 텍스트를 저장
    
    - 이 메모리는 **가상 메모리(VM)**: 실제 RAM에 매핑되고, 처음 접근 시 **페이지 폴트**로 페이지가 할당됨.

> 아직 디스크와 무관. 전부 “내 프로세스 주소공간”에서만 일어납니다.

---

# **2) 저장 버튼 클릭: 시스템 콜 경로 (유저 → 커널)**

대표적인 호출 흐름 (리눅스/유닉스 계열 기준):

```
openat(O_CREAT|O_WRONLY|…)
write(파일디스크립터, 버퍼, 길이)
fsync(파일디스크립터)        # (강한 내구성 보장 시)
close(파일디스크립터)
```

- **write()는 보통 “페이지 캐시로의 복사 완료”까지만 보장**하고 **즉시 리턴**(빠름).
- 진짜 디스크 기록(미디어에 영구히 적힘)은 **커널의 writeback 쓰레드**가 **나중에 비동기**로 수행.
- 앱이 **fsync()/fdatasync()**(Windows는 **FlushFileBuffers**)를 호출하면, **데이터와 메타데이터가 디스크까지 내려가도록 강제**하고, **디바이스 캐시 flush(FUA/FLUSH)** 까지 요청해 **전원 장애에도 살아남게** 함. (성능↓, 내구성↑)

> **블로킹/논블로킹 I/O**

- > 일반 파일에선 O_NONBLOCK이 **효과 거의 없음**(대부분 즉시 복사되니까).
- > 소켓/파이프에서 주로 의미 있음.
- > 디스크 I/O의 실제 블로킹은 주로 **fsync/메모리 압박/dirty-page 제한**에서 발생.

# **3) 커널 안쪽: VFS, 페이지 캐시, 라우팅**

- **VFS(가상 파일 시스템)**: open/write/rename… 같은 공통 API를 받아 **구체 FS(ext4, NTFS 등)의 메서드**로 위임.
- **페이지 캐시**: 파일의 페이지(블록 단위)를 **RAM에 캐싱**. write() 시 **유저 버퍼 → 페이지 캐시**로 복사하고 **dirty** 표시.
- **writeback**: 커널이 주기적으로 dirty 페이지를 디스크로 **배치 쓰기(batch)** 하여 성능을 끌어올림.
- **dentry/inode 캐시**: 경로 탐색과 inode(파일 메타) 접근을 빠르게.

# **4) 파일시스템 레벨 (ext4 vs NTFS) – “무엇을, 어떤 순서로” 쓰나**

## **ext4 (리눅스 기본)**

- **아이노드(inode)**: 파일의 메타데이터(권한, 사이즈, 블록 매핑 등).
- **익스텐트(extent)**: “연속 블록 덩어리” 단위로 데이터 매핑(조각화↓).
- **지연 할당(delayed allocation)**: write() 즉시 블록을 확정하지 않고, **나중(writeback)에 한 번에 좋은 위치로** 할당(성능/연속성↑).
- **저널링(JBD2)**: 기본 data=ordered 모드
    
    1. **데이터 블록**을 먼저 디스크로 보냄
    2. **메타데이터 변경**을 **저널(log)에 커밋**
    3. 체크포인트로 실제 메타데이터를 제자리 업데이트
    4. **배리어(FLUSH/FUA)** 로 디바이스 캐시 비우기 → **크래시 일관성** 확보

- **원자적 rename**: 임시파일에 쓰고 rename()으로 바꿔치기 → **이 시점이 원자적 저장**(crash-safe).
- **fsync(fd)** + **fsync(dir)**(리네임한 디렉터리)에 주의: 파일뿐 아니라 **부모 디렉터리 엔트리**까지 내구성 확보가 필요할 때가 있음.

## **NTFS (윈도우 기본)**

- **MFT($MFT)**: 모든 파일의 레코드(메타데이터).
- **데이터 속성(attribute)**: 데이터가 작으면 **MFT 내부(상주)**, 크면 **클러스터 run(비상주)** 로 매핑.
- **$LogFile 저널(메타데이터 저널링 중심)**: redo/undo 레코드로 트랜잭션 커밋 → crash 후 복구.
- **Cache Manager + Lazy Writer**: 유사하게 **시스템 파일 캐시**에 쓰고 나중에 디스크 기록.
- **FlushFileBuffers** 호출 시: 해당 파일(그리고 필요 시 볼륨 캐시)까지 **플러시** → **디바이스 캐시 FLUSH**로 내구성 확보.
- **원자적 교체**: 일부 앱은 임시파일 작성 후 ReplaceFile() 사용.

> 요약: **둘 다 “저널”로 메타데이터 일관성을 보장**하고, **데이터는 캐시에 모아 순서 있게 쓰되, fsync/Flush로 내구성 강제**가 핵심.

# **5) 디스크/스토리지 레벨: 진짜 “영구화”**

- 커널이 보낸 쓰기 요청은 **블록 레이어 → 드라이버 → 디바이스(NVMe/SATA)** 로 내려감.
- 디바이스에는 **자체 쓰기 캐시**가 있어 더 빠름.
- **barrier/flush/FUA** 가 수행되어야 **전원 장애 시에도** 데이터가 남습니다(그래서 fsync가 비쌈).

---

# **6) 실전에서 많이 쓰는 “안전 저장” 패턴**

1. **임시파일에 전부 쓰기** (.tmp)
2. **fsync(tmp)로 데이터 내구성 보장**
3. **rename(tmp → 최종파일)**  ← **원자적 교체**
4. **fsync(부모 디렉터리)** 로 디렉터리 엔트리까지 보장
5. (Windows라면 ReplaceFileW + FlushFileBuffers)

---

# **7) 메모리 매핑(mmap) 경로(참고)**

- 에디터가 파일을 mmap()하면, 쓰기 시 **페이지가 dirty** 되고, **writeback 때 커널이 디스크로 밀어냄**.
- 내구성 보장은 **msync(MS_SYNC)** 또는 **fsync** 필요.

---

# **8) “지금 이 정도만 기억”**

- **write() 리턴 = 디스크에 박힘(X)**, “**페이지 캐시로 복사 완료**”일 뿐.
- **진짜 영구화**는 **fsync/FlushFileBuffers**(+ 필요 시 **디렉터리 fsync**).
- **ext4**: 지연 할당 + data=ordered 저널링, **원자적 rename** 강력.
- **NTFS**: MFT + 메타데이터 저널, **FlushFileBuffers**로 내구성.
- **성능 vs 안정성**: 캐시(빠름) ↔ fsync/flush(안전, 느림).
