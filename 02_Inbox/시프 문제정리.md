## 1. 시그널(Signal) 관련 문제 핵심 해설

### Q1. 시그널의 발생 원인 3가지

1. **커널/하드웨어 예외 (잘못된 명령 사용)**: 프로그램 내부에서 잘못된 연산을 수행하여 연산 처리 장치(CPU 등)가 예외를 던지면, 운영체제가 이를 감지하여 해당 프로세스에 시그널을 전달합니다.
	- 정수를 0으로 나누는 경우(`SIGFPE`)
	- 잘못된 메모리 주소(널 포인터 등)에 접근하는 경우(`SIGSEGV`).
2. **프로세스 간 명시적 송신 (통신 목적)**: 한 프로세스가 다른 프로세스에게 제어 목적으로 시그널을 인위적으로 보내는 경우입니다. (예: `kill()` 시스템 호출을 이용해 특정 프로세스에 시그널 전달)
	- 시스템 시그널은 모두 고유한 의미가 지정되어있다. 그 의미가 아닌 상황일때 시스템 시그널이 편하다는 이유로 오용하는 경우는 바람직하지 않다 이때는 사용자 정의 시그널 `SIGUSR1`, `SIGUSR2` 을 사용하자
3. **사용자의 하드웨어 인터럽트 키 입력**: 사용자가 터미널에서 직접 키보드로 입력하여 프로세스를 제어하는 경우입니다.
	- 프로세스 강제 종료를 뜻하는 `Ctrl + C` (`SIGINT`),
	- 코어 덤프를 생성하고 종료하는 `Ctrl + \` (`SIGQUIT`).

### Q2. 프로세스 간 통신에서 시그널을 사용하면 좋은 상황

- 데이터의 양이 많지 않고, 프로세스 간에 특정 사건(Event)이 발생했음을 신속하게 알리거나 동기화(Synchronization)를 맞추어야 할 때 가장 유용합니다.
- 무거운 IPC(공유 메모리나 소켓)를 개설하지 않고도, 비동기적으로 상대 프로세스의 상태를 제어하거나 특정 동작을 즉시 유도하고 싶을 때 적합합니다.
    

### Q3. 프로세스에서 무시(Ignore)할 수 없는 시그널

리눅스 시스템 관리 및 안정성을 위해 프로세스가 잡아내거나(`Catch`) 무시(`Ignore`)할 수 없도록 강제된 시그널이 있습니다. **기말고사 단골 객관식 문제**입니다.

- **`SIGKILL` (시그널 번호 9)**: 프로세스를 무조건 강제 종료시킵니다.
- **`SIGSTOP` (시그널 번호 19)**: 프로세스를 무조건 일시 중지시킵니다.
    

### Q4. 시그널 핸들러 실행 중 동일 시그널의 자동 블록(Block) 여부

- **네, 자동으로 블록됩니다.** * 기본적으로 어떤 시그널에 대한 핸들러가 실행되는 동안에는, **동일한 종류의 시그널이 다시 발생하더라도 즉시 전달되지 않고 커널에 의해 대기(Pending) 상태로 블록**됩니다. 핸들러 처리가 완전히 끝난 후에 대기 중이던 시그널이 전달됩니다. (이는 핸들러가 무한 루프나 꼬임 현상에 빠지는 것을 방지하기 위함입니다.)
    

### Q5. `kill()` 시스템 호출의 용도

- 함수 이름 때문에 프로세스를 죽이는 용도로만 생각하기 쉽지만, 실제 본질은 '특정 프로세스나 프로세스 그룹에 임의의 시그널을 보내는 함수'입니다.
- `kill(pid, SIGKILL)`을 보내면 프로세스를 죽이게 되지만, `kill(pid, SIGUSR1)`처럼 사용자 정의 시그널을 보내면 프로세스 간 통신(IPC) 수단으로 활용됩니다.
    

### Q6. 시그널 핸들러의 재진입 가능성(Reentrancy)과 작성 방법

- **개념**: 시그널은 비동기적으로 아무 때나 발생하므로, 메인 루틴이 어떤 함수를 실행하던 중에 갑자기 멈추고 시그널 핸들러가 실행될 수 있습니다. 이때 핸들러 내부에서 메인 루틴이 쓰던 함수를 똑같이 또 호출해도 문제가 없는 성질을 재진입 가능(Reentrant)이라고 합니다.
- **작성 방법**: 시그널 핸들러는 반드시 **비동기 시그널 안전(Async-Signal-Safe)한 함수만 사용**하도록 작성해야 합니다.
    - 핸들러 내부에서는 `malloc()`, `printf()`, `g_variables`(전역 변수)처럼 내부적으로 정적(Static) 버퍼나 락(Lock)을 공유하는 함수를 쓰면 안 됩니다. (메인 루틴이 `printf`를 하던 중 시그널이 터져 핸들러가 또 `printf`를 부르면 데드락이나 데이터 오염이 발생함)
    - 따라서 핸들러 내부에서는 오직 지역 변수만 사용하거나, `write()` 같은 로우 레벨 시스템 호출만 사용해야 안전합니다.


### **Q7.** 시그널에 대한 설명 중 틀린 것 혹은 다른 것을 고르는 문제
#### 시그널의 정의와 특징

- **개념**: 시그널은 일종의 소프트웨어적인 인터럽트(Interrupt)입니다.
- **용도**: 프로그래머 입장에서는 단순한 소프트웨어 인터럽트 처리라기보다는, **프로세스 간 통신에서 동기(Synchronization)를 맞추는 신호** 등의 용도로 활용성이 훨씬 높은 부분입니다.
- **메커니즘**: 소프트웨어적으로 발생하는 인터럽트를 운영체제가 감지하여, 해당 인터럽트가 발생한 프로세스에게 전달하는 메커니즘입니다.
- **비동기성**: 시그널은 비동기적(Asynchronous)으로 발생합니다. 즉, 프로세스가 준비되지 않은 상태일지라도 언제 어디서나 발생과 동시에 전달됩니다.

#### 시그널 수신 시 처리 방법 (기본 동작 및 핸들러)

- **기본 동작 (Default Action)**: 우리가 아무런 설정을 하지 않으면 이미 정의된 기본 동작을 수행하며, **대부분은 프로세스를 종료**하는 것입니다.
- **무시 또는 일시 중지**: 무조건 종료할 수 없는 특수한 경우(예: 하위 프로세스가 상위 프로세스를 강제 종료하려 할 때 이를 다 받아주면 운영체제 구조가 무너지므로)에는 아예 무시하거나, 잠시 중지했다가 후에 재개하는 등의 기본 동작을 수행합니다. 이는 시스템 테이블에 정의되어 있습니다. 프로세스가 모든 시그널을 무시하도록 설정하면 시그널이 아예 전달되지 않습니다.
- **시그널 핸들러(Signal Handler)**: 프로그래머가 지정된 함수를 설정하여, 특정 시그널이 오면 해당 함수를 호출하도록 만드는 방법입니다.
    - **동작 방식**: 시그널은 소프트웨어적 인터럽트이므로, 시그널을 받으면 현재 하던 작업을 딱 세이브(처리 작업을 중지)하고 시그널 핸들러를 호출하여 실행한 뒤, 핸들러가 끝나면 다시 원래 하던 일로 돌아가 계속 작업을 시작합니다.
    - **설정 함수**: 한 번만 유효한 시그널 핸들러를 설치할 수도 있고, 한 번 설정하면 모든 시그널에 대해 계속 유효하게 만들 수도 있습니다. 관련 함수로는 `sigaction()` 등 다양한 함수들이 있습니다. 함수의 세부적인 기능 자체를 외우기보다는 전반적인 개념과 처리 방식을 이해해야 합니다.

## 2. 메모리 매핑(Memory Mapping) 관련 문제 핵심 해설

### 혹시 모를 기타 문제
- #### 통신의 2가지 분류
	- IPC: **동일한 시스템(호스트)** 내부의 프로세스 간 데이터 통신.
	- 네트워크 통신: **서로 다른 시스템** 간에 네트워크를 경유하는 통신.
- #### IPC의 역사와 기술적 한계 극복
	- **초창기 유닉스 파이프**: 특수 파일이나 공통 메모리를 이용해 통신함.
	- **파일 통신의 한계와 해결 (mmap)**: 디스크 파일 I/O 속도 저하 문제를 해결하기 위해, 파일을 메모리에 매핑(`mmap`)하여 통신 속도를 획기적으로 개선함.
	- **공유 메모리의 보안 문제**: 과거처럼 임의의 특정 메모리 주소를 직접 지정하는 방식은 보안 위험이 커 현대 OS에서는 **운영체제(OS)의 통제 하에 관리**함.
	- 현대 OS는 계보(BSD/리눅스)와 상관없이 **System V IPC를 완벽히 지원**한다
- 대용량 데이터 전송뿐만 아니라, **시그널이나 세마포어 상태 값 같은 단순한 정수형 데이터를 주고받으며 동기화를 맞추는 것**도 넓은 의미의 IPC에 포함됨.
- #### 네트워크 통신
	- 요즘엔 TCP/IP가 표준이며, 소켓라이브러리만 사용한다

### Q1. `mmap()` 시스템 호출을 사용하는 목적과 용도

- **성능 최적화**: 일반적인 파일 입출력인 `read()`, `write()`는 커널 공간의 버퍼와 유저 공간의 버퍼 간에 데이터를 복사하는 과정(콘테스트 스위칭)이 필요합니다. 반면 `mmap()`은 파일의 내용을 유저 가상 메모리 공간에 직접 매핑하므로 이 복사 과정이 생략되어 **대용량 파일 읽기/쓰기 속도가 획기적으로 빨라집니다.**
- **편의성**: 파일을 열어 포인터나 배열 다루듯이 메모리 주소 접근 방식(`ptr[i] = 'A'`)으로 다룰 수 있어 코드가 직관적이고 심플해집니다.
- **프로세스 간 공유 (IPC)**: 동일한 파일을 여러 프로세스가 `mmap()`으로 공유 매핑하면, 강력한 메모리 공유 기반의 통신이 가능해집니다.

### Q2. `msync()` 시스템 호출의 용도

- `mmap()`을 통해 메모리의 내용을 변경하더라도, 운영체제는 효율성을 위해 이를 즉시 하드디스크(파일)에 저장하지 않고 메모리(지저분한 페이지, _Dirty Page_)에만 유지할 때가 많습니다.
- **`msync()`는 메모리에 변경된 내용을 물리적인 디스크 파일과 강제로 동기화(즉시 저장)시켜 주는 함수**입니다. 시스템이 갑자기 다운되더라도 데이터가 유실되지 않도록 보장하는 안전장치 역할을 합니다.
    
### **Q3.** 메모리 매핑에 대한 설명 중 옳은 것 혹은 틀린 것을 고르는 문제 대비
- **개념**: 예전에는 공유된 파일을 동시에 오픈(`open`)하고 그것을 라이트(`write`)하는 방식을 썼지만, 메모리 매핑은 파일 자체를 직접 핸들링하지 않습니다. **파일 자체와 메모리를 일대일로 매핑(Mapping)시켜서 메모리를 직접 액세스하면, 그것이 파일에 자동으로 적용되는 방식**을 취합니다.
- **기본 프로세스**:
    1. 열린 파일을 `mmap()`이라는 함수를 이용해 메모리에 매핑합니다.
    2. 매핑된 메모리 영역(포인터나 배열 개념으로 선언된 영역)의 데이터를 대상으로 작업을 수행합니다. 예를 들어 캐릭터 포인터(`char*`)가 있다면 포인터의 주소만 변경해서 메모리 값을 쉽게 읽어올 수 있습니다.
    3. `read()`나 `write()` 같은 파일 입출력 함수를 번거롭게 이용하지 않고 직접 메모리를 제어할 수 있으며, **메모리 매핑을 한 후에는 파일을 클로즈(`close`)해도 변경된 내용이 파일에 계속 적용**됩니다.



## 1. 파이프 (Pipe) 관련 문제 정답 및 해설

### Q1. 파이프에 대한 일반적인 설명 중 옳은 것과 틀린 것 (객관식 대비)

- 파이프는 파일 시스템 상에서 일종의 파일로 취급되며, `ls -l` 명령어 시 파일 유형이 `p`로 표시된다.
- 파이프는 데이터의 경계가 없는 **스트림(Stream) 기반**으로 동작한다.
- **이름 없는 파이프 (Anonymous Pipe) 메커니즘**:
    - 모든 프로세스는 이 파이프를 이용해 통신할 수 있습니다. 파이프 통신을 하려면 먼저 `pipe()` 시스템 호출 함수를 사용해야 합니다.
    - `pipe()` 함수를 호출하면 하나는 **읽기 전용(`fd[0]`)**, 다른 하나는 쓰기 전용(`fd[1]`)입니다.
- **틀린 개념 (오답 선지 예시)**:
    - "파이프는 양방향 통신이 기본이므로 하나의 파이프로 부모와 자식이 동시에 읽고 쓸 수 있다." ($\rightarrow$ **X**, 동시에 쓰면 데이터가 꼬이거나 읽지 못함)
    - "이름 없는 파이프는 네트워크를 통해 서로 다른 컴퓨터에 있는 프로세스 유입이 가능하다." ($\rightarrow$ **X**, 동일 호스트 내에서만 가능)

### Q2. `pipe()` 시스템 호출 시 리턴되는 2개의 파일 기술자(FD) 배열의 역할

- `pipe(int fd[2])` 함수가 성공하면 파이프가 생성되면서 크기가 2인 정수형 배열에 두 개의 파일 기술자(FD)를 넣어 리턴해 줍니다.
    - **`fd[0]`**: **읽기 전용 (Read End)** 파이프 출구
    - **`fd[1]`**: **쓰기 전용 (Write End)** 파이프 입구
- _암기 팁: 0은 입력(가장 먼저 읽음), 1은 출력(가장 먼저 씀)_
### Q3. 이름 없는 파이프(Anonymous)와 이름 있는 파이프(Named, FIFO)의 사용 상황 비교

- **이름 없는 파이프**: 부모-자식 프로세스처럼 **혈연관계(상속 관계)가 있는 프로세스 간 통신**에 사용됩니다. `fork()`를 하기 전에 생성해야 자식이 파일 기술자를 복사받을 수 있기 때문입니다.
- **이름 있는 파이프 (FIFO)**: 파일 시스템에 실제 이름(경로명)이 존재하므로, **아무런 혈연관계가 없는 완전히 독립된 프로세스 간 통신**에 사용됩니다.

### Q4. 파이프 사용에 적합한 시나리오와 적합하지 않은 시나리오 (서술형/선택형)

- **적합한 시나리오**: 한 프로세스의 출력이 다른 프로세스의 입력으로 곧바로 이어지는 **단방향 데이터 스트림 필터링 작업**에 적합합니다. (예: 쉘 명령어 `ls -l | grep .txt`)
- **적합하지 않은 시나리오**: 빈번하게 주고받아야 하는 대용량 복잡한 **양방향 통신**, 혹은 특정 메시지 단위로 끊어서 데이터를 처리해야 하는 구조화된 데이터 통신에는 적합하지 않습니다. (이 경우 공유 메모리나 메시지 큐가 적합)
    

## 2. System V IPC 관련 문제 정답 및 해설

### Q1. 메시지 큐와 공유 메모리의 개념 및 컨셉 비교

- **메시지 큐**: 파이프와 달리 데이터를 시냇물처럼 보내지 않고, 고정된 크기의 메시지 단위(패킷 단위)로 쪼개어 우편함에 넣듯 통신합니다. 경계가 명확하므로 읽는 쪽에서 메시지별로 끊어 읽기 편합니다.
- **공유 메모리**: 커널 공간을 거치지 않고 프로세스들이 동일한 물리 메모리 공간을 직접 공유하므로 복사 과정이 생략됩니다. **모든 IPC 방식 중 데이터 전송 속도가 가장 빠르다는 장점**이 있습니다.
    

### Q2. 독립된 프로세스 간 공유 메모리 통신 시 데이터 오염을 막기 위한 동기화 기법

- **정답: 세마포어 (Semaphore)**
- 여러 프로세스가 공유 메모리에 동시에 접근해 데이터를 수정하면 race condition(경쟁 상태)으로 데이터가 유실되거나 오염됩니다. 이를 막기 위해 진입 순서를 제어하는 세마포어를 함께 연동하여 사용해야 합니다.
    

### Q3. Talker와 Listener 예제 소스코드 흐름 분석 (과제 연계)

- **Talker (송신측/서버역할)**: `ftok()`으로 키 생성 $\rightarrow$ `shmget()`으로 공유 메모리 객체 생성 $\rightarrow$ `shmat()`로 프로세스에 메모리 첨부(Attach) $\rightarrow$ 메모리에 데이터 쓰기.
- **Listener (수신측/클라이언트역할)**: 동일한 키값으로 `shmget()` 및 `shmat()` 수행 $\rightarrow$ 메모리에 적힌 내용 읽기 $\rightarrow$ `shmdt()`로 분리(Detach) $\rightarrow$ 필요시 `shmctl(IPC_RMID)`로 자원 삭제.
    

### Q4. 유닉스/리눅스 시스템에서 세마포어(Semaphore)를 사용하는 본질적인 주된 목적

- **정답: 상호 배제(Mutual Exclusion) 및 프로세스 간 동기화(Synchronization)**
- 여러 프로세스가 한정된 공유 자원(공유 메모리, 하드웨어 등)에 한 번에 하나씩만 순서대로 접근할 수 있도록 통제하여 임계 영역(Critical Section)을 보호하기 위함입니다.
    

### Q5. 세마포어 제어를 위한 `semop()` 시스템 호출 함수가 수행하는 구체적인 작업 내용

- **정답: 세마포어 값의 변경(감소 또는 증가)을 통한 잠금(P) 및 해제(V) 연산 수행**
- `semop()` 구조체 배열에 원하는 연산 값(`-1` 또는 `+1`)을 설정하여 커널에 요청합니다. 값이 0 이하일 때 `-1` 연산을 요청하면 프로세스는 블록(대기) 상태가 되며, 다른 프로세스가 `+1` 연산으로 자원을 반납하면 대기 중인 프로세스를 깨워 진입시킵니다.
    

## 3. 네트워크 소켓 프로그래밍 관련 문제 정답 및 해설

### Q1. 소켓(Socket)의 명확한 정의와 프로그래밍을 위해 알고 있어야 하는 정보

- **소켓의 정의**: 네트워크 통신의 종착점(Endpoint)으로, **[IP 주소 + 포트(Port) 번호]의 결합체**입니다.
- **알고 있어야 하는 정보**:
    
    1. 상대방 혹은 나의 **IP 주소** (컴퓨터의 위치)
    2. 통신 대상 프로세스의 **포트 번호** (프로세스 구별 번호)
    3. 사용할 **프로토콜 종류** (TCP 또는 UDP 등)
        

### Q2. 소켓 주소 구조체 (`struct sockaddr_in`)에 포함된 정보

인터넷 소켓 프로그래밍에서 주소를 지정할 때 쓰는 핵심 구조체입니다. 다음 3가지 주 항목이 포함됩니다.

1. `sin_family`: 주소 체계 패밀리 (인터넷이므로 무조건 **`AF_INET`**)
2. `sin_port`: 16비트 **포트 번호** (반드시 네트워크 바이트 순서 `htons()`로 변환하여 대입)
3. `sin_addr.s_addr`: 32비트 **IP 주소** (문자열 IP 주소를 `inet_addr()` 등을 이용해 바이너리로 변환하여 대입)
    

### Q3. `socket()` 시스템 호출이 성공적으로 수행되었을 때 커널로부터 최종적으로 반환되는 것

- **정답: 소켓 파일 기술자 (Socket File Descriptor, 정수값)**
- 리눅스에서는 소켓도 파일의 일종으로 취급하므로, 성공 시 일반 파일 입출력에서 사용하는 것과 같은 형태의 파일 기술자(FD) 양수 값을 반환합니다. 실패 시 `-1`을 반환합니다.
    

### Q4. 소켓 생성 시 타입을 `SOCK_STREAM`과 `SOCK_DGRAM`으로 설정했을 때의 각각의 의미와 매칭 프로토콜

- **`SOCK_STREAM`**: **TCP 프로토콜**을 의미합니다. 연결 지향형이며 데이터의 분실 없이 신뢰성 있고 안정적인 바이트 스트림 통신을 보장합니다.
- **`SOCK_DGRAM`**: **UDP 프로토콜**을 의미합니다. 비연결형이며 데이터그램 단위로 독립적으로 전송합니다. 신뢰성은 낮지만 전송 속도가 빠릅니다.
    

### Q5. TCP 서버와 클라이언트의 소켓 함수 호출 순서 플로우 차트 (빈칸 채우기 무조건 출제)

반드시 다음 순서 전체를 외우셔야 빈칸 채우기 문제를 맞출 수 있습니다.

- **서버(Server) 호출 순서**:
    
    1. `socket()` : 소켓 생성
    2. `bind()` : IP/Port 번호 결합 (서버 소켓에 주소 부여)
    3. `listen()` : 연결 요청 대기 상태 설정 (클라이언트 접속을 받을 준비)
    4. `accept()` : 클라이언트 연결 요청 수락 (실제 통신용 소켓 생성 및 블로킹)
    5. `recv()` / `send()` : 데이터 송수신
    6. `close()` : 소켓 종료
        
- **클라이언트(Client) 호출 순서**:
    
    1. `socket()` : 소켓 생성
    2. `connect()` : 서버에 연결 요청 (서버의 `accept()`와 연결됨)
    3. `send()` / `recv()` : 데이터 송수신
    4. `close()` : 소켓 종료
