## 1. [Topic: 유닉스 및 리눅스의 역사와 계보]
> 고성능 서버 환경, 임베디드 시스템, 또는 하드웨어를 직접 제어해야 하는 로우 레벨 소프트웨어 개발 시를 위해 리눅스를 배우자
- **Definition:** 1969년 AT&T 벨 연구소에서 시작된 유닉스(UNIX)와 그 철학을 계승하여 오픈소스로 발전한 리눅스(Linux)의 발전 과정.
- **Why in OS:** 현대 서버 및 모바일 운영체제(Android, iOS)의 근간을 이루는 아키텍처를 이해함으로써 시스템 프로그래밍의 환경적 맥락을 파악하기 위함입니다.

### 🏗️ 동작 원리 및 계보 상세

- **기원:** 켄 톰슨과 데니스 리치가 어셈블리어로 개발 후, 1973년 **C 언어**로 재작성하며 이식성이 비약적으로 향상됨.
- **주요 계보:**
    - **System V:** AT&T 기반의 상용 유닉스 정통 계보 (현 오라클 솔라리스 등).
    - **BSD:** 버클리 대학에서 발전시킨 계열로, **TCP/IP** 네트워크 기능을 최초로 통합함 (현 macOS, iOS의 기반).
    - **Linux:** 리누스 토발즈가 미닉스(Minix)를 참고하여 만든 오픈소스 커널. 다양한 배포판(Ubuntu, CentOS 등)으로 발전.
- **모바일 OS:** 안드로이드는 리눅스 커널 기반, iOS는 BSD/NextStep 계열 유닉스 기반임.

## 2. [Topic: 시스템 프로그래밍 표준 (POSIX & FHS)]

- **Definition:** 서로 다른 유닉스/리눅스 시스템 간의 호환성과 이식성을 보장하기 위해 정의된 인터페이스 규격.
- **Why in OS:** 특정 OS에 종속되지 않는 하드웨어 독립적인 소프트웨어를 개발하기 위해 표준 API 준수가 필수적입니다.
    

### 🏗️ 주요 표준 및 규격

- **POSIX (Portable Operating System Interface):** IEEE가 제정한 유닉스 공통 API 표준. 리눅스는 공식 인증은 아니지만 이를 완벽히 준수함.
- **SUS (Single UNIX Specification):** 'UNIX'라는 상표권을 사용하기 위해 준수해야 하는 단일 명세.
- **ANSI C:** C 언어 자체의 문법 및 표준 라이브러리 규격.
- **LSB (Linux Standard Base):** 리눅스 배포판 간의 바이너리 호환성을 위한 표준.
- **FHS (Filesystem Hierarchy Standard):** 리눅스/유닉스의 디렉터리 구조 표준 (예: `/bin`, `/etc`, `/usr` 등 파일의 위치 정의).

## 3. [Topic: 시스템 호출(System Call) vs 라이브러리 함수]

- **Definition:**
	- **커널(Kernel):** 하드웨어를 직접 제어하는 OS의 핵심부.
	- **시스템 호출(System Call):** 응용 프로그램이 커널에게 서비스를 요청하기 위한 유일한 통로.
    - **라이브러리 함수:** 시스템 호출을 효율적으로 사용할 수 있도록 미리 컴파일하여 제공하는 함수 묶음.
- **Why in OS:**
	- 커널의 핵심 자원(CPU, 메모리, 파일)을 응용 프로그램이 무분별하게 직접 조작하면 시스템이 파괴될 수 있으므로, **인터페이스(System Call)**를 통해서만 접근하도록 제한하여 보안과 안정성을 확보합니다.

### 🏗️ 동작 원리 및 API 상세

- **내부 메커니즘:**
    - 응용 프로그램 $\rightarrow$ 라이브러리 함수(선택) $\rightarrow$ **시스템 호출(Trap/Interrupt)** $\rightarrow$ 커널 모드 진입 $\rightarrow$ 커널 서비스 수행 $\rightarrow$ 사용자 모드 복귀.
- **주요 차이점:**
    - 시스템 호출은 커널의 기능을 수행하므로 **모드 전환(User $\leftrightarrow$ Kernel Mode Switching)** 오버헤드가 발생합니다.
    - 라이브러리 함수는 프로그래머의 편의를 위해 표준 C 라이브러리(`libc`) 등에서 제공하며, 내부적으로 시스템 호출을 포함하거나 포함하지 않을 수 있습니다.

## 4. [Topic: man(Manual) 페이지 활용 및 섹션 구분]

- **Definition:** 리눅스 터미널에서 명령어, 함수, 설정 파일 등에 대한 상세 설명을 제공하는 내장 도움말 시스템.
- **Why in OS:** 방대한 시스템 API의 인자값, 반환값, 필요 헤더 파일 등을 네트워크 연결 없이도 즉시 확인하기 위해 필수적입니다.

### 🏗️ man 페이지 섹션 구성

리눅스 매뉴얼은 정보의 성격에 따라 8개 이상의 섹션으로 구분됩니다.

|**섹션 번호**|**주요 내용**|**예시**|
|---|---|---|
|**Section 1**|일반 사용자 명령어 (User Commands)|`ls`, `cp`, `mv`, `uname`|
|**Section 2**|**시스템 호출 (System Calls)**|`open()`, `fork()`, `read()`|
|**Section 3**|**C 라이브러리 함수 (Library Functions)**|`printf()`, `fopen()`, `malloc()`|

### 💻 실제 실습 구현

**1) 동일 이름의 명령어와 시스템 호출 구분 확인**

명령어 `uname`과 시스템 호출 `uname()`은 이름이 같지만 섹션이 다릅니다.

```bash
# 1. 섹션 1: 일반 명령어 uname 확인
$ man uname  # 기본적으로 가장 낮은 섹션인 1이 출력됨

# 2. 섹션 2: 시스템 호출 uname 확인
$ man 2 uname
```

- **결과 분석:** `man 2 uname` 실행 시 상단에 **"LINUX PROGRAMMER'S MANUAL"** 문구와 함께 시스템 호출(Section 2)에 대한 C 언어 프로토타입(`int uname(struct utsname *buf);`)이 출력됩니다.

> [!faq]- Q. 시스템 호출(System Call)과 일반 라이브러리 함수의 가장 큰 차이점은 무엇인가요?
>
> **🗣️ 핵심 답변:** 가장 큰 차이는 **커널 모드로의 진입 여부**입니다. 시스템 호출은 하드웨어 자원 접근을 위해 CPU가 사용자 모드에서 커널 모드로 전환되는 과정이 발생하지만, 일반 함수는 프로세스의 사용자 주소 공간 내에서만 실행됩니다.
>
> **📚 꼬리질문 대비:** 모드 전환(Context Switching과 유사한 맥락)은 비용이 발생하는 작업이므로, 빈번한 시스템 호출은 프로그램 성능을 저하시킬 수 있습니다. 이를 최적화하기 위해 표준 입출력 라이브러리(Standard I/O)는 내부적으로 버퍼링을 사용합니다.
>
> 라이브러리의 버퍼링: 유저영역의 버퍼에다가 데이터를 모았다가 버퍼가 가득차면 그제서야 시스템 호출을 한번 호출

> [!faq]- Q. POSIX 표준이 왜 중요한가요?
>
> **🗣️ 핵심 답변:** **소스 코드 수준의 이식성(Portability)** 때문입니다. POSIX 표준을 준수하여 작성된 C 코드는 리눅스에서 유닉스, 또는 macOS로 옮겨가더라도 별도의 수정 없이 컴파일 및 실행이 가능해집니다.

## 1. [Topic: 시스템 프로그래밍의 에러 처리 매커니즘]

- **Definition:** 시스템 호출이나 라이브러리 함수가 실패했을 때, 커널이나 라이브러리가 기록하는 에러 번호(`errno`)를 해석하여 사용자에게 유의미한 정보를 제공하는 과정.
- **Why in OS:** 시스템 레벨에서는 파일 부재, 권한 부족 등 다양한 예외 상황이 발생하므로, 디버깅과 프로그램의 안정적 종료를 위해 정확한 에러 분석이 필수적입니다.
    

### 🏗️ 동작 원리 및 API 상세

- **에러 리턴값의 규칙:**
    - **시스템 호출:** 성공 시 0 또는 양수, 실패 시 **-1**을 반환.
    - **라이브러리 함수:** 실패 시 **NULL(0)** 을 반환.
- **에러 확인 도구:**
    
    1. **`errno` (전역 변수):** 마지막으로 발생한 에러 번호가 저장됨. `<errno.h>` 헤더 필요.
    2. **`perror(const char *s)`:** 표준 에러(stderr)로 "사용자 문자열: 에러 메시지" 형태로 즉시 출력.
    3. **`strerror(int errnum)`:** 에러 번호를 해당되는 메시지 문자열(String)로 변환하여 반환 (가공 출력 시 유리).

 ![정리](라이브러리%20함수의%20에러처리.md#정리)

### 💻 실제 실습 구현 (`error_test.c`)

**1) Source Code**

```C
#include <stdio.h>
#include <unistd.h>   // 이 안에 access()가 들어있음
#include <errno.h>    // errno 사용을 위한 헤더
#include <string.h>   // strerror 사용을 위한 헤더
#include <stdlib.h>

extern int errno;     // 전역 에러 변수 errno 선언

int main() {
    // 존재하지 않는 파일에 접근 시도 (F_OK: 존재 여부 확인)
    if (access("test.txt", F_OK) == -1) {
        // 방법 1: errno 직접 출력
        printf("Error Number: %d\n", errno);

        // 방법 2: perror 사용 (가장 간편)
        perror("Access failed");

        // 방법 3: strerror 사용 (메시지 가공)
        char *msg = strerror(errno);
        printf("Custom Error Message: %s (Code: %d)\n", msg, errno);
        
        exit(1);
    }
    return 0;
}
```

- **`access()`** : 로그인한 사용자 권한으로 파일에 접근하는 시스템 호출
	- **`F_OK`**: **Existence test**. 파일의 **존재 여부**만 체크하라는 플래그
	- 시스템 호출이므로 성공시 0, 실패시 -1를 반환뒤 errno에 오류이유번호를 적어둠

**2) 컴파일 및 실행 결과**

```bash
$ gcc -o error_test error_test.c
$ ./error_test

# 실행 결과 (test.txt가 없을 때)
Error Number: 2
Access failed: No such file or directory
Custom Error Message: No such file or directory (Code: 2)
```

## 2. [Topic: 빌드 시스템 - gcc와 Makefile]

- **Definition:** 텍스트 소스 코드를 실행 가능한 바이너리로 변환하는 과정과 이를 효율적으로 관리하는 자동화 도구.
- **Why in OS:** 대규모 시스템 프로그래밍에서는 수많은 소스 파일을 일일이 컴파일하기 어렵기 때문에, 변경된 파일만 추적하여 빌드하는 `make` 유틸리티가 필수적입니다.

### 🏗️ 주요 도구 및 옵션

- **gcc 핵심 옵션:**
    - `-o [파일명]`: 출력 실행 파일의 이름을 지정 (미지정 시 `a.out`).
    - `-c`: 링크 과정을 생략하고 오브젝트 파일(`.o`)만 생성.
- **Makefile 구조:**
    - **Target (대상):** 빌드 결과물.
    - **Dependencies (의존성):** 대상 생성에 필요한 소스나 오브젝트 파일.
    - **Recipe (명령어):** 빌드를 수행하는 쉘 명령어 (반드시 **Tab**으로 들여쓰기).

 ![📝 정리](목적파일과%20실행파일의%20차이와%20명령어와%20Makefile%20빌드%20시스템.md#📝%20정리)

### 💻 실제 실습 구현 (`Makefile` 예시)

```Makefile
# 변수 설정
CC = gcc
CFLAGS = -Wall
OBJS = main.o add.o
TARGET = add.out

# 최종 타겟 빌드 규칙
$(TARGET): $(OBJS)
	$(CC) -o $(TARGET) $(OBJS)

# 개별 소스 컴파일 규칙
main.o: main.c
	$(CC) $(CFLAGS) -c main.c

add.o: add.c
	$(CC) $(CFLAGS) -c add.c

# 정리 규칙
clean:
	rm -f $(OBJS) $(TARGET)
```

## 3. [Topic: 동적 메모리 할당 (Dynamic Memory Allocation)]

- **Definition:** 프로그램 실행 중(Runtime) 필요한 만큼의 메모리 크기를 결정하여 힙(Heap) 영역으로부터 할당받는 방식.
- **Why in OS:** 컴파일 타임에 크기를 알 수 없는 가변적인 데이터(예: 사용자 입력 데이터, 파일 내용 등)를 효율적으로 처리하고 메모리 낭비를 줄이기 위해 사용합니다.
    

### 🏗️ API 상세 및 비교

### 💻 실제 실습 구현 (`memory.c`)

**1) Source Code**

```C
#include <stdio.h>
#include <stdlib.h> // 메모리 할당 함수 포함

int main() {
    int *ptr;
    int n = 200;

    // 정수 200개를 저장할 메모리 동적 할당
    ptr = (int *)malloc(n * sizeof(int));

    if (ptr == NULL) {
        perror("Memory allocation failed");
        return 1;
    }

    // 실습 핵심: 사용 후 반드시 해제
    free(ptr);
    
    return 0;
}
```

## 4. [Topic: 명령행 인자 처리 (Command Line Arguments)]

- **Definition:** 프로그램을 실행할 때 터미널에서 함께 입력하는 옵션이나 데이터를 `main()` 함수가 전달받는 매커니즘.
- **Why in OS:** `ls -l`이나 `gcc -o` 처럼 프로그램의 동작 방식을 실행 시점에 유연하게 제어하기 위함입니다.
    

### 🏗️ API 스펙 (`main` 함수 구조)

```C
int main(int argc, char *argv[])
```

- **`argc` (Argument Count):** 인자의 총 개수 (프로그램 이름 포함).
- **`argv` (Argument Vector):** 인자 문자열들의 배열.
    - `argv[0]`: 실행 파일의 경로/이름.
    - `argv[1]`~: 사용자가 입력한 실제 옵션 및 데이터.
        

### 💻 실제 실습 구현 (`arg_test.c`)

**1) Source Code**

```C
#include <stdio.h>

int main(int argc, char *argv[]) {
    printf("Total arguments: %d\n", argc);

    for (int i = 0; i < argc; i++) {
        printf("argv[%d]: %s\n", i, argv[i]);
    }

    return 0;
}
```

**2) 컴파일 및 실행 결과**

```bash
$ gcc -o arg_test arg_test.c
$ ./arg_test -h 2000

# 실행 결과
Total arguments: 3
argv[0]: ./arg_test
argv[1]: -h
argv[2]: 2000
```

## 1. [Topic: 리눅스 파일 시스템과 아이노드(inode)]

- **Definition:** 리눅스에서 모든 개체는 파일로 취급되며, 각 파일의 메타데이터(권한, 소유자, 크기 등)를 관리하는 고유한 자료 구조가 **아이노드(inode)**입니다.
- **Why in OS:** 파일명이 아닌 고유 번호(inode number)를 통해 파일을 식별함으로써 파일 시스템의 효율성과 유연성(심볼릭 링크 등)을 확보합니다.
    

### 🏗️ 동작 원리 및 구성

- **파일의 3요소:**
    
    1. **파일명:** 사용자가 식별하는 이름.
    2. **아이노드(inode):** 파일의 종류, 권한, 소유자, 시간 정보, **데이터 블록의 주소** 등을 포함하는 테이블.
    3. **데이터 블록:** 실제 데이터(텍스트, 바이너리 등)가 저장되는 하드디스크 공간.
        
- **디렉터리 파일:** 디렉터리 역시 파일의 일종으로, 해당 디렉터리에 속한 **[파일명 - 아이노드 번호]**의 매핑 리스트를 데이터 블록으로 가집니다.

## 2. [Topic: 디렉터리 생성 및 삭제 (`mkdir`, `rmdir`)]

- **Definition:** 새로운 디렉터리를 생성하거나 비어 있는 디렉터리를 제거하는 시스템 호출입니다.
- **Why in OS:** 프로세스 실행 중 동적으로 작업 공간을 확보하거나 정리하기 위해 필요합니다.
    

### 🏗️ API 상세

- **`mkdir(const char *pathname, mode_t mode)`**
    - **인자:** 경로명, 접근 권한(예: `0755`). _C언어에서 8진수는 숫자 앞에 '0'을 붙임._
    - **반환:** 성공 시 0, 실패 시 -1 (`errno` 설정).
- **`rmdir(const char *pathname)`**
    - **특징:** 디렉터리가 반드시 **비어 있어야** 삭제 가능합니다.
        

### 💻 실제 실습 구현 (`mkdir_test.c`)

**1) Source Code**

```C
#include <sys/stat.h>
#include <sys/types.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    // 0755(rwxr-xr-x) 권한으로 'suwon' 디렉터리 생성
    if (mkdir("suwon", 0755) == -1) {
        perror("mkdir");
        exit(1);
    }
    printf("Directory 'suwon' created successfully.\n");
    return 0;
}
```

## 3. [Topic: 현재 작업 디렉터리 관리 (`getcwd`, `chdir`)]

- **`getcwd`**: 현재 프로세스의 절대 경로를 `buf`에 복사합니다. (Library)
- **`chdir`**: 프로세스의 현재 작업 디렉토리(CWD)를 지정한 `path`로 직접 변경합니다.(System Call)
- **Why in OS:** 모든 상대 경로는 현재 작업 디렉터리(CWD)를 기준으로 해석되므로, 상대 경로를 사용하여 파일에 접근할 때 기준점이 되는 위치를 제어하기 위함입니다.
    

### 🏗️ API 상세

#### **`getcwd(char *buf, size_t size)`**
- 마지막의 널 문자(`\0`)를 포함하여 총 `size`만큼의 데이터를 `buf`에 저장합니다.
	- **Return:** 성공 시 `buf`의 시작 주소 반환, 실패 시 `NULL` 반환.
- 사용 후 `free()` 필수
- **`chdir(const char *path)`**
    - 프로세스의 현재 작업 디렉터리를 `path`로 변경합니다.
    - **주의:** 프로그램 종료 후 쉘의 위치는 변하지 않으며, 해당 프로세스 내부에서만 유효합니다.
    - System Call

### 💻 실제 실습 구현 (`chdir_test.c`)

**1) Source Code**

```C
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    char *cwd;
    // 메모리 자동 할당 방식으로 현재 경로 가져오기
    cwd = getcwd(NULL, 0);
    printf("Current: %s\n", cwd);

    if (chdir("suwon") == -1) {
        perror("chdir");
    } else {
        free(cwd);
        cwd = getcwd(NULL, 0);
        printf("Moved to: %s\n", cwd);
    }
    free(cwd);
    return 0;
}
```

## 4. [Topic: 디렉터리 탐색 및 내용 읽기]

- **Definition:** 특정 디렉터리 내부에 포함된 파일 리스트와 각 파일의 기본 정보(아이노드 번호 등)를 순차적으로 읽어오는 과정입니다.
- **Why in OS:** `ls` 명령어를 구현하거나, 특정 디렉터리 내의 파일들을 전수 조사하여 처리(백업, 검색 등)해야 할 때 사용합니다.
    

### 🏗️ API 및 구조체 상세

- **`DIR *opendir(const char *name)`**: 디렉터리를 열고 디렉터리 스트림(자료구조)의 포인터를 반환합니다. (실패 시 `NULL`)
- **`struct dirent *readdir(DIR *dirp)`**: 디렉터리 내의 항목을 하나씩 읽어옵니다. 더 이상 읽을 항목이 없으면 `NULL`을 반환합니다.
- **`struct dirent` 구조체 주요 멤버:**
    - `d_ino`: 파일의 아이노드 번호.
    - `d_name`: 파일의 이름 (문자열).
        

### 💻 실제 실습 구현 (`dir_list.c`)

**1) Source Code**

```C
#include <dirent.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    DIR *dp;
    struct dirent *dent;

    // 현재 디렉터리(.) 열기
    if ((dp = opendir(".")) == NULL) {
        perror("opendir");
        exit(1);
    }

    // 디렉터리 끝까지 반복해서 읽기
    while ((dent = readdir(dp)) != NULL) {
        printf("Name: %-20s  |  Inode: %ld\n", dent->d_name, dent->d_ino);
    }

    closedir(dp);
    return 0;
}
```

## 5. [Topic: 디렉터리 오프셋 및 위치 제어]

- **Definition:** 디렉터리 스트림에서 읽기 위치(Offset)를 확인하거나, 특정 위치로 되돌리는 기능입니다.
- **Why in OS:** 파일 리스트를 한 번 읽은 후 다시 처음부터 읽어야 하거나(`rewind`), 특정 지점으로 점프하여 탐색해야 할 때 활용합니다.
    

### 🏗️ 주요 함수

- **`telldir(DIR *dirp)`**: 현재 읽고 있는 위치(오프셋)를 반환합니다.
- **`seekdir(DIR *dirp, long loc)`**: 지정된 위치(`loc`)로 읽기 위치를 이동시킵니다.
- **`rewinddir(DIR *dirp)`**: 읽기 위치를 디렉터리의 **가장 처음**으로 되돌립니다.

### 📝 과제 2: 위치 저장 및 복귀 (Save & Return)

- **요구사항:** 현재 위치 저장 $\rightarrow$ 다른 곳으로 이동하여 작업 $\rightarrow$ 다시 원래 위치로 복귀.
- **핵심 로직:**
    
    1. `char *start_path = getcwd(NULL, 0);` (현재 위치 기억)

>     
> - **결과:** `-1` 반환 및 `errno` 세팅.
>     
> - **Solution:** `perror("rmdir")` 호출 시 **"No such file or directory"** 메시지 출력 확인.

> [!faq]- Q. 리눅스에서 "모든 것은 파일이다"라는 말의 의미와 디렉터리의 관계는?
>
> **🗣️ 핵심 답변:** 리눅스는 하드웨어 장치(특수 파일)와 디렉터리까지 모두 동일한 파일 인터페이스(Open, Read, Write, Close)를 통해 관리한다는 뜻입니다. 디렉터리 역시 파일의 일종이며, 단지 그 데이터 블록에 **'하위 파일들의 이름과 아이노드 번호 목록'**이 담겨 있을 뿐입니다.

> **📚 꼬리질문 대비:** 따라서 디렉터리에 대한 접근 권한(`r, w, x`) 중 `x`(실행) 권한은 해당 디렉터리 내부로 진입(cd)할 수 있는 권한을 의미하게 됩니다.

>

## 🎯 최종 요약 - 시스템 프로그래밍 2026.03.12

### 🔑 오늘의 핵심 System Call & 개념

- **에러 처리 3인방**:
    - `errno`: 마지막 에러 번호를 저장하는 전역 변수.
    - `perror()`: 사용자 메시지와 함께 에러 내용을 즉시 표준 에러로 출력.
    - `strerror()`: 에러 번호를 문자열로 반환하여 자유롭게 가공 가능.
- **디렉터리 제어 API**:
    - `mkdir()` / `rmdir()`: 디렉터리 생성 및 삭제 (삭제 시 비어 있어야 함).
    - `chdir()` / `getcwd()`: 현재 작업 디렉터리 이동 및 경로 확인.
    - `opendir()` / `readdir()`: 디렉터리 내부 파일 리스트(이름, inode 등)를 순차적으로 탐색.
- **아이노드(inode)**: 리눅스 파일 시스템의 핵심으로, 파일명은 사용자를 위한 별명일 뿐 실제 모든 파일 정보(권한, 데이터 주소 등)는 고유 번호인 아이노드에서 관리됨.
    

### 💡 교수님 강조 포인트

- **커널과 사용자 사이의 통로**: 시스템 프로그래밍의 본질은 **시스템 호출(System Call)**을 통해 보호된 커널 자원에 접근하는 것입니다. `man` 페이지의 **Section 2**가 시스템 호출임을 기억하세요.
- **컴파일 효율성**: 소스 파일이 많아질수록 `gcc`를 직접 치는 것은 비효율적입니다. 파일의 의존성을 파악해 변경된 부분만 빌드하는 **Makefile**의 구조(Target-Dependency-Recipe)를 익히는 것이 중요합니다.
- **메모리 책임**: `malloc()`이나 `getcwd(NULL, 0)` 등 시스템으로부터 할당받은 힙 메모리는 반드시 **`free()`**를 통해 반납해야 메모리 누수(Leak)를 방지할 수 있습니다.
- **경로의 이해**: 실행 파일 실행 시 `./`를 붙이는 이유는 보안상의 이유로 현재 디렉터리가 기본 실행 경로(`$PATH`)에 포함되어 있지 않기 때문입니다.
