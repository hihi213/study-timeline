## 1. [Topic: 유닉스 및 리눅스의 역사와 계보]
> 고성능 서버 환경, 임베디드 시스템, 또는 하드웨어를 직접 제어해야 하는 로우 레벨 소프트웨어 개발 시를 위해 리눅스를 배우자
- **Definition:** 1969년 AT&T 벨 연구소에서 시작된 유닉스(UNIX)와 그 철학을 계승하여 오픈소스로 발전한 리눅스(Linux)의 발전 과정.
- **Why in OS:** 현대 서버 및 모바일 운영체제(Android, iOS)의 근간을 이루는 아키텍처를 이해함으로써 시스템 프로그래밍의 환경적 맥락을 파악하기 위함입니다.

### 🏗️ 동작 원리 및 계보 상세

- **기원:** 켄 톰슨과 데니스 리치가 어셈블리어로 개발 후, 1973년 **C 언어**로 재작성하며 이식성이 비약적으로 향상됨.
- **주요 계보:**
    - **System V:** AT&T 기반의 상용 유닉스 정통 계보 (현 오라클 솔라리스 등).
    - **BSD:** 버클리 대학에서 발전시킨 계열로, **TCP/IP** 네트워크 기능을 최초로 통합함 (현 macOS, iOS의 기반).
    - **Linux:** 리누스 토발즈가 미닉스(Minix)를 참고하여 만든 오픈소스 커널. 다양한 배포판(Ubuntu, CentOS 등)으로 발전.
- **모바일 OS:** 안드로이드는 리눅스 커널 기반, iOS는 BSD/NextStep 계열 유닉스 기반임.

## 2. [Topic: 시스템 프로그래밍 표준 (POSIX & FHS)]

- **Definition:** 서로 다른 유닉스/리눅스 시스템 간의 호환성과 이식성을 보장하기 위해 정의된 인터페이스 규격.
- **Why in OS:** 특정 OS에 종속되지 않는 하드웨어 독립적인 소프트웨어를 개발하기 위해 표준 API 준수가 필수적입니다.
    

### 🏗️ 주요 표준 및 규격

- **POSIX (Portable Operating System Interface):** IEEE가 제정한 유닉스 공통 API 표준. 리눅스는 공식 인증은 아니지만 이를 완벽히 준수함.
- **SUS (Single UNIX Specification):** 'UNIX'라는 상표권을 사용하기 위해 준수해야 하는 단일 명세.
- **ANSI C:** C 언어 자체의 문법 및 표준 라이브러리 규격.
- **LSB (Linux Standard Base):** 리눅스 배포판 간의 바이너리 호환성을 위한 표준.
- **FHS (Filesystem Hierarchy Standard):** 리눅스/유닉스의 디렉터리 구조 표준 (예: `/bin`, `/etc`, `/usr` 등 파일의 위치 정의).

## 3. [Topic: 시스템 호출(System Call) vs 라이브러리 함수]

- **Definition:**
	- **커널(Kernel):** 하드웨어를 직접 제어하는 OS의 핵심부.
	- **시스템 호출(System Call):** 응용 프로그램이 커널에게 서비스를 요청하기 위한 유일한 통로.
    - **라이브러리 함수:** 시스템 호출을 효율적으로 사용할 수 있도록 미리 컴파일하여 제공하는 함수 묶음.
- **Why in OS:**
	- 커널의 핵심 자원(CPU, 메모리, 파일)을 응용 프로그램이 무분별하게 직접 조작하면 시스템이 파괴될 수 있으므로, **인터페이스(System Call)**를 통해서만 접근하도록 제한하여 보안과 안정성을 확보합니다.

### 🏗️ 동작 원리 및 API 상세

- **내부 메커니즘:**
    - 응용 프로그램 $\rightarrow$ 라이브러리 함수(선택) $\rightarrow$ **시스템 호출(Trap/Interrupt)** $\rightarrow$ 커널 모드 진입 $\rightarrow$ 커널 서비스 수행 $\rightarrow$ 사용자 모드 복귀.
- **주요 차이점:**
    - 시스템 호출은 커널의 기능을 수행하므로 **모드 전환(User $\leftrightarrow$ Kernel Mode Switching)** 오버헤드가 발생합니다.
    - 라이브러리 함수는 프로그래머의 편의를 위해 표준 C 라이브러리(`libc`) 등에서 제공하며, 내부적으로 시스템 호출을 포함하거나 포함하지 않을 수 있습니다.

## 4. [Topic: man(Manual) 페이지 활용 및 섹션 구분]

- **Definition:** 리눅스 터미널에서 명령어, 함수, 설정 파일 등에 대한 상세 설명을 제공하는 내장 도움말 시스템.
- **Why in OS:** 방대한 시스템 API의 인자값, 반환값, 필요 헤더 파일 등을 네트워크 연결 없이도 즉시 확인하기 위해 필수적입니다.

### 🏗️ man 페이지 섹션 구성

리눅스 매뉴얼은 정보의 성격에 따라 8개 이상의 섹션으로 구분됩니다.

|**섹션 번호**|**주요 내용**|**예시**|
|---|---|---|
|**Section 1**|일반 사용자 명령어 (User Commands)|`ls`, `cp`, `mv`, `uname`|
|**Section 2**|**시스템 호출 (System Calls)**|`open()`, `fork()`, `read()`|
|**Section 3**|**C 라이브러리 함수 (Library Functions)**|`printf()`, `fopen()`, `malloc()`|

### 💻 실제 실습 구현

**1) 동일 이름의 명령어와 시스템 호출 구분 확인**

명령어 `uname`과 시스템 호출 `uname()`은 이름이 같지만 섹션이 다릅니다.

```bash
# 1. 섹션 1: 일반 명령어 uname 확인
$ man uname  # 기본적으로 가장 낮은 섹션인 1이 출력됨

# 2. 섹션 2: 시스템 호출 uname 확인
$ man 2 uname
```

- **결과 분석:** `man 2 uname` 실행 시 상단에 **"LINUX PROGRAMMER'S MANUAL"** 문구와 함께 시스템 호출(Section 2)에 대한 C 언어 프로토타입(`int uname(struct utsname *buf);`)이 출력됩니다.

> [!faq]- Q. 시스템 호출(System Call)과 일반 라이브러리 함수의 가장 큰 차이점은 무엇인가요?
>
> **🗣️ 핵심 답변:** 가장 큰 차이는 **커널 모드로의 진입 여부**입니다. 시스템 호출은 하드웨어 자원 접근을 위해 CPU가 사용자 모드에서 커널 모드로 전환되는 과정이 발생하지만, 일반 함수는 프로세스의 사용자 주소 공간 내에서만 실행됩니다.
>
> **📚 꼬리질문 대비:** 모드 전환(Context Switching과 유사한 맥락)은 비용이 발생하는 작업이므로, 빈번한 시스템 호출은 프로그램 성능을 저하시킬 수 있습니다. 이를 최적화하기 위해 표준 입출력 라이브러리(Standard I/O)는 내부적으로 버퍼링을 사용합니다.
>
> 라이브러리의 버퍼링: 유저영역의 버퍼에다가 데이터를 모았다가 버퍼가 가득차면 그제서야 시스템 호출을 한번 호출

> [!faq]- Q. POSIX 표준이 왜 중요한가요?
>
> **🗣️ 핵심 답변:** **소스 코드 수준의 이식성(Portability)** 때문입니다. POSIX 표준을 준수하여 작성된 C 코드는 리눅스에서 유닉스, 또는 macOS로 옮겨가더라도 별도의 수정 없이 컴파일 및 실행이 가능해집니다.

## [Topic: 시스템 호출과 라이브러리 함수의 에러 처리]

### 1. 🏗️ 빌드업 (Scenario & OS Concept)

- **사용 시점(When):** 파일 접근(`access`), 파일 열기(`fopen`) 등 시스템 자원을 요청했을 때 실패 원인을 정확히 파악해야 하는 경우.
- **OS 핵심 개념:** 라이브러리는 0, 시스템 호출은 - 1이 오류다.
	* **시스템 호출(System Call):** 유저 모드에서 커널 모드로 진입하여 서비스를 요청. 실패 시 보통 `-1` 반환.
    - **라이브러리 함수:** 시스템 호출을 래핑하여 편의성 제공. 실패 시 보통 `NULL` 또는 `0` 반환.

### 2. ⚙️ System Call API (핵심 함수 및 변수)

![정리](라이브러리%20함수의%20에러처리.md#정리)

- **에러 번호 변수:** `extern int errno;` ^4063da
	- 오류코드를 해석하려면 리눅스는 `/usr/include/asm-generic/errno-base.h` 헤더파일에 정의된 주석을 확인.
	- **유닉스:**
	- 유닉스는 헤더 `/usr/include/sys/errno.h`에 선언되어 있다
- **에러 출력 함수:**
    - `void perror(const char *s);`: `s` 출력 후 콜론(`:`)과 함께 `errno`에 해당하는 메시지 자동 출력.
    - `char *strerror(int errnum);`: `errnum`에 해당하는 에러 문자열 포인터 반환 (가공 가능).

### 3. 💻 실제 실습 구현

**[Source Code (`error_test.c`)]**

- **`access()`** : 로그인한 사용자 권한으로 파일에 접근하는 시스템 호출
	- **`F_OK`**: **Existence test**. 파일의 **존재 여부**만 체크하라는 플래그
	- 시스템 호출이므로 성공시 0, 실패시 -1를 반환뒤 errno에 오류이유번호를 적어둠
```C
#include <stdio.h>
#include <unistd.h> // 이 안에 access()가 들어있음
#include <errno.h>
#include <string.h>
#include <stdlib.h>

extern int errno; // 전역 에러 변수 선언

int main() {
    if (access("test.txt", F_OK) == -1) { 
    //리턴값이 -1이면 오류 발생한것
        // 방법 1: 직접 errno 출력
        printf("Errno: %d\n", errno);

        // 방법 2: perror 사용 (표준 에러로 출력)
        perror("Error from perror");

        // 방법 3: strerror 사용하여 메시지 가공
        char *msg = strerror(errno);
        printf("Error from strerror: %s (File: test.txt)\n", msg);
    }
    return 0;
}
```

**[실행결과]**

```Plaintext
Errno: 2
Error from perror: No such file or directory
Error from strerror: No such file or directory (File: test.txt)
```

- **분석:** `errno 2`는 `ENOENT`를 의미하며, 경로 내에 파일이나 디렉토리가 없음을 나타냄.

## [Topic: GCC 컴파일 및 Makefile 빌드 시스템]

### 1. 🏗️ GCC 컴파일 및 Makefile 빌드 시스템

- **사용 시점(When):** 소스 파일이 여러 개일 때 이를 각각 컴파일하여 하나의 실행 파일로 링크해야 하거나, 변경된 파일만 효율적으로 재빌드하고 싶을 때.
- **OS 핵심 개념:** 컴파일(Object 생성)과 링크(Executable 생성) 과정의 분리.
![📝 정리](목적파일과%20실행파일의%20차이와%20명령어와%20Makefile%20빌드%20시스템.md#📝%20정리)

### 2. 💻 실제 실습 구현

**[1단계: GCC 주요 옵션]**

```Bash
# 기본 컴파일 (a.out 생성)
gcc test.c

# 출력 파일명 지정 (-o)
gcc -o my_prog test.c

# 오브젝트 파일만 생성 (-c) -> test.o 생성
gcc -c test.c
```

**[2단계: Makefile 작성 예시]**

```Makefile
# 변수 설정
CC = gcc
CFLAGS = -Wall
OBJS = main.o add.o
TARGET = add.out

# 최종 타겟 빌드 규칙
$(TARGET): $(OBJS)
	$(CC) -o $(TARGET) $(OBJS)

# 개별 소스 컴파일 규칙
main.o: main.c
	$(CC) $(CFLAGS) -c main.c

add.o: add.c
	$(CC) $(CFLAGS) -c add.c

# 정리 규칙
clean:
	rm -f $(OBJS) $(TARGET)
```

> **📚 꼬리질문 대비 / Deep-dive**
>
> - **수행 모드:** 시스템 호출은 유저 모드에서 커널 모드로의 **컨텍스트 스위칭(Context Switching)**이 발생하지만, 순수 라이브러리 함수(예: `strlen`)는 유저 모드 내에서 실행됩니다.
>     
> - **성능:** 시스템 호출은 모드 전환 오버헤드가 크므로 빈번한 호출 시 버퍼링(라이브러리 계층)을 통해 최적화하는 것이 일반적입니다.
>     

> [!faq]- Q. `errno`는 전역 변수인데, 멀티스레드 환경에서 안전한가요(Thread-safe)?
>
> **🗣️ 현대 리눅스 시스템에서 `errno`는 스레드별로 독립된 저장소를 갖도록 구현되어 안전합니다.**
>
> **📚 꼬리질문 대비 / Deep-dive**
>
> - 과거에는 단순 전역 변수였으나, 현재는 `_reentrant` 환경을 지원하기 위해 스레드 로컬 스토리지(TLS) 형태로 제공됩니다. 따라서 스레드 간 에러 번호가 섞이지 않습니다.
>     

## [Topic: 동적 메모리 할당 (Dynamic Memory Allocation)]

### 1. 🏗️ 빌드업 (Scenario & OS Concept)

- **사용 시점(When):** 컴파일 타임에 데이터의 크기를 결정할 수 없고, 실행 중(Runtime)에 필요한 메모리 양이 유동적일 때 사용합니다.
- **OS 핵심 개념:** **힙(Heap) 영역** 관리. 커널로부터 프로세스에게 할당된 힙 영역의 메모리를 유저 레벨 라이브러리 함수가 쪼개서 제공합니다.
    

### 2. ⚙️ System Call & Library API

- **필수 헤더:** `#include <stdlib.h>`
- **`malloc(size_t size)`:** 지정된 바이트만큼 메모리 할당. 초기화되지 않음.
- **`calloc(size_t nmemb, size_t size)`:** `nmemb * size` 크기를 할당하고 **0으로 초기화**.
- **`realloc(void *ptr, size_t size)`:** 이미 할당된 메모리 영역의 크기를 변경.
- **`free(void *ptr)`:** 할당된 메모리 해제 (Memory Leak 방지 필수).
    

### 3. 💻 실제 실습 구현

**[1단계: 메모리 할당 및 해제 (`mem_test.c`)]**


```C
#include <stdio.h>
#include <stdlib.h>

int main() {
    int *ptr;
    int n = 200;

    // 1. 200개의 정수를 담을 메모리 동적 할당
    ptr = (int *)malloc(n * sizeof(int));

    if (ptr == NULL) {
        perror("malloc failed");
        exit(1);
    }

    // 2. 메모리 사용 (생략)
    printf("%d bytes allocated.\n", n * (int)sizeof(int));

    // 3. 메모리 해제 (반드시 수행)
    free(ptr);
    
    return 0;
}
```

## [Topic: 명령행 인자 처리 (Command Line Arguments)]

### 1. 🏗️ 빌드업 (Scenario & OS Concept)

- **사용 시점(When):** 프로그램 실행 시 외부에서 옵션이나 파일명을 전달받아 처리해야 할 때 (예: `ls -l`에서 `-l` 처리).
- **OS 핵심 개념:** 프로세스가 생성될 때 쉘로부터 전달된 인자들이 **스택(Stack) 영역** 상단에 저장되어 메인 함수로 전달됩니다.
    

### 2. ⚙️ Main Function Prototype

- **함수 원형:** `int main(int argc, char *argv[]);`
- **`argc` (Argument Count):** 프로그램 이름을 포함한 인자의 총 개수.
- **`argv` (Argument Vector):** 인자 문자열들의 배열. `argv[0]`은 항상 프로그램의 경로/이름입니다.
    

### 3. 💻 실제 실습 구현

**[1단계: 인자 출력 소스 (`arg_test.c`)]**



```C
#include <stdio.h>

int main(int argc, char *argv[]) {
    printf("인자 개수: %d\n", argc);

    for (int i = 0; i < argc; i++) {
        printf("argv[%d]: %s\n", i, argv[i]);
    }

    return 0;
}
```

**[실행 및 결과]**



```Bash
gcc -o arg_test arg_test.c
./arg_test -h 2000
```

**출력 결과:**



```Plaintext
인자 개수: 3
argv[0]: ./arg_test
argv[1]: -h
argv[2]: 2000
```

## [Topic: 1주차 연습문제 및 핵심 개념 검증]

### 1. 핵심 문제 풀이 (Professor's Review)

- **Q1. 시스템 프로그래밍 표준이 아닌 것?**
    - **정답:** 다중 유닉스 명세 (X) → **단일 유닉스 명세(SUS)** (O).
- **Q2. 시스템 호출의 에러 리턴 값?**
    - **정답:** 일반적으로 `-1`을 반환하며, 상세 에러는 `errno`에 저장됨.
- **Q3. 패턴 검색 리눅스 명령어?**
    - **정답:** `grep`.
- **Q4. 실행 파일 경로 문제:**
    - **현상:** 파일이 있는데 실행이 안 됨.
    - **원인:** 현재 디렉토리(`.`)가 환경변수 `PATH`에 없기 때문.
    - **해결:** `./실행파일명`과 같이 상대 경로를 명시하여 실행.
        

### 🚨 Pitfalls & Troubleshooting

- **메모리 누수(Memory Leak):** `malloc` 후 `free`를 하지 않으면 프로세스 종료 전까지 메모리가 점유됨.
- **경로 설정:** M1 환경에서 실습 시, `PATH` 변수에 `.`이 빠져 있다면 반드시 `./`를 붙여야 함을 강조.

### 💡 CS Interview (운영체제/네트워크 면접 대비)

> [!faq]- Q. malloc()과 calloc()의 가장 큰 차이점은 무엇인가요?
>
> **🗣️ calloc()은 할당된 메모리를 모두 0으로 초기화하지만, malloc()은 이전의 쓰레기 값이 남아있을 수 있습니다.**
>
> **📚 꼬리질문 대비 / Deep-dive**
>
> - 성능 면에서는 초기화 과정이 없는 `malloc()`이 미세하게 빠를 수 있으나, 예측 가능한 동작을 위해서는 `calloc()`이나 `memset()`을 통한 초기화가 권장됩니다.
>     

> [!faq]- Q. 왜 시스템 프로그래밍에서 에러 발생 시 -1을 확인하고 errno를 체크해야 하나요?
>
> **🗣️ 시스템 호출은 성공/실패 여부만 리턴하고, 구체적인 실패 원인은 커널이 전역 변수인 errno에 기록하기 때문입니다.**
>
> **📚 꼬리질문 대비 / Deep-dive**
>
> - `errno` 값은 다음 시스템 호출에 의해 덮어씌워질 수 있으므로, 에러 발생 직후 즉시 확인하거나 별도의 변수에 복사해두어야 합니다.
>
