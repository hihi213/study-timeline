## 📝 [기말고사 최종본] 리눅스 파이프(Pipe) 핵심 총정리

### 1. 파이프의 기본 특징 및 데이터 형태

- **파일 시스템 상의 취급**: 파이프는 리눅스에서 일종의 파일로 관리됩니다.
    - `ls -l` 명령어로 확인 시 맨 앞의 파일 유형이 `p`로 표시됩니다.
- **데이터 형태**: 데이터 간의 경계가 없는 **스트림(Stream) 기반**으로 동작합니다. 즉, 데이터가 구분되어 가지 않고 쓰는 대로 시냇물처럼 연속적으로 흘러갑니다.
- **통신 제어 함수**: 시스템 콜 수준의 저수준 파일 입출력 방식인 `read()`와 **`write()`** 함수를 사용하여 데이터를 주고받습니다.

### 2. 이름 없는 파이프 vs 이름 있는 파이프

- **이름 없는 파이프**: 파일시스템에 이름이 등록되어 있지 않다
	- 하드디스크가 아닌, RAM(커널 메모리)에 임시로 만들어져 FD테이블를 통해서만 관리되고 통신주체 프로세스들이 종료되어 파일기술자가 모두 닫힐때 메모리에서 해제된다.
	- 보안문제로 다른프로세스는 ram(메모리 주소)를 알수없고, 주소를 알더라도 침범할수없다. 자식만이 FD테이블을 상속한다
	- 그래서 이름없는 파이프는 독립된 프로세스는 불가하고, 자식 프로세스와만 주고받을수있다.
	- 그런데 하드디스크(파일시스템)는 누구나 접근할수있다.
	- 그래서 하드디스크에 있는 파일이름 즉 **동일한 경로명을 인자로 하여 저수준 파일 오픈(`open`)을 요청**할 수 있다
	- 그렇다고 하드디스크에 직접 쓰고 지우는건 속도 문제가 있으므로, 하드디스크의 디렉토리 엔트리에 파이프이름과 아이노드 쌍만 저장하고, 데이터 블록 주소 포인터엔 아무것도 저장하지 않는다.
	- 프로세스가 open를 요청시에는 일반파일일때는 ~포인터가 활성화되어 실제 데이터 블록을 가리켜 찾아가지만, FIFO의 경우에는 그 대신 커널 ram 내부의 **`i_pipe` 구조체 포인터**가 활성화되어있다. 이 포인터는 커널 파이프 버퍼 메모리 주소를 가리킨다
	- 운영체제가 ram내부에서 스트림 방식으로 처리한다 스트림 방식이기에, 단방향통신이며, 양방향 통신을 원할시엔
- **이름 있는 파이프 (FIFO)**: 파일시스템에 이름이, 즉 파일이 존재한다.
    - 터미널에서 `ls -F` 옵션으로 확인 시 파일명 뒤에 파이프를 나타내는 기호인 `|`가 붙어서 출력됩니다.
    - 혈연관계가 없는 **완전히 독립된 서로 다른 프로세스 간 통신**에 사용됩니다. 일반 파이프와 마찬가지로 단방향 통신을 합니다.

### 3. 파이프 생성과 복사 메커니즘

- `pipe(fd)` 호출 시 커널 내부에 파이프가 생성되며, 크기가 2인 정수 배열에 파일 기술자(FD)가 담겨 리턴됩니다.
    - **`fd[0]`**: **읽기(수신) 전용** 포트 $\rightarrow$ 파이프의 **출구**
    - **`fd[1]`**: **쓰기(전송) 전용** 포트 $\rightarrow$ 파이프의 **입구**
- **주요 특징**: 파이프 생성 후 `fork()`를 실행하면, 자식 프로세스는 부모의 파일 기술자 테이블을 그대로 복사합니다. 따라서 **부모와 자식이 동일한 `fd[0]`, `fd[1]`을 통해 하나의 파이프를 공유**하게 됩니다.
    

### 4. 단방향(Half-Duplex) 통신의 본질과 오작동 유형

파이프는 데이터를 누가 썼는지 **송신자를 구별하지 못하기 때문에** 본질적으로 한쪽이 '쓰기'를 하면 반대편은 '읽기'만 해야 하는 **단방향 통신**입니다. 하나의 파이프로 번갈아 쓰려고 하면 아래와 같은 오작동이 발생합니다.

- **자가 수신 오류**: 부모가 파이프에 데이터를 쓰고 바로 읽으려고 하면, 자식이 읽기도 전에 부모 자신이 쓴 데이터를 다시 읽어버리는 버그가 발생합니다.
- **데드락(Deadlock)**: 부모와 자식이 동시에 읽기(`read`)를 시도하면, 파이프에 데이터가 들어오기만을 양쪽 모두 영원히 기다리며 프로세스가 완전히 멈춰버립니다.
    

### 5. 올바른 양방향 통신 및 FD 정리 규칙 (★시험 출제 1순위)

부모와 자식이 데이터를 서로 주고받는 완전한 쌍방향 통신을 하려면 **반드시 2개의 파이프를 독립적으로 생성**해야 합니다.

1. **부모 $\rightarrow$ 자식 전송용 파이프**: 부모의 `fd[1]`에서 자식의 `fd[0]`로 데이터가 흐르는 통로
2. **자식 $\rightarrow$ 부모 전송용 파이프**: 자식의 `fd[1]`에서 부모의 `fd[0]`로 데이터가 흐르는 통로
    

#### ⚠️ 데이터 혼선과 블로킹(멈춤) 방지를 위한 `close()` 규칙

통신 방향이 결정되면 데이터의 꼬임을 막기 위해 **사용하지 않는 파일 기술자는 반드시 `close()`로 닫아야 합니다.**

- **부모 $\rightarrow$ 자식 단방향 통신 시 주소 정리 정석**:
    - **부모 프로세스**: 읽기 포트인 **`fd[0]`을 닫고**, 쓰기 포트인 **`fd[1]`만 사용**
    - **자식 프로세스**: 쓰기 포트인 **`fd[1]`을 닫고**, 읽기 포트인 **`fd[0]`만 사용**
        

**💡 최종 점검 키워드:**

`fd[0]`은 읽기(Read), `fd[1]`은 쓰기(Write)라는 점과, 양방향 통신 시 파이프가 2개 필요하며 각 프로세스에서 쓰지 않는 FD를 닫아주는(`close`) 이유(자가 수신 및 데드락 방지)를 서술형 핵심 문장으로 기억하세요!


제시해주신 내용은 리눅스 가상 파일 시스템(VFS)의 핵심 메커니즘을 완벽하게 요약한 뼈대입니다.

기말고사 객관식 및 서술형 시험에서 완전무결한 만점 답안이 되도록, 일반 파일의 활성화 포인터 명칭인 **`i_fop`(파일 오퍼레이션 포인터)** 및 관련 커널 구조를 채워 넣고 전공 정석 용어로 최종 정리했습니다.

## 📝 [최종본] 파이프 종류별 커널 포인터 및 파일 시스템 저장 매커니즘
### 1. 이름 없는 파이프: 가상 메모리 격리와 상속의 한계

- **RAM 기반의 휘발성**: 하드디스크가 아닌 RAM(커널 메모리)에 임시 생성되며, 통신 주체 프로세스들이 종료되어 파일 기술자(FD)가 모두 닫히면 메모리에서 즉시 해제(소멸)됩니다.
- **프로세스 메모리 격리**: 현대 OS의 보안 정책상, 다른 독립 프로세스는 해당 파이프의 RAM 주소를 알 수 없고 물리적인 침범도 불가능합니다.
- **통신 범위의 제한**: 이름 없는 파이프는 오직 프로세스 내부의 고유 주소록인 **FD(파일 기술자) 테이블**로만 접근이 가능합니다. 이 테이블은 오직 `fork()` 시스템 콜을 통해서만 자식 프로세스에게 상속되므로, **독립된 프로세스 간에는 통신이 불가하며 부모-자식 간에만 통신이 가능**합니다.
### 2. 이름 있는 파이프(FIFO): 파일 시스템 공유를 통한 격리 우회

- **모두가 접근가능한 파일 시스템**: 프로세스 간 RAM 공간은 격리되어 접근할 수 없지만, 하드디스크(파일 시스템)는 모든 프로세스에게 접근이 허용되어 있습니다. 따라서 독립된 프로세스들은 **동일한 경로명(파일 이름)을 인자로 하여 저수준 파일 오픈(`open()`)을 요청**함으로써 통신에 참여합니다.
- **실제로 하드디스크엔 쓰고 읽지 않는다.** : 하드디스크의 디렉토리 엔트리(`dentry`)에는 `[파이프 이름 - 아이노드 번호]` 쌍으로 저장. 디스크 I/O로 인한 속도 저하를 막기 위해 아이노드의 **데이터 블록 주소 포인터에는 아무것도 저장되지 않습니다(NULL/0).**

### 3. `open()` 요청 시 파일 타입별 아이노드(inode) 및 포인터 활성화 매커니즘

프로세스가 `open()`을 요청하면 커널은 디스크의 아이노드를 RAM으로 로드하여 `struct inode` 객체를 생성하며, 파일 타입에 따라 활성화되는 내부 주소 포인터와 데이터 접근 방식이 완전히 달라집니다.

#### ① 일반 파일 (Regular File)의 경우

- **아이노드(`inode`)의 역할**: 디스크 상의 아이노드 구조체 내부에 파일의 메타데이터를 저장하고, **데이터 블록 포인터에는 실제 파일의 내용(데이터)이 저장된 하드디스크의 물리적 블록 주소들을 저장**합니다.
- **포인터 활성화**: `open()` 시 일반 파일 연산 주소를 담은 **`i_fop`(file_operations) 포인터와 데이터 블록 포인터가 활성화**됩니다. 이 포인터 계열들이 가리키는 실제 하드디스크 상의 데이터 블록 주소를 추적하여 파일 내용을 읽고 씁니다.
    

#### ② 이름 있는 파이프 (FIFO)의 경우

- **포인터 전환**: 하드디스크 상의 데이터 블록 주소 포인터는 완전히 비활성화(NULL)됩니다. 그 대신, 커널 RAM 내부의 **`i_pipe` 구조체 포인터가 활성화**됩니다.
- **최종 데이터 흐름**: 이 활성화된 **`i_pipe` 포인터는 커널 파이프 버퍼(Ring Buffer)의 메모리 주소**를 가리킵니다. 결과적으로 서로 아무 관계가 없는 독립된 프로세스들이 디스크 상의 '동일한 경로명(아이노드)'을 거쳐 진입한 뒤, 최종적으로는 **RAM 내부의 동일한 커널 파이프 버퍼 주소를 공유**하게 되어 디스크를 거치지 않고 스트림 방식으로 고속 통신을 수행하게 됩니다


독립된 프로세스는 RAM(커널 메모리)에 접근할수없어, 파이프테이블을 알지못해 이름없는 파이프에 접근하지 못했다. 그런데 누구나 접근가능한 파일시스템(하드디스크)에 파이프 이름의 파일을 생성하고, 누구나 open를 요청할수있게 한다.
