### 3. 파이프 생성과 복사 메커니즘

- `pipe(fd)` 호출 시 커널 내부에 파이프가 생성되며, 크기가 2인 정수 배열에 파일 기술자(FD)가 담겨 리턴됩니다.
    - **`fd[0]`**: **읽기(수신) 전용** 포트 $\rightarrow$ 파이프의 **출구**
    - **`fd[1]`**: **쓰기(전송) 전용** 포트 $\rightarrow$ 파이프의 **입구**
- **주요 특징**: 파이프 생성 후 `fork()`를 실행하면, 자식 프로세스는 부모의 파일 기술자 테이블을 그대로 복사합니다. 따라서 **부모와 자식이 동일한 `fd[0]`, `fd[1]`을 통해 하나의 파이프를 공유**하게 됩니다.
    

### 4. 단방향(Half-Duplex) 통신의 본질과 오작동 유형

파이프는 데이터를 누가 썼는지 **송신자를 구별하지 못하기 때문에** 본질적으로 한쪽이 '쓰기'를 하면 반대편은 '읽기'만 해야 하는 **단방향 통신**입니다. 하나의 파이프로 번갈아 쓰려고 하면 아래와 같은 오작동이 발생합니다.

- **자가 수신 오류**: 부모가 파이프에 데이터를 쓰고 바로 읽으려고 하면, 자식이 읽기도 전에 부모 자신이 쓴 데이터를 다시 읽어버리는 버그가 발생합니다.
- **데드락(Deadlock)**: 부모와 자식이 동시에 읽기(`read`)를 시도하면, 파이프에 데이터가 들어오기만을 양쪽 모두 영원히 기다리며 프로세스가 완전히 멈춰버립니다.
    

### 5. 올바른 양방향 통신 및 FD 정리 규칙 (★시험 출제 1순위)

부모와 자식이 데이터를 서로 주고받는 완전한 쌍방향 통신을 하려면 **반드시 2개의 파이프를 독립적으로 생성**해야 합니다.

1. **부모 $\rightarrow$ 자식 전송용 파이프**: 부모의 `fd[1]`에서 자식의 `fd[0]`로 데이터가 흐르는 통로
2. **자식 $\rightarrow$ 부모 전송용 파이프**: 자식의 `fd[1]`에서 부모의 `fd[0]`로 데이터가 흐르는 통로
    

#### ⚠️ 데이터 혼선과 블로킹(멈춤) 방지를 위한 `close()` 규칙

통신 방향이 결정되면 데이터의 꼬임을 막기 위해 **사용하지 않는 파일 기술자는 반드시 `close()`로 닫아야 합니다.**

- **부모 $\rightarrow$ 자식 단방향 통신 시 주소 정리 정석**:
    - **부모 프로세스**: 읽기 포트인 **`fd[0]`을 닫고**, 쓰기 포트인 **`fd[1]`만 사용**
    - **자식 프로세스**: 쓰기 포트인 **`fd[1]`을 닫고**, 읽기 포트인 **`fd[0]`만 사용**

# 📝 [최종본] 리눅스 파이프(Pipe) 및 파일 시스템 메커니즘 총정리

## 1. 파이프

- **파이프는 파일이며, 특수한 파일로 취급한다.**: 터미널에서 `ls -l` 명령어로 확인 시 파일 유형의 맨 앞 글자가 `p`로 표시됩니다.
- **연속적 스트림(Stream) 기반**: 데이터 간의 경계가 없는 바이트 스트림 방식으로 동작합니다. 데이터가 구분되지 않고 쓰는 대로 연속적으로 흘러갑니다.
- **저수준 I/O 제어**: 파일 시스템 콜인 저수준 입출력 함수 `read()`와 `write()`를 사용하여 데이터를 송수신합니다.

## 2. 가상 메모리 격리 보호 정책과 '이름 없는 파이프'의 한계
- **메모리 보호 정책 (OS 대원칙)**: 현대 운영체제는 가상 메모리 시스템을 통해 프로세스 간 주소공간을 격리합니다.(완전히 물리적으로)
- 따라서 타 프로세스의 유저, 커널영역을 직접 접근할수없고, 침범할수도 없습니다. 이는 자식 프로세스도 마찬가지입니다.
-  **"모든 프로세스는 격리 정책 때문에 타 프로세스의 커널 영역을 직접 만질 수 없다(자식도 마찬가지). 하지만 자식은 `fork()` 시 부모의 FD 테이블을 복사받기 때문에, 이 열쇠를 매개로 시스템 콜을 호출하여 OS의 중재 하에 커널 RAM 버퍼를 합법적으로 공유할 수 있는 것이다."**
- **이름 없는 파이프(Anonymous Pipe)의 한계**:
    - **휘발성 생성**: 파일 시스템에 등록되지 않고 커널 메모리(RAM)에 임시 생성되었다가, 관련 파일 기술자가 모두 닫히면 즉시 해제(소멸)됩니다.
    - **접근 매개체**: 오직 프로세스 내부의 고유 주소록인 **FD(파일 기술자) 테이블** 번호로만 접근이 가능합니다.
    - **통신 범위**: 이 FD 테이블은 오직 **`fork()` 시스템 콜을 통한 자식 프로세스로의 복사**로만 공유됩니다.
    - 자식 프로세스가 직접 부모의 커널 RAM 영역을 침범하는 것은 여전히 불가능합니다. 하지만 복사받은 주소록(FD)이 있기 때문에 합법적인 요청이 가능해집니다.
    - 따라서 주소록을 상속받지 못한 독립된 프로세스는 접근이 불가하며, 오직 **부모-자식(혈연관계) 프로세스 간에만 통신이 가능**합니다.

## 3. 하드디스크 파일 시스템 구조 (격리 우회의 매개체)

프로세스 간 가상 메모리는 철저히 격리되어 있지만, 하드디스크 파일 시스템은 경로명만 알면 모든 프로세스가 공통으로 접근할 수 있는 '공유 이정표' 역할을 합니다.

- **디렉토리 엔트리 (`dentry`)**: 문자열로 된 `[파일 이름 - 아이노드(inode) 번호]` 쌍을 매핑하여 저장하는 테이블입니다.
- **아이노드 (`inode`)**: 파일의 형태, 권한, 크기 등 실제 데이터를 제외한 모든 속성 정보(**메타데이터**)를 저장하는 고정 구조체입니다.
- **데이터 블록 (`Data Block`)**: 하드디스크 상에 실제 파일의 내용(데이터)이 물리적으로 저장되는 공간입니다.
    

## 4. `open()` 및 `write/read` 시 커널 RAM 내부 데이터 흐름 비교 (★서술형 1순위)

독립된 프로세스들은 파일 시스템의 **동일한 경로명을 인자로 하여 저수준 파일 오픈(`open()`)을 요청**함으로써 통신에 참여하며, 커널은 파일 타입에 따라 RAM 내부에서 포인터와 데이터를 다르게 처리합니다.

### ① 일반 파일 (Regular File)

- **아이노드 저장 방식**: 아이노드 내부의 **데이터 블록 포인터가 실제 하드디스크의 물리 블록 주소**들을 가리키고 있습니다.
- **커널 RAM의 역할**: `write()` 호출 시 유저 메모리의 데이터가 커널 RAM 내부의 임시 보관소인 **페이지 캐시(Page Cache)** 영역으로 복사됩니다.
- **최종 데이터 목적지**: 일반 파일 연산 주소를 담은 **`i_fop`(file_operations) 포인터** 계열들이 활성화되어, 페이지 캐시의 데이터를 하드디스크의 **물리 데이터 블록에 최종적으로 영구 저장**합니다.
    

### ② 이름 있는 파이프 (FIFO)

- **아이노드 저장 방식**: 디스크 공간을 소모하여 데이터를 저장하지 않으므로, 디스크 상의 **데이터 블록 주소 포인터에는 아무것도 저장되지 않습니다 (NULL / 0).**
- **포인터의 전환**: 커널은 아이노드의 파일 정보를 통해 파일 종류가 파이프(`p`)임을 확인하고 디스크 블록 포인터를 비활성화합니다. 그 대신, 커널 RAM 내부에 전용 통신 공간을 마련하고 이를 가리키는 **`i_pipe` 구조체 포인터를 활성화**하여 주소를 저장합니다.
- **데이터의 실시간 흐름 (W / R)**:
    - **Write**: 프로세스가 `write()`를 호출하면 유저 메모리의 데이터가 **`i_pipe`가 가리키는 커널 RAM(파이프 버퍼/링 버퍼) 공간에 복사**되어 기록됩니다. (디스크로 내려가지 않음)
    - **Read (소멸 메커니즘)**: 상대 프로세스가 `read()`를 호출하는 즉시 커널 RAM 버퍼에 있던 데이터를 **읽기 요청을 한 프로세스의 유저 메모리로 복사해 준 뒤, 커널 RAM 내부의 해당 데이터는 즉시 지워서 비웁니다.**
        

## 5. 단방향 통신의 본질과 올바른 양방향 통신 규칙

- **단방향(Half-Duplex)의 이유**: 파이프는 데이터를 누가 썼는지 **송신자를 구별하지 못합니다.** 이 때문에 한쪽이 '쓰기'를 하면 반대편은 '읽기'만 해야 합니다. 하나의 파이프로 번갈아 쓰려고 하면 아래와 같은 치명적인 오류가 발생합니다.
    - **자가 수신 오류**: 부모가 쓰고 바로 읽으려고 하면, 자식이 읽기 전에 자신이 쓴 데이터를 스스로 다시 읽어버리는 버그 발생.
    - **데드락 (Deadlock)**: 부모와 자식이 동시에 읽기(`read`)를 시도하면 데이터가 오기만을 영원히 기다리며 두 프로세스가 모두 멈춰버림.
        

### ⚠️ 올바른 양방향 통신 및 `close()` 정리 규칙

완전한 쌍방향 통신을 구현하려면 반드시 **2개의 파이프를 독립적으로 생성**하여 교차 연결해야 하며, 데이터 혼선과 블로킹(무한 대기)을 막기 위해 **사용하지 않는 파일 기술자는 반드시 `close()`로 닫아야 합니다.**

- **부모 $\rightarrow$ 자식 단방향 통신 시 FD 주소 정리 정석**:
    - **부모 프로세스**: 읽기 포트인 **`fd[0]`을 닫고**, 쓰기 포트인 **`fd[1]`만 사용**하여 송신
    - **자식 프로세스**: 쓰기 포트인 **`fd[1]`을 닫고**, 읽기 포트인 **`fd[0]`만 사용**하여 수신
        

### 💡 시험장 들어가기 전 최종 암기 공식

> - **이름 없는 파이프** $\rightarrow$ 파일 시스템 이름 없음 $\rightarrow$ RAM에만 존재 $\rightarrow$ **`fork()`를 통한 자식 간 상속만 가능**
>     
> - **이름 있는 파이프 (FIFO)** $\rightarrow$ 디스크에 이름과 inode만 존재(데이터 블록 포인터 = NULL) $\rightarrow$ `open()` 시 **`i_pipe` 포인터 활성화** $\rightarrow$ **독립 프로세스 간 커널 RAM 버퍼 공유 통신**
>     
> - **`fd[0]`** = 읽기(Read / 출구) , **`fd[1]`** = 쓰기(Write / 입구)
>



### 1. 가상 메모리 공간 구조

하나의 프로세스가 실행되면 운영체제로부터 독립된 가상 메모리 공간을 부여받으며, 이는 크게 **유저 공간**과 **커널 공간**으로 양분됩니다.

- **커널 공간 (Kernel Space)**: 운영체제 커널 코드와 시스템 관리를 위한 메모리 영역 (CPU 최고 권한인 Ring 0에서만 직접 제어 가능).
- **유저 공간 (User Space)**: 일반 프로그램이 사용하는 영역으로, 아래의 4대 세그먼트로 쪼개어 관리됩니다.
    - **스택 (Stack)**: 함수 호출 시 생성되는 지역 변수 및 매개 변수 (자동 할당 및 소멸).
    - **힙 (Heap)**: 개발자가 필요에 의해 동적으로 할당하는 공간 (`malloc` 등).
    - **데이터 (Data)**: 프로그램 시작부터 종료까지 유지되는 전역 변수 및 정적 변수.
    - **코드 (Code/Text)**: 컴파일된 기계어 명령어가 저장되는 읽기 전용(Read-Only) 공간.
        

### 2. 메모리 보호 정책 (OS 대원칙)

- **물리적 격리**: 현대 운영체제는 가상 메모리 시스템을 통해 **프로세스 간 주소 공간을 물리적으로 완전히 격리**합니다.
- **침범 불가**: 따라서 어떤 독립된 프로세스도 타 프로세스의 유저 공간은 물론, **커널 영역을 직접 접근할 수 없고 침범할 수도 없습니다.**
* **자식 프로세스의 예외 없음**: 이는 부모-자식 관계라 할지라도 예외가 아닙니다. `fork()`를 통해 태어난 자식 프로세스 역시 독립된 주소 공간을 지니므로, **직접 부모의 커널 RAM 영역을 침범하는 것은 물리적으로 불가능**합니다.

### 3. 이름 없는 파이프(Anonymous Pipe)의 매커니즘과 통신 범위

직접적인 메모리 침범이 불가능한 자식 프로세스가 어떻게 부모의 파이프를 공유하는지에 대한 정석적인 인과관계입니다.

- **휘발성 생성**: 파일 시스템(하드디스크)에 이름을 등록하지 않고 커널 메모리(RAM)에 임시 생성되었다가, 관련 파일 기술자가 모두 닫히면 즉시 해제(소멸)됩니다.
- **접근 매개체**: 이름(경로)이 없기 때문에, 이 파이프는 오직 프로세스 내부의 고유 주소록인 **FD(파일 기술자) 테이블 번호로만 접근이 가능**합니다.
- **상속을 통한 합법적 요청**: 이 FD 테이블은 오직 **`fork()` 시스템 콜을 통한 자식 프로세스로의 복사(상속)로만 공유**됩니다. 자식 프로세스는 직접 커널 RAM을 침범하는 것이 아니라, **복사받은 주소록(FD)이 있기 때문에 운영체제(OS)를 향해 합법적인 대리 수행 요청(`read`/`write` 시스템 콜)이 가능**해집니다.
- **최종 결론**: 주소록(FD 테이블)을 상속받지 못한 독립된 프로세스는 파이프의 존재를 알 수도 없고 접근도 불가능하며, 오직 **부모-자식(혈연관계) 프로세스 간에만 통신이 가능**합니다.

# 📝 [기말고사 최종본] 리눅스 파이프(Pipe) 및 가상 메모리·파일 시스템 메커니즘 총정리

## 1. 가상 메모리 보호 정책
> RAM: 휘발성 하드웨어 장치 그 자체
> 메모리: 운영체제가 물리 RAM 주소가아닌 가상주소로 RAM 관리하는 주소공간
- **물리적 주소공간 격리**: 현대 운영체제는 가상 메모리 시스템을 통해 프로세스 간 주소 공간을 물리적으로 완전히 격리합니다. 
	- 그래서 하나의 프로세스가 실행되면 격리된 가상 메모리 공간을 부여받으며, 그 공간은 **유저 공간**과 **커널 영역**으로 분리됩니다.
- **유저/커널 영역 침범 불가**: 어떤 독립된 프로세스도 타 프로세스의 유저 공간은 물론, 커널 영역을 직접 접근할 수 없고 침범할 수도 없습니다.
- **자식 프로세스 예외 없음**: `fork()`를 통해 생성된 자식 프로세스 역시 독립된 주소 공간을 지니므로, **직접 부모의 유저/커널 RAM 영역을 침범하는 것은 물리적으로 불가능**합니다.
## 2. 하드디스크 파일 시스템 구조 (격리 우회의 매개체)

프로세스 간 가상 메모리는 철저히 격리되어 있지만, 하드디스크 파일 시스템은 경로명만 알면 모든 프로세스가 공통으로 접근할 수 있는 '공유 이정표' 역할을 합니다.

- **디렉토리 엔트리 (`dentry`)**: 파일이름 - 아이노드(inode) 번호 쌍을 매핑하여 문자열로 저장합니다.
- **아이노드 (`inode`)**: 파일의 속성(정보)과 실제 데이터 위치를 가리키는 포인터(데이터 블록 주소)를 저장합니다.
- **데이터 블록 (`Data Block`)**: 하드디스크 상에 실제 파일의 내용(데이터)이 물리적으로 저장되는 공간입니다.

## 4. 이름 없는 파이프 (Anonymous Pipe) 메커니즘

- **개념 및 취급**: 리눅스에서 일종의 파일로 관리되며, `ls -l` 확인 시 맨 앞 글자가 `p`로 표시됩니다. 데이터 간 경계가 없는 **연속적 바이트 스트림(Stream)** 기반으로 동작하며 저수준 시스템 콜(`read`/`write`)로 제어합니다.
- **휘발성 생성**: 파일 시스템에 등록되지 않고 커널 메모리(RAM)에 임시 생성되었다가, 관련 파일 기술자가 모두 닫히면 즉시 해제(소멸)됩니다.
- **접근 매개체 (FD 테이블)**: 이름(경로)이 없기 때문에, 오직 프로세스 내부의 고유 주소록인 **FD(파일 기술자) 테이블 번호**로만 제어할 수 있습니다.
- **상속을 통한 합법적 요청**: 이 FD 테이블은 오직 `fork()` 시스템 콜을 통한 자식 프로세스로의 복사(상속)로만 공유됩니다. 자식 프로세스는 직접 커널 RAM을 침범하는 것이 아니라, **상속받은 열쇠(FD)가 있기 때문에 운영체제(OS)를 향해 합법적인 대리 수행 요청(`read`/`write`)이 가능**해집니다.
- **한계**: 주소록(FD 테이블)을 상속받지 못한 독립된 프로세스는 파이프의 존재를 알 수도 없고 접근도 불가능하며, 오직 **부모-자식(혈연관계) 프로세스 간에만 통신이 가능**합니다.
    

## 5. open() 요청 시 '일반 파일' vs '이름 있는 파이프(FIFO)' 데이터 흐름 비교

독립된 프로세스들은 파일 시스템의 **동일한 경로명을 인자로 하여 저수준 파일 오픈(`open()`)을 요청**함으로써 격리를 우회하여 통신에 참여합니다.

### ① 일반 파일 (Regular File)
> 커널은 파일 타입에 따라 RAM 내부에서 데이터를 다르게 처리합니다.
- 아이노드 구조: 데이터블록 주소 포인터에 데이터 블록 주소 저장
1. **커널 RAM에 복사**: 유저 메모리의 데이터를 커널 RAM(페이지 캐시) 영역에 복사합니다.
2. **데이터 블록에 저장**: 아이노드의 활성화된 **데이터 블록 포인터**를 추적하여, 하드디스크의 **데이터 블록에 실제 내용을 최종적으로 영구 저장**합니다.

### ② 이름 있는 파이프 (FIFO)

- **아이노드 구조**: 디스크에 영구 저장할 필요가 없으니, 디스크 상의 **데이터 블록 주소 포인터에는 아무것도 저장되지 않습니다 (NULL / 0).** 터미널에서 `ls -F`로 확인 시 파일명 뒤에 기호 `|`가 붙습니다.
- **포인터의 전환**: 커널은 아이노드 내 파일 타입을 보고 파이프(`p`)임을 확인한 뒤 디스크 블록 포인터를 비활성화합니다. 그 대신, 커널 RAM 내부에 전용 통신 공간을 마련하고 이를 가리키는 **`i_pipe` 구조체 포인터를 활성화**하여 주소를 저장합니다.
- **실시간 흐름 및 소멸 메커니즘**: 
    - 프로세스가 **Write** 호출: 유저 메모리의 데이터가 **`i_pipe`가 가리키는 커널 RAM(파이프 버퍼/링 버퍼) 공간에 복사**되어 기록됩니다. 
    - 프로세스가 **Read** 호출: `read()`를 호출하는 즉시 커널 RAM 버퍼에 있던 데이터를 **읽기 요청을 한 프로세스의 유저 메모리로 복사해 준 뒤, 커널 RAM 내부의 해당 데이터는 즉시 지워서 비웁니다.**
	- 이 흐름의 반복이라 디스크에 영구 저장할 필요가 없다
## 6. 단방향 통신의 본질과 올바른 양방향 통신 규칙

- **단방향(Half-Duplex)의 이유**: 파이프는 데이터를 누가 썼는지 **송신자를 구별하지 못합니다.** 이 때문에 한쪽이 '쓰기'를 하면 반대편은 '읽기'만 해야 합니다. 하나의 파이프로 번갈아 쓰려고 하면 치명적인 오류가 발생합니다.
    - **자가 수신 오류**: 부모가 쓰고 바로 읽으려고 하면, 자식이 읽기 전에 자신이 쓴 데이터를 스스로 다시 읽어버리는 버그 발생.
    - **데드락 (Deadlock)**: 부모와 자식이 동시에 읽기(`read`)를 시도하면 데이터가 오기만을 양쪽 모두 영원히 기다리며 두 프로세스가 모두 멈춰버림.
        

### ⚠️ 올바른 양방향 통신 및 `close()` 정리 규칙 (★출제 1순위)

완전한 쌍방향 통신을 구현하려면 반드시 **2개의 파이프를 독립적으로 생성**해야 하며, 데이터 혼선과 블로킹(무한 대기)을 막기 위해 **사용하지 않는 파일 기술자는 반드시 `close()`로 닫아야 합니다.**

- **부모 $\rightarrow$ 자식 단방향 통신 시 FD 주소 정리 정석**:
    - **부모 프로세스**: 읽기 포트인 **`fd[0]`을 닫고**, 쓰기 포트인 **`fd[1]`만 사용**하여 송신
    - **자식 프로세스**: 쓰기 포트인 **`fd[1]`을 닫고**, 읽기 포트인 **`fd[0]`만 사용**하여 수신
        

### 💡 시험장 들어가기 전 최종 암기 공식

> - **`fd[0]`** = 읽기(Read / 출구) , **`fd[1]`** = 쓰기(Write / 입구)
>     
> - **이름 없는 파이프** $\rightarrow$ 파일 시스템 이름 없음 $\rightarrow$ RAM에만 존재 $\rightarrow$ **`fork()`를 통한 FD 테이블 상속자만 접근 가능**
>     
> - **이름 있는 파이프 (FIFO)** $\rightarrow$ 디스크엔 이름과 inode만 존재(데이터 블록 포인터 = NULL) $\rightarrow$ `open()` 시 **`i_pipe` 포인터 활성화** $\rightarrow$ **독립 프로세스 간 시스템 콜을 매개로 커널 RAM 버퍼 공유 통신**
>
