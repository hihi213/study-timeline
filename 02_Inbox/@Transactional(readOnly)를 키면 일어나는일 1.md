## 정리

이 트랜잭션 안에서는 데이터를 **'읽기만 하고 절대 수정하지 않겠다'**고 JPA와 데이터베이스에게 **미리 알려주는 것**과 같기 때문입니다.

이 약속 덕분에, 데이터를 변경할 때 필요한 여러 복잡한 작업들을 **생략**할 수 있어 성능이 향상됩니다. 도서관에서 책을 '보기만' 할 사람과 '수정(필기)'할 사람을 다르게 대우하는 것과 같습니다.

---

### 1) 부족 포인트 스캔 (놓쳤을 수 있는 관점)

- **JPA의 기본 동작 원리:** `@Transactional`이 붙은 일반적인(read-write) 트랜잭션 안에서, JPA가 엔티티의 변경을 감지하기 위해 얼마나 많은 일을 하는지(변경 감지, 스냅샷 비교 등) 모르고 있습니다. 최적화는 이 작업들을 '안 하기' 때문에 발생하는 것입니다.
- **트랜잭션의 숨은 비용:** 트랜잭션이 단순히 작업을 묶는 것을 넘어, 데이터 일관성을 위해 내부적으로 상태를 계속 추적하고 관리하는 비용이 발생한다는 점을 간과하고 있습니다.
- **'최적화'의 실체:** 최적화가 막연히 '빨라진다'는 것이 아니라, 구체적으로 **어떤 작업들이 생략되는지** 그 실체를 알지 못하고 있습니다.
- **힌트(Hint)로서의 역할:** `readOnly = true`는 '이렇게 해!'라는 명령이라기보다, "나는 읽기만 할 거야"라고 시스템에 힌트를 주어, 시스템이 스스로 "아, 그럼 이런 작업들은 안 해도 되겠네"라고 판단하게 만드는 개념이라는 점을 놓치고 있습니다.

### 2) 핵심 개념 요약

`@Transactional(readOnly = true)`를 붙이면 크게 3가지 수준에서 최적화가 일어납니다.

1. **JPA: 변경 감지(Dirty Checking) 생략 (가장 큰 이유)**
    
    - **평상시:** JPA는 트랜잭션 시작 시 엔티티의 원본 스냅샷을 1차 캐시에 만들어 둡니다. 트랜잭션이 끝날 때, 현재 엔티티와 스냅샷을 일일이 비교하여 변경된 부분이 있으면 UPDATE 쿼리를 만들어 DB에 보냅니다.
    - **`readOnly = true`일 때:** "어차피 수정 안 할 거지?"라고 인지하고, **스냅샷을 만들지도 않고 비교하지도 않습니다.** 이 과정에 필요한 메모리와 CPU 자원을 크게 아낄 수 있습니다.
        
2. **JPA: 쓰기 지연(Write-behind) SQL 저장소 불필요**
    
    - **평상시:** JPA는 `UPDATE`, `INSERT` 등의 SQL을 바로 실행하지 않고, 트랜잭션 커밋 직전까지 '쓰기 지연 SQL 저장소'에 모아뒀다가 한 번에 DB로 보냅니다(플러시, Flush).
    - **`readOnly = true`일 때:** 데이터를 수정하지 않으므로 SQL을 모아둘 필요가 없습니다. 따라서 트랜잭션 커밋 시 **플러시(Flush)를 생략**하여 불필요한 DB 상호작용을 줄입니다.
        
3. **데이터베이스(DB) / 드라이버 수준**
    
    - DB 드라이버에 "이 트랜잭션은 읽기 전용"이라는 힌트를 전달합니다.
    - DB는 이 힌트를 받아 내부적으로 불필요한 락(Lock)을 줄이거나, 복제(Replication)를 사용하는 환경이라면 **읽기 전용 복제 서버(Read Replica)**로 요청을 보내 기본 서버(Master)의 부하를 줄이는 등의 추가적인 최적화를 수행할 수 있습니다.

### 3) 용어 매핑

- **`@Transactional(readOnly = true)`**: "이번 작업 단위(Transaction)는 **데이터 조회가 목적**이며, 데이터 구조나 내용의 **변경은 일절 발생하지 않음**을 명시하는 힌트(Hint)"
- **"최적화"**: JPA 레벨에서는 **변경 감지(Dirty Checking) 및 플러시(Flush) 작업 생략**, DB 레벨에서는 **부하 분산 및 락(Lock) 최소화** 등의 성능 향상 작업.
- **변경 감지 (Dirty Checking)**: 엔티티가 처음 조회된 상태(스냅샷)와 현재 상태를 비교하여 변경 여부를 감지하는 JPA의 핵심 기능.

### 4) 사고 틀 & 판단 기준

"언제 `@Transactional(readOnly = true)`를 붙여야 할까?"

1. **메서드의 목적을 파악합니다.**
    
    - 이 메서드는 데이터베이스에서 정보를 **가져오기만** 하는가? (SELECT)
    - 아니면 무언가를 **저장, 수정, 삭제**하는가? (INSERT, UPDATE, DELETE)
        
2. **규칙에 따라 결정합니다.**
    
    - **조회만 하는 경우:** 메서드 이름이 `find...()`, `get...()`, `search...()` 등으로 끝나고, 내부 로직이 순수하게 SELECT 작업만 수행한다면 **`@Transactional(readOnly = true)`를 적극적으로 사용**하는 것이 좋습니다. 👍
    - **변경이 포함된 경우:** 회원 가입(`join`), 정보 수정(`update`), 주문(`order`) 등 데이터에 변화를 주는 로직이 단 하나라도 있다면 **절대 사용하면 안 됩니다.** ❌ (사용 시, 데이터 변경이 DB에 반영되지 않을 수 있습니다.)

> 판단 기준: "이 메서드가 실행된 후 DB 데이터에 변화가 있는가?"
> No? → readOnly = true 사용
> Yes? → readOnly = true 미사용

### 5) 체크 질문 (자가 점검)

1. 회원 정보를 수정하는 `updateMember()` 메서드에 `@Transactional(readOnly = true)`를 붙여도 될까요? 안 된다면 왜 그럴까요?
2. `readOnly = true`일 때, JPA가 성능 향상을 위해 생략하는 가장 대표적인 작업은 무엇인가요?
3. 데이터를 '읽기만' 할 때와 '수정'할 때, JPA는 어느 쪽 작업에 더 많은 내부 절차를 거칠까요?
4. 서비스 클래스의 모든 조회(find, search 등) 메서드에 `readOnly = true`를 붙이는 것은 좋은 습관일까요?
