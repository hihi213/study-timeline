## 정리 
### 1) 부족 포인트 스캔 (놓쳤을 수 있는 관점)

- **의존성의 본질:** ‘의존성’이란 단순히 레포지토리에 국한된 개념이 아니라, **"어떤 객체(A)가 다른 객체(B)의 기능이나 정보가 있어야만 자기 일을 할 수 있는 상태"** 그 자체를 의미한다는 점을 놓치고 있습니다.
- **DI의 목적:** 의존성 주입의 진짜 목적이 특정 기술(JPA, 데이터베이스)을 위해서가 아니라, 객체들을 **느슨하게 연결(Loosely Coupled)**하여 **교체하기 쉽고, 테스트하기 쉬운 유연한 코드**를 만들기 위함이라는 큰 그림을 보지 못하고 있습니다.
- **객체의 역할:** 모든 객체는 각자의 역할과 책임이 있습니다. '회원 가입'이라는 기능을 만들 때, 요청을 받는 객체(Controller), 비즈니스 규칙을 처리하는 객체(Service), 데이터를 저장하는 객체(Repository)는 모두 서로를 필요로 하는 ‘의존 관계’에 있습니다.
- **제어의 역전 (IoC):** 내가 필요한 객체를 직접 만드는(`new MemberRepository()`) 것이 아니라, 외부(DI 컨테이너)에서 만들어서 나에게 ‘주입’해준다는 **제어의 역전(Inversion of Control)**이라는 핵심 원리를 간과하고 있습니다.

### 2) 핵심 개념 요약

- **의존성 (Dependency):** 어떤 클래스나 모듈이 다른 클래스나 모듈의 기능을 사용해야만 하는 관계. 예를 들어, `MemberService`는 DB에 접근하기 위해 `MemberRepository`에 의존합니다.
- **의존성 주입 (Dependency Injection, DI):** 클래스 내부에서 필요한 의존 객체를 직접 생성하는 대신, **외부에서(DI 프레임워크가) 생성하여 넣어주는** 디자인 패턴입니다. "필요한 부품은 내가 만들지 않고, 밖에서 조립해서 준다"는 개념입니다.
- **DI 컨테이너 (DI Container):** 객체의 생성과 생명주기를 관리하고, 의존성을 파악하여 자동으로 주입해주는 외부 존재입니다. 스프링 프레임워크의 `ApplicationContext`가 대표적인 예입니다.
- **느슨한 결합 (Loosely Coupled):** DI를 통해 객체들이 서로에게 단단히 묶여있지 않은 상태를 말합니다. `MemberService`는 `JpaMemberRepository`가 아닌, `MemberRepository`라는 ‘인터페이스’에만 의존하므로, 나중에 `JdbcMemberRepository`로 부품을 쉽게 갈아 끼울 수 있습니다.

### 3) 용어 매핑

- **"레파지도리 이것만 있어?"**: Repository는 **데이터 영속성(Persistence)**을 처리하는 객체로, DI가 적용되는 수많은 **의존성(Dependency) 종류 중 하나**에 불과합니다.
- **"다른 경우는??"**: **모든 종류의 협력하는 객체 관계**가 다른 경우에 해당합니다.
    - **Controller가 Service를 필요로 하는 경우:** `Controller` → `Service`에 의존
    - **Service가 Repository를 필요로 하는 경우:** `Service` → `Repository`에 의존
    - **Service가 다른 Service를 필요로 하는 경우:** `OrderService` → `MemberService`에 의존 (주문 시 회원 정보 필요)
    - **Service가 외부 API 통신 모듈을 필요로 하는 경우:** `OrderService` → `PaymentGateway`에 의존 (결제 요청)
    - **Service가 설정값(Configuration)을 필요로 하는 경우:** `ApiService` → `ApiConfig`(API 키, URL 등)에 의존

### 4) 사고 틀 & 판단 기준

"이것이 의존성 주입이 필요한 상황인가?"를 판단하는 사고 과정입니다.

1. **객체의 책임 분리:** 현재 만들고 있는 클래스(`A`)의 핵심 책임이 아닌 일이 있는지 확인합니다.
    
    - 예: `MemberService`의 책임은 '회원 비즈니스 로직 처리'이지, 'DB에 데이터 저장' 그 자체가 아닙니다.
        
2. **외부 기능 식별:** 그 책임을 더 잘하는 다른 객체(`B`)가 있는지 생각합니다.
    
    - 'DB에 데이터 저장'은 `MemberRepository`가 전문입니다.
        
3. **의존 관계 설정:** 클래스 `A`는 `B`의 기능이 **필요하다**는 결론을 내립니다. 즉, `A`는 `B`에 의존합니다.
4. **주입 요청:** `A` 내부에서 `B`를 `new B()`로 직접 만들지 않고, 생성자나 필드를 통해 **"나는 B가 필요하니 외부에서 만들어서 넣어주세요"** 라고 선언합니다.
    
    - 이것이 바로 의존성 주입을 요청하는 코드입니다. (예: `@Autowired`, `private final MemberRepository memberRepository;`)

> 판단 기준: "내가 만들고 있는 이 클래스가, 자기 핵심 책임 외에 다른 객체의 도움이 필요한가?"
> 
> → 그렇다면, 그 다른 객체는 의존성이며, 의존성 주입을 고려해야 합니다.

### 5) 체크 질문 (자가 점검)

1. 사용자의 HTTP 요청을 받아 처리하는 `Controller`가 비즈니스 로직을 처리하는 `Service`의 메서드를 호출해야 한다면, 둘은 의존 관계에 있는 것일까요?
2. 의존성 주입을 사용하면 코드를 수정하지 않고 DB 저장 방식을 JPA에서 JDBC로 쉽게 바꿀 수 있을까요? 그 이유는 무엇인가요?
3. `new` 키워드를 사용해서 클래스 안에서 직접 다른 클래스 객체를 만드는 것은 의존성 주입이라고 할 수 있나요?
4. 결제 처리를 위해 외부 결제 시스템과 통신하는 `PaymentGateway`라는 클래스가 있다면, `OrderService`는 이 클래스를 주입받아 사용해야 할까요?
