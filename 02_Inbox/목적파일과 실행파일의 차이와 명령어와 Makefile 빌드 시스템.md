## 📝 정리
> 여기에 나의 언어로 재작성


- `gcc` : 실행파일을 생성해라(링크 단계까지 수행해라)
	- 입력이 소스파일이면 전처리+컴파일+어셈블+링크
	- 입력이 목적파일이면 링크만 수행
- `gcc -c` : 목적파일(`.o`)를 생성해라
	- 목적파일: 기계어로 번역은 되었으나, 링크 단계를 거치지 않아 메모리 주소가 확정되지 않은 상태
	- 여러 소스 파일중 수정하지 않은 일부파일은 다시 컴파일할 필요가 없으니 수정한 파일만 목적파일 로 재빌드한다 그후 실행파일을 재생성한다.
- `gcc -o` : 생성하는 파일이름을 이 이름으로 지정한다.
- Makefile은 파일의 수정시간을 비교해서, 어떤 파일을 컴파일을 할지, 링크할지 알아서 처리하는 자동화로 편의를 준다.



## 1. `gcc -c` (Compile Only)

이 옵션은 전처리(Preprocessing), 컴파일(Compilation), 어셈블(Assembly) 단계까지만 수행하고 **링크(Linking) 단계는 수행하지 말 것**을 지시합니다.

- **결과물:** **목적 파일(Object File, `.o`)**
- **파일의 본질:**
	* 소스 코드가 기계어로 번역된 **재배치 가능한 이진 코드(Relocatable Machine Code)**입니다.
    - 함수나 전역 변수의 실제 메모리 주소가 결정되지 않은 상태입니다.
    - 예를 들어, `extern int errno;`를 사용하는 코드가 있다면, `main.o` 내부에는 `errno`를 참조한다는 기록만 있을 뿐, `errno`가 실제 메모리 어디에 있는지는 비어 있습니다.
- **핵심 용도:** 분할 컴파일. 여러 소스 파일 중 수정된 파일만 다시 컴파일하여 빌드 시간을 단축할 때 사용합니다.
    

---

## 2. `gcc -o` (Output Naming & Linking)

`-o` 자체는 단순히 **출력 파일의 이름을 지정**하는 옵션입니다. 하지만 보통 링크 단계에서 실행 파일을 생성할 때 함께 사용되므로, 실무적으로는 **링크 과정을 완료하여 최종 결과물을 만드는 것**으로 통용됩니다.

- **결과물:** **실행 파일(Executable File, 확장자 없음 또는 지정 이름)**
- **파일의 본질:**
    - 여러 개의 목적 파일(`.o`)과 표준 라이브러리(libc 등)를 하나로 합친 결과물입니다.
    - **심볼 해석(Symbol Resolution):** `extern`으로 선언되었던 변수(`errno` 등)나 다른 파일의 함수들이 실제 어떤 메모리 주소에 있는지 링커(Linker)가 모두 찾아 연결한 상태입니다.
    - 운영체제가 메모리에 로드하여 바로 실행할 수 있도록 헤더 정보(ELF 포맷 등)가 완성된 파일입니다.
        

---

## 3. 기술적 차이점 요약 (Object vs Executable)

|**항목**|**목적 파일 (-c)**|**실행 파일 (-o)**|
|---|---|---|
|**기계어 포함 여부**|포함됨|포함됨|
|**심볼 주소 결정**|미결정 (Relocatable)|결정됨 (Absolute/Relative)|
|**라이브러리 결합**|결합 안 됨|C 표준 라이브러리 등이 결합됨|
|**엔트리 포인트**|없음 (실행 시작점 정보 없음)|있음 (`_start` 또는 `main` 주소)|
|**운영체제 인식**|단독 실행 불가|단독 실행 가능|

## 4. 시스템 프로그래밍 관점에서의 연결

사용자님이 앞서 공부하신 `extern int errno;`와 연결하면 흐름은 다음과 같습니다.

1. **`gcc -c main.c`**: 컴파일러는 `extern` 선언을 보고 "주소는 나중에 링커가 채워줄 거야"라고 믿고 `main.o`를 만듭니다. (이때 `main.o` 내부의 `errno` 주소는 `0x0000` 처럼 비어 있는 상태입니다.)
2. **`gcc -o app main.o`**: 링커가 `main.o`와 표준 라이브러리를 합칩니다. 이때 라이브러리 안에서 실제 `errno`의 위치를 찾아 `main.o`의 빈 곳에 주소를 써넣습니다.
3. **결과**: 비로소 `app`이라는 실행 파일은 `errno`가 어디 있는지 알고 제대로 동작하게 됩니다.

## 5. Makefile이 해주는 '스마트한' 판단

이걸 사람이 매번 기억해서 하기 힘들기 때문에 **Makefile**을 씁니다. Makefile은 파일의 **'수정 시간(Timestamp)'**을 비교해서 다음과 같이 동작합니다.

- **컴파일 단계:** "`.c` 파일이 `.o` 파일보다 최신인가?" → **YES**면 해당 파일만 `gcc -c` 실행.
- **링크 단계:** "어떤 `.o` 파일이라도 최종 실행 파일보다 최신인가?" → **YES**면 `gcc -o` 실행.
    

> **결국:** 소스 하나만 고쳐도 **링크 단계는 무조건 마지막에 한 번 더 실행**되어야 합니다. 다만, 모든 소스를 처음부터 다 컴파일하는 것보다 훨씬 빠를 뿐입니다.
### 💡 시스템 분석을 위한 팁

실제로 목적 파일과 실행 파일의 차이를 보고 싶다면 `nm` 명령어를 사용해 보세요.

- `nm main.o`: `errno` 옆에 **U** (Undefined)라고 뜹니다. (아직 연결 안 됨)
- `nm app`: `errno` 옆에 실제 주소나 섹션 정보가 뜹니다. (연결 완료)
