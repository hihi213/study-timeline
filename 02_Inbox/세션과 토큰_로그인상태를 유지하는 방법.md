## 정리

### 1. 토큰 기반 인증 (JWT - JSON Web Token) 🌟 _가장 인기가 많음_

세션 방식처럼 서버에 "누가 로그인했는지" 상태를 저장하지 않고, **클라이언트(브라우저/앱)에 인증 정보를 담은 디지털 서명된 '증명서(토큰)'를 발급**해 주는 방식입니다.

- **동작 방식**:
    
    1. 로그인 성공 시 서버가 암호화된 **JWT 토큰**을 만들어 전달합니다.
    2. 클라이언트는 이 토큰을 저장(Local Storage나 쿠키)해 둡니다.
    3. 이후 요청할 때마다 헤더(`Authorization: Bearer <token>`)에 토큰을 얹어서 보냅니다.
    4. 서버는 토큰의 위변조 여부(서명)만 검증하고 바로 요청을 처리합니다.
        
- **장점**: 서버가 세션을 저장할 필요가 없어 **서버 부하가 적고, 서버를 여러 대 늘리는(Scale-out) 대규모 서비스에 매우 유리**합니다. (앱/웹 통합 로그인에도 용이)
- **단점**: 이미 발급된 토큰은 중간에 강제로 만료시키기 어렵습니다. (토큰이 탈취당하면 만료 전까지 위험)
    

### 2. OAuth 2.0 (소셜 로그인 / 위임 인증)

"카카오로 로그인하기", "구글로 로그인하기"처럼 **타사 서비스의 계정 정보를 활용해 인증**하는 방식입니다.

- **동작 방식**:
    
    1. 사용자가 구글/카카오에서 로그인을 진행합니다.
    2. 구글/카카오가 우리 서버에게 "이 사람 인증된 사용자 맞아!"라는 **Access Token**을 발급해 줍니다.
    3. 우리 서버는 이 토큰으로 사용자 정보를 확인한 뒤 자체 서비스를 이용하게 해줍니다.
        
- **장점**: 사용자가 비밀번호를 새로 만들 필요가 없고, 서비스 입장에서도 비밀번호 관리 부담이나 보안 위험이 줄어듭니다.
    

### 3. HTTP Basic / Digest Auth (고전적인 헤더 인증)

매 요청마다 아이디와 비밀번호를 헤더에 직접 실어 보내는 아주 단순한 방식입니다.

- **동작 방식**: `Authorization: Basic dXNlcjpwYXNzd29yZA==` 형태(Base64 인코딩)로 ID와 PW를 매번 전송합니다.
- **특징**: 로그인 상태라는 개념이 아예 없습니다. HTTPS 환경이 아니면 비밀번호가 그대로 노출되어 매우 위험하므로, 일반 서비스 웹사이트보다는 **간단한 내부 API testing이나 내부 서버 통신**용으로 가끔 쓰입니다.
    

### 4. SSO (Single Sign-On - 통합 인증)

**한 번 로그인하면 여러 개의 연관된 서비스나 사이트를 동시에 이용**할 수 있게 해주는 시스템입니다.

- **예시**: Google 계정 하나로 로그인하면 Gmail, Google Drive, YouTube를 별도 로그인 없이 다 쓸 수 있는 형태.
- **특징**: 내부적으로 SAML, OAuth 2.0, OIDC(OpenID Connect) 등의 기술을 결합해서 구축합니다. 기업 내부 시스템(ERP, 메일, 전자결재 등)이나 대기업 서비스군에서 주로 사용합니다.
    

### 💡 한눈에 비교하기 (세션 vs JWT)

요즘 백엔드 개발에서 가장 많이 고민하는 **세션**과 **JWT**의 차이입니다.

|**구분**|**세션 (Session)**|**JWT (Token)**|
|---|---|---|
|**로그인 상태 저장소**|**서버** (메모리, DB, Redis 등)|**클라이언트** (웹 브라우저, 앱)|
|**서버 부담**|사용자가 늘어날수록 서버 메모리 부담 증가|서버 부담이 거의 없음|
|**확장성**|서버를 여러 대 둘 때 세션 공유 설정 필요|서버를 마음껏 늘려도 별도 설정 필요 없음|
|**제어력**|강제 로그아웃/차단이 **쉬움**|강제 로그아웃 처리가 **까다로움**|
|**추천 환경**|보안이 중요하고, 단일 서버/웹 위주의 서비스|모바일 앱, SPA(React/Vue), 대규모/분산 서버 환경|

비유 없이 두 방식의 핵심적인 **기술적 차이점**을 직관적으로 정리해 드릴게요.

가장 근본적인 차이는 "로그인 상태 데이터를 서버에 두느냐, 클라이언트에 두느냐"입니다.

### 1. 상태 저장 위치 (Statefulness)

- **세션 (Session-based)**
    - **상태 유지 (Stateful)** 방식입니다.
    - 로그인 정보(사용자 ID, 로그인 시간 등)를 **서버의 메모리, DB, 또는 Redis**에 직접 저장합니다.
    - 클라이언트(브라우저)에는 이 세션을 찾기 위한 Key 값인 `Session ID`만 쿠키로 전달합니다.
- **토큰 (Token-based / JWT)**
    - **무상태 (Stateless)** 방식입니다.
    - 서버는 로그인 정보를 저장하지 않습니다.
    - 사용자 정보와 권한을 암호화·서명한 **`Token` 데이터 자체를 클라이언트에 통째로 넘겨주고**, 클라이언트가 이를 저장합니다.
        

### 2. 요청 처리 방식 (인증 과정)

- **세션**
    
    1. 클라이언트가 `Session ID`를 헤더(쿠키)에 실어 요청합니다.
    2. 서버는 DB나 메모리에서 해당 `Session ID`를 조회(Look-up)합니다.
    3. 세션 정보가 존재하고 유효하면 요청을 승인합니다.
        
- **토큰**
    
    1. 클라이언트가 `Token`을 헤더에 실어 요청합니다.
    2. 서버는 DB를 조회하지 않고, 토큰의 전자서명(Signature)만 검증(Verify)합니다.
    3. 서명이 위변조되지 않았고 유효기간이 지나지 않았다면, 토큰 내부의 사용자 정보(Payload)를 그대로 신뢰하여 요청을 승인합니다.
        

### 3. 서버 확장성 (Scale-out)

- **세션**
    - 서버를 여러 대(A, B, C)로 늘릴 때 문제가 발생합니다.
    - A 서버에서 로그인한 세션 정보가 B 서버에는 없기 때문에, **세션 동기화 작업**이나 공유 세션 저장소(예: Redis)를 별도로 구축해야 합니다.
- **토큰**
    - 서버가 100대로 늘어나도 아무런 추가 설정이 필요 없습니다.
    - 모든 서버가 동일한 암호화 키(Secret Key)만 가지고 있다면, A 서버에서 발급한 토큰을 B 서버나 C 서버에서도 즉시 검증할 수 있습니다.
        

### 4. 데이터 크기와 네트워크 부하

- **세션**
    - 전달되는 `Session ID`는 단순한 난수 문자열이므로 **데이터 크기가 매우 작습니다.** (네트워크 트래픽 적음)
- **토큰**
    - 토큰(JWT) 내부에 사용자 정보, 권한, 유효기간, 서명 등이 포함되어 있어 **데이터 크기가 상대적으로 큽니다.**
    - 매 요청마다 이 큰 토큰을 주고받아야 하므로 네트워크 대역폭 소비가 더 큽니다.
        

### 5. 통제권 (로그아웃 및 차단)

- **세션**
    - **서버가 완벽한 통제권을 가집니다.**
    - 특정 사용자를 강제 로그아웃시키거나 계정을 차단하고 싶다면, 서버에서 해당 `Session ID`를 삭제하거나 만료시키면 즉시 적용됩니다.
- **토큰**
    - **발급된 토큰을 서버가 직접 취소하기 어렵습니다.**
    - 한번 발급된 토큰은 만료 시간이 될 때까지 서버에서 "유효한 토큰"으로 인식합니다.
    - 차단 목록(Blacklist)을 별도로 관리하지 않는 한, 클라이언트가 토큰을 삭제하지 않는 이상 강제 로그아웃이 불가능합니다.
        

### 📊 요약 비교

|**구분**|**세션 (Session)**|**토큰 (Token / JWT)**|
|---|---|---|
|**상태 저장**|서버 (Stateful)|클라이언트 (Stateless)|
|**서버 검증 방식**|DB/메모리 조회|암호화 서명 검증|
|**서버 확장성**|불리함 (별도 세션 서버 필요)|매우 유리함 (독립적 검증 가능)|
|**데이터 크기**|작음 (`Session ID`만 전송)|큼 (사용자 데이터 포함)|
|**제어력**|강제 로그아웃/차단 **가능**|만료 전까지 강제 차단 **어려움**|

아닙니다! **로그인 시간 기록과 상관없이 현대 IT 회사들의 대다수는 토큰(JWT) 방식을 적극적으로 사용합니다.**

"토큰은 서버에 아무것도 저장하지 않는다(Stateless)"는 말 때문에 혼동이 생기기 쉬운데, '로그인 상태를 유지하기 위한 저장'과 '로그 기록(Audit Log)을 위한 저장'은 완전히 별개의 영역입니다.

### 1. '로그인 상태 저장' vs '로그인 이력 기록'의 차이

- **로그인 상태 저장 (세션의 역할)**
    - *"이 요청을 보낸 사용자가 지금 로그인 중인 상태인가?"*를 판별하기 위해 요청이 올 때마다 메모리/DB를 계속 조회하는 것입니다.
- **로그인 이력 기록 (Log / History)**
    - *"이 사용자가 언제, 어떤 IP로 로그인했는가?"*를 단순히 기록(Write-only)으로 남기는 것입니다.
    - 로그인 버튼을 누르는 **그 순간 딱 1번만** DB에 `INSERT`나 로그 시스템에 전송하면 끝납니다.
        

### 2. 토큰(JWT) 환경에서 로그인 시간을 기록하는 실제 구조

토큰 기반 시스템에서도 로그인 처리 과정에서 DB에 로그인 시간을 기록하는 데 전혀 문제가 없습니다.

```sql
[클라이언트] ---> 1. ID/PW 전달 ---> [인증 서버]
                                         │
                                         ├─► 2. DB에서 사용자 검증
                                         ├─► 3. DB/로그 시스템에 '로그인 일시(last_login_at)' 기록!
                                         │
[클라이언트] <--- 4. JWT 토큰 발급 <──────┘
```

1. 사용자가 ID/비밀번호로 로그인을 시도합니다.
2. 서버는 DB에서 비밀번호를 확인한 뒤, **`user` 테이블의 `last_login_at` 컬럼을 현재 시간으로 업데이트**하거나 별도의 `login_history` 테이블에 기록을 남깁니다.
3. 그 후 클라이언트에게 **JWT 토큰을 발급**해서 돌려줍니다.
4. 이후의 서비스 이용(마이페이지 조회, 글쓰기 등)에서는 DB 조회를 거치지 않고 토큰 서명만 검증하여 빠른 성능을 유지합니다.
    

### 3. 실제로 현대 기업들이 구축하는 형태

보통 대규모 서비스를 운영하는 회사들은 아래 2가지 방식 중 하나로 토큰 환경에서 로그인 이력을 관리합니다.

1. **DB 기반 기록**: 로그인 성공 직후 DB의 유저 테이블 또는 로그인 이력 테이블에 일시, IP, 접속 기기 정보(User-Agent)를 기록합니다.
2. **이벤트/로그 스트리밍**: 로그인을 처리함과 동시에 Kafka나 Logstash 같은 데이터 파이프라인으로 "로그인 이벤트"를 쏴서 BigQuery나 Elasticsearch 등에 분석용으로 저장합니다.
    

결론적으로, **"매 요청마다 상태를 조회하지 않는다(Stateless)"는 것이지, "로그인 순간의 이력을 남기지 않는다"는 뜻이 아니므로** 현대 회사들도 토큰 방식을 사용하는 데 아무런 제약이 없습니다.
