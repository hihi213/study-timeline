## **TL;DR**
- **엔티티 신규 생성법:** **ID 할당 없이** persist()
- **엔티티 수정법**: 조회 → (도메인 메서드로) 필요한 필드만 변경 → 커밋
- 변경되면 안 되는 필드: Setter를 만들지 않거나/private으로 선언해 수정시도 차단
- 변경 후 **save() 습관** → JPA에선 **불필요**(커밋 시 자동 반영)
- (비추천) merge() **:** 전달된 객체의 정보로 영속성 컨텍스트에 있는 원본 엔티티를 **전체 덮어쓰기**
	- 누락 필드가 **NULL로 덮어쓰기**됨
- (비추천) new Entity() 후 **ID만 세팅**해서 repository.save()
	- JPA가 **준영속**으로 보고 자동으로 `entityManager.merge()`를 호출

---

> 차이점: **Dirty가 ‘어떻게 만들어졌는지’** 가 완전히 다름 (선택적 변경 vs 스냅샷 복사).
## A. JPA 영속성 컨텍스트 조회->변경/ Merge 최종 정리: 5단계
### 1. 영속성 컨텍스트 오픈: 서비스 메서드에서 **@Transactional 시작**
- 논리적 관리 영역인 영속성 컨텍스트가 생성됩니다.

### 2. 영속 엔티티 로딩 및 관리 준비
#### 1차 캐시 조회 및 로딩
- **목적**: DB 접근을 최소화하고 성능을 최적화하기 위함입니다.
- **작동**:
	- 엔티티 ID를 기준으로 **1차 캐시**에 먼저 접근합니다.
	- 캐시에 없다면 **DB에 `SELECT` 쿼리**를 실행하여 데이터를 가져옵니다.
- 결과: 가져온 데이터는 **영속 상태**로 전환되어 1차 캐시에 저장되고 **스냅샷**이 찍혀 기록됩니다.
#### 1차 캐시 조회 및 로딩 실패했을 경우

ID를 기준으로 **DB에 데이터 자체가 없는 경우** (즉, 신규 데이터) 두 메커니즘은 다르게 작동합니다.

| 메커니즘          | 입력 객체 상태                  | 결과                                                       |
| ------------- | ------------------------- | -------------------------------------------------------- |
| **조회 → 변경**   | ID로 `find()` 시도           | DB에 없으므로 **`null`을 반환**하고 작업 종료. 끝 ->개발자가 Persist 경로처리해야 |
| **`merge()`** | ID가 없는 **비영속 객체**를 인자로 받음 | **`persist`처럼** 새로운 영속 엔티티를 생성하고, `INSERT`를 준비함.         |

- merge에 persist 기능있다고해도 명시적으로 persist 코드에 사용해 의도 드러내기
---

### 3. 변경 감지 (Dirty Checking)의 역할과 차이

이제부턴 **영속엔티티의 상태를 어떻게 변경했는지**에 따라 매커니즘이 나뉩니다.

| 메커니즘             | Dirty 생성 방식                                    | SQL 생성 유형                                             |
| ---------------- | ---------------------------------------------- | ----------------------------------------------------- |
| **조회 → 변경 (권장)** | **개발자가 메서드로 영속 엔티티를 선택적으로 필드 수정**              | Dirty Checking으로 **수정된 필드**만 감지하여 **`UPDATE`** 쿼리 생성. |
| **`merge()`**    | **준영속 객체의 모든 필드를 영속 객체에 복사**해 영속객체를 변경 상태로 만듦. | **`UPDATE(기존변경시)`** 또는 **`INSERT(신규생성시)`** 쿼리 생성      |

- 이때 merge의 반환값은 영속객체이고 개발자는 이를 사용한다, 데이터를 넘겼던 준영속객체는 계속 준영속인 별개의 객체이다
#### merge가 위험한이유
- 요청에 **없는 필드 = NULL** 로 **덮어쓰기**
- **선택적 변경** 불가(전체 갈아끼우기)
- 권한 밖 필드가 의도치 않게 갱신될 수 있음
---

### 4. 최종 반영 (Flush & Commit)

1) **Flush**: Dirty Checking 실행 → **INSERT/UPDATE/DELETE**를 **제약 고려 순서**로 **전송**(배치 가능) → **스냅샷/버전 갱신**
2) **Commit**:**트랜잭션 확정(ACID)** / **Rollback**: 전송된 변경 취소
	- commit은 필요시 자동 FLUSH함

### 5. 컨텍스트 종료

- commit(또는 rollback) 완료 후 영속성 컨텍스트 **종료**
- 이제 여기서 관리되던 모든 엔티티는 **준영속 상태(Detached)** 로 전환됨
