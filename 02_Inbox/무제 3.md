## [Topic: 시스템 호출 오류 처리 (errno, perror, strerror)]

### 1. 🏗️ 빌드업

> "프로그램이 커널에 서비스를 요청(System Call)했을 때, 실패 원인을 어떻게 정확히 파악할 것인가?"

- **사용 시점:** 파일이 없거나 권한이 없는 등 시스템 호출이 실패했을 때, 단순히 "실패했다"는 사실을 넘어 구체적인 이유(코드)를 확인해야 할 때 사용합니다.
- **OS 핵심 개념:** 커널은 시스템 호출 실패 시 전역 변수 `errno`에 오류 번호를 설정합니다. 이는 프로세스별로 독립적으로 관리되는 상태 값입니다.
    

### 2. ⚙️ System Call API (핵심 함수 원형 및 인자)

- **필수 헤더:**
	- `#include <errno.h>` (errno 변수 활용)
    - `#include <stdio.h>` (perror 함수 활용)
    - `#include <string.h>` (strerror 함수 활용)
- **핵심 메커니즘:**
    - **System Call**: 성공 시 보통 0 또는 양수, 실패 시 `-1` 반환.
    - **Library Function**: 실패 시 보통 `NULL`(0) 반환.
- **오류 확인 함수:**
    - `void perror(const char *s);`: 사용자 메시지와 함께 표준 오류 출력(stderr)으로 오류 내용 출력.
    - `char *strerror(int errnum);`: 오류 번호에 해당하는 문자열 포인터 반환 (가공 출력 가능).
        

### 3. 💻 실제 실습 구현

**[1단계: Source Code (`error_test.c`)]**



```C
#include <stdio.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <stdlib.h>

extern int errno; // 전역 변수 errno 선언

int main() {
    // 1. 존재하지 않는 파일에 access 시스템 호출 시도
    // F_OK: 파일 존재 여부 체크
    if (access("test.txt", F_OK) == -1) {
        // 방법 1: errno 직접 출력
        printf("1. errno: %d\n", errno);

        // 방법 2: perror 활용 (가장 간편함)
        perror("2. perror 결과");

        // 방법 3: strerror 활용 (메시지 가공 가능)
        char *msg = strerror(errno);
        printf("3. strerror 결과: %s (파일명: test.txt)\n", msg);
    }

    return 0;
}
```

**[실행결과]**



```Bash
$ gcc -o error_test.out error_test.c
$ ./error_test.out
1. errno: 2
2. perror 결과: No such file or directory
3. strerror 결과: No such file or directory (파일명: test.txt)
```

- **분석**: `errno` 2번은 `ENOENT`(No such file or directory)를 의미하며, `perror`는 이를 자동으로 해석하여 출력해 줍니다.

## [Topic: GCC 컴파일 및 Makefile 빌드 자동화]

### 1. 🏗️ 빌드업

> "수십 개의 소스 파일을 매번 일일이 gcc로 컴파일할 것인가? 변경된 파일만 효율적으로 빌드할 방법은?"

- **사용 시점:** 대규모 프로젝트에서 여러 소스 코드 간의 의존성을 관리하고, 한 번의 명령으로 전체 빌드/청소를 수행하고 싶을 때 사용합니다.
- **OS 핵심 개념:** `make` 유틸리티는 파일의 수정 시간(mtime)을 비교하여 필요한 부분만 재컴파일(Incremental Build)을 수행합니다.
    

### 2. ⚙️ 빌드 명령어 및 환경

- **GCC 주요 옵션:**
    - `-o [파일명]`: 실행 파일 이름 지정 (기본값 `a.out`)
    - `-c`: 링크를 생략하고 오브젝트 파일(`.o`)만 생성
- **Makefile 구성 요소:**
    - `Target`: 생성할 대상 파일
    - `Dependencies`: 대상 파일을 만들기 위해 필요한 소스들
    - `Recipe`: 실제 실행할 셸 명령 (반드시 **Tab**으로 들여쓰기)
        

### 3. 💻 실제 실습 구현

**[1단계: Makefile 작성]**



```Makefile
# [Terminal: Makefile]
CC = gcc
OBJS = main.o add_num.o
TARGET = add.out

$(TARGET): $(OBJS)
	$(CC) -o $(TARGET) $(OBJS)

main.o: main.c
	$(CC) -c main.c

add_num.o: add_num.c
	$(CC) -c add_num.c

clean:
	rm -f $(OBJS) $(TARGET)
```

**[2단계: 실행 및 검증]**



```Bash
$ make        # Makefile에 정의된 규칙대로 빌드 시작
gcc -c main.c
gcc -c add_num.c
gcc -o add.out main.o add_num.o

$ ./add.out   # 실행 결과 확인
1에서 5까지의 합은 15다.

$ make clean  # 생성된 바이너리 및 오브젝트 파일 삭제
rm -f main.o add_num.o add.out
```

## [Topic: 명령행 인자 처리 (argc, argv)]

### 1. 🏗️ 빌드업

> "사용자가 터미널에서 입력한 옵션(예: ls -l)을 프로그램 내부에서 어떻게 읽어오는가?"

- **사용 시점:** 실행 시점에 파일명, 실행 옵션, 매개변수 등을 프로그램에 전달해야 할 때 필수적입니다.
- **OS 핵심 개념:** 프로세스가 생성될 때 커널은 스택 영역에 `argc`(인자 개수)와 `argv`(인자 문자열 배열)를 준비하여 `main()` 함수로 전달합니다.
    

### 2. ⚙️ System Call API

- **함수 원형:** `int main(int argc, char *argv[]);`
- **인자 설명:**
    - `argc`: 명령행에 입력된 문자열의 개수 (실행 파일명 포함)
    - `argv[]`: 입력된 각 문자열의 주소를 담고 있는 포인터 배열. `argv[0]`은 항상 실행 파일명입니다.
        

### 3. 💻 실제 실습 구현

**[1단계: Source Code (`args.c`)]**



```C
#include <stdio.h>

int main(int argc, char *argv[]) {
    printf("인자 개수: %d\n", argc);
    
    for(int i = 0; i < argc; i++) {
        printf("argv[%d]: %s\n", i, argv[i]);
    }
    
    return 0;
}
```

**[실행결과]**

Bash

```sql
$ gcc -o args.out args.c
$ ./args.out -h 2000
인자 개수: 3
argv[0]: ./args.out
argv[1]: -h
argv[2]: 2000
```

### 💡 CS Interview (운영체제/네트워크 면접 대비)

> [!faq]Q. 시스템 호출(System Call)과 라이브러리 함수(Library Function)의 결정적인 차이는 무엇입니까?
>
> **🗣️ 핵심 답변**
>
> **시스템 호출**은 커널 모드에서 실행되어 하드웨어 자원에 직접 접근하는 인터페이스인 반면, **라이브러리 함수**는 사용자 모드에서 실행되는 일반 함수입니다.
>
> **📚 꼬리질문 대비 / Deep-dive**
>
> - 라이브러리 함수(예: `printf`, `fopen`)는 내부적으로 성능 최적화(버퍼링 등)를 위해 시스템 호출(예: `write`, `open`)을 감싸서 호출하는 구조를 가집니다.
>     
> - 시스템 호출은 사용자 모드에서 커널 모드로의 **Context Switch**를 동반하므로 잦은 호출 시 오버헤드가 발생할 수 있습니다.
>     

> [!faq]Q. `perror()`와 `strerror()` 중 실무에서 어떤 상황에 무엇을 쓰는 것이 더 유리합니까?
>
> **🗣️ 핵심 답변**
>
> 단순 디버깅 시에는 자동으로 표준 오류에 출력해 주는 `perror()`가 편리하지만, 로그 시스템이나 네트워크 전송을 위해 오류 메시지를 가공해야 할 때는 문자열을 반환하는 `strerror()`가 유리합니다.
>
> **📚 꼬리질문 대비 / Deep-dive**
>
> - `strerror()`는 멀티스레드 환경에서 안전하지 않을 수 있으므로, Thread-safe한 `strerror_r()` 사용을 고려해야 합니다.
>
