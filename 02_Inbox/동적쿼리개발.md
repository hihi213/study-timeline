## **1) 동적 쿼리란?**

> **입력 조건 유무에 따라 WHERE/JOIN/ORDER 등이 달라지는 쿼리.**
> 예: status, memberName이 있으면 조건 추가, 없으면 생략.
**동적 쿼리**는 사용자가 어떤 값을 입력하느냐에 따라 `WHERE` 조건절 등이 동적으로 변하거나 추가되는 쿼리를 말합니다
### **왜 필요?**

- 검색 화면(다중 필터)·리스트 페이지처럼 조건 조합이 다양할 때
- 불필요한 조건을 빼서 **실행계획 단순화 + 인덱스 활용**을 돕기 위해

### **구현 방법(선호 순)**

1. **QueryDSL** (권장)
    
    - 타입세이프, 가독성 높음, 동적 조건은 BooleanBuilder/where()에 나열.

```Java
BooleanBuilder where = new BooleanBuilder();
if (status != null) where.and(order.status.eq(status));
if (hasText(name)) where.and(member.name.contains(name));

List<Order> list = queryFactory
    .selectFrom(order)
    .join(order.member, member)
    .where(where)
    .fetch();
```
    
1. **JPA Criteria API**
    
    - 표준이지만 장황함. 동적 조건은 List\<Predicate>에 모아 cq.where(cb.and(...)).

2. **문자열 조립 + 바인딩**
    
    - StringBuilder로 JPQL 문자열을 **만들되, 값은 반드시 바인딩**(아래 2절).
    - 가독성은 떨어지지만 작은 프로젝트에서 간단히 가능.

3. **Spring Data JPA Specification / Example(QBE)**
    
    - 리포지토리 수준에서 재사용 가능한 조건 객체.

## **2) 파라미터 바인딩(Prepared Statement)**

> **쿼리 안에 값(리터럴)을 직접 끼워 넣지 말고, 자리표시자에 바인딩.**
 **정의**: SQL 쿼리문에 변수가 들어갈 자리를 placeholder(`:name` 또는 `?`)로 만들어두고, 실행 시점에 실제 값을 안전하게 채워 넣는 기술.
### **JPQL/SQL 문법**

- **이름 기반(named)**

```java
TypedQuery<Order> q = em.createQuery(
    "select o from Order o join o.member m " +
    "where (:status is null or o.status = :status) " +
    "and (:name is null or m.name like :name)",
    Order.class);
q.setParameter("status", status);
q.setParameter("name", hasText(name) ? "%"+name+"%" : null);
```
    
- **위치 기반(positional)**

```java
Query q = em.createQuery("select m from Member m where m.name = ?1 and m.age > ?2");
q.setParameter(1, name);
q.setParameter(2, 10);
```
    
- **IN 파라미터**

```java
query.setParameter("ids", List.of(1L,2L,3L)); // JPQL의 "in :ids"
```
    
- **LIKE 와일드카드**

    파라미터에 포함시키거나 concat() 사용: like concat(:name, '%')

### **바인딩의 이점**

- **SQL 인젝션 방지**: 값은 데이터로 전달, 쿼리 구조와 분리
- **성능**: **쿼리 플랜 재사용**(문자열 동일 → 파싱/최적화 캐시 히트)
- **타입 안정성**: 드라이버가 타입에 맞게 세팅(날짜/숫자 포맷 문제 해소)
- **로그/감사 용이**: 같은 쿼리에 값만 달라 기록 간결

## **3) 문자열** + 로 변수 끼워넣는것의 문제점

> 예:
> "... where m.name = '" + name + "' and o.status = '" + status + "'"

1. **보안 취약(치명적)**
    
    - ' OR '1'='1 같은 페이로드로 **SQL Injection** 발생.

2. **쿼리 플랜 캐시 붕괴**
    
    - 값이 문자열에 **박혀 버리면 매번 “다른 쿼리”**로 인식 → 파싱/최적화 반복.

3. **타입/포맷 오류**
    
    - 날짜·숫자 로케일/포맷 처리 직접 해야 함(따옴표, 소수점, 타임존 등).

4. **이스케이프·따옴표 지옥**
    
    - 값에 ', %, _ 포함 시 깨짐. 수동 이스케이프 누락 위험 상시 존재.

5. **가독성·유지보수 저하**
    
    - 조건이 많아질수록 문자열 더하기가 난독증 유발, 실수로 공백 빠트리면 문법 오류.

6. **민감정보 노출 위험**
    
    - 로그에 쿼리 문자열 그대로 남아 **개인정보/토큰**이 찍힐 수 있음.

> **결론:** 문자열 연결은 “데모/실습 단계”가 아니면 **금지**.
> 항상 **바인딩**(PreparedStatement) 또는 **QueryDSL**을 쓰자.

---

## **4) 작은 예시(문자열 조립 + 바인딩, 최소형)**

```java
StringBuilder jpql = new StringBuilder(
    "select o from Order o join o.member m where 1=1");

if (status != null) jpql.append(" and o.status = :status");
if (hasText(name)) jpql.append(" and m.name like :name");

TypedQuery<Order> q = em.createQuery(jpql.toString(), Order.class);
if (status != null) q.setParameter("status", status);
if (hasText(name)) q.setParameter("name", "%"+name+"%");
return q.getResultList();
```

- **포인트**: 문자열은 **구조만**, **값은 전부 바인딩**.

## **5) 베스트 프랙티스 체크리스트**

- 값은 **항상 바인딩**(named param 권장)
- LIKE, IN, 날짜 등 **드라이버/JPQL 기능 활용**(직접 포맷 금지)
- 동적 조건은 **QueryDSL(BooleanBuilder)** 또는 **Criteria**로 조립
- 서비스는 “무엇을 찾을지”만, **리포지토리가 쿼리 구현** 캡슐화
- 로깅은 파라미터 마스킹·레벨 조정으로 **민감정보 보호**

---

### **한 줄 요약**

**동적 쿼리**는 조건 조합을 코드로 만들되, **값은 반드시 바인딩**해라.
문자열 + 삽입은 **보안·성능·유지보수** 모두에서 손해다.
