VMware 환경의 Ubuntu Linux에서 C 언어를 이용한 **일반 파일 정보 관리** 실습을 진행함. `/ch3` 디렉터리의 예제 소스 13개를 활용하여 파일의 속성 조회 및 권한 변경을 학습함.

### 🎯 이번 교시 핵심 실습 주제

- 3. `access()`를 이용한 접근 권한 확인 및 `chmod()`를 통한 권한 변경

## 1. [Topic: 파일 정보 검색 (stat & inode)]

- **Definition:** 리눅스 커널이 관리하는 파일의 메타데이터(inode 정보)를 사용자 영역으로 가져오는 시스템 호출입니다.
- **Why in OS:** 리눅스는 모든 것을 파일로 관리하며, 파일의 실제 데이터 외에 소유주, 크기, 권한 등의 속성 정보는 **inode**라는 자료구조에 저장되기 때문에 이를 조회하는 인터페이스가 필수적입니다.
    

### 🏗️ 동작 원리 및 API 상세

- **내부 메커니즘:** 경로명(`path`)을 전달하면 커널은 해당 파일의 inode를 찾아 `struct stat` 구조체에 정보를 채워 넣습니다.
- **API 스펙:**
    - `int stat(const char *pathname, struct stat *statbuf);`
    - `int fstat(int fd, struct stat *statbuf);`
    - **Return:** 성공 시 `0`, 실패 시 `-1` (errno 설정).
    - **주의사항:** `stat()`은 파일 자체에 대한 읽기 권한은 없어도 되지만, 해당 파일에 이르는 경로(디렉터리)에 대한 **실행(x) 및 읽기(r)** 권한이 있어야 접근 가능합니다.
        

### 💻 실제 실습 구현

**1) Source Code (`ex3_1.c`)**

```C
#include <sys/types.h>
#include <sys/stat.h>
#include <stdio.h>

int main() {
    struct stat statbuf; // 파일 정보를 저장할 구조체 선언

    // stat 함수 호출: 파일명과 구조체 주소를 넘김
    if (stat("linux.txt", &statbuf) == -1) {
        perror("stat");
        return 1;
    }

    // 주요 inode 정보 출력
    printf("Inode: %ld\n", (long)statbuf.st_ino);
    printf("Mode: %o\n", statbuf.st_mode);      // 8진수로 출력
    printf("Nlink: %ld\n", (long)statbuf.st_nlink);
    printf("UID: %d, GID: %d\n", statbuf.st_uid, statbuf.st_gid);
    printf("Size: %ld\n", (long)statbuf.st_size);
    printf("Blksize: %ld\n", (long)statbuf.st_blksize);
    printf("Blocks: %ld\n", (long)statbuf.st_blocks);
    
    return 0;
}
```

## 2. [Topic: st_mode 분석 (파일 종류 및 권한)]

- **Definition:** `struct stat`의 `st_mode` 필드(16비트)를 분석하여 파일의 종류(일반, 디렉터리, 링크 등)와 접근 권한을 판별하는 과정입니다.
- **Why in OS:** 리눅스는 16비트 정수 하나에 여러 정보를 압축하여 저장하므로, 비트 연산(Masking)을 통해 필요한 정보를 추출해야 합니다.
    

### 🏗️ 동작 원리 및 API 상세

- **비트 구조 (16-bit):**
    - **상위 4비트:** 파일 종류 (File Type)
    - **중간 3비트:** 특수 권한 (SetUID, SetGID, Sticky bit)
    - **하위 9비트:** 접근 권한 (User, Group, Other의 rwx)
- **판별 방법:**
    - **비트 마스크 방식:** `st_mode & S_IFMT` 연산 후 결과값을 상수와 비교.
    - **매크로 방식:** `S_ISREG(statbuf.st_mode)`와 같이 정의된 매크로 사용 (가독성 높음).
        

### 💻 실제 실습 구현

**1) Source Code (`ex3_3.c` - 매크로 방식)**



```C
#include <sys/types.h>
#include <sys/stat.h>
#include <stdio.h>

int main() {
    struct stat statbuf;
    stat("linux.txt", &statbuf);

    printf("File Mode: %o\n", (unsigned int)statbuf.st_mode);

    // 매크로를 이용한 파일 종류 검사
    if (S_ISREG(statbuf.st_mode)) printf("linux.txt: Regular File\n");
    if (S_ISDIR(statbuf.st_mode)) printf("linux.txt: Directory\n");
    
    // 비트 마스크를 이용한 권한 검사 (Owner Read)
    if (statbuf.st_mode & S_IRUSR) printf("Owner has read permission\n");

    return 0;
}
```

**2) 컴파일 및 실행 결과**

코드 스니펫

```sql
$ gcc -o ex3_3 ex3_3.c
$ ./ex3_3

linux.txt: Regular File
Owner has read permission
```

## 3. [Topic: 파일 접근 권한 확인 및 변경 (access & chmod)]

- **Definition:** `access()`는 프로세스의 실재 사용자 ID(RUID)를 기준으로 파일의 접근 가능 여부를 확인하며, `chmod()`는 파일의 `st_mode` 비트를 수정하여 권한을 변경합니다.
- **Why in OS:** 다중 사용자 환경에서 보안을 유지하기 위해, 특정 프로세스가 파일을 읽거나 실행할 수 있는지 사전에 검증하고 필요에 따라 권한을 제어하기 위함입니다.
    

### 🏗️ 동작 원리 및 API 상세

- **`access()` 메커니즘:**
    - `F_OK`: 파일 존재 여부 확인
    - `R_OK`, `W_OK`, `X_OK`: 각각 읽기, 쓰기, 실행 권한 확인
    - **Return:** 접근 가능 시 `0`, 불가 또는 에러 시 `-1`.
- **`chmod()` 메커니즘:**
    - 파일의 inode 내 `st_mode` 값을 직접 변경합니다.
    - 8진수(Octal) 값을 직접 사용(`0755`)하거나, 정의된 상수를 비트 OR(`|`) 연산하여 설정할 수 있습니다.
        

### 💻 실제 실습 구현

**1) Source Code (`ex3_6.c` - access)**

```c
#include <unistd.h>
#include <stdio.h>
#include <errno.h>

int main() {
    char *filename = "linux.txt";

    // F_OK: 파일 존재 여부 확인
    if (access("linux.bak", F_OK) == -1) {
        if (errno == ENOENT) printf("linux.bak: File does not exist.\n");
    }

    // R_OK: 읽기 권한 확인
    if (access(filename, R_OK) == 0) {
        printf("%s: Read permission granted.\n", filename);
    } else {
        printf("%s: Read permission denied.\n", filename);
    }

    return 0;
}
```

**2) Source Code (`ex3_7.c` - chmod)**


```c
#include <sys/types.h>
#include <sys/stat.h>
#include <stdio.h>

int main() {
    struct stat statbuf;
    
    // 방법 1: 정의된 상수를 이용한 권한 변경 (가독성 중시)
    // S_IRWXU: 소유자 rwx, S_IRGRP: 그룹 r, S_IXGRP: 그룹 x
    chmod("linux.txt", S_IRWXU | S_IRGRP | S_IXGRP | S_IROTH);

    // 방법 2: 8진수 값을 직접 이용 (실무적/직관적)
    // 0751: 소유자(7:rwx), 그룹(5:rx), 기타(1:x)
    chmod("linux.txt", 0751); 

    return 0;
}
```

**3) 컴파일 및 실행 결과**


```shell
# 권한 확인 및 변경 실습
$ gcc -o ex3_7 ex3_7.c
$ ./ex3_7
$ ls -l linux.txt
-rwxr-xr-x 1 user group 25 Mar 19 10:40 linux.txt
```

- **결과 분석:** `chmod` 호출 이후 `ls -l` 명령어로 확인했을 때, 지정한 8진수 값(`0751` 등)에 맞춰 파일 모드 비트가 즉각적으로 변경됨을 확인할 수 있습니다.

## 📌 기타 핵심 & CS Interview

- **기타 팁:** 교수님은 `S_IRUSR` 같은 복잡한 상수보다 **8진수 값(Octal, 0755 등)**을 직접 사용하는 것이 훨씬 직관적이고 빠르기 때문에 실무에서 선호된다고 강조하셨습니다.
- **디버깅 노하우:** `access()` 함수는 심볼릭 링크의 경우 원본 파일을 가리키지만, `stat` vs `lstat`의 차이처럼 대상이 무엇인지 명확히 인지하고 사용해야 합니다.
    

> [!faq]Q. `stat()`과 `access()`의 결정적인 차이점은 무엇인가요?
>
> **🗣️ 핵심 답변:** `stat()`은 파일의 모든 메타데이터를 구조체로 가져오는 무거운 작업인 반면, `access()`는 특정 권한의 가부(Yes/No)만을 빠르게 확인합니다. 또한 `access()`는 프로세스의 **실재 사용자(RUID)** 권한을 체크한다는 점이 보안상 중요합니다.
>
> **📚 꼬리질문 대비:** 만약 SetUID가 설정된 프로그램이라면, `access()`는 실행시킨 사용자의 권한을 보지만 `stat()`으로 확인한 권한은 파일 소유자의 권한을 따를 수 있어 결과가 다를 수 있습니다.

> [!faq]Q. `st_mode`가 16비트인데, 왜 8진수(Octal)로 주로 표현하나요?
>
> **🗣️ 핵심 답변:** 리눅스 권한 시스템(rwx)이 3비트 단위로 구성되어 있기 때문입니다. 8진수 숫자 하나가 정확히 3비트(`r=4, w=2, x=1`)를 표현하므로, `7(111)` 등과 같이 직관적인 대응이 가능합니다.

# 0. 수업 개요 - 2교시_2026.03.19

리눅스 파일 시스템의 핵심 개념인 **링크(Link)**의 두 종류(Hard Link, Symbolic Link)를 구분하고, 관련 시스템 호출을 통해 링크 생성, 정보 검색, 삭제 과정을 실습함.

### 🎯 이번 교시 핵심 실습 주제

- 1. 하드 링크(`link`)와 심볼릭 링크(`symlink`)의 구조적 차이 이해
- 2. `lstat()`, `readlink()`, `realpath()`를 이용한 링크 정보 관리
- 3. `unlink()`를 이용한 파일 삭제 메커니즘 확인
        

---

## 1. [Topic: 하드 링크 vs 심볼릭 링크]

- **Definition:** - **하드 링크 (Hard Link):** 기존 파일과 **동일한 Inode**를 공유하는 새로운 파일명을 생성합니다.
    - **심볼릭 링크 (Symbolic Link):** 원본 파일의 경로를 데이터로 가지는 **새로운 Inode**의 특수 파일을 생성합니다. (Windows의 '바로 가기'와 유사)
- **Why in OS:** 복잡한 경로에 대한 단축 경로 제공, 라이브러리 버전 관리, 파일 시스템 공간 절약 등을 위해 사용됩니다.
    

### 🏗️ 동작 원리 및 API 상세

- **하드 링크:** 링크 생성 시 Inode 내의 **Link Count**가 증가하며, 원본과 링크 파일이 완벽히 대등합니다. 같은 파일 시스템 내에서만 생성이 가능합니다.
- **심볼릭 링크:** 원본 파일과 별개의 Inode를 가지며, 파일 시스템을 가로질러(Cross-file system) 생성이 가능합니다. 원본이 삭제되면 'Broken Link'가 됩니다.
    

|**구분**|**하드 링크 (Hard Link)**|**심볼릭 링크 (Symbolic Link)**|
|---|---|---|
|**Inode**|원본과 동일|원본과 다름 (새로 생성)|
|**Link Count**|증가함|증가하지 않음|
|**타 파일 시스템**|불가|가능|
|**대상**|파일만 가능|파일 및 디렉터리 가능|

---

## 2. [Topic: 링크 생성 및 정보 검색 (`link`, `symlink`, `lstat`)]

- **Definition:** 링크를 생성하고, 링크 파일 자체가 가진 정보를 조회하는 API입니다.
- **API 스펙:**
    - `int link(const char *oldpath, const char *newpath);` (하드 링크)
    - `int symlink(const char *target, const char *linkpath);` (심볼릭 링크)
    - `int lstat(const char *pathname, struct stat *statbuf);` (링크 자체의 정보 조회)
        

### 🏗️ lstat()의 중요성

- `stat()` 함수는 심볼릭 링크를 인자로 받으면 **원본 파일**의 정보를 가져옵니다.
- 반면 `lstat()`은 심볼릭 링크 **파일 자체**의 정보(파일 종류가 'l'로 표시됨)를 가져옵니다.
    

### 💻 실제 실습 구현

**1) Source Code (`ex3_8_9.c` - 링크 생성 및 확인)**


```C
#include <sys/types.h>
#include <sys/stat.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    // 1. 하드 링크 생성
    link("linux.txt", "linux.ln");

    // 2. 심볼릭 링크 생성
    symlink("linux.txt", "linux.sym");

    struct stat buf;
    
    // stat()으로 심볼릭 링크 확인 시 원본 정보 출력
    stat("linux.sym", &buf);
    printf("stat(linux.sym) Inode: %ld\n", (long)buf.st_ino);

    // lstat()으로 심볼릭 링크 확인 시 링크 자체 정보 출력
    lstat("linux.sym", &buf);
    printf("lstat(linux.sym) Inode: %ld\n", (long)buf.st_ino);

    return 0;
}
```

**2) 컴파일 및 실행 결과**


```shell
$ gcc -o link_test ex3_8_9.c
$ ./link_test
$ ls -i linux.txt linux.ln linux.sym
# (결과) linux.txt와 linux.ln은 Inode 번호가 같고, linux.sym은 다름을 확인
```

## 3. [Topic: 링크 해석 및 삭제 (`readlink`, `realpath`, `unlink`)]

- **Definition:** 심볼릭 링크가 가리키는 대상의 경로를 읽거나, 링크를 끊어 파일을 삭제하는 기능입니다.
- **API 스펙:**
    - `ssize_t readlink(const char *pathname, char *buf, size_t bufsiz);`: 링크에 저장된 경로 문자열을 읽음. (NULL 종료 문자를 붙여주지 않으므로 주의)
    - `char *realpath(const char *path, char *resolved_path);`: 상대 경로를 절대 경로로 변환.
    - `int unlink(const char *pathname);`: 파일의 Link Count를 1 감소시킴. Count가 0이 되면 실제 데이터가 삭제됨.
        

### 💻 실제 실습 구현

**1) Source Code (`ex3_11.c` - readlink)**


```C
#include <unistd.h>
#include <stdio.h>

int main() {
    char buf[1024];
    int n;

    // 심볼릭 링크가 가리키는 원본 파일명 읽기
    n = readlink("linux.sym", buf, sizeof(buf)-1);
    if (n != -1) {
        buf[n] = '\0'; // NULL 문자 추가 필수
        printf("linux.sym points to: %s\n", buf);
    }
    return 0;
}
```

## 📌 기타 핵심 & CS Interview

- **명령행 인자(`argc`, `argv`) 활용 팁:**
    - `argv[0]`: 실행 파일 이름
    - `argv[1]`: 첫 번째 인자 (파일명 등)
    - 실습 시 `argc < 2` 조건을 통해 인자 누락 시 사용법(`Usage`)을 안내하는 예외 처리가 필수적임.
        

> [!faq]Q. 왜 `unlink()`는 'delete'가 아닌 'unlink'라는 이름을 사용하나요?
>
> **🗣️ 핵심 답변:** 리눅스에서 파일 삭제는 Inode와 파일명 사이의 **연결(Link)을 끊는 행위**이기 때문입니다. 하드 링크가 여러 개라면 `unlink()`를 호출해도 Link Count가 0이 아니면 데이터는 남게 되며, 0이 되는 순간 커널이 데이터를 삭제합니다.
>
> **📚 꼬리질문 대비:** 만약 어떤 프로세스가 파일을 열고(`open`) 있는 상태에서 `unlink()`를 하면 어떻게 될까요? 파일명은 디렉터리에서 사라지지만, 프로세스가 파일을 닫을 때까지 데이터 블록은 보존됩니다.

> [!faq]Q. 다른 하드디스크 파티션에 하드 링크를 생성할 수 없는 이유는?
>
> **🗣️ 핵심 답변:** 하드 링크는 동일한 Inode 번호를 공유해야 하는데, Inode 번호는 각 **파일 시스템 내에서만 유일**하기 때문입니다. 서로 다른 파일 시스템은 중복된 Inode 번호를 가질 수 있어 관리가 불가능합니다. (이 경우 심볼릭 링크를 사용해야 함)

### 🔑 오늘의 핵심 System Call & 개념

- **파일 정보 조회 계열**
    - **`stat()` / `fstat()`**: 파일의 경로명 또는 파일 기술자(fd)를 통해 **inode**에 저장된 메타데이터를 `struct stat` 구조체로 가져옵니다.
    - **`lstat()`**: 심볼릭 링크를 조회할 때, 원본이 아닌 **링크 파일 자체**의 정보를 가져오는 핵심 함수입니다.
- **권한 관리 계열**
    - **`access()`**: 프로세스의 실재 사용자(RUID) 기준으로 읽기/쓰기/실행/존재 여부를 빠르게 확인합니다.
    - **`chmod()`**: 파일의 접근 권한 비트를 수정합니다. (8진수 표기법 권장)
- **링크(Link) 관리 계열**
    - **`link()` / `symlink()`**: 각각 동일한 inode를 공유하는 **하드 링크**와 경로를 저장하는 **심볼릭 링크**를 생성합니다.
    - **`readlink()` / `realpath()`**: 심볼릭 링크의 데이터(원본 경로명)를 읽거나, 상대 경로를 절대 경로로 변환합니다.
    - **`unlink()`**: 파일의 링크 카운트를 감소시키며, 0이 될 때 실제 데이터 블록을 해제(삭제)합니다.

### 💡 교수님 강조 포인트

- **모든 것은 파일이다**: 리눅스에서 일반 파일, 디렉터리, 장치 파일은 모두 inode로 관리되며, `st_mode` 비트 마스크를 통해 이를 구분하는 것이 시스템 프로그래밍의 기초입니다.
- **8진수(Octal)의 직관성**: `S_IRUSR` 같은 긴 매크로 상수보다 `0755`, `0644`와 같은 8진수 값이 실무 코드 작성 및 권한 제어에서 훨씬 효율적이고 직관적입니다.
- **Hard Link의 제약**: 하드 링크는 같은 파일 시스템 내에서만 가능하며, 디렉터리에 대해서는 생성할 수 없다는 점을 명심해야 합니다. (이러한 제약 때문에 실무에서는 심볼릭 링크가 더 자주 사용됩니다.)
- **명령행 인자 예외 처리**: 시스템 유틸리티 작성 시 `argc`를 체크하여 인자가 부족할 경우 `Usage`를 출력하고 종료하는 습관은 견고한 프로그램을 만드는 첫걸음입니다.
