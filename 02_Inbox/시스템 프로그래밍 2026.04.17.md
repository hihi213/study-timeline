## 📝 정리
제시해주신 세 개의 표는 리눅스 시스템 프로그래밍에서 **프로세스의 생성부터 종료, 그리고 동기화**까지의 생명 주기를 관리하는 가장 핵심적인 API들입니다.

각 표의 핵심 내용을 개발자 관점에서 실무 포인트와 함께 정리해 드릴게요.

---

## ## 1. 프로세스 종료 및 핸들러 (표 7-2)

프로세스가 업무를 마칠 때 **"얼마나 정중하게 정리하고 떠날 것인가"**를 결정합니다.

|**함수**|**핵심 설명 및 차이점**|
|---|---|
|**`exit()`**|**정상 종료 (Standard C):** 모든 I/O 버퍼를 비우고(Flush), `atexit`으로 등록된 핸들러를 실행한 뒤 종료합니다.|
|**`_exit()`**|**즉시 종료 (System Call):** 핸들러 호출이나 버퍼 정리 없이 커널이 즉시 자원을 회수합니다. 보통 `fork()` 후 자식 프로세스 종료 시 사용합니다.|
|**`atexit()`**|**종료 작업 예약:** 프로세스 종료 시 자동으로 실행될 함수를 등록합니다. (인자 전달 불가, LIFO 구조)|
|**`on_exit()`**|**확장형 예약:** 종료 상태값(status)과 사용자 지정 인자를 핸들러에 전달할 수 있는 GNU 확장 함수입니다.|

> **💡 핵심 포인트:** `exit()`는 내부적으로 정리를 다 끝낸 후 마지막에 `_exit()`를 호출하여 커널에 실제 종료를 알립니다.

---

## ## 2. exec 함수군: 프로그램 교체 (표 7-3)

현재 프로세스의 메모리 이미지를 **새로운 실행 파일로 완전히 덮어쓰는** 함수들입니다. 이름의 접미사만 이해하면 사용법이 명확해집니다.

- **`l` (List):** 인자를 리스트 형태(`NULL`로 끝남)로 나열해서 전달합니다.
- **`v` (Vector):** 인자를 문자열 배열(argv)에 담아서 통째로 전달합니다.
- **`p` (Path):** 실행 파일의 절대 경로를 몰라도 `PATH` 환경 변수에서 찾아줍니다.
- **`e` (Environment):** 새로운 프로그램에 넘겨줄 환경 변수를 직접 지정합니다.
    

**[함수 조합 예시]**

- **`execlp("ls", "ls", "-al", NULL);`**: 경로 검색(`p`)을 사용하고 리스트(`l`)로 인자 전달.
- **`execve("/bin/ls", argv, envp);`**: 가장 원초적인 시스템 콜 형태. 배열(`v`)과 환경변수(`e`) 사용.
    

---

## ## 3. 프로세스 동기화: 부모-자식 조율 (표 7-4)

부모 프로세스가 자식 프로세스의 종료를 기다리고, 자식이 남긴 **종료 상태값(Exit Status)**을 수거하는 역할을 합니다.

|**함수**|**핵심 기능 및 활용**|
|---|---|
|**`wait()`**|자식 프로세스 중 **어느 하나라도** 종료될 때까지 부모를 대기(Block)시킵니다. **좀비 프로세스 방지**의 핵심입니다.|
|**`waitpid()`**|특정 `PID`를 가진 자식을 지정해서 기다릴 수 있습니다. `WNOHANG` 옵션을 주면 자식이 안 끝났어도 부모가 자기 할 일을 계속하는 **비차단 모드**가 가능합니다.|
|**`waitid()`**|`waitpid`보다 더 세밀한 제어(프로세스 그룹 단위 대기 등)가 필요할 때 사용하는 현대적인 함수입니다.|

---

## 🏁 요약: 프로세스 생명 주기 흐름도

1. **`fork()`**: 부모와 똑같은 복제본 자식을 생성합니다.
2. **`exec()` 계열**: 자식이 복제본 코드를 버리고 새로운 프로그램으로 탈바꿈합니다.
3. **`exit()`**: 자식이 업무를 마치고 종료 상태값을 남기며 사라집니다.
4. **`wait()`**: 부모가 자식의 종료를 확인하고 시스템 자원을 완전히 정리해줍니다.
- **부모에게 전달되는 정보:** 자식의 PID 이를 통해 부모는 "내가 낳은 자식이 누구인지" 알게 됩니다.
- **자식에게 전달되는 정보:** 숫자 `0`. 그래서 0일때 조건문으로 자식이 수행할 작업을 프로그래밍한다.


프로그램이 종료될 때 자동으로 실행될 '마무리 작업'을 예약하는 함수들입니다. 시스템 프로그래밍이나 백엔드 개발 시 로그를 남기거나, 임시 파일을 삭제하거나, 메모리를 해제하는 **Cleanup 작업**을 위해 자주 사용됩니다.

## 🛠️ atexit() vs on_exit() 비교

두 함수 모두 **종료 핸들러(Exit Handler)**를 등록하는 역할을 하지만, 표준성와 전달받는 인자에서 차이가 있습니다.

|**구분**|**atexit(3)**|**on_exit(3)**|
|---|---|---|
|**표준성**|ANSI C, POSIX 표준 (이식성 높음)|SunOS, GNU 확장 (비표준, glibc 필요)|
|**인자 전달**|불가 (핸들러 함수 인자가 `void`)|가능 (종료 상태값 + 사용자 지정 데이터)|
|**함수 원형**|`int atexit(void (*func)(void));`|`int on_exit(void (*func)(int, void *), void *arg);`|

---

## 1. atexit( ) : 표준 종료 핸들러

프로세스가 **정상 종료**될 때 호출될 함수를 등록합니다.

- **LIFO(Last In, First Out):** 가장 나중에 등록된 함수가 가장 먼저 실행됩니다. (스택 구조)
- **제약 사항:** 등록되는 함수는 인자를 받을 수 없고, 반환값도 없어야 합니다.
- **등록 제한:** 보통 최소 32개 이상의 함수를 등록할 수 있도록 보장됩니다.
    

C

```sql
#include <stdlib.h>
#include <stdio.h>

void cleanup() {
    printf("Cleaning up resources…\n");
}

int main() {
    atexit(cleanup); // 종료 시 cleanup 호출 예약
    printf("End of main.\n");
    return 0; // exit(0)와 동일하게 동작하며 cleanup 호출
}
```

---

## 2. on_exit( ) : 확장형 종료 핸들러

`atexit`보다 더 많은 정보를 핸들러에게 넘겨주고 싶을 때 사용합니다.

- **상태값 확인:** 프로세스가 어떤 상태로 종료(`exit` 인자값)되는지 핸들러가 알 수 있습니다.
- **데이터 전달:** 핸들러 등록 시 임의의 포인터(`arg`)를 넘겨줄 수 있어 데이터 처리가 유연합니다.
    

C

```sql
#include <stdlib.h>
#include <stdio.h>

void extended_cleanup(int status, void *arg) {
    printf("Exit status: %d, Message: %s\n", status, (char *)arg);
}

int main() {
    on_exit(extended_cleanup, "Goodbye!"); 
    exit(1); // 종료 상태값 1과 함께 "Goodbye!" 출력
}
```

## ⚠️ 매우 중요한 공통 주의사항

이 핸들러들이 **실행되지 않는 경우**를 반드시 숙지해야 합니다.

1. **비정상 종료:** `abort()` 함수 호출이나 시그널(SIGKILL, SIGSEGV 등)에 의해 강제 종료될 때는 실행되지 않습니다.
2. **`_exit()` 호출:** 커널 레벨의 종료 함수인 `_exit()`를 직접 호출하면 핸들러를 무시하고 즉시 종료됩니다.
3. **핸들러 내 exit:** 핸들러 함수 내부에서 다시 `exit()`를 호출하면 무한 루프에 빠질 수 있으므로 주의해야 합니다.

## 📑 exit( ) vs _exit( ) 비교표

| **구분**        | **exit()**                           | **_exit()**                       |
| ------------- | ------------------------------------ | --------------------------------- |
| **종류**        | 표준 C 라이브러리 함수 (`<stdlib.h>`)         | 시스템 콜 (System Call, `<unistd.h>`) |
| **사용자 수준 버퍼** | **모두 Flush(비우기)함** (printf 등 데이터 출력) | **비우지 않음** (출력 데이터가 유실될 수 있음)     |
| **종료 핸들러**    | `atexit`, `on_exit`로 등록된 함수 호출       | **호출하지 않음** (즉시 종료)               |
| **임시 파일 정리**  | 표준 I/O 스트림(tmpfile 등)을 닫고 정리함        | 정리 없이 종료                          |
| **사용 목적**     | 일반적인 프로그램의 정상 종료 시                   | `fork()` 이후 자식 프로세스에서 주로 사용       |

## 1. 데이터 유실의 위험 (I/O 버퍼)

가장 실무적으로 큰 차이는 **표준 I/O 버퍼(Buffered I/O)** 처리입니다.

- **`exit()`:** `printf` 등으로 출력했지만 아직 화면에 나오지 않고 메모리(버퍼)에 남아 있는 데이터를 모두 화면이나 파일로 쏟아내고 종료합니다.
- **`_exit()`:** 버퍼에 뭐가 들어있든 상관하지 않고 프로세스를 죽입니다. 만약 버퍼가 가득 차기 전에 `_exit()`를 만나면, 공들여 작성한 출력 내용이 사라질 수 있습니다.
    

---

## 2. 종료 핸들러 호출 여부

이전 질문에서 다뤘던 `atexit()`나 `on_exit()`와의 관계입니다.

- **`exit()`**를 호출하면 우리가 예약해둔 **cleanup 함수들이 차례대로 실행**됩니다.
- **`_exit()`**를 호출하면 커널이 즉시 자원을 회수하므로 **예약된 함수들이 무시**됩니다.
    

---

## 3. 왜 `_exit()`가 필요한가? (fork와의 관계)

"그럼 정중한 `exit()`만 쓰면 되지, 왜 무례한 `_exit()`가 있나요?"라는 의문이 생길 수 있습니다.

주로 **`fork()`로 자식 프로세스를 만들었을 때** 사용합니다.

1. `fork()`를 하면 자식은 부모의 메모리(버퍼 포함)를 그대로 복사합니다.
2. 자식이 `exit()`를 호출하면, 부모로부터 복사해온 **I/O 버퍼를 비우면서 데이터를 출력**해버립니다.
3. 나중에 부모도 `exit()`를 하면 **같은 데이터가 또 출력**되는 '중복 출력' 사고가 발생할 수 있습니다.
4. 그래서 자식 프로세스는 부모의 스트림을 건드리지 않고 깔끔하게 몸만 빠져나가기 위해 **`_exit()`**를 사용하는 것이 관례입니다.

## 💡 결론 요약

> **일반적인 상황(main함수 끝 등)에서는 무조건 `exit()`**를 쓰시고, **`fork()`로 만든 자식 프로세스를 종료할 때는 `_exit()`**를 쓰는 것이 시스템 프로그래밍의 정석입니다.

**`exit()`는 내부적으로 모든 정리를 마친 뒤, 마지막에 결국 `_exit()`를 호출하여 커널에 종료를 알립니다.** 즉, `exit()`는 `_exit()`를 감싸고 있는 더 친절한 포장지라고 이해하시면 됩니다.

## 🛠️ exec 함수군 접미사 의미 (Naming Convention)
- **성공 시:** 프로세스의 텍스트, 데이터, 힙, 스택 영역이 새 프로그램으로 완전히 교체됩니다. 따라서 `exec` 호출 이후의 기존 코드는 실행되지 않습니다.
- **실패 시:** `-1`을 반환하며 제어권이 기존 코드로 돌아와 에러 처리(`perror` 등)를 수행합니다.
- `exec` 함수군은 현재 실행 중인 프로세스를 **새로운 프로그램으로 완전히 대체**하는 역할을 합니다. 이름 뒤에 붙는 알파벳(`l`, `v`, `p`, `e`)들만 이해하면 각 함수의 특징을 바로 파악할 수 있습니다.

이름 뒤에 붙는 글자들은 **"인자를 어떻게 전달할 것인가?"**와 **"프로그램을 어디서 찾을 것인가?"**를 결정합니다.

| **접미사**               | **설명**                                                           |
| --------------------- | ---------------------------------------------------------------- |
| **`l` (List)**        | 인자를 List(나열되게)으로 하나씩 직접 전달합니다. list이므로 마지막은 반드시 `NULL`로 끝나야 합니다. |
| **`v` (Vector)**      | 인자를 배열(Vector/Array)에 담아서 통째로 전달합니다.  (인자 개수가 유동적일때 유리)          |
| **`p` (Path)**        | 실행 파일을 찾을 때 환경 변수 `PATH`를 참조합니다. (경로 없이 파일명만 써도 됨)               |
| **`e` (Environment)** | 새로운 프로그램에 부모의 환경 변수 대신 환경 변수를 직접 지정할 수 있습니다.                     |

## 🔍 2. 실행 파일 탐색 및 실행 메커니즘
### 1. `ls`는 명령어이기 이전에 '파일'입니다.
* **오해:** `ls` = "현재 폴더를 보여줘"라는 뜻의 고유 명사나 상수.
* **진실:** `ls`는 `/bin/ls`라는 경로에 실제로 존재하는 **기계어 코드 파일(Binary)**입니다.
* **코딩 시점:** `execlp("ls", …)`라고 쓰는 것은 "컴퓨터 어딘가에 있는 `ls`라는 이름의 프로그램을 실행해줘"라고 요청하는 것과 같습니다.

### 2. 찾는 위치는 현재 폴더(CWD)가 아니라 PATH입니다. (`p`의 역할)
* **오해:** 현재 내가 `ch6` 폴더에 있으니 거기서 `ls`를 찾겠지?
* **진실:** `execlp`의 `p`는 **`PATH` 환경 변수**를 의미합니다. 시스템은 현재 폴더(`ch6`)는 쳐다보지도 않고, 설정된 `PATH` 목록(`/bin`, `/usr/bin` 등)만 순서대로 뒤집니다.
* **보안 상식:** 만약 시스템이 현재 폴더를 먼저 뒤진다면, 누군가 악의적으로 만든 가짜 `ls` 파일을 내 폴더에 던져놨을 때 내가 그걸 실수로 실행할 수 있겠죠? 그래서 리눅스는 기본적으로 **현재 폴더(`.`)를 검색 대상에서 제외**합니다.

### 3. `ls`가 `ch6`를 출력하는 건 '상속' 때문이다

- `exec` 이후에도 기존 프로세스의 **현재 작업 디렉터리(CWD)** 상태 정보가 유지되기 때문에, 새로 로드된 `ls` 바이너리가 커널로부터 해당 위치 정보를 읽는 동작을 실행할수있는 겁니다.

### 💡 마지막 팁: 직접 만든 파일 실행하기
이제 이 로직을 이해하셨다면 왜 직접 만든 프로그램을 실행할 때 아래와 같이 차이가 나는지 알 수 있습니다.

* `execlp("my_prog", …);` $\rightarrow$ **실패** (시스템 `PATH`에는 내 폴더가 없으니까요)
* `execl("./my_prog", …);` $\rightarrow$ **성공** (`p`를 빼고 주소`./`를 직접 찍어줬으니까요)

## 📂 함수 조합별 특징 및 사용법

### 1. 인자 전달 방식에 따른 분류 (l vs v)

- **`execl` (List):** 인자 개수가 고정적이고 적을 때 직관적입니다.
    - `execl("/bin/ls", "ls", "-l", NULL);`
- **`execv` (Vector):** 인자의 개수가 가변적이거나 배열로 이미 존재할 때 사용합니다.
    - `char *args[] = {"ls", "-l", NULL};`
    - `execv("/bin/ls", args);`
        

### 2. 경로 탐색 여부에 따른 분류 (p)

- **`execlp`, `execvp` (Path):** 파일의 절대 경로를 몰라도 됩니다. 시스템이 알아서 `PATH` 내에서 찾아줍니다.
    - `execlp("ls", "ls", "-l", NULL);` ( `/bin/ls`라고 안 써도 됨)

### 3. 환경 변수 설정 여부에 따른 분류 (e)

- **`execle`, `execve` (Environment):** 기존 부모의 환경 변수를 물려받지 않고, 새로 정의한 환경 변수 세트를 넘겨주고 싶을 때 사용합니다.
    - `char *env[] = {"USER=admin", "PATH=/usr/bin", NULL};`
    - `execve("/bin/ls", args, env);`

## ⚠️ 핵심 주의사항
1. **프로세스 대체:** `exec` 호출이 성공하는 순간, 그 이후의 코드는 메모리에서 사라집니다. **"exec 성공 = 돌아오지 않는 강을 건넘"**이라고 생각하세요. 실패했을 때만 돌아와 하단 코드들이 실행됩니다.
2. **첫 번째 인자의 관례:** $argv[0]$에 해당하는 첫 번째 인자에는 관례적으로 **실행 파일 이름 자체**를 넣어줍니다. (예: `execlp("ls", "ls", …)`에서 두 번째 "ls")
3. **NULL 종료:** `l` 계열 함수를 쓸 때는 인자 리스트의 끝에 반드시 `NULL`을 넣어 컴퓨터에게 "여기까지가 인자다"라고 알려줘야 합니다.

쉽게 요약하자면 **`exec` 함수군은 [어떻게 줄래? + 어디서 찾을래? + 환경은 어쩔래?]의 조합**입니다.

---


| **구분**    | **접미사**   | **결정적 질문**                                 |
| --------- | --------- | ------------------------------------------ |
| **전달 방식** | **l / v** | "인자를 하나씩 나열할까(List), 배열로 묶어줄까(Vector)?"    |
| **탐색 방식** | **p**     | "파일의 정확한 경로를 아는가, 아니면 이름만 아는가(Path)?"      |
| **환경 설정** | **e**     | "부모의 설정을 그대로 쓸까, 내가 새로 정의할까(Environment)?" |

`execvp`라는 이름을 보면 **"아, 배열(v)로 인자를 주고, PATH(p)에서 파일을 찾으라는 뜻이구나!"**


### 1. "어떻게 줄래?" (인자 전달 방식: `l` vs `v`)

이건 말씀하신 대로 **코드를 짜는 사람의 편의성** 차이입니다.

- **`l` (List):** "내가 인자 개수를 정확히 아니까 하나씩 나열할게."
    - `execl("/bin/ls", "ls", "-l", NULL);`
- **`v` (Vector):** "인자가 몇 개일지 모르거나, 이미 배열에 담겨 있어."
    - `char *argv[] = {"ls", "-l", NULL}; execv("/bin/ls", argv);`

---

### 2. "어디서 찾을래?" (경로 탐색 방식: `p` 유무)

이게 질문하신 "프로그램을 어디서 찾을지"에 대한 핵심입니다.

- **`p`가 없는 경우:** 첫 번째 인자에 **정확한 경로**를 줘야 합니다. (예: `/bin/ls`)
- **`p`가 있는 경우:** 첫 번째 인자에 **파일명**만 써도 됩니다. 시스템이 `PATH` 환경 변수에 등록된 폴더들을 샅샅이 뒤져서 찾아냅니다. (예: `ls`)
---

### 3. "환경은 어쩔래?" (환경 변수 설정: `e` 유무)

표에 있던 마지막 차이점이죠.

- **`e`가 없는 경우:** 현재 내 프로세스가 가진 환경 변수(설정값들)를 그대로 자식에게 물려줍니다.
- **`e`가 있는 경우:** "기존 건 다 버리고, 내가 새로 만든 환경 변수 세트만 써라"고 명령할 때 사용합니다.

|**구분**|**접미사**|**핵심 역할**|**코드 작성자의 관점**|
|---|---|---|---|
|**전달 방식**|**`l` / `v`**|인자를 나열할 것인가, 배열로 줄 것인가?|**"내 코드가 짜기 편한 방식은?"**|
|**탐색 방식**|**`p`**|절대 경로를 쓸 것인가, 이름만 쓸 것인가?|**"실행 파일 위치를 정확히 아는가?"**|
|**환경 설정**|**`e`**|부모의 환경을 쓸 것인가, 새로 정의할 것인가?|**"환경 변수 제어가 필요한가?"**|
