## 1. [Topic: 리눅스/유닉스 생태계와 서버 아키텍처]

- **Definition:** 유닉스(UNIX)는 1969년 AT&T 벨 연구소에서 개발된 멀티태스킹 운영체제이며, 리눅스(Linux)는 이를 모태로 하여 리누스 토발즈가 개발한 오픈 소스 커널 기반 운영체제입니다.
- **Why in OS:** 현대의 서버 인프라는 클라이언트의 요청을 효율적으로 처리하기 위해 높은 안정성과 다중 사용자 환경을 지원해야 하며, 리눅스는 이 요구사항을 충족하는 표준 서버 OS로 자리 잡았습니다.
    

### 🏗️ 동작 원리 및 계보

- **서버-클라이언트 모델:** 서버는 UI(GUI)보다는 백엔드 처리 및 자원 제공에 집중하며, 리눅스는 이러한 서버 환경에 최적화된 구조를 가집니다.
- **주요 계보:**
    - **System V:** AT&T의 상용 유닉스 정통 계보.
    - **BSD:** 버클리 대학에서 발전시킨 계열로, 현대 인터넷의 핵심인 **TCP/IP 스택**을 최초로 구현 및 표준화함.
    - **Linux:** 오픈 소스 운동의 결과물로, 다양한 배포판(Ubuntu, CentOS 등)으로 파생되어 현재 서버 시장을 주도함.
- **모바일 확장:** 리눅스 커널은 안드로이드(Android)의 기반이 되었고, BSD 계열은 macOS 및 iOS의 뿌리가 되었습니다.

## 2. [Topic: 시스템 호출(System Call) vs 라이브러리(Library)]

- **Definition:** 시스템 호출은 응용 프로그램이 커널(Kernel)에 특정 서비스를 요청하는 유일한 통로이며, 라이브러리는 시스템 호출을 사용자 수준에서 더 편리하게 사용할 수 있도록 래핑한 함수들의 집합입니다.
- **Why in OS:** 하드웨어 자원(파일 시스템, 메모리, 네트워크 등)은 커널이 독점적으로 관리하므로, 사용자 프로그램이 안전하게 자원을 사용하기 위해서는 반드시 시스템 호출 인터페이스를 거쳐야 합니다.
    

### 🏗️ 동작 원리 및 API 상세

- **내부 메커니즘:**
    - 응용 프로그램이 **시스템 호출**을 발생시키면, CPU는 사용자 모드(User Mode)에서 커널 모드(Kernel Mode)로 전환(Context Switch)됩니다.
    - 커널은 요청된 작업을 수행한 후 다시 사용자 모드로 복귀하여 결과를 반환합니다.
- **주요 차이점:**
    - 시스템 호출은 커널의 기능을 수행하므로 **모드 전환(User $\leftrightarrow$ Kernel Mode Switching)** 오버헤드가 발생합니다.
    - 라이브러리 함수는 프로그래머의 편의를 위해 표준 C 라이브러리(`libc`) 등에서 제공하며, 내부적으로 시스템 호출을 포함하거나 포함하지 않을 수 있습니다.

## 3. [Topic: 유닉스/리눅스 표준 규격 (POSIX, SUS 등)]

- **Definition:** 서로 다른 유닉스/리눅스 변종 간의 소스 코드 호환성과 이식성을 보장하기 위해 제정된 인터페이스 표준 규칙입니다.
- **Why in OS:** 파생된 운영체제마다 시스템 호출의 이름이나 동작이 다르면 소프트웨어 재사용성이 현격히 떨어지므로, 업계 표준을 통해 "한 번 작성한 코드가 어디서든 빌드"되도록 보장합니다.
    

### 🏗️ 주요 표준 규격 상세

- **ANSI C (ISO C):** C 언어 자체의 문법 및 표준 라이브러리에 대한 표준입니다. 리눅스 시스템 프로그래밍의 기초가 됩니다.
- **POSIX (Portable Operating System Interface):** IEEE에서 정의한 유닉스 시스템의 공통 API 규격입니다. 리눅스는 공식 인증을 받지는 않았으나, 이 표준을 거의 완벽하게 준수하도록 설계되었습니다.
- **SUS (Single UNIX Specification):** 'UNIX'라는 상표권을 사용하기 위해 지켜야 하는 단일 명세입니다. 리눅스는 철학적/비용적 이유로 인증을 받지 않는 경우가 많지만, 기능적으로는 SUS와 대등한 수준을 유지합니다.
- **기타 표준:**
    - **LSB (Linux Standard Base):** 리눅스 배포판 간 바이너리 호환성을 위한 표준.
    - **FHS (Filesystem Hierarchy Standard):** `/bin`, `/usr`, `/etc` 등 디렉터리 구조 및 파일 배치에 대한 표준.

## 4. [Topic: man 페이지와 섹션 구조]

- **Definition:** 리눅스 터미널 환경에서 명령어, 시스템 호출, 라이브러리 함수에 대한 기술 문서를 조회하는 명령어(`man`) 및 그 체계입니다.
- **Why in OS:** 인터넷 연결이 없는 환경에서도 API의 인자값, 반환값, 필요 헤더를 즉각적으로 확인할 수 있는 가장 신뢰도 높은 공식 문서이기 때문입니다.
    

### 🏗️ 동작 원리 및 API 상세

리눅스 매뉴얼은 정보의 성격에 따라 8개 이상의 섹션으로 구분됩니다.

| **섹션 번호**     | **주요 내용**                          | **예시**                            |
| ------------- | ---------------------------------- | --------------------------------- |
| **Section 1** | 일반 사용자 명령어 (User Commands)         | `ls`, `cp`, `mv`, `uname`         |
| **Section 2** | **시스템 호출 (System Calls)**          | `open()`, `fork()`, `read()`      |
| **Section 3** | **C 라이브러리 함수 (Library Functions)** | `printf()`, `fopen()`, `malloc()` |

### 💻 실제 실습 구현 (man 활용)

**1) 특정 섹션 지정 조회 명령어**


```shell
# 일반적인 명령어 uname 정보 조회 (Section 1)
$ man uname

# 시스템 호출로서의 uname 정보 조회 (Section 2)
$ man 2 uname

# 라이브러리 함수로서의 fopen 정보 조회 (Section 3)
$ man 3 fopen
```

- **결과 분석:** 동일한 이름(`uname`)이라도 섹션 번호를 지정함에 따라 사용자 명령어에 대한 설명인지, C 프로그래밍에서 사용하는 시스템 호출 함수에 대한 설명인지가 달라집니다. 시스템 프로그래머는 주로 **Section 2와 3**을 참조합니다.

## 📌 기타 핵심 & CS Interview

- **기타 팁:** 시스템 호출과 라이브러리 함수를 엄격히 구분하여 외울 필요는 없으나, `man` 페이지 상단에 표시되는 섹션 번호(2 또는 3)를 통해 해당 함수의 계층을 파악하는 습관이 중요합니다.
    

> [!faq]- Q. 시스템 호출(System Call)과 라이브러리 함수(Library Function)의 성능적 차이는?
>
> **🗣️ 핵심 답변:** 시스템 호출은 실행 시 유저 모드에서 커널 모드로의 **문맥 전환(Context Switching)**이 발생하므로 오버헤드가 큽니다. 반면 라이브러리 함수는 유저 모드에서 실행되며, 내부적으로 시스템 호출을 최소화하도록 최적화(예: 버퍼링)되어 있는 경우가 많습니다.
>
> - 라이브러리의 버퍼링: 유저영역의 버퍼에다가 데이터를 모았다가 버퍼가 가득차면 그제서야 시스템 호출을 한번 호출
>
> **📚 꼬리질문 대비:** 그렇다면 왜 항상 라이브러리만 쓰지 않고 시스템 호출을 직접 쓰는가? 하드웨어의 미세한 제어가 필요하거나 라이브러리가 제공하지 않는 커널 전용 기능을 수행해야 할 때는 직접 시스템 호출을 사용해야 합니다.

> [!faq]- Q. POSIX 표준이 리눅스 생태계에서 중요한 이유는?
>
> **🗣️ 핵심 답변:** 소스 코드의 **이식성(Portability)** 때문입니다. POSIX를 준수하여 작성된 프로그램은 리눅스뿐만 아니라 UNIX, macOS 등 다른 POSIX 준수 OS에서도 최소한의 수정만으로 컴파일 및 실행이 가능합니다.
>
> **📚 꼬리질문 대비:** 리눅스는 왜 공식 유닉스(SUS) 인증을 받지 않는 경우가 많은가? 인증 비용이 고가이며, 오픈 소스 정신에 따라 특정 상업 단체의 상표권에 종속되지 않으려는 철학적 이유 때문입니다.

## 2. [Topic: 시스템 호출 오류 처리 (`errno`)]

- **Definition:** 시스템 호출이나 라이브러리 함수가 실패했을 때, 커널이 설정하는 전역 변수 `errno`를 통해 구체적인 오류 원인을 파악하는 기법입니다.
- **Why in OS:** 시스템 호출은 다양한 외부 요인(권한, 파일 부재 등)으로 실패할 가능성이 높으므로, 정확한 예외 처리가 프로그램의 안정성을 결정합니다.

### 🏗️ 동작 원리 및 API 상세

- **리턴값 규칙:**
    - **System Call:** 성공 시 0 이상, 실패 시 `-1` 반환 및 `errno` 설정.
    - **Library Function:** 실패 시 보통 `NULL` 또는 `0` 반환.
- **주요 함수:**
    - `perror(const char *s)`: 표준 오류(stderr)로 "사용자 메시지: 오류 내용"을 즉시 출력.
    - `strerror(int errnum)`: 오류 번호에 해당하는 문자열 포인터를 반환 (가공 출력 시 유리).

![정리](라이브러리%20함수의%20에러처리.md#정리)
### 💻 실제 실습 구현

**1) Source Code (`ch1_error.c`)**

```C
#include <stdio.h>
#include <unistd.h>     // access()
#include <errno.h>      // errno
#include <string.h>     // strerror()
#include <stdlib.h>     // exit()

extern int errno;       // 외부 전역 변수 errno 선언

int main() {
    // 1. 존재하지 않는 파일에 대한 접근 시도 (F_OK: 존재 여부 확인)
    if (access("test.txt", F_OK) == -1) {
        // 방법 A: errno 직접 출력
        printf("Error Number: %d\n", errno); // 파일 없을 시 2 (ENOENT) 출력

        // 방법 B: perror() 사용 (가장 권장)
        perror("test.txt 접근 오류");

        // 방법 C: strerror()로 메시지 가공
        char *err_msg = strerror(errno);
        printf("가공된 오류 메시지: %s (파일: test.txt)\n", err_msg);
        
        exit(1);
    }
    return 0;
}
```

- **`access()`** : 로그인한 사용자 권한으로 파일에 접근하는 시스템 호출
	- **`F_OK`**: **Existence test**. 파일의 **존재 여부**만 체크하라는 플래그
	- 시스템 호출이므로 성공시 0, 실패시 -1 반환뒤 errno에 오류이유번호를 적어둠

**2) 컴파일 및 실행 결과**


```shell
$ gcc -o ch1_error ch1_error.c
$ ./ch1_error

# 실행 결과 (test.txt가 없을 경우)
Error Number: 2
test.txt 접근 오류: No such file or directory
가공된 오류 메시지: No such file or directory (파일: test.txt)
```

- **결과 분석:** `errno` 2번은 `ENOENT` 상수로 정의되어 있으며, 이는 "해당 파일이나 디렉터리가 없음"을 의미합니다.
    
## 3. [Topic: GCC 컴파일 및 빌드 자동화 (Make)]

- **Definition:** `gcc`는 GNU 프로젝트의 C 컴파일러이며, `make`는 여러 소스 파일 간의 의존성을 관리하여 빌드 과정을 자동화하는 유틸리티입니다.
- **Why in OS:** 시스템 프로그래밍은 커널과 밀접하게 동작하는 대규모 코드를 다루므로, 수정된 파일만 선별적으로 재컴파일하는 효율적인 빌드 관리가 필수적입니다.

### 🏗️ 동작 원리 및 CLI 스펙

- **GCC 주요 옵션:**
    - `-o [파일명]`: 출력 실행 파일의 이름을 지정 (기본값: `a.out`).
    - `-c`: 링크 과정을 생략하고 오브젝트 파일(`.o`)만 생성.
- **Makefile 구조:**
    - **Target (대상):** 빌드 결과물 (실행 파일 또는 오브젝트 파일).
    - **Dependency (의존성):** 대상을 만들기 위해 필요한 소스 파일들.
    - **Command (명령):** 의존성 파일이 변경되었을 때 실행할 셸 명령어 (반드시 **Tab**으로 들여쓰기).
        
![📝 정리](목적파일과%20실행파일의%20차이와%20명령어와%20Makefile%20빌드%20시스템.md#📝%20정리)
### 💻 실제 실습 구현 (다중 소스 빌드)

**1) Source Code (`main.c` / `add_num.c`)**

```C
// main.c
#include <stdio.h>
extern int add_num(int a, int b); // 외부 함수 선언

int main() {
    int sum = add_num(1, 5);
    printf("1부터 5까지의 합: %d\n", sum);
    return 0;
}

// add_num.c
int add_num(int a, int b) {
    int res = 0;
    for (int i = a; i <= b; i++) res += i;
    return res;
}
```

**2) Makefile 구성**

```Makefile
# 변수 설정
CC = gcc
OBJS = main.o add_num.o
TARGET = add.out

# 최종 타겟 빌드 규칙
$(TARGET): $(OBJS)
	$(CC) -o $(TARGET) $(OBJS)

# 개별 소스 컴파일 규칙
main.o: main.c
	$(CC) $(CFLAGS) -c main.c

add.o: add.c
	$(CC) $(CFLAGS) -c add.c

# 정리 규칙
clean:
	rm -f $(OBJS) $(TARGET)
```

- **결과 분석:** `make` 실행 시 소스 코드의 수정 여부를 타임스탬프로 확인하여, 변경된 파일만 다시 컴파일하므로 대규모 프로젝트에서 시간을 획기적으로 단축합니다.

## 4. [Topic: 동적 메모리 할당 및 명령행 인자]

- **Definition:** 실행 시점에 필요한 만큼 힙(Heap) 영역에서 메모리를 할당받는 기법과, 프로그램 실행 시 터미널에서 전달되는 인자를 처리하는 방식입니다.
- **Why in OS:** 고정된 배열 크기만으로는 가변적인 데이터를 처리할 수 없으며, 유틸리티 프로그램(예: `ls -l`)은 사용자 인자에 따라 실행 로직을 결정해야 하기 때문입니다.
    

### 🏗️ API 상세 스펙

- **메모리 할당:**

|**함수명**|**주요 특징**|
|---|---|
|**`malloc()`**|요청한 바이트 크기만큼 메모리 할당. 초기화되지 않음(쓰레기 값 존재).|
|**`calloc()`**|(개수 $\times$ 크기)만큼 할당하고 모든 비트를 **0으로 초기화**.|
|**`realloc()`**|이미 할당된 메모리 블록의 크기를 변경. 기존 데이터는 유지됨.|
|**`free()`**|할당받은 메모리를 커널에 반납. (Memory Leak 방지 필수)|
- **명령행 인자 (`main` 함수 확장):**
    - `int argc`: 인자의 개수 (실행 파일명 포함).
    - `char *argv[]`: 인자 문자열들의 배열.

### 💻 실제 실습 구현

**1) Source Code (`ch1_args.c`)**

```C
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]) {
    printf("인자 개수: %d\n", argc);
    
    for(int i = 0; i < argc; i++) {
        printf("argv[%d]: %s\n", i, argv[i]);
    }

    // 예시: 정수 200개 동적 할당
    int *ptr = (int *)malloc(sizeof(int) * 200);
    if (ptr == NULL) return 1; // 할당 실패 예외 처리
    
    free(ptr); // 사용 후 반드시 해제
    return 0;
}
```

**2) 실행 결과**


```shell
$ gcc -o ch1_args ch1_args.c
$ ./ch1_args -h 2000

# 출력
인자 개수: 3
argv[0]: ./ch1_args
argv[1]: -h
argv[2]: 2000
```

## 📌 기타 핵심 & CS Interview

- **기타 팁:** 실행 파일이 현재 디렉터리에 있는데도 실행되지 않는다면 `./`를 앞에 붙여야 합니다. 이는 보안상의 이유로 현재 디렉터리(`.`)가 `PATH` 환경 변수에 기본 포함되지 않기 때문입니다.
    

> [!faq]- Q. `malloc`과 `calloc`의 결정적인 차이는 무엇인가요?
>
> **🗣️ 핵심 답변:** 가장 큰 차이는 **메모리 초기화 여부**입니다. `malloc`은 할당만 수행하여 기존의 쓰레기 값이 남아있을 수 있지만, `calloc`은 할당된 영역을 모두 0으로 초기화합니다.
>
> **📚 꼬리질문 대비:** 성능 면에서는 초기화 과정이 없는 `malloc`이 미세하게 빠를 수 있으나, 예측 가능한 동작을 위해서는 초기화가 필요할 때 `calloc`을 쓰는 것이 안전합니다.

> [!faq]- Q. `argv[0]`에는 항상 무엇이 담기나요?
>
> **🗣️ 핵심 답변:** 프로그램을 실행할 때 사용한 **실행 파일의 경로 및 이름**이 담깁니다.
>
> **📚 꼬리질문 대비:** 이를 활용하여 프로그램 내부에서 자기 자신의 이름을 출력하거나, 실행 파일 명칭에 따라 다른 모드로 동작하게 설계할 수 있습니다.

## 1. [Topic: 리눅스 파일 종류와 inode]

- **Definition:** 리눅스는 모든 자원을 파일로 관리하며, 파일명-`inode`-데이터 블록의 3단계 구조로 데이터를 저장합니다. `inode`는 파일명 이외의 모든 메타데이터를 담고 있는 색인 객체입니다.
- **Why in OS:** 하드웨어 장치(특수 파일)조차 파일 인터페이스로 추상화함으로써, 일관된 시스템 호출(read/write)로 시스템 전체를 제어하기 위함입니다.
### 🏗️ 동작 원리 및 메커니즘

- **파일의 3요소:**
    1. **파일명:** 사용자가 식별하는 이름.
    2. **아이노드(inode):** 파일의 종류, 권한, 소유자, 시간 정보, **데이터 블록의 주소** 등을 포함하는 테이블.
    3. **데이터 블록:** 실제 데이터(텍스트, 바이너리 등)가 저장되는 하드디스크 공간.
- **파일의 종류:**
    - **일반 파일(`-`):** 텍스트, 바이너리, 이미지 등 실제 데이터 저장.
    - **디렉터리(`d`):** 파일 이름과 해당 파일의 `inode` 번호 목록을 저장하는 특수한 파일.
    - **특수 파일:** 장치 파일(문자 `c`, 블록 `b`), 심볼릭 링크(`l`), 파이프 등.
- **`inode` (Index Node):**
    - 커널이 파일을 식별하는 실제 번호.
    - 포함 정보: 파일 종류, 접근 권한, 소유자, 파일 크기, 수정 시간, 데이터 블록 포인터 등.
    - `ls -i` 명령어로 각 파일의 고유 `inode` 번호 확인 가능.

## 2. [Topic: 디렉터리 생성, 삭제 및 이름 변경]

- **Definition:** 디렉터리를 생성(`mkdir`), 비어 있는 디렉터리를 삭제(`rmdir`), 또는 디렉터리/파일명의 이름을 변경하거나 위치를 이동(`rename`)하는 시스템 호출입니다.
- **Why in OS:** 파일 시스템의 계층 구조(Hierarchy)를 동적으로 관리하기 위해 필수적인 API입니다.
    

### 🏗️ API 스펙 상세

- **`int mkdir(const char *pathname, mode_t mode);`**
    - **성공 시:** 0, **실패 시:** -1 (`errno` 설정).
    - **`mode`:** 8진수 권한 설정 (예: `0755`).
	    - c언어에서 8진수는 숫자앞에 '0'를 붙임
- **`int rmdir(const char *pathname);`**
    - 대상 디렉터리가 반드시 **비어 있어야** 삭제 가능.
- **`int rename(const char *oldpath, const char *newpath);`**
    - 파일이나 디렉터리의 이름을 바꾸거나 경로를 이동할 때 사용.
        

### 💻 실제 실습 구현

**1) Source Code (`ch2_mkdir_rename.c`)**



```C
#include <sys/stat.h>
#include <sys/types.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    // 1. 디렉터리 생성 (권한 0755: rwxr-xr-x)
    if (mkdir("suwon", 0755) == -1) {
        perror("mkdir");
        exit(1);
    }

    // 2. 이름 변경 (suwon -> univ)
    if (rename("suwon", "univ") == -1) {
        perror("rename");
        exit(1);
    }

    return 0;
}
```

**2) 컴파일 및 실행 결과**


```shell
$ gcc -o ch2_dir ch2_mkdir_rename.c
$ ./ch2_dir

# 결과 확인
$ ls -ld univ

```

## 3. [Topic: 작업 디렉터리 위치 제어 (`getcwd`, `chdir`)]

운영체제에서 모든 **상대 경로**는 현재 작업 디렉터리(**CWD**, Current Working Directory)를 기준으로 해석됩니다. CWD는 커널 내의 **PCB**에 저장되어 관리되며, 프로세스가 파일 시스템을 탐색하는 기준점이 됩니다.
### 📊 getcwd vs chdir 비교

| **구분**  | **getcwd**                  | **chdir(Change Directory)** |
| ------- | --------------------------- | --------------------------- |
| **성격**  | Library Function (표준 라이브러리) | **System Call** (커널 직접 요청)  |
| **역할**  | 현재 프로세스의 **절대 경로** 조회       | 프로세스의 **CWD 위치 변경**         |
| **성공시** | 경로문자열이 담긴 `buf` 주소 반환       | `0` 반환                      |
| **실패시** | `NULL` 반환 & `errno` 설정      | `-1`  반환 & `errno` 설정       |


### 🔍 1. getcwd: 현재 경로 확인

> `char *getcwd(char *buf, size_t size);`

- **기능**: 현재 프로세스의 절대 경로를 `\0`(널 문자)을 포함하여 `size`만큼 `buf`에 복사합니다.
- **안전한 버퍼 관리:** * `<limits.h>`의 **`PATH_MAX`** 상수를 사용하면 대부분의 시스템에서 경로를 담기에 충분한 크기를 확보할 수 있습니다.
	- `buf`에 `NULL`을 전달하면 함수가 내부적으로 `malloc`을 수행하므로 사용 후 반드시 `free()`를 호출해 메모리 누수를 막아야 합니다.

---

### 🚀 2. chdir: 작업 디렉터리 변경

> `int chdir(const char *path);`

- **기능**: 호출한 프로세스의 PCB에 기록된 CWD 값을 `path`로 변경합니다
- 자식의 상태변화는 부모에게 영향을 주지 않기 때문에, chdir호출은 누가 호출하는지가 중요합니다 그래서 `cd`는 별도 프로그램이 아닌 쉘의 '내장 명령어'로 설계되었습니다. 
- 모든 프로세스는 자신만의 독립된 메모리와 PCB 정보를 가지기 때문에 **자식 프로세스의 상태 변화는 절대로 부모 프로세스에 영향을 줄 수 없습니다.**
- 따라서 특정 프로세스에서 `chdir`을 호출해 위치를 바꿔도, 그 프로세스가 종료되어 부모로 돌아가면 부모의 위치는 그대로 유지됩니다.
- `ls`, `mkdir`, `rm`등의 일반적인 명령어는 쉘과 별도의 프로그램으로, 쉘이 자식 프로세스로 생성(fork)시켜 대행시켜 실행합니다. 그리고 작업이 끝나면 자식은 사라지고 쉘(부모)로 돌아옵니다. 자식의 상태변화는 부모에게 영향을 주지않는다.
- 그래서 터미널의 위치를 실제로 옮기려면, 자식이 아닌 **쉘 프로세스 자신이 직접 `chdir()`을 호출**해야 합니다. 그래서 `cd`는 별도의 프로그램이 아닌 쉘 프로세스가 직접 `chdir()`을 호출하는 **내장 명령어(Built-in)**로 설계된 것입니다.


### 💻 실제 실습 구현

**1) Source Code (`ch2_cwd.c`)**


```C
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    char *cwd;

    // 현재 위치 가져오기 (자동 할당 방식)
    cwd = getcwd(NULL, 0);
    printf("현재 디렉터리: %s\n", cwd);

    // 디렉터리 이동
    if (chdir("univ") == -1) {
        perror("chdir");
    } else {
        free(cwd);
        cwd = getcwd(NULL, 0);
        printf("이동 후 디렉터리: %s\n", cwd);
    }

    free(cwd);
    return 0;
}
```

- **핵심 분석:** `chdir()`은 해당 **프로세스 내부**의 작업 디렉터리만 변경합니다. 프로그램이 종료되면 쉘의 원래 디렉터리로 돌아옵니다.

## 4. [Topic: 디렉터리 내용 탐색 (`opendir`, `readdir`)]

- **Definition:** 디렉터리 파일 내부에 저장된 파일 목록(엔트리)을 순차적으로 읽어오기 위한 인터페이스입니다.
- **Why in OS:** 디렉터리는 일반 파일과 달리 직접 `read()`로 읽는 것이 권장되지 않으므로, 커널이 제공하는 전용 구조체(`DIR`)와 함수를 통해 안전하게 파일 리스트를 추득해야 합니다.
    

### 🏗️ 동작 원리 및 API 상세

- **내부 메커니즘:** `opendir()`은 디렉터리를 열어 디렉터리 스트림(`DIR *`)을 반환하며, `readdir()`을 호출할 때마다 스트림 내의 파일 엔트리를 하나씩 구조체 형태로 반환합니다. 모든 파일을 읽으면 `NULL`을 반환합니다.
- **주요 구조체 (`struct dirent`):**
    - `ino_t d_ino`: 파일의 아이노드 번호.
    - `char d_name[]`: 파일의 이름.
- **API 스펙:**
    - `DIR *opendir(const char *name);`: 디렉터리 스트림 열기.
    - `struct dirent *readdir(DIR *dirp);`: 다음 엔트리 읽기.
    - `int closedir(DIR *dirp);`: 스트림 닫기.
        

### 💻 실제 실습 구현

**1) Source Code (`ch2_list_dir.c`)**

C

```sql
#include <dirent.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    DIR *dp;
    struct dirent *dent;

    // 현재 디렉터리(.) 열기
    if ((dp = opendir(".")) == NULL) {
        perror("opendir");
        exit(1);
    }

    // 더 이상 읽을 엔트리가 없을 때까지 반복
    while ((dent = readdir(dp))) {
        printf("파일명: %-20s | 아이노드: %ld\n", dent->d_name, (long)dent->d_ino);
    }

    closedir(dp);
    return 0;
}
```

- **결과 분석:** `ls -i` 명령어와 유사한 결과를 출력하며, 숨김 파일(`.`, `..` 포함)까지 모두 리스트업됩니다. 출력 순서는 디렉터리 엔트리에 저장된 순서(보통 생성 순)를 따릅니다.
    

---

## 5. [Topic: 디렉터리 스트림 제어 및 오프셋 관리]

- **Definition:** 디렉터리를 읽는 "커서"의 위치를 확인하거나(`telldir`), 특정 위치로 이동(`seekdir`), 또는 처음으로 되돌리는(`rewinddir`) 기능입니다.
- **Why in OS:** 대규모 디렉터리에서 특정 지점부터 다시 읽어야 하거나, 파일 리스트를 여러 번 순회해야 할 때 효율적인 스트림 관리를 가능하게 합니다.
    

### 🏗️ API 상세 스펙

- **`long telldir(DIR *dirp);`**: 현재 디렉터리 스트림의 읽기 위치(오프셋)를 반환합니다.
- **`void seekdir(DIR *dirp, long loc);`**: `telldir`로 얻은 위치(`loc`)로 커서를 이동시킵니다.
- **`void rewinddir(DIR *dirp);`**: 스트림의 위치를 디렉터리의 맨 처음으로 초기화합니다.
    

### 💻 실제 실습 구현

**1) Source Code (`ch2_seek_dir.c`)**

C

```sql
#include <dirent.h>
#include <stdio.h>

int main() {
    DIR *dp = opendir(".");
    struct dirent *dent;
    long start_pos;

    start_pos = telldir(dp); // 시작 위치 저장
    
    dent = readdir(dp);
    printf("첫 번째 파일: %s\n", dent->d_name);

    rewinddir(dp); // 다시 처음으로
    dent = readdir(dp);
    printf("다시 읽은 첫 번째 파일: %s\n", dent->d_name);

    closedir(dp);
    return 0;
}
```

## 📌 기타 핵심 & CS Interview

- **기타 팁:** 리눅스에서 파일 이름은 대소문자를 엄격히 구분하며, 최대 255바이트까지 지정 가능합니다. 파일명 처리에 널 문자(`\0`)와 슬래시(`/`)는 사용할 수 없음을 유의하세요.
    

> [!faq]Q. `inode`에는 파일 이름이 포함되지 않는 이유는 무엇인가요?
>
> **🗣️ 핵심 답변:** 파일 이름은 **디렉터리 파일의 데이터 블록**에 저장되며, `inode`는 파일의 속성과 데이터 블록 주소만을 관리하기 때문입니다. 이를 통해 하나의 파일(inode)에 여러 개의 이름(하드 링크)을 붙이는 것이 가능해집니다.
>
> **📚 꼬리질문 대비:** 그렇다면 파일 이름을 바꿀 때(`rename`) `inode` 자체가 변경되나요? 아닙니다. 디렉터리 내의 이름-아이노드 매핑 정보만 수정될 뿐, 실제 파일의 속성을 담은 `inode` 번호는 그대로 유지됩니다.

> [!faq]Q. `rmdir()`이 실패하는 대표적인 원인 2가지는?
>
> **🗣️ 핵심 답변:** 첫째, 해당 디렉터리가 **비어 있지 않은 경우**(다른 파일이나 하위 디렉터리가 존재), 둘째, 프로세스가 해당 디렉터리에 대한 **삭제 권한이 없는 경우**입니다.
>
> **📚 꼬리질문 대비:** 비어 있지 않은 디렉터리를 강제로 삭제하려면 어떻게 해야 하나요? 시스템 프로그래밍적으로는 내부의 모든 엔트리를 순회하며 삭제한 뒤 `rmdir()`을 호출하거나, 쉘 명령어로 `rm -r` 옵션을 사용하여 재귀적으로 삭제해야 합니다.

### 🔑 오늘의 핵심 System Call & 개념

#### 1. 시스템 인터페이스 및 오류 처리

- **`System Call vs. Library`**: 커널 모드 진입 여부에 따른 성능과 기능의 차이 이해.
- **`errno` / `perror()` / `strerror()`**: 시스템 호출 실패 시 커널이 설정하는 오류 번호를 사람이 읽을 수 있는 메시지로 변환하는 필수 패턴.
- **`POSIX / SUS`**: 서로 다른 유닉스 계열 OS 간의 소스 코드 호환성을 보장하는 국제 표준 규격.
    

#### 2. 빌드 및 자원 관리

- **`GCC & Make`**: `-o`, `-c` 옵션을 활용한 컴파일과 `Makefile`을 이용한 의존성 기반 자동 빌드 시스템 구축.
- **`Dynamic Memory`**: `malloc`, `calloc`, `realloc`, `free`를 이용한 힙(Heap) 영역의 유연한 메모리 관리.
- **`Command-line Arguments`**: `argc`, `argv`를 통한 사용자 인자 처리.
    

#### 3. 파일 시스템 및 디렉터리 제어

- **`inode`**: 파일명과 실제 데이터를 연결하고 메타데이터를 저장하는 리눅스 파일 시스템의 핵심 자료 구조.
- **`mkdir()` / `rmdir()` / `rename()`**: 디렉터리 계층 구조를 조작하는 기본 시스템 호출.
- **`getcwd()` / `chdir()`**: 프로세스의 작업 경로(Context)를 확인하고 이동하는 방법.
- **`opendir()` / `readdir()`**: 디렉터리 스트림을 열어 내부 파일 목록을 순차적으로 탐색하는 메커니즘.
