## **2025-09-19, 1교시 — 개선본**

개념적 설계 단계를 거쳐 ER 모델(Entity-Relationship Model)이라는 산출물을 얻었습니다. ERD(Entity-Relationship Diagram)는 엔터티와 관계를 그림으로 표현하며, 카디널리티(cardinality)가 중요합니다.

설계 시 주로 사용하는 것은 두 엔터티를 연결하는 이진 관계(binary relationship)이며, 대부분의 현실 세계 의미를 표현할 수 있습니다. 세 개의 엔터티가 얽힌 3진 관계(ternary relationship)도 있지만, 오해의 소지가 많아 여러 개의 이진 관계로 분해하여 모델링하는 것이 더 명확하고 좋다는 의견이 많습니다.

현업에서 가장 어려운 점 중 하나는 특정 개념을 독립된 엔터티로 모델링할지, 아니면 다른 엔터티의 속성(attribute)으로 포함할지 결정하는 것입니다. 이는 이론만으로 해결되지 않으며, 많은 경험이 필요한 부분입니다.

설계 시 기억해야 할 중요한 개념 중 하나는 약한 엔터티(weak entity)입니다. 약한 엔터티는 다른 엔터티(소유 엔터티)에 의존하여 존재하며, ERD에서 이중선 사각형으로 표시합니다. 약한 엔터티를 소유 엔터티와 연결하는 관계는 식별 관계(identifying relationship)라고 하며, 이 관계에서 약한 엔터티는 항상 전체 참여(total participation)를 합니다. 예를 들어 '사원' 엔터티와 '피부양인'이라는 약한 엔터티가 있다면, 모든 피부양인은 반드시 특정 사원과 관계를 맺어야 합니다. 이 경우 카디널리티는 소유 엔터티(사원)와 약한 엔터티(피부양인) 간에 1:N 관계를 따르는 것이 일반적입니다.

오늘은 ER 모델을 테이블의 집합인 관계형 모델(Relational Model)로 변환하는 사상(mapping) 규칙을 배울 것입니다. 이 과정을 통해 논리적 설계를 수행하게 됩니다.

예제로 `Sailors`와 `Boats`라는 두 엔터티와, 이 둘을 잇는 `Reserves` 관계를 사용하겠습니다.

- `Sailors` 엔터티의 속성: `sid` (키), `sname`, `age`, `rating`
- `Boats` 엔터티의 속성: `bid` (키), `bname`, `color`
- `Reserves` 관계의 속성: `date`

**ER-관계형 사상(Mapping) 규칙**

1. **강한 엔터티(Strong Entity) 사상**: 각 강한 엔터티는 하나의 테이블(릴레이션)로 변환됩니다. 엔터티의 속성들은 테이블의 컬럼이 되고, 엔터티의 기본 키는 테이블의 기본 키(Primary Key)가 됩니다.
    
    - `Sailors(sid, sname, age, rating)` 테이블 생성
    - `Boats(bid, bname, color)` 테이블 생성
        
2. **M:N 관계(Many-to-Many Relationship) 사상**: 다대다 관계는 새로운 테이블, 즉 교차 테이블(junction table)로 만들어야 합니다.
    
    - 이 교차 테이블은 관계에 참여하는 양쪽 엔터티의 기본 키를 가져와 외래 키(Foreign Key)로 포함합니다.
    - 이 두 외래 키의 조합이 교차 테이블의 기본 키(복합 키, composite key)가 됩니다.
    - 관계 자체가 가진 속성(`date` 등)도 이 테이블의 컬럼이 됩니다.
    - 예시: `Reserves` 관계는 `Reserves(sid, bid, date)` 테이블로 사상되며, `(sid, bid)`가 기본 키가 됩니다. `sid`는 `Sailors`를, `bid`는 `Boats`를 참조하는 외래 키입니다.
        
3. **1:N 관계(One-to-Many Relationship) 사상**: 일대다 관계에서는 새로운 테이블을 만들지 않습니다. 대신, '1' 쪽 엔터티의 기본 키를 'N' 쪽 엔터티의 테이블에 외래 키로 추가합니다.
4. **1:1 관계(One-to-One Relationship) 사상**: 일대일 관계 역시 새로운 테이블을 만들지 않습니다. 어느 한쪽 엔터티의 기본 키를 다른 쪽 테이블에 외래 키로 포함시키면 됩니다. 어느 쪽에 포함할지는 의미적인 편의성을 고려하여 결정합니다.

외래 키 제약 조건(Foreign Key Constraint)

외래 키로 지정된 컬럼의 값은 반드시 참조하는 테이블의 기본 키 값 중에 존재하거나 NULL이어야 합니다. 예를 들어 Sailors 테이블에 sid가 1, 2, 3번만 존재한다면, Reserves 테이블의 sid 컬럼에는 1, 2, 3 또는 NULL만 들어갈 수 있으며, 존재하지 않는 5와 같은 값은 입력될 수 없습니다. 이는 데이터의 참조 무결성을 보장하는 중요한 규칙입니다. 외래 키 자체는 중복 값이나 NULL 값을 가질 수 있습니다.

데이터베이스 설계에서 키를 잘못 설정하면(예: 모든 컬럼을 키로 잡는 경우) 성능이 매우 저하될 수 있습니다. 올바른 스키마 설계는 시스템 성능에 결정적인 영향을 미칩니다.

2025-09-19, 1교시 — 개념

1. 한 줄 요약

    ER 다이어그램의 엔터티와 관계를 정해진 규칙에 따라 관계형 데이터베이스의 테이블과 제약 조건으로 변환하는 체계적인 절차.

2. **핵심 TL;DR**
    
    - **엔터티 → 테이블**: 모든 강한 엔터티는 그 자체로 하나의 테이블이 된다. 엔터티의 식별자는 테이블의 기본 키(PK)가 된다.
    - **M:N 관계 → 교차 테이블**: 다대다(M:N) 관계는 반드시 별도의 '교차 테이블'로 만들어진다. 이 테이블의 기본 키는 관계에 참여한 양쪽 테이블의 기본 키를 조합한 '복합 키'가 된다.
    - **1:N 관계 → 외래 키 추가**: 일대다(1:N) 관계는 테이블을 새로 만들지 않는다. 대신 '1' 쪽 테이블의 기본 키를 'N' 쪽 테이블에 '외래 키(FK)'로 추가한다.
    - **약한 엔터티 → 복합 키 테이블**: 약한 엔터티는 소유 엔터티의 기본 키를 외래 키로 가져와, 자신의 부분 키와 결합하여 '복합 기본 키'를 구성하는 테이블이 된다.
    - **관계의 속성**: 관계에 딸린 속성(예: 예약 날짜)은 관계가 사상된 테이블(교차 테이블 또는 'N' 쪽 테이블)의 일반 컬럼이 된다.
    - **식별 vs. 비식별 관계**: 식별 관계는 부모의 키를 자식의 '기본 키' 일부로 사용하는 관계(예: 약한 엔터티)이며, 비식별 관계는 부모의 키를 일반 컬럼(외래 키)으로만 사용하는 관계이다.
        
3. **표현 = 표준 용어**
    
    - **Mapping(사상)**: 한 모델(ER)의 구성요소를 다른 모델(관계형)의 구성요소로 체계적으로 변환하는 과정.
    - **Relational Model(관계형 모델)**: 데이터를 테이블(릴레이션)의 집합으로 표현하는 모델.
    - **Cardinality(카디널리티)**: 관계에 참여하는 엔터티 인스턴스의 수를 나타내는 제약 조건 (1:1, 1:N, M:N).
    - **Weak Entity(약한 엔터티)**: 다른 엔터티(소유 엔터티)의 존재에 의존하는 엔터티.
    - **Identifying Relationship(식별 관계)**: 약한 엔터티가 소유 엔터티를 식별하는 데 사용하는 관계.
    - **Primary Key (PK, 기본 키)**: 테이블 내의 각 행(row)을 고유하게 식별하는 하나 이상의 컬럼.
    - **Foreign Key (FK, 외래 키)**: 한 테이블의 컬럼으로, 다른 테이블의 기본 키를 참조하여 테이블 간의 관계를 설정.
    - **Composite Key(복합 키)**: 두 개 이상의 컬럼을 조합하여 기본 키를 구성하는 키.
    - **Referential Integrity(참조 무결성)**: 외래 키 값은 반드시 참조하는 테이블의 기본 키 값이거나 `NULL`이어야 한다는 제약 조건.
        
4. 정석 보강(canon-std)

    ER-관계형 사상의 목표는 ER 모델의 모든 정보(엔터티, 관계, 속성, 제약조건)를 손실 없이 관계형 스키마로 옮기는 것이다. 이 과정은 정규화된 테이블 구조를 유도하며, 특히 M:N 관계를 교차 테이블로 분해하는 것은 제1정규형(1NF)을 만족시키는 핵심 단계이다. 외래 키는 REFERENCES 키워드를 사용하여 참조 무결성을 강제하며, 이는 데이터의 일관성을 유지하는 데 필수적이다.

    ```SQL

    -- M:N 관계 Reserves를 교차 테이블로 사상하는 SQL 예시
    CREATE TABLE Reserves (
        sid INTEGER,
        bid INTEGER,
        day DATE,
        PRIMARY KEY (sid, bid), -- 복합 기본 키
        FOREIGN KEY (sid) REFERENCES Sailors(sid), -- 외래 키 제약 조건 1
        FOREIGN KEY (bid) REFERENCES Boats(bid)  -- 외래 키 제약 조건 2
    );
    ```
    
5. **실수·함정**
    
    - M:N 관계를 별도 테이블 없이 양쪽 테이블에 외래 키를 추가하여 구현하려는 시도.
    - 1:N 관계에서 외래 키의 방향을 혼동하는 것 (항상 '1' 쪽의 PK가 'N' 쪽으로 가야 함).
    - 외래 키(FK)가 항상 고유(unique)해야 한다고 오해하는 것 (FK는 중복 및 `NULL` 허용이 가능).
    - 약한 엔터티 사상 시, 소유 엔터티의 키를 일반 외래 키로만 추가하고 기본 키에 포함하지 않는 실수.
    - 1:1 관계에서 어느 테이블에 외래 키를 둘지 결정할 때, 참여 제약 조건(필수/선택)을 고려하지 않는 것. (필수 참여 쪽에 FK를 두는 것이 `NULL`을 피할 수 있어 유리함).

## **2025-09-19, 1교시 — 질문**

**[Q1] ER 모델링 시 엔터티(Entity)와 속성(Attribute)을 구분하는 실질적인 기준은 무엇인가요? | #ERD, #모델링**

- **· 모범답(강의 기준)**: 이론적 기준은 있지만, 실제 현업에서는 경험에 기반해 결정하는 어려운 문제입니다. 독립적으로 존재하며 여러 정보를 가질 수 있으면 엔터티, 특정 엔터티를 설명하는 단일 값이라면 속성으로 간주합니다.
- **· 정석체크(면접 30초)**: **독립적인 존재 여부**가 핵심 기준입니다. 해당 개념이 여러 속성을 가지며 다른 엔터티와 복합적인 관계를 맺을 수 있다면 엔터티로 모델링합니다. 반면, 더 이상 분해되지 않는 원자적인 값으로 엔터티의 특성을 설명하는 데 그친다면 속성으로 정의합니다.

**[Q2] M:N(다대다) 관계는 왜 반드시 새로운 '교차 테이블'로 만들어야 하나요? | #사상, #M:N, #교차테이블**

- **· 모범답(강의 기준)**: M:N 관계는 양쪽 엔터티 모두에서 하나의 인스턴스가 상대방의 여러 인스턴스와 관계를 맺기 때문에, 기존 테이블 내에 외래 키 컬럼 하나만 추가해서는 표현할 수 없습니다. 따라서 관계 자체를 저장할 별도의 교차 테이블이 필요합니다.
- **· 정석체크(면접 30초)**: 관계형 모델에서 한 컬럼은 원자값만 가져야 한다는 **제1정규형(1NF)**을 만족시키기 위함입니다. M:N 관계를 기존 테이블에 표현하려면 하나의 셀에 여러 값을 넣어야 하므로, 이를 해결하기 위해 양쪽의 기본 키를 외래 키로 갖는 `CREATE TABLE Reserves (sid INT, bid INT, PRIMARY KEY(sid, bid), ...)` 와 같은 교차 테이블로 분리합니다.

**[Q3] 1:N(일대다) 관계는 어떻게 테이블로 사상하며, M:N 관계와 근본적인 차이는 무엇인가요? | #사상, #1:N, #외래키**

- **· 모범답(강의 기준)**: 1:N 관계는 새 테이블 없이, '1' 쪽 엔터티의 기본 키를 'N' 쪽 테이블에 외래 키(FK)로 추가하여 사상합니다. 'N' 쪽의 각 레코드는 '1' 쪽의 단 하나의 레코드만 가리키므로, 컬럼 추가만으로 관계 표현이 가능합니다.
- **· 정석체크(면접 30초)**: 1:N 관계는 **'1' 쪽 테이블의 기본 키(PK)를 'N' 쪽 테이블에 외래 키(FK)로 이전**시켜 구현합니다. M:N 관계와 달리 'N' 쪽의 한 행은 '1' 쪽의 단 하나의 행만 참조하므로, `ALTER TABLE N_side ADD FOREIGN KEY (pk_from_1_side) REFERENCES One_side(pk);` 와 같이 참조 관계를 명확히 할 수 있어 교차 테이블이 불필요합니다.

**[Q4] 약한 엔터티(Weak Entity)는 어떻게 테이블로 변환되며, 일반적인 1:N 관계와 사상 규칙의 차이점은 무엇인가요? | #사상, #약한엔터티, #식별관계**

- **· 모범답(강의 기준)**: 약한 엔터티도 하나의 테이블로 만들어지지만, 소유 엔터티의 기본 키를 외래 키로 가져와 약한 엔터티의 자체 식별자(부분 키)와 **결합하여 복합 기본 키(composite PK)를 구성**합니다.
- **· 정석체크(면접 30초)**: 약한 엔터티는 **소유 엔터티의 PK를 FK로 가져와 자신의 부분 키(partial key)와 함께 복합 기본 키로 설정**합니다. 일반 1:N 관계에서는 FK가 PK의 일부가 아니지만, 약한 엔터티에서는 소유 엔터티에 의존해야만 고유하게 식별되는 '식별 관계'이므로 FK가 PK에 반드시 포함된다는 점이 핵심적인 차이입니다.

**[Q5] 1:1 관계를 사상할 때, 외래 키(FK)는 어느 테이블에 위치시키는 것이 규칙인가요? | #사상, #1:1, #참여제약**

- **· 모범답(강의 기준)**: 규칙이 정해져 있지 않아 어느 쪽에 두어도 무방하며, 두 가지 방법 모두 가능합니다. 설계자가 의미적으로 더 이해하기 쉬운 방향을 선택하여 한쪽 테이블에 다른 쪽의 기본 키를 외래 키로 추가하면 됩니다.
- **· 정석체크(면접 30초)**: 한쪽 테이블의 PK를 다른 쪽 테이블의 FK로 추가하고 해당 FK에 `UNIQUE` 제약 조건을 설정합니다. 이때 FK를 둘 최적의 위치는 **참여 제약 조건(participation constraint)**에 따릅니다. 한쪽이 필수 참여(total)이고 다른 쪽이 선택 참여(partial)라면, **필수 참여 쪽에 FK를 두어 `NULL` 값 발생을 방지**하는 것이 표준 설계 원칙입니다.

끝.

## **2025-09-19, 2교시 — 개선본**

지난 교시에 이어 ER-관계형 사상 규칙의 이유와 추가적인 개념에 대해 설명하겠습니다.

ER 모델에서는 표현 가능하지만 관계형 모델에서는 허용되지 않는 특별한 속성들이 있습니다.

1. **복합 속성(Composite Attribute)**: 주소와 같이 '시, 도, 동' 등으로 나뉠 수 있는 속성입니다. ERD에서는 주소 아래에 하위 속성들이 달린 형태로 표현할 수 있습니다.
2. **다치 속성(Multi-valued Attribute)**: 취미처럼 한 사람이 여러 개의 값을 가질 수 있는 속성입니다. ERD에서는 이중선 타원으로 표현합니다.

관계형 모델의 테이블로 사상할 때는 이 두 가지 형태가 허용되지 않습니다. 모든 속성은 반드시 원자값(atomic value)만 가져야 합니다.

- **복합 속성**은 '시', '도', '동'처럼 각각의 개별 컬럼으로 모두 분해해야 합니다.
- **다치 속성**은 `취미1`, `취미2`, `취미3` 과 같이 최대 개수를 정해 여러 개의 컬럼으로 만들거나, 별도의 테이블로 분리해야 합니다. 만약 특정 인스턴스가 해당 값을 가지지 않으면 그 컬럼들은 `NULL`로 처리됩니다.

이제 관계(Relationship) 사상 규칙을 다시 살펴보겠습니다.

- **1:N 관계**: '내장(embedding)' 방식을 사용합니다. '1' 쪽 엔터티의 기본 키(Primary Key)를 'N' 쪽 테이블에 외래 키(Foreign Key)로 포함시킵니다.
- **M:N 관계**: '내장'이 불가능하여, 관계에 참여하는 엔터티들의 기본 키를 모아 새로운 '교차 테이블'을 생성합니다.

관계형 모델의 키(Key)와 무결성 제약 조건

ER 모델에서의 '키'는 관계형 모델로 넘어오면서 '기본 키(Primary Key, PK)'로 불립니다. 기본 키는 다음과 같은 엄격한 제약 조건을 가집니다.

- **개체 무결성(Entity Integrity)**: 기본 키 값은 **중복될 수 없으며(Unique)**, 절대 **`NULL` 값을 가질 수 없습니다.**

이와 더불어 외래 키(Foreign Key, FK)는 다음 제약 조건을 따릅니다.

- **참조 무결성(Referential Integrity)**: 외래 키 값은 반드시 참조하는 테이블에 **존재하는 기본 키 값이거나 `NULL`이어야 합니다.**

키는 구성하는 속성의 개수에 따라 다음과 같이 분류됩니다.

- **단순 키(Simple Key)**: 하나의 속성으로 구성된 키.
- **복합 키(Composite Key)**: 두 개 이상의 속성으로 구성된 키. 실무에서는 성능 저하를 막기 위해 보통 3개를 초과하지 않도록 설계합니다.

사상 규칙의 존재 이유: 성능

테이블을 적게 만들수록 데이터 조회 성능이 향상됩니다. 여러 테이블에 흩어져 있는 정보를 연결하여 가져오는 조인(JOIN) 연산은 시스템에 큰 부하를 주는 매우 비싼(costly) 작업이기 때문입니다. 외래 키는 바로 이 조인 연산에서 테이블들을 연결하는 '연결고리' 역할을 합니다.

- 1:N 관계에서 '내장' 방식을 쓰는 이유는 테이블 수를 늘리지 않고 두 개의 테이블만으로 관계를 표현할 수 있어 조인 비용을 줄일 수 있기 때문입니다.
- M:N 관계는 어쩔 수 없이 3개의 테이블(기존 2개 + 교차 테이블 1개)이 필요하므로, 관련된 정보를 조회할 때 조인 연산이 더 많이 발생하여 성능상 불리할 수 있습니다.

1:N 관계에서 외래 키 방향이 정해진 이유

1:N 관계에서 반드시 '1' 쪽의 키를 'N' 쪽으로 가져와야 하는 이유는, 반대로 할 경우 관계를 제대로 표현할 수 없기 때문입니다. 만약 'N' 쪽의 키를 '1' 쪽으로 가져오면, '1' 쪽 테이블의 기본 키 제약 조건(중복 불가) 때문에 '한 명의 선원이 여러 배를 예약하는' N쪽의 관계를 표현할 수 없게 됩니다. '1' 쪽에서 'N' 쪽으로 키를 가져와야만, 'N' 쪽 테이블에서 외래 키 값이 중복되는 것을 허용하여 관계를 올바르게 나타낼 수 있습니다.

관계형 모델에서는 기본 키, 외래 키 외에도 후보 키(Candidate Key), 보조 키(Secondary Key) 등 다양한 키 개념이 존재하며, 이는 데이터 검색 속도를 높이는 인덱스(Index)와 밀접한 관련이 있습니다.

## 2025-09-19, 2교시 — 개념

1. 한 줄 요약

    관계형 모델의 원자성 원칙에 따라 복합/다치 속성을 처리하는 방법과, 기본 키 및 외래 키의 무결성 제약 조건, 그리고 조인 비용 최소화를 위한 사상 전략의 이론적 근거.

2. **핵심 TL;DR**
    
    - **원자성(Atomicity) 원칙**: 관계형 데이터베이스의 모든 테이블 셀(컬럼)에는 오직 하나의 원자적인 값만 저장될 수 있다.
    - **복합 속성 → 분해**: '주소'와 같은 복합 속성은 '시', '도', '상세주소' 등 여러 개의 개별 컬럼으로 완전히 분해하여 사상해야 한다.
    - **다치 속성 → 펼치기**: '취미'와 같은 다치 속성은 `취미1`, `취미2` 처럼 여러 컬럼으로 펼치거나, 별도의 테이블로 분리해야 한다. 한 필드에 `'낚시, 등산'` 과 같이 저장하는 것은 금지된다.
    - **개체 무결성**: **기본 키(Primary Key)**는 테이블의 각 행을 식별해야 하므로, 절대 `NULL`일 수 없고 중복된 값을 가질 수 없다.
    - **참조 무결성**: **외래 키(Foreign Key)**는 다른 테이블을 가리키는 포인터 역할을 하므로, 반드시 참조하는 테이블에 존재하는 값이거나 `NULL`이어야 한다.
    - **성능이 규칙을 결정**: 사상 규칙의 최우선 순위는 테이블 수를 줄여 **조인(JOIN) 연산** 횟수를 최소화하는 것이다. 조인은 매우 비용이 큰 연산이기 때문이다.
    - **1:N 사상 방향의 필연성**: '1' 쪽의 키를 'N' 쪽으로 가져오는 이유는, 반대로 할 경우 기본 키의 중복 불가 원칙에 위배되어 관계를 표현할 수 없기 때문이다.

3. **표현 = 표준 용어**
    
    - **Composite Attribute(복합 속성)**: 그 자체로 여러 하위 속성으로 구성된 속성 (예: 주소).
    - **Multi-valued Attribute(다치 속성)**: 하나의 엔터티 인스턴스에 대해 여러 개의 값을 가질 수 있는 속성 (예: 한 사람의 여러 취미).
    - **Atomicity(원자성)**: 컬럼 값이 더 이상 분해될 수 없는 단일 값이어야 한다는 원칙. 제1정규형(1NF)의 기본 조건.
    - **Entity Integrity(개체 무결성)**: 기본 키(PK)가 `NULL`이거나 중복될 수 없다는 제약 조건.
    - **Referential Integrity(참조 무결성)**: 외래 키(FK)가 참조하는 PK 값 또는 `NULL`만 허용한다는 제약 조건.
    - **JOIN Operation(조인 연산)**: 두 개 이상의 테이블을 외래 키를 이용해 연결하여 하나의 결과 집합으로 만드는 연산.
    - **Candidate Key(후보 키)**: 튜플(행)을 유일하게 식별할 수 있는 속성 또는 속성들의 집합. 기본 키가 될 자격이 있는 키들이다.
    - **Alternate Key(대체 키) / Secondary Key(보조 키)**: 후보 키 중에서 기본 키로 선택되지 않은 나머지 키들. `UNIQUE` 제약 조건을 걸어 사용할 수 있다.
    - **Feature(피처)**: 머신러닝(ML) 분야에서 속성(Attribute)을 지칭하는 동의어.
        
4. 정석 보강(canon-std)

    ER-관계형 사상의 모든 규칙은 최종적으로 테이블이 **제1정규형(1NF)**을 만족하도록 보장하는 데 목적이 있다. 1NF는 테이블의 모든 컬럼이 반드시 원자적인 값을 가져야 한다고 정의하며, 복합 및 다치 속성의 분해는 이 원칙을 지키기 위한 필수 과정이다. 또한, 키 무결성 제약은 데이터의 일관성과 신뢰도를 보장하는 핵심 장치로, SQL에서는 다음과 같이 명시적으로 선언된다.

    ``` SQL
    CREATE TABLE Sailors (
        sid INTEGER PRIMARY KEY, -- 개체 무결성 (UNIQUE + NOT NULL)
        sname VARCHAR(30) NOT NULL,
        rating INTEGER
    );
    -- 1:N 관계에서 'N'쪽에 FK를 추가
    ALTER TABLE Boats 
        ADD COLUMN sid INTEGER,
        ADD CONSTRAINT fk_sailor -- 참조 무결성
        FOREIGN KEY (sid) REFERENCES Sailors(sid);
    ```
    
5. **실수·함정**
    
    - `VARCHAR` 컬럼에 쉼표(,)로 구분된 여러 값을 넣어 다치 속성을 구현하려는 시도 (1NF 위반).
    - 기본 키(PK)가 `NULL`이 될 수 있는 상황을 고려하지 않고 설계하는 것.
    - 외래 키(FK)는 중복될 수 없다고 착각하는 것 (1:N 관계의 N쪽 FK는 당연히 중복 가능).
    - 성능 저하를 고려하지 않고 스키마를 과도하게 정규화하여 불필요한 조인을 유발하는 설계.
    - 외래 키가 참조하는 쪽의 기본 키와 데이터 타입이 일치하지 않아 오류가 발생하는 경우.

## 2025-09-19, 2교시 — 질문

**[Q1] 복합 속성(composite)과 다치 속성(multi-valued)은 관계형 모델의 테이블로 어떻게 변환해야 하나요? | #사상, #원자성, #1NF**

- **· 모범답(강의 기준)**: 관계형 모델의 속성은 원자값만 가져야 하므로, 복합 속성은 개별 하위 속성 컬럼들로 모두 분해하고, 다치 속성은 `취미1`, `취미2`처럼 여러 컬럼으로 만들거나 별도의 테이블로 분리해야 합니다.
- **· 정석체크(면접 30초)**: 이는 **제1정규형(1NF)의 원자성(Atomicity) 원칙**을 준수하기 위함입니다. 복합 속성은 `CREATE TABLE ... (city VARCHAR, street VARCHAR, zip_code VARCHAR)` 와 같이 개별 컬럼으로 분해하고, 다치 속성은 별도의 테이블로 분리하여 원래 테이블과 1:N 관계를 맺도록 하는 것이 정석입니다.

**[Q2] 기본 키(PK)와 외래 키(FK)가 각각 만족해야 할 핵심 무결성 제약 조건은 무엇인가요? | #무결성, #기본키, #외래키**

- **· 모범답(강의 기준)**: 기본 키는 중복되거나 `NULL`일 수 없다는 **'개체 무결성'**을, 외래 키는 참조하는 테이블의 기본 키 값이거나 `NULL`이어야 한다는 **'참조 무결성'**을 반드시 만족해야 합니다.
- **· 정석체크(면접 30초)**: **개체 무결성(Entity Integrity)**은 `PRIMARY KEY` 제약으로 보장되며 각 행의 고유 식별을 책임집니다. **참조 무결성(Referential Integrity)**은 `FOREIGN KEY` 제약으로 보장되며 테이블 간의 관계가 논리적으로 깨지지 않도록 합니다. 이 두 제약은 관계형 데이터베이스의 데이터 일관성과 신뢰도를 지키는 핵심 요소입니다.

**[Q3] ER-관계형 사상 시, 테이블 수를 줄이는 것을 우선적으로 고려하는 이유는 무엇인가요? | #성능, #조인, #최적화**

- **· 모범답(강의 기준)**: 여러 테이블을 연결해 데이터를 조회하는 조인(JOIN) 연산은 매우 많은 시간과 자원을 소모하는 비싼 작업이기 때문입니다. 따라서 테이블 수를 줄여 조인 횟수를 최소화하는 것이 전체적인 데이터베이스 성능에 유리합니다.
- **· 정석체크(면접 30초)**: **조인(JOIN) 연산의 비용**을 줄이기 위해서입니다. 조인은 대량의 데이터를 스캔하고 비교하므로 디스크 I/O와 CPU 사용량이 많은 고비용 작업입니다. 설계 단계에서 '내장(embedding)' 방식 등으로 테이블 수를 최소화하는 것은 쿼리 성능 최적화의 가장 기본적인 전략입니다.

**[Q4] 1:N 관계에서 외래 키의 방향이 '1' 쪽에서 'N' 쪽으로 고정되는 이유는 무엇인가요? | #사상, #1:N, #외래키**

- **· 모범답(강의 기준)**: 만약 'N' 쪽의 키를 '1' 쪽 테이블로 가져오면, '1' 쪽의 기본 키 제약 조건(중복 불가) 때문에 '하나'가 '여럿'을 가지는 관계를 표현할 수 없게 됩니다. '1' 쪽 키를 'N' 쪽으로 가져와야만 FK 컬럼의 값 중복을 통해 관계를 올바르게 표현할 수 있습니다.
- **· 정석체크(면접 30초)**: **관계 자체를 표현할 수 없기 때문**입니다. `Sailors`(1)와 `Boats`(N) 관계에서 `Boats`의 키를 `Sailors`로 가져오면, 한 선원이 여러 배를 예약할 때 `sid`가 중복되어 `PRIMARY KEY` 제약에 위배됩니다. 반면 `sid`를 `Boats` 테이블로 가져오면 `sid` 컬럼에 중복 값을 허용하여 한 선원이 여러 보트와 관계 맺는 것을 정확히 표현할 수 있습니다.

**[Q5] 3진(Ternary) 관계보다 더 높은 차수의 관계(4진, 5진 등)도 실제로 사용되나요? | #ERD, #N진관계, #모델링**

- **· 모범답(강의 기준)**: 이론적으로는 4진, 5진 등 무한한 차수의 관계를 만들 수 있지만, 3진 관계조차 이해하기 어려워 거의 사용하지 않으며, 여러 개의 2진 관계로 분해하는 것을 권장합니다.
- **· 정석체크(면접 30초)**: 이론적으로 N-ary relationship은 가능하지만, **3진 관계를 초과하는 모델은 실무에서 사실상 사용되지 않습니다.** 관계의 의미가 매우 복잡해져 해석이 어렵고, 대부분의 고차 관계는 여러 개의 이진(binary) 관계와 하나의 중심 엔터티로 분해하여 더 명확하게 모델링할 수 있기 때문입니다.

## **2025-09-19, 3교시 — 개선본**

지난 시간에 배운 ER-관계형 사상 규칙을 기계적으로 적용하는 연습을 해보겠습니다. (실습)

- **1:N 또는 1:1 관계**: '1' 쪽의 기본 키(PK)를 'N' 쪽 테이블에 외래 키(FK)로 가져옵니다. 관계 자체에 속성(`R1`, `R2` 등)이 있다면, 해당 속성들도 외래 키와 함께 'N' 쪽 테이블로 모두 옮겨옵니다. 테이블을 새로 만들지 마십시오.
- **M:N 관계**: 새로운 교차 테이블을 생성합니다. 관계에 참여한 양쪽 테이블의 기본 키를 가져와 복합 기본 키로 삼고, 관계의 속성들(`R1`, `R2` 등)을 이 새 테이블의 일반 컬럼으로 추가합니다.

이 규칙을 숙지하는 것은 데이터베이스 설계의 가장 기초적이고 확실한 부분이므로 반드시 알아야 합니다.

**관계형 모델에서의 키(Key)의 종류와 속성**

관계형 모델의 키는 엄격한 수학적 정의를 따릅니다. 어떤 속성(또는 속성의 집합)이 '키'가 되기 위해서는 두 가지 핵심 속성을 만족해야 합니다.

1. **유일성(Uniqueness)**: 키 값은 테이블 내 모든 행(tuple)에 대해 유일해야 합니다. 중복된 값이 허용되지 않습니다.
2. **최소성(Minimality)**: 키를 구성하는 속성들 중 어떤 진부분집합(proper subset)도 유일성을 만족해서는 안 됩니다. 즉, 키를 구성하는 속성 중 하나라도 빼면 키의 역할을 할 수 없어야 합니다.

이 두 가지 속성을 기준으로 키의 종류는 다음과 같이 나뉩니다.

- **슈퍼키(Superkey)**: **유일성만** 만족하는 속성의 집합입니다. 최소성은 만족하지 않아도 됩니다. 예를 들어 `sid`가 키라면, `{sid, sname}` 집합도 슈퍼키입니다.
- **후보 키(Candidate Key, CK)**: **유일성과 최소성을 모두** 만족하는 속성의 집합입니다. 하나의 테이블에 여러 개의 후보 키가 존재할 수 있습니다.
- **기본 키(Primary Key, PK)**: 여러 후보 키 중에서 데이터베이스 관리자(DBA)가 **대표로 선정한 단 하나의 키**입니다.
- **대체 키(Alternate Key, AK)** 또는 보조 키(Secondary Key): 후보 키 중에서 **기본 키로 선택되지 않은 나머지 키**들입니다.
- **외래 키(Foreign Key, FK)**: 다른 테이블의 기본 키를 참조하여 테이블 간의 관계를 맺는 키입니다. 이 키는 자체적으로 유일성이나 최소성을 만족할 필요가 없습니다.

키 식별 연습 (실습)

주어진 데이터만 보고 테이블의 키를 찾는 역공학(reverse engineering)을 해보겠습니다. 현재 데이터가 전부라고 가정하고, 유일성과 최소성을 만족하는 모든 후보 키를 찾아봅시다.

1. **사원 테이블 (`사원명`, `부서`, `근무연수`)**
    
    - 단순 키(속성 1개): `사원명`, `부서`, `근무연수` 모두 데이터에 중복이 있어 단독으로 키가 될 수 없습니다.
    - 복합 키(속성 2개):
        - `{사원명, 부서}`: 유일성을 만족합니다. **(후보 키)**
        - `{사원명, 근무연수}`: '을순, 8' 데이터가 중복되어 키가 될 수 없습니다.
        - `{부서, 근무연수}`: 유일성을 만족합니다. **(후보 키)**
    - 복합 키(속성 3개): `{사원명, 부서, 근무연수}`는 이미 그 일부인 `{사원명, 부서}`가 후보 키이므로, 최소성에 위배되어 후보 키가 될 수 없습니다. (슈퍼키는 될 수 있음)
    - **결론**: 후보 키는 `{사원명, 부서}`와 `{부서, 근무연수}` 두 개입니다. 이 중 테이블의 의미(사원 테이블)를 고려하여 `{사원명, 부서}`를 **기본 키(PK)**로, `{부서, 근무연수}`를 **대체 키(AK)**로 선정하는 것이 합리적입니다.
        
2. **자동차 테이블 (`번호판`, `모델`, `색상`, `사원명`, `부서`)**
    
    - 먼저 `{사원명, 부서}`는 사원 테이블에서 온 외래 키로 의심되므로, 키 후보를 찾을 때는 일단 제외하고 나머지 속성으로만 판단합니다.
    - 단순 키: `번호판`은 유일성을 만족합니다. **(후보 키)** `모델`, `색상`은 중복이 있어 키가 될 수 없습니다.
    - 복합 키: `번호판`이 이미 후보 키이므로, `번호판`을 포함하는 다른 조합(`{번호판, 모델}` 등)은 최소성에 위배되어 후보 키가 될 수 없습니다. 남은 조합인 `{모델, 색상}`은 유일성을 만족합니다. **(후보 키)**
    - **결론**: 후보 키는 `{번호판}`과 `{모델, 색상}` 두 개입니다. 이 경우, 속성이 하나인 `{번호판}`을 **기본 키(PK)**로 선정하는 것이 일반적입니다. `{모델, 색상}`은 **대체 키(AK)**가 됩니다.
    - **외래 키(FK)**: 앞서 제외했던 `{사원명, 부서}`는 사원 테이블의 PK를 참조하는 외래 키입니다.

매우 중요한 점

외래 키(Foreign Key)는 ER 모델에 존재하지 않는 개념입니다. ER 모델을 관계형 모델로 사상(mapping)하는 과정에서 비로소 생성되는 것입니다. 따라서 ERD를 작성할 때 외래 키를 표기하는 것은 명백한 오류입니다.

## **2025-09-19, 3교시 — 개념**

1. 한 줄 요약

    테이블의 행(row)을 고유하게 식별하는 '키'의 엄격한 정의(유일성, 최소성)와 슈퍼키, 후보 키, 기본 키, 대체 키로 이어지는 명확한 계층 구조.

2. **핵심 TL;DR**
    
    - **키의 2대 속성**: 어떤 속성 집합이 키가 되려면 **유일성**(Uniqueness)과 **최소성**(Minimality)을 모두 만족해야 한다.
    - **유일성**: 키 값이 테이블 내에서 절대 중복되지 않음.
    - **최소성**: 키를 구성하는 속성 중 하나라도 빠지면 유일성이 깨짐 (더 이상 줄일 수 없음).
    - **슈퍼키(Superkey)**: 최소성은 무시하고, **유일성만 만족**하는 모든 속성의 조합. (후보 키 + 불필요한 속성들)
    - **후보 키(Candidate Key)**: **유일성과 최소성을 모두 만족**하는 키. 테이블의 기본 키가 될 자격이 있는 후보들이다.
    - **기본 키(Primary Key)**: 여러 후보 키 중에서 설계자가 **단 하나만 선택**한 대표 키.
    - **대체 키(Alternate Key)**: 후보 키 중에서 기본 키로 **선택받지 못한 나머지** 키들.
    - **ERD에는 외래 키가 없다**: 외래 키(FK)는 관계형 모델로 사상(mapping)하는 과정에서 생기는 개념이며, ER 모델 단계에는 존재하지 않는다.
        
3. **표현 = 표준 용어**
    
    - **Uniqueness(유일성)**: 테이블의 특정 컬럼(들)에 중복된 값이 없음을 보장하는 속성.
    - **Minimality(최소성)**: 키를 구성하는 데 불필요한 속성이 전혀 없음을 보장하는 속성.
    - **Superkey(슈퍼키)**: 테이블의 행을 고유하게 식별할 수 있는 하나 이상의 속성 집합. (e.g., `{주민번호, 이름}`)
    - **Candidate Key (CK, 후보 키)**: 슈퍼키 중에서 최소성을 만족하는 키. (e.g., `{주민번호}`)
    - **Primary Key (PK, 기본 키)**: 후보 키 중에서 주 식별자로 선택된 키.
    - **Alternate Key (AK, 대체 키)**: 기본 키로 선택되지 않은 후보 키.
    - **Reverse Engineering(역공학)**: 데이터나 스키마만 보고 원래의 설계(키, 관계 등)를 역으로 추론하는 과정.
        
4. 정석 보강(canon-std)

    키들의 관계는 집합으로 표현할 수 있습니다: {기본 키} ⊂ {후보 키} ⊂ {슈퍼키}. 즉, 모든 기본 키는 후보 키이고, 모든 후보 키는 슈퍼키입니다. 슈퍼키 개념은 데이터베이스 정규화(Normalization) 이론, 특히 BCNF(Boyce-Codd Normal Form)에서 '모든 결정자는 슈퍼키여야 한다'는 규칙의 핵심이므로 이론적으로 매우 중요합니다.

    ``` SQL
    CREATE TABLE Users (
        user_id    INTEGER       PRIMARY KEY, -- 기본 키 (PK)
        login_name VARCHAR(50)   NOT NULL UNIQUE, -- 대체 키 (AK)
        email      VARCHAR(100)  UNIQUE,      -- 또 다른 대체 키 (AK)
        -- {user_id, login_name} 조합은 유일하지만 최소가 아니므로 '슈퍼키'이다.
    );
    ```
    
5. **실수·함정**
    
    - `sid`만으로 충분한데 `{sid, sname}`을 기본 키로 잡는 것 (최소성 위배).
    - 테이블에 기본 키를 여러 개 설정하려는 시도 (오직 하나만 가능).
    - 후보 키를 찾을 때, 최소성 검사를 잊고 슈퍼키를 후보 키로 착각하는 것.
    - **ER 다이어그램에 외래 키(FK) 속성을 그려 넣는 심각한 오류.**
    - 외래 키가 항상 키의 속성(유일성, 최소성)을 만족해야 한다고 오해하는 것.

## 2025-09-19, 3교시 — 질문

**[Q1] 관계형 모델에서 어떤 속성이 '키(Key)'로 인정받기 위한 두 가지 핵심 조건은 무엇인가요? | #키, #유일성, #최소성**

- **· 모범답(강의 기준)**: 키가 되기 위해서는 테이블 내에서 값이 중복되지 않는 **'유일성(Uniqueness)'**과, 키를 구성하는 속성 중 하나라도 빼면 유일성이 깨지는 **'최소성(Minimality)'**이라는 두 가지 조건을 반드시 동시에 만족해야 합니다.
- **· 정석체크(면접 30초)**: **유일성(Uniqueness)**은 각 행을 고유하게 식별하는 능력이며, **최소성(Minimality)**은 식별에 불필요한 속성이 포함되지 않았음을 보장합니다. 예를 들어 `{주민번호}`가 키라면 `{주민번호, 이름}`은 유일하지만 최소가 아니므로 후보 키가 될 수 없습니다. 이 두 조건은 데이터의 중복성과 종속성을 제거하는 정규화의 기초가 됩니다.

**[Q2] 슈퍼키, 후보 키, 기본 키, 대체 키의 포함 관계를 설명해주세요. | #키, #슈퍼키, #후보키, #기본키**

- **· 모범답(강의 기준)**: 유일성만 만족하는 가장 넓은 개념인 '슈퍼키'가 있고, 그중 최소성까지 만족하는 것들이 '후보 키'가 됩니다. 설계자는 여러 후보 키 중 단 하나를 '기본 키'로 선택하며, 선택받지 못한 나머지는 '대체 키'가 됩니다.
- **· 정석체크(면접 30초)**: 키의 관계는 집합으로 표현할 수 있습니다: **{기본 키} ⊂ {후보 키} ⊂ {슈퍼키}**. 즉, 기본 키는 후보 키의 일종이며, 모든 후보 키는 슈퍼키의 일종입니다. SQL에서는 `PRIMARY KEY`로 단 하나를 지정하고, 나머지 후보 키들은 `UNIQUE` 제약 조건을 통해 대체 키로 활용할 수 있습니다.

**[Q3] 데이터만 보고 후보 키를 찾을 때, 외래 키(FK)로 의심되는 컬럼은 어떻게 처리해야 하나요? | #키, #후보키, #외래키, #역공학**

- **· 모범답(강의 기준)**: 어떤 테이블의 후보 키를 찾을 때, 다른 테이블에서 온 것으로 보이는 외래 키(FK) 컬럼들은 일단 없는 셈 치고 배제한 뒤, 나머지 순수한 자기 속성들만으로 후보 키를 찾아야 합니다.
- **· 정석체크(면접 30초)**: 후보 키는 해당 테이블의 고유 속성으로만 구성되어야 하므로, 다른 테이블과의 관계를 나타내는 외래 키는 탐색 대상에서 제외하는 것이 원칙입니다. 먼저 FK로 의심되는 컬럼들을 제외하고 후보 키 탐색을 완료한 후, 제외했던 컬럼들을 `FOREIGN KEY`로 명시하는 것이 올바른 역공학 절차입니다.

**[Q4] ER 모델의 관계(Relationship)에 붙어있던 속성은 테이블로 사상될 때 어디로 가나요? | #사상, #관계속성, #외래키**

- **· 모범답(강의 기준)**: 1:N 관계에 속성이 붙어있다면, 그 속성들은 '1'쪽의 기본 키가 'N'쪽으로 옮겨갈 때 함께 따라가 일반 컬럼이 됩니다. M:N 관계의 속성들은 새로 만들어지는 교차 테이블의 컬럼이 됩니다.
- **· 정석체크(면접 30초)**: 관계의 속성은 관계가 구체화되는 테이블로 사상됩니다. 1:N 관계에서는 'N'쪽 테이블이 관계를 표현하므로 `ALTER TABLE N_side ADD (fk_col INT, rel_attr VARCHAR);` 와 같이 FK와 함께 추가됩니다. M:N 관계에서는 교차 테이블이 관계 그 자체이므로 `CREATE TABLE Junction (pk1 INT, pk2 INT, rel_attr DATE);` 처럼 교차 테이블의 속성이 됩니다.

**[Q5] ER 모델링 단계에서 외래 키(FK)를 사용하면 안 되는 근본적인 이유는 무엇인가요? | #ERD, #외래키, #모델링**

- **· 모범답(강의 기준)**: 외래 키(FK)는 물리적인 데이터베이스 설계를 위한 관계형 모델의 개념이지, 비즈니스 논리를 표현하는 개념적 모델인 ER 모델의 구성요소가 아니기 때문입니다. ERD에 FK를 그리는 것은 서로 다른 수준의 모델을 혼합하는 중대한 오류입니다.
- **· 정석체크(면접 30초)**: ER 모델은 **'무엇(What)'**을 표현하는 개념적 단계이고, 외래 키는 **'어떻게(How)'** 관계를 구현할지를 다루는 논리/물리적 단계의 개념이기 때문입니다. ERD에서는 오직 엔터티와 관계만으로 비즈니스 논리를 표현해야 합니다. ERD에 FK를 표기하는 것은 아직 존재하지 않는 구현 세부사항을 개념 모델에 미리 그려 넣어 모델의 추상화 수준을 파괴하는 행위입니다.

끝.

## **2025-09-19, 3교시 — 실습**

**[S1] ER-관계형 모델 사상 규칙 적용 연습**

- **목적**: 주어진 ERD의 관계와 카디널리티를 보고, 정해진 규칙에 따라 관계형 테이블 스키마로 변환하는 능력을 기릅니다.
- **단계요약**: 1) 1:N 관계는 '1' 쪽의 PK를 'N' 쪽 테이블에 FK로 내장(embed)시킨다. 2) 관계 자체의 속성도 'N' 쪽 테이블에 함께 추가한다. 3) M:N 관계는 양쪽 PK를 FK로 갖는 새로운 교차 테이블을 생성하고, 관계의 속성을 이 테이블에 추가한다.
- **⚠️ 주의**: 1:N 관계에 속성이 여러 개 붙어있더라도, 원칙적으로 새 테이블을 만들지 않고 'N' 쪽 테이블에 모두 포함시키세요.

**[S2] 데이터 기반 후보 키(Candidate Key) 식별**

- **목적**: 키가 정의되지 않은 테이블의 실제 데이터를 분석하여, 유일성과 최소성 원칙에 따라 모든 후보 키를 찾아내고, 최적의 기본 키를 선정합니다.
- **단계요약**: 1) 먼저 외래 키로 의심되는 컬럼은 분석에서 제외한다. 2) 단일 컬럼부터 시작해 유일성을 만족하는지 검사한다. 3) 여러 컬럼의 조합을 검사하되, 이미 키로 판명된 속성을 포함하는 더 큰 조합은 최소성 위배로 즉시 제외한다. 4) 찾아낸 모든 후보 키 중 가장 간결하고 대표적인 것을 기본 키(PK)로 선정한다.
- **⚠️ 주의**: 키 후보를 찾을 때, 다른 테이블에서 가져온 것으로 보이는 외래 키(FK)는 반드시 먼저 제외하고 순수 속성들만으로 분석해야 합니다.
