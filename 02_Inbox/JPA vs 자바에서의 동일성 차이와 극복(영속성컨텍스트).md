## 정리
### ## 1. '같다'는 것의 두 가지 의미

이 개념을 이해하려면, '같다'는 말의 두 가지 의미를 구분해야 합니다.

| **구분**       | **JPA 세상 (데이터베이스)**    | **자바 세상 (JVM 메모리)**    |
| ------------ | ---------------------- | ---------------------- |
| **'같다'의 기준** | **Primary Key (PK) 값** | **메모리 주소 ( == )**      |
| **의미**       | 내용이 같다 (동등성, Equality) | 존재가 같다 (동일성, Identity) |
| **비유**       | 주민등록번호가 같은 사람          | 나와 내 앞에 있는 거울 속의 나     |

- **JPA의 정체성:** DB에 사는 `MEMBER` 테이블의 `ID=1`인 데이터는 세상에 단 하나뿐입니다. 이것이 JPA가 말하는 **엔티티 정체성(Identity)**입니다.
- **자바의 정체성:** 하지만 자바 코드에서는 `new Member(1L)`와 `new Member(1L)`를 호출하면, 내용은 같지만 메모리 주소는 다른 **별개의 객체**가 두 개 만들어집니다. == 비교 시 `false`가 나옵니다.

### ## 2. 영속성 컨텍스트: 두 세상을 연결하는 '매니저'

JPA의 **영속성 컨텍스트(1차 캐시)**는 바로 이 두 세상의 간극을 메워주는 역할을 합니다.

두 차이점을 모두 충족시키게합니다

- **역할:** "한 번 조회한 엔티티는 내가 **기억**하고 있겠다!"
- **동작:** 내부적으로 `Map<PK, Entity>`와 같은 저장소를 가집니다.
    
    1. `memberRepository.findById(1L)` 요청이 들어온다.
    2. 매니저(영속성 컨텍스트)는 자신의 **기억(1차 캐시)**을 뒤져본다. "PK가 1인 멤버를 내가 이미 알고 있나?"
    3. **알고 있다면 (Cache Hit):** DB에 가지 않고, **기억해뒀던 바로 그 `Member` 객체의 메모리 주소**를 그대로 돌려준다.
    4. **모른다면 (Cache Miss):** DB에 가서 데이터를 조회한 뒤, 새로운 `Member` 객체를 만들어 **자신의 기억(1차 캐시)에 저장**하고, 그 객체를 돌려준다.

이 메커니즘 덕분에, **"같은 영속성 컨텍스트 내에서는 같은 PK = 같은 인스턴스 보장"**이라는 약속이 지켜지는 것입니다.

다음은 “자바의 동일성(\==/equals)과 JPA 엔티티 동일성(식별자 기반)”의 불일치가 만드는 문제들과, 이를 예방·해결하기 위한 실무 도입 방법입니다.

# **1) 개념 정렬 (한 줄 요약)**

- **자바**: \==는 “같은 객체(참조 동일성 즉 메모리 주소 비교)”, equals는 “동등성(개발자가 정의)”.
	- equals는 두 객체의 **내용(값)이 같은지**를 비교를 개발자가 오버라이딩해 정의해 동등성 비교
- **JPA**: 엔티티의 **동일성은 PK(@Id) 값**으로 정해짐. 같은 테이블 행이면 “같은 엔티티”.

# **2) 불일치로 생기는 대표 문제**

1. **트랜잭션/영속성 컨텍스트가 다르면, 같은 행인데 다른 객체**
    
    - A 트랜잭션에서 로드한 Member(1)과 B 트랜잭션에서 로드한 Member(1)은 **서로 다른 인스턴스** → \==는 false.

2. **컬렉션(Set/Map) 깨짐**
    
    - equals/hashCode가 PK 또는 안정적 키를 제대로 쓰지 않으면
        - HashSet에 **중복 저장**되거나
        - persist() 후 PK가 채워지며 **hashCode가 바뀌어** HashSet/HashMap에서 **찾지 못하는** 현상.

3. **지연 로딩 프록시와 equals 실패**
    
    - 하이버네이트는 LAZY일 때 **프록시 클래스**를 씌움. getClass() 비교식 equals를 쓰면

        proxy != 실제클래스라서 **동등 비교 실패**.

4. **준영속/병합 시 ‘동일 엔티티의 이중 인스턴스’**
    
    - detach된 엔티티와 새로 로드한 영속 엔티티가 공존하면, Set/Map/동등 비교에서 **엇갈림**.

5. **비즈니스 키를 equals에 넣어 발생하는 성능·사이드이펙트**
    
    - LAZY 필드나 변경 가능 필드를 equals/hashCode에 사용 → **지연 초기화 트리거**, **순환 참조**로 스택오버플로, 성능 저하.

# **3) 해결·예방을 위한 도입 방법 (실무 체크리스트)**

## **A. 영속성 컨텍스트 일관성 유지**

- **서비스 계층 @Transactional**로 작업 범위를 한 컨텍스트 안에서 끝내기.

    → 같은 트랜잭션에서는 1차 캐시가 **PK별 단일 인스턴스(Identity Map)**를 보장.

- OSIV를 끄는 경우(권장) 컨트롤러 이전에 **DTO로 변환**해 엔티티가 밖으로 나가지 않게.

## **B. equals/hashCode 안전 구현(프록시·PK·Set/Map 대응)**

하이버네이트/스프링 데이터 실무에서 많이 쓰는 **안전 패턴**:

```java
@MappedSuperclass
public abstract class BaseEntity {

    @Id @GeneratedValue
    private Long id;

    // 프록시 안전 비교
    @Override
    public final boolean equals(Object o) {
        if (this == o) return true;
        if (o == null) return false;
        // 프록시/실체 클래스 차이를 무시
        if (org.hibernate.Hibernate.getClass(this) != org.hibernate.Hibernate.getClass(o)) return false;
        BaseEntity other = (BaseEntity) o;
        // PK가 배정된 후에만 "같다"
        return id != null && id.equals(other.id);
    }

    // 영속 전에도 해시가 바뀌지 않도록: 클래스 해시 사용
    @Override
    public final int hashCode() {
        return getClass().hashCode();
    }
}
```

- **핵심 의도**
    - **프록시 안전**: Hibernate.getClass()로 프록시/실클래스 동등 취급.
    - **영속 전 안정성**: id == null일 땐 절대 같다고 보지 않음(임시 객체 충돌 방지).
    - **해시 안정성**: persist로 PK가 생겨도 **hashCode가 변하지 않음** → HashSet/Map 안전.

> Lombok 사용 시 @EqualsAndHashCode(callSuper = true, onlyExplicitlyIncluded = true) 등으로 위 규칙을 유지하거나, **직접 구현**을 추천. @Data의 기본 equals/hashCode는 위험합니다.
1. equals(Object o) 메서드

이 메서드는 다음 두 가지 문제를 해결합니다.

- 문제 1: 프록시 오류 방지
- 프록시와 실제 엔티티는 클래스가 다르므로, 순수한 자바 getClass() 비교 시 Member != Member$Proxy로 판단되어 동등성 오류가 발생합니다.
- 해결: Hibernate.getClass()를 사용하여 프록시가 아닌 원본 엔티티의 클래스 타입을 얻어 비교합니다.
- 문제 2: 영속화 전/후 비교 기준 확립
- 객체가 DB에 저장되기 전에는 id가 null입니다. id가 null일 때 equals를 참으로 만들면, 저장 후 (id가 할당된 후) 해시 코드가 바뀌어 Set, Map에서 객체를 찾지 못하는 문제가 발생합니다.
- 해결: id != null일 때만 동등성 비교를 수행하여 DB에 저장된 객체만 비교 기준으로 삼습니다.

2. hashCode() 메서드

이 메서드는 해시 코드 계약 위반을 막습니다.

- 문제: hashCode()는 equals()가 참이면 같아야 합니다. 만약 해시 코드에 가변적인 id 필드를 사용하면, 저장 전(id=null)과 저장 후(id=1)의 해시 코드가 바뀌어 해시 기반 컬렉션(Set, Map)에서 객체를 찾지 못하게 됩니다.
- 해결: getClass().hashCode()를 사용하여 객체의 클래스 타입만으로 해시 코드를 결정합니다. id 값이 바뀌어도 해시 코드는 절대 변하지 않아 계약을 안전하게 지킵니다.
## **C. PK 전략과 “비즈니스 키 동등성” 선택 가이드**

- **권장 기본값**: **대리키(PK, @GeneratedValue)** 기반 동등성(위 패턴). 가장 단순하고 안전.
- **자연키(변하지 않는 비즈니스 키)**가 강력히 존재한다면:
    - @NaturalId(Hibernate) + **비즈니스 키 equals**를 고려할 수 있으나,
    - **절대 변경되지 않는** 키만 사용, 지연 필드·컬렉션은 제외.
    - 팀 합의/코드 규약으로 엄격히 관리 필요.

## **D. 컬렉션/연관관계에서의 주의**

- **equals/hashCode에 컬렉션/LAZY 필드 포함 금지**(성능/무한루프 위험).
- **연관관계 편의 메서드**로 양방향 동기화하되, 동등성 판단과는 **분리**.
- Set을 키로 쓸 때는 위의 해시 안정 패턴을 반드시 적용.

## **E. 병합/준영속 시 중복 방지**

- 준영속을 다시 쓸 땐 **merge()** 대신 **식별자 조회 후 필요한 값만 복사** 패턴을 우선 고려(의도치 않은 전체 필드 덮어쓰기/이중 인스턴스 방지).
- 캐시/동시성 계층에서는 **ID 단일 기준**으로 중복 관리.

## **F. 테스트/운영 실수 방지 팁**

- **동일 엔티티를 Set/Map 키로 쓸 테스트**를 만들어 조기 검출.
- 리포지토리 단위 테스트는 항상 **트랜잭션 경계** 안에서 수행.
- 컨버터/매퍼(예: MapStruct) 단계에서 엔티티를 DTO로 즉시 변환해 **영역 분리**.

# **4) 요약**

- 문제의 뿌리: **자바는 객체 참조/임의 equals**, **JPA는 PK 기반 동일성**.
- 주된 증상: **Set/Map 오류**, **프록시 equals 실패**, **트랜잭션 경계 밖 이중 인스턴스**.
- 해법 3종 세트:
    
    1. **@Transactional**로 한 컨텍스트에서 작업,
    2. **프록시 안전 + PK 기반 equals/hashCode**(영속 전 해시 안정),
    3. **LAZY/가변 필드 equals 제외** 및 DTO 경계로 층 분리.
