## 🛡️ TCP 세션 하이재킹: 인증된 사용자의 세션ID를 탈취하여 재사용해 가장하는 공격

TCP 세션 하이재킹은 이미 인증을 마친 사용자(Client)와 서버 사이의 **시퀀스 번호(Sequence Number)**를 가로채, 공격자가 사용자의 권한을 그대로 이어받는 전송 계층 공격입니다.

### 1. 공격의 근본적 원인: "무결성 검증의 부재"

TCP는 패킷을 받을 때 다음 세 가지 정보가 일치하면 정당한 사용자로 간주합니다.

- **Source IP / Port**: 어디서 왔는가?
- **Destination IP / Port**: 어디로 가는가?
- **Sequence Number (SEQ)**: 순서가 맞는가?
    

> **핵심 문제:** TCP 헤더에는 보낸 이가 진짜인지 확인하는 **암호화된 신분증(Token)**이 없어서, 번호만 맞추면 커널은 의심 없이 데이터를 수락합니다.
---

### 2. TCP 3-Way Handshake와 시퀀스 번호

세션 수립 시 양단간의 논리적 통로를 만들기 위해 시퀀스 번호를 동기화합니다.
> 요청(**SYN**)
> 응답(ACK)
> 시퀀스번호(ISN) : 자신을 식별하기위한 번호

1. 클라이언트가 **SYN** 요청: 클라이언트의 ISN를 임의로 생성해 전송
2. 서버가 ACK와 SYN를 함께 전송
	- ACK 응답: 클라이언트 ISN에다가 1를 더한 값을 수락 응답으전송
	- **SYN** 요청: 서버도 자신의 ISN를 임의로 생성해 전송
3. 클라이언트가 ACK 응답: 받은 서버의 ISN에 1을 더해 전송하며 세션이 연결됨
- 이후 서버와 클라이언트는 데이터 받을때마다 자신의 시퀀스 번호를 1씩 증가해 신뢰성을 검증한다.

---

### 3. 세션 하이재킹 4단계 프로세스

공격의 핵심은 **"진짜 사용자보다 먼저 서버가 원하는 번호를 던져 주도권을 뺏는 것"**입니다.

| **단계**       | **주요 행위**                           | **결과**                    |
| ------------ | ----------------------------------- | ------------------------- |
| **탐색 및 스니핑** | 통신 경로에서 패킷을 실시간 감시하며 SEQ, ACK 번호 탈취 | 현재 세션 정보 확보               |
| **번호 예측**    | 서버가 다음에 기다릴 시퀀스 번호를 계산              | 주입할 패킷 설계 완료              |
| **비동기화**     | 위조 패킷을 주입해 서버의 시퀀스 번호를 강제로 높임       | **실제 클라이언트 패킷은 무시(Drop)** |
| **세션 장악**    | 서버와 동기화된 번호로 악성 명령(Payload) 전송      | 공격자가 클라이언트 권한 획득          |

---

### 4. 핵심 방어 전략: SSL/TLS (HTTPS)

세션 하이재킹을 원천 차단하기 위해서는 전송 계층 위에 **암호화 계층**을 추가해야 합니다.

- **암호화의 효과**: 공격자가 시퀀스 번호를 알아내어 패킷을 주입하더라도, 패킷 내부의 **데이터가 암호화**되어 있습니다.
- **무결성 검증**: 서버는 수신한 패킷을 복호화하는 과정에서 키가 맞지 않거나 데이터가 조작되었음을 즉시 감지하고 차단합니다.
    

---

> **💡 요약 (Senior's Note)**
>
> 세션 하이재킹은 **"번호 맞추기 게임"**입니다. TCP가 번호의 연속성만 보고 신뢰한다는 약점을 파고드는 것이죠. 따라서 번호만 맞춘다고 해결되지 않도록 **SSL/TLS 암호화**를 통해 데이터 자체의 진위 여부를 검증하는 것이 가장 확실한 대응책입니다. 암호화된 세션에서는 공격자가 번호를 맞춰 패킷을 주입하더라도 복호화 키가 없어 무결성 검증 단계에서 즉시 차단되기 때문입니다.

## 💭 추가적 생각/질문

작성해주신 내용은 **TCP 3-Way Handshake**의 핵심 절차를 정확히 짚고 있습니다. 다만, 통상적으로 서버가 보내는 **SYN**과 **ACK**는 하나의 패킷(`SYN+ACK`)에 담겨 오기 때문에, 이를 단계별로 명확히 구분하여 시각적으로 정리해 드릴게요.

---

내용의 흐름은 전반적으로 훌륭하지만, **SYN과 ACK의 용어 매칭** 및 **시퀀스 번호의 증가 원리**에서 약간의 정정이 필요합니다. 정확한 개념으로 다듬어 드릴게요.

## 🔄 TCP 3-Way Handshake 과정 정정 및 요약

작성하신 2번 단계에서 **요청(SYN)과 응답(ACK)의 역할**이 서로 바뀌어 기재되었습니다. 아래 내용이 표준 정의에 가깝습니다.

### 1단계: 클라이언트 → 서버 (SYN)

- **역할:** 연결 요청
- **번호:** 클라이언트가 무작위로 생성한 초기 시퀀스 번호($ISN_c$)를 보냅니다.
    

### 2단계: 서버 → 클라이언트 (SYN + ACK)

- **ACK (응답):** 클라이언트가 보낸 $ISN_c$를 잘 받았다는 표시로 **$ISN_c + 1$**을 보냅니다. (작성하신 내용에서 SYN/ACK 역할이 반대로 되어 있습니다.)
- **SYN (요청):** 서버도 자신을 식별하기 위한 초기 시퀀스 번호 **$ISN_s$**를 생성해 보냅니다.
    

### 3단계: 클라이언트 → 서버 (ACK)

- **ACK (응답):** 서버가 보낸 $ISN_s$를 잘 받았다는 표시로 **$ISN_s + 1$**을 보냅니다.
- **결과:** 이 단계가 끝나면 양쪽의 번호가 서로 확인(동기화)되어 **Established(연결됨)** 상태가 됩니다.

## ⚠️ 팩트 체크 및 교정 (중요)

> **"이후 서버는 데이터 받을 때마다 자신의 시퀀스 번호를 1씩 증가해 신뢰성을 검증한다."**

이 문장은 두 가지 측면에서 교정이 필요합니다.

1. **증가 단위:** 시퀀스 번호는 무조건 `1`씩 증가하는 것이 아니라, **보낸 데이터의 바이트(Byte) 수**만큼 증가합니다. 예를 들어 100바이트의 데이터를 보냈다면 다음 시퀀스 번호는 이전 번호 + 100이 됩니다. (단, 제어 플래그인 SYN, FIN은 데이터가 없어도 1을 소비합니다.)
2. **신뢰성 검증의 주체:** 서버만 검증하는 것이 아니라, **클라이언트와 서버 양쪽 모두** 상대방이 보낸 시퀀스 번호와 내가 기다리는 번호가 일치하는지 대조하며 서로를 검증합니다.

### 💡 최종 정리 (Corrected Version)

|**단계**|**주체**|**패킷**|**시퀀스 번호 (SEQ)**|**응답 번호 (ACK)**|
|---|---|---|---|---|
|**1단계**|클라이언트|**SYN**|$ISN_c$|-|
|**2단계**|서버|**SYN+ACK**|$ISN_s$|$ISN_c + 1$|
|**3단계**|클라이언트|**ACK**|$ISN_c + 1$|$ISN_s + 1$|

**핵심 포인트:**

- **ACK 번호**는 "상대방으로부터 다음에 받기를 기대하는 번호"입니다.
- 세션 하이재킹은 바로 이 **"다음에 올 번호"**를 공격자가 스니핑으로 알아내어, 진짜 사용자보다 먼저 서버에 던져버리는 공격입니다.
