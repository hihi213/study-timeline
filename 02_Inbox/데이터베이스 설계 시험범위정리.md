## 🛠️ 실무 및 시험 대비 핵심 설계 규칙

### 1. 기본키(PK) 선정 3원칙

- **Not Null:** 비어 있으면 안 됨.
- **Unique:** 중복되면 안 됨.
- **Minimal:** 가능하면 짧고 간단해야 함. (길면 데이터 양이 늘어남)
- ⚠️ **주의:** 사람 이름이나 상품 이름 등 **'이름' 자 들어가는 속성은 절대 PK로 쓰지 말 것** (중복 방지 불가). 없을 경우 '상품번호', '학번'처럼 인위적인 번호를 만드세요.
    

### 2. 엔티티(Entity) 적격성 체크리스트

- 데이터(인스턴스)가 **최소 2개 이상**이어야 함 (단 하나뿐인 데이터는 엔티티 제외).
- 속성(Attribute)이 **최소 2개 이상**이어야 함 (속성이 하나뿐이면 엔티티 가치 없음).
    

### 3. 피터 첸 vs IE 방식 결정적 차이 ($N:M$ 관계)

- **피터 첸:** 관계(마름모)에 속성을 직접 연결할 수 있어 매우 편함.
- **IE 방식:** 관계에 속성을 넣을 수 없음. 그래서 **$N:M$ 관계는 무조건 별도의 '엔티티'로 변환**해서 그려야 함 (이때 부모 테이블의 PK들을 가져와서 자식의 FK이자 PK로 사용).
    

### 4. 관계와 족보(부모-자식)

- **부모 테이블(Parent):** 참조를 당하는 쪽 (PK 제공).
- **자식 테이블(Child):** 참조를 하는 쪽 (FK 보유).
- **외래키(FK):** 반드시 부모 테이블에 존재하는 값(PK나 Candidate Key)이어야 함.

## 📊 ERD 도형 및 표기법 심화

- **이중 원 ($\bigcirc \bigcirc$):** **다중 속성(Multi-valued Attribute)**. 예: 배송지가 여러 개이거나 취미가 여러 개인 경우.
- **카디널리티(대응수) 계산법:**
    - 양쪽 방향에서 각각 $1:N$인지 생각한 후 합산 (예: $1:N$ + $1:M$ = $N:M$).
    - **(0, n) 표기:** **최솟값이 0**이라는 건 '안 살 수도 있다' 혹은 '안 팔릴 수도 있다'는 선택적 관계(Optional)를 의미함.
        

## 💎 1. 반드시 암기해야 할 핵심 이론 (단답형/객관식 대비)

### **① 데이터베이스 용어 매핑 (매우 중요)**

교수님이 "이 용어들은 알아야 한다"고 강조하신 부분입니다. 파일 시스템과 DB 용어를 혼동하지 않게 정리하세요.

|**구분**|**파일 시스템**|**데이터베이스 (일반적 호칭)**|**관계형 모델 용어**|
|---|---|---|---|
|**전체**|파일 (File)|**테이블 (Table)**|릴레이션 (Relation)|
|**행**|레코드 (Record)|**행 (Row)**|튜플 (Tuple)|
|**열**|필드 (Field)|**열 / 컬럼 (Column)**|속성 (Attribute)|

### **② PK(Primary Key)의 중요성**

- **시험 백퍼 출제 포인트:** PK는 **인덱스(Index)를 형성**하기 때문입니다.
- **특징:** `Not Null`(비어 있으면 안 됨), `Unique`(중복 불가), 최소성(가능한 짧아야 함).
- **설계 팁:** 이름(사람, 상품 등)은 절대 PK로 쓰지 말 것! 대신 '상품번호' 같은 인위적인 번호를 만드세요.
    

### **③ 데이터 모델링 & 트랜잭션 정의**

- **데이터 모델링:** 현실 세계의 업무 프로세스를 추상화하여 DB 구조로 표현하는 과정.
- **트랜잭션(Transaction):** 논리적 기능을 수행하기 위한 **작업의 기본 단위**. (예: 계좌이체 시 A 계좌 마이너스 & B 계좌 플러스가 한 세트여야 함)

## 🎨 2. ERD(ER 다이어그램) 작성 규칙 (실기 대비)

### **① 도형의 의미**

- **직사각형 ($\square$):** 개체(Entity) - 명사에서 추출
- **마름모 ($\diamond$):** 관계(Relationship) - 동사에서 추출
- **타원 ($\bigcirc$):** 속성(Attribute) - PK는 밑줄 필수!
- **이중 타원 ($\bigcirc \bigcirc$):** 다중 속성(Multivalued Attribute) - 예: 여러 개의 배송지, 여러 개의 학위 등
    

### **② 피터 첸(Peter Chen) vs IE 표기법 차이**

- **피터 첸:** 관계(마름모)에 속성을 직접 매달 수 있어 직관적입니다.
- **IE 표기법 (새발 모양):** 관계에 속성을 넣을 수 없습니다. 따라서 **$N:M$ 관계는 반드시 중간에 새로운 '엔티티'를 만들어 변환**해야 합니다.
    - 이때 부모의 PK를 가져와서 자신의 PK 겸 FK로 사용합니다.

## 🏥 3. 사례별 설계 로직 (주관식/서술형 대비)

### **① 환자 기록 관리 (병원 시스템)**

- **개체 추출 과정:**
    
    1. 명사(의사, 환자, 검사내역 등)와 동사(진료하다, 의뢰하다 등) 선별.
    2. **개체 후보 검토:** 데이터나 속성이 1개뿐인 것은 삭제.
        
- **IE 변환 팁:** 의사와 환자가 '진료하다'로 연결될 때, 이 관계를 개체로 만들면 의사번호와 환자번호가 **FK(외래키)**가 됩니다.
    

### **② 쇼핑몰 게시판 관리**

교수님이 중간고사에 출제된다고 예고하신 논리 구조입니다.

- **Q: 상품문의/불만접수 테이블을 따로 안 만드는 이유?**
    - **A:** 제목, 내용, 작성일 등 **공통 속성**이 많으므로 하나의 '게시판' 테이블로 통합하고 '구분 속성'을 두는 것이 관리 효율성과 확장성에 유리하기 때문입니다.
- **Q: 댓글 테이블에 '신고사유'를 직접 넣지 않는 이유?**
    - **A:** 댓글 하나에 여러 번의 신고가 발생할 수 있는 **$1:N$ 관계**이므로, 데이터 중복을 방지하고 정규화를 위해 별도의 '신고' 테이블로 분리해야 합니다.

## 🛠️ 4. 데이터 모델링 6단계 프로세스

1. **요구 분석:** 사용자 식별 및 명세서 작성.
2. **개념적 설계:** 개체/관계 추출 및 **ERD 작성** (결과물: ERD).
3. **논리적 설계:** DBMS에 맞게 매핑, **정규화** 수행 (결과물: 관계형 스키마).
    
    - 표기법 예: `도메인(속성1, 속성2, …)` -> **PK는 밑줄**.
        
4. **물리적 설계:** 성능을 고려한 인덱스, 파티션 등 설계.
5. **구현:** 실제 테이블 생성.
6. **운영 및 유지보수.**
