제공해주신 메모에는 **실무에서 혼동하기 쉬운 핵심 포인트(Core Concepts)**가 아주 잘 잡혀 있습니다. 이 내용을 바탕으로 **비유를 배제**하고, **기술적 정의와 실무적 맥락**을 완벽하게 정리했습니다.

## 1. 웹 아키텍처 및 서버 기초

- **서버 (Server)**: '제공하다(Serve)' + '~하는 주체(er)'
    - **기능적 정의**: 클라이언트에게 회원가입, 정보 조회, 추천 등의 **구체적인 기능을 제공하는 프로그램** (예: Web Server, WAS).
    - **물리적 정의**: 그 프로그램을 24시간 실행시키기 위해 최적화된 **컴퓨터 하드웨어**.
- **클라이언트 (Client)**: 서버에게 요청(Request)을 보내는 모든 주체.
    - **API 클라이언트**: API를 호출하는 도구나 프로그램 (Postman, cURL, 백엔드 서버 간 통신 등).
    - **프론트엔드 클라이언트**: '웹 브라우저' 환경에서 API를 호출하는 주체 (React, Vue, HTML+JS).
- **요청 (Request)**: 기능을 수행하기 위해 서버에 보내는 메시지.
    - **물리적 경로**: 인터넷(네트워크)을 거쳐서 전달됨.
    - **논리적 행위**: "이 데이터를 줘", "이걸 저장해줘"라는 명령.
- **URL (Uniform Resource Locator)**: 자원의 위치이자 **방향지시등**.
    - 서버 내부에서 수많은 기능(Controller) 중 **어떤 컨트롤러의 로직을 실행할지 결정**하는 기준이 됨.
        

### 2. 통신 및 인터페이스 (API & HTTP)

- **API (Application Programming Interface)**: 기능을 외부에서 사용할 수 있게 열어둔 **접점(인터페이스)**.
    - **웹 개발**: 서버의 특정 기능을 URL을 통해 호출할 수 있게 만든 것.
    - **프로그래밍**: 라이브러리나 프레임워크가 제공하는 함수/클래스 명세.
- **HTTP 요청 vs. API 요청**
    - **HTTP 요청 (전송 방식)**: '인터넷'을 통해 데이터를 주고받는 **프로토콜(규약)**. 웹사이트 접속과 API 호출 모두 HTTP를 사용함.
    - **API 요청 (기능 호출)**: 논리적으로 **'기능을 부르는 행위'**.
        - _참고_: 외부 통신은 HTTP를 타지만, **서버 내부 코드나 DB와의 직접 통신은 HTTP를 거치지 않고 직접 호출**함.
- **스펙 (Spec/Specification)**: 기술 명세서.
    - **API 스펙**: 요청 시 어떤 데이터를 보내야 하고, 응답은 어떤 형태로 오는지 정의한 문서 (취업 스펙과는 무관함).
        

### 3. 도메인 및 데이터 (Business & Data)

- **도메인 (Domain)**: '영역' 또는 '범위'.
    - **네트워크 도메인**: `naver.com` 처럼 사람이 식별하기 쉬운 **인터넷 주소 영역**.
    - **소프트웨어 도메인**: 애플리케이션이 해결해야 하는 **비즈니스 핵심 영역** (예: 쇼핑몰의 경우 '주문', '회원', '상품').
- **비즈니스 로직 vs. 도메인 모델**
    - **도메인 모델 (Domain Model)**: 핵심 데이터를 담고 있는 **객체**. 상태(Data)를 가짐.
        - _예시_: `Order` 클래스 (주문자, 상품명, 가격 등의 데이터를 포함).
    - **비즈니스 로직 (Business Logic)**: 데이터를 처리하는 **규칙, 계산, 검증**.
        - _예시_: `Order` 클래스 내부의 `calculateTotalPrice()` 메서드 (할인율 적용 계산 등).
- **엔티티 (Entity)**: 데이터의 실체.
    - **DB 관점**: 테이블에 저장된 **한 행(Row)**.
    - **SW 관점**: 고유 식별자(ID)를 가지며 지속적으로 추적/관리되는 **비즈니스 객체**.
        

### 4. 계층 구조 (Layered Architecture)

- **컨트롤러 (Controller)**: **요청 진입점 및 처리자**.
    - 클라이언트의 요청(HTTP)을 받아 분석하고, 적절한 서비스 로직을 호출한 뒤, 결과를 응답(Response)으로 변환함.
- **서비스 (Service)**: **비즈니스 로직의 집합**.
    - 컨트롤러의 요청을 받아 실제 업무 규칙(계산, 검증, 흐름 제어)을 수행하는 계층.
- **리포지토리 (Repository)**: **저장소 관리자**.
    - **백엔드 개발**: DB에 접근하여 데이터를 저장/조회하는 계층 (예: JPA UserRepository).
    - **형상 관리**: 코드를 저장하고 버전을 관리하는 저장소 (예: Git Repository).
- **모듈 vs. 인터페이스**
    - **인터페이스**: 기능의 껍데기(설계도). '무엇을 할지'만 정의.
    - **모듈**: 인터페이스를 실제로 구현한 코드 덩어리(부품). '어떻게 할지'가 구현됨.
        

### 5. 상태 관리 및 운영 (Infra & Ops)

- **데이터 저장소 (Session / Cookie / Cache)**
    - **세션 (Session)**: **서버 메모리**에 저장. 보안이 중요한 정보(로그인 상태) 유지.
    - **쿠키 (Cookie)**: **클라이언트(브라우저)**에 저장. 재방문 인식, 비로그인 장바구니 등.
    - **캐시 (Cache)**: 빠른 접근을 위한 **임시 저장소**. (브라우저, CDN, 서버 메모리 등 다양한 곳에 존재).
- **라우팅 (Routing)**
    - **백엔드**: 특정 URL(`GET /users`)을 특정 컨트롤러 메서드와 연결해 주는 작업.
    - **네트워크**: 데이터 패킷을 목적지까지 최적의 경로로 이동시키는 기술.
- **빌드 vs. 배포**
    - **빌드 (Build)**: 작성한 코드를 컴퓨터가 실행 가능한 파일(exe, jar 등)로 변환하는 과정.
    - **배포 (Deploy)**: 빌드된 파일을 실제 서버에 업로드하고 실행하여 유저가 접속 가능하게 만드는 과정.
- **부하 관리**
    - **로드 밸런싱**: 들어오는 요청 트래픽을 여러 대의 서버에 균등하게 분산시키는 기술.
    - **스케일링**: 서버의 개수(Scale-out)나 성능(Scale-up)을 조절하는 행위.
- **쿼리 (Query)**
    - **SQL 쿼리**: DB에게 데이터를 요청하는 문장 (`SELECT * FROM…`).
    - **HTTP 쿼리 스트링**: URL 뒤에 `?key=value` 형태로 붙여 서버에 추가 옵션(검색어, 페이지 번호)을 전달하는 부분.

### 🔄 전체적인 호출 흐름 (Flow)

1. **요청 생성**: 유저가 버튼 클릭 → 브라우저(프론트엔드)가 **API 클라이언트**로서 **HTTP 요청** 생성 (`GET /users/1`).
2. **전송**: 인터넷을 통해 요청이 서버로 전달됨.
3. **라우팅 및 수신**: 서버(Spring Boot 등)가 요청을 받고, **URL을 분석**하여 `UserController`로 연결.
4. **비즈니스 로직 수행**:
    
    - **Controller**: 요청 파라미터(`id=1`)를 추출하여 **Service** 호출.
    - **Service**: 비즈니스 로직 수행 중 데이터가 필요하여 **Repository** 호출.
    - **Repository**: **DB**에 쿼리를 날려 실제 데이터(Entity) 조회 후 반환.
        
5. **응답 생성**: 조회된 데이터를 바탕으로 서버가 **JSON 포맷**의 응답 데이터 생성 (`ResponseEntity.ok(user)`).
6. **응답 처리**: HTTP 응답(`200 OK`)이 브라우저로 전송되고, 브라우저가 이를 해석해 화면에 표시.
