- #### 2. 스프링컨테이너와 스프링빈이 무엇인지 이해한다
	1. UserController는 JdbcTemplate이 없으면 작동할 수 없다.
		-  즉, UserController는 JdbcTemplate에 의존하고 있는 상태야.
	2. 그런데 우리는 JdbcTemplate 객체를 생성하지도 않았고, 설정하지도 않았어.
		- new JdbcTemplate() 호출한 적도 없고
		- .setJdbcTemplate(...) 같은 설정도 한 적이 없지.
	3. 그런데도 UserController 안에 JdbcTemplate이 자동으로 들어가 있음.
	- 왜냐면 @RestController가 아래에 있는 클래스를 api 진입지점으로 만들어주고,스프링 빈으로 등록시키기 때문이다.
	- 스프링 빈은 거대한 컨테이너에 들어간 인스턴스다
		- 서버가 시작되면, 스프링서버 내부에 거대한 컨테이너를 만들게 된다
		- 스프링이 클래스들을 스캔해 어노테이션들이 붙은 클래스들을 자동으로 Bean으로 등록한다.
		- 빈으로 등록할때 인스턴스를 생성하고 인스턴스를 거대한 컨테이너에 담아준다
		- 이때 인스턴스 자체만 보관하는게 아닌, 다양한 정보도 추가적으로 함께 담아준다
			- 의존성 정보
				- 이 객체가 생성될때 어떤 다른빈들을 필요로 하는지,
				- 생성자에 어떤파라미터가 필요한지(자동주입)
			- 빈의 이름과 타입
			- 라이프사이클 등
	- **개발자가 JdbcTemplate를 Bean 등록 안 해도 되는 이유와 과정**
		- Gradle로 자동으로 빈이 등록됨!
			```java 
			//build.gradle 파일 안의 코드
			implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
			```
			- Gradle이 JPA 기능에 필요한 여러 라이브러리들을 다운로드하도록 해주고, Spring Boot는 서버 실행 시 spring-boot-autoconfigure에 정의된 설정에 따라 관련 객체들(예: EntityManager, JpaRepository 등)을 자동으로 Bean으로 등록해줍니다.
			- 이것때문이라는데... 사실 아래 이건 이해 못함(아래 내용 틀릴수 있음)
			- build.gradle역할: Gradle이 implementation에 적힌 라이브러리들을 자동으로 **다운로드 및 프로젝트에 추가**합니다.
			- spring-boot-starter-data-jpa : Spring Boot에서 JPA 기능을 쉽게 사용할 수 있도록 관련 라이브러리들을 묶어놓은 **스타터(Starter)**
				- spring-boot-starter 디렉토리안에 있는게 아니라 별개다
			- hibernate-core: JPA 기능을 실제로 구현한 핵심 라이브러리
			- spring-boot-autoconfigure
				- **JPA 관련 객체들을 자동으로 Bean으로 등록해주는 코드들이 들어 있는 라이브러리**
			- spring-boot-starter
				-  Spring Boot에서 특정 기능을 사용하기 위해 **기본적으로 필요한 의존성들을 묶어 놓은 빈 껍데기 라이브러리**
			- 등이 있다
	- 스프링빈으로 등록해야 스프링이 의존성있는 클래스를 넣어줄수있다
- #### 3. new대신 스프링컨테이너가 왜 필요한지 좋은 코드와 어떻게 연관이 있는지 이해한다.

	🎯 목표

	기존에는 Book 데이터를 메모리에 저장하고 있었지만,

	이제는 MySQL DB에 저장하도록 구조를 변경하고 싶음.

	단, 서비스·컨트롤러 코드 수정 없이 구현체만 교체하자!

	⸻

	① \[초기 단계] 직접 new 로 구현체 생성

	BookMemoryRepository repo = new BookMemoryRepository();

	-	✅ 장점: 간단하게 구현체를 직접 써서 사용
	-	❌ 단점: 코드에 구현체가 고정됨
	-	→ 나중에 DB 저장 방식으로 바꾸려면
	→ new BookMySQLRepository() 로
	→ 수백 줄의 코드 모두 수정해야 함 😱

	⸻

	② \[개선1] 인터페이스 도입

	public interface BookRepository { ... }

	public class BookMemoryRepository implements BookRepository { ... }

	-	✅ 장점: 추상화 → BookRepository 타입만 사용하면 구현체는 나중에 갈아끼울 수 있음
	-	❌ 단점: 여전히 직접 new 함
	-	new BookMemoryRepository() → 직접 수정해야 함
	-	인터페이스만으로는 **제어권이 여전히 개발자에게 있음**

	⸻

	③ \[개선2] 스프링 빈 + 의존성 주입(DI) 적용->제어의 역전(IoC)의 실현

	@Service

	public class BookService {

		private final BookRepository bookRepository;

	
		public BookService(BookRepository bookRepository) {
			this.bookRepository = bookRepository;
		}

	}

	@Repository

	public class BookMemoryRepository implements BookRepository { ... }

	@Repository

	public class BookMySQLRepository implements BookRepository { ... }

	-	✅ 장점:
	-	@Repository 를 붙이면 Spring이 자동으로 빈으로 등록
	-	@Service 클래스 생성자에서 **자동으로 필요한 구현체를 주입받음**
	-	구현체 교체는 이제 코드가 아닌, **빈 등록 설정**만 바꾸면 됨
	BookRepository의 구현체가 여러 개 있을 경우,
	어떤 걸 주입해야 할지 스프링이 모호함을 느낄 수 있음
		- ✅ @Primary 를 사용하면 → 우선순위를 지정할 수 있음

	@Repository

	@Primary

	public class BookMySQLRepository implements BookRepository { … }

	->즉 **“처음부터 인터페이스 + 생성자 주입 기반 구조로 짜면, 나중에 구현체만 갈아끼우면 된다”**
	제어의 역전(IoC)이란?

	원래 개발자가 직접 new를 호출해서 객체를 생성하던 제어권(Control) 을,

	스프링 프레임워크에게 넘김으로써

	필요한 객체를 자동으로 주입받는 구조로 바뀐 것입니다.

- #### 4. 스프링빈을 다루는 여러방법을 이해한다
	- 1. 스프링 빈을 등록하는 방법 : **@Configuration + @Bean 기반 등록 (수동 등록 방식)**
		- @Configuration
			- 클래스에 붙이는 어노테이션
			- @Bean을 사용할 때 함께 사용해 주어야 한다.
		- @Bean
			- 메소드에 붙이는 어노테이션
			- 메소드에서 **반환되는 객체를** 스프링빈에 등록한다.
		- 이 두가지를 같이 사용해 외부 라이브러리나 우리가 직접 어노테이션을 붙일 수 없는 클래스들을 **우회적으로 빈으로 등록**할 때 사용 (ex) jdbcTemplate)
	- 2. 스프링 빈을 등록하는 방법: **@Component 기반 등록 (자동 등록 방식)**
		- 주어진 클래스를 **스프링의 컴포넌트**로 간주한다.
		- 이 클래스들은 스프링 서버가 뜰 떄 자동으로 감지되고 스프링 빈으로 등록된다.
		- @Service, @Repository, @RestController 등은 내부에 @Component를 포함하고 있어 이 어노테이션들이 붙은 클래스도 스프링이 자동으로 감지해서 **빈으로 등록**된다.
	- 스프링빈을 주입받는 방법:
		- 생성자(가장 권장)
			- 원래 생성자 위에 @AutoWired라는 어노테이션을 붙여줬어야 했다
			- 생성자에 있는 매걔변수에 스프링 빈을 넣어달라는 의미
			- 자동으로 등록됨
		- Setter만들고 그 위에 @AutoWired를 붙이기
			- 누군가 Setter를 사용하면 다른인스턴스로 교차되기 때문에 오작동할 요지가 있다.
		- 필드에 직접 @AutoWired 붙이기
			- private JdbcTemplate jdbcTemplate; 위에 @AutoWired붙여준다
			- 테스트를 어렵게 만드는 요인이다.
	- @Qualifier("이름")
		- 정확하게 어떤 빈을 사용할지 이름으로 지정
		- 주입 지점마다 다른 빈을 지정 가능
	- 빈주입 우선순위
		- 1순위: 주입받는 쪽에 @Qualifier("이름")
		- 2순위: @Qualifier 없음, 등록된 빈 중 @Primary 존재
			-  @Primary는 **기본값**으로 사용할 빈을 정할 때임
- 알아야할것
	- 클래스 이름으로 메서드를 부르는 건 **static 메서드** 이다
		- **정적 메서드(static)** 는 객체 생성 없이 **클래스 이름으로 직접 호출**할 수 있어요.
		- **JVM은 객체가 없는 상태에서 바로 메서드를 실행**하려고 해요.
	- 아니 나는 생성자 **new UserRepository(…) 를 호출한 적이 없는데 왜 생성된 거지?**
		- 바로 @어노테이션을 붙였기 때문!
		- **Spring Boot가 시작될 때**, 어노테이션 붙은 클래스 스캔
		- Spring이 객체를 **Bean으로 생성해서 내부 컨테이너에 등록**
		- 필요하면 스프링이 자기 컨테이너에서 찾고, 자동으로 넣어줌
	- 그럼 Spring이 만들어준 객체를 우리가 쓰려면?
		- 1. 먼저 클래스 안에 우리가 사용할 객체를 담기 위한 **필드 선언**
			- private final UserRepository userRepository;
		- 2. 생성자도 수정: 생성자의 매개변수로 Bean을 받아와서, 위에서 선언한 필드에 저장합니다.
		- 이렇게 작성하면 Spring이 자동으로 생성한 Bean을 우리 코드에 주입해줘


# 코드상 new와 스프링 주입의 차이
### 1. 개발자가 직접 `new` 하는 경우 (수동 제어)

> **비유:** 내가 요리할 때 필요한 **프라이팬을 직접 마트에 가서 사오는 것**

#### **작동 방식**

- **호출 시점:** 코드가 실행되는 도중 `new` 문장을 만나는 그 즉시 생성자가 호출됩니다.
- **주도권:** 개발자가 객체의 생성부터 소멸(Lifecycle)까지 모두 책임집니다.
- **생성자 호출 예시:**

    ```Java
    public class OrderService {
	    // 개발자가 직접 생성자를 호출하여 의존성 객체를 만듦
        private UserRepository userRepository = new UserRepository(); 
        public void createOrder() {
            userRepository.findUser();
        }
    }
    ```
    

#### **🚨 직접 할 때의 문제점**

- **강한 결합(Tight Coupling):** 의존하는 객체의 생성자에 파라미터가 추가되거나 클래스이름이 바뀌면 모든 호출부의 코드를 찾아가서 `new` 부분을 다 수정해야 합니다.
- **관리 사각지대:** 스프링이 제공하는 **트랜잭션(@Transactional)**, **보안**, **로깅** 등의 강력한 부가 기능을 전혀 사용할 수 없습니다.

---

### 2. 스프링한테 받는 경우 (의존성 주입, DI)

> **비유:** 식당 주방장인 나는 요리만 할 뿐, **재료나 도구는 주방 보조(Spring)가 내 손에 쥐어주는 것**

#### **작동 방식**

- **호출 시점:** 애플리케이션 실행 시 스프링 컨테이너가 미리 객체(Bean)를 만들며 개발자 대신 동적으로 생성자를 호출합니다.
- **주도권:** 스프링 컨테이너가 객체를 생성하고 관리하며, 필요한 곳에 '주입'해줍니다.
- **생성자 주입 예시:**
    ```Java
    @Service
    public class OrderService {
        private final UserRepository userRepository;
        // @Autowired (스프링 4.3 이후 생성자 하나면 생략 가능)
        // 내가 new 하는 게 아니라, 스프링이 "여기UserRepository 객체 있어!" 하고 생성자로 넣어줌
        public OrderService(UserRepository userRepository) {
            this.userRepository = userRepository;
        }
    }
    ```
    

#### **🚨 스프링이 해줄 때의 이점**

- **테스트 용이성:** 가짜 객체(Mock)를 넣어 테스트하기 좋습니다.
- **강화된 기능:** 스프링이 관리하는 객체(Bean)가 되는 순간, 앞서 설명한 **자동화된 기능(Proxy, AOP 등)**이 장착됩니다.
- **유연성:** `UserRepository`가 인터페이스라면, 코드 한 줄 안 바꾸고 구현체만 다른 것으로 싹 갈아 끼울 수 있습니다.
- **단일 책임:** `OrderService`는 자기 할 일(비즈니스 로직)에만 집중하고, 객체를 어떻게 만드는지는 신경 쓰지 않아도 됩니다.

---

### 3. 왜 필드주입대신 '생성자 주입'을 권장하나요?

1. **객체 생성의 원자성:** 재료가 없으면 아예 객체가 안 만들어지므로 런타임 에러 `NullPointerException` 를 방지합니다.
2. **불변성:** `final`을 사용할 수 있어 의존성이 도중에 바뀔 위험이 없습니다.
3. **순환 참조 방지:** 구동 시점에 서로를 호출하는 잘못된 설계를 바로 잡아줍니다.

### 4. 스프링의 관리 범위: "컨테이너"라는 울타리

> **"스프링은 오직 자기 컨테이너에 등록된 객체(Bean)만 알고 관리합니다."**

#### **Q. 왜 스프링이 메모리(JVM) 전체를 스캔해서 관리해주지 않나요?**

- **효율성 문제:** 자바 프로그램이 실행되면 수만 개의 `String`, `List`, `DTO` 같은 객체들이 `new`를 통해 생성되고 사라집니다. 스프링이 이 모든 사소한 객체들을 다 추적하고 기능을 붙이려 한다면 서버는 과부하로 멈출 것입니다.
- **관심사 분리:** 스프링은 **애플리케이션의 뼈대(Service, Repository 등)**가 되는 핵심 부품들만 집중적으로 관리하도록 설계되었습니다.

#### **Q. 내가 `new`로 만든 객체를 스프링이 관리하게 할 순 없나요?**

- **@Bean 등록:** 개발자가 수동으로 객체를 생성하되, 이를 스프링에게 **"이제부터 이건 네가 맡아줘"**라고 넘겨줄 수 있습니다. 주로 외부 라이브러리 객체를 등록할 때 사용합니다.
#### **수동 등록 예시 (@Configuration + @Bean):**

```Java
@Configuration
public class AppConfig {
    @Bean
    public ExternalLibraryService externalLibraryService() {
        // 1. 개발자가 직접 new로 객체를 만듭니다.
        ExternalLibraryService service = new ExternalLibraryService();
        // 2. 초기화 설정을 직접 해줍니다.
        service.setup("API_KEY");
        // 3. 리턴하면 스프링이 이를 받아서 'Bean'으로 관리하기 시작합니다.
        return service; 
    }
}
```

- **결과:** 이제 `new`로 만든 `externalLibraryService`도 스프링 컨테이너 안으로 들어갔으므로, 다른 곳에서 `@Autowired`로 주입받을 수 있고 트랜잭션 등 스프링의 기능도 적용받을 수 있습니다.
    

> [!INFO] 핵심 요약
>
> 1. **`new`**는 내가 객체를 직접 통제하지만 스프링의 지원을 못 받는 방식입니다.
>     
> 2. **스프링 주입**은 스프링이 관리하는 울타리(컨테이너) 안의 객체들끼리만 가능합니다.
>     
> 3. 내가 직접 `new`를 쓰더라도 **`@Bean`**으로 등록하면 스프링의 관리 영역으로 편입시킬 수 있습니다.
>     

| **구분**        | **개발자의 직접 생성 (new)**            | **스프링 컨테이너 생성 (Bean)**             |
| ------------- | ------------------------------- | ---------------------------------- |
| **주체 (Who)**  | **개발자** (제어권이 코드에 있음)           | **스프링 컨테이너**                       |
| **시점 (When)** | **런타임 중 필요 시점** (해당 로직 실행되는 순간) | **애플리케이션 실행 시** (Startup 타임)       |
| **방법 (How)**  | **정적 생성** (직접 생성자 호출)           | **동적 생성** (**리플렉션**을 통한 호출)        |
| **관리 범위**     | 생성 후 가비지 컬렉터(GC)가 수거할 때까지       | 생성부터 소멸(@PreDestroy)까지 **전 과정 관리** |
| **의존성 연결**    | 개발자가 직접 객체를 찾아 주입               | 스프링이 필요한 부품을 찾아 **자동 주입(DI)**      |
| **기능 강화**     | 순수한 자바 객체 기능만 수행                | **프록시(Proxy)**를 입혀 트랜잭션, 로깅 등 추가   |
| **메모리 효율**    | 호출될 때마다 새 객체 생성 가능              | 기본적으로 **싱글톤** (하나만 만들어 공유)         |
