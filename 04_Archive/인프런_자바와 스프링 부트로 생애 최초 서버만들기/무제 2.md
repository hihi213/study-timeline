
### 1. 웹 아키텍처 및 서버 기초

- **서버 (Server)**: 네트워크를 통해 클라이언트의 요청을 받아 서비스를 제공하는 주체.
    - **하드웨어 관점**: 서버 프로그램을 실행하기 위해 고성능 CPU, RAM 등을 갖춘 물리적/가상 컴퓨터.
    - **소프트웨어 관점**: 특정 포트(Port)를 열고 대기하며, 요청이 오면 응답을 반환하는 데몬(Daemon) 프로세스 (예: Apache, Nginx, Tomcat).
- **클라이언트 (Client)**: 서버에 연결을 요청하고 응답을 받아 사용자에게 보여주는 주체.
    - **User-Agent**: HTTP 통신에서 요청을 보내는 소프트웨어 식별자(브라우저, Postman 등).
    - **프론트엔드 클라이언트**: 브라우저 환경에서 실행되며 UI/UX를 담당하는 애플리케이션 (React, Vue 등).
- **API (Application Programming Interface)**: 소프트웨어 간의 상호작용을 위한 **계약(Contract)**이자 명세.
    - **Interface**: 내부 구현을 모르더라도 정의된 입력(Input)과 출력(Output)만으로 기능을 사용할 수 있게 하는 매개체.
    - **Web API**: 네트워크(HTTP)를 통해 원격 서버의 리소스나 기능을 사용할 수 있게 제공되는 인터페이스 (REST, GraphQL).
    - **Library API**: 코드 레벨에서 함수나 클래스를 호출하여 기능을 사용하는 인터페이스 (예: JDK API).
        

### 2. 네트워크 및 통신 (HTTP)

- **HTTP 요청 (HTTP Request)**: 클라이언트와 서버 간의 **무상태(Stateless)** 통신 프로토콜.
    - **구성**: Header(메타데이터), Body(데이터), Method(행위: GET, POST 등).
    - API 요청과의 차이: API 요청은 '기능 호출'이라는 논리적 행위이며, 웹 환경에서는 HTTP라는 '운송 수단'을 사용하여 수행됨.
- **URL (Uniform Resource Locator)**: 네트워크 상에서 자원(Resource)의 **위치**를 지정하는 표준 주소 체계.
    - **구성**: `프로토콜://도메인:포트/경로?쿼리스트링`
    - **라우팅의 기준**: 서버는 URL의 경로(Path)를 보고 어떤 컨트롤러가 처리할지 결정함.
- **도메인 (Domain - Network)**: IP 주소를 사람이 식별하기 쉬운 문자로 매핑한 네트워크 주소 (DNS 시스템에 의해 IP로 변환됨).
- **쿼리 (Query)**: 데이터 베이스나 웹 서버에 특정 정보를 요청하는 질의.
    - **Query String**: URL 뒤에 `?key=value` 형태로 붙어, 리소스에 대한 정렬, 필터링 등 **추가적인 옵션**을 전달하는 데이터.
        

### 3. 애플리케이션 계층 및 데이터 (Backend)

- **컨트롤러 (Controller)**: **프레젠테이션 계층 (Presentation Layer)**.
    - 역할: 외부 요청(HTTP)을 받아 유효성을 검증하고, 서비스 계층으로 위임한 뒤, 결과를 적절한 응답 형식(JSON, HTML 등)으로 변환하여 반환.
- **서비스 (Service)**: **비즈니스 계층 (Business Layer)**.
    - 역할: 애플리케이션의 핵심 로직(규칙, 계산, 흐름 제어)을 수행. 트랜잭션(Transaction) 관리의 단위가 됨.
- **리포지토리 (Repository)**: **데이터 접근 계층 (Data Access Layer)**.
    - 역할: DB, 파일 등 데이터 저장소에 접근하는 코드를 추상화한 계층. 비즈니스 로직이 SQL이나 구체적인 저장 기술에 의존하지 않도록 분리함.
- **도메인 (Domain - Software)**: 소프트웨어가 해결하고자 하는 **문제 영역(Problem Space)**.
    - **도메인 모델**: 문제 영역의 핵심 개념(User, Order)을 객체로 추상화한 것. 상태(Data)와 행위(Behavior)를 모두 가질 수 있음.
- **엔티티 (Entity)**: 식별자(ID)를 가지며, 시간이 지나도 지속성을 가지는 데이터 객체.
    - DB 관점: 테이블과 1:1로 매핑되는 영속성 객체.
- **비즈니스 로직**: 데이터를 단순 저장/조회하는 것을 넘어, 업무 규칙에 따라 데이터를 가공, 검증, 계산하는 실질적인 처리 과정.
    

### 4. 상태 관리 및 저장소

- **세션 (Session)**: **서버 측**에서 클라이언트의 상태 정보를 저장하는 논리적 연결 단위. 보안이 중요한 정보 저장에 유리.
- **쿠키 (Cookie)**: **클라이언트(브라우저) 측**에 저장되는 작은 텍스트 데이터. 주로 세션 ID를 운반하거나 사용자 설정을 저장하는 데 사용.
- **캐시 (Cache)**: 데이터나 계산 결과를 미리 복사해 두는 **임시 고속 저장소**.
    - 목적: DB 부하 감소 및 응답 속도 향상 (L1/L2 캐시, Redis, CDN 등).
        

### 5. 인프라 및 운영

- **빌드 (Build)**: 소스 코드를 컴파일, 패키징, 테스트하여 **실행 가능한 아티팩트(Artifact, 예: .jar, .exe)**로 만드는 과정.
- **배포 (Deploy)**: 빌드된 아티팩트를 실제 운영 환경의 서버에 업로드하고 실행하여 서비스 가능한 상태로 만드는 것.
- **로드 밸런싱 (Load Balancing)**: 트래픽(부하)을 여러 서버로 분산시켜 시스템의 안정성과 가용성을 확보하는 기술 (L4/L7 스위치, Nginx 등).
- **스케일링 (Scaling)**:
    - **Scale-up**: 서버 자체의 성능(CPU, RAM)을 높임.
    - **Scale-out**: 서버의 대수를 늘려 병렬 처리 능력을 높임.

### 📥 API 호출 및 데이터 처리 전체 흐름 (심화)

1. **Event & Request Generation**:
    
    - 사용자 액션 발생 → 프론트엔드(Client)에서 **API 요청** 생성.
    - 브라우저는 이를 **HTTP 메시지**로 변환하여 지정된 URL로 전송.
        
2. **Network Transport**:
    
    - DNS 조회 → IP 확인 → TCP/IP 연결 → 서버로 패킷 전송.
        
3. **Routing & Controller**:
    
    - 서버(Web Server/WAS)가 요청 수신.
    - **라우터**가 URL과 HTTP Method를 분석하여 적절한 **컨트롤러(Controller)**에 매핑.
    - 컨트롤러는 요청 데이터(Body, Query String)를 자바 객체(DTO)로 변환(Parsing).
        
4. **Service Layer (Business Logic)**:
    
    - 컨트롤러가 **서비스(Service)** 메서드 호출.
    - 서비스는 비즈니스 규칙(예: 권한 확인, 중복 검사)을 수행하고 트랜잭션을 시작.
        
5. **Data Access (Repository & DB)**:
    
    - 서비스가 데이터가 필요하면 **리포지토리(Repository)** 호출.
    - 리포지토리는 DB와 통신(SQL 실행)하여 **엔티티(Entity)** 데이터를 조회 후 반환.
        
6. **Response Creation**:
    
    - 서비스는 로직 처리 결과를 컨트롤러에 반환.
    - 컨트롤러는 데이터를 **직렬화(Serialization, 예: Java Object → JSON)**하여 `ResponseEntity` 생성.
    - HTTP 상태 코드(`200 OK`)와 함께 응답 전송.
        
7. **Rendering**:
    
    - 클라이언트가 JSON 응답을 수신하고 파싱하여 UI에 반영.
