## 1. 계층 분리: 컨트롤러는 진입점 역할만 수행해야 한다

애플리케이션이 복잡해질수록 하나의 함수나 클래스가 너무 많은 일을 하면 유지보수가 불가능해집니다. 이를 해결하기 위해 역할을 3가지 계층으로 분리합니다.

### **계층별 역할과 책임**

|**계층**|**역할 명칭**|**핵심 책임**|
|---|---|---|
|**Presentation**|**Controller**|API 진입점. HTTP 요청 수신 및 Body를 객체로 변환.|
|**Business**|**Service**|비즈니스 로직(업무 흐름, 조건 검사) 담당. 데이터를 어떻게 쓸지 결정.|
|**Data Access**|**Repository**|실제 Database와의 통신 및 SQL 실행 담당.|
>sql실행로직이 서비스에 들어가면 서비스가 복잡해져 repository로 분리

### **좋은 코드가 중요한 이유 (리팩토링의 목적)**

- **가독성:** 개발자는 코드를 쓰는 시간보다 읽는 시간이 더 많습니다.
- **유지보수성:** 함수가 너무 크면 동시에 여러 명이 수정할 수 없고, 수정 시 전체 시스템에 미치는 영향을 파악하기 어렵습니다.
- **테스트 용이성:** 한 가지 일만 수행하는 작은 함수는 테스트 코드를 작성하기 매우 쉽습니다.

## 2. 스프링 컨테이너와 스프링 빈(Bean)

직접 `new`를 하지 않아도 객체가 동작하는 이유는 스프링이 **컨테이너**를 통해 객체를 관리하기 때문입니다.

### **스프링 빈(Bean)이란?**

- 스프링 컨테이너에 의해 생성되고 관리되는 자바 객체입니다.
- 서버가 시작되면 스프링은 어노테이션(`@Component` 등)이 붙은 클래스를 스캔하여 인스턴스를 생성하고 컨테이너에 보관합니다.
- 빈으로 등록될 때 **의존성 정보, 빈의 이름/타입, 라이프사이클** 정보가 함께 관리됩니다.
    

### **자동 빈 등록의 마법: Auto-Configuration**

`JdbcTemplate`이나 `EntityManager`를 직접 빈으로 등록하지 않아도 사용할 수 있는 이유는 스프링 부트의 **자동 설정(Auto-Configuration)** 덕분입니다.

- **Gradle의 역할:** `build.gradle`에 `implementation`으로 라이브러리를 추가하면 필요한 파일을 다운로드합니다.
- **Autoconfigure의 역할:** 서버 실행 시 `spring-boot-autoconfigure` 라이브러리가 프로젝트에 추가된 라이브러리들을 감지하여 필요한 객체들을 자동으로 빈으로 등록해줍니다.

## 3. 제어의 역전(IoC)과 의존성 주입(DI)

객체를 직접 생성(`new`)하는 대신 스프링으로부터 주입받는 구조는 코드의 유연성을 극대화합니다.

### **직접 생성(new) vs 스프링 주입(DI)**

- **직접 생성:** 개발자가 마트에서 직접 프라이팬을 사오는 것 (강한 결합).
- **스프링 주입:** 요리사는 요리만 하고, 재료는 주방 보조(Spring)가 손에 쥐어주는 것 (느슨한 결합).
    

### **인터페이스 도입과 구현체 교체**

인터페이스를 기반으로 생성자 주입을 사용하면, 서비스 코드를 단 한 줄도 수정하지 않고 데이터 저장소(Memory → MySQL)를 갈아끼울 수 있습니다.

- **@Primary:** 동일한 인터페이스의 구현체가 여러 개일 때, 우선적으로 주입할 빈을 지정합니다.
- **결과:** 제어권이 개발자에서 스프링으로 넘어가는 **제어의 역전(IoC)**이 실현됩니다.

## 4. 스프링 빈을 다루는 방법

### **1) 빈 등록 방식**

- **자동 등록 (@Component 기반):** `@Service`, `@Repository`, `@RestController` 등을 사용합니다. 스프링이 서버 가동 시 자동으로 스캔합니다.
- **수동 등록 (@Configuration + @Bean):** 외부 라이브러리나 복잡한 설정이 필요한 클래스를 등록할 때 사용합니다. 메서드가 반환하는 객체를 빈으로 등록합니다.
    

### **2) 빈 주입 방식**

|**방식**|**특징**|**비고**|
|---|---|---|
|**생성자 주입**|생성 시점에 의존성 주입. `final` 사용 가능.|**가장 권장됨** (불변성, 순환 참조 방지)|
|**Setter 주입**|언제든 변경 가능하여 오작동 위험 있음.|권장하지 않음|
|**필드 주입**|코드는 간결하나 테스트가 매우 어려움.|권장하지 않음|

### **3) 세밀한 제어**

- **@Qualifier("이름"):** 주입받는 지점에서 특정 빈의 이름을 지정하여 주입받습니다. `@Primary`보다 우선순위가 높습니다.

## 5. 최종 비교: new vs 스프링 빈(Bean)

|**구분**|**개발자의 직접 생성 (new)**|**스프링 컨테이너 생성 (Bean)**|
|---|---|---|
|**주체 (Who)**|**개발자** (제어권이 코드에 있음)|**스프링 컨테이너** (제어의 역전, IoC)|
|**시점 (When)**|런타임 중 필요 시점|**애플리케이션 실행 시** (Startup 타임)|
|**방법 (How)**|정적 생성 (직접 호출)|**동적 생성** (**리플렉션**을 통한 호출)|
|**의존성 연결**|직접 객체를 찾아 주입|스프링이 필요한 부품을 찾아 **자동 주입(DI)**|
|**기능 강화**|순수 자바 객체 기능만 수행|**프록시(Proxy)**를 통한 트랜잭션, 보안 등 추가|
|**메모리 효율**|호출 시마다 생성 가능|기본적으로 **싱글톤** (하나를 공유)|

> [!TIP] 핵심 인사이트
>
> "처음부터 인터페이스와 생성자 주입 기반으로 구조를 짜면, 나중에 비즈니스 로직의 수정 없이 인프라(DB, 외부 API 등)만 자유롭게 갈아끼울 수 있는 유연한 서버가 됩니다."
