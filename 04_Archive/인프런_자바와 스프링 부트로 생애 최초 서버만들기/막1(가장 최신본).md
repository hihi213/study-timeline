# 📚 3장. 역할 분리와 스프링 컨테이너 (완벽 정리)

## 1️⃣ 왜 코드를 분리해야 하는가? (Layered Architecture)

### **1. 문제점: 비대한 컨트롤러 (Massive Controller)**

만약 하나의 컨트롤러 API에서 요청 검증 + 데이터 조회(10개 테이블) + 비즈니스 계산 + 응답 가공을 모두 처리한다면?

코드가 3,000줄이 넘어가며 다음과 같은 지옥이 펼쳐집니다.

- **가독성 저하:** 코드를 읽고 이해하는 데 너무 많은 시간이 걸립니다.
- **유지보수 불가:** 여러 명이 동시에 수정할 수 없고, 작은 수정이 전체에 영향을 미칩니다.
- **테스트 어려움:** 너무 많은 기능이 섞여 있어 테스트 코드를 짜기 힘듭니다.

### **2. 해결책: 역할에 따른 3단 분리**

코드는 요구사항을 표현하는 언어입니다. **"함수와 클래스는 작아야 하며, 하나의 책임만 가져야 한다"**는 원칙에 따라 역할을 나눕니다.

| **계층 (Layer)** | **역할 (Responsibility)**  | **핵심 내용**                              |
| -------------- | ------------------------ | -------------------------------------- |
| **Controller** | **진입점 (Entry Point)**    | HTTP 요청을 받아 객체로 변환(Parsing)하고, 결과만 응답. |
| **Service**    | **비즈니스 로직 (Business)**   | 업무 흐름 제어, 예외 처리, 데이터 가공 담당.            |
| **Repository** | **데이터 접근 (Data Access)** | SQL을 실행하여 실제 DB와 소통하는 역할.              |

> **💡 핵심:** SQL이 바뀌면 `Repository`만, 업무 규칙이 바뀌면 `Service`만 수정하면 됩니다.

## 2️⃣ 스프링 컨테이너와 빈 (Spring Container & Bean)

### **1. "new"를 안 했는데 어떻게 객체가 있죠?**

우리가 직접 `new Service()`를 하지 않아도 서버가 잘 돌아가는 이유는 **스프링 컨테이너** 덕분입니다.

- **스프링 컨테이너:** 서버 실행 시 생성되는 **거대한 객체 관리 상자**입니다.
- **스프링 빈 (Bean):** 스프링 컨테이너에 의해 생성되고 관리되는 자바 객체입니다.

### **2. 빈(Bean)의 생명주기 관리**

서버가 켜지면 스프링은 다음 과정을 수행합니다.

1. **스캔:** `@Component` (또는 `@Controller`, `@Service` 등)가 붙은 클래스를 찾습니다.
2. **등록:** 해당 클래스의 객체(Instance)를 딱 **하나만 생성(Singleton)**하여 컨테이너에 넣습니다.
	- 이때 **의존성 정보, 빈의 이름/타입, 라이프사이클** 정보를 함께 등록합니다
	- 의존성정보: 이 객체가 생성될때 어떤 다른빈들을 필요로 하는지, 생성자에 어떤 파라미터들이 필요한지(자동주입)
3. **조립:** 객체 생성 시 필요한 의존성(다른 빈)이 있다면 찾아서 넣어줍니다.
    

### **💡 참고: Gradle과 자동 설정 (AutoConfiguration)**
>객체마다 개발자가 직접 빈으로 일일히 등록하지 않게 해주는 스프링 부트의 자동설정

- **`build.gradle`**: 필요한 라이브러리(Jar)를 다운로드하고 프로젝트에 추가합니다.
- **`spring-boot-starter-data-jpa`**: JPA 사용에 필요한 라이브러리 모음(Starter)입니다.
- **`AutoConfiguration`**: 스프링 부트는 라이브러리가 추가된 것을 감지하면, 관련된 필수 객체(예: `EntityManager`, `JdbcTemplate` 등)를 **자동으로 빈으로 등록**해 줍니다. 우리가 일일이 등록하지 않아도 되는 이유입니다.

## 3️⃣ 제어의 역전 (IoC)과 의존성 주입 (DI)

**"객체 관리의 주도권을 개발자에게서 스프링으로 넘긴다"**는 것이 핵심입니다.

### **단계별 발전 과정: Memory → MySQL 교체 시나리오**

#### **단계 1: 직접 `new` 사용 (최악 - 강한 결합)**

```Java
// 개발자가 직접 '메모리' 저장소를 선택함
BookRepository repo = new BookMemoryRepository(); 
``` 

- **문제:** MySQL로 바꾸려면 이 코드를 찾아가서 `new BookMySQLRepository()`로 **직접 수정**해야 합니다.
    

#### **단계 2: 인터페이스 도입 (개선)**

```Java
// 타입은 추상화했지만, 구현체 선택은 여전히 개발자 몫
BookRepository repo = new BookMemoryRepository(); 
``` 

- **문제:** 여전히 `new` 뒤에 구현체를 선택하는 코드는 여전히 개발자가 작성해야 함.

#### **단계 3: 스프링 DI 적용 (완성 - IoC)**

```Java
@Service
public class BookService {
    private final BookRepository bookRepository;

    // 스프링: "너한테 필요한 Repository 구현체는 내가 알아서 넣어줄게!"
    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }
}
```

- **IoC (제어의 역전):** 객체를 생성하고 연결하는 책임이 **개발자 → 스프링**으로 이동했습니다.
- **효과:** 코드를 한 줄도 수정하지 않고, `@Repository` 어노테이션 위치만 옮기면 DB가 교체됩니다.

## 4️⃣ 실전: 빈을 등록하고 주입받는 법
> **"스프링은 오직 자기 컨테이너에 등록된 객체(Bean)만 알고 관리합니다."**

#### **Q. 왜 스프링이 메모리(JVM) 전체를 스캔해서 관리해주지 않나요?**

- **효율성 문제:** 자바 프로그램이 실행되면 수만 개의 `String`, `List`, `DTO` 같은 객체들이 `new`를 통해 생성되고 사라집니다. 스프링이 이 모든 사소한 객체들을 다 추적하고 기능을 붙이려 한다면 서버는 과부하로 멈출 것입니다.
- **관심사 분리:** 스프링은 **애플리케이션의 뼈대(Service, Repository 등)**가 되는 핵심 부품들만 집중적으로 관리하도록 설계되었습니다.

#### **Q. 내가 `new`로 만든 객체를 스프링이 관리하게 할 순 없나요?**

- **@Bean 등록:** 개발자가 수동으로 객체를 생성하되, 이를 스프링에게 **"이제부터 이건 네가 맡아줘"**라고 넘겨줄 수 있습니다. 주로 외부 라이브러리 객체를 등록할 때 사용합니다.

### **1. 빈 등록 방법**

- **자동 등록 (`@Component` 계열):**
    - `@Controller`, `@Service`, `@Repository`
    - 우리가 직접 작성한 클래스에 사용합니다.
- **수동 등록 (`@Configuration` + `@Bean`):**
    - 외부 라이브러리(예: `Gson`, `Querydsl`)를 빈으로 등록할 때 사용합니다.
    - 메서드가 **반환(Return)하는 객체**가 빈이 됩니다.

```Java
@Configuration
public class AppConfig {
    @Bean
    public ExternalLibraryService externalLibraryService() {
        // 1. 개발자가 직접 new로 객체를 만듭니다.
        ExternalLibraryService service = new ExternalLibraryService();
        // 2. 초기화 설정을 직접 해줍니다.
        service.setup("API_KEY");
        // 3. 리턴하면 스프링이 이를 받아서 'Bean'으로 관리하기 시작합니다.
        return service; 
    }
}
```

- **결과:** 이제 `new`로 만든 `externalLibraryService`도 스프링 컨테이너 안으로 들어갔으므로, 다른 곳에서 `@Autowired`로 주입받을 수 있고 트랜잭션 등 스프링의 기능도 적용받을 수 있습니다.

> [!INFO] 핵심 요약
>
> 1. **`new`**는 내가 객체를 직접 통제하지만 스프링의 지원을 못 받는 방식입니다.
>     
> 2. **스프링 주입**은 스프링이 관리하는 울타리(컨테이너) 안의 객체들끼리만 가능합니다.
>     
> 3. 내가 직접 `new`를 쓰더라도 **`@Bean`**으로 등록하면 스프링의 관리 영역으로 편입시킬 수 있습니다.
>

### **2. 빈 주입 방법 (우선순위)**
 @AutoWired: 생성자에 있는 매걔변수에 스프링빈을 넣어달라는 의미
- **1순위: 생성자 주입 (추천 ⭐)**
    - 생성자가 1개면 `@Autowired` 생략 가능.
    - 필수 의존성 보장, 불변성(`final`) 유지 가능.
- **2순위: Setter** (비추)
	- Setter만들고 그 위에 @AutoWired를 붙이기
	- 누군가 Setter를 사용하면 다른인스턴스로 교차되기 때문에 오작동할 요지가 있다.
- 3순위: 필드 주입 (금지)
	- private JdbcTemplate jdbcTemplate; 필드에 직접 @AutoWired붙여준다
	- 테스트를 어렵게 만드는 요인이다.

> [!NOTE] 왜 필드주입대신 '생성자 주입'을 권장하나요?
> 1. **객체 생성의 원자성:** 재료가 없으면 아예 객체가 안 만들어지므로 런타임 에러 `NullPointerException` 를 방지합니다.
> 2. **불변성:** `final`을 사용할 수 있어 의존성이 도중에 바뀔 위험이 없습니다.
> 3. **순환 참조 방지:** 구동 시점에 서로를 호출하는 잘못된 설계를 바로 잡아줍니다.

### **💡 같은 타입의 빈이 여러 개라면?**

1. **`@Primary`**: "일단 헷갈리면 얘를 써!" (기본값 설정)
2. **`@Qualifier("이름")`**: "콕 집어서 얘를 가져와." (Primary보다 우선순위 높음)

> [!TIP] 핵심 인사이트
>
> "처음부터 인터페이스와 생성자 주입 기반으로 구조를 짜면, 나중에 비즈니스 로직의 수정 없이 인프라(DB, 외부 API 등)만 자유롭게 갈아끼울 수 있는 유연한 서버가 됩니다."
> **⚠️ 주의:** `static` 메서드는 객체 생성 없이 클래스 레벨에서 실행되므로, 스프링 컨테이너의 도움(DI, AOP 등)을 전혀 받을 수 없습니다. 비즈니스 로직은 `static` 대신 **빈 주입 방식**을 사용하세요.

  
- 알아야할것
	- 클래스 이름으로 메서드를 부르는 건 **static 메서드** 이다
		- **정적 메서드(static)** 는 객체 생성 없이 **클래스 이름으로 직접 호출**할 수 있어요.
		- **JVM은 객체가 없는 상태에서 바로 메서드를 실행**하려고 해요.
	- 그럼 Spring이 만들어준 객체를 우리가 쓰려면?
		- 1. 먼저 클래스 안에 우리가 사용할 객체를 담기 위한 **필드 선언**
			- private final UserRepository userRepository;
		- 2. 생성자도 수정: 생성자의 매개변수로 Bean을 받아와서, 위에서 선언한 필드에 저장합니다.
		- 이렇게 작성하면 Spring이 자동으로 생성한 Bean을 우리 코드에 주입해줘

## 코드상 new와 스프링 주입의 차이
### 1. 개발자가 직접 `new` 하는 경우 (수동 제어)

> **비유:** 내가 요리할 때 필요한 **프라이팬을 직접 마트에 가서 사오는 것**

#### **작동 방식**

- **호출 시점:** 코드가 실행되는 도중 `new` 문장을 만나는 그 즉시 생성자가 호출됩니다.
- **주도권:** 개발자가 객체의 생성부터 소멸(Lifecycle)까지 모두 책임집니다.
- **생성자 호출 예시:**

    ```Java
    public class OrderService {
	    // 개발자가 직접 생성자를 호출하여 의존성 객체를 만듦
        private UserRepository userRepository = new UserRepository(); 
        public void createOrder() {
            userRepository.findUser();
        }
    }
    ```
    

#### **🚨 직접 할 때의 문제점**

- **강한 결합(Tight Coupling):** 의존하는 객체의 생성자에 파라미터가 추가되거나 클래스이름이 바뀌면 모든 호출부의 코드를 찾아가서 `new` 부분을 다 수정해야 합니다.
- **관리 사각지대:** 스프링이 제공하는 **트랜잭션(@Transactional)**, **보안**, **로깅** 등의 강력한 부가 기능을 전혀 사용할 수 없습니다.

---

### 2. 스프링한테 받는 경우 (의존성 주입, DI)

> **비유:** 식당 주방장인 나는 요리만 할 뿐, **재료나 도구는 주방 보조(Spring)가 내 손에 쥐어주는 것**

#### **작동 방식**

- **호출 시점:** 애플리케이션 실행 시 스프링 컨테이너가 미리 객체(Bean)를 만들며 개발자 대신 동적으로 생성자를 호출합니다.
- **주도권:** 스프링 컨테이너가 객체를 생성하고 관리하며, 필요한 곳에 '주입'해줍니다.
- **생성자 주입 예시:**
    ```Java
    @Service
    public class OrderService {
        private final UserRepository userRepository;
        // @Autowired (스프링 4.3 이후 생성자 하나면 생략 가능)
        // 내가 new 하는 게 아니라, 스프링이 "여기UserRepository 객체 있어!" 하고 생성자로 넣어줌
        public OrderService(UserRepository userRepository) {
            this.userRepository = userRepository;
        }
    }
    ```
    

#### **🚨 스프링이 해줄 때의 이점**

- **테스트 용이성:** 가짜 객체(Mock)를 넣어 테스트하기 좋습니다.
- **강화된 기능:** 스프링이 관리하는 객체(Bean)가 되는 순간, 앞서 설명한 **자동화된 기능(Proxy, AOP 등)**이 장착됩니다.
- **유연성:** `UserRepository`가 인터페이스라면, 코드 한 줄 안 바꾸고 구현체만 다른 것으로 싹 갈아 끼울 수 있습니다.
- **단일 책임:** `OrderService`는 자기 할 일(비즈니스 로직)에만 집중하고, 객체를 어떻게 만드는지는 신경 쓰지 않아도 됩니다.

### **📊 한 눈에 비교하기**

|**구분**|**개발자가 직접 new**|**스프링 컨테이너 (Bean)**|
|---|---|---|
|**주체**|**개발자** (내 코드 안에서 결정)|**스프링** (외부에서 결정 후 주입)|
|**생성 시점**|코드가 실행되는 라인 지날 때|서버가 켜질 때 (Startup)|
|**메모리**|호출할 때마다 계속 생성 (낭비)|**싱글톤** (하나만 만들어 공유)|
|**트랜잭션**|적용 불가 ❌|**적용 가능 ✅ (@Transactional)**|
|**유지보수**|변경 시 코드 수정 필요 (불편)|설정만 변경하면 됨 (편안)|

| **구분**        | **개발자의 직접 생성 (new)**            | **스프링 컨테이너 생성 (Bean)**             |
| ------------- | ------------------------------- | ---------------------------------- |
| **주체 (Who)**  | **개발자** (제어권이 코드에 있음)           | **스프링 컨테이너**                       |
| **시점 (When)** | **런타임 중 필요 시점** (해당 로직 실행되는 순간) | **애플리케이션 실행 시** (Startup 타임)       |
| **방법 (How)**  | **정적 생성** (직접 생성자 호출)           | **동적 생성** (**리플렉션**을 통한 호출)        |
| **관리 범위**     | 생성 후 가비지 컬렉터(GC)가 수거할 때까지       | 생성부터 소멸(@PreDestroy)까지 **전 과정 관리** |
| **의존성 연결**    | 개발자가 직접 객체를 찾아 주입               | 스프링이 필요한 부품을 찾아 **자동 주입(DI)**      |
| **기능 강화**     | 순수한 자바 객체 기능만 수행                | **프록시(Proxy)**를 입혀 트랜잭션, 로깅 등 추가   |
| **메모리 효율**    | 호출될 때마다 새 객체 생성 가능              | 기본적으로 **싱글톤** (하나만 만들어 공유)         |
