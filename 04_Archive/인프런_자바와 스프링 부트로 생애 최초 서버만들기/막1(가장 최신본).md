
# 📚 3장. 역할 분리와 스프링 컨테이너 (완벽 정리)

## 1️⃣ 왜 코드를 분리해야 하는가? (Layered Architecture)

### **1. 문제점: 비대한 컨트롤러 (Massive Controller)**

만약 하나의 컨트롤러 API에서 요청 검증 + 데이터 조회(10개 테이블) + 비즈니스 계산 + 응답 가공을 모두 처리한다면?

코드가 3,000줄이 넘어가며 다음과 같은 지옥이 펼쳐집니다.

- **📉 가독성 최악:** 코드를 읽는 데만 몇 시간이 걸립니다.
- **🛠 유지보수 불가:** 로직 하나를 수정하면 전혀 상관없는 기능이 고장 납니다. (Side Effect)
- **🧪 테스트 불가:** 너무 많은 기능이 섞여 있어 단위 테스트 작성이 불가능합니다.
    

### **2. 해결책: 역할에 따른 3단 분리**

**"함수와 클래스는 작아야 하며, 하나의 책임만 가져야 한다(SRP)"**는 원칙에 따라 계층을 나눕니다.

|**계층 (Layer)**|**구성 요소**|**핵심 역할 (Responsibility)**|
|---|---|---|
|**Presentation**|**Controller**|**"웨이터"**<br><br>  <br><br>HTTP 요청 수신, 파라미터 검증, 결과 응답 (진입점)|
|**Business**|**Service**|**"요리사"**<br><br>  <br><br>실제 업무 흐름 제어, 데이터 가공, 트랜잭션 관리|
|**Data Access**|**Repository**|**"재료 창고지기"**<br><br>  <br><br>DB에 접근하여 SQL을 실행하고 데이터 저장/조회|

> **💡 핵심:** SQL이 바뀌면 `Repository`만, 업무 규칙이 바뀌면 `Service`만 수정하면 됩니다.

## 2️⃣ 스프링 컨테이너와 빈 (Spring Container & Bean)

### **1. "new"를 안 했는데 어떻게 객체가 있죠?**

우리가 직접 `new Service()`를 하지 않아도 서버가 잘 돌아가는 이유는 **스프링 컨테이너** 덕분입니다.

- **스프링 컨테이너:** 서버 실행 시 생성되는 **거대한 객체 관리 상자**입니다.
- **스프링 빈 (Bean):** 이 컨테이너 안에 들어있는 **자바 객체**를 부르는 말입니다.
    

### **2. 빈(Bean)의 생명주기 관리**

서버가 켜지면 스프링은 다음 과정을 수행합니다.

1. **스캔:** `@Component` (또는 `@Controller`, `@Service` 등)가 붙은 클래스를 찾습니다.
2. **등록:** 해당 클래스의 객체(Instance)를 딱 **하나만 생성(Singleton)**하여 컨테이너에 넣습니다.
3. **조립:** 객체 생성 시 필요한 의존성(다른 빈)이 있다면 찾아서 넣어줍니다.
    

### **💡 참고: Gradle과 자동 설정 (AutoConfiguration)**

- **`build.gradle`**: 요리 재료(라이브러리/Jar)를 마트에서 사오는 주문서입니다.
- **`spring-boot-starter-data-jpa`**: JPA 요리 세트(Starter)입니다.
- **`AutoConfiguration`**: 스프링 부트는 재료가 있으면 **"어? JPA 있네? 그럼 `EntityManager` 빈은 내가 자동으로 만들어 줄게!"** 하고 알아서 빈을 등록해 줍니다. 이것이 우리가 복잡한 설정 없이 개발할 수 있는 비결입니다.

## 3️⃣ 제어의 역전 (IoC)과 의존성 주입 (DI)

**"객체 관리의 주도권을 개발자에게서 스프링으로 넘긴다"**는 것이 핵심입니다.

### **단계별 발전 과정: Memory → MySQL 교체 시나리오**

#### **단계 1: 직접 `new` 사용 (최악 - 강한 결합)**

Java

```sql
// 개발자가 직접 '메모리' 저장소를 선택함
BookRepository repo = new BookMemoryRepository(); 
``` 

- **문제:** MySQL로 바꾸려면 이 코드를 찾아가서 `new BookMySQLRepository()`로 **직접 수정**해야 합니다.
    

#### **단계 2: 인터페이스 도입 (개선)**

Java

```sql
// 타입은 추상화했지만, 구현체 선택은 여전히 개발자 몫
BookRepository repo = new BookMemoryRepository(); 
``` 

- **문제:** 여전히 `new` 뒤에 구현체 이름이 남아있어 수정이 필요합니다.
    

#### **단계 3: 스프링 DI 적용 (완성 - IoC)**



```Java
@Service
public class BookService {
    private final BookRepository bookRepository;

    // 스프링: "너한테 필요한 Repository 구현체는 내가 알아서 넣어줄게!"
    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }
}
```

- **IoC (제어의 역전):** 객체를 생성하고 연결하는 책임이 **개발자 → 스프링**으로 이동했습니다.
- **효과:** 코드를 한 줄도 수정하지 않고, 외부 설정(어노테이션 등)만으로 DB를 교체할 수 있습니다.

## 4️⃣ 실전: 빈을 등록하고 주입받는 법

### **1. 빈 등록 방법**

- **자동 등록 (`@Component` 계열):**
    - `@Controller`, `@Service`, `@Repository`
    - 우리가 직접 작성한 클래스에 사용합니다.
- **수동 등록 (`@Configuration` + `@Bean`):**
    - 외부 라이브러리(예: `Gson`, `Querydsl`)를 빈으로 등록할 때 사용합니다.
    - 메서드가 **반환(Return)하는 객체**가 빈이 됩니다.
        

### **2. 빈 주입 방법 (우선순위)**

|**순위**|**방식**|**특징**|**추천 여부**|
|---|---|---|---|
|**1**|**생성자 주입**|`final` 키워드 사용 가능, 필수 의존성 보장.|**강력 추천 ⭐**|
|**2**|**Setter 주입**|`setRepository(…)` 메서드 사용. 도중에 객체가 바뀔 위험 있음.|비추천|
|**3**|**필드 주입**|`@Autowired private Repository repo;`. 테스트 코드 작성이 매우 어려움.|**사용 금지 🚫**|

> **⚠️ 주의:** `static` 메서드는 객체 생성 없이 클래스 레벨에서 실행되므로, 스프링 컨테이너의 도움(DI, AOP 등)을 전혀 받을 수 없습니다. 비즈니스 로직은 `static` 대신 **빈 주입 방식**을 사용하세요.

### **💡 같은 타입의 빈이 여러 개라면?**

1. **`@Primary`**: "일단 헷갈리면 얘를 써!" (기본값 설정)
2. **`@Qualifier("이름")`**: "콕 집어서 얘를 가져와." (Primary보다 우선순위 높음)

## 5️⃣ 심화: `new` vs 스프링 주입 (완벽 비교)

이 차이를 이해하는 것이 스프링 초급과 중급을 가르는 기준입니다.

### **1. 개발자가 직접 `new` 하는 경우 (수동 제어)**

> **비유:** 요리할 때 필요한 **프라이팬을 그때그때 마트 가서 사오는 것**

- **작동 방식:** 코드 실행 중 `new`를 만나는 순간 객체가 생성됩니다.
- **문제점:**
    
    1. **관리 사각지대:** 스프링의 기능(**트랜잭션 `@Transactional`**, 보안, 로깅 등)이 적용되지 않습니다.
    2. **강한 결합:** 의존하는 객체가 바뀌면 모든 코드를 뜯어고쳐야 합니다.
        

### **2. 스프링에게 주입받는 경우 (DI)**

> **비유:** 나는 요리만 하고, **도구(프라이팬)는 보조 셰프(Spring)가 내 손에 쥐어주는 것**

- **작동 방식:** 서버 시작 시점에 스프링이 미리 만들어둔 객체(Singleton)를 필요한 곳에 꽂아줍니다.
- **장점:**
    
    1. **기능 강화:** 스프링이 관리하는 객체(Proxy)가 되어 트랜잭션 등 강력한 기능을 무료로 사용합니다.
    2. **유연성:** 구현체가 바뀌어도 비즈니스 로직 코드는 수정할 필요가 없습니다.
    3. **효율성:** 객체를 매번 `new` 하지 않고 하나를 돌려 쓰므로(싱글톤) 메모리를 아낍니다.
        

### **📊 한 눈에 비교하기**

|**구분**|**개발자가 직접 new**|**스프링 컨테이너 (Bean)**|
|---|---|---|
|**주체**|**개발자** (내 코드 안에서 결정)|**스프링** (외부에서 결정 후 주입)|
|**생성 시점**|코드가 실행되는 라인 지날 때|서버가 켜질 때 (Startup)|
|**메모리**|호출할 때마다 계속 생성 (낭비)|**싱글톤** (하나만 만들어 공유)|
|**트랜잭션**|적용 불가 ❌|**적용 가능 ✅ (@Transactional)**|
|**유지보수**|변경 시 코드 수정 필요 (불편)|설정만 변경하면 됨 (편안)|

---

### **📝 요약 및 결론**

1. **역할 분리:** Controller, Service, Repository로 나누면 유지보수와 협업이 쉬워진다.
2. **IoC/DI:** 객체 생성의 책임을 스프링에게 넘겨라(`new` 금지). 코드가 유연해진다.
3. **생성자 주입:** 빈을 주입받을 때는 무조건 **생성자 주입(`private final`)**을 사용해라.
4. **관리의 이점:** 스프링 빈으로 등록해야만 트랜잭션 등 스프링의 강력한 기능을 누릴 수 있다.
