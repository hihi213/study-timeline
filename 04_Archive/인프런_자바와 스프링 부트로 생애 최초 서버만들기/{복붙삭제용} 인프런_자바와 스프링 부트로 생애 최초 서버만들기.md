- **DML (Data Manipulation Language)**: **백엔드에서 직접 코드로 작성하는 SQL 문법들**
- →**DML은 백엔드가 다루는 SQL, 그걸 CRUD로 4가지를 나눠서 설명한다***
	- CRUD
		- Create : 생성(데이터를 넣는다)
			- create 범위에 들어가는 SQL문법
				- INSERT – 가장 일반적인 데이터 삽입
				- INSERT INTO ... SELECT – 다른 테이블에서 가져와 삽입
				- REPLACE INTO – 기존에 동일한 키가 있으면 삭제 후 삽입 (MySQL 전용)
				- MERGE – 조건에 따라 INSERT or UPDATE (Oracle, SQL Server 등)
		- Read : 읽기(데이터를 조회한다)
			- read 범위에 들어가는 SQL문법
			- SELECT – 기본 조회 문법
			- SELECT ... JOIN – 여러 테이블을 묶어 조회
			- SELECT ... WHERE, GROUP BY, ORDER BY 등 – 조건부 조회, 그룹핑, 정렬 등도 포함
			- EXISTS, IN, LIKE, BETWEEN – 조건절로 사용되어도 읽기 범주로 봄
		- Update: 업데이트(데이터를 수정한다)
			- update 범위에 들어가는 SQL문법
			- UPDATE – 기본적인 행 단위 수정
			- UPDATE ... JOIN – 여러 테이블 기준으로 수정 (MySQL 지원)
			- MERGE – 조건에 따라 INSERT or UPDATE (Oracle, SQL Server 등)
		- Delete: 제거(데이터를 삭제한다)
			- DELETE – 조건에 맞는 행 삭제
			- TRUNCATE – 테이블 전체 삭제 (DDL 성격도 있음, 롤백 불가)
			- MERGE – 조건에 따라 DELETE (일부 DBMS)
		- MERGE는 CREATE + UPDATE + DELETE의 복합 기능을 가진 특수 문법 (일부 DBMS에서만 지원)
		- TRUNCATE는 DELETE처럼 보이지만 DDL에 속함 (빠른 전체 삭제, 롤백 불가)
	- CRUD API작업하자
		- 어떤 대상에 대해 생성, 조회, 업데이트, 제거를 하는 api를 만든다.
	- 데이터 넣기
		- INSERT INTO 테이블이름 (필드이름1,필드이름2, ...)
			VALUES (값1, 값2, ...)
		- INSERT INTO, VALUES는 대문자가 아니어도 된다
		- 생성할때 id에 auto_increment설정을 해줬기 때문에 id는 따로 값을 넣어줄 필요가 없다.
	- 데이터 조회
		- select \* from 테이블이름
			- select 필드이름 from 테이블이름
			- select 필드이름1,필드이름2 from 테이블이름
		- select \* from 테이블이름 where 조건
			- 데이터를 조회할때 필터를 걸수있다.
			- 조건은 AND나 OR로 이어쓸수있다.
			- 조건
				- =, !=,<=, >=,<,>
				- between 첫번째범위 and 두번째범위
					- 첫번째 범위부터 두번째 범위까지(포함해서)
				- in ( value1, value2, ... )
					- 값이 이 목록안의 여러값 중 하나와 일치하니?
					- 걍 OR임
				- not in
					- 그 어떤 값과도 같지 않으면 TRUE
	- 데이터 수정
		- UPDATE 테이블이름
			SET 필드이름1=값1, 필드이름2= 값2, ...
			WHERE 조건
		- where 없이 조건을 쓰지않으면 모든 데이터가 업데이트 된다.
		- 이때 조건에 and, or 등을 사용할수있다.
	- 데이터 삭제
		- DELETE FROM 테이블이름
			WHERE 조건
		- where 없이 조건을 쓰지않으면 모든 데이터가 삭제된다.

			1. 클래스에 @Component, @Service, @Controller 등을 붙이면
			2. Spring이 **이 클래스를 Bean으로 등록**

			4. **Spring이 내부적으로 new + 생성자 호출을 자동으로 해줌**
			5. 이때 만들어진 객체만 **Spring이 관리할 수 있음**
	- ###### 3_5) SQL를 만들어 문자열변수로 만들고 jdbcTemplate로 조작한다
		- 유저생성API
			- 무슨 요청을 받고 무슨 응답을 할까?
			- 받을 요청
				- HTTP Method: POST
				- HTTP Path: /user
				- HTTPBODY:
					- {
					- "name": "홍길동",
					- "age": 25
					- }
			- 우리가 할 응답
				- 작성할 코드 x (HTTP 상태 200 OK면 충분)
				- 아무 값도 반환하지 않으면 HTTP 200 OK 응답 전송됨
			```Java
			#예시 유저 생성api
			String sql="INSERT INTO user(name, age) VALUES(?, ?)";  
			jdbcTemplate.update(sql,request.getName(),request.getAge());
			```
			- jdbcTemplate.update()의 update는 SQL의 업데이트 의미가 아니다, **update, delete, insert 쿼리마다 메서드 따로 만들면 복잡해지니까**, **Spring은 데이터를 변경한다는 목적 기준으로 추상화**해서 update()라는 통합된 이름을 사용한 것.
		- 조회 API
			- 무슨 요청을 받고 무슨 응답을 할까?
			- 받을 요청
				- HTTP Method ->GET
				- HTTP Path -> :/user
				- 쿼리 -> 없음(전체유저데이터를 줄것이기 때문)
			- 우리가 할 응답
				- 결과반환 ->
					\[{
						"id" : Long // id는 식별용 번호 추가하자!
						"name" : String
						"price" : int

					}...\]

				- 이때 우리가 코드로 유저객체List를 반환하기만 하면 spring이 자동으로 내부적으로 **Jackson**을 이용해 **자동으로 JSON 변환** 해주고, HTTP 응답을 작성해줌
				- 자세히 말하자면 **우리가 리턴한 Java 객체(List\<UserResponse>)를** **@RestController + @ResponseBody 조합**이 감지하고 **HTTP 응답을 생성해줘야겠다고 DispatcherServlet이 판단** -> 내부적으로 **HttpMessageConverter** 를 사용해서 **Jackson 라이브러리**를 통해 Java 객체 → JSON 문자열로 **변환** , 변환된 JSON을 **HTTP 응답 바디에 담음** ->HTTP 응답 전체를 완성해서 클라이언트에게 전송
				
			```Java
			#예시 메모리가 아닌, 데이터베이스에서 유저 목록을 가져오는 코드
			@GetMapping("/user")
			public List<UserResponse> getUsers() {
				String sql = "SELECT * FROM user";
								
			return jdbcTemplate.query(sql, new RowMapper<UserResponse>() {
				@Override
				public UserResponse mapRow(ResultSet rs, int rowNum) throws SQLException {
					return new UserResponse(
						rs.getLong("id"),//그 한줄에서long타입 변수를 가져오고 그 이름은 Id다
						rs.getString("name"),//
						rs.getInt("age")
					);
				}
			});
			}
				```
			- jdbcTemplate.qurely(sql, new **new RowMapper\<UserResponse>() {...}** );
			- JdbcTemplate.query()는 query()는 SQL을 DB에 전달해서,“이 조건에 맞는 데이터를 주세요!"라는 **질문(Query)** 을 날리는 메서드
				- query() 메서드를 사용해 sql 문장을 DB에 날린다
				- DB가 결과를 ResultSet 형태로 돌려준다
				- 두 번째 인자는 결과를 **어떤 객체로 변환할지**를 지정하는 RowMapper로 설정한다
				- query()메서드는 그걸 **List로 자동으로 모아서 반환**해줘요.
				- query()는 클라이언트에게 줄 데이터가 결과가 없을 수도 있고, 여러 건일 수도 있을 때 적합하고(전체 유저 조회,키워드 검색), queryForObject는 정확히 하나의 값만 나오는 쿼리에 사용한다 
				- queryForObjec은 RowMapper를  **하나의 행 전체를 자바 객체로 받고 싶을 때** 사용하고, 하나의 필드값만 가져올때는 사용 안한다.
				- 그니까 자바의 메서드의 반환타입은 한타입만 지정이 가능하고, 그래서 한 행같이 필드를 반환할때는 하나의 객체타입으로 반환해야하는데, 객체는 개발자 설계에 따라 (id,name만, id,name,age만, 모두다)이런식으로 다르게 정의되기 때문에 spring은 자동으로 객체로 만들어줄수없다. 그래서 우리가 변환방식을 정의하는 RowMapper가 필요하다
			- RowMapper는 DB 테이블의 한 줄(Row) 을 Java 객체로 바꾸는 도구이고, maprow()를 오버라이딩하기위한 인터페이스
				- ResultSet: DB 결과 전체를 담는 자바 객체
				- 이때 ctrl+o를 눌러 maprow() 오버라이딩을 해줘야해
				- maprow(): 안의 로직은 우리가 설정한 sql의 조건에 부합한 행이 있을때만 실행됨

| ------------------------ | ------------------------- | ------------- | ---------------------- |

- ## 2장 스스로 실습해서 배운것 정리
- 값이 null이 들어올수 있는거는 int가 아닌 객체 Integer를 사용한다
- 기본생성자: 객체만 ‘비어 있는 상태’로 생성→ 나중에 setter로 값을 채움
- 매걔변수있는 생성자:  **객체 생성 시점에 값을 한 번에 주입**
	- 불변객체를 만들때 이때 final필드와 매걔변수 있는 생성자를 만들어준다
	- 개발자가 new를 사용할때(이때 생성한 객체는 스프링이 관리하려면 추가적인 과정 필요)
- spring이 요청받을때, json->객체로 자동으로 변환할때, 즉 @RequestBody로 JSON을 받을 때는
	- 기본생성자+getter만있으면 된다
	- @RequestBody는 내부적으로 **Jackson**을 사용하는데 얘는 기본생성자 호출해 객체를 만든뒤 리플렉션을 이용해 private 필드에도 값을 **직접 주입**할 수 있어서 setter없어도 private 필드에 값넣는게 가능
- spring이 응답보낼때 객체->json으로 자동변환해주고 응답다 작성해서 보내서 우리는 객체만 리턴하면되는데 스프링이 자동변환 안해주는 예외
	- @RestController 있고, 불변객체에 getter 있음->자동변환
	- **Getter가 없거나 필드가 private인 경우**
	- 무한 순환 참조 있음
	- 반환 **컬렉션 내부에 null 값이 있거나 타입이 모호할 때**
	- Jackson 누락
	- 반환객체가 Socket, Thread, FileInputStream 같이 **직렬화 불가능한 객체**면 에러 발생
		- 그런 필드는 @JsonIgnore로 제외하거나 DTO로 분리
- jdbcTemplate.update()는 **INSERT, UPDATE, DELETE** 전용
	- SELECT 쿼리는 jdbcTemplate.query(), queryForObject() 등을 사용해야 함.
- 자바의 메서드의 반환타입은 한타입만 지정이 가능하고, 그래서 한 행같이 필드를 반환할때는 하나의 객체타입으로 반환해야하는데, 객체는 개발자 설계에 따라 (id,name만, id,name,age만, 모두다)이런식으로 다르게 정의되기 때문에 spring은 자동으로 객체로 만들어줄수없다. 그래서 우리가 변환방식을 정의하는 RowMapper가 필요하다 -> 그래서  **queryForObject()는** 한 행 반환할땐 rowmapper가 필요하고 하나의 값 반환할땐 rowmapper필요없다. query()는 여러행을 반환하니 필수

	@Repository

	@Primary

	제어의 역전(IoC)이란?

	원래 개발자가 직접 new를 호출해서 객체를 생성하던 제어권(Control) 을,

	스프링 프레임워크에게 넘김으로써

	필요한 객체를 자동으로 주입받는 구조로 바뀐 것입니다.

- #### 4. 스프링빈을 다루는 여러방법을 이해한다
	- 1. 스프링 빈을 등록하는 방법 : **@Configuration + @Bean 기반 등록 (수동 등록 방식)**
		- @Configuration
			- 클래스에 붙이는 어노테이션
			- @Bean을 사용할 때 함께 사용해 주어야 한다.
		- @Bean
			- 메소드에 붙이는 어노테이션
			- 메소드에서 **반환되는 객체를** 스프링빈에 등록한다.
		- 이 두가지를 같이 사용해 외부 라이브러리나 우리가 직접 어노테이션을 붙일 수 없는 클래스들을 **우회적으로 빈으로 등록**할 때 사용 (ex) jdbcTemplate)
	- 2. 스프링 빈을 등록하는 방법: **@Component 기반 등록 (자동 등록 방식)**
		- 주어진 클래스를 **스프링의 컴포넌트**로 간주한다.
		- 이 클래스들은 스프링 서버가 뜰 떄 자동으로 감지되고 스프링 빈으로 등록된다.
		- @Service, @Repository, @RestController 등은 내부에 @Component를 포함하고 있어 이 어노테이션들이 붙은 클래스도 스프링이 자동으로 감지해서 **빈으로 등록**된다.
	- 스프링빈을 주입받는 방법:
		- 생성자(가장 권장)
			- 원래 생성자 위에 @AutoWired라는 어노테이션을 붙여줬어야 했다
			- 생성자에 있는 매걔변수에 스프링 빈을 넣어달라는 의미
			- 자동으로 등록됨
		- Setter만들고 그 위에 @AutoWired를 붙이기
			- 누군가 Setter를 사용하면 다른인스턴스로 교차되기 때문에 오작동할 요지가 있다.
		- 필드에 직접 @AutoWired 붙이기
			- private JdbcTemplate jdbcTemplate; 위에 @AutoWired붙여준다
			- 테스트를 어렵게 만드는 요인이다.
	- @Qualifier("이름")
		- 정확하게 어떤 빈을 사용할지 이름으로 지정
		- 주입 지점마다 다른 빈을 지정 가능
	- 빈주입 우선순위
		- 1순위: 주입받는 쪽에 @Qualifier("이름")
		- 2순위: @Qualifier 없음, 등록된 빈 중 @Primary 존재
			-  @Primary는 **기본값**으로 사용할 빈을 정할 때임
- 알아야할것
	- 클래스 이름으로 메서드를 부르는 건 **static 메서드** 이다
		- **정적 메서드(static)** 는 객체 생성 없이 **클래스 이름으로 직접 호출**할 수 있어요.
		- **JVM은 객체가 없는 상태에서 바로 메서드를 실행**하려고 해요.
	- 아니 나는 생성자 **new UserRepository(…) 를 호출한 적이 없는데 왜 생성된 거지?**
		- 바로 @어노테이션을 붙였기 때문!
		- **Spring Boot가 시작될 때**, 어노테이션 붙은 클래스 스캔
		- Spring이 객체를 **Bean으로 생성해서 내부 컨테이너에 등록**
		- 필요하면 스프링이 자기 컨테이너에서 찾고, 자동으로 넣어줌
	- 그럼 Spring이 만들어준 객체를 우리가 쓰려면?
		- 1. 먼저 클래스 안에 우리가 사용할 객체를 담기 위한 **필드 선언**
			- private final UserRepository userRepository;
		- 2. 생성자도 수정: 생성자의 매개변수로 Bean을 받아와서, 위에서 선언한 필드에 저장합니다.
		- 이렇게 작성하면 Spring이 자동으로 생성한 Bean을 우리 코드에 주입해줘

- ### 1. 문자열 SQL을 직접 사용할때의 한계를 이해하고, 해결책인 JPA, Hibernate, Spring Data JPA가 무엇인지 이해한다
	- 한계:SQL를 문자열로 직접 작성하면..
		- 실수할수있고, 실수를 알아차리기 느리다
			- String sql="UPDATE user SET name=?;
			- 문자열 오타내도 서버는 정상 시작이 되고, 이 코드를 사용할때 되서야 에러가 난다. 즉 컴파일시점에 발견되지 않고, 런타임 시점에 발견된다
			- 오류는 런타임보다 컴파일시점에 발견하는게 용이하다.
		- 특정 데이터베이스에 종속적이게 된다.
			- mysql말고 다양한 데이터베이스가 있는데, 다른 DB로 갈아탈시에 문자열 코드 다 고쳐줘야한다.
		- 반복 작업이 많아지고 테이블을 하나만들때마다 CRUD쿼리가 항상 필요하다.
		- DB의 테이블과 객체는 패러다임이 다르다. 현재는 객체지향적 개발이기 때문에 패러다임이 다른 테이블의 직접적인 사용은 아쉽다.
			- 객체는
				- 단순한 데이터 저장소가 아니라, 책임과 행위를 함께 지닌 존재
				- 관계 또한 테이블의 외래키가 아닌, 객체 간 참조 관계로 표현
			- 테이블은
				- 단순히 속성의 나열이며, 행위(메서드) 에 대한 표현이 없습니다.
				- 테이블 간 관계는 코드 내부가 아닌, SQL의 JOIN 연산으로 외부적으로 구성
				- 객체의 상속을 표현하기가 힘들다.
	- JPA(Java Persistence영속성 API) :규칙이다. 규칙이 라는건 규칙일뿐이고 누군가는 이거를 코드로 구현해야한다 즉 JPA는 인터페이스라고 생각하자.
		- 객체와 RDB의 테이블을 짝지어 데이터를 영구적으로 DB에 보관하기위해 Java 진영에서 정해진 규칙
		- Java진영의 ORM이라고도 한다
			- ORM(Object-Relational Mapping)
				- Object: 객체
				- Relational: 관계형DB의 Table를 의미
				- Mapping: 객체의 정보와 테이블의 정보 둘을 짝짓는다.
		- 영속성: 서버가 재시작되어도 데이터는 영구적으로 저장된다.
			- 서버를 종료하면 Ram에 있는 정보는 사라진다
			- 우리가 데이터베이스를 사용한것은 유저데이터에 영속성을 우리가 부여한것이다
	- Hibernate: JPA구현한 코드
		- 내부적으로 JDBC를 사용한다.

			- id임을 알려주는 java.x.persistence경로의 @id를 붙여준다
			- 테이블의 id에는 autoincrement 속성은  @GeneratedValue를 붙여준다

				```java
				private Long id;		
				```
				-  **JPA의 @GeneratedValue 전략은 사용하는 DB 종류에 따라 방식이 다르며,** **MySQL은 IDENTITY, Oracle은 SEQUENCE, 모든 DB에서 쓸 수 있는 건 TABLE이다.**

				- 필드명과 컬럼명이 다를때 이름(name)지정

				- length 문자열의경우 255
				- VARCHAR(255) 이런식으로 자동 설정됨
		- 1-5. application.yml 수정하기
			```yml
				spring:
				  jpa:
					hibernate:
					  ddl-auto: none
					show-sql: true
					properties:
					  hibernate:
						format_sql: true
			```

			- ddl-auto는 Hibernate가 DB 테이블을 어떻게 생성/갱신할지를 설정하는 옵션

				- 이는 변경 감지 (Dirty Checking)라고한다
				- > @Transactional 안에서 기존 엔티티를 조회해 수정만 했다면,  save() 없이도 트랜잭션이 끝나는 시점에 변경된 내용을 자동으로 감지해서 UPDATE SQL을 날림. 다만, 신규 저장이거나 트랜잭션이 없다면 save()가 필요하다.
		- 스프링은 JpaRepository<Entity, ID>를 구현받는 Repository에 대해 자동으로 SimpleJpaRepository 기능을 사용할 수 있게도 해준다.
		- SimpleJpaRepository 코드를 열어보면, 조금 복잡한 코드들을 확인할 수 있는데, 이게 바로JPA 코드이다. Spring Data JPA 를 사용하는 덕분에 복잡한 JPA 코드를 직접 사용하는 게 아니라 기능로써 사용할 수 있게 되는 것이다.
		- Spring Data JPA를 직접사용하지만 사실은 Spring Data JPA 안의 JPA 구현체인 Hibernate의 JDBC를 쓰고 있다 
	- 새로알게 된것 자바에서 자주 보이는 Optional\<T>
		-  null 때문에 생기는 **에러나 혼란을 줄이기 위한 안전한 “포장지”** 같은 클래스
		- 1. 옵셔널 객체만들기
			- Optional\<객체 타입> name = Optional.of("승현");
		- **2. 값이 있는지 확인하고 꺼내기**
			- isPresent() 값이 있으면 true, 없으면 false
			- ifPresent(람다) 값이 있으면 실행
			- orElse(기본값) 값이 없을 때 기본값 반환
			- orElseThrow() 값이 없으면 예외 발생
			- get() 안에 있는 값 꺼내기 (값이 없으면 예외 발생) ← 주의! 가급적 쓰지 말기 (옵셔널의 의미가 없는 메서드)
		-  **findById(id)**하면 이런 옵셔널 타입으로 반환되니 위의 메서드가 쓰인것.
