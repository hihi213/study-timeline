- ## 4장 JPA 사용하기
- ### 1. 문자열 SQL을 직접 사용할때의 한계를 이해하고, 해결책인 JPA, Hibernate, Spring Data JPA가 무엇인지 이해한다
	- 한계:SQL를 문자열로 직접 작성하면..
		- 실수할수있고, 실수를 알아차리기 느리다
			- String sql="UPDATE user SET name=?;
			- 문자열 오타내도 서버는 정상 시작이 되고, 이 코드를 사용할때 되서야 에러가 난다. 즉 컴파일시점에 발견되지 않고, 런타임 시점에 발견된다
			- 오류는 런타임보다 컴파일시점에 발견하는게 용이하다.
		- 특정 데이터베이스에 종속적이게 된다.
			- mysql말고 다양한 데이터베이스가 있는데, 다른 DB로 갈아탈시에 문자열 코드 다 고쳐줘야한다.
		- 반복 작업이 많아지고 테이블을 하나만들때마다 CRUD쿼리가 항상 필요하다.
		- DB의 테이블과 객체는 패러다임이 다르다. 현재는 객체지향적 개발이기 때문에 패러다임이 다른 테이블의 직접적인 사용은 아쉽다.
			- 객체는
				- 단순한 데이터 저장소가 아니라, 책임과 행위를 함께 지닌 존재
				- 관계 또한 테이블의 외래키가 아닌, 객체 간 참조 관계로 표현
			- 테이블은
				- 단순히 속성의 나열이며, 행위(메서드) 에 대한 표현이 없습니다.
				- 테이블 간 관계는 코드 내부가 아닌, SQL의 JOIN 연산으로 외부적으로 구성
				- 객체의 상속을 표현하기가 힘들다.
	- JPA(Java Persistence영속성 API) :규칙이다. 규칙이 라는건 규칙일뿐이고 누군가는 이거를 코드로 구현해야한다 즉 JPA는 인터페이스라고 생각하자.
		- 객체와 RDB의 테이블을 짝지어 데이터를 영구적으로 DB에 보관하기위해 Java 진영에서 정해진 규칙
		- Java진영의 ORM이라고도 한다
			- ORM(Object-Relational Mapping)
				- Object: 객체
				- Relational: 관계형DB의 Table를 의미
				- Mapping: 객체의 정보와 테이블의 정보 둘을 짝짓는다.
		- 영속성: 서버가 재시작되어도 데이터는 영구적으로 저장된다.
			- 서버를 종료하면 Ram에 있는 정보는 사라진다
			- 우리가 데이터베이스를 사용한것은 유저데이터에 영속성을 우리가 부여한것이다
	- Hibernate: JPA구현한 코드
		- 내부적으로 JDBC를 사용한다.
- ### 2. Spring Data JPA를 이용해 데이터를 조회, 수정, 삭제 할 수 있다.
	- Spring Data JPA
		- Spring에서 JPA와 Hibernate를 더 쉽게 쓸 수 있게 만든 도구
		- @Repository 인터페이스만 만들어도 자동으로 SQL 실행됨
		- 메서드 이름만으로 쿼리 실행 가능
	- 1. 테이블과 유저객체를 Spring Data JPA를 이용해 매핑하자.
		- 1-1. 클래스 매핑: 클래스 위에 @Entity를 붙인다
			- 클래스 이름이 기본적으로 테이블 이름이 됨 (@Table로 수정 가능)
			- 클래스는 **DB의 테이블 1개에 대응**
			- @Entity: 이 클래스가 DB 테이블과 매핑된다는 것을 명시해 JPA가 이 객체를 관리할 수 있도록 설정
				- 엔티티: DB에서 저장되고 관리되어야할 데이터를 의미한다
		- 1-2. PK(기본키) 매핑:-> 테이블의 기본 키를 Java 객체 필드와 연결
			- id임을 알려주는 java.x.persistence경로의 @id를 붙여준다
			- 테이블의 id에는 autoincrement 속성은  @GeneratedValue를 붙여준다
				```java
				@Id
				@GeneratedValue(strategy = GenerationType.IDENTITY)//db따라 코드가 달라짐
				private Long id;		
				```
				-  **JPA의 @GeneratedValue 전략은 사용하는 DB 종류에 따라 방식이 다르며,** **MySQL은 IDENTITY, Oracle은 SEQUENCE, 모든 DB에서 쓸 수 있는 건 TABLE이다.**
		- 1-3. 엔티티객체(JPA객체)에는 매걔변수가 하나도 없는 기본생성자가 있어야 하니 꼭 만들어주기
			- protected 타입으로 기본생성자 만들어도 ㄱㅊ
		- 1-4. 나머지 필드에 @Column붙여주기→ 테이블의 컬럼으로 매핑
			- 필드명과 컬럼명이 다르면 @Column(name = "...")
				- null들어갈수있는지(nullable) 여부, 길이제한(length) 를 주로 사용
				- 필드명과 컬럼명이 다를때 이름(name)지정
			- 사실 @Column은 생략할 수 있다.
				- nullable = true
				- length 문자열의경우 255
				- VARCHAR(255) 이런식으로 자동 설정됨
		- 1-5. application.yml 수정하기
			```yml
				spring:
				  jpa:
					hibernate:
					  ddl-auto: none
					show-sql: true
					properties:
					  hibernate:
						format_sql: true
						dialect: org.hibernate.dialect.MySQL8Dialect
			```
			-  Spring Boot에서 spring-boot-starter-data-jpa를 쓰면, 내부적으로 JPA를 실제로 구현한 구현체인 Hibernate가 작동 그래서 설정 파일에 hibernate.xxx 설정을 넣는 것
			- ddl-auto는 Hibernate가 DB 테이블을 어떻게 생성/갱신할지를 설정하는 옵션
				- none 아무 것도 하지 않음 (수동으로 테이블 준비)
				- create 실행 시 테이블 새로 생성 (기존 테이블 삭제)
				- create-drop 실행 시 생성 → 종료 시 삭제
				- update 테이블이 없으면 추가함 (기존 데이터 유지)
				- validate 테이블 구조 검증만 하고 생성은 안 함
			- show_sql = true
				Hibernate가 실행하는 SQL문을 콘솔에 출력하게 합니다.
			- format_sql = true
				콘솔에 출력되는 SQL을 가독성 있게 정렬해서 보여줍니다. (줄바꿈, 들여쓰기 등)
			- dialect = org.hibernate.dialect.MySQL8Dialect
				- dialect: 방언, DB따라 다른 문법
				어떤 DB를 사용하는지 Hibernate에 알려주는 설정입니다.
				MySQL8Dialect: MySQL 8 버전용 SQL 문법을 사용할 수 있도록 알려줌.
				Oracle12cDialect:  Oracle DB라면이걸 쓰기
	- 2. Sql를 작성하지 않고 Spring Data JPA를 이용해 자동으로 쿼리 날리기
		- 2_1 : User 도메인 객체와 같은 위치에 UserRepository라는 인터페이스를 만들어 주자
		- 2_2 : 그 인터페이스가 JpaRepository<Entity, ID>라는 인터페이스를 상속하게해 CRUD 기능을 자동으로 사용한다.
			- extends JpaRepository: Spring Data JPA가 제공하는 CRUD 자동 처리용 인터페이스
			- Entity: DB와 매핑된 Entity 클래스
				- ex) User

			- 우리가 만든 인터페이스이름.**save(new 객체)**

						- ResultSet → UserResponse 객체를 직접 매핑해야 했음 즉, DB에서 값을 꺼내면서 일일이 가공해서 집어넣는 작업 필요

						- 먼저 DB에서 User 엔티티 객체들을 가져오고
						- 그걸 stream으로 DTO(UserResponse) 로 변환만 해주면 끝
					- 즉 컬럼 추가/삭제 시 **모든 SQL과 RowMapper 수정** 필요했는데, JPA 방식은 결과를 받아오는 필드를 따로 작성하지 않아서(매핑), **엔티티 클래스만 수정하면 자동으로 쿼리와 매핑이 반영**되어 **유지보수가 훨씬 간단하고 안정적**입니다.
			- Optional\<객체> user =우리가 만든 인터페이스이름.**findById(id)**
				- Optional로 반환되므로 null 처리 걱정 줄어듦
			-  인터페이스이름.**deleteName(name)** 하면 지워짐
		- spring Data JPA 사용자 정의 메서드
			- 이름을 기준으로 조회하는건 없어서 우리가 인터페이스에 들어가 findByName를 선언해준다
				- findByName- **메서드 이름 규칙만 맞추면 자동으로 SQL 생성됨**
			- 형식 구절1 by 구절2
				- 암기할필요x
			- by앞
				- find: 1건의 객체, Optional<타입>을 반봔
				- findAll : List<타입> 반환 (n건의 결과물)
				- exists : 존재여부를 boolean으로 반환
				- count: sql의 결과개수를 쓴다 반환타입은 long이다
			- by뒤
				- 각구절은 and나 or로 조합할수있다.
				- GreaterThan: 초과
				- GreaterThanEqual: 이상
				- LessThan: 미만
				- LessthanEqual: 이하
				- Between: 사이에
				- StartsWith: ~로 시작하는
				- EndsWith: ~로 끝나는
		- jpa를 활용하면 업데이트 sql를 직접 날리는게 아니라 유저의 객체를 가져와서 업데이트하게됨
			- 이때 User에 getName의 역할을하는 updateName이라는 메소드를 만들어서 가져온객체의 이름을 변경하고
			- 인터페이스이름.save(가져온객체)
				- 이는 변경 감지 (Dirty Checking)라고한다
				- > @Transactional 안에서 기존 엔티티를 조회해 수정만 했다면,  save() 없이도 트랜잭션이 끝나는 시점에 변경된 내용을 자동으로 감지해서 UPDATE SQL을 날림. 다만, 신규 저장이거나 트랜잭션이 없다면 save()가 필요하다.
		- 스프링은 JpaRepository<Entity, ID>를 구현받는 Repository에 대해 자동으로 SimpleJpaRepository 기능을 사용할 수 있게도 해준다.
		- SimpleJpaRepository 코드를 열어보면, 조금 복잡한 코드들을 확인할 수 있는데, 이게 바로JPA 코드이다. Spring Data JPA 를 사용하는 덕분에 복잡한 JPA 코드를 직접 사용하는 게 아니라 기능로써 사용할 수 있게 되는 것이다.
		- Spring Data JPA를 직접사용하지만 사실은 Spring Data JPA 안의 JPA 구현체인 Hibernate의 JDBC를 쓰고 있다 
	- 새로알게 된것 자바에서 자주 보이는 Optional\<T>
		-  null 때문에 생기는 **에러나 혼란을 줄이기 위한 안전한 “포장지”** 같은 클래스
		- 1. 옵셔널 객체만들기
			- Optional\<객체 타입> name = Optional.of("승현");
		- **2. 값이 있는지 확인하고 꺼내기**
			- isPresent() 값이 있으면 true, 없으면 false
			- ifPresent(람다) 값이 있으면 실행
			- orElse(기본값) 값이 없을 때 기본값 반환
			- orElseThrow() 값이 없으면 예외 발생
			- get() 안에 있는 값 꺼내기 (값이 없으면 예외 발생) ← 주의! 가급적 쓰지 말기 (옵셔널의 의미가 없는 메서드)
		-  **findById(id)**하면 이런 옵셔널 타입으로 반환되니 위의 메서드가 쓰인것.
