| :--- | :--- |

CPU의 덧셈 연산이 예를 들어 '3 클럭'을 필요로 한다면, 4GHz CPU는 이 덧셈을 `3 / (4 * 10^9)`초, 즉 0.75 나노초(nanosecond) 만에 끝낼 수 있습니다. 즉, **클럭 속도**는 하나의 연산을 얼마나 잘게 쪼개서 빠르게 처리하는지를 나타내는 지표입니다. 단, 실제 성능은 한 클럭당 몇 개의 명령어를 처리하는지(IPC)와 코어 개수 등 다른 요소에도 영향을 받습니다. \<br\> **출처**: `transcript` |

| **꼬리 질문** | CPU와 RAM의 클럭 속도가 다른데, 이 속도 차이로 발생하는 병목 현상을 해결하기 위해 컴퓨터에는 어떤 장치가 존재하는가? (캐시 메모리) |

### 2교시 핵심 개념 요약

#### **1. 오늘 배운 내용 한 줄 요약**
2교시는 **배열**과 **연결 리스트**의 메모리 구조 및 성능 차이를 CPU 레지스터, 동적 할당과 연관 지어 설명하고, 이를 기반으로 **스택(LIFO)**의 인터럽트 처리 방식과 **큐(FIFO)**의 구현상 장단점을 심층적으로 분석합니다. [P02, P05, P07]

---

#### **2. TL;DR (Too Long; Didn't Read)**
* **배열**: 메모리 공간이 **연속적**이고 **정적**입니다. 인덱스를 통한 접근(`O(1)`)은 빠르지만, 사용하지 않는 공간은 그대로 낭비됩니다. [P02]
* **연결 리스트**: 메모리 공간이 **비연속적**이고 **동적**입니다. `malloc()`으로 필요할 때마다 할당하여 메모리 효율이 좋지만, 특정 원소에 접근하려면 처음부터 순차 탐색(`O(n)`)해야 합니다. [P02]
* **하드웨어와 자료구조**: 배열의 빠른 인덱싱은 CPU의 `베이스 레지스터`와 `인덱스 레지스터`가 직접 주소를 계산하기 때문에 가능합니다. [P03]
* **시스템 스택의 역할**: 프로그램 실행 중 인터럽트가 발생하면, 돌아와야 할 위치 주소(`PC` 값)를 **스택**에 저장했다가 복귀함으로써 프로그램 흐름이 유지됩니다. [P05]
* **큐의 구현**: **큐**를 배열로 구현하면 `dequeue` 시 원소들을 앞으로 이동시키는 비용이 크지만, 연결 리스트로 구현하면 포인터 조작만으로 효율적인 삽입/삭제가 가능합니다. [P07]
* **추상과 현실**: `트리`, `그래프` 같은 복잡한 자료구조도 실제 컴퓨터 내부에서는 결국 기본적인 `배열`이나 `연결 리스트`로 구현됩니다. [P08]
* **연결 리스트의 진화**: 단방향 탐색만 가능한 단일 연결 리스트의 단점을 보완하기 위해, 이전 노드 포인터를 추가한 **이중 연결 리스트**가 사용됩니다. [P10]
* **우선순위의 개념**: **힙(Heap)**은 일반적인 큐(FIFO)와 달리, '우선순위'가 높은 데이터가 먼저 처리되어야 하는 상황(예: 응급 차량)을 구현하는 데 사용됩니다. [P11]
* **알고리즘의 효율성**: 프로그램이 언젠가 정확한 답을 내놓는다고 해도, 제한된 시간과 자원 내에서 결과를 내지 못하면 '비효율적인' 알고리즘입니다. [P12]

#### **5. 실수 및 함정 (Pitfalls)**
1.  **"배열의 빈 공간은 유휴 자원이다"**: 배열 선언 시 할당된 메모리는 전부 사용하지 않더라도 해당 프로그램이 독점하므로, 이는 메모리 낭비(누수)이지 유휴 자원이 아니다. [P02]
2.  **"`register`는 강제 명령이다"**: `C` 언어의 `register` 키워드는 컴파일러에게 레지스터 할당을 '권장'하는 것일 뿐, 레지스터에 공간이 없으면 일반 메모리에 할당된다. [P04]
3.  **"레지스터 변수는 주소가 있다"**: 레지스터는 CPU 내부의 고속 저장 공간으로, 메모리 주소(address)가 아닌 번호(name)로 관리된다. 따라서 `&` 연산자로 주소를 가져올 수 없다. [P04]
4.  **"배열 큐에서 삭제는 인덱스 이동이면 충분하다"**: `dequeue` 후 front 인덱스만 증가시키면, 배열 앞부분이 비어있음에도 배열 끝에 도달 시 큐가 가득 찼다고 오판하게 된다. (원형 큐 설계가 필요한 이유) [P07]
5.  **"단일 연결 리스트는 만능이다"**: 단일 연결 리스트는 특정 노드에서 이전 노드로 돌아갈 방법이 없다. 양방향 탐색이 필요하다면 반드시 이중 연결 리스트를 사용해야 한다. [P10]
6.  **"정확하면 효율적인 알고리즘이다"**: 알고리즘의 최우선 조건은 정확성이지만, 현실적인 시간 제약 내에 답을 내지 못하면 비효율적인 알고리즘으로 간주된다. [P12]

2교시 강의에서는 명시적인 실습 과제가 주어지지 않았습니다. 하지만 강의의 핵심 주제였던 '배열과 연결 리스트를 이용한 자료구조 구현'의 장단점을 직접 체험할 수 있는 실습 계획을 다음과 같이 제안합니다.

### **실습: 큐(Queue) 구현 방식에 따른 성능 비교**

#### **개요**

2교시 강의에서는 \*\*큐(Queue)\*\*를 배열로 구현할 때와 연결 리스트로 구현할 때의 효율성 차이를 집중적으로 다루었습니다. [P07] 이번 실습은 큐 ADT(추상 자료형)를 두 가지 방식, 즉 (1) **데이터 이동이 필요한 배열**과 (2) **단일 연결 리스트**로 직접 구현하는 것을 목표로 합니다. 그 후, `enqueue` 및 `dequeue` 연산을 대량으로 수행하여 실행 시간을 측정하고, 이론으로만 배웠던 성능 차이를 실제 데이터로 증명합니다.

#### **환경 및 전제 조건**

  * **사용 언어**: `C`, `Java`, `Python` 등 (포인터와 동적 메모리 할당을 직접 다룰 수 있는 `C` 언어를 권장합니다.)
  * **구현 함수**: `void enqueue(int data)`, `int dequeue()`, `bool isEmpty()`
  * **제약 조건**: 언어에서 기본으로 제공하는 `Queue`, `LinkedList` 등의 내장 라이브러리/클래스 사용을 금지하고, 모든 로직을 직접 구현해야 합니다.

#### **실습 단계**

| 단계 | 목적 | 절차 (의사코드/핵심 로직) | 예상 결과 | 검증 포인트 | 실패 시 롤백 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 배열 기반 큐 구현** | `dequeue`의 비효율(`O(n)`) 직접 구현 및 확인 | `int queue_array[MAX_SIZE];` \<br\> `int front, rear;` \<br\> `// dequeue 로직` \<br\> `data = queue_array[front];` \<br\> `for i from front to rear-1:` \<br\> `   queue_array[i] = queue_array[i+1]; ` \<br\> `rear--;` | 원소 삭제 시 모든 데이터를 앞으로 이동시키는 `ArrayQueue` 완성 | 큐가 비어있거나 가득 찼을 때의 예외 처리가 정상 동작하는지 확인 | `dequeue` 후 원소를 이동시키는 반복문의 인덱스 범위(`i`와 `i+1`)가 올바른지 디버깅 |
| **2. 연결 리스트 기반 큐 구현** | `dequeue`의 효율성(`O(1)`) 직접 구현 및 확인 | `Node { int data; Node* next; }` \<br\> `Node *front, *rear;` \<br\> `// dequeue 로직` \<br\> `temp = front;` \<br\> `data = temp->data;` \<br\> `front = front->next;` \<br\> `free(temp);` | 포인터 조작만으로 원소를 삭제하는 `LinkedQueue` 완성 | 큐가 비어있을 때(`front == NULL`) `dequeue`를 시도하면 오류 없이 처리되는지 확인 | `front`와 `rear` 포인터가 `NULL`이 되는 조건, 메모리 해제(`free`) 로직 점검 |
| **3. 성능 측정** | 두 구현 방식의 `dequeue` 연산 속도를 정량적으로 비교 | `// N = 10000;` \<br\> `start_time = clock();` \<br\> `for i from 0 to N-1: dequeue();` \<br\> `end_time = clock();` \<br\> `elapsed = end_time - start_time;` \<br\> `// ArrayQueue와 LinkedQueue에 대해 각각 측정` | 대량의 `dequeue` 연산에 대한 각 구현체의 실행 시간 | 데이터 개수(N)를 늘렸을 때, `ArrayQueue`의 실행 시간이 급격히 증가하는지 확인 | 타이머 함수의 정확도 확인 및 N의 크기를 충분히 크게(e.g., 50,000 이상) 설정 |
| **4. 결과 분석** | 측정된 데이터를 바탕으로 이론적 복잡도를 실제 성능과 연결 | N의 크기에 따른 실행 시간 변화를 표와 그래프로 정리한다. | `ArrayQueue`의 `dequeue` 시간은 `O(N^2)`, `LinkedQueue`는 `O(N)`임을 보여주는 명확한 성능 차이 그래프. | 측정한 시간이 이론적 복잡도(선형 증가 vs. 이차 함수 증가)와 일치하는 경향을 보이는지 분석 | 구현 코드에 로직 오류가 없는지, 시간 측정이 올바른 구간에서 이루어지는지 재검토 |

#### **체크리스트**

  - [ ] `dequeue` 시 원소를 이동시키는 배열 기반 큐 구현 완료
  - [ ] 포인터를 사용하는 연결 리스트 기반 큐 구현 완료
  - [ ] 두 가지 큐의 `dequeue` 연산 시간을 측정하고 비교하는 테스트 프로그램 작성 완료
  - [ ] 데이터 개수(N)를 1,000개, 10,000개, 50,000개로 변경하며 실행 시간 기록 완료
  - [ ] 측정 결과를 바탕으로 "왜 연결 리스트 기반 큐의 `dequeue`가 더 효율적인가?"에 대한 분석 완료

#### **흔한 오류 및 해결 방안**

| 오류 유형 | 예상 원인 | 해결 방안 |
| :--- | :--- | :--- |
| **연결 리스트 큐**에서 마지막 원소 `dequeue` 후 오류 발생 | 큐가 비게 되었을 때(`front`가 `NULL`이 될 때), `rear` 포인터를 `NULL`로 함께 변경해주지 않아 쓰레기 값을 가리키게 됨. | `front`가 `NULL`이 되면, `rear`도 `NULL`로 설정하는 로직을 추가. |
| **배열 큐**의 성능이 예상보다 좋게 나옴 | `dequeue` 시 원소 이동(`shift`) 로직을 구현하지 않고, `front` 인덱스만 1 증가시켰음. (이는 원형 큐의 방식) | 강의에서 설명한 문제 상황을 재현하기 위해, 의도적으로 데이터를 한 칸씩 이동시키는 로직을 반드시 구현. |
| **메모리 누수 (Memory Leak)** | `LinkedQueue`의 `dequeue` 시, 제거되는 노드를 `free()` 함수로 메모리에서 해제하지 않음. | `front` 포인터를 다음 노드로 옮기기 전, 현재 `front` 노드의 주소를 임시 변수에 저장했다가 `free()`를 호출. |

| **오해 포인트** | 1. `arr`과 `ptr`은 모든 면에서 동일하게 동작한다. |
| **꼬리 질문** | `sizeof(arr)`와 `sizeof(ptr)`를 각각 출력하면 어떤 값이 나오며, 왜 다른가? |

### **[2] 핵심 개념 요약**

-----

#### **1. 오늘 배운 내용 한 줄 요약**

3교시는 **포인터**의 본질(`주소 값 저장`)과 특징(`고정 크기`, `타입`), 그리고 이를 활용한 **자기 참조 구조체**(연결 리스트 구현), **포인터 연산**, **배열 이름과의 차이점** 등 `C` 언어의 핵심이자 가장 혼란스러운 포인터 개념을 총정리합니다. [P01, P06, P08, P09]

-----

#### **2. TL;DR (Too Long; Didn't Read)**

  * **포인터의 정의**: 포인터 변수의 유일한 임무는 다른 변수의 **메모리 시작 주소**를 저장하는 것입니다. [P01]
  * **포인터의 타입**: `int*`, `float*` 등 포인터의 타입은 '저장된 주소로 찾아갔을 때 그곳의 데이터를 어떤 방식으로 해석할 것인지'를 컴파일러에게 알려줍니다. [P03]
  * **포인터의 크기**: 포인터가 무엇을 가리키든 포인터 변수 자체의 크기는 시스템의 주소 체계(예: 32비트는 4바이트, 64비트는 8바이트)에 따라 고정됩니다. [P04, P05]
  * **자기 참조 구조체**: `struct Node { ... struct Node* next; }` 처럼 구조체 내부에 자기 타입의 포인터를 두어 **연결 리스트**나 **트리** 같은 동적 자료구조를 만듭니다. [P06]
  * **포인터 연산**: `ptr++`는 주소를 1바이트가 아닌, `ptr`이 가리키는 **자료형의 크기만큼** 증가시킵니다. (`int*`는 4바이트, `double*`은 8바이트) [P10]
  * **배열 이름 = 상수 포인터**: 배열의 이름은 그 자체로 배열의 시작 주소를 가리키는 **상수**이므로, `arr++` 처럼 그 값을 변경하려는 시도는 컴파일 오류를 유발합니다. [P09]
  * **`void*` 포인터**: `malloc`이 반환하는 것처럼, 특정 타입에 얽매이지 않는 범용 주소 저장소 역할을 합니다. 사용 시에는 원하는 타입으로 반드시 **명시적 형 변환**을 해야 합니다. [P12]

#### **3. 심화 개념: 포인터 핵심 비교**

##### **일반 변수 vs. 포인터 변수**

| 구분 | **일반 변수 (`int a`)** | **포인터 변수 (`int* p`)** | 근거 |
| :--- | :--- | :--- | :--- |
| **저장 대상** | 데이터 값 (e.g., `10`) | 메모리 주소 값 (e.g., `0x7ffee...`) | [P01] |
| **선언 의미** | 정수 값을 저장할 공간을 할당 | 정수 값의 주소를 저장할 공간을 할당 | [P01] |
| **`sizeof` 결과** | 자료형의 크기 (e.g., `4`) | 주소의 크기 (e.g., `4` or `8`) | [P05] |

##### **배열 이름 (`arr`) vs. 포인터 변수 (`ptr`)**

| 구분 | **배열 이름 (`arr`)** | **포인터 변수 (`ptr`)** | 근거 |
| :--- | :--- | :--- | :--- |
| **특성** | **상수 (Constant)**, 값 변경 불가 | **변수 (Variable)**, 값 변경 가능 | [P09] |
| **`++` 연산** | `arr++` → **컴파일 에러** | `ptr++` → **가능** (다음 원소 주소로 이동) | [P09] |
| **`sizeof` 결과** | 배열 전체의 크기 (`sizeof(type) * length`) | 포인터 변수 자체의 크기 (`4` or `8`) | [P09] |

##### **포인터 연산자 우선순위**

| 표현식 | 해석 (우선순위: `++`(후위) \> `*`) | 의미 | 근거 |
| :--- | :--- | :--- | :--- |
| `*ptr++` | `*(ptr++)` | `ptr`이 가리키는 값을 먼저 반환하고, 그 후에 `ptr` 주소를 1 증가 | [P08] |
| `(*ptr)++` | `(*ptr)++` | `ptr`이 가리키는 곳의 '값'을 1 증가 (주소는 불변) | [P08] |

#### **실습: 자기 참조 구조체를 이용한 단일 연결 리스트(Singly Linked List) 구현**

#### **개요**

3교시 강의에서 학습한 **자기 참조 구조체**와 **포인터** 개념을 종합적으로 활용하여, 가장 기본적인 동적 자료구조인 단일 연결 리스트의 핵심 기능(삽입, 삭제, 출력)을 `C` 언어로 직접 구현합니다. [P06] 이를 통해 동적 메모리 할당(`malloc`, `free`)과 포인터 조작에 대한 실질적인 이해를 높이는 것을 목표로 합니다.

#### **실습 단계**

| 단계                    | 목적                                | 절차 (의사코드/핵심 로직)                                                                                                                                                                                                                                                              | 예상 결과                             | 검증 포인트                                        | 실패 시 롤백                                                 |
| :-------------------- | :-------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------- | :-------------------------------------------- | :------------------------------------------------------ |
| **1. 노드 구조체 정의**      | 연결 리스트의 기본 단위인 자기 참조 구조체 설계       | `typedef struct Node {` \<br\> `   int data; ` \<br\> `   struct Node* next; ` \<br\> `} Node;`                                                                                                                                                                              | `Node` 타입 정의 완료                   | `next` 멤버가 자기 자신 타입의 포인터로 선언되었는지 확인           | 구조체 선언 문법 오류 점검                                         |
| **2. 노드 생성**          | 동적 메모리 할당을 통해 새로운 노드를 만드는 기능 구현   | `Node* create_node(int data) {` \<br\> `   Node* new_node = (Node*)malloc(sizeof(Node)); ` \<br\> `   new_node->data = data; ` \<br\> `   new_node->next = NULL; ` \<br\> `   return new_node; ` \<br\> `}`                                                                  | 데이터가 채워진 새 노드의 주소를 반환하는 함수        | `malloc` 후 `NULL` 체크, 멤버 변수 초기화 확인            | `malloc` 사이즈, 타입 캐스팅, `->` 연산자 사용법 확인                   |
| **3. 리스트 맨 뒤에 노드 추가** | 리스트를 순회하며 마지막에 새 노드를 연결           | `void append(Node** head, int data) {` \<br\> `   if (*head == NULL) *head = new_node; ` \<br\> `   else { ` \<br\> `     Node* curr = *head; ` \<br\> `     while (curr->next != NULL) curr = curr->next; ` \<br\> `     curr->next = new_node; ` \<br\> `   } ` \<br\> `}` | 리스트의 끝에 새로운 노드가 성공적으로 추가됨         | 빈 리스트에 추가할 때와 기존 리스트에 추가할 때 모두 정상 동작하는지 확인    | `while` 루프의 종료 조건, 이중 포인터(`head`)의 사용법 이해               |
| **4. 특정 노드 삭제**       | 특정 값을 가진 노드를 찾아 리스트에서 제거하고 메모리 해제 | 이전 노드(`prev`)의 `next` 포인터를 삭제할 노드의 `next`로 변경: `prev->next = target->next;` \<br\> 그 후, 대상 노드를 `free(target);`                                                                                                                                                               | 지정된 값을 가진 노드가 리스트에서 사라지고 메모리가 해제됨 | 첫 노드 삭제, 중간 노드 삭제, 마지막 노드 삭제 시 모두 정상 동작하는지 확인 | 삭제할 노드를 찾기 위한 순회 로직, 포인터 연결 변경 순서, `free()` 호출 누락 여부 점검 |
| **5. 리스트 메모리 전체 해제**  | 프로그램 종료 시 모든 노드의 메모리 누수를 방지       | `while (head != NULL)` 루프를 돌며, `head`를 다음 노드로 옮기기 전에 현재 노드를 `free()`                                                                                                                                                                                                         | 모든 노드가 `free`되어 메모리 누수가 발생하지 않음   | `Valgrind`와 같은 메모리 디버깅 툴로 누수 여부 확인            | 노드를 `free`하기 전에 다음 노드의 주소를 미리 저장해두었는지 확인 (댕글링 포인터 방지)   |
