훌륭합니다. 지금 제시하신 **“AI가 이해 → 내가 승인 → AI가 큰 단계 제시 → 1단계 세분화 → 개념 최소 설명 → 주석 포함 파일 제안/생성 → 내가 구현 → AI는 코드 없이 리뷰(요청 시에만 코드 생성)”** 흐름은, 우리 프로젝트의 **문서 우선(SSOT=OpenAPI)**, **JWT 7일/RBAC/트랜잭션/실시간 정책**, **MVP 범위(냉장고 중심)**와 잘 맞습니다. 다만 _실전에서 매번 흔들리기 쉬운 경계들_—“코드 언제부터?”, “테스트로 어떻게 닫나?”, “태스크/CI 연결”—을 **명확한 게이트와 템플릿**으로 고정하면 더 안전하고 빨라집니다. 아래에 **추천 운영 절차(개선본)**을 드립니다.       

---

## **A. 대체 흐름(추천): “7-스텝 게이트드 루프”**

> 각 기능(예: **AUTH-01** 가입/승인, **FRIDGE-02** 포장 CRUD…) 단위로 아래 1→7을 반복합니다.

**0) 사전 조건**

- 관련 문서가 최신: docs/service/*, docs/openapi/fridge-mvp.yaml (SSOT). 바뀌면 **문서→스펙→테스트** 순으로 먼저 수정. 

**1) AI 이해안 → 당신 승인 (Design 프로필)**

- AI는 _문서 용어만_ 사용해 요구를 **재진술**하고, 필요한 경우 “어느 문서 어느 섹션을 먼저 수정해야 하는지”를 지적(코드 금지). 당신이 **맞다/수정**으로 확정.
    - 근거: 서비스 정의의 Must 범위·역할별 시나리오. 

**2) 큰 단계 제시 + 1단계 세분화 제안 (Design)**

- AI가 **대단계(35개)**와 **1단계의 세부 서브태스크(37개)**를 제시. 각 서브태스크는 **성공 조건(테스트 관점)**을 포함(코드 금지).
    - 근거: 기술 가이드의 완료 기준과 테스트 전략. 

**3) 개념 최소 설명(핵심만) (Design)**

- “왜 이 파일/DTO/엔드포인트가 필요한지”, “트랜잭션/권한/실시간 포인트”만 짧게 설명.
    - 예: 검사 **제출**은 조치/통계/알림까지 **원자적 트랜잭션**으로 묶임. 

**4) 주석 포함 파일 추천/생성 (Stubs)**

- 당신이 “진행”을 누르면 AI가 **빈 클래스/테스트 파일**을 생성(주석에 **입력/출력/권한/예외/트랜잭션 경계/테스트ID**). _구현 코드는 없음._
    - 도메인 용어/스키마 명칭은 **도메인 모델** 그대로. (Bundle/Item/Session/Action 등) 

**5) 당신이 코드 구현 → AI 리뷰(Review)**

- 당신이 구현 후 “리뷰 요청” → AI는 **문서/스펙 대비 불일치/누락/과설계** 지적, **실패 경로 테스트** 보강 제안(코드 X).
    - 필요 시 “코드 작성 요청”을 따로 명시하면 그때만 코드 생성.

**6) 기능 테스트로 닫기**

- 서브태스크의 마지막 체크: **MockMvc(+Testcontainers) 또는 Playwright E2E**가 **그린**. 실패했으면 3→6 반복.   

**7) Taskmaster/문서 업데이트**

- 태스크 상태 **Done**, checklist.md 및 해당 문서(서비스/도메인/가이드)의 **변경점 반영**. 다음 서브태스크로 이동. 

> 이 루프는 _인증/권한/JWT 7일_, _SSE→5초 폴링_, _검사 잠금/제출 원자성_, _알림 정책_ 같은 **핵심 원칙**을 설계/주석/테스트 모든 단계에 녹입니다.

## **B. 각 단계에서 쓰는 “짤막 프롬프트 템플릿”**

- **① 요구 재진술**
    
    > “아래 요구를 _문서 용어만_ 사용해 재진술. 새 엔티티/필드 제안 금지. 필요하면 어느 문서/섹션을 먼저 수정해야 하는지 지적.”
    
- **② 단계/세분화**
    
    > “대단계 35개, 1단계의 서브태스크 37개. 각 서브태스크 끝의 **테스트 통과 조건**을 써.”
    
- **③ 개념 최소 설명**
    
    > “이 기능을 이해하는 데 필요한 개념만 10줄 이내로. 권한/트랜잭션/실시간 포인트 표시.”
    
- **④ 주석 스텁 생성**
    
    > “빈 파일과 테스트 파일을 생성. 각 메서드/테스트에 입력/출력/예외/권한/트랜잭션 경계/테스트ID를 _주석_으로. 코드 구현 금지.”
    
- **⑤ 리뷰**
    
    > “문서/스펙 대비 불일치/누락/과설계 지적. **실패 경로 테스트** 보강안 제시(MockMvc/Playwright). 코드 제시 금지.”
    
- **(옵션) 코드 작성**
    
    > “지금부터 **해당 파일만** 코드 구현을 작성해줘.”

## **C. Taskmaster 연계: 태스크/체크리스트 템플릿**

**태스크 YAML 샘플**

```
# docs/tasks/FRIDGE-02.yaml
id: FRIDGE-02
title: 포장 CRUD + 물품 기본 등록/수정/삭제
refs:
  - docs/service/service-definition.md#냉장고-일반-기숙사생
  - docs/openapi/fridge-mvp.yaml#/paths/~1api~1fridge~1compartments~1{compartmentId}~1bundles
acceptance:
  - OpenAPI 스펙에 요청/응답/에러(401/403/409/422) 정의
  - MockMvc: 등록/수정/삭제/권한 오류/용량 초과 시나리오 **그린**
  - 라벨 재사용 정책 반영(삭제 후 재사용 가능) **검증 완료**
checks:
  - spectral lint OK
  - prism mock에서 happy path 호출 2건 성공
  - checklist.md 해당 섹션 업데이트
```

- 라벨/용량/권한/잠금 등 **실패 경로**를 명시적으로 포함하세요. (도메인/정책 반영)

## **D. 실행/테스트: Make 타깃 제안(간단·안전형)**

> 경로에 괄호가 있으므로 **항상 따옴표**로 감쌉니다.

```
# Makefile (루트)
PROJECT := "/Users/gimseunghyeon/Desktop/school/졸업프로젝트(세탁)/pj_DormMate"

dev-front:
	@bash -lc 'cd $(PROJECT) && \
	  docker compose up -d postgres && \
	  (npx @stoplight/prism mock docs/openapi/fridge-mvp.yaml > .tmp/prism.log 2>&1 &) && \
	  (./gradlew bootRun > .tmp/backend.log 2>&1 &) && \
	  (cd client && pnpm dev > ../.tmp/frontend.log 2>&1 &) && \
	  echo "✅ dev-front started: prism/backend/frontend (logs in .tmp/*.log)"'

dev-stop:
	@bash -lc 'cd $(PROJECT) && \
	  pkill -f "prism mock" || true && \
	  pkill -f "gradlew bootRun" || true && \
	  pkill -f "vite" || pkill -f "pnpm dev" || true && \
	  docker compose down && echo "🛑 dev stopped"'

test-back:
	@bash -lc 'cd $(PROJECT) && ./gradlew clean test'

test-front:
	@bash -lc 'cd $(PROJECT)/client && pnpm test'

test-e2e:
	@bash -lc 'cd $(PROJECT) && npx playwright test'

api-lint:
	@bash -lc 'cd $(PROJECT) && npx @stoplight/spectral lint docs/openapi/fridge-mvp.yaml'

api-mock:
	@bash -lc 'cd $(PROJECT) && npx @stoplight/prism mock docs/openapi/fridge-mvp.yaml'

# git HEAD와 현재 스펙 비교(레포에 redocly CLI 설치 시)
api-diff:
	@bash -lc 'cd $(PROJECT) && npx @redocly/cli diff HEAD docs/openapi/fridge-mvp.yaml || true'
```

- **왜 이렇게?**
    - _한 번에_ prism/mock, backend, frontend를 기동(요청하신 dev-front).
    - 경로 안전성(공백·괄호) 보장.
    - 테스트/스펙 품질 타깃을 Make로 표준화 → **Taskmaster acceptance**와 연결.
    - OpenAPI를 **계약의 기준선**으로 지속 검증.

## **E. CI/배포 파이프라인 골격(요약)**

1. **OpenAPI 품질**: spectral lint → (옵션) redocly diff.
2. **Backend**: ./gradlew test(MockMvc + Testcontainers).
3. **Frontend**: pnpm test → npx playwright test(핵심 여정 1~2건).
4. **이미지 빌드**: docker build(백/프론트).
5. **스테이징**: Compose로 배포 → **체크리스트 패스** 후 프로덕션.

- JWT 7일/RBAC/검사 트랜잭션/SSE 폴백은 **통합테스트/E2E에서 실패 경로까지 검증**하는 걸 _완료 기준_으로 둡니다.

## **F. “코드 언제부터?”를 지키는 3중 안전장치**

1. **Codex 프로필**: design(코드 금지) → stubs(주석만) → review(코드 없이 지적) → (요청 시) 코드.
2. **OpenAPI 스펙 없는 작업 금지**: 스펙 미정이면 **문서/스펙부터**. 
3. **태스크 마지막=테스트 그린**: 기능이 끝났다고 말하려면 **테스트가 증빙**.

## **G. 역할/권한/도메인 용어 일치(혼선 방지 체크)**

- **JWT(7일)·RBAC 경로** **/api/admin/**** **/api/inspector/**** **/api/fridge/****, 승인 전 403, 벌점 10점↑ 제한(냉장고 예외). 
- **검사 세션=칸 잠금/세션 UUID/합류/제출 원자성**, 조치 유형 PASS/WARN/DISPOSE/UNREGISTERED_DISPOSE. 
- **포장(FridgeBundle)/물품(FridgeItem)/라벨 재사용/임박·만료 필터/검사 후 수정 표시**.
