# **DormMate – 통합 정리**

> **최상위 목표**: 중견기업이상 취업을 목표로하는 백엔드 지망자가 혼자서 진행하는 첫 프로젝트로서 구현 요소를 최대한 줄이되, 실사용에 필요한 핵심만 정확히 제공. 공통화/표준화로 재사용성을 극대화하고, 역할 기반 접근 제어와 추적 가능성을 기본값으로 한다.

## **1) 요약 스택**

- **프론트**: React(TypeScript) · Vite · Tailwind · shadcn/ui · TanStack Query · PWA
- **백엔드**: Spring Boot **Java 21** · Spring Security(JWT) · Spring Data JPA · PostgreSQL · Flyway · Actuator
- **실시간**: **SSE**(단일 스트림)
- **인프라**: **AWS Lightsail**(+ Nginx 리버스 프록시)
- **모니터링/로그**: **Sentry** (Phase A: Prometheus+Grafana)
- **보안**: HTTPS, CORS 화이트리스트, 레이트리밋(nginx 또는 Bucket4j 중 1)
- **캐시/세션/메시징**: **미도입**(단일 인스턴스 기준). 다중 인스턴스 전환 시 Redis(PubSub) 도입.

> 선택 근거: 초기 트래픽·운영 복잡도 최소화. 비용·학습부담 절감.

- 개발환경
	- **M1 MacBook**
	- **IntelliJ IDEA / VS Code**
	- **Postman** – API 테스트
	- **DBeaver** – DB 관리
	- **Obsidian** – 설계/문서 관리
## **2) 기본 원칙**

- **RBAC**: `ADMIN_ROOT` | `ADMIN` | `INSPECTOR` | `RESIDENT`
- **로그인 필수**, **딥링크 필수**, **감사로그 기본값**
- **관리/검사 화면**: 사용자 UI 재사용 + “추가 액션 버튼”
- **정정 규칙**: 점검 결과 원본 불변. **AMENDMENT**로만 보정. 조회는 뷰 `v_inspection_results_effective`.
- **락**: 점검 전 `resource_locks` 선취. TTL 5분 + **하트비트 30초**. 단절 90초 후 회수.
- **감사**: 모든 쓰기 전 `GUC(app.user_id, app.change_reason)` 설정 → `event_log` 적재.
- **벌점**: 앱 로직 산정. DB에는 원본/ 조정만 기록.
## **3) 실시간 & 알림**

- **포그라운드 동기화 = SSE**: 자동 재연결, Last-Event-ID, 30s keepalive.
    프록시 버퍼링 off, read_timeout 확장(아래 구현상세 참조).
- **백그라운드 알림 = Web Push(VAPID)**: iOS는 PWA 설치 상태에서만 수신/권한. **무음 푸시 금지**.
- **표시 원칙**
    - 문서 **visible**: 인앱 토스트/배지 우선, 시스템 알림 최소화(중복 방지)
    - **읽음 처리**: 관련 화면/팝업 진입 시 자동 읽음
- **알림 채널 일원화**: 기존에 존재하는 관리자-기숙사생 소통앱인 band과 중복되는 “역할 임명/공지” 등은 **미발송**

## **5) 도메인 표준화**

- **상태(enum, 공통)**: `AVAILABLE, IN_USE, RESERVED, DONE, UNAUTHORIZED_USE, ERROR_REPORTED, OUT_OF_SERVICE`
- **용어**: 스키마는 `resource_id` 고정. UI에만 "칸" 사용.
- **스티커 표기(SNNN)**
    - `S`= 칸 번호, `NNN`= 칸 내부 라벨 번호(1..999, 제로패딩).
    - **DB에는 `label_no`만 저장**. `SNNN`은 **런타임 파생**.
    - `S` 산출: `resources.position_order` ASC 정렬 → 1..N(냉장), 냉동은 `N+1`.
- **유니크 규칙**: `(resource_id, label_no)`는 **ACTIVE 상태에서만** 유니크(부분 인덱스).

## **5) 모듈별 정책(핵심 요약)**

### **5.1 냉장고**

- 등록: 단일/묶음. 번호 **재사용**(removed_at 설정 즉시 가능).
- 검색: 식별번호 **정확/접두** 검색.
- 검사: 칸 단위 잠금. 동시 2인. 제출 후 **사유 필수 수정**.
- 충돌: 활성 (resource_id,label_no) 충돌 시 **409**.
- 자동 재번호: **검사 컨텍스트에서만** next_free_label로 재부여 + event_log(auto_relabel).
- 칸 이동: item_groups.resource_id 변경. 충돌 시 409.
- 스티커 표기: S=position_order, NNN=label_no. 표시값 예 냉장1-123 (1123).

### **5.2 세탁실**(상세구현에서 정의함)

### **5.3 도서관**

- 원스톱 팝업: 대출/반납/연장/예약.
- 알림: 반납 **D-5**, 당일, 연체, 예약 가능/만료.
- 경량화: 예약 대기열 **1명**.

    - 활성화 시 **일반 사용자 로그인 제한**.
    - 휴관 시작 시 **냉장고 물품 일괄 소프트 삭제**.

### 냉장고
- **사용자 기능**
    - 단일 품목 또는 여러 품목을 한 번에 등록하는 묶음 등록기능-> 등록시 식별번호 발급되고 사용자는 식별번호를 적은 스티커를 물품에 부착해야한다.
    - **번호 재사용**: 해당 번호가 `REMOVED`면 즉시 재사용 가능.
    - 조회: 기본 "내 물품", 필터(임박/만료), **식별번호 검색**.
    - 상태 변경: `부분 소비`, `전량 제거`
    - 물품정보 수정
- **층별장(검사자) 기능**
    - **검사 모드**: 검사 시작 시 해당 칸 **잠금**(사용자 수정 불가, TTL 5분).
    - **동시 검사**: 2명 동시 가능, **검사자별 처리 이력** 분리 기록.
    - **조치**: `⚠️ 경고`(정보 불일치/보관 불량/스티커 미부착-DB엔 존재), `🗑️ 폐기`(유통기한 지남/DB에 없는 미부착).
    - **미부착 처리**: 미등록 물품도 즉시 폐기 등록 가능.
    - **결과 제출/수정**: 제출 시 통계/알림 발송. **제출 후 수정 가능(사유 필수, 이력 모두 기록)**.

## 상세구현(변경이 잦거나 확실히 확정되지 않아 따로 분류함)

- **검사 단위**: 층이 아니라 **칸(Compartment) 단위**.
- **스티커 규격**: `칸번호(1자리)+식별번호(3자리)` → **4자리 숫자**기입.
	- **SNNN**: 4자리 숫자. `S`=칸번호(1자리), `NNN`=칸 내부 라벨 번호(3자리).
	- **칸번호 S**: 해당 냉장고의 칸을 사람이 구분하기 위한 번호.  
	    기본 맵: `1=냉장1`, `2=냉장2`, `3=냉장3`, `4=냉동`.
	    
	- **라벨 번호 NNN**: 해당 칸 내부에서 유일한 1~999의 정수(스티커엔 3자리 제로패딩).
	- DB에는 `item_groups(compartment_id, label_no)`만 저장하고, 스티커 **SNNN은 저장하지 않음**.
	- S(칸번호) 산출
	- **저장 X**. 클라이언트/서버에서 **런타임 파생**.
	- 현재 정책(층당 냉장고 1대 기준):
	    
	    1. 냉장칸을 `position_order ASC`로 정렬 → `S = 1..N`
	    2. 냉동칸 → `S = N+1` (현 배치에선 4)
	        
	- 서버에서 **“칸 -> S” 변환**을 제공하면 UI가 확정적으로 표기 가능.
	-  NNN(칸 내부 라벨번호)
		- DB `item_groups.label_no`(INT, 1~999) 값에 **좌측 제로패딩**해 3자리 표기.
		- **유일성 범위**는 “해당 칸(compartment_id) + ACTIVE 상태” (부분 유니크 인덱스가 보장).
		-  2.1 등록 플로우
		
		1. 사용자가 **칸 선택**(냉장1/2/3/냉동) → 이때 서버가 칸의 UUID(`compartment_id`)를 넘겨줌
		2. 서버 `next_free_label(compartment_id)` 호출 → **다음 사용가능 NNN** 추천
		3. 등록 요청: `compartment_id`, `label_no`(정수), 기타 메타(expires_on 등)
		4. 응답 시 **사람친화 표기** 함께 반환:
		    
		    - 예: `display_label: "냉장1-123", sticker_code: "1123"`
		스티커에는 **1123**처럼 4자리 숫자만 적어 물품에 부착 	UI에는 **“냉장1-123 (1123)”** 형태 병기 추천(혼동 방지).

- 단일품목일시 단일품목단위/묶음일시 묶음 단위 고유 **식별번호 자동 발급**
	- 단일품목: 이름, 메모, 유통기한 입력 수량은 1로 선택되어있음
	- 이때 수량을 증가시키면 묶음이되고 세부수정 버튼이 활성화되고 숫자만큼 물품이 생성됨
		- 기존입력했던 이름->대표이름, 기존입력했던 메모->대표메모
		- 개별이름, 개별유통기한, 기존입력했던 이름, 유통기한으로 자동 입력되고 세부수정 버튼시 수정하고 최종 등록 가능
- 물품 칸이동 기능 넣을까 말까 고민중
- 최근 검사일 이후 물품정보 수정시 다음 검사일때 자동분류됨

### 세탁실
- 사용자 흐름
    1. 세탁실 메인 페이지의 대시보드에서 **바로 사용 가능** 기기 상단 그룹 + 진행바/남은시간이 표시됨을 확인
    2. 기기클릭시 상세팝업이 뜨고: 
	    - INUSE인 경우
		    - 그 기기에대해 유저가 보낸 메세지 목록 표시
			    - 사용중인 사람이 읽음 여부가 표시됨
			- 자신이 설정에서 설정한 알림전송여부 간략히 표시
				- 종료알림을 꺼놓았습니다. 라는 간단한 텍스트만 보이고 실제 수정은 설정앱에서 수정하게 하기
		    - 타인의 사용인경우
			    - 종료 알림 신청 또는 **남은시간 정정**(정정 시 원사용자에게 알림, 종료 알림 자동 보정).
		    - 자신의 사용인경우
			    - 남은시간 정정(알림x)
	    - AVAILABLE 상태인경우
		    - **사용 등록**: 기본시간(세탁기 38분 / 건조기 50분), **1분/10분 단위 증감**, 개인 **프리셋 저장**(옵션).
		    - **미등록 사용(UNAUTHORIZED_USE)** 발견 시 대신 남은시간 등록(종료 알림 **기본 비활성**). 설정 시간 경과 시 자동 `AVAILABLE`.
		    - 이전 사용자에게 다음엔 **필터 청소 요청**(필터 청소는 **건조기만** 해당)
		- DONE인경우
	    -  `DONE` 후 5분 경과 시
	        - **"기다리고 있어요" 알림(1회성)** 또는 **"세탁물 빼놨어요" 알림**(+ 강제 `AVAILABLE`). 활성화
    3. **고장 신고**: 누구나 가능 → `ERROR_REPORTED`(사용 차단, 신고자/사유 기록). 관리자가 접수 시 `OUT_OF_SERVICE`.
        
- **상태 정의**
    - **기본**: `AVAILABLE` (사용 가능) → `IN_USE` (사용 중) → `DONE` (완료) → `AVAILABLE`
	- 특수: `UNAUTHORIZED_USE`(미등록 사용 등록: 타임스탬프 경과 시 자동 복귀), `ERROR_REPORTED`(신고됨), `OUT_OF_SERVICE`(관리자 확정 비활성). `OUT_OF_SERVICE` (사용 중지)
	- 관리자 수동 제어 시, 해당 기기 사용자에게 별도 알림 전송.
- **경량화/가드레일**
    - **남은시간 정정은 ±10분**, **사유 필수**(남용 방지).
    - 관리자 수동 제어 시, 해당 기기 사용자에게 **별도 알림**.

## 알림구현

웹페이지는 메인화면, 냉장고,다목적실,도서관,세탁실메인화면으로 구성되어있다.

메인화면에는 당일 사용하는 다목적실의 정보와 현재 사용중/ 종료알림 신청한 세탁실기기의 정보와 메세지 읽음여부 표시하며 각 클릭시 해당 상태제어를 할수있는 버튼과 해당 기기에 관련된 알림/메세지가 표시되는 팝업이 뜬다.

알림을 표시하는건 4가지 방법이 있다

1. 백그라운드 푸시알림
2. 메인화면에서 다목적실, 세탁실기기의 메세지 읽음여부 표시 아이콘으로 기기 상태팝업으로 이동을 유도해 상세 팝업에서 메세지를 읽게함
3. 메인페이지의 종모양 알림버튼
4. 메인화면, 냉장고,다목적실,도서관,세탁실메인화면으로 이동하는 하단탭에서의 뱃지 표시
사용자가 **관련 정보에대해 파악했다고 판단가능한 페이지나 팝업에 진입하는 순간**, 시스템은 해당 알림을 자동으로 '읽음'으로 변경한다.

이미 관리자와 기숙사생들은 band라는 채팅, 게시물 앱으로 소통하고있다.

4가지 알림방법은 읽음 상태가 아닐때 활성화 할려고 한다. 해당알림을 유저의 피곤함 없이 어떻게 표시하려고 한 결과물은 다음과 같다

#### 4. 탭 읽음
- 값: 미읽음 수(최대 9+), 점 표시 허용.
- 규칙: 관련 화면 진입 시 소거. 24시간 경과 시 자동 만료 가능.
- 냉장고탭: (유통기한 임박 묶음이 있다면 오전 9시 이후 기준 1회/폐기물품이 있다면 영속)
- 도서관탭: (대출/도서/예약 임박 묶음이있다면 기준 1회(확인시 사라짐)/연체묶음이 있다면 영속)
- 냉장고: 임박 묶음은 매일 09:00 1회 생성 확인시 소거. 폐기 알림은 해제 전까지 유지.
- 도서관: 임박·당일·예약 가능 묶음은 매일 09:00 1회 생성 확인 시 소거. 연체는 해결 전까지 유지.
- 밴드앱과 중복이라 알림표시, 전송은 불필요하다고 생각되어 제외한 목록
	- 내 역할 임명/해제: (층별장용) 관리자로부터 **층별장으로 임명**되었습니다.
	- **공지**등록알림 : 관리자가 등록한 **새로운 공지사항**이 있습니다.
		- 공지등록이 여러곳에서 이뤄지면 관리자, 유저 모두 피로높아짐

### 메모

- Safari(iOS/macOS)는 **표준 Web Push**를 지원하며, 개발자는 **VAPID만** 사용하면 됨(별도 APNs 유료 구독 불필요).
- iOS는 **홈 화면 추가(PWA 설치)** 조건에서만 웹푸시 권한/수신 가능. 설치 가이드 UX 필수.
- **보이지 않는 푸시 금지**: 가시 알림 원칙 준수. 화면 갱신은 SSE로.
- 프록시/SSE 설정은 환경별로 차이가 크므로 사전 부하 테스트 권장.
