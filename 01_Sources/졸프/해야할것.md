좋아요. **DormMate 냉장고 MVP**를 25일 안에 배포하려는 목표와 당신의 개발 플로우(“설계→주석 스텁→직접 구현→리뷰/테스트”)에 맞춰, **Codex 전역 설정**과 **MCP 서버 구성**을 “바로 적용 가능한 형태”로 정리했습니다. 아래 제안은 당신의 기술 가이드/서비스 정의/도메인 모델/기능 인벤토리 문서를 기준으로 최적화되어 있어, AI 혼선을 줄이고(문서 우선·계약 우선) 작업 속도를 끌어올리는 데 집중합니다.

## **1) 목표·제약 요약 → 설정 방향**

- **계약 우선(SSOT)**: OpenAPI 스펙에 맞춰 프론트/백엔드/테스트가 모두 일치해야 함. 새 필드/용어는 _반드시 문서부터 갱신 후_ 코드로 반영. → Codex/MCP가 문서 파일을 항상 먼저 읽도록 구성.
- **보안/흐름**: 관리자 승인 → JWT(7일) → RBAC, 검사 세션 잠금/제출은 단일 트랜잭션 보장. → Codex 시스템 프롬프트에 인증/RBAC/트랜잭션 경계 준수 규칙을 박아 둠. 
- **실시간**: SSE 기본, 실패 시 폴링 폴백. → 테스트 러너/모크 서버 호출을 MCP로 표준화. 
- **MVP 범위 잠금(냉장고 중심)**: 포장/물품, 검사 세션/조치/제출, 알림(앱 내), 벌점 노출. → 태스크 템플릿/체크리스트에 이 범위만 포함.

### **(B) 시스템 프롬프트(핵심 가드레일)**

아래 블록을 Codex의 **Global System Prompt**로 넣어두세요(한국어 유지).

```
당신은 DormMate 냉장고 MVP의 설계 보조자다.
절대 코드를 즉시 작성하지 말고, 다음 순서를 항상 지켜라:
1) 문서 확인: service-definition.md, tech-guide.md, domain-model.md, feature-inventory.md를 먼저 스캔하고 용어/정책을 그대로 따른다. 새 용어나 필드가 필요하면 "문서 먼저 갱신"을 제안하고, 어디를 바꿔야 하는지 명시한다.
2) 설계 설명 전용 단계: 무엇(파일/클래스/엔드포인트/DTO), 왜(도메인 규칙/보안/트랜잭션), 어디(패키지/경로)만 서술한다. 코드, 의사코드, 스니펫은 금지.
3) 주석 스텁 생성 단계: 요청이 있을 때만 비어 있는 파일/테스트 뼈대와 상세 주석(입력/출력/예외/테스트 케이스 ID)을 생성한다. 실제 구현은 사용자가 한다.
4) 리뷰 단계: 구현된 코드가 문서와 OpenAPI 계약에 맞는지 엄격히 비교하고, 누락/불일치/과설계를 지적하며 테스트를 보강한다.

반드시 준수할 고정 규칙:
- 인증: Access Token 7일, 'Authorization: Bearer', RBAC 경로 매핑 준수.
- 트랜잭션: 검사 세션/제출은 단일 트랜잭션 원자성 보장.
- 실시간: SSE 기본, 실패 시 5초 폴링 폴백.
- 에러: 권한/잠금/용량/라벨/중복 알림 등 예외 경로를 우선 기술.
- OpenAPI가 단일 진실(SSOT)이며, 스키마/에러코드는 반드시 계약대로.

문서 경로(프로젝트 루트 기준):
- docs/service-definition.md
- docs/tech-guide.md
- docs/domain-model.md
- docs/feature-inventory.md
```

위 규칙은 기술 가이드/서비스 정의/도메인 모델/기능 인벤토리의 정책을 그대로 옮긴 것입니다.

### **(C) 단계별 “코드 억제” 안전장치**

- **출력 스타일 프리셋**: no_code_until_stubs=true 같은 내부 플래그를 만든 뒤(설정 메모), 설계 단계에선 “코드블록( ``` )”이 나오면 중단하도록 _Stop Sequence_를 추가합니다.

```
[output_controls]
stop = ["```"]  # 설계/리뷰 단계에서 코드블록 방지
```
    
- **태스크 라벨**: 설계 단계 답변 맨 뒤에 [#PHASE:DESIGN]/[#PHASE:STUBS]/[#PHASE:REVIEW] 같은 라벨을 강제해, 어느 단계인지 항상 명시.

## **3) MCP 서버 구성(권장 세트)**

> **개념/연결 흐름**: MCP는 모델이 바깥 도구(파일/프로세스/DB 등)에 접근하는 표준입니다. Codex/Responses API/Apps SDK 모두 MCP를 통해 도구 호출을 수행할 수 있습니다. 

> **설정 방식**: Codex CLI의 codex mcp 하위 명령 또는 위 config.toml을 직접 편집해 서버를 등록합니다. 

### **(A) 필수(Foundation)**

1. **filesystem(project-ro)** – 프로젝트 루트 읽기/쓰기
    
    - 용도: 주석 스텁 생성/테스트 파일 추가.
    - 가드: docs/**는 읽기 전용으로 분리(문서 오염 방지).
    - 근거: 문서 우선·주석 스텁 플로우. 

2. **process(exec-allowlist)** – 제한 명령 실행
    
    - Allowlist 예:
        - 백엔드: ./gradlew test, ./gradlew bootRun
        - 프론트: pnpm test, npx playwright test
        - 품질: npx @stoplight/spectral lint docs/openapi/fridge-mvp.yaml
        - 모크: npx @stoplight/prism mock docs/openapi/fridge-mvp.yaml
    - 근거: 계약 우선 검증(OpenAPI lint/mock) + 테스트로 마무리. 

3. **git** – 브랜치/PR/디프(읽기 중심)
    
    - 용도: PR 템플릿 강제, 작은 수직 슬라이스 단위 머지.
    - 근거: “작은 슬라이스 + 테스트로 닫기” 원칙. 

4. **openapi(local)** – 스펙 읽기/미리보기(가능하면 전용 서버, 없으면 filesystem+process로 대체)
    
    - 용도: 스키마/에러코드 정합 체크, 목 서버 기동.
    - 근거: SSOT. 

### **(B) 선택(Convenience)**

5. **postgres(ro)** – 로컬 Testcontainers/개발 DB **읽기 전용**(SELECT/EXPLAIN만)
    
    - 용도: 마이그레이션 후 스키마/인덱스 점검.
    - 근거: 트랜잭션/감사 로그/코드 테이블 정합.

6. **docker/compose** – compose up -d, compose logs 등 읽기 위주
    
    - 용도: 스테이징 유사 환경 로컬 재현.
    - 근거: 운영/배포 가이드. 

> ※ 일부 MCP 클라이언트는 세부 권한(RO/RW, path 단위)을 제한적으로만 지원합니다. 이 경우 OS 권한/컨테이너 경계로 보조하세요. MCP 자체 개념/도입 가이드는 OpenAI 공식 문서를 참고하면 좋습니다. 

### **(C)** 

### **config.toml**

###  **예시 스니펫(개념형)**

> 실제 키 이름은 클라이언트/버전에 따라 다를 수 있습니다. Codex의 MCP 등록은 CLI(codex mcp …) 또는 설정 파일로 가능하니, 로컬 환경의 도움말을 함께 확인하세요. 

```
[mcp.servers.fs_project]
type = "filesystem"
root = "/path/to/dormmate"   # 프로젝트 루트
mode = "rw"

[mcp.servers.fs_docs]
type = "filesystem"
root = "/path/to/dormmate/docs"
mode = "ro"

[mcp.servers.proc]
type = "process"
allowed = [
  "./gradlew test",
  "pnpm test",
  "npx @stoplight/spectral lint docs/openapi/fridge-mvp.yaml",
  "npx @stoplight/prism mock docs/openapi/fridge-mvp.yaml",
  "docker compose ps",
  "docker compose logs --no-color --tail=200"
]

[mcp.servers.git_local]
type = "git"
repo = "/path/to/dormmate"

[mcp.servers.pg_ro]
type = "postgres"
dsn  = "postgres://user:pass@localhost:5432/dormmate?sslmode=disable"
read_only = true
```

## **4) “당신 플로우”에 맞춘** 

## **Codex 프롬프트 템플릿**

> 각 기능 태스크 시작 시 Codex에게 아래 **템플릿**으로 지시하면, 일관성 있게 “설명→주석→리뷰” 루프가 굴러갑니다.

### **(1) 요구 확인 & 재진술**

```
[요구 재진술]
- 아래 요구를 *문서 용어만* 사용해 재진술해줘.
- 새 엔티티/필드/에러코드 제안 금지. 필요하면 어느 문서 어느 섹션을 먼저 고쳐야 하는지 지적해.
(문서: docs/service-definition.md, docs/domain-model.md, docs/tech-guide.md, docs/feature-inventory.md)
```

→ 문서 우선·용어 통일 규칙을 강제.

### **(2) 설계 설명(코드 금지)**

```
[설계 설명 – 코드 금지]
- 필요한 파일/클래스/패키지/엔드포인트/DTO/에러코드만 목록화.
- 각 항목에 "왜 필요한지(도메인/보안/트랜잭션)"와 "어디에 둘지(경로/패키지)"를 적어.
- OpenAPI 경로/스키마/권한을 명시하고, 스펙 변경 시 변경 diff를 서술(코드X).
```

→ 인증/RBAC/트랜잭션/에러 경로를 빠뜨리지 않게. 

### **(3) 주석 스텁 생성**

```
[주석 스텁]
- 위 설계대로 빈 파일들을 생성해(컨트롤러/서비스/엔티티/리포지토리/테스트).
- 각 메서드/테스트에 주석으로: 입력/출력/예외/권한/트랜잭션 경계/테스트 케이스 ID를 써.
- 실제 코드는 쓰지 마.
```

### **(4) 리뷰/테스트 보강**

```
[리뷰]
- 내가 작성한 코드가 문서/OpenAPI와 어디가 다른지 지적.
- 실패 경로(403/409/422/429 등) 테스트를 보강해줘.
- MockMvc(Testcontainers) 또는 Playwright 기준으로 테스트 케이스를 목록화.
```

→ “태스크 마지막은 기능 테스트” 원칙.

## **5) Taskmaster(MCP) 태스크 템플릿(샘플)**

> 모든 태스크는 **“기능 테스트 통과”** 항목으로 종료합니다. 

```
# docs/tasks/AUTH-01.yaml
id: AUTH-01
title: 회원가입(대기)·관리자 승인·로그인 API 계약/테스트
refs:
  - docs/service-definition.md#계정·권한
  - docs/tech-guide.md#1-인증-및-권한
acceptance:
  - OpenAPI 스펙에 /auth/signup, /admin/users/approvals, /auth/login 정의
  - 승인 전 로그인 403, 승인 후 200 + JWT(7일) 발급
  - MockMvc 통합 테스트 통과
checks:
  - spectral lint OK
  - prism mock 서버로 2개 시나리오 호출 성공
```

→ 인증/승인/JWT/RBAC 정책과 1:1로 연결.
