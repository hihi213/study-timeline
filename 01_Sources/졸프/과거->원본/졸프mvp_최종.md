# 1. 프로젝트 개요 및 현황

DormMate 프로젝트는 기숙사 냉장고 관리 시스템으로, 기숙사생의 물품 등록, 유통기한 관리, 층별장 검사, 알림 기능을 통해 냉장고 위생과 효율성을 높이는 것을 목표로 합니다. 이 프로젝트는 사용자의 첫 번째 솔로 개발 경험으로, Spring Boot 백엔드 중심의 MVP(Minimum Viable Product)를 6주 내 구현하며, 프론트엔드는 AI 도움을 받아 최소화합니다. 전체적으로 현실적인 기숙사 운영 문제를 해결하면서, 백엔드 개발자 포트폴리오로 활용할 수 있도록 설계되었습니다.

## 현실 기숙사 및 내 상황 요약

### 기숙사 운영 현황

**층 구성 및 성별 배치**

기숙사는 2층부터 5층까지 숙소로 운영되며, 2층은 남성 전용, 3~5층은 여성 전용입니다. 각 층에는 24개의 호실(예: 201~224, 301~324)이 배치되어 있으며, 1인실, 3인실 두가지 종류로 나뉘어집니다

**호실 유형 및 1인실 위치**
- **3인실 (TRIPLE)**: 22개 호실, capacity=3, personal_no 1~3
- **층별 1인실 위치**: capacity=1, personal_no=1 고정
  - 2층: 213호, 224호
  - 3층: 313호
  - 4층: 413호
  - 5층: 513호

거주자는 호실 번호와 개인 번호로 식별되며, 예를 들어 "201-1"과 같이 구분합니다. 거주 기간은 최대 1년으로, 중도 퇴사가 가능합니다.

**냉장고 구조 및 호실 배분**

각 거주층에는 냉장고 1대가 배치되어 있으며(총 4대, 2~5층),

현재의 냉장고는 냉장 칸 3개와 냉동 칸 1개로 구성됩니다(총 4칸).

다음 추가할 냉장고의 냉장,냉동칸 개수는 예측할수없습니다.

**호실 배분 규칙**: 층당 냉장칸/냉동칸에 24개 호실을 균등 배분
- 냉장칸 3개의 경우: 24/3=8, 8호실 균등배분
- 냉동칸 1개의 경우: 24/1=24, 24호실 공용
- slot 1 (냉장 1번 칸): 01~08호
- slot 2 (냉장 2번 칸): 09~16호
- slot 3 (냉장 3번 칸): 17~24호
- slot 4 (냉동 칸): 전체 24호실 공용 (24/1=24)
- 층당 2대로 증설시
	- 1호 냉장고: slot 1~4 (기존)
	- 2호 냉장고: slot 5~8 (신규)
	- 호실 재배분: 냉장 6칸 → 4호실/칸
	- compartment_room_access 자동 재계산

**층별장 및 검사**

층별로 기숙사생 중 일부를 '층별장'으로 임명하여 냉장고 관리, 정기 검사, 벌점 부여 등의 역할을 맡깁니다. 층별장은 1명혹은 최대 2명 임명되며, 동일칸 검사시 최대 2명이 동일 검사 세션을 공유하여 함께 검사를 진행합니다

**기타 시설 및 소통**

세탁실은 별도 건물에 남성용(세탁기 6대 + 건조기 2대)과 여성용(세탁기 7대 + 건조기 6대)으로 나뉘어 있으며, 남성 세탁실의 이불 건조기 2대는 남녀 공용이라 모두가 사용가능합니다. 다목적실과 도서관은 모든 기숙사생이 자유롭게 이용 가능합니다. 현재 소통은 Band 앱을 통해 이뤄지며, 공지사항은 게시물 형태로 전달되고, 냉장고 점검 결과(위반 목록)도 게시물로 공유됩니다. 이로 인해 신규 알림 시스템이 Band와 중복되지 않도록 설계해야 하며, 기숙사생의 알림 피로를 고려해 백그라운드 알림 설정 기능을 포함합니다.

### 개발자(사용자) 상황

사용자는 컴퓨터 공학 전공 대학생으로, Java 기초는 익혔으나 Spring Boot는 기본 수준만 학습한 상태입니다. 중견 기업 이상의 백엔드 개발자 지망생으로, 이 프로젝트가 첫 번째 솔로 개발 프로젝트입니다. 혼자서 진행하며, 총 6주(약 120시간) 내 MVP를 완성해야 하는 제약 조건 하에 있습니다. 프론트엔드(React) 부분은 AI 도구를 최대한 활용하여 80% 이상 생성할 계획으로, 백엔드(Spring Boot, JPA, Security) 학습과 구현에 집중합니다. 개발 환경은 M1 MacBook을 기반으로 하며, AI 어시스턴트(예: ChatGPT, Perplexity)를 통해 코드 생성과 디버깅을 지원받습니다.

## 핵심 요구사항 도출

기숙사 상황과 사용자 제약을 바탕으로, 프로젝트의 핵심 요구사항을 다음과 같이 도출합니다. 이는 냉장고 관리의 실사용성을 우선하며, Band 앱과의 중복을 피하고 알림 피로를 최소화하는 방향으로 초점을 맞춥니다.

### 기능적 요구사항
- **물품 관리**: 기숙사생이 호실/개인 번호 기반으로 냉장고 칸(slot 1~4)에 단일 품목 등록(이름, 유통기한, 라벨 번호 자동 발급). 조회/삭제는 기본 지원. 식별번호 검색은 정확 매칭으로 제한하여 구현 단순화. 스티커 코드는 {슬롯번호}{라벨번호 3자리} 형식(예: 1005, 5123, 8056).
-	검사 시스템:
	-	검사 세션은 칸 단위로 생성되며, 최대 2명의 검사자가 동일 세션에 합류 가능
	-	검사자가 특정 칸을 선택해 검사 세션을 시작하면, 검사 세션 ID를 부여받아 해당 세션의 상태를 공유
	-	두 검사자가 동일 칸에 함께 참여하는 경우, 동일한 세션 ID로 검사 화면을 공유하며, 검사 상태가 실시간 또는 주기적으로 동기화
	-	각 물품의 검사 완료 상태는 클라이언트 또는 Redis에서 관리되고, 완료된 물품은 UI에 ‘검사 완료’로 표시되어 중복 검사 방지
	-	모든 물품의 검사 상태가 ‘검사 완료’일 때, 검사자 중 한 명이 최종 제출 버튼을 클릭하여 검사 결과를 서버에 전송
	-	서버는 최종 검사 결과만 DB에 저장하며 검사 중간 상태는 DB에 반영하지 않음
	-	검사 중 세션을 취소하면 그 검사 결과는 저장되지 않고, 세션 데이터는 클라이언트 캐시 또는 Redis를 통해 관리
- **알림 기능**: 유통기한 임박(3일 전) 시 인앱 알림 생성(배치 스케줄링). 검사 결과 알림도 지원하나, Band 게시물과 중복되지 않도록 검사 결과 요약만 전달. 하루 1건 제한(유통기한 임박), 백그라운드 알림 설정 옵션 포함.
- **역할 기반 접근 제어(RBAC)**: RESIDENT(기숙사생: 자기 물품만), INSPECTOR(층별장: 검사 권한), ADMIN(전체 관리).

### 비기능적 요구사항
- **보안 및 운영**: JWT 인증(리프레시 토큰 MVP 제외), HTTPS 강제, CORS 화이트리스트. 알림 피로 방지를 위해 설정 가능성 보장. Band 앱과의 중복 전달 최소화(예: 링크 공유)
- **제약 고려**: 6주/120시간 내 구현으로 스코프 30% 축소(예: 세탁실/다목적실/도서관 기능 완전 제외). AI 의존으로 프론트 개발 시간 단축, 테스트는 해피 패스 중심.
- **확장성**: 현실 변화(냉장고 추가, 칸수 변경)를 고려해 칸/호실 구조 유연하게 설계. compartment_room_access 테이블로 동적 매핑 지원. Phase 2에서 상벌점, 동시 검사 강화, 푸시 알림 추가 가능

이 요구사항은 기숙사 위생 관리의 핵심(물품 등록 → 검사 → 알림)을 중심으로 하며, 사용자 상황(초보자 솔로 개발)을 반영해 최소 실행 가능 제품(MVP)으로 한정합니다. 후속 섹션에서 이 기반 위에 기능과 계획을 세부화합니다.

# 2. 전체 기능 및 정책 요약

DormMate의 전체 기능은 기숙사 공용 시설(냉장고, 세탁실, 도서관, 다목적실) 관리를 중심으로 설계되었으나, MVP에서는 냉장고 관리(물품 등록/검사/알림)에 초점을 맞춰 스코프를 축소합니다. 이는 개발자 혼자서 6주 내 구현 가능성을 고려한 결정으로, 공통 원칙(RBAC, 감사 로그, 상태 관리)을 모든 모듈에 적용하여 재사용성과 유지보수성을 강조합니다. 기능은 사용자 중심(RESIDENT)부터 관리자(ADMIN) 역할까지 계층화되어 있으며, Band 앱과의 중복을 피하기 위해 알림은 실질적 행동 유도(예: 유통기한 임박, 검사 결과)에 한정됩니다.

## 기능 모듈별 설명

### 냉장고 관리 (MVP 핵심 모듈)

**냉장고 구조 정책**
- 층당 냉장고 1대, 각 4칸(slot 1~4)
- slot 1~3: 냉장 칸 (kind='FRIDGE')
- slot 4: 냉동 칸 (kind='FREEZER')
- 냉장 칸 3개 → 8호실씩 배분 (24호실 ÷ 3칸)
- 냉동 칸 1개 → 전체 24호실 공용 (24호실 ÷ 1칸)

**스티커 코드 생성**
- 형식: {슬롯번호}{라벨번호 3자리}
- 예시: slot 1 + label 5 → "1005"
- 냉장고별 구분: 1호 냉장고(1~4), 2호 냉장고(5~8)

**사용자(RESIDENT) 기능**
- 단일 또는 묶음 물품 등록(이름, 메모, 유통기한 입력, 자동 라벨 번호 발급)
- 스티커 부착 의무, 번호 재사용(REMOVED 상태 물품 즉시 가능)
- 조회(내 물품 기본, 임박/만료 필터, 식별번호 정확/접두 검색)
- 상태 변경(부분 소비/전량 제거), 물품 수정
- 최근 검사 후 수정 시 다음 검사에서 자동 분류
- 접근 제어: 본인 호실이 배정된 칸에만 등록 가능 (compartment_room_access 검증)

**검사자(INSPECTOR) 기능**
- 칸 단위 검사 모드(검사중일땐 검사자가 아닌 사용자는 칸의 물품 수정, 등록 불가)
-	검사 세션 공유 방식:
	-	칸당 1개의 검사 세션 생성, 최대 2명 동시 참여
	-	검사자 A가 세션 시작 → 검사자 B가 같은 칸 선택 시 자동 합류
	-	동일 세션 ID로 검사 화면 공유, 물품별 검사 상태 실시간 동기화
	-	검사 중 상태는 클라이언트 캐시 또는 Redis에 저장
	-	물품별 검사 완료 상태를 UI에 표시 (다른 검사자 및 자신이 검사한 물품은 ‘검사 완료’ 탭으로 분리)
	-	최종 제출 시 모든 검사 결과를 DB에 일괄 반영
	-	검사 취소 시 데이터는 DB 미반영, 캐시에서만 관리
- 조치 유형:
  - ⚠️ 경고(WARN): INFO_MISMATCH(정보 불일치), STORAGE_ISSUE(보관 불량), STICKER_MISSING_REGISTERED(등록됐으나 스티커 붙이지 않음)
  - 🗑️ 폐기(DISPOSE): EXPIRED(유통기한 만료), UNREGISTERED(미등록 물품)
- 미부착 물품 즉시 폐기 등록, 결과 제출/수정(통계 집계, 조치된 물품 보유자에게만 알림 발송)
**관리자(ADMIN) 기능**
- 자원 관리(냉장고 유닛 추가/편집/삭제), 상태 일괄 변경
- 층별장 임명/해제, 벌점 조정, 휴관 모드(로그인 제한, 물품 소프트 삭제)

### 세탁실
- 사용자 등록(기기 클릭 → 사용 시간 설정, 프리셋 저장), 미등록 사용(UNAUTHORIZED_USE) 처리, 종료 알림 신청/시간 정정(±10분 범위), 고장 신고(ERROR_REPORTED), 메시지 교환(기기 내 채팅). 상태: AVAILABLE → IN_USE → DONE → AVAILABLE. 필터 청소 요청(건조기 한정).

### 도서관
- 사용자 검색(제목/저자/번호), 원스톱 팝업(대출/반납/연장/예약 - 대기열 1명 한정), 인기/신규 탭(대출수/등록일 정렬). 알림: 반납 D-5/당일, 연체(자동 벌점), 예약 가능/만료. 관리자: 도서 등록/수정/분실/삭제.

### 다목적실
- 타임라인 뷰(시간대 예약 현황), 10분 단위 예약(매주 월요일 주간 오픈), 합석 뱃지 표시, 노쇼/미등록 신고(관리자 큐 적재). 알림: 시작/종료 15분 전, 노쇼 신고. 관리자: 강제 예약, 사용자 다이얼로그 재사용.

### 알림 시스템
- 유형: 유통기한 임박(하루 1회, 3일 전), 검사 결과(경고/폐기), 상벌점 변동
- 표시: 인앱 토스트/배지 우선(문서 visible 시), 읽음 자동 처리(관련 화면 진입 시)
- 백그라운드: Web Push(VAPID, PWA 설치 조건, 무음 금지)
- Band 중복 피함(임명/공지 미발송)
- 탭 뱃지: 미읽음 수(9+ 표시, 24시간 자동 만료)
- 발송 시각: KST 기준 (09:00 배치 실행)

### 마이페이지 및 공통
- 통합 이력(필터: 전체/냉장고 등), 간단 통계(이용 횟수/벌점 변화), 설정(알림 수신, 세탁 프리셋). 감사 로그 기본(모든 쓰기 적재), 딥링크 지원(로그인 후 직행).

## 역할 및 보안 정책

### 역할 기반 접근 제어(RBAC)
-	ADMIN_ROOT: 최고 관리자 - 전체 시스템 제어(계정 승인, 자원 관리, 벌점 조정, 휴관 모드 활성화)
-	ADMIN: 관리자 - 자원 상태 변경, 층별장 임명/해제, 강제 예약/취소, 알림 큐 처리
-	INSPECTOR: 층별장 - 검사 모드 진입(칸 잠금), 조치/제출, 자기 층 냉장고 조회(통계 포함). 2명 동시 가능, 동일 세션 공유
-	RESIDENT: 기숙사생 - 자기 물품만 등록/조회/수정, 알림 수신. 로그인 필수, 호실/개인 번호 기반 식별

### 보안 정책
- **인증/인가**: JWT(Spring Security) 기반 로그인 필수, RBAC 적용(역할별 API 엔드포인트 제한). 감사 로그 기본(모든 쓰기 시 적재).
- **접근 제어**: 딥링크 지원(인증 후 직행), 자원 락, 충돌 시 409 응답(라벨 중복 등).
- **보안 기본**: HTTPS 강제, CORS 화이트리스트(도메인 제한), 레이트 리밋(Nginx 또는 Bucket4j). 비밀번호 BCrypt 해싱, 알림 피로 방지(읽음 자동, 하루 제한).

## 아키텍처 스택 요약

# 3. MVP 구현 계획 및 일정

MVP 구현은 총 6주(약 126시간, 주 21시간 기준)로 진행되며, 백엔드 중심으로 물품 CRUD, 검사 시스템, 알림 인프라를 완성합니다. 전체 기능 중 냉장고 관리에 초점을 맞춰 스코프를 30% 축소하였으며, 프론트엔드는 AI 도구를 활용해 2~3일 단위로 통합합니다. 계획은 Block 단위로 세분화되어 각 주 종료 시 즉시 검증 가능하도록 설계되었으며, 품질 게이트를 통해 안정성을 확보합니다. 리스크는 동시성 처리(라벨 발급, 검사 슬롯)와 타임존 관리에 집중되며, 버퍼 시간(총 42시간)을 통해 대응합니다.

- **타임존/배치 리스크 (중간)**: 서버/컨테이너/DB 불일치. 대응: spring.task.scheduling.time-zone=Asia/Seoul, Docker TZ 환경변수 설정. 테스트: UTC 서버에서 KST 9시 실행 확인.

## 구현 힌트 및 주의 사항

### 구현 힌트
- **어드바이저리 락 (물품 등록)**: @Transactional 메서드 내 JdbcTemplate로 "SELECT pg_advisory_xact_lock(?)" 실행(compartment_id 기준), MAX(label_no)+1 후 INSERT. 데드락 시 DeadlockLoserDataAccessException catch하여 409 Conflict 반환.
- **슬롯별 스티커 코드**: slot_no(1~8) 직접 사용, 냉장고 구분 불필요. short_code = slot_no::text || LPAD(label_no, 3, '0'). 트리거 fn_compute_item_group_shortcode에서 compartment.slot_no 조회.
- **호실 접근 제어**: tg_item_group_owner_guard 트리거에서 compartment_room_access 조인 확인. 호실 미매핑 시 'room not allowed for this compartment' 예외.
- **슬롯 자동 배정 (검사 시작)**: active 세션 쿼리 후 usedSlots 리스트 생성 → 빈 슬롯(1 or 2) 할당. 2개 모두 사용 시 NoSlotAvailableException(409). 트리거 권한 검증 병행.
- **리프레시 토큰 회전 (로그인/갱신)**: SHA-256 해시 저장, 기존 토큰 revoked_at=now() 후 신규 발급. interceptor에서 401 시 자동 /auth/refresh 호출, 실패 시 로그인 리다이렉트.
- **배치 스케줄링 (유통기한 임박)**: @Scheduled(cron="0 0 9 * * *", zone="Asia/Seoul")으로 threshold=now()+3days 쿼리. 사용자별 그룹핑 후 알림 생성(중복 체크: created_on 유니크 인덱스).
- **RFC7807 에러 (전체)**: @ControllerAdvice로 ProblemDetail 반환(예: 409 시 title="Label Conflict", detail="Label 23 in use"). Spring Boot 3.2+ 필수.

### 주의 사항
- **트랜잭션 경계**: 모든 쓰기 작업(등록/조치) @Transactional로 래핑, 락 해제 자동화. 부분 인덱스(removed_at IS NULL) 조건 누락 시 중복 허용 위험.
- **타임존 일관성**: application.yml에 spring.task.scheduling.time-zone: Asia/Seoul, Docker environment TZ: Asia/Seoul. DB TIMESTAMPTZ 사용 시 now()로 UTC 저장, 쿼리 시 AT TIME ZONE 'Asia/Seoul' 변환 확인.
- **프론트 통합**: React Query onSuccess로 invalidateQueries 사용(캐싱 갱신). 30초 폴링은 배터리 소모 고려, SSE로 대체 가능(Phase A).
- **테스트 전략**: Postman(Week 1~2), 브라우저 E2E(Week 4), JMeter 동시(Week 4). 로그: PostgreSQL log_statement=all로 트리거 디버깅.
- **버전 관리**: Spring Boot 3.2.0 명시(pom.xml), Flyway V1__init_mvp.sql 실행 후 시드 확인. 예외: DataIntegrityViolationException → 사용자 친화적 메시지 변환.

이 계획은 개발자 초보 수준을 고려해 힌트 중심으로 설계되었으며, 매일 1~2 Block 완결형으로 지연 최소화합니다.

# 4. 후속 계획 및 확장 방향

MVP 완성(6주 후) 이후, DormMate는 Phase A(3~4주, 기능 강화)와 Phase B(6~8주, 모듈 확장)로 이어지며, 총 3~4개월 내 풀 버전 구현을 목표로 합니다. 확장 로드맵은 MVP의 핵심(냉장고 관리)을 기반으로 하되, 기숙사 전체 시설(세탁실, 도서관, 다목적실)을 통합하며, 사용자 피드백과 Band 앱 연동을 반영합니다. 운영 측면에서는 단일 인스턴스에서 다중 인스턴스 전환을 준비하며, 모니터링을 강화해 안정성을 확보합니다. 이 계획은 개발자 혼자서 진행하되, AI 도움을 확대하고 오픈소스 재사용으로 효율성을 높입니다.

## 기능 확장 로드맵

### Phase A: MVP 강화 (3~4주, 60~80시간, Week 7~10)

MVP의 안정화와 냉장고 모듈 고도화를 우선하며, 실시간성과 사용자 편의성을 강조합니다. 배포 후 사용자 테스트(기숙사 내 10~20명)를 통해 피드백 수집, Band 중복 알림 최소화(예: 링크 공유) 적용.

- **실시간 통합 (Week 7, 15h)**: SSE(Server-Sent Events) 도입으로 알림 푸시 실시간화(폴링 30초 → 즉시). 검사 세션 하트비트(30초) 추가, 동시 2인 검사 강화 힌트: Spring Boot @EventListener로 이벤트 발행, 클라이언트 EventSource 연결. 리스크: 연결 끊김 처리(재연결 로직).
- **푸시 알림 및 설정 확장 (Week 8, 20h)**: Web Push(VAPID 프로토콜, PWA 기반) 구현, FCM(iOS/Android) 준비. 알림 설정 세분화(DND 시간대, 카테고리별 opt-in). 유통기한 배치 최적화(이메일 백업). 힌트: push_endpoints 테이블 활용, revoked_at으로 만료 관리. 테스트: 브라우저 푸시 허용 후 수신 확인.
- **물품/검사 고도화 (Week 9~10, 25h)**: 물품 부분 수정(PATCH /api/items/{id}, expiry_date/quantity 업데이트), 제출 후 수정(supersedes_action_id 활용, 이력 뷰 생성). 상벌점 시스템 도입(penalty_records 확장, 자동 알림). 라벨 재사용 강화(REMOVED 상태 자동 next_free). 힌트: JPA @OptimisticLocking으로 버전 충돌 방지. E2E: 사용자 시나리오 10건 추가 테스트.

Phase A 완료 후, 기숙사 내 베타 배포(20명 사용자), Band와 연동 테스트(알림 링크 삽입).

### Phase B: 전체 모듈 확장 (6~8주, 120~160시간, Week 11~18)

기숙사 전체 시설 통합, 관리자 도구 강화. 사용자 규모(100명 이상) 대비 스케일링.

- **세탁실 모듈 (Week 11~13, 40h)**: 기기 등록/예약(시간 프리셋 저장), 미등록 사용 처리(UNAUTHORIZED_USE), 종료 알림/정정(±10분). 고장 신고 + 메시지 채팅(기기 내). 힌트: resources 테이블 확장(kind='WASHER'), resource_status로 상태 관리. 통합: 알림 유형 'LAUNDRY_START/END' 추가.
- **도서관/다목적실 (Week 14~16, 50h)**: 도서 대출/반납 팝업(원스톱), 예약 대기열, 인기/신규 탭. 다목적실 타임라인 뷰(10분 단위), 노쇼 신고 큐. 힌트: resources(kind='BOOK/ROOM') 재사용, SSE로 예약 알림. 연체 벌점 자동화(penalty_records 연동).

## 운영 및 서비스 모니터링 전략

MVP 배포 후 운영은 Lightsail 단일 인스턴스로 시작하며, 안정성과 사용자 경험을 최우선으로 합니다. 모니터링은 기본(Actuator)에서 고급(Prometheus)으로 단계적 도입, 로그 중심 문제 진단을 강조합니다.

### 운영 전략
- **배포/유지보수**: Docker Compose로 Spring Boot + PostgreSQL 패키징, Flyway 자동 마이그레이션. 배포 주기: 매주 월요일(Week 5~6 패턴), 롤백 스크립트 준비(V2__seed_mvp.sql 백업). 백업: DB 덤프 매일 자동(AWS S3), 코드 GitHub 브랜치(develop/main).
- **사용자 지원**: Band 앱 연동(FAQ 게시물), 인앱 헬프(문의 폼 → ADMIN 큐). 업데이트 알림(Phase A 푸시 활용). 스케일: 200명 초과 시 Lightsail 업그레이드(4GB RAM), Redis 도입.
- **보안/컴플라이언스**: HTTPS/CORS 고정, 레이트 리밋(100req/min/IP). 감사 로그(penalty_records + event_log)로 분쟁 추적. OWASP Top 10 준수(Week 6 체크리스트).
- **비용 관리**: Lightsail $5~10/월, 도메인 $10/년. 무료 티어(Sentry 기본) 활용.

### 서비스 모니터링 전략
- **기본 모니터링 (MVP, Week 5~6)**: Spring Actuator(/health, /metrics)로 헬스 체크(UP/DOWN), 메트릭(응답 시간, 에러율). 로그: SLF4J + Logback(파일/콘솔), Sentry(에러 트래킹 - JavaScript/백엔드 통합). 힌트: application.yml logging.level.root=INFO, Sentry DSN 환경변수.
- **고급 모니터링 (Phase A, Week 7~10)**: Prometheus + Grafana 도입(Actuator exporter), 대시보드(CPU/메모리, API 호출/에러, 배치 실행 성공률). 알림: Slack/Prometheus Alertmanager(에러율 5% 초과 시). DB 모니터링: pgBadger로 쿼리 분석(느린 쿼리: 검사 슬롯 조회 최적화).
- **운영 지표 및 대응**:
  - **KPI**: 가용성 99.5%(다운타임 <4h/월), 응답 시간 <500ms(95%), 알림 전달률 95%(Sentry 추적).
  - **문제 대응**: 로그 분석(예: 라벨 충돌 → 어드바이저리 락 확인), 롤백(Docker 이미지 태그), 핫픽스(GitHub Actions CI).
  - **성능 튜닝**: 인덱스 최적화(Week 10, pg_trgm 활용 검색), 캐싱(Phase B, Redis for 사용자 세션).
