# 데모 시나리오 로드맵
`docs/feature-inventory.md`와 `docs/data-model.md`에서 정리한 MVP 정책을 실제 구현 단위로 검증하기 위한 시나리오 모음이다. 각 단위는 백엔드와 프론트엔드가 함께 충족해야 하는 목표, 선행 조건, 성공 기준을 포함한다.

## 0. 공통 사전 준비
- **시드 계정**: 거주자 `alice`, `bob`, `charlie`, 관리자 `admin`. 추가 샘플(`dylan`, `diana`, `eric`, `fiona`)은 층/칸 접근 제어 검증용으로 활용한다.
- **데이터 세팅**
  - Flyway로 기본 스키마와 `compartment_room_access`, 샘플 포장/물품 시드를 적용한다.
  - 임박·만료 사례(D-2, 만료 지난 품목)와 미등록 폐기 데이터를 준비하고, `notification_policy` 기본값을 점검한다.
  - 냉장고 칸별 라벨 시퀀스가 중복 없이 증가하는지 확인하며, 데모용으로 특정 칸 `max_bundle_count`를 3개로 제한한다.
- **도구 및 로그**: Postman 컬렉션, `./auto tests backend`, `./auto tests frontend`, `audit_log`와 `notification_dispatch_log` 조회 스크립트를 사전에 준비한다.
- **토큰 관리**: 계정별 Access/Refresh 토큰을 미리 발급해 시나리오 전환 시간을 줄인다.

## 2. 구현 단위별 시나리오

### U1. 인증·세션 (AUTH-01)
- **목표**: 세션 7일 유지, 실패 누적 잠금, 관리자 해제 흐름을 검증한다.
- **선행 조건**: `alice`는 활성, `disabled_user`는 비활성, `admin`은 잠금 해제 권한을 보유한다.
- **수행 흐름**
  1. `alice`가 대소문자 혼용 ID로 로그인 → Access/Refresh 토큰 발급 기록 확인.
  2. 동일 브라우저 새 탭/새로고침으로 세션 유지 후 강제 로그아웃 → 재로그인.
  3. 잘못된 비밀번호를 5회 입력하여 잠금 발생 여부와 `audit_log`의 `LOGIN_FAILED` 누적을 확인한다.
  4. 잠긴 상태에서 올바른 비밀번호 입력 시도 → 추가 인증 없이 거절되는지 확인한다.
  5. `admin`이 `PATCH /admin/users/{userId}/unlock` 호출 → `LOGIN_UNLOCKED` 로그와 계정 정상화를 확인한다.
  6. `disabled_user` 로그인 시도 → 401/403 응답과 비활성 안내 메시지를 확인한다.
  7. 만료된 Access/Refresh 토큰으로 API 호출 → 각각 401/419 응답과 세션 무효화 로그를 검토한다.
- **실패/예외 시나리오**: Refresh 토큰 재사용(두 번째 요청 401), 만료 토큰 재사용 시 세션 폐기.
- **기대 산출물**: 잠금·해제 타임라인, `audit_log` 캡처, Postman 스크린샷.

### U2. 거주자 냉장고 (FRIDGE-02)
- **목표**: 칸 배정, 포장/물품 CRUD, 접근 제한, 미등록 폐기를 검증한다.
- **선행 조건**: `alice`는 201호 2번, `diana`는 201호 1번, `eric`은 211호 1번을 배정받는다.
- **수행 흐름**
  1. `alice` 로그인 → 냉장고 메인에서 배정 칸만 노출되는지 확인한다.
  2. 포장 생성: 포장명/메모 입력, 물품(우유·계란) 추가 → 저장 시 라벨 자동 발급과 허용량 검사 확인.
  3. 포장/물품 수정: 유통기한을 D-2로 변경 후 임박 배지 노출 확인, 메모 수정 가능 여부 검토.
  4. 물품 삭제 → 소프트 삭제 처리와 라벨 재사용(새 포장 생성 시 번호 재발급) 확인.
  5. `alice` 토큰으로 `bob` 포장 수정/삭제 시도 → 403 응답과 `FRIDGE_BUNDLE_ACCESS_DENIED` 로그 확인.
  6. 3층 `diana`가 2층 칸 API 접근 시도 → 403 또는 빈 목록, UI에서 칸 비노출을 확인한다.
  7. 미등록 물품 발견 → 간편 등록 후 즉시 폐기 → 통계에서 “미등록 폐기”로 집계되는지 검증한다.
- **실패/예외 시나리오**: 용량 초과 등록 시 경고 토스트, 잘못된 스티커 번호 검색 시 빈 응답.
- **기대 산출물**: 포장/물품 CRUD 요청·응답, UI 캡처, 라벨 시퀀스 증가 로그.

### U3. 층별장 검사 (INSPECT-01)
- **목표**: 단독 검사 세션 생성부터 제출, 권한 변화까지의 흐름을 검증한다.
- **선행 조건**: `admin`이 `bob`을 `FLOOR_MANAGER`로 승격하고 검사 대상 포장을 준비한다.
- **수행 흐름**
  1. `bob`이 검사 세션 생성 → 칸 잠금(`is_locked=true`)과 `inspection_participant` 기록 확인.
  2. “검사 전” 탭에서 포장별 조치(경고, 폐기, 통과, 미등록 폐기)를 입력한다.
  3. 모든 포장을 처리해 “검사 전” 탭이 비면 제출 버튼 활성화 → 제출 시 통계 집계 및 상태 `SUBMITTED`.
  4. 제출 직후 칸 잠금 해제와 `inspection_action` 기록을 확인한다.
  5. 검사 도중 새로고침/브라우저 종료 후 재진입 → 로컬 Draft 복원 확인(서버 Draft 미도입 메모 포함).
  6. 일반 거주자(`alice`)가 검사 세션 생성/조치 API 호출 → 403 응답과 `INSPECTION_FORBIDDEN` 로그 확인.
  7. 제출 후 `admin`이 `bob`의 `FLOOR_MANAGER`를 해제 → 이후 세션 생성이 거절되는지 검증한다.
- **실패/예외 시나리오**: 제출 전 포장 누락 시 제출 버튼 비활성, 임시 저장 버튼이 로컬 스토리지에만 반영되는지 확인.
- **기대 산출물**: 검사 세션 타임라인, 조치 요약, 칸 잠금/해제 로그.

### U4. 검사 결과 알림 (NOTI-01)
- **목표**: 검사 제출 시 즉시 알림 생성, 읽음/TTL, 알림 설정을 검증한다.
- **선행 조건**: U3 완료 후 `alice`가 검사 대상 거주자로 지정되고, `diana`는 백그라운드 허용 OFF 상태다.
- **수행 흐름**
  1. 검사 제출 직후 `alice` 계정에서 `FRIDGE_RESULT` 알림 생성과 미읽음 배지/탭 배지를 확인한다.
  2. 알림 상세 진입 → 자동 읽음 처리 및 `ttl_at`이 생성 시각 + 7일로 저장되는지 확인한다.
  3. `alice`가 검사 결과(kind 코드) 알림 OFF → 이후 검사 제출 시 신규 알림이 생성되지 않는지 확인한다.
  4. `diana`가 임박·만료 배치 실행 후 PWA 푸시는 수신하지 않지만 앱 목록에는 레코드만 남는지 확인한다.
  5. 동일 세션/사용자 조합으로 재제출할 경우 dedupe 키로 중복 알림이 차단되는지 검증한다.
- **실패/예외 시나리오**: 알림 OFF 상태에서 서버가 `is_enabled=false`를 존중하는지, 백그라운드 OFF 시 `notification_dispatch_log`에 제외되는지 확인.
- **기대 산출물**: 알림 목록/상세 캡처, `notification`·`notification_preference`·`notification_dispatch_log` 레코드.

### U5. 관리자 현황 (ADMIN-01)
- **목표**: 관리자 대시보드에 최신 검사/알림이 반영되고, 역할 승격/해제가 안전하게 수행되는지 확인한다.
- **선행 조건**: U3~U4 결과가 존재하며, `admin` 계정으로 접근한다.
- **수행 흐름**
  1. `admin` 로그인 → “최근 검사/알림 로그” 화면에서 방금 제출한 검사와 알림 발행 건이 반영됐는지 확인한다.
  2. 층별장 임명/해제 UI 실행 → `user_role` 기록이 즉시 갱신되고 진행 중 검사에 영향이 없는지 확인한다.
  3. 실패 로그/통계 카드가 최신 상태인지 확인하고, CSV 등 미구현 기능은 비활성 안내로 유지한다.
- **실패/예외 시나리오**: 임명 해제 직후 기존 검사 세션 접근이 거절되는지, 권한 갱신이 지연될 경우 재로그인 요구 여부 확인.
- **기대 산출물**: 관리자 화면 캡처, `user_role` 변경 로그, 관련 API 응답.

## 3. 통합 데모 동선
1. **준비**: `admin`이 `bob`을 층별장으로 승격하고 `alice` 포장 데이터를 세팅한다(U3 선행, U2 참고).
2. **로그인 시연(U1)**: `alice` 로그인 → 세션 유지 → 잠금 → 관리자 해제.
3. **거주자 포장(U2)**: `alice`가 포장을 등록·편집, 타인 접근 차단, `diana`의 타층 접근 실패 확인.
4. **검사 진행(U3)**: `bob`이 검사 세션 생성 → 조치 → 제출, 권한 해제 후 재시도 차단.
5. **알림 확인(U4)**: `alice` 알림 수신 → 읽음/TTL → 알림 OFF → 재검사. `diana` 배치 푸시 제외 확인.
6. **관리자 검토(U5)**: `admin`이 로그 화면 확인 → 역할 조정, 필요 시 알림/검사 통계 확인.
7. **마무리**: `./auto cleanup`으로 테스트 데이터 정리, `audit_log`·`notification_dispatch_log` 결과를 팀 공유 채널에 기록한다.

## 4. MVP 확장 (11/11 목표)
- **물품 CRUD 고도화**: 다중 검색, 임박/만료 필터, 미등록 폐기 통계 연동.
- **검사 합류/SSE**: `charlie` 보조 층별장 합류, 실시간 조치 동기화, 토큰 만료 처리, 검사 임시저장 로컬에서 서버로 Draft저장으로 이전
- **알림 배치**: 09:00 임박/만료 배치 트리거, kind별 OFF/백그라운드 토글 반영, dedupe 키 검증.
- **관리자 확장 기능**: 임박 물품·주간 검사 통계 카드, 냉장고 증설/재배치 시뮬레이션, 강제 수정 알림 발송.
- **다층 교차 검증**: 2층 `bob`, 3층 `charlie` 동시 검사로 관리자 통계 분리 반영.

## 5. MVP 이후 확장 (11/12 이후)
- **계정 및 권한**: 회원가입 승인/반려, 탈퇴, Band 연동, 벌점/감사 로그 강화.
- **알림 시스템**: dedupe/TTL 정책 UI, 푸시·이메일 채널, 통계/분석 대시보드.
