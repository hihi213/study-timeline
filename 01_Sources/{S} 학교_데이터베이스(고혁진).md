#### **개념 콘솔리데이션 (Concept Consolidation)**
오늘 배운 개념들은 다음과 같은 흐름으로 연결됩니다.
* **과학적 모델링 (Scientific Modeling)**: 실세계 문제를 해결하는 체계적 접근법
    * **`→` 1. 개념적 설계 (Conceptual Design)**: ERD를 통해 문제의 핵심을 사람이 이해하기 쉽게 그림.
        * **`→` 2. 논리적 설계 (Logical Design)**: ERD를 DBMS가 이해할 수 있는 **관계형 모델(Relational Model)**로 변환.
            * **`→` 관계 (Relation)** = **`표 (Table)`**
            * **`→` 표의 구조/틀** = **`스키마 (Schema)`**
            * **`→` 표의 실제 데이터** = **`인스턴스 (Instance)`**
        * **`→` 3. 물리적 설계 (Physical Design)**: SQL을 통해 실제 DBMS에 구현.
* **데이터베이스 시스템 (DBS)**: 위의 결과물을 운영하는 전체 시스템
    * **`→` DBS** = **`DBMS (소프트웨어)`** + **`DB (데이터)`**
    * **`→` 작업의 논리적 단위** = **`트랜잭션 (Transaction)`**

#### **오해 및 에러 로그**
1.  **증상**: "관계형 데이터베이스는 개체 간의 관계를 다루는 것이다."
    * **원인**: '관계(Relation)'와 '관계(Relationship)' 용어 혼동.
    * **올바른 해석**: 관계형 DB의 '관계(Relation)'는 수학적 용어로 **'표(Table)'**를 의미한다. 개체 간의 관계는 ERD의 'Relationship'이다.
2.  **증상**: "병행 처리나 병렬 처리나 둘 다 동시에 하는 거니 같은 말이다."
    * **원인**: CPU 개수라는 핵심 기준 간과.
    * **올바른 해석**: **병행**은 CPU 1개가 시분할로 동시성을 흉내 내는 것이고, **병렬**은 CPU 여러 개가 물리적으로 동시에 처리하는 것이다.
3.  **증상**: "DBMS나 DBS나 그게 그거다."
    * **원인**: 포함 관계에 대한 이해 부족.
    * **올바른 해석**: DBS는 시스템 전체(`DBMS+DB`)를, DBMS는 관리 소프트웨어만을 지칭한다.
4.  **증상**: "데이터를 추가했으니 테이블의 스키마가 변경되었다."
    * **원인**: 구조(스키마)와 데이터(인스턴스)의 개념 혼동.
    * **올바른 해석**: 데이터(`INSERT`, `UPDATE`, `DELETE`)가 변하는 것은 **인스턴스**의 변경이다. 스키마는 `ALTER TABLE` 같은 구조 변경 명령으로만 바뀐다.
5.  **증상**: "계좌 이체 중 입금이 실패했지만, 출금은 성공했으니 괜찮다."
    * **원인**: 트랜잭션의 원자성(Atomicity) 위반.
    * **올바른 해석**: 트랜잭션은 'All or Nothing'이다. 일부만 성공한 상태로 끝나면 안 되며, 실패 시 출금까지 모두 취소(Rollback)되어야 데이터 무결성이 지켜진다.
