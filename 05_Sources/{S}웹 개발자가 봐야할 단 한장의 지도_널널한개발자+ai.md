## 📖 소스 요약 (Summary)
- 티모시 버너스 리: html, http의 창시자
	- 지겹도록 논문을 봤다.
	- 참고문헌으로 다른 논문도 봐야했다.
	- 또다른 문서와의 관계를 링크라 하고, 이 링크를 가진 문서형식을 HTML이라고 하자.
	- TCP/IP를 이용해서 HTML를 실어나르기 위한 프로토콜인 HTTP를 창시
	- 웹의 핵심기술 두가지: HTML, HTTP
### **1. 리소스 (Resource)** : 우리가 관리하고자 하는 '대상'
초기 웹에서는 `.html`, `.jpg` 같은 식별하고자 하는 **정보 생성의 기본 단위**인 실제 **파일**을 의미했다.
현대 웹에서는 파일뿐만 아니라 데이터베이스의 데이터, 서비스의 기능 등 **추상적인 정보 단위**도 포함한다.

### **2. 리소스를 식별하는 URI**
- **URI (Uniform Resource Identifier)**:
	- 인터넷상에서 리소스를 식별하는 URI는 식별 방식에 따라 URL(위치)과 URN(이름)으로 나뉜다
- **URL (Uniform Resource Locator)**: 리소스의 식별을 **'위치'** 로 하는 방식
	- "어느 컴퓨터(Host)의 어느 경로(Path)에 있는가"라는 **전체 위치 정보**
- URN (Uniform Resource Name): 리소스의 식별을 **'이름'** 으로 하는 방식
	- **위치(URL)가 바뀌어도 변하지 않는 고유한 ID**
	    - 파일이 다른 폴더나 서버로 이사를 가도(URL 변경), 그 파일 자체의 고유한 이름(URN)은 그대로 유지됨.
	    - **예시**: 책의 **ISBN** (어느 서점(URL)에 있든 책의 고유 번호(URN)는 똑같음)

### **3. URL의 구성 요소와 식별 단계**

URL은 **`프로토콜://호스트:포트/경로`** 구조를 통해, 먼저 컴퓨터를 찾고 그 안의 프로그램을 찾고 그안의 리소스를 찾는 순서로 동작합니다.

| **이 구성요소로**                         | **식별 대상을 찾자** | **기술적 동작 및 역할**                                                                                                  |
| ----------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------- |
| **프로토콜** (Scheme)<br>`https://`     | **통신 규약**     | • 데이터를 주고받는 **방법**을 결정합니다.<br>• 보안(SSL) 적용 여부 등을 정의합니다.                                                          |
| **호스트** (Host)<br>`www.naver.com`   | **서버 컴퓨터**    | • **위치 식별**: 전 세계 네트워크에서 특정 서버(컴퓨터)를 찾습니다.<br>• DNS를 통해 도메인(www.naver.com)을 **IP 주소**(123.45.67.89)로 변환하여 접속합니다. |
| **포트** (Port)<br>`:8080`            | **애플리케이션**    | • **입구 식별**: 서버 내 여러 프로그램 중 어떤 서비스에 연결할지 결정합니다.<br>• (웹의 기본 포트인 80/443은 보통 생략됩니다.)                               |
| **경로** (Path)<br>`/news/index.html` | **리소스(자원)**   | • **내부 식별**: 서버 내부에서 관리하는 **구체적인 정보 단위**를 가리킵니다.<br>• 계층 구조를 통해 데이터의 부모-자식 관계를 표현합니다.                            |

> www.naver.com처럼 뒤의 구체적인 파일명(index.html)을 생략해도 서버는 경로까지만 요청받을 경우 약속된 기본 파일(index.html)을 자동으로 응답해 정상작동됨


## 🌐 URL 경로와 데이터 처리의 진화

### 1. URL의 Path 의미 차이
- 과거웹: 물리적 경로
- 현대웹: 실제 파일 위치가 아닌 서버가 정해둔 논리적 가상주소
	- 라우팅: 클라이언트의 요청(HTTP 메서드 + URL 경로)을 서버 내부의 특정 처리 로직(함수/메서드)으로 연결해 주는 프로세스

| **구분**     | **과거 웹 (정적 리소스)**                                                                      | **현대 웹 (동적 API)**                                    |
| ---------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Path의미** | 서버 하드디스크의 **실제 폴더/파일 위치**                                                              | 실행할 **함수의 식별자**                                      |
| **동작 원리**  | `/docs/index.html` 요청 시 자기 컴퓨터의 `C:\Web\docs\` 폴더에 들어가 `index.html`이라는 **실제 파일**를 찾는다. | `/docs/index.html` 요청 시 매핑 테이블을 확인해 `render()` 함수 실행 |
| **결과물**    | 저장된 파일의 바이너리 데이터를 HTTP 응답 바디에 담아 전송하고, 없으면 `404 Not Found`를 반환                         | DB 조회나 연산을 거쳐 가공된 데이터(JSON 등) 응답                     |

---

### 2. 쿼리 스트링(Query String): 함수를 제어하는 세부 옵션

URL 끝에 `?`로 시작하며 `key=value` 형태로 붙는 데이터 조각으로, 라우팅된 함수에 전달할 **세부 명령**을 담습니다.

- **구조:** `경로?키1=값1&키2=값2`
- **의미:** "이 리소스(함수)를 실행하되, **내가 준 조건**에 맞춰서 결과를 만들어줘."
    

#### **기술적 동작 프로세스**

1. **파싱(Parsing):** 서버가 URL을 읽다가 `?` 이후의 문자열을 잘라내어 **데이터 Map(Key-Value)** 형태로 변환합니다.
2. **함수 인자 전달:** 변환된 데이터를 라우팅된 **함수(Controller)**의 인자로 넘겨줍니다.
3. **조건부 로직 실행:** 함수 내부에서 전달받은 값을 사용해 DB 쿼리를 수정(WHERE절 추가 등)하거나 로직을 분기합니다.
    

> **예시: `GET /fridge/slots?floor=1`**
>
> - **서버의 판단:** "오케이, `/fridge/slots`니까 `getSlots()` 함수를 실행하자. 어? 옵션에 `floor=1`이 있네? DB에서 1층 데이터만 뽑아오게(WHERE floor=1) 처리해야겠다."

---

### 3. 경로(Path) vs 쿼리(Query) 설계 원칙
>왜 '경로'에 안 넣고 '쿼리'에 넣나요? (식별 vs 필터링)

- 경로는 대상을 거르고, 쿼리는 그 결과물을 필터링한다

|**구분**|**경로 (Path Variable)**|**쿼리 (Query Parameter)**|
|---|---|---|
|**역할**|리소스를 **식별** (Identity)|리소스를 **정렬/필터링** (Filter/Sort)|
|**관점**|"어떤 종류의 데이터인가?"|"그 데이터를 어떻게 보여줄까?"|
|**예시**|`/slots/3` (3번 칸이라는 **유일한 대상**)|`/slots?floor=1` (전체 중 **1층인 것들만**)|

---

### 4. 실전 대입 (냉장고 API 프로젝트)

우리가 설계한 **`GET /fridge/slots?floor=1&page=2`** 주소는 이렇게 해석됩니다.

1. **경로(`/fridge/slots`):** 냉장고 칸 목록을 처리하는 비즈니스 로직(함수)을 찾아감.
2. **쿼리(`floor=1`, `page=2`):**
    - `floor=1`: 1층 데이터만 검색하도록 필터링.
    - `page=2`: 전체 결과 중 두 번째 페이지 분량만큼만 데이터를 잘라서 응답.
### 💡 학습 정리

1. **경로**는 서버의 특정 **함수(로직)**를 찾아가는 주소다.
2. **쿼리 스트링**은 그 함수에 전달하는 **옵션(인자)**이다.
3. 서버는 이 옵션을 받아 **DB 쿼리를 동적으로 생성**하거나 데이터를 가공한다.

## 🌐 웹 통신 프로세스 및 인프라 흐름

### 1. 네트워크 경로 및 서버 보안 (접속 경로 계층)

클라이언트와 서버는 각자의 로컬 네트워크를 거쳐 공용 인터넷망(WAN)에서 만납니다.

- **웹 클라이언트의 외부 도달 경로:** 클라이언트의 브라우저에서 출발한 데이터 패킷은 내부망의 **L2 스위치**를 거쳐 게이트웨이 역할을 하는 **라우터**를 통과한 뒤, 공용 **인터넷(WAN)** 망에 도달합니다.
- **웹 서버의 인터넷 연결 및 보호 장치:** 서버 역시 인터넷에 연결되기 위해 라우터를 거치지만, 불특정 접근으로부터 리소스를 보호하기 위해 최소 3가지의 논리적 보안 계층을 추가적으로 둡니다.
    
	1. **방화벽 (Firewall):** 미리 정의된 보안 규칙에 따라 특정 IP와 포트(Port)의 접근을 1차적으로 제어
	2. **로드 밸런서 (Load Balancer):** 서버의 실제 IP 주소를 은닉(Private IP)하고, 외부의 대량 접속 요청(트래픽)을 여러 대의 서버로 분산해 가용성 보장.
	3. **WAF/IPS (웹 방화벽 및 침입 차단 시스템):** HTTP 메시지 내부의 악성 코드나 해킹 패턴(SQL 인젝션 등)을 실시간으로 분석하고 차단합니다.

### 2. 통신 수립 및 데이터 교환 5단계

웹 통신의 근본적인 출발은 **"원격지(멀리떨어져있는) 컴퓨터에 저장된 문서를 읽어오는 것"**입니다. 이를 위해 브라우저와 서버는 다음 5단계 절차를 수행합니다.

#### **1단계 [Server Setup] : 서버의 수신 대기**

- **프로세스 선행:** 클라이언트가 요청하기 전, 서버 애플리케이션이 먼저 구동되어야 합니다.
- **Listen 상태:** 서버는 운영체제로부터 특정 **포트(Port)**를 할당받아 점유하고, 클라이언트의 연결 요청을 수락할 수 있는 **Listen(수신 대기)** 상태를 유지합니다.
#### **2단계 [Addressing] : 브라우저의 주소 식별**
- 사용자가 브라우저 주소창에 URL을 입력해 접속대상을 지정했다면
-  **DNS 조회:** 브라우저는 **DNS(Domain Name System)** 서버를 통해 문자열로 된 도메인 네임을 실제 통신 가능한 **IP 주소**로 변환합니다.
#### **3단계 [Connection] : TCP/IP 통로 생성**

- 확보한 IP와 포트 번호를 바탕으로 클라이언트와 서버가 서로의 상태를 확인하는 **3-Way Handshake** 과정을 거쳐, 신뢰성 있는 **TCP/IP** 연결 통로를 생성합니다.

#### **4단계 [Data Exchange] : HTTP 메시지 송수신**

- **HTTP Request:** 클라이언트는 **HTTP 프로토콜** 규격에 맞춰 리소스를 요청합니다.
    - _(예시)_ **GET 메서드:** "이 경로의 문서를 읽고 싶다(Read)"는 요청을 보냅니다.
- **HTTP Response:** 서버는 요청을 처리한 후 결과물을 HTTP 응답 메시지에 담아 클라이언트에게 반환합니다.
    - _(예시)_ **200 OK:** 요청이 정상적이면, 상태 코드 200과 함께 요청한 리소스(HTML 등)를 바디에 담아 보냅니다.

#### **5단계 [Rendering] : 브라우저의 시각화**

- **해석 및 출력:** 브라우저는 수신한 **HTML 문서** 데이터를 분석(Parsing)하고 시각적으로 가공하여 화면에 출력합니다.
- **결론:** 브라우저의 본질은 **'원격지에 저장된 HTML을 해석해 보여주는 문서 뷰어'**입니다.

## 🏗️ 3. SW 설계 대원칙: 관심사의 분리와 웹의 3요소
> 소프트웨어 설계의 핵심 목표는 **유지보수성**입니다
> 	웹은 **구조, 꾸밈, 동작**을 엄격히 파일로 분리합니다
> 	자바는 객체

- **문제 인식:** 초기에는 HTML 내부에 꾸밈 정보(디자인)가 섞여 있어, 디자인 하나를 바꾸려면 모든 데이터를 수정해야 하는 의존성 문제가 있었습니다.
- **해결책:** 역할을 분리하여 파일로 관리합니다.
    - **HTML:** 데이터와 구조와 데이터(텍스트/사진/이미지)
    - **CSS:** 꾸밈과 레이아웃
    - **JavaScript (동작/로직):** 정적인 문서에 '움직임'과 '상태 변화'를 부여합니다.
- **정적 문서(Static Document):** 서버 하드디스크에 저장된 이 3가지 파일들을 가공 없이 그대로 전송하는 단계를 의미합니다.

| **구분**     | **정적 문서 (Static)**     | **동적 서비스 (Dynamic)**        |
| ---------- | ---------------------- | --------------------------- |
| **데이터 상태** | 서버에 저장된 **파일** 그 자체    | 서버 프로그램이 **실시간으로 생성한 결과물**  |
| **서버의 동작** | **파일 읽기 및 전송** (단순 배달) | **코드 실행 및 연산** (프로그램 작동)    |
| **내용의 결정** | 개발자가 파일을 저장할 때 결정됨     | 서버 로직이 실행될 때 결정됨 (예: 현재 시간) |
## ⚙️ 3. 브라우저의 내부 구조: 3대 핵심 엔진

서버는 JS 파일을 **저장 및 전달**만 하고 브라우저는 서버로부터 받은 **정적 리소스(HTML, CSS, JS)**를 해석하여 실행하는 역할을 합니다. 이때 각 요소를 처리하기 위해선 각 전용 엔진이 필요합니다.

- **브라우저의 3대 핵심 요소:**
    1. **파서(Parser):** **HTML** 태그를 분석해 데이터 구조(DOM)를 생성합니다.
    2. **렌더링 엔진:** 생성된 구조에 **CSS**를 결합하여 화면에 시각적으로 그립니다.
    3. **자바스크립트 엔진(예: V8):** 전달받은 **JS** 코드를 해석하고 실행하여 동적 기능을 수행.

## 🚀 4. [다음 예고] 문서 송수신에서 '서비스'로의 확장

초기 웹이 단순히 '파일(문서)을 주고받는 것'이었다면, 이제 현대 웹은 서버가 **기능(Service)**하는 단계로 진화합니다.

- 초기웹: 클라이언트가 서버 하드디스크에 존재하는 특정 파일의 경로를 요청하면, 서버는 해당 파일을 가공 없이 복사하여 전송합니다. (데이터의 1:1 매핑)
- 현대 웹: 클라이언트가 특정 매개변수(Parameter)와 함께 서버의 특정 기능을 작동시켜 실시간으로 생성된 그 **실행 결과값**을 받아옵니다.
- 즉 실행 로직이 **서버(Back-end)**에도 존재하게 됩니다.
- 서버에선 CGI로 코드 실행한다.
- **CGI(Common Gateway Interface):** 서버가 외부 프로그램을 실행하여 동적으로 결과를 생성하는 기술

1. **인프라:** 서버는 **방화벽/LB/WAF**로 보호받으며, **Listen** 상태로 대기한다.
2. **통신:** **DNS(주소) → TCP(연결) → HTTP(교환)** 순으로 진행된다.
3. **설계:** 유지보수를 위해 **HTML(구조), CSS(꾸밈), JS(동작)**로 역할을 분리한다.
4. **엔진:** 브라우저는 **파서, 렌더링 엔진, JS 엔진**을 통해 이를 처리한다.
5. **진화:** 웹은 **정적 파일 전송**에서 **동적 서비스 제공(CGI)**으로 확장되었다.

## 웹의 기술적 진화: 상호작용의 확장부터 플랫폼 독립성까지
### 1. 상호작용의 진화: GET에서 POST로

초기의 웹은 이미 만들어진 문서를 읽는 것이 전부였으나, 사용자의 데이터를 서버에 전달해야 하는 필요성이 생기면서 큰 변화가 일어났습니다.

- **단방향 (Static):** 서버에 저장된 HTML 파일을 그대로 가져오는 단계입니다. 주된 목적은 **조회(Read)**이며, HTTP **GET** 메서드가 이 역할을 담당합니다.
- **양방향 (Dynamic):** 사용자가 입력한 값(ID, 비밀번호 등)을 서버가 처리해야 합니다. 이는 단순 조회를 넘어선 **처리(Process)**와 **상태 변화**를 의미하며, 보안과 데이터 전송을 위해 **POST** 메서드가 핵심적인 역할을 수행하게 됩니다.

> [!NOTE]- 절차와 상태전이
>
> - **절차 발생 (Procedure):** 입력값을 바탕으로 목표 결과를 도출하는 일련의 연산 단계입니다.
> 	> 예: 로그인의 절차 [데이터 수신 → 유효성 검사 → DB 대조 → 세션 생성]
> - **상태 전이 (State Transition):** 절차 완료 후 시스템이 보유한 데이터의 **스냅샷(Snapshot)** 이 업데이트되는 현상입니다.
>     - **상태(State):** **특정 시점**, 시스템에 저장된 데이터의 구체적인 값.
>     - **전이(Transition):** 로직 결과에 따라 기존 상태(비로그인)가 새로운 상태(로그인)로 바뀌는 것.

### 2. 처리의 등장과 CGI의 한계

서버가 '계산'이나 '로직'을 수행하기 위해 도입된 첫 번째 표준이 **CGI(Common Gateway Interface)**였습니다.

- **CGI의 역할:** 웹 서버가 직접 실행할 수 없는 로직을 외부 프로그램(C, Perl 등)에 맡기고 그 결과를 돌려받는 인터페이스입니다.
- **C언어 기반 CGI의 문제점:**
    - **보안:** 메모리 직접 제어로 인한 오버플로우 등 보안 취약점 노출.
    - **플랫폼 종속성 (Native Code):** C언어로 작성된 코드는 특정 플랫폼(CPU + OS)에 최적화된 **기계어(네이티브코드)**로 컴파일됩니다. 따라서 서버 환경이 바뀌면 코드를 다시 짜거나 재컴파일해야 하는 유지보수 지옥이 발생합니다.

### 3. Java의 등장과 플랫폼 독립성

C언어의 '플랫폼 종속성' 문제를 해결하며 등장한 것이 **Java**입니다.

- **JVM(Java Virtual Machine):** Java는 머신코드 대신 **바이트코드**를 생성합니다. 이를 JVM이 실행 시점에 각 플랫폼에 맞게 해석하므로, 환경에 상관없이 동일한 코드를 실행하는 플랫폼 독립성을 실행합니다.

### 4. **서버의 파일전달과 로직실행의 분리**

서버의 통신과 로직을 분리함으로써 대규모 시스템에서도 상태 전이 로직을 안정적이고 효율적으로 관리한다.
- **Web Server (Apache 등):** 정적 리소스 송수신 및 클라이언트와의 통신 인프라 담당.
- **WAS (Tomcat 등):** 복잡한 비즈니스 로직 처리 및 애플리케이션 실행 담당.

### 💡 최종 핵심 요약

1. **동작의 확장:** 웹은 리소스 조회(GET)를 넘어 시스템 상태를 변경하는 **기능 호출(POST)**로 진화했다.
2. **핵심 기제:** 양방향 통신은 서버 내부의 **절차**를 가동하고, 그 결과로 데이터의 **상태 전이**를 일으킨다.
3. **환경의 극복:** 특정 플랫폼(CPU+OS)에 종속적인 **Native Code**의 한계를 **Java(JVM)**가 해결했다.
4. **효율적 설계:** 유지보수를 위해 송수신(Web Server)과 처리(WAS)를 분리하는 **현대적 WAS 구조**가 확립되었다.

| **구분**          | **요소**                           | **설명**                        |
| --------------- | -------------------------------- | ----------------------------- |
| **클라이언트**       | **HTML / CSS / JS**              | 구조, 꾸밈, 동작을 엄격히 분리하여 브라우저가 해석 |
| **서버 (Logic)**  | **WAS (Web Application Server)** | 대규모 비즈니스 로직과 데이터베이스 연동 처리     |
| **서버 (Static)** | **Web Server (Apache, Nginx 등)** | 정적 리소스 전달 및 WAS의 부하 분산        |
