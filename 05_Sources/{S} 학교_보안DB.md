    * **정석체크(면접 30초)**: 위험 평가는 먼저 보호할 **자산(Asset)을 식별하고 등급을 부여**하는 것에서 시작합니다. 이후 해당 자산의 **취약점(Vulnerability)**을 악용할 수 있는 **위협(Threat)**을 분석하여 위험 시나리오를 정의하고, **발생 가능성과 영향도**를 평가하여 최종 위험 수준을 결정합니다.
* **[Q3] 여러 사용자가 동시에 동일 데이터를 수정할 때 어떤 문제가 발생하며, 이를 어떻게 방지하나요? | 태그: 트랜잭션, 병행 제어, 무결성**
    * **정석체크(면접 30초)**: 동시성 문제는 **갱신 손실(Lost Update)**이나 **현황 파악 오류(Dirty Read)** 등을 유발하여 데이터 무결성을 훼손합니다. 이를 방지하기 위해 `DBMS`는 **락(Locking)** 기법을 사용하여 트랜잭션의 공유 데이터 접근을 제어합니다. 하지만 락을 과도하게 사용하면 **교착상태(Deadlock)**가 발생할 수 있으므로 주의해야 합니다.

    * **정석체크(면접 30초)**: `CREATE PROFILE` 명령어로 패스워드 정책을 정의하고, `ALTER USER ... PROFILE` 구문을 통해 사용자에게 해당 프로파일을 할당합니다. 예를 들어 `ALTER PROFILE app_user_profile LIMIT FAILED_LOGIN_ATTEMPTS 5 PASSWORD_LIFE_TIME 90;` 처럼 설정할 수 있습니다. `DEFAULT` 프로파일을 그대로 사용하면 보안에 취약할 수 있습니다.
* **[Q5] 사용자에게 테이블의 모든 정보가 아닌 특정 컬럼에 대한 `SELECT` 권한만 부여하는 등, 세분화된 권한 설정이 가능한가요? | 태그: 권한(GRANT/REVOKE), 객체 권한, 최소 권한 원칙**
    * **정석체크(면접 30초)**: **객체 권한(Object Privilege)**을 통해 세분화된 통제가 가능합니다. 예를 들어, `GRANT SELECT (emp_name, salary) ON employees TO analyst_role;` 과 같이 특정 컬럼에 대한 조회 권한만 부여할 수 있습니다. 이는 **최소 권한 원칙(Principle of Least Privilege)**을 준수하는 중요한 방법입니다.

### 🔥 필수 질문 Top-5

1. **[Q1] SQL 쿼리에서 `WHERE` 절과 `HAVING` 절의 기능적 차이와 올바른 사용법은 무엇인가?**
    
    - `WHERE`는 그룹화 전 개별 행을 필터링하고, `HAVING`은 그룹화 후의 집계 결과에 대한 조건을 필터링합니다. `WHERE`에는 집계 함수를 쓸 수 없지만 `HAVING`에서는 가능합니다.
        
2. **[Q2] 새로운 데이터베이스 사용자를 생성하고, 실습에 필요한 기본 권한을 부여하는 절차는 무엇인가?**
    
    - `SYSTEM` 계정에서 `CREATE USER`로 사용자를 생성한 뒤, 접속 권한(`CONNECT` Role)과 객체 생성 권한(`RESOURCE` Role)을 `GRANT` 명령어로 부여합니다.
        
3. **[Q3] `NULL` 값을 조회할 때 = 연산자 대신 `IS NULL`을 사용해야 하는 이유는 무엇인가?**
    
    - `NULL`은 '값이 없는 상태'이므로, 특정 값과 비교하는 = 연산자로는 결과를 반환하지 않습니다. `NULL` 상태 자체를 검사하는 `IS NULL` 또는 `IS NOT NULL`을 사용해야 합니다.
        
4. **[Q4] `COUNT(*)`와 `COUNT(컬럼명)`의 차이점은 무엇이며, 언제 각각 사용해야 하는가?**
    
    - `COUNT(*)`는 `NULL`을 포함한 모든 행의 수를 계산하여 테이블의 전체 크기를 파악할 때 사용하고, `COUNT(컬럼명)`은 해당 컬럼에 `NULL`이 아닌 유효한 값이 있는 행의 수만 계산할 때 사용합니다.
        
5. **[Q5] 오라클의 기본 비밀번호 만료 정책을 비활성화하려면 어떤 명령어를 사용해야 하는가?**

## **2025-09-22 — 최종(1~2교시 통합)**

### **하루 TL;DR (5줄)**

오늘은 여러 테이블의 데이터를 결합하는 **조인(Join)** 기법부터 학습했습니다. `INNER JOIN`부터 `OUTER`, `SELF JOIN`까지 다양한 조인을 `WHERE`절과 `JOIN ON` 구문으로 다루었습니다. 이어서 쿼리 내부에 쿼리를 사용하는 **서브쿼리(Subquery)**를 통해 복잡한 필터링을 수행했으며, 특히 성능이 중요한 상황에서 `EXISTS` 연산자를 활용하는 법을 익혔습니다. `GROUP BY`와 `HAVING`을 이용해 데이터를 집계하고 그룹별로 필터링하는 방법을 배웠고, 마지막으로 이 모든 개념을 종합한 실무형 문제 풀이를 진행했습니다.

### **🔥 필수 질문 Top-5**

1. **`INNER JOIN`과 `OUTER JOIN`의 근본적인 차이는 무엇인가요?**
    
    - 두 테이블의 교집합만 반환하는지, 한쪽 테이블의 모든 행을 보존하는지의 차이입니다.
        
2. **`WHERE` 절에 `MAX()` 같은 집계 함수를 직접 쓸 수 없는 이유는 무엇이며, 어떻게 해결해야 하나요?**
    
    - SQL 실행 순서상 `WHERE`절이 그룹화보다 먼저 실행되기 때문이며, 서브쿼리로 집계 값을 미리 계산하여 해결합니다.
        
3. **`EXISTS` 연산자는 `IN`과 비교했을 때 어떤 차이가 있으며, 언제 사용하는 것이 유리한가요?**
    
    - `EXISTS`는 존재 여부만 확인하고 멈추므로, 서브쿼리 결과가 매우 클 때 값 목록과 비교하는 `IN`보다 성능에 유리합니다.
        
4. **동일한 문제를 조인과 서브쿼리로 해결할 때, 두 방식의 접근법 차이는 무엇인가요?**
    
    - 조인은 테이블을 하나의 큰 집합으로 합친 후 처리하는 선언적 방식이고, 서브쿼리는 여러 단계로 나누어 처리하는 절차적 방식에 가깝습니다.
        
5. **그룹으로 묶인 데이터에 조건을 적용하려면(예: '사원이 3명 이상인 부서'), `WHERE`가 아닌 `HAVING`을 쓰는 이유는 무엇인가요?**
    
    - `WHERE`는 그룹화 전 개별 행을, `HAVING`은 `GROUP BY`로 그룹화된 결과(집계 값)를 필터링하기 때문입니다.

---

### **📚 핵심 개념 3개**

- **조인(Join)**
    - 둘 이상의 테이블에 나뉘어 저장된 데이터를 공통 컬럼을 기준으로 합쳐 하나의 결과 집합으로 만드는 연산.
- **서브쿼리(Subquery)**
    - 다른 SQL문(메인 쿼리)에 포함되어, 메인 쿼리가 사용할 값을 제공하거나 필터링 조건을 구체화하는 `SELECT`문.
- **그룹화 및 필터링 (`GROUP BY` / `HAVING`)**
    - 특정 기준으로 데이터를 그룹화하고(`GROUP BY`), 집계 함수 결과에 대한 조건을 적용(`HAVING`)하여 요약 정보를 추출하는 기법.

[연결맵]

조인(Join) → 서브쿼리(Subquery) → 그룹화 및 필터링 (GROUP BY/HAVING)

(조인으로 데이터 기반을 마련하고, 서브쿼리로 복잡한 조건을 필터링한 뒤, 그룹화로 최종 요약 보고서를 만듭니다.)

### 3) Key SQL/PLSQL 패턴 (Cheatsheet)

- **소스 코드 암호화**: `DBMS_DDL.CREATE_WRAPPED('CREATE … END;');`

- **강제 예외 발생 (방어)**: `RAISE_APPLICATION_ERROR(-20001, '경고메시지');`

    ```SQL
    CREATE VIEW vw_my_profile AS
    SELECT * FROM employee WHERE id = SUBSTR(USER, 5); -- 접속자 ID 기반 필터링
    ```

- **권한 부여**: `GRANT SELECT ON [뷰이름] TO [유저명];`
    

### 4) 오늘의 함정 Top 5

1. **Quotation Hell (따옴표 지옥)**: 1교시 Wrapping 실습 시, 문자열 내부의 따옴표를 `''` 두 개로 처리하지 않아 발생하는 `ORA-01756` 오류.

5. **View 수정 제한**: 뷰를 통해 데이터를 `INSERT/UPDATE` 하려면, 뷰가 단순해야 하며(조인/집계 X) 원본 테이블의 `NOT NULL` 제약 조건을 만족해야 함. (보안상 뷰는 **조회 전용(Read-Only)** 사용을 권장)

### 2) 오늘의 연결고리 (Workflow Context Link)

- **Role(1차 방어)**: 권한 관리를 그룹화하여 효율적으로 접근을 제어했지만, 권한이 있는 내부자의 악의적 행위는 막을 수 없습니다.
- **Audit(2차 감시)**: 따라서 `AUDIT` 설정을 통해 "누가, 언제, 무엇을 했는지" 로그(`DBA_AUDIT_TRAIL`)를 남겨 사후 추적성을 확보했습니다.
- **Encryption(3차 보호)**: 만약 DB 파일 자체가 탈취되더라도 내용을 볼 수 없도록, 중요 컬럼(주민번호)을 **AES256 알고리즘으로 암호화**하여 저장하는 최종 보호 조치를 수행했습니다.
    

### 3) Key SQL/PLSQL 패턴 (Cheatsheet)

- **감사 활성화 (재시작 필수)**

    ```SQL
    ALTER SYSTEM SET AUDIT_TRAIL=DB,EXTENDED SCOPE=SPFILE;
    -- SHUTDOWN IMMEDIATE; -> STARTUP;
    ```
    
- **감사 정책 설정/해제**
    ```SQL
    AUDIT SELECT ON HR.EMPLOYEES BY HR; -- 설정
    NOAUDIT SESSION; -- 해제
    ```
    
- **암호화 함수 (Core Logic)**

    ```SQL
    DBMS_CRYPTO.encrypt(
        src => UTL_RAW.cast_to_raw(평문),
        typ => DBMS_CRYPTO.encrypt_aes256 + DBMS_CRYPTO.chain_cbc + DBMS_CRYPTO.pad_pkcs5,
        key => UTL_RAW.cast_to_raw('32바이트_길이의_키_필수')
    );
    ```
    
- **데이터 타입 변환**
    - `UTL_RAW.cast_to_raw('문자열')`: VARCHAR2 → RAW (암호화 입력용)
    - `UTL_RAW.cast_to_varchar2('RAW데이터')`: RAW → VARCHAR2 (복호화 출력용)
        

### 4) 오늘의 함정 Top

1. **DB 재시작 누락**: `AUDIT_TRAIL` 파라미터는 `SCOPE=SPFILE` 전용이므로, 변경 후 DB를 껐다 켜지 않으면(`SHUTDOWN`→`STARTUP`) 감사가 작동하지 않음.
2. **데이터 타입 실수 (VARCHAR2 vs RAW)**: 암호화된 결과는 바이너리(`RAW`)입니다. 이를 일반 `VARCHAR2` 컬럼에 억지로 넣으면 데이터가 깨지거나 에러가 발생합니다.
3. **AES256 키 길이**: AES256을 쓴다면 키 길이는 정확히 **32Byte(256bit)**여야 합니다. (1글자라도 틀리면 `ORA-28234` 발생).
4. **권한 부족**: `DBMS_CRYPTO` 패키지는 기본적으로 `SYS` 소유입니다. 일반 계정 사용 시 `SYS`에서 `GRANT EXECUTE ON DBMS_CRYPTO TO 유저명`을 해줘야 합니다.

## 최종 요약 - DB보안 2025.11.17

### 1) 하루 TL;DR

오늘 수업은 **"설계부터 구현까지(End-to-End)"**의 전체 흐름을 관통했습니다. 1교시에는 **SQL Developer Data Modeler**를 사용해 요구사항을 물리적 테이블로 설계하고 DDL로 배포하는 **Forward Engineering**을 수행했으며, 2교시에는 이렇게 구축된 DB를 자바 애플리케이션에서 제어하기 위해 **JDBC 환경(OJDBC Driver, Build Path)**을 구축하고 연결 테스트까지 완료했습니다.

### 2) 오늘의 연결고리 (Workflow Context Link)

> **Design(설계) → Build(구축) → Connect(연동)**

- **Step 1 (Modeler)**: '고객'과 '구매'라는 비즈니스 개념을 **Data Modeler**를 통해 시각적인 **물리 모델(ERD)**로 구체화했습니다.
- **Step 2 (DDL)**: 그림으로 그려진 설계를 `Generate DDL` 기능을 통해 실제 **SQL 코드**로 변환하여 DB에 테이블을 생성했습니다.
- **Step 3 (JDBC)**: 구축된 DB를 외부(Java)에서 사용하기 위해 **OJDBC 드라이버**를 `Build Path`에 등록했습니다.
- **Step 4 (Test)**: Java 코드로 DB에 접속(`Connection`)함으로써, **설계된 데이터가 실제 애플리케이션으로 흐르는 길**을 뚫었습니다.
    

### 3) Key SQL/Java 패턴 (Cheatsheet)

**[Data Modeler]**

- **DDL 생성**: 관계형 모델 캔버스 활성화 → 도구 모음 '원기둥 아이콘(DDL 생성)' 클릭 → `Generate`
- **역공학(Import)**: `파일` → `데이터 모델러` → `임포트` → `데이터 딕셔너리`
    

**[Java JDBC]**

- **드라이버 로딩**:
    ```Java
    Class.forName("oracle.jdbc.driver.OracleDriver");
    ```
    
- **DB 연결 객체 생성**:
    
    
    
    ```Java
    String url = "jdbc:oracle:thin:@localhost:1521:xe"; // 포트/SID 확인
    Connection conn = DriverManager.getConnection(url, "ID", "PW");
    ```
    
- **필수 설정**: 프로젝트 우클릭 → `Build Path` → `Add to Build Path` (단순 파일 복사 X)
    

### 4) 오늘의 함정 Top 4

1. **Build Path 누락 (`ClassNotFoundException`)**
    
    - `lib` 폴더에 `ojdbc.jar`를 복사만 해두고 **Build Path에 추가하지 않아** 드라이버를 못 찾는 경우가 가장 빈번함.
        
2. **복붙 시 따옴표 깨짐 (Syntax Error)**
    
    - 카톡/웹의 코드를 복사할 때 **이중 따옴표(" ")**가 특수문자(Smart Quotes)로 변환되어 들어감. 빨간 줄이 뜨면 지우고 다시 타이핑할 것.
        
3. **접속 정보 불일치 (`ORA-01017`)**
    
    - 예제 코드의 `ID/PW`를 그대로 사용하여 본인의 실습 계정과 맞지 않아 로그인 실패.
        
4. **DDL 생성 시점**
    
    - 모델러에서 `논리 모델`이 아닌 **`관계형 모델(물리)`** 탭이 활성화된 상태여야 DDL 생성 아이콘이 작동함.
## 최종 요약 - DB보안 2025.11.24

### 1) 하루 TL;DR

오늘은 지난 시간의 콘솔 기반 연동을 넘어, **Java Swing(GUI)을 이용한 완전한 DB 관리 프로그램**을 구현했습니다. `JTable`을 통해 데이터를 시각화하고, 버튼 이벤트와 `PreparedStatement`를 연결하여 **CRUD(생성, 조회, 수정, 삭제)**가 실시간으로 DB와 연동되는 **Event-Driven 아키텍처**를 완성했습니다.

### 2) 오늘의 연결고리 (Workflow Context Link)

> **Console Basic → GUI Skeleton → CRUD Logic → Synchronization**

- **Step 1 (Review)**: `Statement`의 보안 취약점(SQL Injection)을 보완하는 **`PreparedStatement`**의 중요성을 재확인했습니다.
- **Step 2 (Structure)**: 교수님이 제공한 `DB_MemTable.java`의 구조(Layout, Listener)를 분석하여 UI와 DB 로직이 어떻게 분리되는지 파악했습니다.
- **Step 3 (Implementation)**: `funSelect`, `funAdd`, `funDel`, `funUpdate` 메서드를 직접 코딩하여 버튼 클릭 시 실제 SQL이 실행되도록 연결했습니다.
- **Step 4 (Sync)**: **"DB에 저장된 데이터"**와 **"화면에 보이는 데이터(JTable)"**의 상태를 일치시키는(동기화) 로직을 중점적으로 다뤘습니다.
    

### 3) Key SQL/Java 패턴 (Cheatsheet)

**[JDBC Logic]**

- **PreparedStatement (보안/성능)**:
    ```Java
    String sql = "INSERT INTO STUDENT VALUES(?, ?, ?)";
    pstmt = con.prepareStatement(sql);
    pstmt.setString(1, "값"); // 1부터 시작
    pstmt.executeUpdate();
    ```
    
- **OracleDataSource (연결)**:

    ```Java
    OracleDataSource ods = new OracleDataSource();
    ods.setURL("jdbc:oracle:thin:@localhost:1521:xe");
    con = ods.getConnection();
    ```
    

**[GUI Sync]**

- **화면 갱신 (DB 성공 후)**:
    
    ```Java
    if (result > 0) {
        model.addRow(new Object[]{id, name, …}); // 조회 없이 즉시 반영
        // 또는 funSelect(); // DB 다시 조회 (데이터 무결성 확실)
    }
    ```
    

### 4) 오늘의 함정 Top 3

1. **선택 없는 삭제/수정 (`ArrayIndexOutOfBounds`)**
    
    - `JTable`에서 행을 클릭하지 않고(`row == -1`) 버튼을 누르면 인덱스 에러 발생. 반드시 `if(row == -1) return;` 처리가 필요함.
        
2. **화면 따로 DB 따로 (동기화 누락)**
    
    - `executeUpdate()`로 DB에는 넣었으나 `model.addRow()`를 안 하면, 사용자는 "왜 버튼을 눌렀는데 안 변하지?"라고 착각함.
        
3. **PK 수정 시도 (`Constraint Violation`)**
    
    - 수정(`Update`) 다이얼로그에서 식별자(PK)인 '학번'을 수정 가능하게 두면 데이터 무결성이 깨짐. 반드시 `setEnabled(false)`로 막아야 함.
