## 정리
# 0. 수업 개요 - DB보안 1교시_2025.11.10

### 오늘의 Workflow

- **Step 1) Role & Privilege Review** (Role 개념 및 부여/회수 복습)
- **Step 2) Database Auditing** (감사 활성화, 설정, 로그 확인, 해제)
- **Step 3) Column Encryption (AES)** (`DBMS_CRYPTO` 패키지를 이용한 암/복호화 함수 구현)
- **Step 4) Auto-Encryption (Conceptual)** (Trigger와 View를 이용한 투명 암호화 시도 및 한계)
    

### 오늘의 실습 연결고리 (Flow Summary)

- **접근 제어(Role) → 감시(Audit) → 데이터 보호(Encryption)**
- 권한 관리로 접근을 통제했더라도, **누가 언제 무엇을 했는지 기록(Audit)**해야 하며, DB 파일이 탈취되더라도 내용을 볼 수 없도록 **중요 데이터(주민번호 등)는 암호화(Encryption)**하여 저장해야 함.
- 마지막으로 매번 함수를 호출하는 불편함을 없애기 위해 **Trigger**를 이용한 자동화를 시도함.

## Step 1. Role & Privilege Review (권한 및 롤 복습)

### Goal & Preconditions

- **Goal**: 개별 권한 부여의 불편함을 해소하기 위한 Role의 개념 재확인.
- **Context**: `CONNECT`, `RESOURCE` 롤의 구성 요소 이해.
    

### Concept

- **Role (롤)**: 사용자에게 부여할 권한들의 집합(Group).
    - 관리 효율성 증대: `GRANT SELECT, INSERT, UPDATE …`를 매번 하는 대신 `GRANT TEAM_A_ROLE TO USER`로 한 번에 처리.
    - **System Role**: `CONNECT` (접속 권한), `RESOURCE` (객체 생성 권한), `DBA` (관리자).
        

### Build & Execute

#### Logic

- 시스템 계정(`SYSTEM`)에서 메타데이터 뷰(`DBA_ROLE_PRIVS`, `DBA_SYS_PRIVS`)를 조회하여 롤에 포함된 권한을 확인한다.
    

#### Code

```SQL
-- 접속: SYSTEM
-- 1. 특정 유저에게 부여된 롤 확인
SELECT * FROM DBA_ROLE_PRIVS WHERE GRANTEE = 'USER01';

-- 2. CONNECT, RESOURCE 롤에 어떤 시스템 권한이 있는지 확인
SELECT * FROM DBA_SYS_PRIVS WHERE GRANTEE IN ('CONNECT', 'RESOURCE');
```

## Step 2. Database Auditing (DB 감사 설정)

### Goal & Preconditions

- **Goal**: 사용자 행동(Login, SQL 실행)을 추적하여 로그로 남긴다.
- **Preconditions**:
    - `SYS` 계정 접속 필요 (파라미터 변경 및 `SHUTDOWN` 권한).
    - SQL Developer보다는 **CMD(명령 프롬프트)** SQLPlus 권장 (DB 재시작 용이).
        

### Concept

- **AUDIT (감사)**: 데이터베이스 사용자의 행동을 감시하고 기록하는 기능.
- **`AUDIT_TRAIL` Parameter**: 감사 로그 저장 위치 설정.
    - `DB`: 데이터베이스 내부 테이블(`SYS.AUD$` 등)에 저장.
    - `OS`: 운영체제 파일로 저장 (XML, Text 등).
    - `NONE`: 감사 비활성화.
- **Audit Types**:
    - **Statement Audit**: 특정 명령(예: `CREATE TABLE`) 감사.
    - **Privilege Audit**: 특정 권한 사용 감사.
    - **Object Audit**: 특정 객체(테이블)에 대한 작업(SELECT, INSERT 등) 감사.
        

### Build & Execute

#### Logic

1. 현재 감사 설정 확인 (`SHOW PARAMETER`).
2. 감사 활성화 (`ALTER SYSTEM` → `SCOPE=SPFILE`).
3. **DB 재시작** (필수).
4. 감사 정책 설정 (`AUDIT … BY …`).
5. 행위 유발 (Target 유저로 접속 및 쿼리 실행).
6. 로그 확인 (`DBA_AUDIT_TRAIL`).
7. Cleanup (`NOAUDIT`, 로그 삭제).
    

#### Code

```SQL
-- 접속: SYS (CMD 권장)

-- 1. 감사 파라미터 확인 및 활성화
SHOW PARAMETER AUDIT_TRAIL; 
-- 결과가 NONE이면 활성화 필요 (DB, EXTENDED는 SQL Text까지 저장)
ALTER SYSTEM SET AUDIT_TRAIL=DB,EXTENDED SCOPE=SPFILE;

-- 2. DB 재시작 (파라미터 적용)
SHUTDOWN IMMEDIATE;
STARTUP;

-- 3. 감사 정책 설정
-- 3-1. 로그인 실패 감사 (세션)
AUDIT SESSION WHENEVER NOT SUCCESSFUL;

-- 3-2. 특정 유저(HR)의 EMPLOYEES 테이블 조회 감사
AUDIT SELECT ON HR.EMPLOYEES BY HR;

-- 접속: HR (행위 유발)
SELECT * FROM EMPLOYEES WHERE ROWNUM <= 5;

-- 접속: SYSTEM/SYS (로그 확인)
-- 전체 감사 로그 확인
SELECT username, timestamp, obj_name, action_name, sql_text 
FROM DBA_AUDIT_TRAIL 
WHERE username = 'HR' 
ORDER BY timestamp DESC;

-- 4. 감사 해제 (Cleanup)
NOAUDIT SESSION;
NOAUDIT SELECT ON HR.EMPLOYEES;
```

#### **Pitfalls**

- ⚠️ **재시작 누락**: `AUDIT_TRAIL` 파라미터는 `SCOPE=SPFILE`로만 변경 가능하므로, DB를 재시작(`SHUTDOWN` -> `STARTUP`)하지 않으면 활성화되지 않음.
- ⚠️ **디스크 용량**: 감사 로그(`AUD$`)가 너무 많이 쌓이면 SYSTEM 테이블스페이스가 꽉 차서 DB가 멈출 수 있음. 주기적인 삭제/백업 필요.

## Step 3. Column Encryption (AES256 암호화)

### Goal & Preconditions

- **Goal**: 민감 정보(주민번호 등)를 평문이 아닌 암호화된 상태로 저장.
- **Preconditions**: `DBMS_CRYPTO` 패키지 사용 권한 필요 (`SYS`에서 `GRANT EXECUTE ON DBMS_CRYPTO TO SYSTEM/USER` 필요).
    

### Concept

- **Symmetric Key (대칭키)**: 암호화와 복호화에 **동일한 키**를 사용하는 방식. (AES, DES 등)
- **Block Cipher Modes**:
    - **CBC (Cipher Block Chaining)**: 이전 블록의 암호문이 다음 블록 암호화에 영향을 줌 (보안성 높음).
    - **Padding**: 데이터 길이가 블록 크기의 배수가 아닐 때 빈 공간을 채우는 규칙 (PKCS5 등).
- **RAW Type**: 암호화된 데이터는 바이너리 형태이므로 `VARCHAR2`가 아닌 `RAW` 타입(또는 `BLOB`)에 저장해야 함.
    

### Build & Execute

#### Logic

1. 암호화 데이터를 저장할 테이블 생성 (Data Type: `RAW`).
2. `DBMS_CRYPTO`를 이용한 암호화(`encrypt_aes`) / 복호화(`decrypt_aes`) 함수 생성.
3. 데이터 삽입 시 암호화 함수 적용.
4. 데이터 조회 시 복호화 함수 적용.
    

#### Code

```SQL
-- 접속: SYSTEM (또는 권한이 있는 사용자)

-- 1. 테이블 생성 (암호문은 RAW 타입 권장)
CREATE TABLE T_USER_SEC (
    USER_ID VARCHAR2(20),
    USER_NAME VARCHAR2(20),
    SSN RAW(2000) -- 암호화된 주민번호 저장 (넉넉하게 2000)
);

-- 2. 암호화/복호화 함수 생성 (교수님 제공 코드 기반)
-- 키 길이는 32Byte (256bit)여야 함.
CREATE OR REPLACE FUNCTION encrypt_aes(p_plain IN VARCHAR2) RETURN RAW IS
    -- 키는 32바이트(AES256)
    l_key RAW(32) := UTL_RAW.cast_to_raw('01234567890123456789012345678901'); 
BEGIN
    IF p_plain IS NULL THEN RETURN NULL; END IF;
    
    RETURN DBMS_CRYPTO.encrypt(
        src => UTL_RAW.cast_to_raw(p_plain),
        typ => DBMS_CRYPTO.encrypt_aes256 
             + DBMS_CRYPTO.chain_cbc 
             + DBMS_CRYPTO.pad_pkcs5,
        key => l_key
    );
END;
/

CREATE OR REPLACE FUNCTION decrypt_aes(p_raw IN RAW) RETURN VARCHAR2 IS
    l_key RAW(32) := UTL_RAW.cast_to_raw('01234567890123456789012345678901');
BEGIN
    IF p_raw IS NULL THEN RETURN NULL; END IF;

    RETURN UTL_RAW.cast_to_varchar2(
        DBMS_CRYPTO.decrypt(
            src => p_raw,
            typ => DBMS_CRYPTO.encrypt_aes256 
                 + DBMS_CRYPTO.chain_cbc 
                 + DBMS_CRYPTO.pad_pkcs5,
            key => l_key
        )
    );
END;
/

-- 3. 테스트
-- 암호화해서 저장
INSERT INTO T_USER_SEC VALUES ('user01', '홍길동', encrypt_aes('900101-1234567'));
COMMIT;

-- 조회 (평문 노출 안됨)
SELECT * FROM T_USER_SEC; 

-- 복호화해서 조회
SELECT USER_ID, decrypt_aes(SSN) as DECRYPTED_SSN FROM T_USER_SEC;
```

#### **Pitfalls**

- ⚠️ **Key Length Mismatch**: AES256을 사용하려면 키 길이가 정확히 256bit(32Byte)여야 함. 짧거나 길면 `ORA-28234` 등의 에러 발생.
- ⚠️ **Data Type Mismatch**: `DBMS_CRYPTO`는 `RAW` 타입을 반환함. 테이블 컬럼을 `VARCHAR2`로 하면 데이터가 깨지거나 저장이 안 될 수 있음. (`RAW` 권장).

## Step 4. Auto-Encryption with Trigger (Advanced/Conceptual)

### Goal & Preconditions

- **Goal**: 애플리케이션(개발자)이 명시적으로 `encrypt_aes()`를 호출하지 않아도, `INSERT` 시 자동으로 암호화되도록 구현.
- **Result**: 실습 환경(패키지 권한, `DBMS_CRYPTO` 설치 문제) 이슈로 인해 **실패**했으나, 개념과 로직은 중요함.
    

### Concept

- **Trigger**: DML(Insert/Update/Delete) 발생 전후에 자동으로 실행되는 PL/SQL 블록.
- **View**: 복호화된 데이터를 보여주는 가상의 테이블.
- **Architecture**:
    
    1. `Table` (실제 저장소): 암호화된 데이터(`RAW`) 저장.
    2. `Trigger`: `BEFORE INSERT` 시 평문을 암호문으로 변환하여 저장.
    3. `View`: `SELECT` 시 암호문을 복호화하여 평문으로 보여줌.
        

### Build & Execute (Conceptual Logic)

#### Logic

1. 테이블은 `VARCHAR2`로 입력을 받지만 실제 저장은 `RAW`로 해야 하므로, 보통 뷰를 통해 입력을 받거나(INSTEAD OF Trigger), 컬럼 타입을 맞추는 과정이 필요함.
2. 트리거 로직: `:NEW.ssn := encrypt_aes(:NEW.ssn);`
3. 뷰 로직: `SELECT decrypt_aes(ssn) FROM table;`
    
사용자가 평문으로 `INSERT` 하면 트리거가 자동으로 암호화하고, 조회 시 뷰(View)가 자동으로 복호화합니다. 저장 타입이 `VARCHAR2`로 변경됩니다.

#### 1) 자동화용 테이블 생성

트리거 처리를 위해 암호화 컬럼을 `VARCHAR2` 타입으로 생성합니다.

```SQL
CREATE TABLE secure_table2 (
    id NUMBER PRIMARY KEY,
    name VARCHAR2(50),
    ssn_raw VARCHAR2(2000) -- RAW 값을 HEX 문자열로 변환해 저장하기 위해 VARCHAR2 사용
);
```

#### 2) 자동 암호화 트리거 생성 (`trg_encrypt_ssn`)

데이터가 삽입(`INSERT`)되거나 수정(`UPDATE`)되기 직전(`BEFORE`)에 자동으로 동작합니다. `RAWTOHEX` 함수를 사용하여 RAW 데이터를 16진수 문자열로 변환해 저장합니다.

```SQL
CREATE OR REPLACE TRIGGER trg_encrypt_ssn
BEFORE INSERT OR UPDATE ON secure_table2
FOR EACH ROW
BEGIN
    IF :NEW.ssn_raw IS NOT NULL THEN
        -- 입력받은 평문을 암호화 후, HEX 문자열로 변환하여 저장
        :NEW.ssn_raw := RAWTOHEX(encrypt_aes(:NEW.ssn_raw));
    END IF;
END;
/
```

#### 3) HEX 복호화 래퍼(Wrapper) 함수 생성 (`decrypt_aes_hex`)

문자열로 저장된 HEX 값을 다시 RAW로 변환(`HEXTORAW`)한 뒤 복호화하는 보조 함수입니다.

```SQL
CREATE OR REPLACE FUNCTION decrypt_aes_hex(p_hex IN VARCHAR2) RETURN VARCHAR2 IS
BEGIN
    IF p_hex IS NULL THEN
        RETURN NULL;
    END IF;
    -- HEX 문자열 -> RAW 변환 -> 복호화 수행
    RETURN decrypt_aes(HEXTORAW(p_hex));
END;
/
```

#### 4) 자동 복호화 뷰(View) 생성 (`secure_table_v`)

사용자가 조회할 때 복호화 함수를 매번 쓰지 않도록, 미리 함수가 적용된 뷰를 만듭니다.

```SQL
CREATE OR REPLACE VIEW secure_table_v AS
SELECT id, name, decrypt_aes_hex(ssn_raw) AS ssn
FROM secure_table2;
```

#### 5) 자동화 테스트

평문으로 입력해도 트리거가 암호화해주고, 뷰를 통해 조회하면 복호화된 결과가 나옵니다.

```SQL
-- 1. 평문으로 INSERT (트리거가 작동하여 자동 암호화됨)
INSERT INTO secure_table2 (id, name, ssn_raw)
VALUES (1, '홍길동', '900101-1234567');
COMMIT;

-- 2. 실제 테이블 조회 (암호화된 16진수 문자열 확인)
SELECT * FROM secure_table2;

-- 3. 뷰(View)를 통해 조회 (자동 복호화된 결과 확인)
SELECT * FROM secure_table_v;
```
#### **Pitfalls (Build Log: Why it failed)**

- ⚠️ **System vs User Privileges**: `DBMS_CRYPTO` 패키지는 `SYS` 소유이며, 일반 유저나 `SYSTEM`에게 명시적인 `GRANT EXECUTE`가 없으면 프로시저/트리거 내부에서 호출 시 권한 부족 에러 발생.
- ⚠️ **Trigger Limitations**: 트리거 내부에서는 `SELECT` 트랜잭션 처리에 제약이 있으며, 데이터 타입 변환(`VARCHAR2` ↔ `RAW`) 과정에서 `HEXTORAW` 등의 추가 처리가 필요할 수 있음.

## 기타 핵심 (Etc & Tips) - DB보안 2025.11.10

- **RAW vs VARCHAR2**: 암호화된 이진 데이터를 DB에 저장할 때 `VARCHAR2`를 쓰면 인코딩 문제로 데이터 손실이 발생할 수 있음. 반드시 `RAW`나 `BLOB`을 사용하거나, `RAWTOHEX()`로 16진수 문자열로 변환하여 저장해야 함.
- **Audit File Location**: OS Audit 설정 시 로그 파일은 보통 `$ORACLE_BASE/admin/{SID}/adump` 경로에 `.aud` 확장자로 저장됨.
    

### Prof’s Comment

> "트리거 생성은 루트(SYS)에서는 막혀 있어서 못 하고, 시스템(SYSTEM)에서 하려니 패키지 권한이 꼬여서 실습이 잘 안 됐네요. 하지만 **실무에서는 개발자가 직접 암호화 함수를 호출하는 것보다, 뷰와 트리거를 통해 투명하게 처리하는 방식(TDE 등)을 선호**한다는 개념을 알아두세요."
