# 0. 수업 개요 - DB보안 1교시_2025.10.27

### 공지사항

- 기존 프로시저/함수 시험 범위 이후, **보안 관점(암호화)**에서 프로시저를 다루는 실습 추가됨.
- 새로운 교안(카톡 전달)의 `userTBL` 사용.

### 오늘의 Workflow

- Step 1) 실습 환경 구축 (회원 테이블 생성 및 데이터 삽입)
- Step 2) 평문 프로시저 작성 (이름 마스킹 출력)
- Step 3) **Source Code Wrapping** (프로시저 소스 코드 암호화)
- Step 4) `USER_SOURCE`를 통한 소스 코드 노출 여부 검증
    

### 오늘의 실습 연결고리 (Flow Summary)

- 프로시저로 민감 정보(이름)를 마스킹하여 보여주는 로직을 짰더라도, **DBA나 해커가 `USER_SOURCE`를 조회하면 마스킹 로직(소스 코드) 자체가 평문으로 노출됨**.
- 따라서 **소스 코드 자체를 난독화(Wrapping)** 하여 로직을 숨기는 보안 기법(`DBMS_DDL.CREATE_WRAPPED`)을 적용함.

## Step 2. 평문 프로시저 작성 (데이터 마스킹) - DB보안 1교시_2025.10.27

### Goal & Preconditions

- 입력받은 ID에 해당하는 회원의 이름을 조회하되, **첫 글자만 노출하고 나머지는 'OO' 등으로 마스킹**하여 출력하는 프로시저 작성.
- `SET SERVEROUTPUT ON` 필수.
### Concept

- **%TYPE**: 특정 테이블 컬럼의 데이터 타입을 그대로 참조. 컬럼 속성이 변경(예: VARCHAR2(10) -> (20))되어도 프로시저 코드를 수정할 필요가 없어 유지보수성이 높음.
- **SUBSTR**: 문자열 자르기 함수. `SUBSTR(문자열, 시작위치, 길이)`.
### Build & Execute

#### Logic

1. 사용자 ID를 입력(`IN`) 받음.
2. `userTBL`에서 해당 ID의 이름과 생년을 조회하여 변수에 저장.
3. 이름의 첫 글자만 자르고(`SUBSTR`) 뒤에 마스킹 문자(`**` 등)를 붙임(`||`).
4. `DBMS_OUTPUT.PUT_LINE`으로 결과 출력.

#### Code

```SQL
-- 출력 결과 확인을 위해 필수
SET SERVEROUTPUT ON;

CREATE OR REPLACE PROCEDURE pro_user_info
    ( p_userID IN userTBL.userID%TYPE ) -- 입력 변수
IS
    v_userName userTBL.userName%TYPE; -- 내부 변수 (이름)
    v_birthYear userTBL.birthYear%TYPE; -- 내부 변수 (생년)
BEGIN
    -- 1. 데이터 조회 (Select Into)
    SELECT userName, birthYear
    INTO v_userName, v_birthYear
    FROM userTBL
    WHERE userID = p_userID;

    -- 2. 마스킹 처리 및 출력 (예: 조용필 -> 조00)
    -- SUBSTR(이름, 1, 1) : 첫글자 추출
    DBMS_OUTPUT.PUT_LINE(
        SUBSTR(v_userName, 1, 1) || '00 (' || v_birthYear || ')'
    );
END;
/
-- 워크시트에서 '/'는 PL/SQL 블록 종료 및 실행(컴파일)을 의미
```

#### **Pitfalls**

- ⚠️ **ORA-01403: no data found**: `p_userID`에 해당하는 사용자가 없을 때 발생. (실습에선 예외처리 생략됨).
- ⚠️ **컴파일 오류**: 변수 선언 시 `;` 누락, 혹은 `INTO` 절 순서 불일치.
    

### 검증

```SQL
-- 실행 (JYP 유저 조회)
EXEC pro_user_info('JYP');
-- 기대 결과: 조00 (1950)
```

> 🗣️ 핵심 답변
>
> 데이터 무결성 유지와 유지보수 효율성 때문입니다.
>

> - **Example**: `v_name userTBL.userName%TYPE`으로 선언하면 DB 설계 변경에 유연하게 대처 가능합니다.

## Step 3. Source Code Wrapping (소스 코드 암호화) - DB보안 1교시_2025.10.27

### Goal & Preconditions

- Step 2에서 만든 프로시저는 `USER_SOURCE` 뷰를 조회하면 소스 코드가 다 보임.
- **Dynamic SQL**과 **`DBMS_DDL.CREATE_WRAPPED`** 패키지를 사용하여 소스 코드 자체를 난독화하여 재생성함.
    

### Concept

- **DBMS_DDL.CREATE_WRAPPED**: PL/SQL 소스 코드를 인자로 받아, 내용을 난독화(Wrapping)한 상태로 컴파일하는 오라클 내장 패키지.
- **Wrapping(래핑)**: 소스 코드를 바이너리 형태에 가깝게 변환하여 사람이 읽을 수 없게 만듦 (단, 실행은 정상적으로 됨).
    

### Build & Execute

#### Logic

1. `v_code`라는 긴 문자열 변수에 프로시저 생성 구문(CREATE PROCEDURE…) 전체를 텍스트로 담음.
2. 이때 작은따옴표(`'`) 안에 또 작은따옴표를 넣기 위해 이스케이프 처리가 필요함.
3. `BEGIN … END;` 블록 안에서 `DBMS_DDL.CREATE_WRAPPED(v_code)`를 호출하여 즉시 실행.
    

#### Code

```SQL
-- 접속: Test User

DECLARE
    v_code VARCHAR2(3000); -- 소스 코드를 담을 변수
BEGIN
    -- 문자열 연결 연산자(||)를 사용해 쿼리 조립
    -- 주의: 문자열 내부의 따옴표는 '' (2개)로 처리해야 함
    v_code := 'CREATE OR REPLACE PROCEDURE pro_user_wrap ' ||
              ' ( p_userID IN userTBL.userID%TYPE ) ' ||
              ' IS ' ||
              '   v_userName userTBL.userName%TYPE; ' ||
              '   v_birthYear userTBL.birthYear%TYPE; ' ||
              ' BEGIN ' ||
              '   SELECT userName, birthYear ' ||
              '   INTO v_userName, v_birthYear ' ||
              '   FROM userTBL ' ||
              '   WHERE userID = p_userID; ' ||
                  -- 아래 부분이 중요: 마스킹 로직을 숨기기 위함
              '   DBMS_OUTPUT.PUT_LINE(SUBSTR(v_userName, 1, 1) || ''**'' || '' ('' || v_birthYear || '')''); ' ||
              ' END; ';
              
    -- 래핑(암호화)하여 프로시저 생성
    DBMS_DDL.CREATE_WRAPPED(v_code);
END;
/
```

#### **Pitfalls**

- ⚠️ **Quotation Hell**: Dynamic SQL 작성 시 가장 큰 실수는 따옴표 처리임.
    - `DBMS_OUTPUT` 내부의 문자열 `'**'`를 표현하려면 `''**''`로 써야 함.
    - 오타 발생 시 `ORA-01756` (문자열이 제대로 닫히지 않음) 발생 빈번.
        

### 검증

1. **기능 실행 검증** (암호화되어도 실행은 잘 되는가?)
    

```SQL
SET SERVEROUTPUT ON;
EXEC pro_user_wrap('JYP');
-- 결과: 조** (1950) -> 정상 실행됨
```

1. **소스 코드 보안 검증** (소스가 보이는가?)
    

```SQL
-- 시스템 뷰에서 소스 조회
SELECT name, text
FROM USER_SOURCE
WHERE name = 'PRO_USER_WRAP'
ORDER BY line;
```

- **결과 확인**: `text` 컬럼에 `CREATE OR REPLACE PROCEDURE … wrapped … abcd123…` 처럼 알 수 없는 난수표가 출력되어야 성공.

>

- **`USER_SOURCE`**: 현재 계정이 소유한 프로시저, 함수, 트리거 등의 소스 코드를 저장하는 Data Dictionary View.

- **새로고침(Refresh)**: 좌측 접속 창의 [Procedures] 폴더에서 우클릭 > 새로고침 해야 방금 만든 프로시저가 보인다.

## Step 4. 보안 검증 (Data Dictionary 조회) - DB보안 1교시_2025.10.27

### Goal & Preconditions

- 생성된 프로시저가 시스템 카탈로그(데이터 사전)에 어떻게 저장되는지 확인.
- **평문 프로시저**와 **Wrapped 프로시저**의 저장 형태 차이 확인.
    

### Concept

- **USER_SOURCE**: 현재 접속한 사용자가 생성한 PL/SQL 객체(프로시저, 함수, 패키지, 트리거 등)의 **소스 코드 텍스트**를 줄 단위(`TEXT`)로 저장하고 있는 데이터 사전 뷰.
- **Data Dictionary (시스템 카탈로그)**: DB의 메타데이터(테이블 정보, 유저 정보, 소스 코드 등)가 저장된 읽기 전용 테이블들의 집합.
    

### Build & Execute

#### Logic

1. `USER_SOURCE` 뷰에서 방금 만든 프로시저(`PRO_USER_WRAP`)를 조회한다.
2. `TEXT` 컬럼의 내용이 읽을 수 없는 난수표(Hex String 등) 형태로 변환되었는지 확인한다.
    

#### Code

```SQL
-- 1. 평문 프로시저 확인 (Step 2에서 만든 것)
-- 소스 코드가 그대로 보임 (보안 취약점 확인)
SELECT line, text
FROM USER_SOURCE
WHERE name = 'PRO_USER_INFO'
ORDER BY line;

-- 2. 암호화된 프로시저 확인 (Step 3에서 만든 것)
-- 'wrapped' 키워드와 함께 읽을 수 없는 문자열로 출력됨
SELECT line, text
FROM USER_SOURCE
WHERE name = 'PRO_USER_WRAP'
ORDER BY line;
```

#### **Pitfalls**

- ⚠️ **객체 이름 대문자**: 오라클 데이터 사전(`USER_SOURCE`)에서 `NAME` 컬럼은 기본적으로 **대문자**로 저장됩니다.
    - `WHERE name = 'pro_user_wrap'` (소문자) → 조회 안 됨.
    - `WHERE name = 'PRO_USER_WRAP'` (대문자) → **조회 됨**.
        

### 검증

- **성공 기준**: `PRO_USER_WRAP` 조회 시 첫 줄에 `create or replace procedure pro_user_wrap wrapped` 문구가 보이고, 그 이후 내용이 암호문으로 출력되어야 함.

>

## 기타 핵심 (Etc & Tips) - DB보안 2025.10.27

### 1. Dynamic SQL 문자열 조합 시 주의사항 (Concatenation)

- 강의 중 "`n 퍼센티지` 연결 연산자", "오아(OR)" 등의 발음이 섞여 있으나, 정확한 SQL 문법은 **파이프 2개(`||`)**입니다.
- **Tip**: 문자열을 연결할 때 코드가 길어지면 가독성이 떨어지므로, `v_code` 변수에 한 줄씩 `||`로 붙여나가는 방식을 권장합니다.
    
    
    
    ```SQL
    v_code := '첫줄' ||
              '두번째줄' ||
              '세번째줄';
    ```
    

### 2. SQL Developer GUI 갱신

- **문제**: 프로시저를 생성했는데 왼쪽 [접속] 패널의 [프로시저] 목록에 바로 안 뜰 수 있습니다.
- **해결**: [프로시저] 폴더 우클릭 → **[새로고침(Refresh)]**을 해야 반영됩니다. Wrapped 된 프로시저도 목록에는 뜨지만, 클릭해서 내용을 보면 암호화된 텍스트가 보입니다.
    

### Prof’s Comment

> "과제 올릴 때는 보안 처리된(암호화된) 실행 결과가 보이게 캡처해서 올려주시면 됩니다. 관리자도 암호화된 내용으로 확인되어야 정상입니다."
>
> "이제 코딩이 조금씩 길어집니다. 다음으로 트리거(Trigger) 들어갈게요."

# 0. 수업 개요 - DB보안 2교시_2025.10.27
1교시의 `Procedures`가 "명시적 실행"이라면, 2교시의 `Trigger`는 "자동 실행"되는 보안 도구입니다.
### 공지사항

- **Cursor(커서)**: 개념 설명(파일 포인터와 유사, `OPEN`->`FETCH`->`CLOSE`)만 하고 실습은 생략. (DB 수업 내용 복습 차원)
- **시험 관련**: 정보처리 기사 실기 등에서 트리거는 개념 위주, 프로시저는 구현 위주로 출제되는 경향 언급.
    

### 오늘의 Workflow

- Step 1) Trigger 기본 구조 이해 (테스트 테이블 및 단순 출력)
- Step 2) **Audit Logging** 구현 (변경 전 데이터 백업 트리거)
- Step 3) **Access Control** 구현 (강제 예외 발생으로 입력 차단)
    

### 오늘의 실습 연결고리 (Flow Summary)

- 트리거의 기본 동작 확인(`DBMS_OUTPUT`) → 실제 보안 업무인 **"누가 언제 데이터를 수정/삭제했는가?"(감사 로그)** 구현 → 더 나아가 **"특정 시간/조건에 작업을 아예 못하게 막기"**(보안 차단)로 심화.

## Step 1. Trigger Hello World (기본 동작 확인) - DB보안 2교시_2025.10.27

### Goal & Preconditions

- `testTBL`을 만들고, 데이터 변경(`UPDATE`, `DELETE`) 이벤트 발생 시 자동으로 메시지를 출력하는 트리거를 생성하여 동작 원리를 파악한다.
- `SET SERVEROUTPUT ON` 필수.
    

### Concept

- **Trigger(트리거)**: 테이블에 특정 이벤트(INSERT, UPDATE, DELETE)가 발생했을 때 **DBMS가 자동으로 실행**하는 저장 프로시저의 일종.
- **FOR EACH ROW**: 문장(Statement) 단위가 아니라, 변경되는 **각 행(Row)마다** 트리거를 실행하겠다는 의미. (예: 5행 업데이트 시 5번 실행)
    

### Build & Execute

#### Logic

1. 테스트용 테이블(`testTBL`) 생성 및 데이터 입력.
2. `AFTER UPDATE OR DELETE` 이벤트를 감지하는 트리거 생성.
3. `UPDATE`나 `DELETE` 수행 시 "트리거가 작동했습니다" 메시지 출력 확인.
    

#### Code

```SQL
-- 접속: Test User

-- 1. 테스트 테이블 준비
DROP TABLE testTBL; -- 기존에 있다면 삭제
CREATE TABLE testTBL (id NUMBER, text NVARCHAR2(10));

INSERT INTO testTBL VALUES(1, '아이브');
INSERT INTO testTBL VALUES(2, '블랙핑크');
INSERT INTO testTBL VALUES(3, '방탄소년단');
COMMIT;

-- 2. 트리거 생성 (기본 문법)
CREATE OR REPLACE TRIGGER trg_test
    AFTER DELETE OR UPDATE ON testTBL -- 이 테이블에서 삭제/수정 후에 동작
    FOR EACH ROW                      -- 각 행마다 실행
BEGIN
    DBMS_OUTPUT.PUT_LINE('트리거가 작동했습니다.');
END;
/

-- 3. 동작 확인
SET SERVEROUTPUT ON;

-- 업데이트 실행 (1건) -> 메시지 1번 출력 예상
UPDATE testTBL SET text = 'IVE' WHERE id = 1;

-- 딜리트 실행 (1건) -> 메시지 1번 출력 예상
DELETE FROM testTBL WHERE id = 2;
```

#### **Pitfalls**

- ⚠️ **메시지 미출력**: `SET SERVEROUTPUT ON`을 하지 않으면 트리거는 돌았어도 화면에 아무것도 안 보임.
- ⚠️ **UPDATE/DELETE 조건**: `WHERE` 절 없이 업데이트하면 모든 행이 변경되므로, 데이터 건수만큼 트리거 메시지가 와르르 쏟아짐 (`FOR EACH ROW` 때문).
    

### 검증

- `UPDATE` 수행 직후 "트리거가 작동했습니다" 문구가 Script Output 창에 뜨는지 확인.
    

### 💡 Interview

> [!faq]- Q. Trigger의 실행 시점인 BEFORE와 AFTER의 차이는 무엇인가요?
>
> 🗣️ 핵심 답변
>
> 실제 데이터가 테이블에 반영되기 **전(BEFORE)**에 로직을 수행할지, 반영된 **후(AFTER)**에 수행할지의 차이입니다.
>
> **📚 꼬리질문 대비**
>
> - **Use Case**: **BEFORE**는 데이터 유효성 검사나 값 자동 보정(예: 데이터 삽입 전 대문자 변환)에 쓰이고, **AFTER**는 주로 로깅(Logging)이나 연쇄 작업(Cascading)에 사용됩니다.
>

## Step 2. Audit Logging (데이터 감사 로그 구축) - DB보안 2교시_2025.10.27

### Goal & Preconditions

- **`userTBL`**(1교시 생성)의 데이터가 수정되거나 삭제될 때, 변경 전의 원본 데이터를 **`backup_userTBL`**에 자동으로 저장하는 **백업(감사) 시스템**을 구축한다.
- **필수 개념**: `:OLD` 변수 사용법.
    

### Concept

- **Pseudo Records (:OLD / :NEW)**: 트리거 내부에서만 사용할 수 있는 가상 레코드.
    - **:OLD**: 변경 **전**의 데이터 (UPDATE 전 값, DELETE 되는 값).
    - **:NEW**: 변경 **후**의 데이터 (UPDATE 후 값, INSERT 되는 값).
- **Audit Trail(감사 추적)**: 누가(`USER`), 언제(`SYSDATE`), 무엇을 했는지 기록하여 보안 사고 발생 시 추적 가능하게 함.
    

### Build & Execute

#### Logic

1. 로그를 담을 `backup_userTBL` 생성 (구조는 `userTBL` + 감사 컬럼 3개).
2. `userTBL`에 트리거 부착.
3. `IF UPDATING`: 수정 시 `:OLD` 데이터를 백업하고 타입은 '수정'으로 기록.
4. `IF DELETING`: 삭제 시 `:OLD` 데이터를 백업하고 타입은 '삭제'로 기록.
    

#### Code

```SQL
-- 1. 백업(로그) 테이블 생성
CREATE TABLE backup_userTBL (
    userID      CHAR(8)       NOT NULL, -- PK 아님(중복 로그 허용)
    userName    NVARCHAR2(10) NOT NULL,            
    birthYear   NUMBER(4)     NOT NULL,            
    addr        NCHAR(2)      NOT NULL,            
    mobile1     CHAR(3),                            
    mobile2     CHAR(8),                            
    height      NUMBER(3),                          
    mDate       DATE,                                
    modType     NCHAR(2),       -- 변경 타입 (수정/삭제)
    modDate     DATE,           -- 변경 일시
    modUser     NVARCHAR2(256)  -- 변경 수행자 (계정명)
);

-- 2. 감사 트리거 생성
CREATE OR REPLACE TRIGGER trg_backupUser
    AFTER UPDATE OR DELETE ON userTBL
    FOR EACH ROW
BEGIN
    -- 업데이트 발생 시
    IF UPDATING THEN
        INSERT INTO backup_userTBL VALUES (
            :OLD.userID, :OLD.userName, :OLD.birthYear, :OLD.addr, 
            :OLD.mobile1, :OLD.mobile2, :OLD.height, :OLD.mDate,
            '수정', SYSDATE, USER
        );
    END IF;

    -- 삭제 발생 시
    IF DELETING THEN
        INSERT INTO backup_userTBL VALUES (
            :OLD.userID, :OLD.userName, :OLD.birthYear, :OLD.addr, 
            :OLD.mobile1, :OLD.mobile2, :OLD.height, :OLD.mDate,
            '삭제', SYSDATE, USER
        );
    END IF;
END;
/
```

#### **Pitfalls**

- ⚠️ **PK 제약조건**: 백업 테이블(`backup_userTBL`)에는 `PRIMARY KEY`를 걸면 안 됨. 한 명의 유저가 여러 번 수정될 수 있으므로 userID가 중복 저장되어야 함.
- ⚠️ **컬럼 매칭**: `INSERT INTO … VALUES` 사용 시 `userTBL`의 컬럼 순서와 `backup_userTBL`의 컬럼 순서/개수가 정확히 일치해야 함.
    

### 검증

```SQL
-- 1. 데이터 수정 (이승기 -> 키 변경)
UPDATE userTBL SET height = 185 WHERE userID = 'LSG';

-- 2. 데이터 삭제 (김범수 삭제)
DELETE FROM userTBL WHERE userID = 'KBS';

-- 3. 백업 테이블 확인 (로그가 남았는지)
SELECT * FROM backup_userTBL;
-- 결과: LSG는 '수정', KBS는 '삭제' 타입으로 기존 정보가 남아있어야 함.
```

### 💡 Interview

> [!faq]- Q. 트리거 내에서 :OLD와 :NEW는 각각 어느 작업(INSERT/UPDATE/DELETE)에서 사용할 수 있나요?
>
> 🗣️ 핵심 답변
>
> - **INSERT**: 입력될 새 값이므로 **:NEW**만 존재합니다.
>     
> - **UPDATE**: 변경 전(**:OLD**)과 변경 후(**:NEW**) 값이 모두 존재합니다.
>     
> - **DELETE**: 삭제될 값이므로 **:OLD**만 존재합니다.
>

## Step 3. Access Control (입력 차단 및 예외 발생) - DB보안 2교시_2025.10.27

### Goal & Preconditions

- 특정 테이블(`userTBL`)에 새로운 데이터 입력(`INSERT`)을 시도하면, **경고 메시지를 띄우고 입력을 강제로 막는(Rollback)** 보안 트리거를 작성한다.
- 기존 트리거 삭제 필요 (충돌 방지 및 성능 고려).
    

### Concept

- **RAISE_APPLICATION_ERROR**: 사용자 정의 예외를 강제로 발생시키는 프로시저.
    - 에러 코드: `-20000` ~ `-20999` 사이의 값 사용.
    - 실행 시 트랜잭션이 중단되고 자동 롤백됨.
        

### Build & Execute

#### Logic

1. 기존 트리거 정리(삭제).
2. `BEFORE INSERT` 트리거 생성 (데이터가 들어가기 **전**에 막아야 함).
3. 트리거 내부에서 `RAISE_APPLICATION_ERROR` 호출.
    

#### Code



```SQL
-- 1. 기존 트리거 삭제 (실습 혼선 방지)
DROP TRIGGER trg_backupUser;

-- 2. 입력 차단 트리거 생성
CREATE OR REPLACE TRIGGER trg_insert_block
    BEFORE INSERT ON userTBL -- 입력하기 '전'에 동작
    FOR EACH ROW
BEGIN
    -- 에러 발생 (번호는 -20000 ~ -20999 사용자 지정)
    RAISE_APPLICATION_ERROR(-20001, '⚠️ [보안 경고] 데이터 입력이 차단되었습니다!');
END;
/
```

#### **Pitfalls**

- ⚠️ **AFTER vs BEFORE**: 차단이 목적이라면 `BEFORE`가 효율적임. `AFTER`를 써도 `RAISE_ERROR`가 나면 롤백되긴 하지만, 불필요한 작업 후 롤백하는 셈.
- ⚠️ **트리거 오버헤드**: 강의에서 교수님이 강조함. 트리거가 너무 많으면 모든 DML 작업마다 실행되어 DB 성능이 느려짐. 테스트 후엔 반드시 삭제(`DROP`)할 것.
    

### 검증



```SQL
-- 신규 입력 시도
INSERT INTO userTBL VALUES ('NEW', '신규', 2000, '서울', NULL, NULL, 180, SYSDATE);
-- 결과: ORA-20001: ⚠️ [보안 경고] 데이터 입력이 차단되었습니다! 에러 발생하며 입력 실패.
```

### Goal & Preconditions

- 실습 목적으로 생성한 트리거들을 삭제하여 DB 성능 오버헤드를 방지한다.

### Build & Execute

#### Code

-- 접속: Test User

SELECT trigger_name, status 
FROM user_triggers;

-- 2. 트리거 삭제
DROP TRIGGER trg_insert_block;
-- (앞서 만들었던 다른 트리거들도 필요 시 삭제)
-- DROP TRIGGER trg_backupUser; 
-- DROP TRIGGER trg_test;

-- 3. 확인 (입력이 다시 정상적으로 되는지)

## 기타 핵심 (Etc & Tips) - DB보안 2025.10.27

### 1. `INSTEAD OF` Trigger

- 강의 중 짧게 언급된 개념.
- 일반적인 테이블이 아니라 **뷰(View)**에 사용됩니다.
- 뷰는 원래 직접적인 INSERT/UPDATE가 제한적인데, `INSTEAD OF` 트리거를 달면 "뷰에 업데이트를 시도했을 때, 실제로는 베이스 테이블을 업데이트해라"라는 식으로 동작을 가로채서 처리할 수 있습니다.
    

### 2. 커밋(Commit)과 세미콜론(;)

- 강의 후반부 트러블 슈팅: `COMMIT`만 쓰고 실행하면 간혹 툴에서 인식이 안 될 때가 있음.
- **습관**: `COMMIT;` (반드시 세미콜론 포함)으로 명령을 종결짓는 습관을 들일 것.
    

### 3. GUI 생성 방식

- SQL Developer 좌측 [접속] 패널 -> [트리거] 폴더 우클릭 -> [새 트리거]를 선택하면 마법사(GUI) 형태로 생성 가능.
- 하지만 시험이나 현업 스크립트 관리를 위해 DDL(`CREATE TRIGGER…`) 문법을 외우는 것이 중요.
    

### Prof’s Comment

> "트리거가 보안 처리하는 데 많이 쓰입니다. 특히 **감사 로그(Audit Log)**를 남길 때, 누가 언제 데이터를 건드렸는지 '몰래' 기록하는 용도로 핵심적입니다. 하지만 너무 많이 쓰면 느려지니 꼭 필요한 곳에만 쓰세요."

# 0. 수업 개요 - DB보안 3교시_2025.10.27
3교시 강의는 **DB 보안의 핵심인 View(뷰)**를 다룹니다. 단순히 쿼리를 저장하는 용도를 넘어, 사용자(User)별로 **보여줄 데이터(Column)와 범위(Row)를 제한**하는 강력한 접근 제어 도구로서의 뷰를 실습합니다.
### 오늘의 Workflow

- Step 1) View 생성 권한 부여 (`SYSTEM` 계정 작업)
- Step 2) 보안 실습 환경 구축 (`employee2` 테이블 및 역할별 계정 생성)
- Step 3) **Security View** 작성 (Row-level & Column-level Security 구현)
- Step 4) 권한 부여(Grant) 및 접속 테스트(Verification)
    

### 오늘의 실습 연결고리 (Flow Summary)

- 앞선 교시에서 테이블 자체를 암호화하거나 로그를 남겼다면, 이번에는 **"보여줘도 되는 것만 보여주는 가상 테이블(View)"**을 만듭니다.
- 특히 **'내 정보만 보기'**, **'민감 컬럼(주민번호) 숨기기'** 등 실무적인 보안 요구사항을 뷰와 계정 권한(`GRANT`)을 결합하여 해결합니다.

## Step 1. View 생성 권한 부여 - DB보안 3교시_2025.10.27

### Goal & Preconditions

- `VIEW` 생성은 아무나 할 수 없는 **시스템 권한(System Privilege)**입니다.
- 실습 계정(Test User)에게 `CREATE VIEW` 권한을 부여해야 합니다.
    

### Build & Execute

#### Logic

1. **관리자(SYSTEM)** 계정으로 접속 전환.
2. 실습할 사용자(예: `TEST_USER` 또는 본인 이니셜 계정)에게 `CREATE VIEW` 권한 부여.
    

#### Code

```SQL
-- 접속: SYSTEM (관리자)

-- 사용자에게 뷰 생성 권한 부여
-- (TEST_USER 부분에 본인이 실습 중인 계정명 입력)
GRANT CREATE VIEW TO TEST_USER;
```

#### **Pitfalls**

- ⚠️ **ORA-01031: insufficient privileges**: `CREATE VIEW` 권한 없이 뷰를 생성하려 할 때 발생. 반드시 `SYSTEM` 계정에서 `GRANT` 해줘야 함.
- ⚠️ **GUI 체크**: SQL Developer에서 `사용자 편집 > 시스템 권한` 탭에서 `CREATE VIEW`를 체크해도 동일한 효과임.

## Step 2. 보안 실습 환경 구축 (Table & User) - DB보안 3교시_2025.10.27

### Goal & Preconditions

- 보안 요구사항:
    
    1. **일반 직원**: 본인 정보만 조회 가능 (타인 정보 불가).
    2. **인사팀(HR)**: 주민번호(SSN)를 제외한 모든 사원 정보 조회 가능.
    3. **관리자(Admin)**: 모든 정보(주민번호 포함) 조회 가능.
        
- 이를 위해 `employee2` 테이블을 만들고, 3개의 테스트 계정(`EMP_1001`, `HR_USER`, `ADMIN_USER`)을 생성합니다.
    

### Build & Execute

#### Logic

1. `Test User` 접속: 원본 데이터가 담길 `employee2` 테이블 생성 및 데이터 삽입.
2. `SYSTEM` 접속: 실습용 부계정 3개 생성 및 접속 권한(`CONNECT`) 부여.
    

#### Code



```SQL
-- 접속: Test User (데이터 소유자)

-- 1. 원본 테이블 생성 (주민번호 SSN 포함)
DROP TABLE employee2;
CREATE TABLE employee2 (
    emp_id        NUMBER PRIMARY KEY,
    name          VARCHAR2(100),
    department    VARCHAR2(50),
    position      VARCHAR2(50),
    salary        NUMBER,
    ssn           VARCHAR2(20)  -- 민감 정보
);

-- 2. 데이터 삽입
INSERT INTO employee2 VALUES (1001, '김민수', '인사부', '대리', 4200000, '900101-1234567');
INSERT INTO employee2 VALUES (1002, '이서연', '재무부', '과장', 5300000, '880512-2345678');
-- … (나머지 데이터는 제공된 스크립트 참조)
COMMIT;

----------------------------------------------------

-- 접속: SYSTEM (관리자)

-- 3. 역할별 계정 생성
-- 일반 직원 (EMP_1001)
CREATE USER EMP_1001 IDENTIFIED BY 1234 ACCOUNT UNLOCK;
GRANT CONNECT TO EMP_1001;

-- 인사팀 (HR_USER)
CREATE USER HR_USER IDENTIFIED BY 1234 ACCOUNT UNLOCK;
GRANT CONNECT TO HR_USER;

-- 관리자 (ADMIN_USER)
CREATE USER ADMIN_USER IDENTIFIED BY 1234 ACCOUNT UNLOCK;
GRANT CONNECT, DBA TO ADMIN_USER; 
```

## Step 3. Security View 작성 (Row/Column Security) - DB보안 3교시_2025.10.27

### Goal & Preconditions

- 각 계정의 역할에 맞는 **맞춤형 뷰(View)** 3개를 생성합니다.
- **Row-level Security**: `WHERE` 절을 통해 특정 행만 보이게 함.
- **Column-level Security**: `SELECT` 절에서 특정 컬럼(SSN)을 제외함.
    

### Concept

- **USER (System Variable)**: 현재 접속한 사용자의 계정명(ID)을 반환하는 오라클 내장 변수.
- **Data Masking via View**: 뷰에서 아예 민감 컬럼을 `SELECT` 하지 않으면, 사용자는 해당 컬럼의 존재조차 알 수 없거나 접근할 수 없음.
    

### Build & Execute

#### Logic

1. **일반 직원용 뷰 (`vw_my_profile`)**:
    
    - 현재 접속자(`USER`)가 `EMP_1001`이라면, 뒤의 숫자 `1001`만 추출하여 `emp_id`와 비교.
    - 본인 행(Row)만 조회되도록 필터링.
        
2. **인사팀용 뷰 (`vw_hr_view`)**:
    
    - `ssn` 컬럼을 제외하고 나머지 컬럼만 선택.
        
3. **관리자용 뷰 (`vw_admin_view`)**:
    
    - 모든 컬럼(`*`) 포함.
        

#### Code



```SQL
-- 접속: Test User (데이터 소유자)

-- 1. 일반 직원용 뷰 (Row-level Security)
-- 내 정보만 보기: 접속 계정명에서 사번 추출하여 매칭
CREATE OR REPLACE VIEW vw_my_profile AS
SELECT emp_id, name, department, position, salary, ssn
FROM employee2
WHERE emp_id = TO_NUMBER(SUBSTR(USER, 5)); 
-- 설명: USER가 'EMP_1001'일 때, SUBSTR(USER, 5)는 '1001'.
-- 즉, WHERE emp_id = 1001 이 되어 내 것만 보임.

-- 2. 인사팀용 뷰 (Column-level Security)
-- 주민번호(ssn) 제외
CREATE OR REPLACE VIEW vw_hr_view AS
SELECT emp_id, name, department, position, salary
FROM employee2;

-- 3. 관리자용 뷰
-- 모든 정보 열람 가능
CREATE OR REPLACE VIEW vw_admin_view AS
SELECT * FROM employee2;
```

#### **Pitfalls**

- ⚠️ **타입 불일치**: `SUBSTR`의 결과는 문자열, `emp_id`는 숫자. 오라클이 자동 형변환을 해주지만, 명시적으로 `TO_NUMBER`를 쓰는 것이 안전함.
- ⚠️ **뷰 수정 제한**: 뷰를 통해 `INSERT/UPDATE`를 하려면 뷰가 단순해야 하며(조인 X, 집계함수 X), 원본 테이블의 `NOT NULL` 제약조건 등을 만족해야 함. (강의에서는 조회용으로 권장)
    

### 💡 Interview

> [!faq]- Q. View를 사용하는 보안상의 이점은 무엇인가요? (일반 테이블 권한 부여와 비교)
>
> 🗣️ 핵심 답변
>
> 테이블 전체 권한을 주면 민감한 행이나 열까지 모두 노출되지만, View는 보여줄 컬럼과 행을 미리 필터링하여 그 결과 집합에만 권한을 부여할 수 있어 **최소 권한의 원칙(Principle of Least Privilege)**을 준수할 수 있습니다.
>
> **📚 꼬리질문 대비**
>
> - **Example**: 인사팀에게 '사원 테이블' 권한을 주는 대신, '주민번호가 빠진 사원 뷰'에 권한을 주어 개인정보 유출을 막습니다.
>

## Step 4. 권한 부여 및 검증 (Grant & Verify) - DB보안 3교시_2025.10.27

### Goal & Preconditions

- 생성된 3개의 뷰를 각각의 대상 사용자에게 `SELECT` 권한을 부여(`GRANT`)하고, 실제 접속하여 의도대로 보이는지 확인한다.
    

### Build & Execute

#### Logic

1. `Test User`에서 각 뷰에 대한 `SELECT` 권한을 해당 사용자에게 부여.
2. 각 사용자로 접속(`CONN`)하여 뷰 조회 (`SELECT * FROM TEST_USER.VIEW_NAME`).
    
    - _주의_: 다른 사용자의 객체를 조회할 때는 `스키마명.객체명` 포맷을 써야 함.
        

#### Code



```SQL
-- 접속: Test User

-- 1. 권한 부여 (Grant)
-- 일반 직원 -> vw_my_profile
GRANT SELECT ON vw_my_profile TO EMP_1001;
-- 인사팀 -> vw_hr_view
GRANT SELECT ON vw_hr_view TO HR_USER;
-- 관리자 -> vw_admin_view
GRANT SELECT ON vw_admin_view TO ADMIN_USER;

----------------------------------------------------
-- 검증 테스트 (SQL Developer 워크시트 혹은 CMD)

-- Case A: 일반 직원 접속 (EMP_1001 / 1234)
-- CONN EMP_1001/1234; (CMD 창에서 빠른 접속)
SELECT * FROM TestUser.vw_my_profile;
-- 결과: 김민수(1001) 데이터 1건만 나와야 성공.

-- Case B: 인사팀 접속 (HR_USER / 1234)
SELECT * FROM TestUser.vw_hr_view;
-- 결과: 5건 모두 나오지만, 'SSN' 컬럼은 아예 없어야 성공.

-- Case C: 관리자 접속 (ADMIN_USER / 1234)
SELECT * FROM TestUser.vw_admin_view;
-- 결과: 5건 모두 나오고, 'SSN' 컬럼도 보여야 성공.
```

### 💡 Interview

> [!faq]- Q. GRANT SELECT ON View를 했는데 사용자가 조회가 안 된다고 합니다. 원인은?
>
> 🗣️ 핵심 답변
>
> 사용자가 뷰 이름 앞에 스키마(소유자) 명을 붙이지 않았거나, 해당 뷰의 Base Table(원본 테이블)에 대한 권한 체인 문제가 있을 수 있습니다.
>
> **📚 꼬리질문 대비**
>
> - **Solution**: `SELECT * FROM 원본소유자.뷰이름` 형태로 쿼리해야 하며, 편의를 위해 **Synonym(동의어)**을 생성해주기도 합니다.
>

## 기타 핵심 (Etc & Tips) - DB보안 2025.10.27

- **`WITH CHECK OPTION`**: 뷰 생성 시 이 옵션을 붙이면, 뷰의 `WHERE` 조건에 위배되는 데이터로 `UPDATE`나 `INSERT` 하는 것을 방지함. (강의 중 짧게 언급)
- **접속 팁 (`/`)**: SQLPlus나 CMD에서 `CONN 유저명/비번` 입력 시 슬래시를 사용하면 한 줄에 입력 가능.
- **스키마 명시**: 뷰를 생성한 건 `TEST` 계정이므로, 다른 계정(`HR_USER` 등)에서 조회할 때는 반드시 `TEST.뷰이름`으로 접근해야 함.
