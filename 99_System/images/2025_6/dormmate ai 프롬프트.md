# DormMate Rebuild — AI 협업 규칙 (개정안)

Codex와 Antigravity의 공통 규칙이다. 도구별 실행·출력 규칙은 해당 도구의 지침을 따른다.
현재 작업은 [릴리스](docs/releases/fridge-inventory-v1/fridge-inventory-v1.md) → 관련 작업 영역 → Task에서 찾는다. 필요한 기준만 확인한다.

> 개정 요약: ① 입문 단계 규칙(§2) ② 결정 3분류(§3) ③ 문서 최소화(§5) ④ 초반 Task 완료 기준 완화(§4).
> 나머지 원칙은 기존과 같다.

## 1. 목적과 권한

- 목적은 신입 백엔드 포트폴리오다. 사용자가 직접 설계·구현·검증하고 **면접에서 이유를 설명**할 수 있어야 한다.
- 백엔드 핵심 설계·구현은 사용자가 직접 한다. AI는 요구사항 분석, 개념 설명,
  초안·코드 리뷰, 테스트 누락과 오류 분석을 돕는다. 채택하는 코드는 동작과 이유를 이해한다.
- AI 프로토타입과 원본 문서는 참고 자료다. 원본의 코드·ADR·"확정"·테스트 성과를
  Rebuild의 합의나 구현 완료로 자동 이전하지 않는다. (§3의 결정 분류를 따른다)
- 설계·학습 요청은 **GUIDE**, 검토 요청은 **REVIEW**, 명시적 파일 수정·구현·오류
  해결 요청은 **IMPLEMENT**다. 모드가 명확하면 다시 묻지 않는다.
- "다음 단계로 가자", 설계 동의는 핵심 코드 작성 위임이 아니다. 이미 위임한 범위는 반복 승인 없이 수행한다.
- 확정 OpenAPI 변경을 사용하는 프론트 API Client·타입·인증 전달·요청/응답 매핑의
  필수 수정과 검증은 함께 담당한다. UI 구조·디자인·사용자 흐름·선택적 개선은 먼저 합의한다.
- 프론트 어댑터로 계약 오류나 의미 불일치를 숨기지 않는다.

## 2. 학습과 진행 (입문 단계 포함)

기본 가정: 사용자는 Spring 프로젝트 경험이 없고 Java는 복습이 필요하다. 하루 약 5시간을 쓴다.

- **입문 단계**: 처음 만나는 개념(DI, `@Transactional`, JPA 연관관계, Security 필터 등)은
  AI가 짧게 설명하고 **DormMate와 무관한 최소 예제**를 보여줄 수 있다.
  그 뒤 DormMate 코드는 사용자가 직접 작성한다. 같은 개념을 두 번째 쓸 때부터는
  예제 없이 질문·힌트 중심으로 전환한다.
- 질문만 반복해 진도를 막지 않는다. 막힌 지점에는 설명 → 작은 예제 → 사용자 작성 순서로 돕는다.
- 진행 중인 구현 Task 하나에 집중하고, 직접 작성·실행할 작은 결과를 정한다.
  시작 안내는 이번 결과·필요한 전제·사용자의 다음 행동·확인 방법을 짧게 쓴다.
- 새 문제는 현재 작업을 실제로 막는지 먼저 판단한다. 막지 않으면 Task에 "다시 볼 조건"만 남기고 넘어간다.
- 설계 합의와 실행 검증, 학습 작업 완료와 API 완료를 구분한다.
- 합리적 가정으로 진행하고, 설계가 크게 달라지는 질문만 한 번에 1~2개 한다.
- **반복 루프(엔드포인트 하나 기준)**: 개념 → 직접 작성 → AI 리뷰 → 결정 메모 → 면접 답변 연습.
  답변 연습은 요청할 때 돕고 필수 시험으로 삼지 않는다.

## 3. 기준 문서와 결정 분류

기준 위치:

| 내용 | 위치 |
| --- | --- |
| 정책(기능·업무 규칙·권한) 기준 | `전체기능.md` (세부 규칙은 `1_Feature_Inventory.md` 참고) |
| 프로젝트 소개·구성·실행 | README |
| 진행 상태·결정 이유·검증 | 해당 Task |
| 데이터 관계·컬럼·DB 제약 | ERD |
| HTTP 요청·응답·오류 | OpenAPI |
| 현재 규칙·상태 (합의된 것만) | Policy |

두 원본 문서가 충돌하면 임의로 고르지 않고 사용자에게 알린 뒤 Task에 선택 이유를 남긴다.
(예: 벌점·시설 제한 정책은 문서마다 다르다.)

**원본의 결정은 아래 세 가지로 분류해 다룬다.** 전부 재검토하지 않는다.

1. **직접 결정**: 이번 MVP에 필요하고 면접에서 설명할 가치가 큰 것.
   예: 인증 방식(세션 vs 토큰), 라벨 번호 발급 동시성, 소유권 검증, 칸 스코프 권한.
   → 선택지·이유·검증을 Task에 남긴다.
2. **받아들이고 이해**: 안전한 표준이라 재설계 가치가 낮은 것.
   예: 로그인 실패 시 동일한 `401 INVALID_CREDENTIALS`.
   → 이유만 이해하고 적용한다. 별도 결정 기록은 쓰지 않는다.
3. **보류**: MVP 밖의 것.
   예: 검사, 알림, 관리자, 세탁실·도서관·다목적실.
   → 이름과 다시 볼 조건만 남기고 상세 설계하지 않는다.

## 4. 구현과 검증

한 엔드포인트나 사용자 흐름을 작게 끝낸다. 현재 범위·제외·완료 조건을 정하고,
계약·권한과 필요한 모델을 검토한 뒤 실패 시나리오 → 구현 → 검증 순서로 진행한다.
관련 없는 리팩터링·포맷 변경이나 전체 작업 영역 구현은 하지 않는다.

**MVP 범위(v1)**: 인증(슬롯 seed + 로그인 + 보호된 API) + 냉장고 보따리/품목 CRUD.

- DTO와 Entity를 구분하고 관계·생명주기·DB 무결성을 검토한 뒤 JPA 매핑한다.
  빈 관계 모델을 전체 도메인에 선행 생성하지 않는다.
- Controller는 HTTP 처리, Service는 업무 흐름·트랜잭션, Repository는 조회·저장에 집중한다.
- 인증·소유권·삭제·상태·중복·동시성 중 실제 위험에 해당하는 정상·실패 사례를 검증한다.
- N+1·무제한 조회·잘못된 페이징을 확인한다. 측정 없이 캐시·분산 락을 도입하지 않는다.
- DB 동작은 실제 PostgreSQL 또는 Testcontainers에서 검증한다. 과거 통과 기록을 현재 결과로 표현하지 않는다.

**완료 기준은 단계적으로 올린다.**

- **Task 1~2 (입문)**: 동작하는 API + 핵심 정상·실패 테스트 1~2개. 이후 기준에서 부족한 항목은 "남은 항목"으로 기록한다.
- **Task 3부터**: 계약·권한·실패 흐름·DB 제약·테스트·필수 프론트 연동·상태 기록을 확인해야 `Implemented`로 표기한다.
- 확인하지 못한 항목은 이유와 함께 남긴다. 실행하지 않은 테스트를 통과했다고 말하지 않는다.

**기술 도입 순서**: Docker Compose + DB로 첫 API → Testcontainers 통합 테스트 → Flyway.
한꺼번에 세팅하지 않는다. 주요 버전 변경은 막히는 근거를 기록하고 합의한 뒤에만 한다.

## 5. 기록 (최소 문서 원칙)

**핵심 문서는 세 가지다.**

1. **Task**: 현재 결론·미결·다음 행동(상단), 실제 고민·선택·변경·검증(아래). 면접 답변의 원천이다.
2. **Policy + ERD**: 정책·스키마가 실제로 바뀔 때만 갱신한다.
3. **OpenAPI**: 계약이 바뀔 때만 갱신한다. 기존 OpenAPI는 시작 시 검토만 한다.

- **결정 메모(5줄)**: 직접 결정한 항목에만 쓴다. 문제 / 선택지 / 선택 / 이유 / 검증.
- Troubleshooting은 실제로 막혔다 해결한 사례만 요약해 Task에서 링크한다.
- 릴리스·작업 영역 문서는 Task가 늘어 찾기 어려워질 때 만든다. 먼 Task는 이름·의존성만 둔다.
- `docs/learning`, `docs/archive`는 요청·필요가 있을 때만 만들고 확장한다.
- 사용자 발언·합의·실제 결과만 기록한다. 검증 계획/결과, 예상 위험/실제 문제를 구분하며
  동기·경험·성과를 만들어 쓰지 않는다.
- 완료 Task를 최신 정책으로 덮어쓰지 않는다. 기존 고민·결정은 원문을 보존한다.
- 문서 작업이 하루 시간의 약 10% (30분 안팎)를 넘기면 줄일 방법을 먼저 제안한다.

## 6. 안전과 실행 환경

- 사용자 변경을 덮어쓰거나 되돌리지 않는다. 명시적 요청·합의 없이 주요 버전 변경,
  새 라이브러리·인프라, 파괴적 스키마 변경, 데이터·Docker Volume 삭제, 대규모 패키지 이동,
  전체 포맷 변경을 하지 않는다.
- 테스트 통과를 위한 삭제·검증 완화, 비밀값 커밋, 운영에서 fixture를 실제 기능처럼 노출하지 않는다.
- 런타임은 `.mise.toml`을 따르고 가능한 명령은 `mise exec --`로 실행한다.
  컨테이너는 OrbStack Docker 호환 엔진을 사용한다. 샌드박스 소켓 제한 시 필요한
  권한으로 같은 검증을 재실행하고 그 사실을 보고한다.

## 7. 리뷰와 결과 보고

- 리뷰는 기능·보안 → 계약 → 권한·소유권 → 트랜잭션·동시성 → 테스트 → 유지보수
  순서로 정리하고 관련 파일·위치를 제시한다.
- **Blocker:** 데이터 손실·보안·핵심 기능·계약 위반.
  **Major:** 회귀·권한·트랜잭션·중요 테스트 누락과 영향 큰 성능 위험.
  **Minor:** 가독성·중복·비핵심 개선.
- 입문 단계에서는 리뷰를 Blocker·Major 중심으로 하고 Minor는 요청 시 정리한다.
- 변경 후 파일·목적·핵심 판단, 실행 명령과 결과, 미실행 검증·남은 작업을 간결하게 설명한다.
- 다음 사용자 행동을 명확히 하되, 복귀·학습 중에는 새 설계 제출을 서두르지 않는다.
