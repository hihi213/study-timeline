### 📢 수업 공지

- **중간고사 성적 확인:** 쉬는 시간을 이용하여 성적 확인이 가능합니다.
- **강의 계획 변경:** 기존 `PROCEDURE` 및 `FUNCTION` 범위에서 **'DB 암호화(Encryption)'** 실습 예제가 추가되었습니다. (새로운 교안 참고)
- **향후 일정:** 오늘 암호화 기초를 시작으로 `TRIGGER`를 활용한 로그 기록, `VIEW`와 `INDEX`를 활용한 보안 기법을 순차적으로 진행합니다.

### 🛡️ 보안 맥락 분석 (Security Context)

#### 1. 데이터 마스킹 (Data Masking)

- **보안 위협:** `SELECT` 권한이 있는 사용자가 고객의 실명, 주민번호 등 민감 정보(PII)를 그대로 열람할 위험이 있습니다.
- **대응 정책:** 데이터베이스 레벨에서 **프로시저(Procedure)** 를 통해 데이터를 가공하여 출력합니다.
- **구현 논리:** `SUBSTR` 함수 등을 사용하여 이름의 첫 글자만 남기고 나머지를 특수문자(`**` 등)로 치환하여 출력합니다. (예: `JYP` → `조**`)
    

#### 2. 소스 코드 난독화/암호화 (PL/SQL Wrapping)

- **보안 위협:** 악의적인 내부자나 개발자가 비즈니스 로직이 담긴 프로시저의 소스 코드(`USER_SOURCE`)를 조회하여 로직을 탈취하거나 변조할 수 있습니다.
- **대응 정책:** DDL 문을 실행할 때 평문(Plain Text)이 아닌 암호화된 형태로 컴파일되도록 처리합니다.
- **구현 논리:**
    - Oracle의 `DBMS_DDL` 패키지(또는 래퍼 유틸리티)를 활용합니다.
    - 강의에서는 DDL 구문 전체를 문자열 변수에 담아 동적 SQL(`EXECUTE IMMEDIATE`) 혹은 암호화 함수로 처리하여, `USER_SOURCE` 테이블 조회 시 코드가 해석 불가능한 16진수/특수문자 조합으로 보이게 만듭니다.

### 📝 강의 내용 정제

#### 1. 실습 환경 구성 (User Table Setup)

- 보안 실습을 위해 제공된 `userTBL` 스크립트를 실행합니다.
- **주요 절차:**
    
    1. 기존 테이블이 있다면 삭제 (`DROP TABLE`).
    2. `CREATE TABLE`로 회원 테이블 생성.
    3. `INSERT` 문으로 10건의 샘플 데이터(이승기, 김범수 등) 적재.
    4. `COMMIT`으로 트랜잭션 확정.
        

#### 2. 프로시저를 이용한 데이터 조회 및 마스킹

- **기본 문법 복습:**
    - `%TYPE`: 테이블의 특정 컬럼과 동일한 데이터 타입을 변수에 할당할 때 사용 (유지보수성 향상).
    - `IN/OUT`: 프로시저의 매개변수 모드.
- **마스킹 로직:**
    - 입력받은 `userID`에 해당하는 회원의 이름을 조회.
    - `SUBSTR(name, 1, 1) || '**'` 와 같은 형태로 가공하여 출력.
        

#### 3. 동적 SQL을 활용한 프로시저 암호화 (Wrapping)

- **문자열 연결 (Concatenation):**
    - 프로시저 생성 구문(`CREATE OR REPLACE PROCEDURE…`) 전체를 하나의 긴 문자열 변수(`source`)에 담습니다.
    - Oracle의 연결 연산자 `||` (강의 중 '오아', 'n퍼센티지'로 언급된 부분)를 사용하여 여러 줄의 코드를 하나로 합칩니다.
- **암호화 실행:**
    - 단순 문자열 실행이 아니라, `DBMS_DDL.WRAP` 혹은 관련 암호화 메소드를 통해 소스 코드를 난독화하여 생성합니다.
- **결과 검증:**
    - `SELECT text FROM USER_SOURCE WHERE name = '프로시저명';` 조회 시, 원본 SQL이 아닌 암호화된 문자열이 출력됨을 확인합니다.

## 개념 - DB보안 1교시_2025.10.27

### 1. 핵심 용어 (Terminology)

#### **① 데이터 마스킹 (Data Masking)**

- **정의:** 데이터베이스 내의 민감한 정보(개인정보, 카드번호 등)를 인가되지 않은 사용자에게 보여줄 때, 일부를 가리거나 변조하여 식별할 수 없게 만드는 기법입니다.
- **구현 방식:**
    - **정적 마스킹(Static):** 원본 데이터 자체를 변조하여 저장 (테스트 DB 구축 시 사용).
    - **동적 마스킹(Dynamic):** 데이터는 원본 그대로 두되, `SELECT` 하여 보여주는 시점에 프로시저나 함수(`SUBSTR` 등)를 통해 가공하여 출력. (금일 수업 방식)
        

#### **② PL/SQL 래핑 (Wrapping/Obfuscation)**

- **정의:** PL/SQL 소스 코드(프로시저, 함수 등)를 평문(Plain Text)이 아닌 **알아볼 수 없는 형태(16진수 코드 등)**로 변환하여 DB에 저장하는 기술입니다.
- **목적:**
    - **지적 재산권 보호:** 개발된 비즈니스 로직을 제3자가 복제하지 못하도록 방지.
    - **무결성 보장:** 악의적인 내부자나 해커가 소스 코드를 분석하여 로직을 변조하는 것을 방지.
- **확인:** `USER_SOURCE` 뷰를 조회했을 때 코드가 난독화되어 보입니다.
    

---

### 2. SQL 패턴 (Syntax Pattern)

#### **① 타입 참조 (%TYPE)**

변수 선언 시, 하드코딩하지 않고 특정 테이블의 컬럼 타입을 그대로 상속받습니다.



```SQL
v_variable_name  Table_Name.Column_Name%TYPE;
-- 예: v_id  userTBL.userID%TYPE;
```

#### **② 부분 문자열 추출 (SUBSTR - 마스킹용)**

문자열의 특정 부분만 남기고 나머지는 가립니다.



```SQL
SUBSTR(컬럼명, 시작위치, 길이) || '**'
-- 예: SUBSTR(userName, 1, 1) || '**' -> '이**'
```

#### **③ 동적 SQL 실행 (Dynamic SQL)**

런타임에 SQL 문장을 문자열로 완성하여 실행하거나, 암호화 래퍼를 호출합니다.



```SQL
-- 문자열로 DDL 구성 후 실행
EXECUTE IMMEDIATE 'CREATE … '; 

-- (심화) 래핑 유틸리티 패키지 활용
DBMS_DDL.CREATE_WRAPPED( … );
```

## 질문 - DB보안 1교시_2025.10.27

<details>

<summary>Q1. PL/SQL 변수 선언 시 '%TYPE' 속성을 사용하는 이유는?</summary>

  

[🗣️ 핵심 요약]

특정 테이블의 컬럼 데이터 타입을 그대로 **참조(Reference)**하여 변수를 선언하는 속성입니다. 테이블의 컬럼 타입이 변경되어도 프로시저 코드를 수정할 필요가 없어 유지보수성이 높아집니다.

  
  

[📚 상세 설명]

- **문법:** `v_name userTBL.userName%TYPE;`
- **장점:** 만약 `userTBL`의 `userName`이 `VARCHAR2(10)`에서 `VARCHAR2(20)`으로 변경되더라도, `%TYPE`을 쓰면 변수 선언부를 일일이 고칠 필요가 없습니다.
- 시험 포인트: 교수님께서 "시험에 냈던 내용"이라고 강조하셨으며, 직접 타입을 명시(VARCHAR2 등)해도 틀린 건 아니지만 %TYPE 사용이 권장됩니다.
    
    </details>
    

<details>

<summary>Q2. 프로시저의 소스 코드(로직)를 보안상 숨기려면 어떻게 해야 하는가?</summary>

  

[🗣️ 핵심 요약]

일반적인 CREATE PROCEDURE로 생성하면 USER_SOURCE 뷰에서 누구나 소스를 볼 수 있습니다. 이를 방지하기 위해 코드를 **난독화(Wrapping)**하거나 암호화하여 컴파일해야 합니다.

  
  

[📚 상세 설명]

- **Wrapping:** 오라클의 `wrap` 유틸리티나 `DBMS_DDL` 패키지를 사용하여 사람이 읽을 수 없는 16진수/특수문자 형태로 변환합니다.
- **실습 방식:** 강의에서는 SQL 구문을 문자열 변수에 담고, 이를 암호화 함수(`DBMS_DDL` 관련)를 통해 처리하거나 동적으로 실행하여 소스가 평문으로 남지 않도록 했습니다.
- 확인: SELECT text FROM USER_SOURCE WHERE name = &#39;프로시저명&#39;; 실행 시 알 수 없는 문자열이 출력되면 성공입니다.
    
    </details>
    

<details>

<summary>Q3. DB 내부에서 '홍길동'을 '홍**'으로 마스킹(Masking)하는 기본 원리는?</summary>

  

[🗣️ 핵심 요약]

문자열 조작 함수인 SUBSTR을 사용하여 보여줄 부분만 잘라내고, 나머지 부분은 연결 연산자(||)를 사용하여 특수문자(*)와 결합합니다.

  
  

[📚 상세 설명]

- **SQL 패턴:** `SUBSTR(컬럼명, 1, 1) || &#39;**&#39;`
    - `SUBSTR(…, 1, 1)`: 첫 번째 글자부터 1글자만 추출 ('홍').
    - `|| &#39;**&#39;`: 뒤에 별표 두 개를 붙임 ('홍**').
- 활용: 뷰(View)나 프로시저(Procedure)의 출력 단계에서 적용하여, 애플리케이션 개발자가 원본 데이터를 볼 수 없게 차단합니다.
    
    </details>

## 실습 - DB보안 1교시_2025.10.27

### S#1. 실습 환경 구성 (User Table Setup)

#### **1. Scenario & Goal**

보안 실습을 진행하기 위해 회원 테이블(`userTBL`)을 생성하고, 교수님께서 제공해주신 샘플 데이터(가수 정보) 10건을 적재합니다.

#### **2. SQL Implementation**

```SQL
-- 1. 기존 테이블 정리 (Clean Up)
DROP TABLE userTBL CASCADE CONSTRAINTS;

-- 2. 테이블 생성
CREATE TABLE userTBL (
    userID    CHAR(8)       NOT NULL PRIMARY KEY, -- 사용자 ID
    userName  NVARCHAR2(10) NOT NULL,             -- 이름
    birthYear NUMBER(4)     NOT NULL,             -- 출생년도
    addr      NCHAR(2)      NOT NULL,             -- 지역
    mobile1   CHAR(3),
    mobile2   CHAR(8),
    height    NUMBER(3),
    mDate     DATE                                -- 가입일
);

-- 3. 데이터 삽입 (Sample Data)
INSERT INTO userTBL VALUES ('LSG', '이승기', 1987, '서울', '011', '11111111', 182, TO_DATE('2008-08-08', 'YYYY-MM-DD'));
INSERT INTO userTBL VALUES ('JYP', '조용필', 1950, '경기', '011', '44444444', 166, TO_DATE('2009-04-04', 'YYYY-MM-DD'));
-- (나머지 데이터 생략, 필요시 전체 스크립트 실행)

COMMIT;
```

---

### S#2. 데이터 마스킹 프로시저 (Basic Masking)

#### **1. Scenario & Goal**

`SELECT` 권한이 있는 사용자가 데이터를 조회할 때, 이름의 첫 글자만 남기고 나머지는 `**`로 가려지도록 처리합니다. 테이블의 컬럼 타입이 변경되어도 유연하게 대응하기 위해 `%TYPE`을 사용합니다.

#### **2. SQL Implementation**

```SQL
-- 출력 결과 확인을 위해 서버 출력 활성화
SET SERVEROUTPUT ON;

CREATE OR REPLACE PROCEDURE proc_view_user (
    p_id IN userTBL.userID%TYPE  -- 입력: 조회할 ID (테이블 타입 참조)
) 
IS
    -- 변수 선언: 테이블 컬럼 타입을 그대로 상속 (%TYPE)
    v_name userTBL.userName%TYPE;
    v_year userTBL.birthYear%TYPE;
BEGIN
    -- 1. 데이터 조회
    SELECT userName, birthYear 
    INTO v_name, v_year
    FROM userTBL 
    WHERE userID = p_id;

    -- 2. 마스킹 처리 및 출력 (이름 첫 글자 + '**')
    DBMS_OUTPUT.PUT_LINE('--------------------------');
    DBMS_OUTPUT.PUT_LINE('ID   : ' || p_id);
    DBMS_OUTPUT.PUT_LINE('Name : ' || SUBSTR(v_name, 1, 1) || '**'); -- 마스킹 핵심 로직
    DBMS_OUTPUT.PUT_LINE('Year : ' || v_year);
    DBMS_OUTPUT.PUT_LINE('--------------------------');

EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('❌ 해당 ID의 사용자가 존재하지 않습니다.');
END;
/
```

```SQL
    v_source VARCHAR2(32767); -- 소스 코드를 담을 변수

    -- 주의: 문자열 내부의 작은 따옴표(')는 두 번('') 써야 이스케이프 처리됨
    v_source := 'CREATE OR REPLACE PROCEDURE proc_secure_wrap IS ' ||
                'BEGIN ' ||
                '   DBMS_OUTPUT.PUT_LINE(''🔒 이 코드는 암호화되었습니다.''); ' ||
                '   DBMS_OUTPUT.PUT_LINE(''소스 보기를 해도 내용을 알 수 없습니다.''); ' ||
                'END;';

    -- SYS.DBMS_DDL.CREATE_WRAPPED: 평문 DDL을 암호화된 형태로 컴파일하는 시스템 패키지
```

### [🛡️ 보안 맥락 분석 (Security Context)]

#### 1. 감사 로그 자동화 (Audit Logging)

- **보안 위협:** 악의적인 내부자나 해커가 데이터를 무단으로 수정(`UPDATE`)하거나 삭제(`DELETE`)할 경우, 누가 언제 어떤 데이터를 건드렸는지 추적하기 어렵습니다.
- **대응 정책:** **트리거(Trigger)**를 사용하여 데이터 변경 이벤트 발생 시, 변경 전 데이터(`:OLD`)와 수행자 정보를 별도의 백업 테이블(`backup_userTBL`)에 자동으로 기록합니다.

#### 2. 비인가 행위 강제 차단 (Access Control via Error)

- **보안 위협:** 특정 테이블(예: 이력 관리 테이블)에는 데이터가 추가(`INSERT`)되면 안 되는 보안 정책이 있을 수 있습니다.
- **대응 정책:** `INSERT` 시도가 감지되면 트리거를 통해 강제로 시스템 에러(`RAISE_APPLICATION_ERROR`)를 발생시켜 트랜잭션을 롤백(Rollback) 시킵니다.

### [📝 강의 내용 정제]

#### 1. 커서 (CURSOR) - _개념 참조_

- **정의:** `SELECT` 결과가 여러 행(Row)일 때, 파일 포인터처럼 한 줄씩 읽어 내려가며 처리하는 방식입니다.
- **흐름:** `DECLARE`(선언) → `OPEN`(메모리 적재) → `FETCH`(한 줄 읽기) → `CLOSE`(해제).
    

#### 2. 트리거 (TRIGGER) 기초

- **정의:** 특정 테이블에 DML(`INSERT`, `UPDATE`, `DELETE`) 이벤트가 발생했을 때, DBMS가 자동으로 실행하는 저장 프로시저(Stored Program)의 일종입니다.
- **주요 문법:**
    - **Timing:** `BEFORE` (처리 전), `AFTER` (처리 후 - 주로 사용), `INSTEAD OF` (뷰 전용).
    - **Scope:** `FOR EACH ROW` (영향받는 각 행마다 실행).
    - **Pseudo Records:**
        - `:OLD` : 변경 **전** 데이터 (수정 전 값, 삭제될 값).
        - `:NEW` : 변경 **후** 데이터 (입력할 값, 수정 후 값).
            

#### 3. 실습 시나리오 흐름

1. **기초 테스트:** `testTBL` 생성 후 `UPDATE`/`DELETE` 시 "트리거 동작함" 메시지 출력 확인.
2. **보안 로그 구현:**
    
    - `backup_userTBL` 생성 (로그 저장소).
    - `userTBL`에 변경 발생 시, `:OLD` 값을 백업 테이블로 이관하는 트리거 작성.
        
3. **입력 차단 구현:**
    
    - `userTBL`에 `INSERT` 시도 시 `RAISE_APPLICATION_ERROR`를 통해 "입력 시도가 발견되었습니다" 경고와 함께 차단.

### 1. 핵심 용어 (Terminology)

#### **① 트리거 (Trigger)**

- **정의:** 테이블에 특정 이벤트(INSERT, UPDATE, DELETE)가 발생했을 때, DBMS가 **자동으로 실행**하는 PL/SQL 블록입니다.
- **보안적 용도 (Security Use Case):**
    - **감사 추적 (Audit Trail):** 누가, 언제, 어떤 데이터를 변경했는지 자동으로 기록을 남깁니다.
    - **무결성 강화:** 업무 규칙(Business Rule)에 위배되는 데이터 변경(예: 업무 시간 외 접속, 승인 없는 데이터 삭제)을 강제로 차단합니다.
        

#### **② 의사 레코드 (Pseudo Records: :OLD / :NEW)**

트리거 내부에서만 사용할 수 있는 임시 레코드 구조체입니다. 변경 전후의 값을 비교할 때 필수적입니다.

- **`:OLD` (Old Value):**
    - 명령 실행 **전**의 데이터입니다.
    - `UPDATE` 시 수정 전 값, `DELETE` 시 삭제될 값을 가지고 있습니다.
    - 주로 **로그(백업) 테이블**에 이관할 때 사용합니다.
- **`:NEW` (New Value):**
    - 명령 실행 **후**에 들어갈 데이터입니다.
    - `INSERT` 시 입력될 값, `UPDATE` 시 수정 후 값을 가지고 있습니다.
    - `DELETE` 시에는 NULL입니다.
        

#### **③ 커서 (Cursor)**

- **정의:** `SELECT` 문의 결과 집합이 여러 행일 때, 이를 한 줄씩 처리하기 위해 사용하는 메모리상의 포인터입니다. (C언어의 파일 포인터와 유사)
- **처리 단계:** 선언(Declare) → 열기(Open) → 인출(Fetch) → 닫기(Close).
    

---

### 2. SQL 패턴 (Syntax Pattern)

#### **① 기본 트리거 구조 (Audit Logging)**

이벤트 발생 **후(AFTER)**, 변경된 행마다(**FOR EACH ROW**) 로그를 남기는 패턴입니다.



```SQL
CREATE OR REPLACE TRIGGER 트리거명
    AFTER UPDATE OR DELETE ON 테이블명
    FOR EACH ROW
BEGIN
    -- :OLD 변수를 사용하여 백업 테이블에 기록
    INSERT INTO 백업테이블 VALUES (:OLD.컬럼1, :OLD.컬럼2, …);
END;
/
```

#### **② 강제 에러 발생 (Security Blocking)**

보안 정책에 위배되는 행위 시, 트랜잭션을 중단하고 에러 메시지를 띄웁니다.



```SQL
-- Oracle 사용자 정의 에러 코드 범위: -20000 ~ -20999
RAISE_APPLICATION_ERROR(-20001, '⛔ [보안 경고] 데이터 입력이 허용되지 않습니다.');
```

### S#2. 감사 로그 시스템 구축 (Audit Logging)

#### **1. Scenario & Goal**

회원 테이블(`userTBL`)의 데이터가 변경될 경우, **누가(Who)**, **언제(When)**, **어떤 데이터(What)**를 건드렸는지 `backup_userTBL`에 자동으로 기록합니다. 변경 전 데이터(`:OLD`)를 보존하는 것이 핵심입니다.

#### **2. SQL Implementation**

Step 1: 로그용 백업 테이블 생성


```SQL
CREATE TABLE backup_userTBL (
    userID    CHAR(8)       NOT NULL, -- PK 아님 (중복 로그 허용)
    userName  NVARCHAR2(10) NOT NULL,
    birthYear NUMBER(4)     NOT NULL,
    addr      NCHAR(2)      NOT NULL,
    mobile1   CHAR(3),
    mobile2   CHAR(8),
    height    NUMBER(3),
    mDate     DATE,
    modType   NCHAR(2),       -- 변경 타입 (수정/삭제)
    modDate   DATE,           -- 변경 일시
    modUser   NVARCHAR2(256)  -- 변경 수행자 (계정명)
);
```

**Step 2: 감사 트리거(Audit Trigger) 작성**

```SQL
CREATE OR REPLACE TRIGGER trig_user_backup
    AFTER UPDATE OR DELETE ON userTBL
    FOR EACH ROW
DECLARE
    v_type NCHAR(2); -- '수정' 또는 '삭제'를 담을 변수
BEGIN
    -- 1. 이벤트 타입 구분
    IF UPDATING THEN
        v_type := '수정';
    ELSIF DELETING THEN
        v_type := '삭제';
    END IF;

    -- 2. 백업 테이블에 변경 전(:OLD) 데이터와 감사 정보 기록
```

### [🛡️ 보안 맥락 분석 (Security Context)]

#### 1. 논리적 데이터 분리 (Logical Isolation)

- **보안 위협:** `employee2` 같은 원본 테이블에는 주민번호(SSN), 급여(Salary) 등 민감 정보가 섞여 있어, 일반 직원에게 `SELECT` 권한을 통째로 주면 보안 사고가 발생합니다.
- **대응 정책:** 부서별(인사팀, 일반직원, 관리자)로 **접근 가능한 컬럼만 정의한 가상 테이블(VIEW)**을 제공합니다.
    - **인사팀:** 급여 정보 포함.
    - **복지팀:** 생일, 주소 포함.
    - **일반직원:** 본인의 기본 정보만 열람 가능.
        

#### 2. 복잡성 은폐 및 성능 향상

- **현황:** 여러 테이블을 `JOIN` 해야 하는 복잡한 쿼리를 매번 작성하면 실수로 민감 정보를 누락하거나 잘못 조회할 수 있습니다.
- **대응:** 미리 정의된 뷰(`PRE-DEFINED VIEW`)를 통해 복잡한 로직을 숨기고, 사용자는 마치 단순한 테이블을 조회하듯(`SELECT * FROM 뷰이름`) 접근하게 합니다.
    

#### 3. 행 기반 접근 제어 (Row-Level Security)

- **구현 논리:** `WHERE` 절에 `USER` 시스템 변수(현재 로그인한 계정명)를 활용하여, **"로그인한 본인의 데이터만"** 조회되도록 필터링합니다.
    - 예: `WHERE user_id = USER` (본인 ID와 일치하는 행만 출력)

#### 2. 실습 시나리오 흐름

- **1단계 (Admin):** `employee2` 테이블 생성 및 기초 데이터 입력. (주민번호 등 민감정보 포함)
- **2단계 (Admin):** 역할별 계정 생성 (`EMP_1001`, `HR_USER`, `ADMIN_USER`).
- **3단계 (Dev/Security):** 각 역할에 맞는 뷰(View) 생성.
    - `vw_my_profile`: 일반 직원용 (본인 정보만, 민감정보 제외).

    - `vw_admin_view`: 관리자용 (모든 정보).
- **4단계 (Grant):** 각 계정에 **테이블이 아닌 뷰에 대한 SELECT 권한**만 부여.

## 개념 - DB보안 3교시_2025.10.27

### 1. 핵심 용어 (Terminology)

#### **① 뷰 (VIEW) - 가상 테이블**

- **정의:** 실제 물리적인 데이터는 저장하지 않고, 원본 테이블(Base Table)에서 유도된 **논리적인 가상 테이블**입니다.
- **보안적 용도:**
    - **컬럼 기반 제어 (Column-Level Security):** 민감한 컬럼(주민번호, 급여 등)을 제외하고, 업무에 필요한 컬럼만 정의하여 제공합니다.
    - **복잡성 은폐:** 복잡한 조인(Join) 쿼리를 미리 정의해 두어, 사용자는 단순한 테이블처럼 조회하게 합니다.
- **특징:** 뷰를 조회(`SELECT`)하면, DBMS 내부적으로 저장된 정의(쿼리문)가 실행되어 원본 테이블에서 실시간으로 데이터를 가져옵니다.
    

![Database View Architecture 이미지](https://encrypted-tbn0.gstatic.com/licensed-image?q=tbn:ANd9GcRm0tMkozbiam-p73JrTJ9wSmz7J-nIkBmuAbCXaUdWnBnrf3TO8qWrCI8NxwsNQCJ7j_uQWP19tp71EsAFt3LGn6ZJ5pAc5NJ33Yoac3J1Mxpc_iw)

#### **② 시스템 변수 (USER)**

- **정의:** 현재 데이터베이스 세션에 접속한 **사용자의 계정명(ID)**을 반환하는 오라클 내장 의사 컬럼(Pseudo-column)입니다.
- **활용:** 뷰의 `WHERE` 절에 사용하여, "로그인한 사용자 본인의 데이터"만 보이도록 **행 기반 접근 제어(Row-Level Security)**를 구현할 때 핵심적으로 사용됩니다.
    

---

### 2. SQL 패턴 (Syntax Pattern)

#### **① 기본 뷰 생성 (특정 컬럼 노출)**

민감 정보(주민번호 등)를 제외한 컬럼만 나열합니다.

```SQL
CREATE OR REPLACE VIEW 뷰이름 AS
SELECT 
    컬럼1,  -- (예: 사원명)
    컬럼2   -- (예: 부서명)
    -- 민감 컬럼(주민번호)은 제외
FROM 원본테이블명;
```

#### **② 행 기반 보안 뷰 (Row-Level Security)**

현재 접속자와 관련된 행만 필터링합니다.

```SQL
CREATE OR REPLACE VIEW 뷰이름 AS
SELECT * FROM 원본테이블명
WHERE 사번_컬럼 = USER; -- 접속 계정명과 사번이 일치하는 행만 출력
```

### 3. Standard Check 보안성 검증

|**항목**|**강의 내용 (Classroom)**|**보안 표준 (Standard Practice)**|
|---|---|---|
|**권한 분리**|뷰를 생성하기 위해 `SYSTEM` 계정에서 `GRANT CREATE VIEW` 권한을 부여함.|실무에서도 개발자/DBA에게 **최소 권한의 원칙**을 적용하여, 꼭 필요한 계정(스키마 오너)에게만 뷰 생성 권한을 부여해야 합니다.|
|**데이터 수정**|뷰를 통한 `INSERT/UPDATE` 가능성을 언급.|뷰는 **조회(SELECT) 전용**으로 사용하는 것이 보안상 안전합니다. 뷰를 통해 원본 데이터를 수정하려면 `WITH READ ONLY` 옵션을 사용하여 원천 차단하는 것이 권장됩니다.|
|**접근 제어**|각 사용자에게 테이블(`employee2`) 권한을 주지 않고, 뷰(`vw_…`) 권한만 부여.|이는 **가장 권장되는 보안 모델**입니다. 사용자는 원본 테이블의 존재조차 알 필요가 없으며, 오직 허용된 뷰를 통해서만 데이터에 접근해야 합니다.|

뷰(View)를 생성하려면 **시스템 권한**이 필요합니다. 또한, 실습에 사용할 3가지 역할(일반직원, 인사팀, 관리자)의 계정을 미리 생성해야 합니다. 이 작업은 **관리자(SYSTEM) 계정**에서 수행합니다.

```SQL
-- 1. 관리자(SYSTEM) 접속
CONN system/oracle;

-- 2. 실습 메인 계정(TEST)에 뷰 생성 권한 부여 (필수!)

-- 3. 역할별 테스트 계정 3개 생성

-- 3-3. 관리자 (Admin)
CREATE USER ADMIN_USER IDENTIFIED BY 1234;
GRANT CREATE SESSION TO ADMIN_USER;
```

### S#2. 원본 데이터 및 보안 뷰 생성 (Developer Task)

#### **1. Scenario & Goal**

**실습 메인 계정(TEST)**으로 돌아와서, 원본 테이블(`employee2`)을 만들고 각 역할에 맞는 **보안 뷰(Security View)** 3가지를 설계합니다.

#### **2. SQL Implementation (Test Account)**

```SQL
-- 1. 실습 계정(TEST) 접속
CONN test/1234;

-- 2. 원본 테이블 생성 (민감정보 포함)
DROP TABLE employee2;
CREATE TABLE employee2 (
    emp_id     NUMBER PRIMARY KEY,
    name       VARCHAR2(20),
    dept       VARCHAR2(20),
    rank       VARCHAR2(20),
    salary     NUMBER,          -- 민감정보 (급여)
    ssn        VARCHAR2(14)     -- 초민감정보 (주민번호)
);

-- 3. 데이터 삽입
INSERT INTO employee2 VALUES (1001, '김민수', '인사부', '대리', 4200000, '900101-1234567');
INSERT INTO employee2 VALUES (1002, '이서연', '재무부', '과장', 5300000, '880512-2345678');
INSERT INTO employee2 VALUES (1003, '박지훈', '개발부', '사원', 3800000, '950305-1456789');
COMMIT;

-- 4. 역할별 보안 뷰(View) 생성

-- [A] 일반 직원용: 본인 정보만 조회 (Row-Level Security)
-- 원리: 접속한 계정명(EMP_1001)에서 뒤 4자리(1001)를 잘라 사번과 매칭
CREATE OR REPLACE VIEW vw_my_profile AS
SELECT emp_id, name, dept, rank
FROM employee2
WHERE emp_id = TO_NUMBER(SUBSTR(USER, 5)); 
-- 설명: USER가 'EMP_1001'이면 SUBSTR(USER, 5)는 '1001'이 됨.

-- [B] 인사팀용: 주민번호 제외, 나머지(급여 포함) 조회 (Column-Level Security)
CREATE OR REPLACE VIEW vw_hr_view AS
SELECT emp_id, name, dept, rank, salary
FROM employee2;

-- [C] 관리자용: 모든 정보 조회
CREATE OR REPLACE VIEW vw_admin_view AS
SELECT * FROM employee2;
```

> 해결: SYSTEM 계정으로 들어가서 GRANT CREATE VIEW TO [실습계정];을 실행하지 않아서 발생합니다. 뷰 생성은 RESOURCE 롤에 포함되지 않는 특수 권한임을 명심하세요.
