# 📚 Chapter 7. 고급 DB 오브젝트 심층 분석

## 1. PL/SQL 기초 및 프로시저/함수

프로시저와 함수는 DB 내에 저장되는 미니 프로그램입니다. 보안 관점에서는 소스 코드 암호화가 중요합니다.

### 1.1 핵심 변수 타입 (빈칸 채우기 대비)

- **`%TYPE`**: 특정 테이블의 **한 컬럼**과 동일한 데이터 타입을 선언할 때 사용합니다.
    - 예: `v_name userTBL.userName%TYPE;` (데이터 타입 변경 시 유연하게 대처 가능)
- **`%ROWTYPE`**: 특정 테이블의 **전체 행(모든 컬럼)** 구조를 가져올 때 사용합니다.
    - 예: `v_userData userTBL%ROWTYPE;`

### 1.2 프로시저(Procedure) vs 함수(Function) 차이점

시험에서 두 객체의 특징을 비교하는 문제가 나올 수 있습니다.

|**구분**|**프로시저 (Procedure)**|**함수 (Function)**|
|---|---|---|
|**실행 방식**|`EXEC` 또는 `EXECUTE` 명령어로 실행|SQL 문장 안에서 호출 (예: `SELECT f_grade(sal)…`)|
|**반환 값**|반환값이 없거나, `OUT` 변수를 통해 여러 개 반환 가능|**반드시** 하나의 값을 `RETURN` 해야 함|
|**용도**|복잡한 로직 처리, 트랜잭션 관리|계산, 값 변환 등 결과를 즉시 활용할 때|

### 1.3 [보안] 소스 코드 암호화

- DB에 저장된 프로시저나 함수의 소스 코드는 관리자가 조회할 수 있습니다. 이를 방지하기 위해 **`WRAP`** 기능을 사용합니다.
- **실습 내용:** `DBMS_DDL.wrap`을 사용하여 프로시저 생성 구문을 암호화하여, `USER_SOURCE` 뷰를 조회해도 코드를 알아볼 수 없게 만듭니다.

## 2. 트리거 (Trigger)

**보안 감사(Auditing)**를 구현하는 핵심 도구입니다.

### 2.1 개념 및 키워드

- **동작 시점:** `BEFORE` (작업 전, 검증용), `AFTER` (작업 후, 로깅용), `INSTEAD OF` (뷰 전용).
- **`FOR EACH ROW`**: 문장 단위가 아니라 변경되는 **각 행(Row)마다** 트리거가 실행됨을 명시합니다. 이 옵션이 있어야 `:OLD`, `:NEW` 변수를 사용할 수 있습니다.
- **`:OLD` vs `:NEW` 변수**:
    - **:OLD**: 수정/삭제 **전**의 기존 데이터 (UPDATE, DELETE 시 존재)
    - **:NEW**: 입력/수정 **후**의 새로운 데이터 (INSERT, UPDATE 시 존재)

### 2.2 [핵심 실습] 감사 로그(Audit Log) 기록하기

누가 데이터를 수정하거나 삭제했는지 기록하는 트리거입니다. **코드의 빈칸 채우기**나 **작성 문제**로 출제될 가능성이 높습니다.

> **시나리오:** 회원 테이블(`userTBL`)에서 데이터가 수정되거나 삭제되면, 그 내역을 백업 테이블(`backup_userTBL`)에 저장하라.



```SQL
CREATE OR REPLACE TRIGGER trg_BackupUserTbl
    AFTER UPDATE OR DELETE ON userTBL  -- [포인트 1] 시점과 이벤트 지정
    FOR EACH ROW                       -- [포인트 2] 행 단위 트리거
DECLARE
    v_modeType VARCHAR2(10);
BEGIN
    -- [포인트 3] 동작 구분 (UPDATING, DELETING, INSERTING 시스템 변수 활용)
    IF UPDATING THEN
        v_modeType := '수정';
    ELSIF DELETING THEN
        v_modeType := '삭제';
    END IF;

    -- [포인트 4] 변경 전 데이터(:OLD)와 작업자(USER)를 백업 테이블에 저장
    INSERT INTO backup_userTBL (userID, userName, modType, modDate, modUser)
    VALUES (:OLD.userID, :OLD.userName, v_modeType, SYSDATE, USER); 
END;
/
```

- **`USER`**: 현재 작업을 수행 중인 사용자 아이디를 반환하는 오라클 내장 함수.

## 3. 뷰 (View)

물리적 데이터 없이 논리적으로만 존재하는 가상 테이블입니다. **접근 제어**와 **데이터 마스킹**에 필수적입니다.

### 3.1 보안적 활용 (서술형 대비)

1. **데이터 마스킹(Data Masking):** `SELECT` 문에서 민감한 컬럼(주민번호 등)을 제외하거나 `SUBSTR` 등으로 가려서 뷰를 생성합니다.
2. **접근 제어:** 사용자에게 실제 테이블(`userTBL`)에 대한 권한은 뺏고(`REVOKE`), 필요한 데이터만 있는 **뷰에 대한 권한(`GRANT`)만 부여**합니다.
    

### 3.2 [핵심 실습] 사용자별 맞춤형 뷰 (Row-Level Security)

로그인한 사용자에 따라 자기 자신의 데이터만 보이게 하는 기법입니다.

```SQL
CREATE OR REPLACE VIEW vw_my_profile AS
    SELECT * FROM employee
    WHERE emp_id = USER; -- [포인트] 현재 접속한 사용자(USER)와 ID가 같은 행만 조회
```

### 3.3 `WITH CHECK OPTION` (무결성 및 보안 강화)

- **기능:** 뷰를 생성할 때 사용한 `WHERE` 조건에 위배되는 데이터의 **수정(UPDATE)이나 입력(INSERT)을 막습니다.**
- **예시:** '인사팀' 부서원만 조회하는 뷰에서, 부서를 '개발팀'으로 수정하려고 하면 에러를 발생시켜 **데이터 변조를 방지**합니다.

## 4. 인덱스 (Index)

빠른 검색을 위해 사용하지만, 보안 관점에서는 주의가 필요합니다.

### 4.1 보안 취약점

- **문제점:** 인덱스는 별도의 파일로 저장되는데, 여기에 평문 데이터가 정렬되어 저장됩니다. 해커가 인덱스 파일을 입수하면 원본 데이터를 유추하거나 검색 속도를 이용한 공격(Brute-force)을 할 수 있습니다.
- **원칙:** 주민등록번호(SSN), 여권번호 등 **민감한 정보에는 절대 일반 인덱스를 생성하지 않습니다.**
    

### 4.2 보안을 고려한 인덱스 설계

1. **함수 기반 인덱스 (Function-based Index):**
    
    - 전체 데이터를 인덱싱하지 않고, 가공된 데이터만 인덱싱합니다.
    - 예: 주민번호 전체가 아닌, 생년월일(앞 6자리)로만 검색이 필요할 때.
        
    ```SQL
    CREATE INDEX idx_user_birth 
    ON userTBL( SUBSTR(ssn, 1, 6) ); 
    ``` 
    
2. **부분 인덱스 (Partial Index):**
    
    - `WHERE` 조건을 주어 특정 데이터만 인덱싱하여 불필요한 데이터 노출을 최소화합니다.

# 📚 Chapter 8. DB 보안 관리 실무 심층 분석

## 1. 사용자 계정 관리 (User Account)

**출제 포인트:** `CREATE USER` 문법, **프로파일(Profile)**을 이용한 패스워드 및 리소스 보안 정책 설정.

### 1.1 계정 생성 기본 문법

시스템 관리자(`SYS`, `SYSTEM`)만이 수행할 수 있는 작업입니다 .

```SQL
CREATE USER 사용자명
IDENTIFIED BY 비밀번호
DEFAULT TABLESPACE 테이블스페이스명; -- 데이터가 저장될 기본 공간 지정
```

- **보안 포인트:** 오라클 12c 이후 아키텍처에서는 **공통 사용자**(CDB, 모든 DB 접근, `C##` 접두어 필요)와 **로컬 사용자**(PDB, 특정 DB 접근)로 나뉩니다 . 시험 실습 환경은 주로 로컬 사용자 개념을 사용합니다.

### 1.2 [핵심] 프로파일(Profile)을 이용한 보안 정책

단순히 계정만 만드는 것이 아니라, **패스워드 정책**과 **시스템 리소스 제한**을 걸어 보안을 강화합니다. 이 부분은 **단답형**이나 **괄호 채우기**로 출제될 확률이 높습니다 .

|**정책 구분**|**파라미터**|**설명**|
|---|---|---|
|**패스워드 정책**|`FAILED_LOGIN_ATTEMPTS`|로그인 n회 실패 시 계정 잠금 .|
||`PASSWORD_LOCK_TIME`|계정이 잠겼을 때 잠금 지속 시간(일 단위) .|
||`PASSWORD_LIFE_TIME`|암호 유효 기간(만료일) 설정 .|
||`PASSWORD_REUSE_TIME`|동일한 암호를 다시 사용할 수 없는 기간 .|
|**리소스 정책**|`IDLE_TIME`|지정한 시간 동안 활동이 없으면 세션 강제 종료 .|
||`SESSIONS_PER_USER`|한 계정으로 동시 접속 가능한 세션 수 제한 .|

**[실습 코드 예시]**


```SQL
-- 1. 프로파일 생성 (보안 정책 정의)
CREATE PROFILE secure_prof LIMIT
    FAILED_LOGIN_ATTEMPTS 3    -- 3회 실패 시 잠금
    PASSWORD_LIFE_TIME 90      -- 90일마다 변경
    IDLE_TIME 10;              -- 10분 유휴 시 로그아웃

-- 2. 사용자에게 프로파일 적용
ALTER USER student01 PROFILE secure_prof;

-- 3. 잠긴 계정 해제 (관리자 권한)
ALTER USER student01 ACCOUNT UNLOCK; -- [시험 출제 유력]
```

## 2. 권한 관리 (Privilege Management)

**출제 포인트:** 시스템 권한 vs 객체 권한 구분, `GRANT`/`REVOKE` 문법, 권한 부여 옵션 차이.

### 2.1 시스템 권한 vs 객체 권한

이 둘을 구분하는 것이 중요합니다 .

1. **시스템 권한 (System Privilege):** DB에 영향을 주는 행위.
    
    - 예: `CREATE SESSION`(접속), `CREATE TABLE`, `CREATE VIEW`, `DROP ANY TABLE`.
        
2. **객체 권한 (Object Privilege):** 특정 데이터(테이블) 조작 행위.
    
    - 예: `SELECT`, `INSERT`, `UPDATE`, `DELETE` **ON 테이블명**.
        

### 2.2 GRANT (권한 부여) & REVOKE (권한 회수)

**기본 문법:**

```SQL
-- 권한 부여
GRANT 권한_리스트 ON 객체명 TO 사용자;

-- 권한 회수
REVOKE 권한_리스트 ON 객체명 FROM 사용자;
```

### 2.3 [함정 문제] 재부여 옵션의 차이 (중요!)

권한을 받은 사용자가 **"다른 사람에게 그 권한을 또 줄 수 있는가?"**를 결정하는 옵션입니다 .

|**구분**|**옵션 키워드**|**적용 대상**|**특징**|
|---|---|---|---|
|**WITH ADMIN OPTION**|시스템 권한|`REVOKE` 시 **연쇄 회수 안 됨**. (내가 준 권한을 받은 제3자는 권한 유지)||
|**WITH GRANT OPTION**|객체 권한|`REVOKE` 시 **연쇄 회수 됨 (Cascade)**. (내가 권한을 뺏기면, 내가 줬던 애들도 다 뺏김)||

## 3. 롤 (ROLE) 관리

**출제 포인트:** 롤의 목적(그룹핑), 기본 롤(`CONNECT`, `RESOURCE`), 사용자 정의 롤 생성 절차.

### 3.1 롤의 개념 및 필요성

- **정의:** 여러 권한들을 묶어놓은 **권한의 그룹(집합)**입니다 .
- **목적:** 수십 개의 권한을 일일이 사용자마다 부여하는 번거로움을 줄여 관리의 효율성을 높입니다 .
    

### 3.2 오라클 기본 롤 (Standard Roles)

가장 많이 사용되는 3대 롤을 반드시 암기해야 합니다 .

1. **CONNECT:** DB 접속에 필요한 기본 권한 (`CREATE SESSION` 등).
2. **RESOURCE:** 객체(테이블, 시퀀스, 프로시저 등)를 생성할 수 있는 권한 집합.
3. **DBA:** 모든 시스템 권한을 가진 최고 관리자 롤.
    

### 3.3 [실습] 사용자 정의 롤 생성 및 부여 절차

시험 문제로 **"순서대로 나열하시오"** 혹은 **"SQL을 작성하시오"**가 나올 수 있습니다 .

> **시나리오:** '개발팀' 롤을 만들고, 테이블 생성 및 조회 권한을 넣은 뒤, `User1`에게 부여하라.

1. **롤 생성:** `CREATE ROLE DevTeam;`
2. **롤에 권한 부여:** `GRANT CREATE TABLE, CREATE SESSION TO DevTeam;`
3. **사용자에게 롤 부여:** `GRANT DevTeam TO User1;`

## 📝 기말고사 대비 요약 (Chapter 8)

1. **계정 관리:**
    
    - `ALTER USER … ACCOUNT UNLOCK` (잠금 해제 명령어 필수 암기).
    - `PROFILE`: `FAILED_LOGIN_ATTEMPTS`(실패 횟수), `PASSWORD_LIFE_TIME`(암호 수명).
        
2. **권한 (Privilege):**
    
    - 시스템(`CREATE SESSION`) vs 객체(`SELECT ON table`) 구분.
    - **옵션 차이:** `WITH ADMIN OPTION`(시스템, 연쇄회수X) vs `WITH GRANT OPTION`(객체, 연쇄회수O).
        
3. **롤 (Role):**
    
    - 권한의 그룹핑.
    - `CONNECT`, `RESOURCE` 롤의 역할.
    - 생성 절차: `CREATE ROLE` $\rightarrow$ `GRANT 권한 TO 롤` $\rightarrow$ `GRANT 롤 TO 유저`.

# 📚 Chapter 9. 감사(Audit) 및 데이터 암호화 심층 분석
암호화 부분은 실습 환경의 제약으로 인해 **개념 및 빈칸 채우기** 위주로 출제될 가능성이 높으니 키워드 위주로 학습해야 합니다.

## 1. 데이터베이스 감사 (Database Audit)

**출제 포인트:** 감사의 목적, 설정 명령어(`AUDIT`/`NOAUDIT`), 로그 확인 뷰(`DBA_AUDIT_TRAIL`).

### 1.1 감사의 개념 및 필요성

- **정의:** 사용자의 데이터베이스 작업(로그인, 테이블 조회, 수정 등)을 모니터링하고 기록하는 활동입니다 .
- **목적:** 의심스러운 활동 감지, 침입자 식별, 규정 준수 확인.
    

### 1.2 감사 설정 및 해제 명령어 (필수 암기)

기본 문법은 `AUDIT` 명령어입니다. **성공/실패 여부**에 따라 기록을 다르게 남길 수 있습니다 .

|**기능**|**명령어 예시**|**설명**|
|---|---|---|
|**로그인 감사**|`AUDIT SESSION;`|접속/접속종료 기록 (가장 기본) .|
|**권한 감사**|`AUDIT CREATE TABLE;`|누가 테이블을 생성했는지 기록 (시스템 권한) .|
|**객체 감사**|`AUDIT SELECT ON hr.employees;`|특정 테이블 조회 시 기록 (객체 권한) .|
|**조건부 감사**|`… WHENEVER NOT SUCCESSFUL;`|**실패한 작업만** 기록 (예: 로그인 실패, 권한 없는 접근 시도) .|
|**감사 해제**|`NOAUDIT SESSION;`|감사 설정을 끄는 명령어 .|

### 1.3 [실습] 감사 활성화 및 로그 확인 프로세스

시험 문제로 **"순서대로 나열하시오"**가 나올 수 있는 프로세스입니다 .

1. **파라미터 확인:** `SHOW PARAMETER audit_trail;` (기본값 `NONE`이면 감사 안 됨).
2. **감사 활성화:** `ALTER SYSTEM SET audit_trail=DB,EXTENDED SCOPE=SPFILE;`
    
    - `DB`: 로그를 DB 테이블(`SYS.AUD$`)에 저장 .
    - `EXTENDED`: 실행한 **SQL 문장까지** 상세히 기록 .
        
3. **DB 재시작:** `SHUTDOWN IMMEDIATE;` $\rightarrow$ `STARTUP;` (재시작해야 적용됨) .
4. **감사 설정:** `AUDIT SELECT ON employees;`
5. **로그 확인:** `SELECT * FROM DBA_AUDIT_TRAIL;` (가장 중요한 뷰 이름) .
    

---

## 2. 데이터 암호화 (Data Encryption)

**출제 포인트:** **AES256** 알고리즘, **RAW** 데이터 타입, 암호화/복호화 함수 개념 (실습보다는 개념 위주).


### 2.1 암호화 핵심 개념

- **알고리즘:** 오라클 실습에서는 **AES256** (대칭키, 256비트 키 사용) 방식을 사용합니다 .
- **데이터 타입:** 암호화된 데이터는 일반 문자열이 아닌 **이진(Binary)** 형태가 되므로, 테이블 설계 시 **`RAW`** 타입을 사용해야 합니다 .
    - 예: `ssn VARCHAR2(20)` $\rightarrow$ `ssn_raw RAW(2000)`

### 2.2 암호화/복호화 구현 (PL/SQL 함수)

수업 시간에 `DBMS_CRYPTO` 패키지를 사용했지만, 환경 설정 문제로 실행이 안 될 수 있다고 하셨습니다. 따라서 **코드의 흐름과 키워드**를 이해하는 것이 중요합니다 .

1. **암호화 (Encrypt):** 평문(Plain Text) $\rightarrow$ 암호문(Cypher Text/RAW).
    
    - 함수: `DBMS_CRYPTO.ENCRYPT`
    - 입력: 평문, 암호화 키, 알고리즘 타입.
        
2. **복호화 (Decrypt):** 암호문(RAW) $\rightarrow$ 평문(Plain Text).
    
    - 함수: `DBMS_CRYPTO.DECRYPT`
    - **중요:** 암호화할 때 쓴 **키(Key)**와 똑같은 키를 써야 풀립니다 (대칭키 특징) .
        

### 2.3 [응용] 자동 암호화/복호화 구조

사용자가 매번 함수를 호출하지 않도록 자동화하는 구조입니다 .

- **INSERT 시 (트리거 활용):**
    - 데이터가 입력될 때 **트리거**가 작동하여, 평문을 암호화 함수로 변환 후 테이블에 저장합니다.
- **SELECT 시 (뷰 활용):**
    - 사용자는 테이블을 직접 조회하지 않고, **뷰(View)**를 통해 조회합니다.
    - 뷰 내부에서 복호화 함수를 호출하여 평문으로 보여줍니다.

## 📝 기말고사 대비 요약 (Chapter 9)

1. **감사(Audit):**
    
    - 명령어: `AUDIT` (설정), `NOAUDIT` (해제).
    - 뷰: **`DBA_AUDIT_TRAIL`** (로그 확인 장소, 필수 암기).
    - 옵션: `WHENEVER NOT SUCCESSFUL` (실패 시에만 기록).
        
2. **암호화(Encryption):**
    
    - 알고리즘: **AES256** (대칭키).
    - 저장 타입: **`RAW`** (암호문은 바이너리 데이터).
    - 패키지: `DBMS_CRYPTO` (암/복호화 수행).
    - 전략: `Trigger`(자동 암호화) + `View`(자동 복호화).
        

# 📚 Chapter 10. DB 보안 종합 실습 분석

이 챕터는 크게 **4가지 영역**으로 나뉩니다. 각 영역별 핵심 문제와 예상 답안(SQL)을 정리해 드립니다.

## 1. 사용자 계정 및 권한 관리 (문제 1~3)

**핵심 목표:** 사용자를 생성하고, 최소한의 권한만 부여하며, 효율적인 관리를 위해 롤(Role)을 사용하는 과정을 평가합니다.

✅ 문제 1: 사용자 계정 생성

- **요구사항:** `student01` 계정 생성, 비밀번호 `stud1234`, 접속 권한(`CONNECT`)만 부여
- **핵심 SQL:**
    
    ```SQL
    -- 1. 계정 생성
    CREATE USER student01 IDENTIFIED BY stud1234;
    -- 2. 접속 권한 부여
    GRANT CONNECT TO student01;
    ```
    

✅ 문제 2: 권한 부여 및 회수

- **요구사항:** `employees` 테이블 조회 권한 부여 후 다시 회수.
- **핵심 SQL:**

    ```SQL
    -- 권한 부여
    GRANT SELECT ON hr.employees TO student01;
    -- 권한 회수 (시험 출제 유력)
    REVOKE SELECT ON hr.employees FROM student01;
    ```
    

✅ 문제 3: ROLE 생성 및 적용

- **요구사항:** `data_user` 롤 생성 $\rightarrow$ `CREATE TABLE`, `SELECT` 권한 추가 $\rightarrow$ 롤을 `student01`에게 부여.
- **핵심 SQL:**

    ```SQL
    CREATE ROLE data_user; -- 롤 생성
    GRANT CREATE TABLE, SELECT ANY TABLE TO data_user; -- 롤에 권한 담기
    GRANT data_user TO student01; -- 롤을 사용자에게 부여
    ```

## 2. 비밀번호 및 계정 정책 관리 (문제 4~5)

**핵심 목표:** **프로파일(Profile)**을 사용하여 보안 정책(로그인 실패 제한 등)을 강제하고, 잠긴 계정을 관리자가 해제하는 능력을 평가합니다.

✅ 문제 4: 비밀번호 정책(Profile) 적용

- **요구사항:** 로그인 3회 실패 시 계정 잠금 정책이 담긴 `secure_prof` 프로파일 생성 및 적용

    ```SQL
    -- 프로파일 생성 (FAILED_LOGIN_ATTEMPTS가 핵심 키워드)
    CREATE PROFILE secure_prof LIMIT
        FAILED_LOGIN_ATTEMPTS 3;
    
    -- 사용자에게 적용
    ALTER USER student01 PROFILE secure_prof;
    ```
    

✅ 문제 5: 계정 잠금 해제 (Account Unlock)

- **요구사항:** 잠긴 계정을 관리자가 다시 풀어주는 명령어 작성
- **핵심 SQL (필수 암기):**

    ```SQL

    ```

## 3. 객체 보안 및 데이터 마스킹 (문제 6~7)

**핵심 목표:** **뷰(View)**를 활용하여 민감한 컬럼을 숨기고, 데이터 일부를 마스킹(Masking)하여 보여주는 기술을 평가합니다.

✅ 문제 6: 특정 컬럼 제한 뷰

- **요구사항:** `ename`, `job` 컬럼만 보이는 뷰 `emp_view` 생성 및 조회 권한 부여
- **핵심 SQL:**
    ```SQL
    CREATE OR REPLACE VIEW emp_view AS
    SELECT ename, job FROM employees;
    
    GRANT SELECT ON emp_view TO student01;
    ```
    

✅ 문제 7: 데이터 마스킹 (주민번호 가리기)

- **요구사항:** 주민번호 뒷자리를 `*****`로 가린 뷰 생성

- **핵심 SQL:**
    ```SQL
    CREATE VIEW person_masked AS
    SELECT name, 
           SUBSTR(ssn, 1, 6) || '-*******' AS ssn_masked 
    FROM person;
    ```

# 📚 Chapter 11. 데이터 모델링 (DB 설계) 심층 분석

## 1. 데이터베이스 설계 프로세스

시험에서는 이론적인 순서보다는 **실제 설계 결과물**을 도출해내는 것이 중요합니다.

- **설계 흐름:** 요구사항 분석 $\rightarrow$ (개념/논리 모델링 생략) $\rightarrow$ **물리적 모델링** $\rightarrow$ DB 구축 .
- **핵심 목표:** 현실 세계의 업무(예: 쇼핑몰 주문)를 데이터베이스의 **테이블(Table)** 구조로 변환하는 것 .
    

## 2. [핵심 실습] 쇼핑몰 DB 설계 시나리오

강의 자료에 나온 **"고객 방문 및 구매 기록"** 예제가 시험 문제의 원형이 될 가능성이 매우 높습니다. 이 흐름을 완벽히 이해해야 합니다.

### 2.1 1단계: 데이터 분리 (정규화 개념)

처음에는 모든 데이터가 엑셀 시트 하나에 섞여 있는 상태(비정규화)입니다. 이를 주제별로 나누어야 합니다 .

- **문제점:** 한 테이블에 고객 정보와 구매 정보가 섞여 있으면, 물건을 사지 않은 고객의 구매란이 `NULL`로 채워지거나, 한 사람이 여러 물건을 살 때 고객 정보가 중복 저장됩니다 .
- **해결:** **고객 테이블(`userTBL`)**과 **구매 테이블(`buyTBL`)**로 분리합니다 .
    

### 2.2 2단계: 관계 설정 (PK와 FK)

분리된 두 테이블을 연결하는 고리가 필요합니다 .

- **Primary Key (PK, 기본키):** 각 행을 식별하는 유일한 값.
    - `userTBL`의 PK: **`userID`** (이름은 중복될 수 있으므로 ID를 사용) .
- **Foreign Key (FK, 외래키):** 다른 테이블의 PK를 참조하는 값.
    - `buyTBL`의 FK: **`userID`** (누가 샀는지 알기 위해 고객 테이블의 ID를 기록) .
- **관계:** **1:N (일대다)** 관계입니다. 한 명의 고객(1)은 여러 개의 물건을 구매(N)할 수 있습니다 .
    

## 3. [시험 출제 유력] 물리적 설계 (테이블 명세서 작성)

시험 문제로 **"다음 시나리오를 보고 테이블 명세서를 작성하시오"**가 출제될 것입니다. 작성해야 할 필수 항목은 **테이블 명, 컬럼 명, 데이터 타입, 제약조건(PK/FK)**입니다 .

### ✅ 작성 예시 (쇼핑몰 시나리오)

**1) 고객 테이블 (`userTBL`)**

|**한글명**|**영문명(컬럼명)**|**데이터 타입**|**필수(NULL)**|**제약조건**|
|---|---|---|---|---|
|**아이디**|`userID`|`CHAR(8)`|NOT NULL|**PK**|
|**이름**|`userName`|`NVARCHAR2(10)`|NOT NULL||
|**출생년도**|`birthYear`|`NUMBER(4)`|NOT NULL||
|**주소**|`addr`|`NCHAR(2)`|NOT NULL||
|**연락처**|`mobile`|`CHAR(13)`|NULL||

**2) 구매 테이블 (`buyTBL`)**

|**한글명**|**영문명(컬럼명)**|**데이터 타입**|**필수(NULL)**|**제약조건**|
|---|---|---|---|---|
|**순번**|`num`|`NUMBER(8)`|NOT NULL|**PK**|
|**구매자ID**|`userID`|`CHAR(8)`|NOT NULL|**FK**|
|**상품명**|`prodName`|`NCHAR(6)`|NOT NULL||
|**단가**|`price`|`NUMBER(8)`|NOT NULL||
|**수량**|`amount`|`NUMBER(3)`|NOT NULL||

>[!tip] **💡 답안 작성 팁:**
> - **데이터 타입:** 오라클 기준 타입을 정확히 써야 합니다.
>     - 한글 저장: `NCHAR`, `NVARCHAR2` .
>     - 숫자 저장: `NUMBER`, `INTEGER` .
>     - 고정 길이 문자: `CHAR` (ID 등 길이가 일정한 경우).
> - **PK/FK 표시:** 어느 컬럼이 기본키이고, 어느 컬럼이 외래키인지 반드시 표기해야 합니다.
