## **TL;DR**

- **수정의 정석:** 조회 → (도메인 메서드로) 필요한 필드만 변경 → 커밋
- **신규 생성:** **ID 없이** persist
- **merge()는 최후의 수단:** 스냅샷 **전체 치환**이라 누락 필드가 **NULL로 덮어쓰기**될 위험 큼
- **레이어 원칙:** 컨트롤러는 **폼/DTO만 다루고**, 엔티티 생성·변경은 **서비스(트랜잭션)** 에서

---

> 차이점: **Dirty가 ‘어떻게 만들어졌는지’** 가 완전히 다름 (선택적 변경 vs 스냅샷 복사).
## A. JPA 영속성 컨텍스트 조회->변경/ Merge 최종 정리: 5단계
### 1. 영속성 컨텍스트 오픈: 서비스 메서드에서 **@Transactional 시작**
- 논리적 관리 영역인 영속성 컨텍스트가 생성됩니다.

### 2. 영속 엔티티 로딩 및 관리 준비
#### 1차 캐시 조회 및 로딩
- **목적**: DB 접근을 최소화하고 성능을 최적화하기 위함입니다.
- **작동**:
	- 엔티티 ID를 기준으로 **1차 캐시**에 먼저 접근합니다.
	- 캐시에 없으면 **DB에 `SELECT` 쿼리**를 실행하여 데이터를 가져옵니다.
- 결과: 가져온 데이터는 **영속 상태**로 전환되어 1차 캐시에 저장되고 **스냅샷**이 찍혀 기록됩니다.
#### 1차 캐시 조회 및 로딩 실패했을 경우

ID를 기준으로 **DB에 데이터 자체가 없는 경우** (즉, 신규 데이터) 두 메커니즘은 다르게 작동합니다.

| 메커니즘          | 입력 객체 상태                  | 결과                                                     |
| ------------- | ------------------------- | ------------------------------------------------------ |
| **조회 → 변경**   | ID로 `find()` 시도           | DB에 없으므로 **`null`을 반환**하고 작업 종료. ->개발자가 Persist 경로처리해야 |
| **`merge()`** | ID가 없는 **비영속 객체**를 인자로 받음 | **`persist`와 동일하게** 새로운 영속 엔티티를 생성하고, `INSERT`를 준비함.   |

- merge에 persist 기능있다고해도 명시적으로 persist 코드에 사용해 의도 드러내기
---

### 3. 변경 감지 (Dirty Checking)의 역할과 차이

데이터 변경을 감지하고 DB에 반영하는 과정은 **엔티티의 상태를 어떻게 변경했는지**에 따라 나뉩니다.

| 메커니즘             | Dirty 생성 방식                                    | SQL 생성 유형                                             |
| ---------------- | ---------------------------------------------- | ----------------------------------------------------- |
| **조회 → 변경 (권장)** | **개발자가 영속 엔티티를 직접 선택적으로 필드 수정**                | Dirty Checking으로 **수정된 필드**만 감지하여 **`UPDATE`** 쿼리 생성. |
| **`merge()`**    | **준영속 객체의 모든 필드를 복사**하여 영속 객체를 강제로 변경 상태로 만듦.  | **`UPDATE(기존변경)`** 또는 **`INSERT(신규생성)`** 쿼리 생성        |

- 이때 merge의 반환값은 영속객체이고 개발자는 이를 사용한다, 데이터를 넘겼던 준영속객체는 계속 준영속인 별개의 객체이다
#### merge가 위험한이유
- 요청에 **없는 필드 = NULL** 로 **덮어쓰기**
- **선택적 변경** 불가(전체 갈아끼우기)
- 권한 밖 필드가 의도치 않게 갱신될 수 있음
---

### 4. 최종 반영 (Flush & Commit)

- **Flush**: Dirty Checking 실행 → **INSERT/UPDATE/DELETE**를 **제약 고려 순서**로 **전송**(배치 가능) → **스냅샷/버전 갱신**
- **Commit**:**트랜잭션 확정(ACID)** / **Rollback**: 전송된 변경 미확정/취소
	- commit은 필요시 자동 FLUSH하는 기능있음

### 5. 컨텍스트 종료

- commit(또는 rollback) 완료 후 영속성 컨텍스트 **종료**
- 여기서 관리되던 모든 엔티티는 **준영속 상태(Detached)** 로 전환됩니다.

## **B. 레이어드 아키텍처 원칙**

- **컨트롤러**
    - 폼 → **DTO(Command)** 로 변환만
    - 엔티티 **생성·변경 금지**
- **서비스(트랜잭션 경계)**
    - **조회 → 변경감지** 수행
    - 파라미터 많으면 **전용 Command DTO** 도입
- **엔티티**
    - **세터 남발 금지**, 의미 있는 **도메인 변경 메서드** 제공
    - 컬렉션/연관관계는 **편의 메서드**로 일관성 유지

```java
public record UpdateItemCommand(Long id, String name, Integer price, Integer stockQuantity) {}

@Transactional
public void updateItem(UpdateItemCommand c) {
  Item item = repo.findById(c.id()).orElseThrow();
  item.changeName(c.name());
  item.changePrice(c.price());
  item.changeStockQuantity(c.stockQuantity());
}
```

## **C. 체크리스트 (실무용)**

- **신규**: ID 미지정 + persist
- **수정**: findById 후 **필드만 변경**(Dirty Checking)
- 컨트롤러 → **DTO만 전달**, 서비스에서 **명시적 매핑/검증**
- 엔티티에 **change*** 메서드로 변경 수렴
- **수정 가능/불가 필드** 구분(예: price, stockQuantity만 수정; isbn 등은 금지)
- merge() 필요한 경우 **NULL-무시/화이트리스트 복사**로 가드

---

## **D. 안티패턴**

- new Entity() 후 **ID만 세팅**해서 저장 → JPA가 **준영속**으로 보고 merge() 경로로 빠짐(전체 덮어쓰기 위험)
- 변경 후 **save() 습관** → JPA에선 **불필요**(커밋 시 자동 반영)
- 컨트롤러에서 **엔티티 직접 생성/수정**

---

## **한 줄 마무리**

> **“폼은 DTO로 끝, 수정은 서비스 트랜잭션에서 ‘조회→도메인 변경→커밋’.”**
> 이 규칙만 지키면 안전성·가독성·추적성·테스트가 모두 좋아집니다.
