**2025.10.17, 1교시 — 개선본**

1번은 문장을 주고 True/False를 묻는 문제입니다. 틀린 이유를 쓸 필요는 없습니다.

2번은 무결성 제약 조건(Integrity Constraints, IC) 4가지 정도를 쓰는 주관식입니다. 간단히 생각하면 `entity` 무결성, `key` 제약, `foreign key(FK)` 제약, `cardinality`, `participation`, `semantic` (내부 비즈니스 규칙, 예: 과장 월급은 부장보다 높을 수 없다) 등이 있습니다.

`Entity` 무결성은 실세계의 entity를 유일하게 구별하도록 `key` 속성을 만들어야 한다는 것입니다. `Key` 제약은 key에 해당하는 값이 유일해야 하고 `NULL` 값이 있어서는 안 된다는 것입니다. `Foreign key(FK)`는 중복 및 `NULL`이 가능하지만, 참조하는 테이블에 있는 값에 속해야 합니다. `Cardinality`는 관계(relationship)에 엮인 정도를 나타냅니다. `Participation`은 관계에 전체(total)로 참여할지 부분(partial)으로 참여할지이며, 중요도는 낮습니다. `Semantic` 제약은 회사 내부에서 정해진 규칙입니다.

3번은 key 종류를 구하는 문제입니다. (예시 스키마 제시) (실습)

R1 테이블에서 후보 키(candidate key), 기본 키(primary key), 대체 키(alternate key, AK)를 구해야 합니다. (실습) AK는 SK(superkey)와 구분하기 위해 사용합니다. foreign key(FK)도 찾아야 합니다. (실습) R2, R3, R4 테이블에 대해서도 마찬가지로 수행해야 합니다. (실습)

이것은 `reverse engineering` 문제입니다. 테이블 스키마를 보고 key가 정해지지 않은 상태에서 reverse engineering을 해보겠습니다.

(R1, R2 관계 추정) ... R1의 A1과 R2의 B1을 가져간 것 같습니다. R1의 A1은 key가 될 수 있습니다. A2, A3는 단독으로 key가 될 수 없습니다. (중복 값 10, 100) A1이 이미 key이므로 최소성을 만족해야 하기에 A1A2, A1A3는 볼 필요 없습니다. A2A3는 (10, a) (10, a)로 중복되어 key가 아닙니다.

R1의 후보 키는 A1이고, 따라서 PK도 A1입니다. AK는 없습니다. FK는 없는 것 같습니다. R2의 후보 키는 B1, B2 둘 다 가능합니다. 이후 관계(reverse engineering)를 고려하여 PK를 정해야 합니다. (R3 테이블을 보고 추정) R2의 PK는 B1으로 보입니다. 그러면 AK는 B2입니다.

AK(B2)는 인덱스 구성 시 옵션으로 사용될 수 있습니다. PK(B1)는 기본적으로 인덱스가 생성됩니다. R3 테이블은 R1과 R2에서 속성을 가져온 매핑 테이블(N:M 관계)로 보입니다. R3의 PK는 규칙에 의해 (A1, B1)을 합친 것이 됩니다. 후보 키나 AK는 고려하지 않습니다. R3의 FK는 A1 (R1.A1 참조), B1 (R2.B1 참조) 두 개가 있습니다. 이렇게 key를 찾으면 됩니다. `(실습)`

시험 문제는 N:M이 아닌 1:N reverse engineering이 나올 것입니다. 1:N 기능 파악이 중요하기 때문입니다.

4번은 (ERD를 주고) 테이블을 만드는, 반대 방향의 문제입니다. `(실습)`

5번은 `SELECT ... FROM ... WHERE ...` SQL 문제입니다. 스키마(예: Sailors)를 주고 조회 SQL을 작성하는 것입니다. `(실습)`

6번은 `requirements`를 주고 데이터 모델링을 하는 문제입니다. `(실습)` 첫 번째로 ERD를 작성하고, `mapping rule`을 이용해 (관계 스키마 설계를) 해야 합니다. `(실습)` Requirements를 해석할 때 무엇이 entity이고, 무엇이 속성인지, 무엇이 관계인지 잘 살펴봐야 합니다. 실제 요구사항처럼 혼란스럽게 주어질 수 있습니다.

(예시: 고객 만족 부서) "고객 만족 부서는 근무하는 사람이 없다"는 정보는, 사원-부서 간 '근무' 관계에서 부서 측의 `participation`이 전체(total)가 아닌 부분(partial)이라는 의미입니다.

설계 시 가장 중요한 것은 `cardinality`입니다. (1:1, 1:N, N:M) `Cardinality`가 틀리면 (설계가) 끝입니다.

(시험 범위 요약) PPT보다 나눠준 참고 자료(IC 정리 문서, key 연습 테이블)를 보십시오. 배점은 6번(모델링)이 가장 높을 것입니다. 1번(TF)은 5점, 2/3/4/5번은 중간 정도(15점)일 것입니다.

**2025.10.17, 1교시 — 개념**

1. 한 줄 요약

    데이터 무결성 제약 조건(IC), 키(Key)의 종류와 역할, 요구사항으로부터 ERD를 도출하고 스키마로 변환(Mapping)하는 데이터 모델링 프로세스 및 리버스 엔지니어링 개념을 다룹니다.

2. **핵심 TL;DR**

- **무결성 제약 조건(Integrity Constraint, IC)**: 데이터베이스의 정확성과 일관성을 보장하기 위한 규칙입니다.
- **개체 무결성(Entity Integrity)**: `PRIMARY KEY` 제약. 테이블 내의 행(tuple)을 유일하게 식별해야 하며, `NULL` 값을 가질 수 없습니다.
- **참조 무결성(Referential Integrity)**: `FOREIGN KEY` 제약. 참조하는 테이블(부모)의 `PRIMARY KEY`에 존재하는 값이거나 `NULL`이어야 합니다.
- **키(Key)의 종류**:
    - **슈퍼키(Superkey)**: 유일성을 보장하는 속성 또는 속성의 집합.
    - **후보키(Candidate Key)**: 유일성과 **최소성**을 만족하는 슈퍼키.
    - **기본키(Primary Key, PK)**: 후보키 중 선택된 대표 키.
    - **대체키(Alternate Key, AK)**: PK로 선택되지 않은 나머지 후보키.
    - **외래키(Foreign Key, FK)**: 다른 테이블의 PK를 참조하는 키.
- **카디널리티(Cardinality)**: 관계(relationship)에 참여하는 엔터티 인스턴스의 수(1:1, 1:N, N:M). 스키마 설계 시 구조를 결정하는 가장 중요한 요소입니다.
- **참여(Participation)**: 관계 참여가 필수(Total, 전체)인지 선택(Partial, 부분)인지 정의합니다. (예: 모든 사원은 부서에 '반드시' 소속됨 → Total)
- **시맨틱(Semantic) 제약**: 도메인 고유의 비즈니스 규칙입니다. (예: `CHECK (salary <= manager_salary)`)
- **데이터 모델링(Data Modeling)**: (1) 요구사항 분석 → (2) ERD 작성 → (3) 매핑 규칙(Mapping Rule) 적용 → (4) 관계 스키마 도출.
- **리버스 엔지니어링(Reverse Engineering)**: 이미 존재하는 테이블 스키마를 분석하여 거꾸로 ERD나 관계 구조(1:N, N:M 등)를 추론하는 과정입니다.
- **인덱스(Index)**: `PRIMARY KEY`는 생성 시 기본적으로 인덱스가 생성됩니다. `Alternate Key` 등 다른 속성은 조희 속도 향상을 위해 선택적으로 인덱스를 생성할 수 있습니다.

3. **표현 = 표준 용어**

- **Integrity Constraint (IC)**: 무결성 제약 조건
- **Entity Integrity**: 개체 무결성 (PK 제약)
- **Referential Integrity**: 참조 무결성 (FK 제약)
- **Key (PK, FK, AK, CK, SK)**: 키 (기본키, 외래키, 대체키, 후보키, 슈퍼키)
- **Cardinality**: 카디널리티 (1:1, 1:N, N:M)
- **Participation (Total, Partial)**: 참여 (전체, 부분)
- **Reverse Engineering**: 리버스 엔지니어링
- **Data Modeling (ERD, Mapping Rule)**: 데이터 모델링 (ERD, 사상 규칙)
- **Index**: 인덱스

4. 정석 보강(canon-std)

    데이터 모델링은 요구사항을 ERD로 변환하고, 이를 **매핑 규칙(Mapping Rule)**을 통해 관계 스키마로 사상하는 과정입니다. 이 스키마의 논리적 일관성은 **무결성 제약 조건(IC)**으로 보장됩니다. 개체 무결성(PRIMARY KEY)은 각 행의 유일한 식별(Unique, Not NULL)을 보장하며, 참조 무결성(FOREIGN KEY)은 관계의 유효성(참조되는 PK에 값이 존재하거나 NULL 허용)을 보장합니다. **카디널리티(Cardinality)**는 스키마 구조를 결정하며, 특히 N:M 관계는 반드시 두 엔터티를 참조하는 별도의 매핑 테이블(linking table)로 구현되어야 합니다.

5. **실수·함정**

- 슈퍼키(유일성)와 후보키(유일성+최소성)를 혼동하는 것.
- `FOREIGN KEY`는 `NOT NULL`이 명시되지 않는 한 `NULL` 값을 가질 수 있음을 간과하는 것.
- 카디널리티(1:N vs N:M)를 잘못 식별하는 것. 이는 스키마 구조에 치명적인 오류를 유발합니다.
- 참여(Participation, 전체/부분)와 카디널리티(1:N)를 혼동하는 것.
- 리버스 엔지니어링 시, 1:N 관계에서 N측의 FK를 N:M 매핑 테이블로 오해하는 것.
- 대체키(AK)가 자동으로 인덱스된다고 가정하는 것. (PK만 기본 생성, AK는 옵션)
- 시맨틱(비즈니스 규칙) 제약 조건을 모델링에서 누락하는 것. (예: `CHECK` 제약)

**2025.10.17, 1교시 — 질문**

[Q1] 1번. 주어진 문장이 맞는지 틀리는지(T/F) 판단하시오. | 태그: 개념 이해

- **모범답(강의 기준)**: 문장의 True/False만 판단하며, 틀린 이유를 서술할 필요는 없습니다.

[Q2] 2번. 무결성 제약 조건(Integrity Constraints, IC) 4가지를 서술하시오. | 태그: 제약(PK/FK), ERD

- **정석체크(면접 30초)**: 핵심 IC는 **개체 무결성**(`PK`는 `NOT NULL`, `UNIQUE`)과 **참조 무결성**(`FK`는 참조하는 `PK` 값이거나 `NULL`이어야 함)입니다. 또한 **도메인 무결성**(`CHECK`, `NOT NULL`)과 고유 비즈니스 규칙(Semantic)이 있습니다. `Cardinality`나 `Participation`은 ERD 단계의 논리적 제약입니다.

[Q3] 3번. 주어진 테이블 스키마에서 키(PK, AK, FK) 종류를 찾고 관계를 리버스 엔지니어링 하시오. | 태그: 키, ERD, 리버스 엔지니어링

- **모범답(강의 기준)**: 후보키(유일성+최소성)를 모두 찾고, 그중 PK를 선정합니다. N:M 관계(R3)의 PK는 양쪽 FK(A1, B1)의 조합이며, FK는 R1, R2를 각각 참조합니다. `(실습)`
- **정석체크(면접 30초)**: **후보키**는 유일성과 최소성을 만족하는 속성 집합입니다. **PK**는 후보키 중 선택된 것이고, **AK**는 나머지 후보키입니다. **FK**는 참조 무결성을 강제하며, N:M 관계는 두 1:N 관계를 구현하는 _연결 테이블_(R3)로 분해됩니다. `(실습)`

[Q4] 4번. (주어진 ERD를) 테이블 스키마로 변환(Mapping)하시오. | 태그: ERD, 관계 스키마, 사상

- **모범답(강의 기준)**: ERD의 엔터티를 테이블로, 속성을 컬럼으로 변환합니다. (강의에서 상세 매핑 규칙 언급은 생략됨) `(실습)`
- **정석체크(면접 30초)**: ERD를 관계 스키마로 변환 시, **엔터티**는 테이블이 됩니다. 1:N 관계는 N측이 1측의 PK를 **FK**로 가집니다. N:M 관계는 두 엔터티의 PK를 FK로 갖는 **별도 테이블**로 생성해야 합니다. `CREATE TABLE ... PRIMARY KEY(...), FOREIGN KEY(...) REFERENCES ...` `(실습)`

[Q5] 5번. 주어진 스키마(예: Sailors)에서 요구사항을 만족하는 `SELECT` SQL을 작성하시오. | 태그: SQL(DML)

- **모범답(강의 기준)**: `SELECT ... FROM ... WHERE ...` 구문을 사용하여 조건에 맞는 데이터를 조회합니다. `(실습)`
- **정석체크(면접 30초)**: SQL 조회는 `SELECT` (컬럼), `FROM` (테이블), `WHERE` (필터 조건)가 기본입니다. `JOIN` (테이블 연결), `GROUP BY` (집계), `ORDER BY` (정렬) 사용법을 숙지해야 합니다. `NULL`은 =이 아닌 `IS NULL`로 비교해야 합니다.

[Q6] 6번. 요구사항(Requirements)을 분석하여 ERD를 작성하고 데이터 모델링을 완료하시오. | 태그: ERD, 관계 스키마, 카디널리티

- **모범답(강의 기준)**: 요구사항에서 엔터티, 속성, 관계를 식별하여 ERD를 작성한 후, 매핑 규칙을 적용해 스키마를 설계합니다. `(실습)`
- **정석체크(면접 30초)**: 모델링의 핵심은 **카디널리티**(1:1, 1:N, N:M)와 **참여**(Total/Partial)를 정확히 식별하는 것입니다. 카디널리티가 틀리면 스키마 구조 전체가 잘못됩니다. 불필요한 정보(예: 고객 만족 부서 예시)를 걸러내고 논리적 구조(예: 근무 관계)에 집중해야 합니다. `(실습)`
