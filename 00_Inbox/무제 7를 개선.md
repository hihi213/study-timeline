# 📜 [통합 가이드] DBMS 메커니즘, SQL 실행 원리 및 최적화

## 1. 기본 원리: DBMS 작동 메커니즘과 SQL

데이터베이스를 이해하려면 물리적인 **저장 구조**, 논리적인 **역할 분담**, 그리고 **처리 순서**를 파악해야 합니다.

### A. 데이터베이스 작동 메커니즘 (Memory vs Disk)

CPU는 디스크(Disk)에 있는 데이터에 직접 접근하여 연산할 수 없습니다. 따라서 모든 DBMS는 **버퍼 캐시(Buffer Cache)**라는 메모리 공간을 중심으로 동작합니다.

1. **Block I/O:** 디스크에 저장된 데이터 블록을 메모리(Buffer Cache)로 복사합니다.
2. **Memory Access:** CPU는 오직 메모리에 올라와 있는 데이터만 읽거나 수정할 수 있습니다.
3. **Flush:** 변경된 데이터는 즉시 디스크에 쓰지 않고, 나중에 일괄적으로 기록(DBWR)합니다.
    

> **핵심:** 우리가 수행하는 모든 SQL은 디스크가 아닌 **메모리 위에서의 작업**을 전제로 합니다.

### B. 역할의 분리: SQL과 옵티마이저 (What vs How)

사용자가 요청을 보내면, DBMS는 **"무엇을 할 것인가(SQL)"**와 **"어떻게 처리할 것인가(Plan)"**를 철저히 구분하여 처리합니다.

**1. SQL (Declarative Language - 사용자 영역)**

- **역할:** 데이터의 추출과 조작에 대한 **결과물(Requirement)**을 정의합니다.
- **특징:** 구체적인 경로(How)는 기술하지 않고, 엔진에게 위임하는 선언형 언어입니다.
    

**2. 옵티마이저 (Optimizer - DBMS 영역)**

- **역할:** 사용자의 SQL을 분석하여 비용(Cost)이 가장 낮은 최적의 경로(Plan)를 수립합니다.
- **옵티마이저가 바라보는 3가지 대상:**
    
    1. **SQL:** 분석 및 최적화의 기본 단위.
    2. **함수(Function):** 내부 로직을 알 수 없는 **"행(Row)마다 CPU를 소모하는 블랙박스 비용"**으로 간주합니다. (최적화 불가능)
    3. **인덱스 & 통계:** 길 안내를 위한 지도(Map)이자 나침반.
        

### C. DBMS 내부 처리 과정 (Process Flow)

위의 역할 분담에 따라 엔진 내부는 다음과 같이 움직입니다.

1. **파싱 (Parser):** 문법적 오류(Syntax)와 테이블 존재 여부(Semantics)를 검사합니다.
2. **최적화 (Optimizer):** 통계 정보를 바탕으로 가장 효율적인 실행 계획을 짭니다.
3. **실행 (Executor):** 결정된 계획에 따라 데이터를 가져오고(Fetch) 필터링합니다.
    

### D. SQL의 논리적 실행 순서 (Logical Execution Order)

개발자는 `SELECT`부터 작성하지만, 엔진은 `FROM`부터 해석합니다. 이 순서는 **별칭(Alias) 사용 가능 여부**와 **함수 사용 시 성능**에 결정적인 영향을 미칩니다.

|**순서**|**절 (Clause)**|**설명 (역할)**|
|---|---|---|
|**1**|**FROM / JOIN**|조회할 테이블(데이터셋)을 가져와 조립합니다.|
|**2**|**WHERE**|조건에 맞지 않는 행을 필터링합니다. (가장 중요한 성능 포인트)|
|**3**|**GROUP BY**|데이터를 그룹핑하여 집계할 준비를 합니다.|
|**4**|**HAVING**|그룹핑된 데이터 중 조건에 맞는 것만 남깁니다.|
|**5**|**SELECT**|최종적으로 출력할 컬럼이나 계산식을 처리합니다.|
|**6**|**ORDER BY**|데이터를 정렬하여 사용자에게 보여줍니다.|

## 2. 심화 메커니즘: 선(先)조회, 후(後)조작 (Read before Write)

1번의 원리(메모리 기반 작동)에 따라, 데이터를 조작하는 DML 작업도 **"대상을 메모리로 가져오는 것"**이 먼저 선행되어야 합니다.

### A. DML(수정/삭제)의 필수 3단계

`UPDATE` 문은 단순히 쓰는 작업이 아니라, **복잡한 읽기 과정**을 포함합니다.

1. **FETCH (읽기):** `WHERE` 조건에 맞는 데이터를 인덱스 등을 통해 찾아 **메모리(Buffer Cache)로 로딩**하고, 커서를 위치시킵니다.
    
    - _커서(Cursor): 현재 읽고 있는 행을 가리키는 포인터_
        
2. **LOCK (잠금):** 다른 트랜잭션이 동시에 해당 데이터를 변경하지 못하도록 행(Row)을 잠급니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 장애 복구를 위해 로그(Redo/Undo)를 남깁니다.
    

> **💡 Insight:** 쓰기 성능을 높이고 싶다면, 역설적으로 **"대상을 빨리 찾는 읽기 튜닝(인덱스 최적화)"**이 선행되어야 합니다.

### B. 기술적 제약: 할로윈 문제 (Halloween Problem)

DBMS는 **"읽는 도중(Fetch, Cursor 이동 중)에는 데이터를 변경할 수 없다"**는 제약을 가집니다. 읽는 도중 데이터 위치가 바뀌면 중복 읽기나 누락이 발생하기 때문입니다.

$\rightarrow$ 이로 인해 **읽기(Function)**와 **쓰기(Procedure)**의 구현 방식이 분리되어야 합니다.

## 3. 개발자의 영역: 로직 구현 전략 (Implementation)

할로윈 문제를 피하고 엔진의 특성에 맞게 로직을 설계해야 합니다.

### A. 함수 (Function) - Read Only

- **위치:** SQL 문장 내(`SELECT`, `WHERE` 절 등) 표현식으로 사용됩니다.
- **실행 시점:** Fetch(읽기) 단계 내부.
    - Fetch 단계이므로 내부에서 `INSERT`, `UPDATE` 등 **상태 변경 불가**.
- **위험성:** `WHERE` 절에 사용 시 인덱스 사용을 방해하거나, 모든 행마다 실행되어 성능 저하 유발 가능.
    

### B. 프로시저 (Procedure) - Transaction Control

- **성격:** 비즈니스 로직의 **전체 흐름을 제어**하는 실행 컨테이너입니다.
- **위치:** 애플리케이션에서 호출하는 최상위 진입점입니다. (SQL 내부에서 호출 불가)
- **실행 시점:** Fetch가 끝난 후 독립적으로 실행.
    - Fetch가 끝난 후이므로 트랜잭션(`COMMIT`/`ROLLBACK`) 제어 가능, 자유로운 데이터 변경(`DML`) 가능.

## 4. 성능 최적화: 옵티마이저와 인덱스 억제 방지

옵티마이저는 `WHERE` 절을 가장 먼저 처리하여 데이터 범위를 줄이려 합니다. 이때 개발자의 실수가 잦습니다.

### 🚨 핵심 튜닝: 좌변 가공 금지 (No Left-side Manipulation)

"좌변 가공"은 옵티마이저가 인덱스를 포기하고 **Full Table Scan(전체 뒤지기)**을 하게 만드는 주범입니다.

- **Bad Case:** `WHERE YEAR(date_col) = '2024'`
    - **원인:** 인덱스는 `date_col` 원본 값 기준으로 정렬되어 있습니다. 이를 `YEAR()` 함수로 2차 가공하면, 정렬 순서가 깨져 인덱스 매칭이 불가능해집니다.
    - **결과:** 인덱스를 포기하고 전체 데이터를 뒤지며 모든 행에 대해 함수를 실행합니다.
- **Good Case:** `WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'`
    - **해결:** 컬럼은 그대로 두고, 비교할 값(우변)을 가공하여 **인덱스 범위 스캔(Range Scan)**을 유도해야 합니다.
    - **효과:**
        
        1. `WHERE` 절이 인덱스를 통해 대상을 먼저 줄임.
        2. 필터링된 결과 집합에 대해서만 필요한 함수가 실행됨.

## 💡 종합 요약 (Summary)

> [!note] **구조적 이해를 통한 최적화**
>
> 1. **Mechanics:** DB는 디스크가 아닌 **메모리**에서 일합니다. 따라서 수정(`UPDATE`)하려 해도 먼저 메모리로 불러오는 **읽기(Fetch)** 과정이 필수입니다.
>     
> 2. **Flow:** SQL은 `FROM` $\rightarrow$ `WHERE` $\rightarrow$ `SELECT` 순으로 작동합니다. 데이터가 걸러지는 `WHERE` 절에서의 효율이 성능을 좌우합니다.
>     
> 3. **Optimization:**
>     
>     - `WHERE` 절의 컬럼을 가공하지 마십시오. (인덱스 보호)
>         
>     - 단순 연산은 **함수**, 데이터 변경 흐름은 **프로시저**로 역할을 분리하십시오.
>         

> [!tip] **핵심 정리**
>
> 1. **Write는 Read를 포함한다:** 수정/삭제가 느리다면, 타겟 데이터를 찾는 **인덱스(Read)**부터 점검하십시오.
>     
> 2. **컬럼은 신성불가침이다:** `WHERE` 절의 컬럼을 함수로 감싸는 순간 인덱스는 무용지물이 됩니다. (항상 비교 값을 가공할 것)
>     
> 3. **역할을 분리하라:**
>     
>     - 값의 계산/변환 $\rightarrow$ **함수 (Function)**
>         
>     - 데이터 변경/트랜잭션 제어 $\rightarrow$ **프로시저 (Procedure)**
>
