# 🏗️ [Deep Dive] DBMS 메커니즘과 SQL 최적화 가이드

데이터베이스 성능 최적화는 단순히 쿼리를 짧게 쓰는 것이 아닙니다. **"엔진이 데이터를 어떻게 메모리로 가져오고(Physical), 어떤 순서로 처리하며(Logical), 그 과정에서 어떤 제약이 발생하는지"** 를 이해하는 것이 핵심입니다.

## 1. 물리적 기반: 메모리 중심의 작동 (Physical Mechanism)

모든 DBMS 튜닝의 제1원칙은 **"디스크 I/O를 줄이고 메모리 히트율을 높이는 것"** 입니다. 그 이유는 하드웨어의 근본적인 한계 때문입니다.

### 🛑 CPU는 디스크를 직접 연산할 수 없다.

1. **속도의 차이 (Speed Gap):** 디스크는 CPU에 비해 너무 느립니다. CPU가 디스크를 직접 기다리면 시스템은 멈춰버릴 것입니다.
2. **단위의 차이 (Unit Gap):** CPU는 바이트(Byte) 단위의 미세한 데이터를 원하지만, 디스크는 블록(Block) 단위의 뭉텅이 데이터만 줄 수 있습니다.
    

### ⚙️ 작동 메커니즘: 버퍼 캐시의 역할

위 한계 때문에 **버퍼 캐시(Buffer Cache)**라는 메모리가 필수적인 중간 다리 역할을 합니다.

1. **Block I/O (적재):** 디스크의 데이터 블록을 통째로 메모리(Buffer Cache)로 복사합니다.
2. **Memory Access (연산):** CPU는 메모리에 올라와 있는 데이터만 읽거나 수정합니다.
3. **Flush (기록):** 변경된 데이터는 즉시 디스크에 쓰지 않고, 나중에 일괄 기록(Dirty Write)합니다.
    

> [!tip] **핵심 원리:**
>
> **SQL의 대상:** 우리가 작성한 SQL은 디스크가 아닌 **메모리(Buffer Cache)**를 조작하는 명령어입니다.
>
> **성능의 척도:** 결국 "누가 더 적은 블록을 메모리로 불러와서 효율적으로 쓰느냐"가 성능을 결정합니다.
>

## 2. 논리적 실행 체계: 역할과 순서 (Logical Layer)

물리적 기반 위에, 개발자와 엔진은 각자의 역할을 수행하며 데이터를 처리합니다.

### A. 역할 분담: 무엇(What) vs 어떻게(How)

개발자는
1. SQL: 최종 **결과물(What)** 를 기술
2. SQL만으로 표현하기 힘든 절차적 흐름이나 복잡한 연산을 함수나 프로시저로 정의
옵티마이저(DBMS)은 실행 경로를 결정합니다.
3. **개발자의 SQL**:
4. **옵티마이저 (Plan = Strategy):**
    - 개발자가 던진 SQL을 분석하여 가장 효율적인 **경로(How)**를 수립합니다.

> SQL은 구체적인 탐색 경로(How)는 기술하지 않는 선언형 언어이다.
> 옵티마이저는 최종 결과물만 정의한 SQL를 토대로 탐색경로를 계획하고 수행한다.

### B. 실행 순서: 순서가 제약을 만든다

옵티마이저는 개발자가 작성한 순서가 아닌, **"대상을 먼저 메모리로 가져오는 순서"** 로 데이터를 단계별로 걸러내며 비용을 계산해 계획을 짭니다.

|**실행 순서**|**절 (Clause)**|**설명 및 튜닝 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업할 테이블과 데이터셋을 메모리로 가져올 준비를 합니다.|
|**2**|**WHERE**|**(필터링)** 조건에 안 맞는 행을 버립니다. **여기서 데이터 양을 얼마나 줄이느냐가 성능의 90%를 결정**합니다.|
|**3**|**GROUP BY**|**(집계)** 남은 데이터를 기준에 따라 묶습니다.|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 특정 조건만 남깁니다.|
|**5**|**SELECT**|**(표현)** 최종 결과를 출력하거나 계산식을 수행합니다.|
|**6**|**ORDER BY**|**(정렬)** 사용자에게 보여주기 위해 순서를 나열합니다.|

## 3. 실행의 본질과 제약: 읽어야 쓸 수 있다

위의 메모리기반 작동에 따라, 데이터를 조작하는 DML 작업도 **"대상을 메모리로 가져오는 것"** 이 먼저 선행되어야 합니다.

> **💡 Insight:** 쓰기 성능을 높이고 싶다면, 역설적으로 **"대상을 빨리 찾는 읽기 튜닝(인덱스 최적화)"**이 선행되어야 합니다.
### A. Read before Write (수정의 메커니즘)

1. **FETCH (읽기):** `FROM` $\rightarrow$ `WHERE`을 수행하여 대상을 찾아 **메모리로 로딩**합니다. (인덱스가 없으면 전체를 뒤져야 합니다.)
2. **LOCK (잠금):** 찾은 행(Row)을 다른 트랜잭션이 건드리지 못하게 잡습니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 로그(Redo/Undo)를 남깁니다.

> FETCH때 커서(포인터)를 움직여 현재 행을 기억합니다
### B. 필연적 제약: 할로윈 문제 (Halloween Problem)

"읽으면서 동시에 쓰는 것"은 데이터의 위치 변경을 유발하여, 커서가 이미 읽은 행을 또 읽거나 건너뛰는 **할로윈 문제**를 발생시킵니다. 이를 방지하기 위해 DB 개발 로직은 읽기와 쓰기 로직으로 엄격히 분리됩니다.

| **구분**     | **함수 (Function)**               | **프로시저 (Procedure)**                 |
| ---------- | ------------------------------- | ------------------------------------ |
| **목적**     | 값의 계산 및 변환 (**Read Only**)      | 비즈니스 흐름 제어 (**Transaction Control**) |
| **실행 위치**  | SQL 문장 내부 (`SELECT`, `WHERE` 등) | 애플리케이션 최상위 호출                        |
| **실행 시점**  | Fetch(읽기) 단계 도중 실행              | Fetch가 끝난 후 독립적으로 실행                 |
| <br>생기는 제약 | 내부에서 `INSERT`, `UPDATE` 불가      | `COMMIT`, `ROLLBACK`, `DML` 자유 사용    |


> **💡 Insight:**
>
> - 단순 연산은 **함수**로 처리하되, `WHERE` 절 사용 시 인덱스 방해를 주의하십시오.
>     
> - 데이터 변경과 트랜잭션 관리는 반드시 **프로시저** 영역에서 수행해야 합니다.
>

## 4. 성능 최적화: 인덱스를 태워라

옵티마이저가 가장 먼저 수행하는 `WHERE` 절에서 인덱스를 제대로 타게 하는 것이 튜닝의 시작과 끝입니다.

### 🚨 핵심 튜닝: 좌변 가공 금지 (No Left-side Manipulation)

DB의 인덱스는 **컬럼의 원본 값**을 기준으로 정렬되어 있습니다. 컬럼(좌변)을 가공하는 순간, 정렬이 깨져 **Full Table Scan(전체 뒤지기)**이 발생합니다.

#### ❌ Bad Case (인덱스 미사용)

SQL

```Java
WHERE YEAR(date_col) = '2024'
```

- **원인:** `date_col`은 정렬되어 있지만, `YEAR()` 함수를 거친 결과값은 정렬 순서를 보장할 수 없습니다.
- **결과:** 인덱스를 포기하고 모든 행에 대해 함수를 실행합니다.
    

#### ✅ Good Case (인덱스 사용)

SQL

```Java
WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
```

- **해결:** 컬럼은 그대로 두고, 비교할 값(우변)을 가공하여 **인덱스 범위 스캔(Range Scan)**을 유도합니다.
- **효과:** `WHERE` 절이 인덱스를 통해 대상을 먼저 확실하게 줄여줍니다.

## 📝 종합 요약 (Summary)

> [!note] **구조적 이해를 통한 최적화**
>
> 1. **Mechanics:** DB는 디스크가 아닌 **메모리**에서 일합니다. `UPDATE`가 느리다면, 먼저 대상을 메모리로 퍼올리는 **읽기(Fetch)** 과정부터 튜닝하십시오.
>     
> 2. **Flow:** SQL은 `FROM` $\rightarrow$ `WHERE` $\rightarrow$ `SELECT` 순입니다. 초반(`WHERE`)에 데이터를 얼마나 잘라내느냐가 승부처입니다.
>     

> [!tip] **Action Plan**
>
> 1. **컬럼은 신성불가침:** `WHERE` 절의 컬럼을 함수로 감싸지 마십시오. (우변을 가공할 것)
>     
> 2. **역할 분리:** 값의 계산은 **함수**, 트랜잭션과 데이터 변경은 **프로시저**로 명확히 나누십시오.
>
