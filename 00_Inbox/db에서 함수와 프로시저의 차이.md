## 정리
### 종합 요약 (Logic Flow)

> [!note]- 함수에서 프로시저로의 논리적 흐름과 관계 정의
>
> 1. SQL은 요구사항(**What**)만 정의하며, 데이터를 가져오는 과정(**How**)은 DBMS(옵티마이저)가 전담합니다.
>     
> 2. **함수의 역할:** DBMS가 데이터를 **읽는(Fetch)** 과정에서 값을 계산하는 연산 대상, **읽기 전용(Read-Only)** 속성을 가집니다.
>     
> 3. **직면한 문제:** 시스템은 단순 계산을 넘어, 데이터의 **상태 변경(Write)**과 그에 따른 **트랜잭션 제어**를 요구합니다.
>     
> 4. **해결책:** 조회 문맥에서 벗어나 독립적으로 실행되며, 데이터 변경 권한을 가진 **프로시저**로 비즈니스 로직을 수행합니다.
>     

>

## 1. SQL과 옵티마이저 (What vs How)

함수는 옵티마이저가 '데이터를 가져오는 과정'를 수행할때의 **'연산 작업 덩어리(Computation Unit)'** 입니다. 데이터를 읽어들이는(Fetch) 과정에서, 값을 계산하기 위한 조회 과정에 종속되므로 읽기 전용(Read-Only) 속성을 가집니다.

- **사용자의 영역 (What - 선언):**
    - 사용자는 데이터가 _어디에_ 있고 _어떻게_ 가져와야 하는지 명시하지 않습니다. 단지 "무엇을(Target)" 원하는지만 `SELECT` 문으로 정의합니다.
- **DBMS의 영역 (How - 실행):**
    - 실제 데이터를 가져오는 과정(반복문 수행, 인덱스 탐색 등)은 **옵티마이저(Optimizer)**가 결정합니다.
- **함수의 위치:**
    - 옵티마이저가 데이터를 한 줄씩 읽어들이는(Fetch) 과정에서, 값을 변환하기 위해 호출하는 **연산 작업 덩어리**로 동작합니다.
    - 따라서 함수는 **조회 프로세스(Read Context)**에 종속됩니다.
        

## 2. 한계 직면과 프로시저의 도입 (Read vs Write)

조회용으로 설계된 함수만으로는 부족해, 실제 값을 변경하고 흐름을 제어할 별도의 객체가 필요해졌습니다.

### **A. 함수의 한계 (Only Read)**

- **데이터 변경 불가:** 옵티마이저가 데이터를 읽고 있는 도중(Projection)에는 데이터의 무결성을 해칠 수 있는 행위(값 변경)가 차단됩니다. 결과적으로 함수는 **"값을 보여주는 것"** 외에는 시스템 상태에 영향을 줄 수 없습니다.
- **트랜잭션 제어 불가:** "재고 차감 $\rightarrow$ 주문 생성 $\rightarrow$ 결제 승인"과 같이 여러 단계가 **모두 성공(COMMIT)**하거나 **모두 취소(ROLLBACK)**되어야 하는 원자성(Atomicity)이 필요합니다. 하지만 함수는 상위 쿼리의 트랜잭션에 종속되므로 독자적인 제어가 불가능합니다.
- **반환값 강제:** 단순히 "삭제하라"는 명령이 목적일 때도, 함수는 구조적으로 반드시 결과값을 반환해야 하므로 문법적 비효율이 발생합니다.
    

### **B. 프로시저의 필요성 (Read & Write)**

- 단순 조회가 아닌 **"비즈니스 로직(행위)"**을 완결 짓기 위해 **트랜잭션(Transaction)** 제어가 필수적입니다.
- 이를 위해 옵티마이저의 조회 루프에서 벗어나, 독자적으로 **명령을 수행하고 상태를 변경**할 수 있는 **프로시저**가 도입되었습니다.
    - **해결 ① 상태 변경 허용:** `SELECT` 문 내부가 아니라 독립적으로 실행(`EXEC`)되므로, `INSERT`, `UPDATE`, `DELETE`를 자유롭게 수행합니다.
    - **해결 ② 트랜잭션 소유:** 내부에서 `COMMIT`, `ROLLBACK`을 직접 명시하여 로직의 완결성을 보장합니다.
    - **해결 ③ 리턴값 없는 실행:** 반환값에 구애받지 않고, 명령 수행 후 종료하는 절차적 처리가 가능합니다.
        

## 3. 핵심 정정: 프로시저와 옵티마이저의 관계 (Container vs Tool)

- **인덱스(Index) = 도구(Tool):**
    - 옵티마이저가 데이터를 빨리 찾기 위해 **사용하는 수단**입니다.
- **프로시저(Procedure) = 컨테이너(Container):**
    - 옵티마이저가 **분석하고 실행해야 할 대상(SQL)들의 집합**입니다.
    - **작동 원리:** 프로시저 생성 시 옵티마이저가 미리 개입하여 내부 SQL의 **실행 계획을 수립(Pre-compile)**해 둡니다. 실행 시에는 이 계획을 재사용하므로 성능이 빠를 뿐, 프로시저 자체가 옵티마이저의 기능을 돕는 것은 아닙니다.
### 1. 옵티마이저의 도구 (Tools)

옵티마이저가 "어떻게 하면 데이터를 가장 빠르게 가져올까?"를 판단할 때 **참조하는 자원**입니다.

- **인덱스 (Index):** 데이터의 위치를 빠르게 찾기 위한 지도(B-Tree 등).
- **통계 정보 (Statistics):** 데이터의 분포도, 행(Row)의 개수, 블록 수 등 옵티마이저의 판단 근거가 되는 메타 데이터.
- **시스템 지표 (System Metrics):** CPU 속도, 디스크 I/O 속도 등 하드웨어 환경 정보.
    

### 2. 옵티마이저의 대상 (Targets)

옵티마이저가 분석하고 실행 계획을 수립해야 하는 **작업물**입니다.

- **SQL 문장:** 가장 기본 단위.
- **프로시저 (Procedure):** SQL과 제어 구문의 집합체 (컨테이너).
- **함수 (Function):** 값을 계산하는 로직의 집합체.
    - 옵티마이저 입장에서 함수는 "실행해서 값을 얻어내야 하는 **연산 작업(Workload)**"입니다.
        

---

### 🚨 핵심 오개념 수정: 함수와 옵티마이저의 관계

"함수가 옵티마이저의 도구"가 될 수 없는 결정적인 이유는, 함수가 종종 **옵티마이저의 도구(인덱스) 사용을 무력화**시키기 때문입니다.

#### 예시: 인덱스 컬럼 가공 (좌변 가공) 문제

- **상황:** `date` 컬럼에 인덱스가 걸려 있음.
- **함수 사용 (비효율):**
    ```SQL
    WHERE YEAR(date) = '2024'  -- 컬럼을 함수로 감쌈
    ```
    
- **결과:** 옵티마이저는 변형된 `YEAR(date)` 값을 인덱스에서 찾을 수 없습니다. (인덱스는 원본 `date`로 정렬되어 있음).
- **영향:** 옵티마이저는 인덱스(도구)를 포기하고 **테이블 전체 스캔(Full Table Scan)**을 선택합니다.
    

$\therefore$ 함수는 옵티마이저를 돕는 도구가 아니라, 옵티마이저가 **처리해야 할 연산 대상**이며, 때로는 최적화를 방해하는 **장애물**이 되기도 합니다.
