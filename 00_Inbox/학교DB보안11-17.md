### 📝 수업 흐름 및 보안 맥락 분석 (Context & Flow)

#### 1. 소프트웨어 개발 생명주기와 DB 설계의 중요성

프로젝트는 요구사항 분석 → 시스템 설계 → 구현 → 테스트 → 유지보수의 단계로 진행됩니다. 이 중 **DB 설계(System Design)**는 데이터의 무결성과 보안을 담보하는 기초 단계입니다.

- **모델링 프로세스:** 현실 세계의 업무(Business Logic)를 분석하여 **개념적(Conceptual) → 논리적(Logical) → 물리적(Physical)** 모델로 구체화합니다.
- **보안 관점:** 잘못된 설계(예: 정규화 미흡으로 인한 중복 데이터)는 데이터 불일치(Inconsistency)와 관리 포인트 증가로 이어져 보안 취약점이 될 수 있습니다.
    

#### 2. 실무적 데이터 모델링 (Modeling Practice)

강의에서는 이론적인 개념/논리 모델링 단계를 간소화하고, Oracle SQL Developer를 사용하여 즉시 **물리적 모델(Relational Model)**을 설계하는 방식을 채택했습니다.

- **식별자 전략 (PK Strategy):** 교수님은 '연락처(Mobile)'와 같이 유일한 값을 가진 속성(Natural Key)이 있더라도, 실무적으로는 **회원 번호(Surrogate Key)**와 같은 인조 식별자를 `PRIMARY KEY`로 생성할 것을 권장했습니다. 이는 향후 개인정보(전화번호) 변경 시 키 관리의 유연성을 확보하고 보안성을 높이는 표준적인 방법입니다.
- **관계 설정 (Relationships):** `고객(User)`과 `구매(Buy)` 테이블 간의 관계를 설정하며 **참조 무결성(Referential Integrity)**을 위해 `FOREIGN KEY`를 적용합니다.
    

#### 3. 엔지니어링 도구 활용 (Forward & Reverse Engineering)

- **Forward Engineering (순공학):** GUI 환경에서 설계한 ERD를 바탕으로 `DDL(CREATE TABLE …)` 스크립트를 자동 생성하여 DB에 반영합니다. 이는 수동 코딩 시 발생할 수 있는 휴먼 에러를 줄여줍니다.
- **Reverse Engineering (역공학):** 이미 구축된 데이터베이스(예: `EMP`, `DEPT` 테이블)의 정보를 읽어와(Import Dictionary), 이를 다시 시각적인 ERD로 변환합니다. 이는 레거시 시스템 분석이나 보안 감사 시 DB 구조를 빠르게 파악하는 데 유용합니다.

### 1. 핵심 용어 (Terminology)

- **데이터 모델링 (Data Modeling):** 현실 세계의 업무 프로세스를 추상화하여 데이터베이스 구조로 변환하는 과정입니다.
    - **개념적 설계 (Conceptual):** 핵심 개체(Entity)와 관계(Relationship) 도출 (ERD 작성).
    - **논리적 설계 (Logical):** 정규화 수행, 속성(Attribute) 정의, 식별자(Key) 확정.
    - **물리적 설계 (Physical):** DBMS에 맞는 데이터 타입(Oracle `VARCHAR2`, `NUMBER` 등) 지정, 테이블 명세서 작성.
- **공학적 접근 (Engineering Direction):**
    - **순공학 (Forward Engineering):** 설계된 모델(ERD)을 바탕으로 `DDL` 스크립트(SQL)를 자동 생성하여 DB에 반영하는 기법.
    - **역공학 (Reverse Engineering):** 이미 구축된 DB(Dictionary) 정보를 읽어와 모델(ERD)로 시각화하는 기법. (레거시 시스템 분석 및 보안 감사 시 필수)
- **대리 키 (Surrogate Key):** 비즈니스적 의미가 없는 인위적인 식별자 (예: `USER_ID`, `SEQ_NO`). 주민번호나 전화번호 같은 **자연 키(Natural Key)** 대신 사용하는 것을 권장합니다.
    

---

### 2. SQL 패턴 (Syntax Pattern)

데이터 모델링의 결과물인 **DDL(Data Definition Language)**의 기본 패턴입니다.

#### **A. 테이블 생성 및 제약조건 (Basic Structure)**



```SQL
CREATE TABLE table_name (
    column1_name DATATYPE [DEFAULT value] [NOT NULL],
    column2_name DATATYPE,
    …
    -- 식별자(PK) 설정
    CONSTRAINT pk_name PRIMARY KEY (column1_name),
    -- 참조 무결성(FK) 설정
    CONSTRAINT fk_name FOREIGN KEY (column2_name)
        REFERENCES parent_table (parent_column)
        [ON DELETE action]
);
```

#### **B. 참조 무결성 옵션 (Foreign Key Options)**

부모 데이터 삭제 시 자식 데이터 처리 방식:

- `ON DELETE CASCADE`: 부모 삭제 시 자식도 자동 삭제 (위험).
- `ON DELETE SET NULL`: 부모 삭제 시 자식의 FK를 `NULL`로 변경.
- `ON DELETE NO ACTION` (또는 생략): 자식이 존재하면 부모 삭제 거부 (데이터 무결성 최우선).
    

---

### 3. Standard Check 보안성 검증

수업 내용과 실무 보안 표준(Security Best Practice) 간의 비교 분석입니다.

#### **① 식별자 선정 (PK Strategy)**

- **강의 내용:** 전화번호(Mobile)는 유일하더라도 `회원번호(User ID)`를 새로 만들어 PK로 사용하라.
- **보안 표준 (Standard):** **적합 (Compliant)**.
    - **이유 1 (Privacy):** 전화번호는 **개인정보(PII)**입니다. PK로 사용 시 로그 파일이나 참조 테이블(FK)에 평문으로 남을 위험이 큽니다.
    - **이유 2 (Immutability):** PK는 변하면 안 됩니다. 전화번호는 변경될 수 있으므로 PK로 부적합합니다.
    - **이유 3 (Performance):** 문자열보다 숫자형 시퀀스(Surrogate Key)가 인덱싱 성능이 우수합니다.
        

#### **② 모델링 도구 활용 (Tools)**

- **강의 내용:** SQL Developer의 `Data Modeler`를 사용하여 GUI로 설계 후 DDL 생성.
- **보안 표준 (Standard):** **권장 (Recommended)**.
    - 손으로 직접 DDL을 작성(Human Coding)할 때 발생하는 오타나 제약조건 누락을 방지합니다.
    - 특히 `FOREIGN KEY` 설정 시 참조 관계를 명확히 시각화하여, **고아 레코드(Orphan Record)** 발생 가능성을 차단합니다.

### **S#1. Forward Engineering (모델링 → DB 구축)**

#### **1. Scenario & Goal**

- **목표:** Oracle SQL Developer의 **Data Modeler** 기능을 사용하여 쇼핑몰 데이터베이스(`User`, `Buy`)를 시각적으로 설계(GUI)하고, 이를 **DDL(SQL)**로 자동 변환하여 DB에 구축합니다.
- **보안 포인트:**
    - 개인정보(전화번호)가 아닌 **인공 키(Surrogate Key)**를 PK로 설정하여 보안성을 강화합니다.
    - 참조 무결성(FK)을 설정하여 데이터 고립(Orphan Data)을 방지합니다.
        

#### **2. Lab Steps (GUI & SQL)**

**Step A. GUI 모델링 (Relational Model)**

1. **SQL Developer 실행:** `보기(View)` → `Data Modeler` → `브라우저(Browser)`.
2. **테이블 생성 (User):**
    
    - `Relational Model` 우클릭 → `새 릴레이션 모델`.
    - 도구 모음에서 `새 테이블` 클릭 후 캔버스 클릭.
    - **이름:** `USER_TABLE`
    - **열(Columns):** `USER_ID` (PK), `USER_NAME`, `BIRTH_YEAR`, `ADDR`, `MOBILE`.
        
3. **테이블 생성 (Buy):**
    
    - **이름:** `BUY_TABLE`
    - **열(Columns):** `BUY_ID` (PK), `PROD_NAME`, `PRICE`, `AMOUNT`.
        
4. **관계 설정 (FK):**
    
    - 도구 모음 `새 외래 키(FK)` 선택.
    - **자식(`BUY_TABLE`)** 클릭 → **부모(`USER_TABLE`)** 클릭 (Drag).
    - 설정 확인: `USER_ID`가 FK로 자동 매핑됨.
        

**Step B. DDL 생성 및 적용 (Implementation)**

- 캔버스의 `DDL 생성(원기둥 아이콘)` 클릭 → `생성` 버튼 클릭.
- 자동 생성된 스크립트 예시:
    

```SQL
-- 1. 사용자 테이블 생성 (부모)
CREATE TABLE user_table (
    user_id     NUMBER NOT NULL,      -- 인공 식별자 (권장)
    user_name   VARCHAR2(20),
    birth_year  NUMBER(4),
    addr        VARCHAR2(100),
    mobile      VARCHAR2(15)          -- 개인정보 (PK 사용 지양)
);

ALTER TABLE user_table ADD CONSTRAINT user_pk PRIMARY KEY ( user_id );

-- 2. 구매 테이블 생성 (자식)
CREATE TABLE buy_table (
    buy_id      NUMBER NOT NULL,
    user_id     NUMBER NOT NULL,      -- FK 컬럼
    prod_name   VARCHAR2(30),
    price       NUMBER(10),
    amount      NUMBER(3)
);

ALTER TABLE buy_table ADD CONSTRAINT buy_pk PRIMARY KEY ( buy_id );

-- 3. 참조 무결성(FK) 제약조건 추가
ALTER TABLE buy_table
    ADD CONSTRAINT buy_user_fk FOREIGN KEY ( user_id )
        REFERENCES user_table ( user_id )
        -- 수업 중 언급된 옵션 (삭제 제한)
        -- ON DELETE NO ACTION (Default)
;
```
### **Step C. DDL 파일 저장 (Export)**

1. DDL 미리보기 창에서 **`저장(Save)`** 버튼을 클릭합니다.
2. 파일명(`modelSchema.ddl`)을 입력하고 저장 경로를 지정합니다.
3. 저장된 파일은 추후 DB 재구축이나 형상 관리에 사용됩니다.

### **3. Verification & Error Case**

#### **Verification (검증)**



```SQL
-- 테이블 생성 확인
SELECT table_name FROM user_tables WHERE table_name IN ('USER_TABLE', 'BUY_TABLE');

-- 제약조건(PK, FK) 확인
SELECT constraint_name, constraint_type, table_name 
FROM user_constraints 
WHERE table_name IN ('USER_TABLE', 'BUY_TABLE');
-- P: Primary Key, R: Referential Integrity (FK) 확인
```

#### **⚠️ Error Case: 무결성 위배 (Integrity Violation)**

- **상황:** `USER_TABLE`(부모)에 없는 `user_id`를 `BUY_TABLE`(자식)에 넣으려 하거나, 자식이 있는 부모를 삭제하려 할 때.
- **에러 코드:** `ORA-02291` (부모 키 없음) / `ORA-02292` (자식 레코드 발견)
- **해결:**
    
    1. 데이터 입력 순서 준수: 부모(`USER`) → 자식(`BUY`).
    2. 삭제 시 정책 결정: `ON DELETE CASCADE` 사용 여부 신중 검토 (보안상 주의).

#### 1. JDBC (Java Database Connectivity)의 이해

1교시가 데이터베이스 '설계'였다면, 2교시는 **'어플리케이션 연동'**입니다. Java 프로그램이 Oracle DB에 접속하여 데이터를 조작(DML)하기 위해서는 중간 매개체인 **Driver(Connector)**가 필요합니다.

- **보안 맥락:** 어플리케이션이 DB에 접속하는 과정은 보안상 가장 취약한 지점 중 하나입니다. 소스 코드 내에 DB 계정 정보(ID/PW)가 하드코딩되는 실습 방식은 교육용이며, 실무에서는 **암호화된 설정 파일**이나 **환경 변수**를 사용해야 함을 인지해야 합니다.
    

#### 2. DB 스키마 구성 (Schema Setup)

Java 연동 테스트를 위해 DEPARTMENT(학과)와 STUDENT(학생) 테이블을 생성하고 기초 데이터를 입력합니다.

- **기존 계정 활용:** 별도의 계정 생성 없이 기존 `TEST` 계정을 사용하여 테이블을 생성합니다.
- **데이터 무결성:** 학과 정보가 먼저 존재해야 학생 정보가 참조할 수 있으므로, 테이블 생성 및 데이터 입력 순서(Dependency)가 중요합니다.
    

#### **3. 트러블 슈팅 (Troubleshooting)**

- **ClassNotFoundException:** JDBC Driver가 Build Path에 추가되지 않았을 때 발생.
- **SQLException:** 접속 URL(`jdbc:oracle:thin:@IP:PORT:SID`)이나 계정 정보 불일치 시 발생.
- **Syntax Error:** 카카오톡/웹에서 코드를 복사할 때 발생하는 따옴표 문자 깨짐 현상 수정.
    
## 개념 - DB보안 2교시_2025.11.17

### 1. 핵심 용어 (Terminology)

- **JDBC (Java Database Connectivity):** 자바 프로그램이 데이터베이스와 연결하여 데이터를 주고받을 수 있게 해주는 표준 인터페이스(API)입니다.
- **JDBC Driver (`ojdbc.jar`):** 자바 애플리케이션과 오라클 DB 사이의 **통역사** 역할을 하는 라이브러리입니다. DBMS 제조사(Oracle)마다 제공하는 파일이 다르며, 이를 프로젝트의 **Build Path(Classpath)**에 추가해야만 프로그램이 DB를 인식할 수 있습니다.
- **연결 문자열 (Connection String):** DB 접속 정보를 담은 URL입니다.
    - 형식: `jdbc:oracle:thin:@IP주소:포트번호:SID`
    - _(예: `jdbc:oracle:thin:@localhost:1521:xe`)_
        
> [!TIP] **Driver Version Check**: Oracle 11g XE 환경에서는 보통 `ojdbc6.jar` (JDK 6, 7, 8 호환) 또는 `ojdbc8.jar` (JDK 8, 11+ 호환)를 사용합니다. 프로젝트의 JDK 버전에 맞는 드라이버를 선택해야 `UnsupportedClassVersionError`를 방지할 수 있습니다.

### 2. SQL 패턴 (Syntax Pattern: Schema Setup)

교수님께서 카카오톡으로 전달해주신 **초기 데이터 구축 스크립트**입니다. JDBC 연동 테스트를 위해 `TEST` 계정에서 실행해야 합니다.

#### **A. 테이블 생성 (DDL)**



```SQL
-- 1. 학과 테이블 (PK: dept_id)
CREATE TABLE department (
    dept_id    VARCHAR2(10),
    dept_name  VARCHAR2(30) NOT NULL,
    office     VARCHAR2(30),
    CONSTRAINT pk_department PRIMARY KEY(dept_id)
);

-- 2. 학생 테이블 (PK: stu_id)
-- [주의] 현재 스키마에는 학과와의 연결 고리(FK)가 정의되지 않았음.
CREATE TABLE student (
    stu_id     VARCHAR2(20),
    name       VARCHAR2(30) NOT NULL,
    address    VARCHAR2(50),
    CONSTRAINT pk_student PRIMARY KEY(stu_id)
);
```

#### **B. 데이터 입력 (DML)**


```SQL

COMMIT;
```

### 3. Standard Check 보안성 검증

수업 중 진행된 JDBC 연결 방식과 실무 보안 표준의 차이점입니다.

#### **① DB 연결 정보 관리 (Credential Management)**

- **강의 (Lab):** 소스 코드 내에 ID/PW를 직접 입력(Hardcoding).
    - `DriverManager.getConnection(url, "test", "1234");`
- **보안 표준 (Standard):** **취약 (Vulnerable)**.
    - 소스 코드가 유출되거나 형상 관리 도구(Git)에 업로드될 경우 DB 계정 정보가 즉시 탈취됩니다.
    - **대안:** 환경 변수(Environment Variable), 별도의 설정 파일(Properties), 또는 암호화된 Vault 시스템을 사용하여 자격 증명을 분리해야 합니다.
        

#### **② 드라이버 버전 관리 (Dependency)**

- **강의 (Lab):** 교수님이 배포한 파일을 다운로드하여 수동 추가.
- **보안 표준 (Standard):** **권장 (Recommended via Maven/Gradle)**.
    - `ojdbc` 드라이버 버전에 따라 보안 패치 여부가 다릅니다. 실무에서는 **Maven**이나 **Gradle** 같은 빌드 도구를 통해 검증된 버전의 라이브러리를 자동으로 관리하고 업데이트합니다.

클릭하여 정답을 확인해보세요.

<details>

<summary>Q1. (보안) 왜 사용자 테이블의 PK로 '전화번호'를 쓰지 않고 굳이 '회원번호'를 새로 만드나요?</summary>
<br>
[🗣️ 핵심 요약]

전화번호는 **개인정보(PII)**이며 변경 가능성이 있기 때문입니다. 보안과 성능을 위해 비즈니스 의미가 없는 **대리 키(Surrogate Key)**를 사용하는 것이 표준입니다.
<br><br>
[📚 상세 설명]

1. **개인정보 노출 위험:** 전화번호를 PK로 쓰면, 자식 테이블(FK)이나 로그 파일에 전화번호가 평문으로 여기저기 저장됩니다.
    <br>
2. **불변성(Immutability) 위배:** PK는 영원히 변하지 않아야 가장 좋지만, 전화번호는 변경될 수 있습니다. PK가 바뀌면 관련된 모든 FK 데이터를 업데이트해야 하는 오버헤드가 발생합니다.
    <br>
3. 성능: 문자열(VARCHAR)보다 숫자형(NUMBER) 시퀀스가 인덱싱 및 조인 성능이 더 우수합니다.
    <br>
    </details>
    

<details>

<summary>Q2. (무결성) 부모 테이블(User)의 데이터를 삭제할 때 '참조 무결성 위배' 에러가 나는 이유는?</summary>

  

[🗣️ 핵심 요약]

자식 테이블(Buy)이 해당 부모 데이터를 **참조(FK)**하고 있기 때문입니다. 이를 방치하고 부모만 삭제하면 자식 데이터는 **고아(Orphan)**가 되어 데이터 무결성이 깨집니다.

  
  

[📚 상세 설명]

- **해결 방법 1 (삭제 제한):** 자식 데이터를 먼저 삭제하거나 FK 연결을 끊은 후 부모를 삭제합니다. (가장 안전)
- **해결 방법 2 (Cascade):** `ON DELETE CASCADE` 옵션을 사용하여 부모 삭제 시 자식도 자동 삭제되게 합니다. (편리하지만 실수로 대량 데이터 손실 위험)
- 보안 관점: 실무에서는 중요한 로그(구매 이력 등)가 사라지지 않도록 CASCADE 사용을 엄격히 제한하거나, 논리적 삭제(Logical Delete, status=&#39;N&#39; 업데이트)를 주로 사용합니다.
    
    </details>
    

<details>

<summary>Q3. (공학) Forward Engineering과 Reverse Engineering의 차이는?</summary>
<br>
[🗣️ 핵심 요약]

**Forward(순공학)**는 모델(설계도)을 짜서 DB를 구축하는 것이고, **Reverse(역공학)**는 이미 있는 DB에서 설계도를 추출해내는 것입니다.
<br><br>
[📚 상세 설명]

- **Forward:** `ERD 설계 → DDL 생성 → DB 구축`. (신규 개발 시 사용)
- Reverse: DB 딕셔너리 스캔 → ERD 복원. (레거시 시스템 분석, 보안 감사, 문서화 작업 시 필수)
    
</details>
    

<details>

<summary>Q4. (JDBC 보안) 소스 코드에 DB ID/PW를 하드코딩하면 안 되는 이유는?</summary>
<br>
[🗣️ 핵심 요약]

소스 코드가 형상 관리 시스템(Git)이나 서버에 업로드될 때 **자격 증명(Credential)**이 평문으로 노출될 수 있기 때문입니다.
<br><br>
[📚 상세 설명]

- **보안 위협:** 공격자가 소스 코드를 입수하면 즉시 DB에 접속하여 데이터를 탈취하거나 파괴할 수 있습니다.
- **대응 방안:**
    
    1. **환경 변수(OS Environment Variable)** 사용.
    2. 권한이 제한된 **설정 파일(Properties)** 별도 관리.
    3. 암호화된 Vault 시스템 연동.
        
</details>
