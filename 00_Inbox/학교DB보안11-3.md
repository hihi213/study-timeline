**범위:** PDF p~49, p~71 **주제:** Oracle XE 환경에서의 보안 기능(VPD, FGA) 대체 구현 실습

### 1. 🔐 VPD(Virtual Private Database) 대체 구현 (p~49)

**핵심 개념:** 원래 VPD는 데이터베이스 엔진 레벨에서 자동으로 `WHERE` 절을 붙여주는 고급 기능입니다. 하지만 우리가 쓰는 XE 버전에서는 지원되지 않으므로, **뷰(View)로 조회를 제한**하고 **트리거(Trigger)로 수정을 제한**하여 비슷한 효과를 냅니다.

#### **[1단계] 테이블 및 계정 준비 (p~46)**

관리자(`SYSTEM` 또는 `TEST` 계정)에서 테이블을 만들고, `login_id` 컬럼을 추가하여 오라클 접속 계정과 매핑합니다.


```SQL
-- 테이블 생성 (login_id 포함) 
CREATE TABLE employee2 (
    emp_id      NUMBER PRIMARY KEY,
    name        VARCHAR2(100),
    department  VARCHAR2(50),
    salary      NUMBER,
    ssn         VARCHAR2(20),
    login_id    VARCHAR2(50)   -- ★ 접속한 계정명(USER)과 비교할 컬럼
);

-- 데이터 삽입 예시 
INSERT INTO employee2 VALUES (1001, '홍길동', '인사팀', 5000, '900101-…', 'EMP_1001');
```

#### **[2단계] 조회 통제: 뷰(View) 생성 (p)**

사용자별로 볼 수 있는 데이터가 다른 뷰를 생성합니다.

- **일반 직원용 (`vw_my_profile`):** `WHERE login_id = USER` 조건을 넣어 본인 행만 보이게 합니다.
- **인사팀용 (`vw_hr_view`):** `ssn` 등 민감 컬럼을 제외하고 조회합니다.
- **관리자용 (`vw_admin_view`):** 모든 데이터를 조회합니다.

```SQL
-- 일반 직원용 뷰 (본인 데이터만 조회) 
CREATE OR REPLACE VIEW vw_my_profile AS
SELECT * FROM employee2
WHERE login_id = USER;
```

#### **[3단계] 수정 통제: 트리거(Trigger) 생성 (p) ★중요**

뷰만으로는 `UPDATE`나 `DELETE`를 완벽히 막기 어렵거나 로직이 복잡할 수 있어, 테이블에 직접 트리거를 걸어 **타인의 데이터를 건드리면 에러를 발생**시킵니다.


```SQL
-- 본인 정보만 수정 가능하게 하는 트리거 
CREATE OR REPLACE TRIGGER trg_emp_self_update
    BEFORE UPDATE OR DELETE ON employee2
    FOR EACH ROW
BEGIN
    -- 접속자(USER)와 데이터 주인(:OLD.login_id)이 다르면 차단
    IF USER <> :OLD.login_id THEN
        RAISE_APPLICATION_ERROR(-20001, '자신의 정보만 수정하거나 삭제할 수 있습니다.');
    END IF;
END;
/
```

### 2. 🕵️‍♀️ FGA(Fine-Grained Auditing) 대체 구현 (p~71)

**핵심 개념:** FGA는 특정 컬럼(예: 연봉, 주민번호)을 조회하거나 수정할 때 자동으로 로그를 남기는 기능입니다. XE에서는 이를 지원하지 않으므로, **별도의 로그 테이블**을 만들고 **트리거**를 이용해 변경 사항을 기록합니다.

#### **[1단계] 감사 로그 테이블 생성 (p)**

누가, 언제, 무엇을 건드렸는지 저장할 껍데기 테이블을 만듭니다.


```SQL
-- 로그 테이블 생성 
CREATE TABLE audit_log (
    log_id        NUMBER PRIMARY KEY,
    username      VARCHAR2(50),
    access_time   DATE,
    action_type   VARCHAR2(10),     -- INSERT, UPDATE, DELETE
    accessed_col  VARCHAR2(50),     -- 건드린 컬럼 (SSN, SALARY 등)
    accessed_data VARCHAR2(200)     -- 변경 내용
);
```

#### **[2단계] 민감 정보 감시 트리거 (p)**

주민번호(`SSN`)가 변경(`UPDATE`)될 때 기록을 남깁니다.


```SQL
-- SSN 변경 감시 트리거 
CREATE OR REPLACE TRIGGER trg_audit_ssn_update
    AFTER UPDATE OF ssn ON users
    FOR EACH ROW
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'UPDATE', 'SSN', :OLD.ssn || ' -> ' || :NEW.ssn);
END;
/
```

#### **[3단계] 조건부 감시 트리거 (p) ★중요**

모든 변경을 기록하는 게 아니라, **특정 조건(예: 급여가 10,000 이상일 때)**을 만족할 때만 로그를 남기는 고급 기법입니다. `WHEN` 절을 사용합니다.



```SQL
-- 고액 연봉(10,000 초과) 변경 시에만 기록 
CREATE OR REPLACE TRIGGER trg_audit_salary_update
    AFTER UPDATE OF salary ON users
    FOR EACH ROW
    WHEN (NEW.salary > 10000)  -- ★ 조건절: 이 조건이 참일 때만 트리거 실행
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'UPDATE', 'SALARY', :OLD.salary || ' -> ' || :NEW.salary);
END;
/
```

### 🎓 결석하신 부분 학습 포인트

1. **VPD 대체:** XE 버전에서는 보안을 위해 `View`(조회 제한)와 `Trigger`(수정 제한)를 조합해서 사용해야 한다는 점을 이해했는지 묻는 문제가 나올 수 있습니다.
2. **Trigger의 WHEN 절:** p의 실습처럼 **"조건부 트리거"**(`WHEN (NEW.salary > 10000)`)를 작성할 수 있는지가 핵심 구현 포인트입니다.
    

## 상세 버전
### 1. VPD (Virtual Private Database)

VPD는 데이터베이스 접근을 **통제(Control)**하는 데 중점을 둔 기술입니다.

- **핵심 정의:** **행 단위 보안 (Row-Level Security)**
    - 사용자마다 **접근 가능한 데이터(행)** 를 자동으로 제한하는 기술입니다.
- **작동 원리:** 사용자가 SQL을 실행하면, DB가 자동으로 **`WHERE` 절(조건)**을 추가하여 실행합니다.
    - _(예: `SELECT * FROM emp` → `SELECT * FROM emp WHERE 부서 = '내부서'`)_
- **핵심 패키지:** **`DBMS_RLS`** (RLS = Row Level Security)

### **1단계: 실습용 계정 및 권한 생성**

작업 위치: 관리자 계정 (SYSTEM 또는 SYSDBA)

기존 계정을 정리하고, 역할별(인사팀, 일반직원, 관리자) 계정을 새로 생성합니다.

```SQL
-- 1. 기존 계정이 있다면 삭제 (초기화)
DROP USER HR_USER CASCADE;
DROP USER EMP_1001 CASCADE;
DROP USER ADMIN_USER CASCADE;

-- 2. 계정 생성 (비밀번호: 1234)
CREATE USER HR_USER IDENTIFIED BY 1234 ACCOUNT UNLOCK;
CREATE USER EMP_1001 IDENTIFIED BY 1234 ACCOUNT UNLOCK;
CREATE USER ADMIN_USER IDENTIFIED BY 1234 ACCOUNT UNLOCK;

-- 3. 기본 접속 권한 부여
GRANT CONNECT TO HR_USER;
GRANT CONNECT TO EMP_1001;
GRANT CONNECT TO ADMIN_USER;
```

### **3단계: 사용자별 맞춤형 뷰(View) 생성 (조회 보안)**

## 2. FGA (Fine-Grained Auditing)

FGA는 데이터 접근을 **감시(Audit)** 하고 기록을 남기는 데 중점을 둔 기술입니다. 단순 감사가 아니라 **'정밀'** 감사라는 점이 중요합니다.

- **핵심 정의:** **조건 기반/컬럼 단위 정밀 감사**
    - '급여(`SALARY`)' 컬럼을 조회했거나, '급여가 10,000 이상'인 데이터를 조회했을 때처럼, **특정 컬럼이나 조건**에 대해서만 콕 집어 기록합니다.
- **핵심 패키지:** **`DBMS_FGA`**
- **로그 확인 뷰:** **`DBA_FGA_AUDIT_TRAIL
### **1단계: 감사 로그(Audit Log) 저장용 테이블 생성**

작업 위치: TEST 계정

감사 기록이 저장될 테이블과 순번 자동 생성을 위한 시퀀스를 만듭니다.

```SQL
-- 1. 시퀀스 생성 (로그 ID 자동 증가용)
CREATE SEQUENCE audit_log_seq
START WITH 1
INCREMENT BY 1
NOCACHE
NOCYCLE; 

-- 2. 감사 로그 테이블 생성
CREATE TABLE audit_log (
    log_id        NUMBER PRIMARY KEY,
    username      VARCHAR2(50),    -- 변경한 사용자
    access_time   DATE,            -- 변경 일시
    action_type   VARCHAR2(10),    -- 동작 유형 (INSERT/UPDATE/DELETE)
    accessed_col  VARCHAR2(50),    -- 접근한 컬럼명 (SSN 등)
    accessed_data VARCHAR2(200)    -- 변경된 데이터 내용 (이전값 -> 새값)
); 

-- 3. 로그 ID 자동 입력 트리거 (INSERT 시 시퀀스 값 자동 할당)
CREATE OR REPLACE TRIGGER trg_audit_log_id
BEFORE INSERT ON audit_log
FOR EACH ROW
BEGIN
    :NEW.log_id := audit_log_seq.NEXTVAL;
END;
/ 
```

### **2단계: 민감 정보(SSN) 감시 트리거 생성**

작업 위치: TEST 계정

주민등록번호(ssn)가 변경되거나 삭제될 때 로그를 남깁니다.

```SQL
-- 1. SSN 수정(UPDATE) 감시 트리거
CREATE OR REPLACE TRIGGER trg_audit_ssn_update
AFTER UPDATE OF ssn ON employee2  -- (교재의 users 테이블 대신 앞서 만든 employee2 사용)
FOR EACH ROW
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'UPDATE', 'SSN', :OLD.ssn || ' -> ' || :NEW.ssn);
END;
/ 

-- 2. 삭제(DELETE) 감시 트리거
CREATE OR REPLACE TRIGGER trg_audit_ssn_delete
BEFORE DELETE ON employee2
FOR EACH ROW
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'DELETE', 'SSN', :OLD.ssn);
END;
/ 
```

---

### **3단계: 중요 데이터(고액 연봉) 감시 트리거 생성**

작업 위치: TEST 계정

급여(salary)가 10,000을 초과하는 값으로 입력되거나 수정될 때만 로그를 남깁니다

```SQL
-- 1. 급여 수정(UPDATE) 감시 (새 값이 10000 초과일 때만)
CREATE OR REPLACE TRIGGER trg_audit_salary_update
AFTER UPDATE OF salary ON employee2
FOR EACH ROW
WHEN (NEW.salary > 10000)
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'UPDATE', 'SALARY', :OLD.salary || ' -> ' || :NEW.salary);
END;
/ 

-- 2. 급여 입력(INSERT) 감시 (10000 초과일 때만)
CREATE OR REPLACE TRIGGER trg_audit_salary_insert
AFTER INSERT ON employee2
FOR EACH ROW
WHEN (NEW.salary > 10000)
BEGIN
    INSERT INTO audit_log (username, access_time, action_type, accessed_col, accessed_data)
    VALUES (USER, SYSDATE, 'INSERT', 'SALARY', :NEW.salary);
END;
/ 
```

### **4단계: 동작 테스트**

작업 위치: TEST 계정

실제 데이터를 조작하여 audit_log 테이블에 기록이 남는지 확인합니다.

```SQL
-- 1. 고액 연봉자(12000) 추가 -> INSERT 트리거 작동
INSERT INTO employee2 VALUES (1006, '조세호', '총무팀', 12000, '950606-6789012', 'EMP_1006');
COMMIT; 

-- 2. 급여 인상 (9000 -> 16000) -> UPDATE 트리거 작동
-- (주의: emp_id=1001 등 기존 데이터에 맞게 수정 필요)
UPDATE employee2 SET salary = 16000 WHERE emp_id = 1001; 
COMMIT; 
-- 3. 주민번호 변경 시도 -> SSN UPDATE 트리거 작동
UPDATE employee2 SET ssn = '900101-9999999' WHERE emp_id = 1001;
COMMIT; 
-- 4. 직원 삭제 -> SSN DELETE 트리거 작동
DELETE FROM employee2 WHERE emp_id = 1003;
COMMIT; 

-- 5. 감사 로그 확인
SELECT * FROM audit_log ORDER BY log_id; 
```

## **'보안 관점에서의 인덱스 활용(함수 기반 인덱스 & 리버스 키 인덱스)'**

이 과정은 인덱스를 생성할 때도 **민감 정보 노출을 최소화**하고, **공격자가 데이터 패턴을 유추하기 어렵게 만드는** 보안 기법입니다.

---

### **1단계: 실습용 고객 테이블 생성**

작업 위치: TEST 계정

실습을 위해 고객 정보(customer) 테이블을 생성하고 데이터를 입력합니다

```SQL
-- 1. 고객 테이블 생성
CREATE TABLE customer (
    cust_id     NUMBER PRIMARY KEY,
    name        VARCHAR2(100),
    email       VARCHAR2(100),
    phone       VARCHAR2(20),
    credit_card VARCHAR2(20),
    ssn         VARCHAR2(20)  -- 민감 정보(주민번호)
);

-- 2. 샘플 데이터 삽입
INSERT INTO customer VALUES (1, '홍길동', 'hong@test.com', '010-1111-2222', '1234-5678', '900101-1234567');
INSERT INTO customer VALUES (2, '김철수', 'kim@test.com', NULL, '4321-8765', '950505-2345678');
COMMIT;
```

### **2단계: 함수 기반 인덱스 (Function-Based Index) - 마스킹 검색**

**목적:** 주민번호(`ssn`) 전체에 인덱스를 걸면 보안상 위험하므로, **생년월일(앞 6자리)로만 검색**할 수 있도록 제한적인 인덱스를 만듭니다

```SQL
-- 1. 주민번호 앞 6자리(생년월일)만 인덱싱 (전체 주민번호 노출 방지)
CREATE INDEX idx_cust_ssn_prefix
ON customer(SUBSTR(ssn, 1, 6)); 

-- 2. 인덱스 활용 검색 테스트
-- (WHERE 절에 인덱스 생성 시 사용한 함수 그대로 사용)
SELECT * FROM customer
WHERE SUBSTR(ssn, 1, 6) = '900101'; 
```

### **3단계: 리버스 키 인덱스 (Reverse Key Index) - 패턴 은폐**

**목적:** `cust_id`가 1, 2, 3… 처럼 순차적으로 증가할 경우, 공격자가 **다음 ID를 예측하여 무차별 대입 공격(Brute-force)**을 하기 쉽습니다. 이를 방지하기 위해 키 값을 역순으로 저장하여 물리적 저장 위치를

```SQL
-- 1. 리버스 키 인덱스 생성
-- (키 값이 1001 -> 1001을 뒤집어서 저장, 연속된 값의 물리적 위치를 섞음)
CREATE INDEX idx_cust_id_reverse
ON customer(cust_id) REVERSE; 

-- 2. 일반 인덱스와의 차이점
-- 일반 인덱스: 1001, 1002, 1003이 인접하게 저장됨 (예측 쉬움)
-- 리버스 인덱스: 1001(1001), 2001(1002), 3001(1003) 처럼 분산 저장됨 (패턴 숨김)
```

### **4단계: 부분 인덱스 (Partial Index) - 접근 최소화**

**목적:** 전화번호(`phone`)가 있는 고객만 마케팅 대상이 되므로, `NULL`이 아닌 데이터만 인덱싱하여 불필요한 데이터 노출을 줄이고 성능을 높입니다

```SQL
-- 전화번호가 존재하는 고객만 인덱싱
CREATE INDEX idx_cust_phone_valid
ON customer(phone)
WHERE phone IS NOT NULL; 
```
