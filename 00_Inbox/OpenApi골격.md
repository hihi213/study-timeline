## 정리

### 1) 이 항목은 무엇인가 (What)

-   **한 줄 요약**: 우리 프로젝트의 모든 API에 대한 '설계도'이자 '사용 설명서'를 만들기 위한 표준 형식(OpenAPI)을 도입하고, 그 첫 번째 뼈대 파일을 만드는 작업입니다.
-   **시스템 내 위치**: API 설계 및 문서화 계층입니다. 실제 실행되는 코드는 아니지만, 코드가 어떤 모양이어야 하는지를 정의하는 '명세(Specification)' 또는 '계약(Contract)'의 역할을 합니다. 프론트엔드 개발자와 백엔드 개발자 모두 이 문서를 보고 소통하게 됩니다.
-   **용어 정의**:
    -   **OpenAPI**: REST API를 설명하기 위한 표준 명세입니다. YAML이나 JSON 형식으로 작성하며, 어떤 엔드포인트가 있고, 어떤 파라미터를 받으며, 무엇을 응답하는지 등을 정의합니다. ^9g70lh
    -   **Swagger**: OpenAPI 명세를 기반으로 문서를 시각화해주거나(`Swagger UI`), 코드를 생성해주는(`Swagger Codegen`) 등 다양한 기능을 제공하는 도구 세트입니다. 흔히 OpenAPI와 같은 의미로 쓰이기도 합니다.
    -   **`openapi.yml`**: 우리가 직접 API 명세를 작성할 YAML 파일의 이름입니다.
    -   **RFC 7807**: API 에러 응답을 위한 표준 규격입니다. `{"error": "bad request"}`처럼 제각각인 에러 메시지 대신, `type`, `title`, `status`, `detail` 등 정해진 필드를 사용해 일관된 방식으로 에러를 표현하도록 합니다.
    -   **API-First Design**: 실제 코드를 작성하기 전에, API 명세(계약)를 먼저 설계하고 확정하는 개발 방식입니다. 백엔드와 프론트엔드가 이 명세만 보고 병렬로 개발을 진행할 수 있습니다.

### 2) 왜 지금 이걸 구현하는가 (Why)

-   **사용자 여정/운영 관점**: API의 '단일 진실 공급원(Single Source of Truth)'이 됩니다. 프론트엔드 개발자는 이 문서만 보면 백엔드 API를 어떻게 호출할지 알 수 있고, 백엔드 개발자는 이 문서를 청사진 삼아 개발하면 됩니다. "API 이거 어떻게 쓰는 거였죠?" 같은 불필요한 소통 비용을 극적으로 줄여줍니다.
-   **이번 주 Gate/DoD와 연결**: 직접적인 연관은 없지만, 앞으로 만들 모든 API(인증, 아이템 등록 등)의 기본 구조와 에러 형식을 지금 정의함으로써 후속 개발을 더 빠르고 예측 가능하게 만듭니다. 특히 **W8의 `OpenAPI 스냅샷 회귀(CI)`** 목표를 달성하기 위한 첫걸음입니다.
-   **후속 스프린트와의 연결**: 앞으로 W2~W6에서 개발할 모든 API는 이 OpenAPI 파일에 먼저 정의되고 구현될 것입니다.

### 3) 구현 방식 선택지

#### 옵션 A: `Design-First` - 수동으로 `openapi.yml` 파일 작성

-   **어떻게?**: IDE(VS Code + Extension 추천)를 이용해 `openapi.yml` 파일을 직접 손으로 작성합니다. API 설계가 끝나면 이 파일을 기준으로 코드를 구현합니다. 문서는 Swagger UI Docker 이미지 등을 이용해 별도로 띄워서 확인합니다.
-   **언제 좋음?**: API 설계를 코드 구현과 명확히 분리하고 싶을 때. API 명세를 '설계도'로서 엄격하게 관리하고 싶을 때 좋습니다. API-First 원칙을 제대로 지킬 수 있습니다.
-   **언제 나쁨?**: 코드 수정 사항을 `openapi.yml` 파일에 반영하는 것을 잊기 쉽습니다. 개발 규율이 잡혀있지 않으면 문서와 실제 코드가 따로 놀게 될 위험이 있습니다.
-   **리스크**: 문서가 실제 구현과 달라져서 오히려 개발에 혼란을 주는, '죽은 문서'가 될 수 있습니다.
-   **확장성**: 좋습니다. API 설계 리뷰 프로세스가 있는 큰 조직에서 선호하는 방식입니다.

#### 옵션 B: `Code-First` - 코드에서 명세 자동 생성 (e.g., `springdoc-openapi`)

-   **어떻게?**: `springdoc-openapi` 같은 라이브러리를 프로젝트에 추가합니다. 그러면 라이브러리가 `@RestController` 같은 Java 어노테이션을 분석해서 OpenAPI 명세를 자동으로 생성하고, `/swagger-ui.html` 같은 경로에 API 문서 페이지까지 만들어 줍니다.
-   **언제 좋음?**: 문서와 코드를 항상 100% 일치시키고 싶을 때. 빠르게 API 문서를 만들고 싶을 때 좋습니다.
-   **언제 나쁨?**: API 설계에 대한 깊은 고민 없이 바로 코드부터 짜게 될 수 있습니다. 명세가 코드의 '결과물'이 되므로, 설계의 중심을 잡기 어렵습니다. 상세한 설명을 위해 코드에 어노테이션(`@Operation`, `@ApiResponse` 등)이 많아져 지저분해 보일 수 있습니다.
-   **리스크**: 개발자가 어노테이션으로 설명을 추가하는 것을 잊으면, 기능은 있지만 설명이 부실한 문서가 만들어지기 쉽습니다.
-   **확장성**: 작은 프로젝트나 백엔드 개발자가 API 설계를 전담하는 팀에 적합합니다.

### 4) 선택 요청

**API 명세서를 어떻게 관리하시겠어요?**

-   **옵션 A**: `Design-First`, 직접 `openapi.yml` 파일을 작성하고 관리한다.
-   **옵션 B**: `Code-First`, 코드에서 자동으로 생성하도록 한다.

**선택 기준**: **API를 '설계도'로서 엄격하게 다룰 것인가 (A)**, 아니면 **코드의 '결과물'로서 항상 최신 상태를 유지하는 데 집중할 것인가 (B)**에 따라 결정할 수 있습니다.

### 인터뷰 브리프 (3/3)

**Title**: 하이브리드 API 명세 시스템 구축 (Design-Seed + Code-First + CI 검증)

#### STAR 요약
-   **Situation**: 프로젝트 초기, API 명세가 코드와 불일치하는 '문서 드리프트' 문제를 예방하고, 프론트엔드와의 협업을 위한 명확한 'API 계약'이 필요했습니다.
-   **Task**: API 설계를 강제하면서도 개발 편의성을 해치지 않는 지속 가능한 API 문서화 시스템을 구축하는 과제를 맡았습니다.
-   **Action**: `Design-First`와 `Code-First` 방식의 장단점을 분석 후, 두 가지를 결합한 하이브리드 방식을 직접 설계했습니다. 핵심 계약은 `seed/openapi.yml`에 먼저 정의하고, `springdoc`으로 코드에서 전체 명세를 자동 생성한 뒤, CI 파이프라인에서 `openapi-diff` 도구로 두 명세의 차이점을 비교하여 '설계 드리프트'를 자동 검증하는 시스템을 구축했습니다.
-   **Result**: "설계가 먼저"라는 원칙을 CI를 통해 강제하는 자동화된 시스템을 완성했습니다. 문서와 코드가 항상 일치함을 보장하고, 의도치 않은 변경(Breaking Change)을 조기에 차단하는 안전망을 확보했습니다.

#### 고려한 옵션 요약
* **`Design-First` (수동 관리)**: 설계 규율은 좋으나, 문서와 코드 간의 불일치(Drift)가 발생하기 쉬움.
* **`Code-First` (자동 생성)**: 문서는 항상 최신이지만, API 설계에 대한 사전 고민 없이 코드가 난립할 위험.
* **하이브리드 방식 (채택)**: `Design-First`의 계약 중심 접근법과 `Code-First`의 자동화를 결합하여 두 방식의 단점을 모두 보완.

#### 최종 선택 & 이유
* **신뢰성 (Reliability)**: CI를 통한 자동 검증으로 API 명세의 신뢰도를 극대화했습니다.
* **개발자 경험 (DX)**: 개발자는 코드에 집중하면 문서가 자동으로 생성되고, 설계 변경 시에는 CI가 명확하게 알려주므로 실수를 줄이고 생산성을 높입니다.
* **지속 가능성 (Sustainability)**: 프로젝트가 커지고 팀원이 늘어나도, 설계 원칙이 코드가 아닌 시스템을 통해 유지되므로 장기적으로 안정적인 운영이 가능합니다.

#### 구현 하이라이트
* `seed/openapi.yml`에 RFC7807 표준 에러와 같은 핵심 계약을 먼저 정의하여 프로젝트 전반의 일관성을 확보.
* GitHub Actions 워크플로우를 설계하여, PR마다 임시로 서버를 실행하고 `curl`로 런타임 명세를 추출.
* `openapi-diff`(npm) 스크립트를 CI에 통합하여 Seed 파일과 런타임 명세 간의 차이점을 자동으로 비교 및 차단.
* `Makefile`에 `make api-diff` 명령어를 추가하여 개발자가 로컬에서도 CI 검증을 미리 수행할 수 있도록 지원.

#### 증빙 지표
* **Drift 감지 시간**: PR 생성 후 CI 실행 완료까지 약 1~2분 내외. (수동 리뷰 대비 대폭 단축)
* **문서 정확도**: 100% (CI 통과 시 코드와 문서의 일치 보장)
* **설계 변경 프로세스**: 의도된 변경 시, `seed/openapi.yml` 파일을 먼저 수정하고 PR에 함께 제출하도록 프로세스 정립.

#### 리스크 & 완화
* **리스크**: CI 검증 파이프라인 자체가 복잡해지거나 실패하여 병목이 될 수 있음.
* **완화**: `Makefile`을 통해 로컬에서도 동일한 검증 스크립트를 실행할 수 있게 하여, CI 실패 시 개발자가 빠르게 원인을 파악하고 수정하도록 지원.

#### 다음에 할 일 (Next)
* API 버전 관리 전략과 연동하여, 이전 버전과의 하위 호환성(Backward Compatibility)을 깨뜨리는 변경을 자동으로 감지하는 규칙 추가.
* 생성된 OpenAPI 문서를 기반으로 API 클라이언트 SDK나 테스트 케이스를 자동으로 생성하는 방안 모색.

#### 예상 꼬리질문 & 짧은 답
1.  **"왜 CI에서 서버를 직접 띄워서 명세를 추출했나?"**
    컴파일 타임에 생성된 명세는 실제 런타임 환경(보안 필터 등)의 영향을 완벽히 반영하지 못할 수 있습니다. 가장 정확한 '실행 결과물'을 검증하기 위해 실제 서버를 구동했습니다.
2.  **"단순 `diff`가 아니라 `openapi-diff` 같은 전문 도구를 쓴 이유는?"**
    단순 텍스트 비교는 주석이나 순서 변경 등 비기능적 변화에도 실패합니다. `openapi-diff`는 OpenAPI의 구조(Schema)를 이해하고 의미론적으로 중요한 변경(breaking change)만 선별하여 알려주기 때문에 더 정교한 검증이 가능합니다.
3.  **"이 방식이 1인 프로젝트에 과하다고 생각하지 않나? (Over-engineering)"**
    '좋은 설계를 강제하는 시스템'을 초기에 구축하는 것은 장기적으로 기술 부채를 줄이는 가장 효과적인 투자라고 생각합니다. 팀원이 늘어날수록 이 시스템의 가치는 기하급수적으로 커질 것입니다.

#### 이력서 한 줄 요약
"CI/CD와 `openapi-diff`를 활용하여 `Design-First`와 `Code-First`의 장점을 결합한 하이브리드 API 문서화 시스템을 구축, API 명세와 코드 간의 불일치를 자동 검증하여 설계 일관성을 확보함."

#### 60초 데모 스크립트
1.  **(문제)** "API 문서는 코드와 달라지기 쉽상이며, 이는 협업 비용을 증가시키는 주된 원인이었습니다."
2.  **(선택)** "이를 해결하기 위해, 핵심 설계는 'Seed 파일'에 먼저 정의하고, 상세 내용은 코드에서 자동 생성하되, 그 둘의 차이를 CI에서 자동으로 비교하는 하이브리드 전략을 설계했습니다."
3.  **(흐름)** "개발자가 PR을 올리면, Github Actions가 서버를 띄워 실제 런타임 명세를 추출하고, `openapi-diff`가 Seed 파일과 비교합니다. 만약 설계와 다른 코드가 있다면 CI는 실패합니다."
4.  **(지표)** "이 시스템 덕분에 문서 정확도는 100%를 유지하고, 의도치 않은 설계 변경은 PR 단계에서 2분 안에 자동으로 차단됩니다."
5.  **(다음)** "이제 이 검증 시스템에 '하위 호환성' 규칙을 추가하여, 더 안정적인 API 운영 기반을 마련할 계획입니다."


아래는 네가 방금 구현한 **OpenAPI 하이브리드(Seed + Code-Gen + CI Diff)** 기반 문서 시스템에 대한 **면접용 브리프**야. 그대로 복붙해서 포트폴리오/면접 노트로 써도 돼.

# **인터뷰 브리프 — OpenAPI 하이브리드 문서 시스템**

  

**Title**: DormMate API — OpenAPI 하이브리드(Design-Seed + Code-Gen + CI Diff) 도입

**기간/역할**: 10주 MVP 초반(W1~W2) · 백엔드 단독(설계/구현/CI)

  

## **STAR 요약**

- **S(상황)**: 10주 안에 작동+증빙 중심의 MVP를 만들어야 했고, 문서-코드 드리프트가 발생하기 쉬운 1인 개발 환경.
    
- **T(과제)**: REST 기준(409/422/423/429, RFC7807)을 일관되게 강제하고, 변화가 생기면 **자동으로** 감지/차단하는 체계를 구축.
    
- **A(행동)**:
    
    1. 얇은 **Design-Seed**(api/openapi.yml)로 핵심 계약 고정
        
    2. **springdoc**로 런타임 **Code-Gen**
        
    3. **scripts + Makefile + GitHub Actions**로 **Seed↔Generated Diff**를 CI 게이트로 운영
        
    4. **dev/prod 환경 분리**로 Swagger UI 보안
        
    5. **버전 스냅샷**(api/versions/v0.1.0.yml)로 하위 호환 검토
        
    
- **R(결과)**: 코드 변경 시 문서-코드 불일치가 **자동 검출/차단**되는 파이프라인 완성. 팀 규약(에러/보안/상태코드)이 Seed로 표준화되고, 실행/검증은 make api-*로 일상화.
    

  

## **고려했던 옵션 & 트레이드오프**

- **A. Design-First(수기 관리)**: 설계 통제력↑ / 동기화 비용↑, 드리프트 위험.
    
- **B. Code-First(주석→자동생성)**: 속도↑ / 설계 품질 설득력↓(URI 난잡화 리스크).
    
- **C. 하이브리드(선택)**: **얇은 Seed로 핵심 계약 고정 + 코드 생성 + CI Diff 강제** — 초기 셋업 약간↑ 대신 장기 유지보수성·학습·속도 균형.
    

  

## **최종 선택 & 이유(핵심 3가지)**

- **설계 가시성**: 409/422/423/429, RFC7807, 보안스킴(JWT)을 **Seed에 못박아** 면접/협업에서 설계 의도를 설명 가능.
    
- **실행 일관성**: 실제 서버가 내놓는 문서를 **런타임에서 덤프**해 비교 → “돌아가는 코드 기준”으로 검증.
    
- **자동 품질 게이트**: CI **Diff Fail**을 통해 의도되지 않은 계약 변경을 차단(Seed 업데이트 없으면 머지 불가).

## **예상 꼬리질문 & 짧은 답**

1. **왜 폴링 먼저, SSE는 나중?**
    
    10주 MVP의 “작동+증빙” 우선. 폴링은 인프라 요구가 낮고 **커서 계약**을 먼저 고정할 수 있음. R1에서 SSE로 전환하되 계약은 그대로 재사용.
    
2. **왜 423을 DB가 아닌 앱에서 판정?**
    
    DB의 resource_locks는 **근거 데이터**만 저장. 차단 로직을 앱 미들웨어에 두면 락 GC/예외 케이스 처리 유연성↑, DB 트리거 복잡성↓.
    
3. **설계가 SSoT면 코드-퍼스트 장점은?**
    
    런타임 생성으로 실제 동작을 반영하니 **드리프트 탐지**가 확실. Seed는 얇게 핵심 계약만 고정해 양쪽 장점을 취함.
    
4. **RFC7807을 왜 Seed에?**
    
    에러 형식이 표준화되면 테스트/로깅/모니터링이 단순해지고, 면접에서 **상태코드·문제세부**를 근거있게 설명 가능.
    
5. **호환성 정책은?**
    
    api/versions/에 스냅샷 저장, **호환성 체크 타깃**으로 비교. 브레이킹 체인지 시 메이저 버전업 원칙 적용.
    
6. **왜 Makefile로 래핑?**
    
    로컬=CI 명령 일치. “명령어를 외우지 않아도 되는 자동화”는 1인 개발의 실수율↓.
