## Topic 1. PL/SQL 데이터 마스킹 (Data Masking Logic)

### 1) 📌 One-Liner (면접 즉답)

- DB 내부에서 데이터를 조회할 때, 애플리케이션 레벨이 아닌 **프로시저 레벨에서 즉시 마스킹(Masking)**하여 원본 데이터 유출을 원천 차단하는 기법입니다. `(Data Privacy)`
    

### 2) 📘 Theory & Policy (개념 & 정책)

- **정의**: 특정 사용자(개발자, DB 운영자)가 조회할 때 민감 정보(이름, 주민번호 등)를 부분적으로 가려서 보여주는 로직.
- **Security Boundary**: **Data Access Layer**. 데이터가 DB에서 나가는 시점에 이미 가공되어 있으므로, 네트워크 스니핑이나 애플리케이션 로그 유출 시에도 원본이 보호됨.
- **Architecture**: `SUBSTR`, `||` (연결 연산자) 등을 활용해 변수 단계에서 가공 후 출력.
    

### 3) 🛡️ Security Audit (취약점 및 권장사항)

- **Attack Surface**: 마스킹 로직이 단순하거나(규칙 유추 가능), 권한 관리가 미흡하여 `EXECUTE` 권한이 남발되면 원본 데이터 추론 가능.
- **Best Practice**:
    - 테이블 컬럼 타입 변경에 유연하게 대응하기 위해 `%TYPE` 참조 변수 사용.
    - 입력값 검증(Validation) 로직 포함 권장.
        

### 4) 💻 SQL Workflow (실습 로그)

(Scenario: `userTBL`의 사용자 이름을 조회하되, 첫 글자만 노출하고 나머지는 '00'으로 마스킹하여 출력하는 프로시저 작성)



```SQL
-- 1. [Setup] 실습용 테이블 및 데이터 생성 (카카오톡 공유 코드)
CREATE TABLE userTBL (
    userID CHAR(8) NOT NULL PRIMARY KEY,
    userName NVARCHAR2(10) NOT NULL,
    birthYear NUMBER(4) NOT NULL,
    addr NCHAR(2) NOT NULL,
    mobile1 CHAR(3), mobile2 CHAR(8),
    height NUMBER(3), mDate DATE
);

-- (데이터 INSERT 구문은 생략, 10건 적재 완료)
COMMIT;

-- 2. [Implementation] 마스킹 프로시저 생성
CREATE OR REPLACE PROCEDURE proc_mask_name (
    p_id IN userTBL.userID%TYPE -- 입력: 사용자 ID
)
IS
    v_name userTBL.userName%TYPE; -- 변수: 이름
    v_year userTBL.birthYear%TYPE; -- 변수: 생년
BEGIN
    -- ID로 조회하여 이름과 생년 추출
    SELECT userName, birthYear
      INTO v_name, v_year
      FROM userTBL
     WHERE userID = p_id;

    -- [Security Logic] 이름 마스킹 (첫 글자 + '00')
    DBMS_OUTPUT.PUT_LINE('Masked Name: ' || SUBSTR(v_name, 1, 1) || '00');
    DBMS_OUTPUT.PUT_LINE('Birth Year: ' || v_year);
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('존재하지 않는 ID입니다.');
END;
/

-- 3. [Verification] 실행 테스트
SET SERVEROUTPUT ON;
EXEC proc_mask_name('JYP');
```

- 🚨 Result:
    - 입력: `JYP` (조용필)
    - 출력: `Masked Name: 조00` (마스킹 적용 확인)

## Topic 2. 소스 코드 난독화 (PL/SQL Wrapping)

### 1) 📌 One-Liner (면접 즉답)

- PL/SQL 소스 코드가 `USER_SOURCE` 딕셔너리에 평문으로 저장되는 것을 방지하기 위해, **`DBMS_DDL.CREATE_WRAPPED`** 등을 사용하여 코드를 알아볼 수 없게 암호화(난독화)하는 보안 기법입니다. `(Intellectual Property)`
    

### 2) 📘 Theory & Policy (개념 & 정책)

- **정의**: DB 내 저장된 프로시저, 함수의 로직(알고리즘, 보안 키 생성 방식 등)을 관리자나 다른 개발자가 `SELECT`로 조회해도 해석할 수 없도록 바이너리 형태로 변환하여 저장하는 기술.
- **Security Boundary**: **Object Management**. 소스 코드 자체의 기밀성 보장.
- **Architecture**:
    - 평문 생성 시: `USER_SOURCE` 테이블 `TEXT` 컬럼에 소스 코드 그대로 저장.
    - Wrap 적용 시: `TEXT` 컬럼에 `wrapped` 키워드와 함께 16진수 난독화 코드가 저장됨.
        

### 3) 🛡️ Security Audit (취약점 및 권장사항)

- **Attack Surface**:
    - 암호화/해싱 알고리즘이 구현된 프로시저 소스가 평문으로 노출되면, 공격자가 **Rainbow Table** 공격 등을 수행하기 쉬워짐.
    - 비즈니스 로직(할인율, 검증 로직) 유출 위험.
- **Best Practice**:
    - 보안 민감 로직(로그인, 암호화, 개인정보 접근)이 포함된 PL/SQL 객체는 반드시 **Wrap 처리** 후 배포.
    - 원본 소스 코드는 별도의 형상 관리 시스템(Git 등)에서 철저히 보안 관리. (DB에서 복호화 불가능)
        

### 4) 💻 SQL Workflow (실습 로그)

(Scenario: 앞서 만든 마스킹 프로시저의 소스 코드를 다른 관리자가 볼 수 없도록 난독화하여 재생성)

```SQL
-- 1. [Threat Analysis] 난독화 전 소스 코드 확인
-- 누구나 딕셔너리를 통해 로직(SUBSTR 사용 등)을 볼 수 있음
SELECT name, text 
  FROM user_source 
 WHERE name = 'PROC_MASK_NAME'
 ORDER BY line;

-- 2. [Implementation] DBMS_DDL을 활용한 Dynamic SQL Wrapping
DECLARE
    v_ddl_code VARCHAR2(32000);
BEGIN
    -- 소스 코드를 문자열 변수에 담음 (문자열 연결 연산자 || 활용)
    v_ddl_code := 'CREATE OR REPLACE PROCEDURE proc_secure_mask ( ' ||
                  '    p_id IN userTBL.userID%TYPE ) ' ||
                  'IS ' ||
                  '    v_name userTBL.userName%TYPE; ' ||
                  'BEGIN ' ||
                  '    SELECT userName INTO v_name FROM userTBL WHERE userID = p_id; ' ||
                  '    DBMS_OUTPUT.PUT_LINE(SUBSTR(v_name, 1, 1) || ''**''); ' || 
                  'END;';
                  
    -- [Key Point] 평문 DDL을 즉시 난독화하여 컴파일
    SYS.DBMS_DDL.CREATE_WRAPPED(v_ddl_code);
END;
/

-- 3. [Verification] 딕셔너리 재조회 (난독화 확인)
SELECT text 
  FROM user_source 
 WHERE name = 'PROC_SECURE_MASK';
```

- 🚨 Result (`USER_SOURCE` 조회 결과):
    - `CREATE OR REPLACE PROCEDURE proc_secure_mask wrapped a000000…` (알 수 없는 16진수 문자열로 표기됨)
    - 기능은 정상 동작하나, 소스 코드는 **복원 불가**.

## Topic 1. 트리거 기본과 이벤트 핸들링 (Trigger Basics)

### 1) 📌 One-Liner (면접 즉답)

- 특정 테이블에 **DML(Insert, Update, Delete)** 이벤트가 발생했을 때, DBMS가 자동으로 실행하는 저장 프로시저(Stored Program)의 일종입니다. `(Event-Driven)`
    

### 2) 📘 Theory & Policy (개념 & 정책)

- **정의**: 사용자가 직접 호출(`EXEC`)하지 않고, 데이터 변경 이벤트 시 자동 격발(Fire)되는 객체.
- **Timing**:
    - `BEFORE`: 데이터 변경 **전** 수행 (데이터 검증, 기본값 설정).
    - `AFTER`: 데이터 변경 **후** 수행 (로그 기록, 연쇄 작업).
- **Scope**: `FOR EACH ROW` (행 단위 트리거) vs 문장 단위 트리거.
    

### 3) 🛡️ Security Audit (취약점 및 권장사항)

- **Attack Surface**: 트리거 내부에 악의적인 로직(예: 관리자 몰래 데이터 유출)이 숨겨질 경우 탐지가 어려움.
- **Best Practice**:
    - **Performance**: 트리거가 많아지면 DML 성능이 저하(Overhead)되므로 꼭 필요한 감사/무결성 로직에만 적용.
    - **Visibility**: 정기적으로 `USER_TRIGGERS`를 조회하여 불필요하거나 의심스러운 트리거 존재 여부 확인.
        

### 4) 💻 SQL Workflow (실습 로그)

(Scenario: `testTBL`에 데이터 변경이 일어날 때마다 알림을 출력하는 기본 트리거 작성)

SQL

```Java
-- 1. [Setup] 테스트 테이블 생성 (카카오톡 코드)
DROP TABLE testTBL;
CREATE TABLE testTBL (id NUMBER, text NVARCHAR2(10));
INSERT INTO testTBL VALUES(1, '아이브');
INSERT INTO testTBL VALUES(2, '블랙핑크');
INSERT INTO testTBL VALUES(3, '방탄소년단');
COMMIT;

-- 2. [Implementation] 기본 트리거 생성
CREATE OR REPLACE TRIGGER trg_test_alarm
    AFTER DELETE OR UPDATE -- 삭제 또는 수정 후 동작
    ON testTBL
    FOR EACH ROW -- 각 행마다 실행
BEGIN
    DBMS_OUTPUT.PUT_LINE('트리거가 작동했습니다! (Event Detected)');
END;
/

-- 3. [Verification] 동작 확인
SET SERVEROUTPUT ON;
UPDATE testTBL SET text = '뉴진스' WHERE id = 1;
-- 출력: 트리거가 작동했습니다! (Event Detected)
```

## Topic 2. 보안 감사 로그 구현 (Audit Logging)

### 1) 📌 One-Liner (면접 즉답)

- 트리거의 **`:OLD` (변경 전 값)**와 **`:NEW` (변경 후 값)** 가상 레코드(Pseudo Record)를 활용하여, 누가 언제 데이터를 수정/삭제했는지 별도의 **백업 테이블에 기록(Audit Trail)**하는 기술입니다. `(Non-repudiation)`
    

### 2) 📘 Theory & Policy (개념 & 정책)

- **Pseudo Records**:
    - `:OLD`: 수정/삭제 **전**의 데이터 (UPDATE, DELETE 시 존재).
    - `:NEW`: 수정/삽입 **후**의 데이터 (INSERT, UPDATE 시 존재).
- **Architecture**: 원본 테이블(`userTBL`) → 트리거(Interceptor) → 로그 테이블(`backup_userTBL`).
    

### 3) 🛡️ Security Audit (취약점 및 권장사항)

- **Attack Surface**: 내부자가 민감 데이터를 조작하고 로그를 남기지 않으려 할 때, 애플리케이션 레벨의 로깅은 우회 가능함.
- **Best Practice**:
    - DB 레벨 트리거로 강제 로깅을 구현하면, SQL Plus 등 어떤 툴로 접속해도 기록이 남음(부인 방지).
    - `USER` (접속 계정), `SYSDATE` (발생 시각), `modType` (행위 유형)을 반드시 포함.
        

### 4) 💻 SQL Workflow (실습 로그)

(Scenario: 회원 정보가 수정되거나 삭제될 때, 변경 전 데이터를 백업 테이블에 저장)

SQL

```Java
-- 1. [Setup] 백업(로그) 테이블 생성
CREATE TABLE backup_userTBL (
    userID CHAR(8) NOT NULL, 
    userName NVARCHAR2(10) NOT NULL, 
    birthYear NUMBER(4), addr NCHAR(2), 
    mobile1 CHAR(3), mobile2 CHAR(8), 
    height NUMBER(3), mDate DATE,
    modType NCHAR(2),      -- 변경 타입 (수정/삭제)
    modDate DATE,          -- 변경 일시
    modUser NVARCHAR2(256) -- 작업자(Account)
);

-- 2. [Implementation] 감사 트리거 작성
CREATE OR REPLACE TRIGGER trg_user_backup
    AFTER UPDATE OR DELETE ON userTBL
    FOR EACH ROW
DECLARE
    v_type NCHAR(2);
BEGIN
    -- 작업 유형 구분
    IF UPDATING THEN
        v_type := '수정';
    ELSIF DELETING THEN
        v_type := '삭제';
    END IF;

    -- [Log Logic] 변경 전 데이터(:OLD)를 백업 테이블에 저장
    INSERT INTO backup_userTBL VALUES (
        :OLD.userID, :OLD.userName, :OLD.birthYear, 
        :OLD.addr, :OLD.mobile1, :OLD.mobile2, 
        :OLD.height, :OLD.mDate,
        v_type, SYSDATE, USER -- 메타데이터(타입, 시간, 수행자)
    );
END;
/

-- 3. [Verification] 수정 및 삭제 후 로그 확인
UPDATE userTBL SET addr = '제주' WHERE userID = 'JYP';
DELETE FROM userTBL WHERE userID = 'BBK';

-- 로그 테이블 조회
SELECT modType, modUser, modDate, userName FROM backup_userTBL;
```

- 🚨 Result:
    - `JYP`의 주소 변경 전 데이터가 '수정' 타입으로 저장됨.
    - `BBK`의 삭제 전 데이터가 '삭제' 타입으로 저장됨.

## Topic 3. 보안 정책 강제 및 차단 (Blocking DML)

### 1) 📌 One-Liner (면접 즉답)

- 트리거 내부에서 **`RAISE_APPLICATION_ERROR`**를 호출하여, 특정 조건(예: 업무 시간 외 변경, 권한 없음)에 해당할 경우 트랜잭션을 강제 롤백하고 작업을 차단하는 방식입니다. `(Active Defense)`
    

### 2) 📘 Theory & Policy (개념 & 정책)

- **RAISE_APPLICATION_ERROR**: 사용자 정의 에러를 발생시키는 오라클 내장 프로시저.
    - 에러 코드 범위: `-20000` ~ `-20999`.
- **Policy**: "데이터의 무결성을 해치거나 보안 정책에 위배되는 DML은 DB 엔진 레벨에서 거부한다."
    

### 3) 🛡️ Security Audit (취약점 및 권장사항)

- **Attack Surface**: 애플리케이션단에서 유효성 검사를 하더라도, 공격자가 DB에 직접 접속(`Direct Access`)하여 데이터를 오염시키는 시도.
- **Best Practice**: 중요한 테이블(예: 결제 정보, 로그 테이블 자체)은 트리거를 통해 `DELETE`나 `UPDATE`를 원천 차단하거나, 특정 시간대(업무 시간 외) 접근을 막는 로직 구현.
    

### 4) 💻 SQL Workflow (실습 로그)

(Scenario: `userTBL`에 새로운 데이터 삽입(INSERT)을 전면 차단하는 보안 트리거)

SQL

```Java
-- 1. [Implementation] 입력 차단 트리거
CREATE OR REPLACE TRIGGER trg_no_insert
    BEFORE INSERT ON userTBL -- 입력하기 전에 검사
    FOR EACH ROW
BEGIN
    -- [Security Logic] 강제 에러 발생으로 트랜잭션 중단
    RAISE_APPLICATION_ERROR(-20001, '⛔ [보안 경고] 새로운 회원 데이터 삽입이 금지되어 있습니다.');
END;
/

-- 2. [Verification] 강제 에러 발생 확인
INSERT INTO userTBL (userID, userName, birthYear, addr)
VALUES ('NEW', '신입', 2000, '서울');
```

- 🚨 Result:
    - `ORA-20001: ⛔ [보안 경고] 새로운 회원 데이터 삽입이 금지되어 있습니다.` 에러 발생.
    - 데이터 삽입 실패 (Rollback).
        

### 5) 💡 Interview Shot (신입 면접 대비)

> [!faq]Q. 트리거를 사용할 때 주의할 점(성능/보안)은 무엇인가요?
>
> 🗣️ 핵심 답변
>
> 트리거는 데이터 변경 시마다 자동으로 실행되므로 과도하게 사용하면 DB 성능(Overhead)이 저하될 수 있습니다. 따라서 꼭 필요한 **보안 감사(Audit)**나 데이터 무결성 유지에만 제한적으로 사용해야 합니다.
>
> **📚 꼬리질문 대비**
>
> - **재귀 호출(Recursive Call)**: 트리거가 업데이트한 테이블이 또 다른 트리거를 격발시키는 무한 루프 상황을 주의해야 합니다.
>     
> - **INSTEAD OF 트리거**: 뷰(View)에 DML을 수행할 때 사용하는 특수 트리거입니다.
>

## 기타 핵심 (Etc & Tips) - DB보안 2025.10.27

### 🧩 Residual Knowledge (자투리 지식)

- **`INSTEAD OF` 트리거**: 주로 **View(뷰)**는 읽기 전용이지만, 뷰를 통해 원본 테이블을 업데이트하고 싶을 때 사용하는 특수 트리거. `BEFORE` 타이밍의 변형. `(강의)`
- **`USER` 키워드**: 현재 세션의 로그인된 사용자 ID를 반환하는 오라클 내장 변수. 감사 로그 작성 시 필수.
- **커서(Cursor)**: SQL은 집합(Set) 단위로 처리하지만, **행(Row) 단위**로 세밀한 제어가 필요할 때 사용하는 메모리 포인터. (Open → Fetch → Close). `(개념만)`
    

### 💻 Command Snippet (트리거 관리)

SQL

```Java
-- 접속: SYS or Owner
-- 특정 테이블의 트리거 상태 확인
SELECT trigger_name, trigger_type, triggering_event, status
  FROM user_triggers
 WHERE table_name = 'USERTBL';

-- 트리거 비활성화/활성화 (삭제하지 않고 멈출 때)

```

### 💬 Prof's Comment

> "트리거는 너무 많이 있으면 느려요(Overhead). 인서트/딜리트 할 때마다 계속 함수가 호출되는 거니까. 그래서 테스트만 하고 필요 없는 건 다 삭제해 주는 게 좋습니다. 하지만 실무 DB 보안에서는 **로그 기록** 남길 때 트리거를 가장 많이 활용합니다."
