아래는 주어진 녹취 텍스트를 바탕으로 **가독성 있게 정리한 시험 안내 및 ‘문제‑답안 형식’ 템플릿**입니다.

(불명확하거나 중복·잡담 성 내용은 학습 포인트 위주로 정리했고, 교수님 표현을 최대한 살렸습니다.)

---

## **시험 개요 (녹취 요지)**

- **형식**: 1번 T/F(객관식), **2~6번 서술형** 중심.
- **핵심 주제**:

    무결성 제약, 키 종류(후보키/기본키/대체키/슈퍼키/외래키), **리버스 엔지니어링(테이블↔ERD)**, 기본 **SQL(SELECT … WHERE …)**, 요구사항→**ERD 작성 및 매핑 규칙**.

- **출제 경향 특기**: 리버스 엔지니어링은 **1:N(또는 1:1)** 위주로 출제( **N:M은 시험에 안 낼 가능성 높음** ).
- **채점 감**: 설계·모델링 계열(역엔지니어링, 요구사항→ERD)이 **가장 큰 배점**, T/F는 **소배점**, SQL은 **중간(예: ~15점)** 수준 언급.

# **문제별 정리 및** 

# **답안 템플릿**

## **1번. T/F (True/False) – 이유는 안 써도 됨**

- **출제 취지**: 문장을 주고 **맞/틀**만 표기(이유 불필요).
- **자주 나오는 문장 유형 예시(연습용)**
    - 기본키 속성은 **NULL 불가**이고 **유일**하다 → **T**
    - 외래키 값은 **참조 테이블에 존재**해야 하며 **중복 가능**, **NULL 허용(부분참여일 때)** → **T**
    - 1:N 관계는 항상 별도 연결테이블을 만든다 → **F**(N쪽에 FK 두는 게 원칙)

---

## **2번.** 

## **무결성 제약/제약 개념 서술 (대표 4가지 + 보강)**

> 교수님 키워드: _Entity, Key, Foreign Key, Cardinality, Participation, Semantic_

### **정답 템플릿(요약 정의)**

- **(1) 엔터티/키 제약(Key/Entity Integrity)**
    - **기본키(PK)** 값은 **유일(Unique)** 해야 하며 **NULL 불가**.
    - 목적: 실세계 개체를 **유일 식별**.
- **(2) 참조 무결성(Referential/Foreign Key)**
    - **외래키(FK)** 값은 **참조 대상(보통 상대 테이블의 PK/UK)에 존재해야 함**.
    - **중복 가능**, **NULL 허용**(관계 **부분 참여**일 때).
- **(3) 카디널리티(Cardinality)**
    - 관계의 **연결 비율(1:1 / 1:N / N:M)**.
    - 설계에서 가장 중요: **1:N이 대부분**, N:M은 보조(시험 비중↓).
- **(4) 참여(Participation)**
    - **Total(전체 참여)** / **Partial(부분 참여)**.
    - Total이면 FK **NULL 불가** 등으로 강제 가능.
- **(보강) 시맨틱(업무) 제약(Semantic/Business Rules)**
    - 조직 내부 규칙(예: 직급별 급여 상하관계). **DB 제약/트리거/검증 로직** 등으로 구현.

> **채점 포인트**: 용어 정확성(영문 병기), **PK: 유일+NULL불가**, **FK: 존재성+중복/NULL 규칙**, **Cardinality/Participation 구분** 명확히.

## **3번 키 종류 식별 문제 (테이블 스키마 제공)**

### **답안에 반드시 구분할 항목**

- **후보키(Candidate Key)**: 유일 식별 & **최소성** 충족하는 속성 집합
- **기본키(PK)**: 후보키 중 채택된 키
- **대체키(AK, Alternate Key)**: **PK가 아닌 후보키**
- **슈퍼키(SK, Super Key)**: 유일 식별 가능하나 **최소성 미충족** 가능(예: PK+다른 속성 포함)
- **외래키(FK)**: 다른 테이블의 PK/UK를 참조하는 속성

> 용어 표기 주의: **AK**를 보통 _대체키_로 씁니다. _Secondary Key_를 SK로 쓰면 **슈퍼키(Super Key)**와 혼동되니 **SK=Super Key**로 사용.

### **해결 절차(답안 템플릿)**

1. **단일 속성**으로 유일 식별 가능한지 확인 → 가능하면 **후보키**
2. **복합 속성** 조합으로 유일 식별 가능한지 확인
    
    - 유일하지만 **부분집합**으로도 유일하면 **슈퍼키**(후보키 아님)

3. 모든 후보키 중 **PK 1개 선택** → 나머지는 **AK**
4. 스키마/명세의 **참조선언/명명(FK_…)·도메인**으로 **FK 식별**
5. 인덱스 참고: **PK는 기본 인덱스 자동 부여**, **후보키(UNIQUE)**에 인덱스 부여 가능(선택)

### **간단 예시(설명형)**

- R1(a1, a2, a3)에서 **a1만**으로 유일 식별 가능 → **CK={a1}**, **PK=a1**, **AK=없음**
- {a1,a2}, {a1,a3}, {a1,a2,a3}는 **SK(슈퍼키)**
- FK는 **다른 테이블 참조 여부**를 보고 결정(문제에서 명시/제약 확인)

## **4번. 리버스 엔지니어링(테이블 → ERD)**

> 시험은 **1:N(또는 1:1)** 위주로 출제 예정. **N:M형 브릿지 테이블**은 이번 시험에선 비중 낮음.

### **답안 작성 체크리스트**

1. **엔터티 식별**: PK 존재 & 독립적 의미가 있으면 엔터티
2. **관계 도출**:
    
    - **1:N**: N측 테이블에 **FK** + (필요시) **NOT NULL(총참여)** / **UNIQUE(1:1 강제)**
    - **1:1**: 한쪽에 FK + **UNIQUE**
    - **N:M**(만약 주면): **연결테이블**(두 FK + 복합PK)

3. **카디널리티/참여 판단 근거**를 **명시**:
    
    - FK **NULL 허용** → **부분 참여**
    - FK **NOT NULL** → **총참여**
    - FK에 **UNIQUE** → 상위쪽 관계 **1:1** 시사

4. **약한 엔터티/다중값 속성** 등 특수 케이스는 분리 테이블로 매핑
5. **최종 ERD 표기**: (엔터티, 주요 속성, PK 밑줄, 관계명, (min,max) 또는 1|N)
6. **메모**: “해당 테이블은 상위에서 유도된 관계테이블로 **독립 후보키/AK 산정 불가(해당 없음)**”처럼 **해석 불가/미적용**은 ‘없음’이 아닌 **사유**를 적시

## **5번.** SQL 작성(SELECT … WHERE …)

> 스키마 예시는 _사원/부서_ 또는 _Sailor_류로 간단히 제공될 가능성.

### **답안 템플릿**

- **기본 형태**

```
SELECT 컬럼들
FROM   테이블들
WHERE  조건들
ORDER BY 정렬기준;
```
    
- **관계 활용 예(1:N)**: 부서별 사원 조회, 특정 조건(급여/입사일 등) 필터링
- **조인 규칙**:
    - 1:N은 **PK=FK** 조인
    - 필요한 컬럼만 명시, 별칭 사용으로 가독성↑
- **주의**: NULL 비교(IS NULL/IS NOT NULL), 집계 시 GROUP BY, 조건은 HAVING 구분

## **6번.** 요구사항 → ERD 작성 → 관계형 매핑**

> “실제 현업 요구사항처럼 **깔끔하지 않게** 제시됨” — **필요 정보만 추출**, 잡설·홍보성 문구는 **모델링에 불필요**(예: ‘고객만족부서는 실인원이 없다’ → ‘부서‑사원’ 관계의 **부분참여** 힌트 정도만 반영)

### **정답 작성 흐름(템플릿)**

1. **용어 분류**
    
    - **엔터티 후보**(명사, 독립 개체) vs **속성**(엔터티의 성질) vs **관계**(엔터티 간 동사/연결)

2. **카디널리티/참여 결정**
    
    - 1:1 / **1:N(주류)** / N:M, **Total/Partial** 명시

3. **ERD 제시**
    
    - 엔터티(주요 속성, **PK 밑줄**), 관계(이름, 1|N, 참여)

4. **매핑 규칙 서술**
    
    - **1:N**: N측 테이블에 **FK** 추가(필요 시 **NOT NULL/UNIQUE**)
    - **1:1**: 한쪽에 **FK+UNIQUE** (또는 테이블 통합 사유 명시)
    - **N:M**: **연결테이블**(FK×2, 복합PK)
    - **다중값 속성**: 별도 테이블로 분리(OwnerFK + 값 + (OwnerFK,값) PK)
    - **약한 엔터티**: **소유자 PK + 부분키**로 **복합PK**

5. **제약 요약 표**
    
    - **PK/UK**, **FK(ON DELETE/UPDATE 정책)**, **CHECK(도메인/시맨틱)**, **NULL 허용 여부**

6. **가정/해석 메모**
    
    - 애매한 부분은 **합리적 가정**을 한 줄씩 명시(채점자 친화)

> **중요 포인트(교수님 강조)**

- > **카디널리티를 제대로 잡는 것**이 설계의 핵심(시험 고득점 분기점).
- > 실무·시험 모두 **1:N**이 **대부분**, N:M·삼진관계 등은 소수.

# **빠르게 보는** 

# **용어·표기 정리**

- **PK**: Primary Key(기본키) – **유일 + NULL 불가**, 자동 인덱스
- **CK**: Candidate Key(후보키) – 유일 식별 **+ 최소성**
- **AK**: Alternate Key(대체키) – PK가 아닌 후보키(UNIQUE로 구현 가능)
- **SK**: Super Key(슈퍼키) – 유일하지만 **최소성 불만족** 가능
- **FK**: Foreign Key(외래키) – 참조 무결성, **중복 가능/NULL 가능(부분참여)**
- **Cardinality**: 1:1, **1:N**, N:M
- **Participation**: **Total** / **Partial**
- **Semantic Constraints**: 업무 규칙(CHECK/트리거/애플리케이션 로직)

1. 엔터티: …
2. 관계: X–Y (1:N, X **Total**, Y Partial 등)
3. 근거: FK(…): NOT NULL → Total, UNIQUE → 1:1 …
4. ERD 스케치: (텍스트로 표기 가능)
5. 매핑 결과 요약: (FK 배치/제약)

### **(E) SQL**

```
-- 요구된 질의 설명 한 줄
SELECT …
FROM   …

-- NULL/집계/조인 근거 간단 주석
```

### **(F) 요구사항 → ERD → 매핑**

- 엔터티/속성/관계 추출 표
- 카디널리티·참여 결정 근거
- ERD 제시(텍스트/간단 도식)
- 매핑 규칙 적용 결과(테이블·PK/FK/UK/NULL/CHECK)
- 가정/해석 목록(번호 매겨 1~3줄)

## **마지막 팁**

- **카디널리티 & 참여**를 **근거와 함께 명시**하면 설계 문제에서 큰 점수 확보.
- **PK는 자동 인덱스**, **AK(UNIQUE)**도 인덱스 고려 가능 — 키 문제에서 한 줄 메모해두면 +α.
- **N:M은 연결테이블**, 이번 시험은 **1:N, 1:1 중심**이라는 힌트 반영.
- T/F는 **빠르게 체크**, 시간은 **2~6번**에 배분.
