## 정리
  

> [!summary] TL;DR
> **트랜잭션** 안에서 **영속성 컨텍스트(PC)** 가 열리고, PC **안**에 **1차 캐시(L1)** 가 있다.
> **2차 캐시(L2)** 는 PC **밖**(앱 전역/클러스터)에서 선택적으로 DB 부하를 줄인다.
> **식별자(@Id)** 는 L1/L2/DB를 잇는 키이자 PC의 **동일성 기준**이다.

---

## **1) 개념 한 줄 정의**

- **트랜잭션**: 한 작업 단위를 **모두 커밋/모두 롤백**으로 보장
	- Spring 환경에서는 `@Transactional` 어노테이션이 붙은 메서드가 시작될 때 영속성 컨텍스트(PC)가 생성되고, 메서드가 종료될 때 트랜잭션이 커밋되면서 영속성 컨텍스트가 flush되고 종료되는 것이 일반적인 라이프사이클입니다.
- **영속성 컨텍스트(PC)**: '엔티티를 영구 저장하는 환경'이라는 뜻으로, **엔티티를 담아두고 관리하는 가상의 공간(논리적 개념)**으로 이해하시면 완벽합니다. EntityManager를 통해 이 공간에 접근하고 관리하게 됩니다.
	- 동일성(\==) 보장: 같은 ID의 엔티티는 항상 같은 객체 인스턴스를 반환합니다.
	- 변경 감지 (Dirty Checking): 커밋 시점에 변경된 엔티티를 자동으로 찾아 UPDATE 쿼리를 날립니다.
	- 지연 쓰기 (Write-behind): SQL을 바로 보내지 않고 모았다가 커밋 시 한 번에 보냅니다.
- **1차 캐시(L1)**: PC 내부의 맵 ((엔티티타입,@Id) → 엔티티 인스턴스) — **항상 존재**, **동일성 보장**.
- **2차 캐시(L2)**: EMF/SessionFactory 레벨 **공유 스냅샷 캐시** — **선택**, **동일성 보장 X**.
- **식별자(@Id)**: DB **기본키 값**. L1/L2/DB 조회 키이자 **동일성 기준 키**

---

## **2) 관계 한 눈에**

```
요청 → [트랜잭션]
        └─ [영속성 컨텍스트(PC)]
             └─ [1차 캐시(L1)]   ← 먼저 조회
             └─ (미스) 2차 캐시(L2) ← 선택
             └─ (미스) DB
```

|**관계**|**의미**|
|---|---|
|트랜잭션 ↔ PC|보통 1:1로 시작/종료. 같은 트랜잭션이면 같은 PC.|
|PC ↔ L1|L1은 PC 내부 필수 구성. 같은 @Id 재조회 → **같은 인스턴스(== true)**|
|PC ↔ L2|L1 미스 시 L2 조회; 가져와도 **현재 PC에 새 관리 엔티티로 적재**|
|식별자 ↔ L1/L2|키는 (타입,@Id) 조합.|
|트랜잭션 ↔ L2|커밋 시점에 L2 **무효화/갱신**(전략별). 롤백이면 변경 없음.|

---

## **3) 동작 흐름**

  

**읽기 find(id)**

1. **L1** 조회 → 있으면 즉시 반환(== 동일 인스턴스)
    
2. L1 미스 → **L2** 조회 → 있으면 PC에 올리고 반환
    
3. L2 미스 → **DB SELECT** → PC(L1)에 올리고(필요시 L2 캐시) 반환
    

  

**쓰기/커밋**

- PC가 **변경감지** → flush() 시 DML 생성/전송 → **커밋**
    
- 커밋 후 L2는 **무효화/갱신**
    

---

## **4) 동일성 vs 동등성 & 식별자**

- **동일성(==)**: **같은 객체 인스턴스**
    
    - **같은 PC + 같은 @Id**일 때만 성립
        
    
- **동등성(equals)**: **값 기준 동일**
    
    - PC가 달라도 성립 가능(설계에 따름)
        
    
- **식별자(@Id)**: 메모리 주소가 아니라 **DB 기본키 값**.
    
    - L1/L2/DB 조회·매핑의 **키**.
        
    

  

> [!tip] 언제 == 가 깨지나?

> 트랜잭션이 바뀌거나 clear()/close() 후 재조회하면 **다른 PC**가 되어 **다른 인스턴스**가 나온다(동등성만 동일).

---

## **5) 자주 하는 질문**

- **“같은 @Id면 무조건 같은 객체?”** → **같은 PC 안에서만** 그렇다. PC가 다르면 다른 인스턴스.
    
- **“L2 있으면 L1 없어도 되나?”** → **아니오.** L1은 필수(동일성·변경감지·flush 기반). L2는 DB 부하 절감용 선택.
    
- **“@Transactional 없이도?”** → 읽기는 가능해도, **쓰기/일관된 flush/변경감지**를 위해 트랜잭션은 **필수**.
    

---

## **6) 실전 체크리스트**

- 쓰기 로직은 **반드시 @Transactional** 경계 안에서.
    
- DB 실제 반영 확인은 **flush() + clear() 후 find()로 재조회**.
    
- L2 사용 시 **무효화 전략/Region/일관성**을 명확히.
    
- equals/hashCode를 @Id 기반으로 둘 경우 **ID 배정 시점**(IDENTITY/SEQUENCE) 고려.
