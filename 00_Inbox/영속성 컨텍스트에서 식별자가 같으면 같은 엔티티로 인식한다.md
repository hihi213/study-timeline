## 정리

## 1) 영속성 컨텍스트(Persistence Context)란?
- 정의: 엔티티를 1차 캐시로 관리하는 논리적 공간. EntityManager가 들고 있는 “현재 트랜잭션의 엔티티 저장소/작업장”.
- 역할(핵심 기능)
	- 1차 캐시(Identity Map): 엔티티클래스 + 식별자를 키로 단 한 개 인스턴스만 보관. (cpu래지스터 1차캐시랑 다른거)
	- 동일성 보장: 같은 클래스, 같은 식별자로 다시 조회하면 항상 같은 객체 인스턴스를 돌려줌.
	- 변경 감지(Dirty Checking): 트랜잭션 끝에 바뀐 필드를 찾아 자동으로 UPDATE.
	- 지연 쓰기(Write-behind): persist()해도 즉시 SQL이 안 나가고 커밋/flush 때 모아 보냄.

네 테스트에서 @Transactional을 붙였기 때문에 메서드 전체가 하나의 영속성 컨텍스트를 공유합니다. 그래서
```Java
Member findMember = memberRepository.find(savedId);
System.out.println(findMember == member); // true
```
가 됩니다. (같은 인스턴스)

2) 식별자(Identifier)란?
	- 엔티티의 기본 키(@Id). DB의 PK와 1:1.
	- 생성 전략: @GeneratedValue(strategy = IDENTITY/SEQUENCE/TABLE) 등.
	- 영속성 컨텍스트의 키로 쓰입니다 → (엔티티클래스, @Id 값) 조합이 유일키.

3) “식별자가 같으면 같은 엔티티로 인식한다”의 정확한 의미
	•	같은 영속성 컨텍스트 안에서
	•	같은 @Entity 타입 + 같은 @Id → 이미 관리 중이면 그 객체를 그대로 반환
	•	따라서 참조 동일성(\==) 까지 성립합니다.
	•	이 규칙 덕분에 변경 감지, 일관성이 보장됩니다.

4) 언제 “같은 객체(\==)가 아니게” 되나?
	•	영속성 컨텍스트가 달라지면: 트랜잭션을 바꾸거나 entityManager.clear()/close() 후 다시 조회

em.persist(member);
em.flush(); em.clear();           // PC 비움
Member x = em.find(Member.class, id); // 새 인스턴스 → (x == member) == false

	•	다른 스레드/요청(다른 EM) 에서 조회할 때.
	•	merge 결과 객체는 새 관리 인스턴스가 됩니다.

그래도 JPA 스펙상, 현재 컨텍스트에 이미 관리 중인 엔티티가 있으면 JPQL/크리테리아 조회도 그 인스턴스를 반환해야 합니다(동일성 유지).

5) 관련 주의사항
	•	equals/hashCode 오버라이드: 엔티티는 보통 식별자 기반으로 오버라이드합니다.
	•	단, **ID가 아직 없는 “새 엔티티”**를 컬렉션 키로 쓰면 문제. (ID 배정 시점 고려)
	•	안전한 패턴: 생성 전에는 동등성 비교에 엮지 않거나, 비즈니스 키가 정말 불변일 때만 사용.
	•	지연로딩 프록시: getReference()나 LAZY 연관을 꺼냈을 때 프록시가 올 수 있음. 같은 PC면 결국 동일성은 유지되지만 instanceof/클래스 비교는 주의.

6) 손으로 확인해보기 (짧은 실험)

@Transactional
@Test
void same_instance_in_same_persistence_context() {
    Member m = new Member(); m.setUsername("A");
    em.persist(m);                 // 아직 DB INSERT는 아님(보통 flush/commit 시점)
    Member f = em.find(Member.class, m.getId());
    assertThat(f == m).isTrue();   // 같은 인스턴스 (동일성 보장)
}

@Transactional
@Test
void different_after_clear() {
    Member m = new Member(); m.setUsername("A");
    em.persist(m); em.flush(); em.clear();
    Member f = em.find(Member.class, m.getId());
    assertThat(f == m).isFalse();  // 다른 인스턴스 (컨텍스트가 달라짐)
    assertThat(f.getId()).isEqualTo(m.getId()); // 값 동등성은 동일
}

한 줄 정리
	•	영속성 컨텍스트 = EntityManager가 관리하는 1차 캐시/작업 단위.
	•	식별자(@Id) = 엔티티의 유일 키, 1차 캐시의 키.
	•	같은 컨텍스트 안에서 같은 타입 + 같은 식별자는 항상 같은 객체(\==) 로 취급됩니다.

한 줄 암기

영속성 컨텍스트 = JPA의 1차 캐시(Identity Map).
같은 컨텍스트 + 같은 엔티티타입 + 같은 @Id ⇒ 같은 객체(\==).
CPU 레지스터/L1 캐시는 하드웨어, 전혀 다른 개념.

핵심 개념 정리
	•	영속성 컨텍스트(Persistence Context): EntityManager가 트랜잭션 동안 관리하는 엔티티 저장소(1차 캐시).
	•	1차 캐시: (엔티티클래스, @Id) → 엔티티 인스턴스 맵. 동일성 보장, 변경 감지(더티체킹), 지연쓰기 지원.
	•	식별자(@Id): 엔티티의 기본키. 1차 캐시의 키로 사용.
	•	동일성 vs 동등성
	•	동일성 == : 같은 인스턴스 (같은 컨텍스트에서 같은 @Id 재조회 시 성립)
	•	동등성 equals() : 값 기준 동일 (컨텍스트가 달라도 가능)

언제 같은 인스턴스? 언제 달라짐?
	•	같은 트랜잭션(같은 EM) 에서 find()/JPQL → 같은 객체(== true).
	•	flush()+clear() 후 재조회, 다른 트랜잭션/스레드/요청에서 재조회 → **다른 객체(== false)**지만 id는 같음.

자주 쓰는 API 감각
	•	persist(e) : 영속 상태 등록(보통 커밋 시 INSERT).
	•	find(X.class, id) : 1차 캐시 → DB 순으로 조회.
	•	flush() : 변경사항을 DB로 밀어넣음.
	•	clear() / detach(e) : 컨텍스트에서 분리(더 이상 관리 안 함).
	•	merge(e) : 분리된 엔티티를 새 관리 엔티티로 병합(새 인스턴스 생성).

2차 캐시와의 차이
	•	1차 캐시: 트랜잭션/EntityManager 범위(필수, 기본 기능).
	•	2차 캐시: 애플리케이션 전역/클러스터 공유(선택, Ehcache/Caffeine 등).

오해 방지
	•	JPA 1차 캐시 ≠ CPU L1/L2/레지스터: 전자는 JVM 힙의 소프트웨어 캐시, 후자는 하드웨어 메모리 계층.
	•	동일성 보장을 믿고 로직을 짜되, 컨텍스트 경계가 바뀌면 동일성이 깨질 수 있음을 항상 염두.

미니 체크리스트
	•	테스트에서 @Transactional로 한 컨텍스트 유지.
	•	DB 실제 반영 확인 시 flush() 후 clear() 하고 다시 find().
	•	엔티티 equals/hashCode는 식별자 기준 설계 시 생성 시점/불변성 주의.
