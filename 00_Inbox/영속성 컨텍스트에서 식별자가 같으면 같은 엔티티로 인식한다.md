## 정리

> [!summary] TL;DR
> **트랜잭션** 안에서 **영속성 컨텍스트(PC)** 가 열리고, PC **안**에 **1차 캐시(L1)** 가 있다.
> **2차 캐시(L2)** 는 PC **밖**(앱 전역/클러스터)에서 선택적으로 DB 부하를 줄인다.
> **식별자(@Id)** 는 L1/L2/DB를 잇는 키이자 PC의 **동일성 기준**이다.

---

## **0) 동일성 vs 동등성 & 식별자**

- **동일성(\==)**: **같은 객체 인스턴스**
    - **같은 PC(영속성컨텍스트) + 같은 @Id**일 때만 성립
- **동등성(equals)**: **값 기준 동일**
    - PC가 달라도 성립 가능(설계에 따름)
- **식별자(@Id)**: 메모리 주소가 아니라 **DB 기본키 값**.
    - L1/L2/DB 조회·매핑의 **키**.

## **1) 개념 한 줄 정의**

- **트랜잭션**: 한 작업 단위를 **모두 커밋/모두 롤백**으로 보장
	- Spring 환경에서는 `@Transactional` 어노테이션이 붙은 메서드가 시작될 때 영속성 컨텍스트(PC)가 생성되고, 메서드가 종료될 때 트랜잭션이 커밋되면서 영속성 컨텍스트가 flush되고 종료되는 것이 일반적인 라이프사이클입니다.
- **영속성 컨텍스트(PC)**: '엔티티를 영구 저장하는 환경'이라는 뜻으로, **엔티티를 담아두고 관리하는 가상의 공간(논리적 개념)** 으로 이해하시면 완벽합니다. EntityManager를 통해 이 공간에 접근하고 관리하게 됩니다.
	- 동일성(\==) 보장: 같은 ID의 엔티티는 항상 같은 객체 인스턴스를 반환합니다. (pc1에서 가져온것끼리는 같은 인스턴스)
	- 변경 감지 (Dirty Checking): 커밋 시점에 변경된 엔티티를 자동으로 찾아 UPDATE 쿼리를 날립니다.
	- 지연 쓰기 (Write-behind): SQL을 바로 보내지 않고 모았다가 커밋 시 한 번에 보냅니다.
	- [엔티티와 bean이 다르다고](엔티티와%20Bean의%20차이(+DTO%20vs%20값).md)
- **1차 캐시(L1)**: 영속성 컨텍스트 내부에 존재하는, **필수적인 캐시** 
	- Map 형태로 (Key: @Id, Value: Entity Instance) 엔티티를 보관
	- **하나의 트랜잭션 내에서** 불필요한 SELECT 쿼리를 줄임
	- key 존재하는지 먼저 확인해서 하나의 영속성컨텍스트에는 같은 Key(`@Id`)에 대해 **오직 하나의 객체 인스턴스만 존재** 하게됨
- **2차 캐시(L2)**: **애플리케이션 전체에서 공유**하는 **선택 사항** 캐시입니다
	- **목적**: DB 접근 자체를 줄여 **전체 성능을 향상**시킵니다.
		- 공용자료실인 L2 캐시에서 데이터를 찾으면(`@Id` Key로 조회), 그 데이터를 바탕으로 **새로운 객체를 생성해서** 현재 트랜잭션의 1차 캐시(개인 책상)에 올려주는 것.
- **식별자(@Id)**: 1차캐시, 2차캐시의 키
	- DB **기본키 값**. L1/L2/DB 조회 키이자 **동일성 기준 키**
	- **식별자 값:** `@Id`로 지정된 `member.getId()`의 값 (예: `1L`, `"user-a"`)
		- JPA는 이 **식별자 값**을 기준으로 1차 캐시, 2차 캐시, DB에서 엔티티를 찾고 동일성을 판단합니다.
	 - **메모리 주소값:** `new Member()` 할 때마다 달라지는, JVM이 관리하는 값

---
- 1차캐시, 2차캐시 동등성?
	- 걍 내가 써먹을려고 엔티티를 가져옴
	- pc1에서 가져오면 같은 인스턴스를 받는데
	- pc2에서 가져오면 새 인스턴스를 생성해 주는거라 다른 인스턴스(다른 주소값)을 가져오는거라 참조가 다름 
	- 그래서 pc1에서 가져온것끼리는 같은 인스턴스인데 pc2에서 가져온것 끼리는 다른 인스턴스임

## **2) 동작 흐름**

**읽기 find(id)**

1. **L1** 조회 → 있으면 즉시 반환(== 동일 인스턴스)
2. L1 미스 → **L2** 조회 → 있으면 PC에 올리고 반환
3. L2 미스 → **DB SELECT** → PC(L1)에 올리고(필요시 L2 캐시) 반환

**쓰기/커밋**
- PC가 **변경감지** → flush() 시 DML 생성/전송 → **커밋**
- 커밋 후 L2는 **무효화/갱신**
- **첫 작업 (DB 조회)**
    - 제가 '1번 회원' 문서를 보려고 합니다. 제 책상(1차 캐시)에 없네요.
    - 그래서 저는 DB 창고까지 가서 문서를 가져와 **제 책상(1차 캐시) 위에 올려둡니다.**
    - 작업을 마치고 퇴근하면서, 자주 쓰는 문서이니 팀 공용 자료실(2차 캐시)에 **'복사본'을 한 부** 두고 갑니다.
- **다음 날, 내 작업 (1차 캐시 히트)**
    - 제가 다시 '1번 회원' 문서가 필요합니다.
    - DB 창고까지 갈 필요 없이, **제 책상(1차 캐시) 위에 있는 어제 그 '원본 객체'를 그대로 사용**합니다. 당연히 어제 보던 그 문서와 100% 동일한 문서(\==)입니다.
- **다음 날, 동료의 작업 (2차 캐시 히트)**
    - 제 동료가 '1번 회원' 문서가 필요합니다. 동료의 책상(동료의 1차 캐시)에는 당연히 없겠죠.
    - 동료는 DB 창고까지 가기 전에 **팀 공용 자료실(2차 캐시)을 먼저 확인**합니다.
    - 어제 제가 복사해 둔 '복사본'을 발견하고, 이 문서를 **'새롭게 한 부 더 복사'해서 자기 책상(동료의 1차 캐시) 위로 가져갑니다.**

```
요청 → [트랜잭션]
        └─ [영속성 컨텍스트(PC)]
             └─ [1차 캐시(L1)]   ← 먼저 조회
             └─ (미스) 2차 캐시(L2) ← 선택
             └─ (미스) DB
```

| **관계**      | **의미**                                             |
| ----------- | -------------------------------------------------- |
| 트랜잭션 ↔ PC   | 보통 1:1로 시작/종료. 같은 트랜잭션이면 같은 PC.                    |
| PC ↔ L1     | L1은 PC 내부 필수 구성. 같은 @Id 재조회 → **같은 인스턴스(== true)** |
| PC ↔ L2     | L1 미스 시 L2 조회; 가져와도 **현재 PC에 새 관리 엔티티로 적재**        |
| 식별자 ↔ L1/L2 | 키는 (타입,@Id) 조합.                                    |
| 트랜잭션 ↔ L2   | 커밋 시점에 L2 **무효화/갱신**(전략별). 롤백이면 변경 없음.             |
|             |                                                    |
|             |                                                    |
|             |                                                    |

---

> [!tip] 언제 == 가 깨지나?

> 트랜잭션이 바뀌거나 clear()/close() 후 재조회하면 **다른 PC**가 되어 **다른 인스턴스**가 나온다(동등성만 동일).

## **5) 자주 하는 질문**

- **“같은 @Id면 무조건 같은 객체?”** → **같은 PC 안에서만** 그렇다. PC가 다르면 다른 인스턴스.
- **“L2 있으면 L1 없어도 되나?”** → **아니오.** L1은 필수(동일성·변경감지·flush 기반). L2는 DB 부하 절감용 선택.
- **“@Transactional 없이도?”** → 읽기는 가능해도, **쓰기/일관된 flush/변경감지**를 위해 트랜잭션은 **필수**.

---

## **6) 실전 체크리스트**

- 쓰기 로직은 **반드시 @Transactional** 경계 안에서.
- DB 실제 반영 확인은 **flush() + clear() 후 find()로 재조회**.
- L2 사용 시 **무효화 전략/Region/일관성**을 명확히.
- equals/hashCode를 @Id 기반으로 둘 경우 **ID 배정 시점**(IDENTITY/SEQUENCE) 고려.
