## 문제 5번.
**DB 보안:** 시스템 보안(ID/PW)을 통과하더라도 내부적으로 데이터(문서)와 유저의 등급을 나눠 관리해야 한다는 개념입니다.

### RSA방식
RSA는 누구나 알수있는 공개키와 소유자만 알고있는 개인키 쌍으로 구성된다. 수신자의 공개키로 암호화하고, 송신자의 개인키로 복호화한다. 송신자가 보냄을 증명하기 위한 전자서명시에는 송신자의 개인키로 잠그고(서명) 송신자의 공개키로 푼다(확인)
- 부연설명: 비대칭키인이유는 암호화와 복호화에 서로다른키를 사용해서
- 부연설명: 중간에 문서를 가로채도 해커는 개인키가 없으므로 못푼다
- 부연설명: 해커도 수신자의 공개키를 안다면 문서를 위조해서 수신자에게 보낼수있기 때문에 전자서명이 등장

### MAC
- Subject와 Object 등급을 나누고 매핑한다 이때, **Bell-LaPadula 모델**의 두 가지 원칙인 자신보다 높은 등급의 문서를 읽을 수 없는 **Simple Security Property(no read up)** 와 낮은 등급의 문서에 쓸수없는 **Star Property(no write down)** 를 지킨다. 여기서 조직내에서 역할에 권한을 부여하는게 추가되면 RBAC다
- 부연설명: noreadup은 기밀성 보장, nowritedownd은 정보가 낮은 등급의 문서에 정보 유출을 방지
- 부연설명: RBAC= MAC+ 사용자(User)와 권한 사이 'Role(역할)'이 매핑되는 개념

## 문제 3번: 정규화란 중복 제거하자 테이블의 기본키를 중심으로 테이블을 쪼개자(분해)

정규화 (Normalization)** : 설계가 끝난 후에도 데이터의 **중복성(Redundancy)** 문제가 남아있음을 해결하기위해 테이블을 쪼개는 분해를 한다.

정규화는 하위 단계를 만족해야 상위 단계로 나아갈 수 있는 계층 구조를 가집니다.

- **진행 순서:** 1NF $\rightarrow$ 2NF $\rightarrow$ 3NF $\rightarrow$ BCNF
- **검증 원칙:** 상위 정규형(예: 3NF)을 만족하려면 반드시 하위 정규형(예: 2NF)을 먼저 만족해야 합니다

왼쪽->오른쪽: 왼쪽이 오른쪽을 결정하는 관계다. 왼쪽이 그러므로 핵심인자리.
슈퍼키: 기본키를 포함한 집합
프라임키: 기본키의 일부

- BCNF: 왼쪽은 무조건 슈퍼키
- 2정규형: 왼쪽이 프라임키이면 위반
	- 오른쪽도 프라임키인 경우 봐줌
- 3정규형: 왼쪽이 슈퍼키이거나 오른쪽이 프라임키 둘중 하나면됨

### FD가 정규형 위반인지 찾는다
1. 왼쪽이 **슈퍼키** 인가? -> BCNF
2. 오른쪽이 **프라임 속성**인가? -> 3NF
3. 왼쪽이 프라임인가? -> 2NF위반(부분종속 발생)
4. 셋다 아니라면 3NF 위반(이행종속 발생)

### 위반시 분해한다: 원인제공자 왼쪽이 오른쪽을 데리고 나간다.
1. 새 테이블 생성: 왼쪽(기본키), 오른쪽
2. 기존 테이블에서 오른쪽만 삭제
- 분해하고나서 조인했을때 원래 테이블과 일치해야함(튜플 더 생기면 안됨)

### 부가정보: 중복의 문제점
- **갱신 이상:** 일부 튜플만 갱신되어 데이터 불일치 발생
- **삽입 이상:** 불필요한 정보 없이는 데이터를 추가하지 못함
- **삭제 이상:** 튜플 삭제 시 필요한 정보까지 함께 삭제됨
