### 1) 이 항목은 무엇인가 (What)

-   **한 줄 요약**: 사용자가 아이디/비밀번호로 자신을 증명하면, 우리 서버가 "이 사람은 신원이 확인됐음"이라는 임시 출입증(JWT)을 발급해주는 API 엔드포인트(`POST /auth/login`)를 만드는 작업입니다.
-   **시스템 내 위치**: 인증은 '보안 필터' 또는 '미들웨어'라는 관문에서 처리됩니다. 모든 요청은 이 관문을 통과하는데, `/auth/login` 요청은 그냥 통과시켜주고, 나머지 보호된 API 요청들은 유효한 출입증(JWT)이 있는지 검사합니다. 출입증이 없거나 위조되었다면 401 Unauthorized 에러를 내보내며 입장을 거부합니다.
-   **용어 정의**:
    -   **인증 (Authentication)**: "당신은 누구십니까?"에 답하는 과정. 사용자가 제시한 신원(아이디/비밀번호)이 진짜인지 확인하는 절차입니다.
    -   **인가 (Authorization)**: "당신은 무엇을 할 수 있습니까?"에 답하는 과정. 인증된 사용자가 특정 행동(예: 관리자 페이지 접근)을 할 권한이 있는지 확인하는 절차입니다.
    -   **JWT (JSON Web Token)**: 사용자의 정보와 권한을 담아 전자서명한 '디지털 출입증'입니다. `헤더.페이로드.서명` 세 부분으로 구성되며, 서명을 통해 위변조 여부를 검증할 수 있습니다.
    -   **무상태 (Stateless)**: 서버가 로그인 상태를 기억하지 않는다는 의미입니다. 클라이언트는 매 요청마다 JWT를 제시해야 하며, 서버는 그 JWT만 보고 신원을 파악합니다. 서버 확장에 매우 유리한 방식입니다.
    -   **비밀 키 (Secret Key)**: JWT의 서명을 만들고 검증하는 데 사용되는 서버만 알고 있는 비밀 문자열입니다. 이 키가 유출되면 누구나 유효한 JWT를 만들어낼 수 있으므로, 코드에 하드코딩하지 않고 안전하게 보관해야 합니다.

### 2) 왜 지금 이걸 구현하는가 (Why)

-   **사용자 여정/운영 관점**: 로그인은 우리 서비스의 '현관문'입니다. 이게 없으면 사용자는 아이템을 등록하거나 검사를 하는 등 자신만의 데이터를 관리하는 핵심 기능을 전혀 사용할 수 없습니다.
-   **이번 주 Gate/DoD와 연결**: 이번 주 목표인 "권한 밖 403"을 테스트하려면, 일단 '로그인된 사용자'가 있어야 합니다. 로그인을 구현해야 비로소 특정 역할(Role)이 없는 사용자가 접근을 거부당하는 시나리오를 검증할 수 있습니다.
-   **후속 스프린트와의 연결**: 지금 만드는 인증 계층은 앞으로 만들 모든 기능(아이템 관리, 검사, 벌점)을 보호하는 기본 골격이 됩니다. 한번 잘 만들어두면 계속 재사용하게 됩니다.

### 3) 구현 방식 선택지

혼자서 처음 개발하는 상황임을 감안하여, 학습 목표에 따라 두 가지 방식을 제안합니다.

#### 옵션 A: Spring Security + JWT 라이브러리 (표준적이고 강력한 방식)

-   **어떻게?**: `spring-boot-starter-security` 의존성을 추가하고, JWT 생성을 위해 `jjwt` 같은 라이브러리를 사용합니다. Spring Security의 설정을 통해 로그인 로직과 JWT 검증 필터를 연동합니다.
-   **언제 좋음?**: Spring 생태계의 표준 보안 프레임워크를 경험하고 싶을 때. 이미 검증된 강력한 프레임워크 위에서 안정적으로 기능을 구축하고 싶을 때 좋습니다.
-   **언제 나쁨?**: Spring Security는 초기 설정이 복잡하고, 내부 동작 방식이 '마법'처럼 느껴질 수 있습니다. 간단한 기능에 비해 배워야 할 것이 많다고 느낄 수 있습니다.
-   **리스크**: 설정이 복잡한 만큼, 작은 실수 하나가 보안 허점으로 이어질 수 있습니다. (예: 특정 경로를 실수로 열어두는 것)
-   **확장성**: 최고 수준. RBAC, OAuth2 등 복잡한 보안 요구사항이 생겨도 손쉽게 확장할 수 있습니다.

#### 옵션 B: 직접 만든 Filter + JWT 라이브러리 (가볍고 학습에 좋은 방식)

-   **어떻게?**: Spring Security를 사용하지 않고, 모든 요청을 가로채는 `Filter`를 직접 만듭니다. 이 필터 안에서 요청 헤더의 JWT를 직접 파싱하고 검증하는 로직을 `jjwt` 라이브러리를 이용해 작성합니다.
-   **언제 좋음?**: JWT 인증의 전체 흐름을 A부터 Z까지 내 손으로 구현하며 원리를 깊게 이해하고 싶을 때. 프레임워크의 도움 없이 최소한의 코드로 빠르게 핵심 기능을 만들고 싶을 때 좋습니다.
-   **언제 나쁨?**: 직접 구현하다 보면 보안적으로 고려해야 할 많은 부분을 놓칠 수 있습니다. 결국 Spring Security가 자동으로 해주던 많은 기능들을 직접 만들게 될 수 있습니다.
-   **리스크**: 직접 구현한 로직에 보안 허점이 있을 수 있습니다. (예: 토큰 만료 시간 검증 누락, 서명 검증 오류 등)
-   **확장성**: 프로젝트가 커지고 보안 규칙이 복잡해지면, 직접 만든 필터가 점점 비대해져 유지보수가 어려워질 수 있습니다.

### 4) 선택 요청

**어떤 방식으로 인증을 구현하시겠어요?**

-   **옵션 A**: Spring Security의 강력함과 표준을 따른다.
-   **옵션 B**: 직접 Filter를 만들어보며 JWT의 동작 원리를 처음부터 끝까지 학습한다.

**선택 기준**: **Spring 생태계의 표준 보안 프레임워크를 경험하는 것(A)**과 **인증 흐름의 기본 원리를 직접 구현하며 파악하는 것(B)** 중 어떤 학습 목표를 더 중요하게 생각하시나요?

**함께 정할 파라미터**:
1.  JWT 비밀 키(Secret Key)는 우선 어디에 보관할까요? (예: `application.yml`의 변수)
2.  JWT 만료 시간은 몇 분으로 할까요? (15분? 30분?)

알겠습니다. \*\*Spring Security(옵션 A)\*\*를 기반으로, 비밀 키는 **환경변수**로 관리하는 표준적이고 안전한 방식으로 진행하겠습니다. 아주 좋은 결정입니다.

Spring Security는 처음에는 다소 복잡하게 느껴질 수 있지만, 한번 구조를 이해하고 나면 가장 강력하고 신뢰할 수 있는 방법입니다. 제가 그 구조를 쉽게 이해하실 수 있도록 단계별로 안내해 드리겠습니다.

### 5\) 구현 절차 (저코드 가이드)

#### 체크리스트

1.  [ ] **설계**: `POST /auth/login` 요청 시, Spring Security의 `AuthenticationManager`로 사용자(아이디/비밀번호)를 인증하고, 성공 시 `JwtTokenProvider`가 JWT를 생성하여 반환한다. 이후 모든 요청은 `JwtAuthenticationFilter`가 가로채 JWT를 검증하고 사용자의 인증 정보를 설정한다.
2.  [ ] **DB/마이그**: 사용자 비밀번호 암호화(Bcrypt)를 위해 테스트 유저를 미리 생성해 둔다. (Spring Security에 Bcrypt가 내장되어 있어 별도 라이브러리 추가는 불필요)
3.  [ ] **API 스펙 (산출물)**:

      * `build.gradle.kts`: `spring-boot-starter-security`, `jjwt` 라이브러리 의존성 추가.
      * `.env` 파일: `JWT_SECRET=...` 환경변수 추가 (32바이트 이상의 매우 긴 무작위 문자열 추천).
      * `application.yml`: `@Value("\${JWT_SECRET}")`로 읽을 수 있도록 설정.
      * `api/openapi.yml`: `/auth/login` 경로 및 요청/응답 스키마(`LoginRequest`, `LoginResponse`) 추가.
      * `dto/LoginRequest.java`, `dto/LoginResponse.java`: 로그인 요청/응답에 사용할 데이터 전송 객체(DTO).

4.  [ ] **핵심 로직 (산출물)**:

      * `config/SecurityConfig.java`: Spring Security의 핵심 설정 파일. `SecurityFilterChain` Bean을 통해 HTTP 보안 규칙(CSRF 비활성화, 세션 무상태 설정 등)과 커스텀 필터 체인을 정의.
      * `auth/JwtTokenProvider.java`: JWT의 생성, 유효성 검증, 정보 추출을 전담하는 컴포넌트.
      * `auth/JwtAuthenticationFilter.java`: 모든 요청의 `Authorization` 헤더에서 JWT를 꺼내 검증하고, 유효하면 Spring Security의 인증 컨텍스트(`SecurityContext`)에 사용자 정보를 등록하는 필터.
      * `service/UserDetailsServiceImpl.java`: Spring Security가 사용자 정보를 DB에서 조회할 때 사용하는 `UserDetailsService`의 구현체.
      * `controller/AuthController.java`: `/auth/login` 엔드포인트를 담당하는 컨트롤러.

5.  [ ] **권한/에러**: `SecurityConfig`에서 인증 실패(401), 인가 실패(403) 시 처리할 로직을 설정.
6.  [ ] **로그/지표**: 로그인 성공/실패 이벤트에 대한 로그를 남긴다.

#### 핵심 스니펫

*`config/SecurityConfig.java`* 내 `SecurityFilterChain` Bean 설정:

```java
// 이유: Spring Security의 '청사진'을 그리는 가장 핵심적인 부분.
//       어떤 필터를 쓰고, 어떤 요청을 허용/차단할지 선언적으로 정의한다.
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
            .csrf(AbstractHttpConfigurer::disable) // CSRF 보호 비활성화 (Stateless API)
            .sessionManagement(c -> c.sessionCreationPolicy(SessionCreationPolicy.STATELESS)) // 세션 사용 안함
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/auth/login").permitAll() // '/auth/login'은 누구나 접근 가능
                    .anyRequest().authenticated() // 나머지 요청은 인증 필요
            )
            // 직접 만든 JwtAuthenticationFilter를 UsernamePasswordAuthenticationFilter 앞에 추가
            .addFilterBefore(new JwtAuthenticationFilter(jwtTokenProvider), UsernamePasswordAuthenticationFilter.class)
            .build();
}
```

      - DB에 테스트 사용자를 추가합니다.
        ```sql
        -- psql에서 실행

        ('testuser', '$2a$10$abcdefghijklmnopqrstuv.1234567890abcdefghijklmnopqrstu', '테스트유저');
        ```

2.  **로그인 실패 (잘못된 비밀번호)**

      * **기대 응답 스케치**: `HTTP/1.1 401 Unauthorized`

3.  **로그인 성공**

      * `curl -X POST -H "Content-Type: application/json" -d '{"username":"testuser", "password":"password123"}' http://localhost:8080/auth/login`
      * **기대 응답 스케치**:
        ```json
        {
          "accessToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c"
        }
        ```

4.  **보호된 API 접근 (토큰 없이)**

      * `/me` 엔드포인트를 임시로 만든 후 `curl http://localhost:8080/me` 호출
      * **기대 응답 스케치**: `HTTP/1.1 401 Unauthorized`

5.  **보호된 API 접근 (토큰 사용)**

      * 위에서 받은 `accessToken`을 변수에 저장한 후,
      * `TOKEN="eyJhbG..."`
      * `curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/me`
      * **기대 응답 스케치**: `HTTP/1.1 200 OK` 와 함께 사용자 정보 반환.

	- ### 키가 생성되어 사용되기까지의 과정
		1.  **[생성] 원본 키는 바이너리다.**
		    * 처음 암호화 키를 만들면, 그것은 무작위 바이트의 나열(`byte[]`)입니다. 이것이 키의 ‘본체’입니다.
		2.  **[문제] 바이너리는 텍스트 파일에 위험하다.**
		    * 이 `byte[]`를 `application.yml`에 직접 넣으려고 하면 문제가 생깁니다. 만약 바이트 배열에 줄바꿈(newline)이나 탭(tab) 문자에 해당하는 값이 포함되어 있다면, `.yml` 파일의 구조 자체가 망가집니다.
		3.  **[해결책] 안전한 텍스트로 ‘포장’하자 (인코딩)**
		    * 이 문제를 해결하기 위해, 원본 `byte[]`를 Base64 인코딩하여 안전한 문자들로만 구성된 `String`으로 변환합니다. 이 변환된 문자열을 `application.yml`의 `JWT_SECRET` 값으로 저장합니다.
		4.  **[사용] 원상복구하여 ‘내용물’을 꺼내자 (디코딩)**
		    * 애플리케이션이 `@Value`로 이 문자열을 읽어왔을 때는, 아직 ‘포장된’ 상태입니다. 암호화 연산에 필요한 것은 포장지가 아닌 내용물(원본 `byte[]`)이므로, **반드시 Base64 디코딩을 통해 ‘포장’을 풀어 원래의 `byte[]`로 되돌려야 합니다.**
			
			**결론: 디코딩은 텍스트 파일에 안전하게 저장하기 위해 잠시 다른 모습(String)으로 변환했던 키를, 암호화 연산에 사용하기 위해 원래의 모습(byte[])으로 되돌리는 필수적인 원상복구 과정입니다.**
	- Step 3: 인증(Authentication) 객체를 인자로 받아 JWT를 생성하는 메서드를 구현하세요. 토큰의 주체(Subject), 클레임(Claims), 만료 시간을 설정한 후, 서명 키로 서명하여 최종 토큰 문자열을 반환하도록 구성하세요.

📚 핵심 개념

- **JWT (JSON Web Token)**: 사용자 인증 및 정보 교환을 위해 사용되는 간결하고 독립적인 방식의 토큰입니다. 헤더(Header), 페이로드(Payload), 서명(Signature) 세 부분으로 구성되며, 각 부분은 `.`으로 구분됩니다.
- **페이로드 (Payload)**: 토큰에 담을 정보, 즉 클레임(Claim)의 집합입니다. 클레임은 사용자의 ID, 권한 등 전달하려는 데이터 조각을 의미하며, 등록된 클레임(iss, sub, exp 등)과 공개/비공개 클레임으로 나뉩니다.
- **서명 (Signature)**: 토큰의 무결성을 보장하는 가장 중요한 부분입니다. 헤더와 페이로드를 비밀 키(`JWT_SECRET`)로 암호화하여 생성하며, 서버는 이 서명을 검증함으로써 토큰이 위변조되지 않았음을 신뢰할 수 있습니다.
- **JWS (JSON Web Signature)**: 서명이 포함된 JWT를 지칭하는 표준 규격입니다. `JwtTokenProvider`가 생성하는 토큰은 정확히는 JWS에 해당합니다.
