실습 파트의 범위는 5장부터 7장까지이며, 이 부분은 대부분 실습 문제로 구성됩니다. 주요 내용은 DDL, DML, 그리고 procedure와 function을 포함하는 PL/SQL 프로그래밍입니다. 시험 범위에는 INSERT, DELETE, UPDATE, ALTER, SELECT 등 모든 DML 및 DDL 쿼리문이 포함됩니다. DCL은 이후 보안 파트에서 다룰 예정이므로 이번 시험 범위에서는 제외됩니다. 오늘 학습한 procedure와 function에서는 FOR문과 IF문을 활용할 수 있는 수준이면 충분합니다. 다만, SELECT뿐만 아니라 INSERT, UPDATE, DELETE 구문을 응용하여 프로그래밍하는 문제가 출제될 수 있습니다.

## **2025-09-08, 1교시 — 개선본**

DB 보안 프레임워크의 구성 요소와 보안 관리 단계에 대해 알아보겠습니다. 보안 프레임워크 구축의 필요성, 구성 기술 요소 도출 방법, 그리고 여러 보안 통제 사례와 매핑하여 접근 제한, 암호화, 작업 결재, 취약점 분석을 기준으로 구성 요소를 정의했습니다. 이제 이 구성 요소들을 이용해 보안 구축 단계를 살펴보겠습니다.

먼저 **기획 단계**입니다. 이 단계는 보안 구축 계획을 수립하고, 보안 정책의 지침과 가이드라인을 개발하는 과정입니다. 결과물로는 구축 계획서, 보안 지침서, 가이드라인이 산출됩니다. 보호할 데이터를 분류하고, 해당 데이터를 어떤 원칙과 지침으로 보호할지 정의하며, 담당 조직의 역할과 책임을 명확히 합니다. 또한, 기술 요소의 개선이나 변경, 추가 절차에 대한 가이드라인도 이 단계에서 수립합니다.

다음은 **설계 단계**입니다. 기획 단계가 전체적인 그림을 그렸다면, 설계 단계에서는 `DB` 접근 제어 규칙이나 작업 결재 규칙처럼 각 기술 요소별로 상세한 구현 방안을 구체화합니다. 사용자 인증, 로그인 과정, 모니터링 지표, 운영 방안 등을 상세히 설계합니다. 암호화의 경우, 복호화 권한 통제, 암호화 알고리즘 정의 등 기술적인 설계서가 작성됩니다. 작업 결재는 결재 경로 규칙과 모니터링 지표를, 취약점 분석은 분석 계획서를 포함하여 각 구성 요소에 필요한 기술적 설계를 진행합니다.

이후 **구축 단계**로 넘어갑니다. 이는 설계 단계의 결과를 바탕으로 각 기술 요소를 실제 시스템에 구현하고 테스트하는 과정입니다. 설계된 접근 제어 규칙을 구현하고, 일반적인 로그인 외에 우회 접근 시도를 방어하는지 테스트해야 합니다. 암호화의 경우, 주민등록번호와 같은 민감 정보가 저장 시점에 올바르게 암호화되는지, 원본 데이터는 안전하게 삭제되는지 확인합니다. 또한, 암호화된 데이터가 필요시 정상적으로 복호화되어 사용자가 판독할 수 있는지도 검증합니다. 설계 단계에서 도출된 취약점을 실제로 테스트하여 보안 솔루션을 적용하고, 개선 여부를 모니터링하며 내부 보안 감사를 실행합니다. 이 단계의 결과물은 구현 내역서와 테스트 결과서입니다.

마지막으로 **운영 단계**입니다. 구축된 프레임워크가 지속적으로 정상 작동하는지 모니터링하고 문제점을 개선하는 유지 관리 단계입니다. 보안 규칙 변경 사항을 관리하고, 로그를 주기적으로 점검하여 부적절한 접근 시도 등을 파악하고 보안을 강화해야 합니다. 정기적인 점검을 위해 체크리스트를 만들어 관리하는 것이 효과적이며, 운영 보고서와 개선 사항 보고서를 통해 지속적인 관리가 이루어져야 합니다.

구축보다 더 중요한 것이 운영입니다. 구축 이후의 보안 관리는 보안 조직, 보안 준비, 보안 통제 구축, 보안 통제 활동, 보안 교육 등으로 구성됩니다. 먼저 전담 **보안 조직**을 구성하고, 솔루션 도입 시기와 선정 기준을 정하는 **보안 준비**를 합니다. 이 과정에서 구성원들의 보안 인식을 높이기 위한 교육도 필요합니다. 이후, 프레임워크 프로세스에 따라 기술 요소를 구축하고 운영하는 **보안 통제 구축**을 진행합니다.

**보안 통제 활동**은 운영 단계에서 지속적으로 수행하는 관리 감독 활동으로, 로그 검토, 취약점 테스트 등을 통해 개선점을 찾아 반영합니다. 마지막으로 **보안 교육**은 각 단계별로 필요한 기술 교육, 관리 방법 교육 등을 시행하여 조직의 보안 역량을 높이고, 보안 시스템 도입에 대한 거부감을 최소화하는 것을 목표로 합니다.

`DB` 보안을 고려할 때는 `DB` 가용성을 위한 백업 및 복구 절차, 비인가 접근 제어, 동시성 제어, 불법 침입 차단, 분산 환경에서의 로그 추적, 애플리케이션을 통한 정보 유출, 그리고 모든 업무를 중앙 서버에서 관리하는 씬 클라이언트(thin client)의 정보 유출 가능성 등을 고려해야 합니다. 경영진과 임직원의 보안 의식 또한 매우 중요합니다. 이러한 고려 사항들은 `DB` 보안의 3대 요소인 기밀성, 무결성, 가용성에 미치는 영향을 분석하여 프레임워크 솔루션에 반영되어야 합니다.

정보 침해 요소를 분석하고 평가하는 절차는 다음과 같습니다.

1.  **자산 식별**: 데이터의 가치와 민감성에 따라 보호 대상을 등급별로 분류합니다.
2.  **위협 식별**: 각 데이터 자산에 발생할 수 있는 위협(자연적, 인적, 환경적)의 종류를 식별합니다.
3.  **발생 가능성 식별**: 식별된 위협이 실제로 발생할 확률을 '상, 중, 하'로 평가합니다.
4.  **영향도 식별**: 위협 발생 시 기밀성, 무결성, 가용성에 미치는 손실 수준을 평가합니다.
5.  **위험도 산정**: 발생 가능성과 영향도를 조합하여 위험의 수준을 결정합니다.
6.  **보안 대책 식별**: 산출된 위험도에 따라 접근 제어, 암호화 등 필요한 보안 대책을 수립합니다.
7.  **결과 기록 및 보고**: 분석 결과를 기록하고 보고하여 보안 투자 등 의사결정에 반영합니다.

이러한 분석을 통해 도출된 위험도에 따라 개선 활동이 필수적인 영역, 개선이 필요한 영역, 지속적인 모니터링이 필요한 영역으로 나누어 솔루션을 차등 적용합니다.

`DB` 보안 관리 체계는 이러한 모든 과정을 포괄하며, 데이터의 일관성과 합리성을 증대시키는 것을 목적으로 합니다. 이 체계는 **관리 조직**, **관리 절차**, **관리 인력**으로 구성됩니다. 관리 조직은 경영진부터 `DBA`, 임직원까지 역할과 책임을 분담합니다. 관리 절차는 로그 및 백업 관리, 권한 관리, 취약점 관리 등 모든 활동을 표준화하고 문서화하여 일관성을 유지하는 것입니다. 관리 인력은 리더십, 기술적 역량, 적용 역량으로 구분하여 각 직무에 맞는 역량을 정의하고 확보하는 것을 의미합니다.

결론적으로, `DB` 보안 관리 체계 구축을 위해서는 조직, 프로세스, 인력이 조화를 이루어야 하며, 주기적인 교육과 점검을 통해 지속적으로 개선해 나가는 것이 중요합니다.

## **2025-09-08, 1교시 — 개념**

1) **한 줄 요약**(≤120자)
DB 보안 프레임워크의 기획, 설계, 구축, 운영 단계를 이해하고, 정보 침해 위험을 체계적으로 분석하여 효과적인 관리 체계를 수립하는 전 과정을 학습합니다.

2) **핵심 TL;DR**
* **보안 프레임워크 수명주기**: 보안은 **기획 → 설계 → 구축 → 운영**의 4단계 생명주기를 가지며, 구축 후 지속적인 모니터링과 개선이 핵심입니다.
* **위험 평가 절차**: **자산 식별**에서 시작해 **위협 분석**, **발생 가능성 및 영향도 평가**를 거쳐 **위험도**를 산정하고 **보안 대책**을 수립하는 체계적 과정입니다.
* **위험 매트릭스**: 발생 가능성과 영향도를 기준으로 위험도를 '상-중-하'로 등급화하여, 즉시 개선이 필요한 영역과 지속 관찰이 필요한 영역을 구분하고 자원을 배분합니다.
* **보안 관리의 3요소**: 효과적인 보안 관리 체계는 **조직(역할과 책임), 절차(표준화된 활동), 인력(역량과 교육)**의 세 가지 축으로 구성됩니다.
* **위협의 분류**: `DB`에 가해지는 위협은 **자연재해(자연적), 인적 실수나 악의적 공격(인적), 정전 등(환경적)**으로 분류하여 다각도로 대비해야 합니다.
* **보안의 근본 목표**: 모든 보안 활동은 데이터의 **기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)**을 보장하는 것을 최종 목표로 합니다.
* **비용-효과성 원칙**: 보안 솔루션은 무조건적인 고비용이 아닌, 조직이 감수할 위험 수준과 보호 대상의 가치를 고려하여 비용 대비 효과가 가장 높은 대책을 선택해야 합니다.
* **보안 교육의 중요성**: 기술적 통제만큼이나 중요한 것은 모든 단계(준비, 구축, 운영)에서 임직원의 보안 인식을 높이는 지속적인 교육입니다.

3) **표현 = 표준 용어**
* **보안 프레임워크 (Security Framework)**: 보안 목표 달성을 위한 정책, 절차, 기술의 구조화된 집합체.
* **위험 평가 (Risk Assessment)**: 자산, 위협, 취약점을 식별하고 위험 수준을 분석 및 평가하는 과정.
* **기밀성, 무결성, 가용성 (Confidentiality, Integrity, Availability - CIA Triad)**: 정보 보안의 3대 기본 원칙.
* **위험 매트릭스 (Risk Matrix)**: 위험의 발생 가능성과 영향도를 시각적으로 표현하여 우선순위를 정하는 도구.
* **씬 클라이언트 (Thin Client)**: 최소한의 자원으로 중앙 서버에 의존하여 동작하는 업무용 PC. 중앙 관리의 이점이 있으나, 서버 자체가 유출 경로가 될 수 있음.

4) **정석 보강(canon-std)**
정보보안 위험 평가는 조직의 자산을 식별하고, 해당 자산에 대한 **위협(Threat)**과 **취약점(Vulnerability)**을 분석하여 **위험(Risk)**을 정량적·정성적으로 산정하는 체계적 과정입니다. 핵심은 `위험 = 발생 가능성(Likelihood) × 영향도(Impact)` 공식을 통해 위험 수준을 도출하고, 이를 기반으로 허용 가능한 수준까지 위험을 감소시키기 위한 보안 통제(Control)의 우선순위를 결정하는 것입니다.

5) **실수·함정**
* **구축 후 방치**: 프레임워크 구축에만 집중하고, 가장 중요한 운영 및 지속적 개선 단계를 소홀히 하는 것.
* **일회성 평가**: 위험 평가는 비즈니스 환경 변화에 따라 주기적으로 갱신되어야 함에도 불구하고, 최초 1회만 수행하고 마는 실수.
* **기술 만능주의**: 암호화, 접근 제어 등 기술적 보안에만 치중하고 관리적·물리적 보안(정책, 교육, 조직)을 간과하는 함정.
* **내부자 위협 무시**: 외부 해킹 등 인적 위협을 외부 위협으로만 한정하고, 내부자의 실수나 악의적 행위 가능성을 낮게 평가하는 오류.
* **문서화 부실**: 관리 절차나 점검 결과를 문서로 남기지 않아, 보안 활동의 일관성이 깨지고 인수인계 시 문제가 발생하는 경우.
* **모든 데이터 동일 취급**: 데이터의 중요도나 민감성을 등급화하지 않고 모든 자산에 동일한 보안 수준을 적용하여 비효율을 초래하는 것.

**[Q1] DB 보안 프레임워크의 전체 수명주기(Life Cycle)는 어떻게 구성되며, 각 단계의 핵심 목표는 무엇인가요? | 태그: 보안 프레임워크, 수명주기**

**[Q2] 정보 침해 위험을 평가하는 구체적인 절차는 어떻게 되나요? | 태그: 위험 평가, 자산 식별, 영향도 분석**

## **2025-09-08, 2교시 — 개선본**

지난 시간에는 보안 프레임워크 개념을 다루었고, 이번에는 실제 `DBMS` 내에서 보안을 적용하는 실습 방법을 개괄적으로 살펴보겠습니다.

데이터베이스는 정보가 집약된 중요한 자산이므로 보안이 필수적입니다. 데이터 유출, 무단 접근, 무결성 훼손 등의 위협으로부터 데이터를 보호하는 것이 목표이며, 크게 `DB` 데이터 보안과 관리자 보안으로 나눌 수 있습니다. 데이터 유출의 가장 큰 원인은 내부자로, 권한 있는 사용자의 악의적인 행위가 약 80~90%를 차지합니다. 그 외에 `SQL Injection`, 피싱(phishing), 사회 공학적 공격 등도 주요 위협입니다. `SQL Injection`은 `SQL` 쿼리 내부에 악의적인 코드를 주입하는 공격 기법이며, 피싱은 사용자를 속여 정보를 입력하게 만드는 방식입니다.

이러한 위협으로부터 데이터베이스를 보호하기 위한 주요 보안 기법은 다음과 같습니다.

첫째, **사용자 인증(Authentication)**입니다. ID/패스워드, 생체 인식, 2단계 인증 등을 통해 인가된 사용자만 시스템에 접근하도록 통제합니다. 패스워드는 주기적으로 변경하도록 정책을 설정할 수 있으며, `DBMS`가 제공하는 인증 메커니즘을 이용해 인증 시스템을 실습할 수 있습니다. `(실습)`

둘째, **권한 관리(Authorization)**입니다. 역할 기반 접근 제어(RBAC)를 통해 사용자별로 접근 가능한 데이터와 수행할 수 있는 작업을 세분화하여 통제합니다. 특정 테이블의 `SELECT` 권한만 부여하거나, 특정 컬럼에만 접근하도록 제한할 수 있습니다. `(실습)` 또한, 뷰(View)를 이용해 테이블의 특정 행이나 컬럼만 노출시키는 것도 가능합니다. `(실습)`

셋째, **데이터 암호화(Encryption)**입니다. 전송 중인 데이터를 보호하기 위해 TLS(Transport Layer Security)나 SSL(Secure Sockets Layer) 같은 프로토콜을 사용합니다. 이는 클라이언트와 서버 간의 통신을 암호화하여 중간에서 데이터를 탈취하거나 변조하는 것을 방지하며, `HTTPS`가 대표적인 예입니다. 저장된 데이터 자체를 암호화하는 것도 중요하며, 디스크, 테이블, 컬럼 단위로 암호화를 적용할 수 있습니다. `(실습)` 암호화 키의 생성, 저장, 회전, 폐기 등 키 관리 절차 또한 `DBMS` 내에서 관리 가능합니다.

넷째, **데이터 무결성(Integrity) 및 가용성(Availability) 보장**입니다. 무결성은 데이터가 항상 정확하고 일관된 상태를 유지하는 것을 의미합니다. 이를 위해 **트랜잭션(Transaction)** 개념이 사용되며, 트랜잭션은 ACID 속성(원자성, 일관성, 고립성, 영속성)을 가집니다. 특히 여러 사용자가 동시에 데이터에 접근할 때 발생하는 문제를 막기 위해 병행 제어(Concurrency Control)가 필요하며, 이는 데이터 보안의 중요한 요소입니다. `(실습)` 또한, 주기적인 **백업과 복구** 절차를 통해 재해나 장애 발생 시 데이터를 보호하고 서비스의 연속성을 보장해야 합니다. `(실습)`

가용성 측면에서는 서버 중단을 방지하고 최적의 성능을 유지하는 것이 중요합니다. **인덱스(Index)**를 활용해 검색 효율을 높이고, **쿼리 최적화**를 통해 `SQL` 실행 속도를 개선할 수 있습니다. `(실습)`

다섯째, **네트워크 기반 접근 제어**입니다. 방화벽, 침입 탐지 시스템(IDS), 침입 방지 시스템(IPS) 등을 통해 네트워크 레벨에서부터 비인가 접근을 차단할 수 있습니다.

여섯째, **감사와 모니터링**입니다. `DBMS`의 로그 기록 기능을 활용하여 사용자의 모든 활동(로그인, 데이터 접근, 쿼리 실행 등)을 추적하고 분석할 수 있습니다. `(실습)` 누가, 언제, 무엇을 했는지 추적하여 이상 행위를 탐지하고, 민감 데이터에 대한 접근은 실시간으로 모니터링하여 보안을 강화할 수 있습니다.

최신 보안 이슈로는 클라우드 환경에서의 데이터 보안, 그리고 GDPR(유럽 개인정보보호법)이나 CCPA(캘리포니아 소비자 개인정보보호법) 같은 데이터 보호 규정 준수가 중요해지고 있습니다. 이러한 법규를 준수하지 않으면 막대한 벌금이나 법적 책임을 질 수 있습니다.

향후 실습할 내용들은 다음과 같습니다.

* **사용자 및 권한 관리**: `CREATE USER`로 계정을 만들고 `GRANT`, `REVOKE`로 권한을 부여 및 회수합니다. `(실습)`
* **프로파일(Profile) 활용**: 프로파일을 생성하여 사용자의 로그인 실패 횟수 제한이나 비밀번호 유효 기간을 설정합니다. `(실습)`
* **객체 권한 관리**: 특정 테이블이나 뷰에 대해 `SELECT`, `INSERT` 등 특정 작업만 허용하는 권한을 부여합니다. `(실습)`
* **감사(Auditing)**: `AUDIT` 명령어를 사용해 특정 테이블에 대한 접근 기록을 남기도록 설정합니다. `(실습)`
* **데이터 암호화**: `DBMS_CRYPTO`와 같은 패키지를 사용해 특정 컬럼의 데이터를 `AES` 알고리즘으로 암호화하여 저장합니다. `(실습)`
* **뷰(View) 생성**: `CREATE VIEW`를 통해 민감한 정보(주민등록번호 뒷자리 등)를 마스킹 처리한 가상 테이블을 만듭니다. `(실습)`
* **트랜잭션과 백업/복구**: `COMMIT`, `ROLLBACK`, `SAVEPOINT` 등을 사용해 트랜잭션을 제어하고, 데이터 복구 상황을 실습합니다. `(실습)`

이러한 실습은 오라클 `DBMS` 환경에서 진행될 예정입니다.

**[Q1] 데이터 무결성을 보장하기 위해 트랜잭션이 가져야 할 ACID 속성이란 무엇인가요? | 태그: 트랜잭션, 무결성, ACID**
* **모범답(강의 기준)**: ACID는 원자성, 일관성, 고립성, 영속성을 의미합니다. 트랜잭션은 분해되지 않는 하나의 단위(원자성)로 처리되어야 하고, 처리 후에도 데이터는 일관성을 유지해야 하며(일관성), 한 트랜잭션이 실행되는 동안 다른 트랜잭션이 개입할 수 없어야 합니다(고립성).

**[Q2] 여러 사용자가 동시에 동일 데이터를 수정할 때 어떤 문제가 발생하며, 이를 어떻게 방지하나요? | 태그: 트랜잭션, 병행 제어, 무결성**
* **모범답(강의 기준)**: 한 사용자가 데이터를 수정하는 도중에 다른 사용자가 접근하면 데이터 일관성이 깨지는 문제가 발생합니다. 이를 방지하기 위해 트랜잭션의 고립성을 보장하는 병행 제어가 필요하며, 한 작업이 끝날 때까지 다른 작업이 접근하지 못하도록 막아야 합니다.
* **정석체크(면접 3초)**: 동시성 문제는 **갱신 손실(Lost Update)**이나 **현황 파악 오류(Dirty Read)** 등을 유발하여 데이터 무결성을 훼손합니다. 이를 방지하기 위해 `DBMS`는 **락(Locking)** 기법을 사용하여 트랜잭션의 공유 데이터 접근을 제어합니다. 하지만 락을 과도하게 사용하면 **교착상태(Deadlock)**가 발생할 수 있으므로 주의해야 합니다.

**[Q3] 사용자 계정의 비밀번호 정책(예: 유효기간, 실패 횟수)은 어떻게 강제할 수 있나요? | 태그: 계정 관리, 프로파일, 비밀번호 정책**

* **정석체크(면접 3초)**: `CREATE PROFILE` 명령어로 패스워드 정책을 정의하고, `ALTER USER ... PROFILE` 구문을 통해 사용자에게 해당 프로파일을 할당합니다. 예를 들어 `ALTER PROFILE app_user_profile LIMIT FAILED_LOGIN_ATTEMPTS 5 PASSWORD_LIFE_TIME 90;` 처럼 설정할 수 있습니다. `DEFAULT` 프로파일을 그대로 사용하면 보안에 취약할 수 있습니다.

**[Q4] 데이터 암호화는 '전송 중'인 데이터와 '저장된' 데이터에 대해 어떻게 다르게 적용되나요? | 태그: 암호화, TDE, TLS**

* **정석체크(면접 3초)**: 전송 중인 데이터(in-transit)는 **TLS**를 통해 네트워크 구간을 암호화하여 보호합니다. 저장된 데이터(at-rest)는 **TDE(Transparent Data Encryption)**로 데이터 파일 전체를 암호화하거나, 특정 컬럼만 암호화 함수(`AES_ENCRYPT`)를 이용해 보호합니다. 두 가지 모두 적용해야 완전한 데이터 보호가 가능합니다.

**[Q5] 사용자에게 테이블의 모든 정보가 아닌 특정 컬럼에 대한 `SELECT` 권한만 부여하는 등, 세분화된 권한 설정이 가능한가요? | 태그: 권한(GRANT/REVOKE), 객체 권한, 최소 권한 원칙**
* **모범답(강의 기준)**: 네, 가능합니다. 특정 테이블의 특정 컬럼에 대해서만 `SELECT`나 `UPDATE` 같은 특정 명령어만 수행할 수 있도록 권한을 세분화하여 부여할 수 있습니다. 이는 객체 보안의 일부입니다.
* **정석체크(면접 3초)**: **객체 권한(Object Privilege)**을 통해 세분화된 통제가 가능합니다. 예를 들어, `GRANT SELECT (emp_name, salary) ON employees TO analyst_role;` 과 같이 특정 컬럼에 대한 조회 권한만 부여할 수 있습니다. 이는 **최소 권한 원칙(Principle of Least Privilege)**을 준수하는 중요한 방법입니다.

보안 설정에서는 주로 `GRANT`, `REVOKE`, `COMMIT`, `ROLLBACK`과 같은 데이터 제어어(DCL)를 사용하지만, `SELECT`나 `UPDATE` 같은 데이터 조작어(DML)와 `ALTER` 같은 데이터 정의어(DDL)도 필요에 따라 함께 활용됩니다. 특히 감사나 암호화 기능은 단순한 DCL만으로는 구현이 어려워, `FUNCTION`이나 `PROCEDURE` 같은 PL/SQL 프로그램 로직이 추가됩니다. 2학년 과정에서 배운 데이터베이스 내용을 복습하며, 뷰와 인덱스 역시 보안에 어떻게 활용되는지 다룰 것입니다.

SQL의 세 가지 주요 언어는 다음과 같습니다.

1. **DDL (Data Definition Language)**: `CREATE`, `ALTER`, `DROP` 등을 사용하여 테이블 구조를 생성하거나 변경합니다.
2. **DML (Data Manipulation Language)**: `INSERT`, `DELETE`, `UPDATE`, `SELECT`를 사용하여 테이블 내 데이터를 조작합니다.
3. **DCL (Data Control Language)**: 데이터 접근 및 사용 권한을 제어합니다. 데이터베이스 보안 시간에는 `GRANT`, `REVOKE`, `ROLE`뿐만 아니라 감사(Auditing)와 암호화까지 심도 있게 다룹니다.

SQL 쿼리는 대소문자를 구분하지 않지만, 테이블에 저장된 데이터 값 자체는 대소문자를 정확히 구별합니다. 모든 SQL 명령어는 세미콜론(;)으로 끝나야 합니다.

오늘 실습에서는 `EMP`와 `DEPT` 테이블을 사용할 것입니다. `EMP` 테이블의 `DEPTNO` 컬럼은 `DEPT` 테이블의 `DEPTNO`를 참조하는 외래 키 관계를 가집니다. 또한 `EMP` 테이블의 `MGR` 컬럼은 같은 테이블의 `EMPNO`를 참조하는 자기 자신 참조(self-join) 구조를 가지고 있어, 사수-부사수 관계를 표현합니다. 최상위 관리자는 사수가 없으므로 `MGR` 값이 `NULL`로 채워집니다.

본격적인 실습에 앞서 각자 개인 이니셜로 실습용 계정을 생성하겠습니다. (실습) 시스템 관리자 계정(`SYSTEM`)으로 접속하여 새 사용자를 생성합니다. (실습) 사용자 이름은 본인 이니셜로, 비밀번호는 `1234`로 설정하고 기본 테이블스페이스는 `USERS`, 임시 테이블스페이스는 `TEMP`로 지정합니다. (실습) 생성된 계정에는 데이터베이스 접속 권한(`CONNECT` role)과 객체 생성 및 조작 권한(`RESOURCE` role)을 부여해야 합니다. (실습) 테이블스페이스 할당량은 무제한(unlimited)으로 설정하고 적용합니다. (실습)

계정 생성이 완료되면, 해당 계정으로 새로운 접속을 추가합니다. (실습) 접속 테스트를 통해 성공적으로 연결되는지 확인합니다. (실습) 그다음 제공된 스크립트 파일을 사용하여 `DEPT` 테이블과 `EMP` 테이블을 순서대로 생성합니다. (실습) 참조 무결성 제약조건 때문에 부모 테이블인 `DEPT`를 먼저 생성해야 합니다. (실습) 스크립트 실행 후, 테이블 목록을 새로고침하여 두 테이블이 정상적으로 생성되었는지 확인합니다. (실습)

오라클 데이터베이스는 기본적으로 계정 비밀번호 만료 기간이 180일로 설정되어 있습니다. 이 설정을 변경하여 비밀번호가 만료되지 않도록 처리하겠습니다. (실습) SYSTEM 계정에서 다음 query를 실행하여 현재 프로파일의 비밀번호 만료 설정을 확인할 수 있습니다.

SELECT * FROM dba_profiles WHERE profile = 'DEFAULT' AND resource_name = 'PASSWORD_LIFE_TIME';

변경 후 다시 확인 query를 실행하여 UNLIMITED로 바뀌었는지 점검합니다. (실습)

## 2025-09-15, 1교시 — 개념

### 한 줄 요약

데이터베이스 보안의 이론적 배경을 복습하고, 사용자 계정 생성, Role을 이용한 기본 권한 부여 등 보안 실무의 기초가 되는 SQL(DDL, DML, DCL) 및 관리자 실습을 시작합니다.

### 핵심 TL;DR

- 데이터베이스 보안은 **DCL(Data Control Language)**, 즉 `GRANT`와 `REVOKE`가 핵심이지만, 실제 구현을 위해서는 DDL, DML, PL/SQL에 대한 종합적인 이해가 필수적입니다.
- SQL은 크게 **DDL(정의)**, **DML(조작)**, **DCL(제어)** 세 가지로 나뉘며, 보안은 주로 DCL의 영역에 집중됩니다.
- **PL/SQL** (`FUNCTION`, `PROCEDURE`)은 단순 DCL만으로 처리하기 어려운 복잡한 감사 추적이나 데이터 암호화 로직을 구현할 때 사용됩니다.
- **사용자(User)**는 데이터베이스 접근과 객체 소유의 기본 단위로, 고유한 계정과 인증 수단(비밀번호)을 가집니다.
- **권한(Privilege)**은 특정 SQL 명령어나 객체에 접근하여 조작할 수 있는 허가이며, **역할(Role)**을 통해 그룹으로 묶어 효율적으로 관리합니다.
- **`CONNECT` Role**은 데이터베이스에 접속할 수 있는 기본 권한을, **`RESOURCE` Role**은 테이블, 인덱스 등 객체를 생성하고 조작할 수 있는 권한을 포함합니다.
- **프로파일(Profile)**은 사용자에게 적용되는 리소스 제한 및 비밀번호 정책(만료 기간, 복잡도, 실패 시 잠금 등)을 정의하는 객체입니다.
- `WHERE` 절은 `SELECT` 문에서 가장 기본적인 데이터 접근 제어 수단으로, 조건에 맞는 행(Row)만 필터링하여 반환합니다.
- **참조 무결성(Referential Integrity)**은 외래 키(Foreign Key) 제약조건을 통해 테이블 간 데이터의 일관성을 유지하며, 잘못된 데이터 삽입/삭제를 막는 중요한 보안 요소입니다.

### 표현 = 표준 용어

- **DDL (Data Definition Language)**: 데이터 구조를 정의하는 언어. (`CREATE`, `ALTER`, `DROP`)
- **DML (Data Manipulation Language)**: 데이터를 조작(조회, 삽입, 수정, 삭제)하는 언어.
- **DCL (Data Control Language)**: 데이터에 대한 접근 권한을 제어하는 언어.
- **User / Schema**: 데이터베이스 사용자 계정 및 해당 사용자가 소유한 객체의 집합.
- **Role**: 하나 이상의 권한(Privilege)을 담는 컨테이너로, 사용자에게 부여하여 권한을 관리.
- **Privilege**: 특정 작업을 수행할 수 있도록 부여된 권한.
- **Profile**: 사용자의 시스템 리소스 사용 및 비밀번호 정책을 관리하는 객체.
- **`GRANT privilege | role TO user | role;`**: 사용자나 다른 역할에 권한 또는 역할을 부여하는 명령어.
- **`REVOKE privilege | role FROM user | role;`**: 부여된 권한이나 역할을 회수하는 명령어.
- **`ALTER PROFILE ... LIMIT ...`**: 프로파일의 리소스 제한(예: 비밀번호 만료 기간)을 수정하는 명령어.
- **Referential Integrity**: 외래 키를 통해 테이블 간의 관계에서 데이터의 일관성을 보장하는 규칙.

### 정석 보강(canon-std)

데이터베이스 보안의 시작은 **사용자(User)와 역할(Role)을 명확히 분리**하는 것입니다. 사용자는 시스템에 접속하는 주체(identity)이며, 역할은 직무에 따라 필요한 권한(privilege)들의 묶음입니다. 권한을 사용자에 직접 부여하는 대신 역할에 부여하고, 사용자에게는 역할을 부여하는 **RBAC(Role-Based Access Control)** 모델을 따르는 것이 표준입니다. 이는 최소 권한 원칙을 적용하고 권한 관리를 단순화하는 핵심 요소입니다. `CREATE USER kym IDENTIFIED BY ...;`로 사용자를 생성하고, `GRANT CONNECT, RESOURCE TO kym;` 처럼 역할을 부여하여 권한을 위임합니다.

### 실수·함정

- 개발 편의를 위해 모든 권한을 가진 `PUBLIC` 역할에 불필요한 권한을 부여하는 행위.
- `DBA`나 `ANY`로 시작하는 강력한 시스템 권한(`CREATE ANY TABLE` 등)을 일반 사용자 계정에 직접 부여하는 것.
- `RESOURCE` Role이 단순히 테이블 생성 권한만 포함한다고 오해하고, 불필요한 프로시저, 트리거 생성 권한까지 함께 부여하는 경우.
- 애플리케이션 소스 코드나 배포 스크립트에 데이터베이스 계정의 비밀번호를 평문으로 하드코딩하는 것.
- `DEFAULT` 프로파일의 기본 비밀번호 정책(예: 180일 만료)을 확인하지 않아 운영 중인 계정이 예고 없이 만료되거나 잠기는 문제.
- `GRANT` 또는 `REVOKE` 실행 후, 해당 변경 사항이 시스템에 즉시 적용되지 않는 경우를 고려하지 않는 것.
- 권한 회수(`REVOKE`) 시 다른 객체나 권한에 미치는 종속성(dependency)을 파악하지 않고 실행하는 경우.

## **2025-09-15, 2교시 — 개선본**

`SELECT` 문의 기본 구조는 `SELECT`, `FROM`, `WHERE`로 이루어집니다. `SELECT` 절에는 조회할 컬럼 목록이나 전체를 의미하는 `*`를, `FROM` 절에는 테이블명을, `WHERE` 절에는 조회 조건을 기술합니다. `DISTINCT` 키워드로 중복을 제거하거나, `AS`를 사용해 컬럼 별칭(alias)을 지정할 수 있으며, 집계 함수도 사용 가능합니다. SQL 쿼리는 다양한 방식으로 작성할 수 있지만, 처리 속도와 효율성을 고려하여 간결하게 작성하는 것이 좋습니다.

WHERE 절에서 NULL 값을 다룰 때는 = 연산자가 아닌 IS NULL 또는 IS NOT NULL 키워드를 사용해야 합니다. NULL은 '값이 없음' 또는 '미정'을 의미하며, 숫자 0이나 공백 문자와는 다릅니다. 예를 들어, 커미션(Comm) 값이 NULL이 아닌 사원의 이름과 커미션을 조회하는 쿼리는 다음과 같습니다. (실습)

SELECT Ename, Comm FROM EMP WHERE Comm IS NOT NULL;

만약 0을 제외하고 싶다면, WHERE Comm > 0과 같이 명시적인 조건을 추가해야 합니다.

실습을 진행하며 실행한 쿼리문은 워크시트에 모두 남겨두시기 바랍니다. 나중에 실습 내용 전체를 확인할 수 있도록 한 줄씩 실행(`Ctrl+Enter`)하며 결과를 확인하고, 쿼리 내역은 지우지 않고 유지합니다. (실습)

`WHERE` 절에서 다수의 값을 비교할 때 유용한 키워드들이 있습니다.

- `BETWEEN a AND b`: `a`와 `b` 사이의 값(경계값 포함)을 조회할 때 사용하며, `컬럼 >= a AND 컬럼 <= b` 와 동일합니다. (실습)
- `IN (list)`: 괄호 안의 목록에 포함된 값 중 하나와 일치하는 데이터를 조회할 때 사용하며, 여러 개의 `OR` 조건을 간결하게 표현할 수 있습니다. (실습)
- `NOT` 키워드를 `NOT BETWEEN`, `NOT IN`과 같이 사용하면 조건의 반대, 즉 범위를 벗어나거나 목록에 포함되지 않는 데이터를 조회할 수 있습니다. (실습)

문자열의 일부가 일치하는 데이터를 검색할 때는 `LIKE` 연산자를 와일드카드와 함께 사용합니다.

- `%` (percent): 0개 이상의 모든 문자를 의미합니다. (예: `A%`는 A로 시작하는 모든 문자열)
- `_` (underscore): 정확히 1개의 문자를 의미합니다. (예: `__A%`는 세 번째 글자가 A인 모든 문자열)

이름이 'A'로 시작하는 사원을 찾는 쿼리는 다음과 같습니다. (실습)

SELECT * FROM EMP WHERE Ename LIKE 'A%';

대표적인 집계 함수로는 `COUNT` (개수), `SUM` (합계), `AVG` (평균), `MIN` (최소값), `MAX` (최대값)가 있습니다. `COUNT` 함수 사용 시 주의할 점은, `COUNT(*)`가 `NULL` 값을 포함한 모든 행의 수를 반환하는 반면, `COUNT(컬럼명)`은 해당 컬럼의 값이 `NULL`인 행을 제외하고 개수를 센다는 것입니다. (실습) 따라서 전체 레코드 수를 정확히 세려면 `COUNT(*)`를 사용하는 것이 일반적입니다. 집계 함수의 결과 컬럼은 `AS` 키워드를 이용해 의미 있는 이름으로 변경할 수 있습니다. (실습)

숫자 타입의 컬럼은 `+`, `-`, `*`, `/` 같은 산술 연산자를 사용하여 새로운 값을 계산할 수 있습니다. 예를 들어, 급여를 10% 인상한 값을 조회할 수 있습니다. (실습) `AVG` 함수 등으로 소수점이 발생한 결과는 `ROUND` 함수를 사용하여 반올림할 수 있습니다. (실습)

데이터베이스의 조회 결과는 기본적으로 순서가 보장되지 않으므로, 특정 순서로 정렬하려면 `ORDER BY` 절을 사용해야 합니다. `ORDER BY`는 항상 쿼리문의 가장 마지막에 위치합니다.

- `ASC` (Ascending): 오름차순 (기본값, 생략 가능)
- DESC (Descending): 내림차순

    ORDER BY DEPTNO ASC, ENAME ASC와 같이 콤마(,)로 구분하여 여러 기준으로 다중 정렬을 할 수도 있습니다. (실습)

`GROUP BY` 절은 특정 컬럼의 값을 기준으로 데이터를 그룹화하고, 각 그룹에 대해 집계 함수를 적용할 때 사용합니다. `SELECT` 절에는 `GROUP BY`에서 사용한 컬럼과 집계 함수만 올 수 있다는 문법적 제약이 있습니다. 예를 들어, 각 부서별 평균 연봉을 계산할 수 있습니다. (실습)

`HAVING` 절은 `GROUP BY`로 그룹화된 결과에 대한 조건을 지정할 때 사용됩니다. `WHERE` 절이 그룹화 전의 개별 행 데이터를 필터링한다면, `HAVING` 절은 그룹화 후의 집계 결과를 필터링합니다. 예를 들어, 부서별 인원수를 계산한 후, 인원이 5명 이상인 부서만 조회할 수 있습니다. (실습)

쿼리의 실행 순서는 일반적으로 `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` 순으로 처리됩니다. 그룹화 전 조건은 `WHERE`에, 그룹화 후 조건은 `HAVING`에 기술해야 합니다. (실습)

## **2025-09-15, 2교시 — 개념**

### 한 줄 요약

`WHERE` 절의 `NULL`, `BETWEEN`, `IN`, `LIKE` 등 다양한 조건 연산자를 학습하고, 데이터를 그룹화(`GROUP BY`, `HAVING`)하고 정렬(`ORDER BY`)하는 고급 `SELECT` 쿼리 기법을 다룹니다.

### 핵심 TL;DR

- **`NULL`**은 '값이 없음'을 의미하며, 일반 비교 연산자(`=`, `!=`)가 아닌 `IS NULL` 또는 `IS NOT NULL` 키워드로만 비교해야 합니다.
- **`BETWEEN`**은 지정된 두 값 사이의 범위(경계값 포함)를 검색하며, **`IN`**은 제시된 목록 내 값들과 일치하는 데이터를 검색하는 데 사용됩니다.
- **`LIKE`** 연산자는 와일드카드(`%`: 0개 이상 문자, `_`: 1개 문자)와 함께 사용하여 문자열의 특정 패턴을 검색합니다.
- **`COUNT(*)`**는 `NULL`을 포함한 모든 행의 수를 반환하는 반면, **`COUNT(컬럼명)`**은 해당 컬럼 값이 `NULL`인 행을 제외하고 개수를 계산합니다.
- **`ORDER BY`**는 조회된 결과 집합을 특정 기준에 따라 정렬하는 유일한 방법이며, 항상 쿼리문의 가장 마지막에 작성됩니다.
- **`GROUP BY`**는 특정 컬럼을 기준으로 데이터를 그룹화하여, 각 그룹에 대한 통계(예: 부서별 평균 급여)를 집계 함수로 계산하는 기능입니다.
- **`WHERE`**는 그룹화 전 개별 행을 필터링하고, **`HAVING`**은 `GROUP BY`로 집계된 그룹 결과에 대한 조건을 적용하여 필터링합니다.
- SQL 쿼리의 논리적 실행 순서는 **`FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`** 이며, 이 순서를 이해해야 복잡한 쿼리를 정확히 작성할 수 있습니다.

### 표현 = 표준 용어

- **`NULL`**: 데이터 값이 존재하지 않거나 알 수 없는 상태를 나타내는 특수한 마커.
- **`IS NULL / IS NOT NULL`**: `NULL` 값을 검사하기 위한 전용 연산자.
- **`BETWEEN a AND b`**: `a`와 `b`를 포함하는 연속적인 범위를 지정하는 연산자.
- **`IN (value1, value2, ...)`**: 값 목록 중 하나와 일치하는지 확인하는 연산자.
- **`LIKE 'pattern'`**: 문자열 데이터에 대한 패턴 일치 검색을 수행하는 연산자.
- **Wildcards (`%`, `_`)**: `LIKE`와 함께 사용되어 임의의 문자(열)을 대체하는 특수 기호.
- **Aggregate Function**: 여러 행의 값을 입력받아 단일 값을 반환하는 함수. (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`)
- **`ORDER BY column [ASC|DESC]`**: 결과 집합을 오름차순(`ASC`) 또는 내림차순(`DESC`)으로 정렬하는 절.
- **`GROUP BY column`**: 지정된 컬럼 값이 같은 행들을 하나의 그룹으로 묶는 절.
- **`HAVING condition`**: `GROUP BY`로 생성된 그룹에 대한 조건을 지정하는 절.

### 정석 보강(canon-std)

`SELECT` 문에서 **`WHERE`와 `HAVING`의 차이를 명확히 구분**하는 것이 중요합니다. 두 절 모두 데이터를 필터링하지만, 작동하는 시점이 다릅니다. **`WHERE` 절은 `GROUP BY`가 적용되기 전**, 즉 개별 행(row)에 대해 조건을 적용하여 필터링합니다. 반면 **`HAVING` 절은 `GROUP BY`로 데이터가 그룹화된 후**, 집계 함수를 통해 나온 그룹 결과에 대해 조건을 적용합니다. 따라서 `WHERE` 절에는 집계 함수를 쓸 수 없지만, `HAVING` 절에서는 집계 함수를 조건으로 사용할 수 있습니다. `... WHERE sal > 1000 GROUP BY deptno HAVING COUNT(*) > 3;`는 "급여 1000 초과인 직원들을 대상으로, 부서별 그룹화를 한 뒤, 그룹 내 인원이 3명을 초과하는 부서만 보여달라"는 의미입니다.

### 실수·함정

- `WHERE Comm = NULL`과 같이, `NULL` 값을 = 연산자로 비교하여 원하는 결과를 얻지 못하는 실수.
- `COUNT(*)`와 `COUNT(Comm)`의 차이를 인지하지 못하고, `NULL` 값이 많은 컬럼을 카운트하여 전체 행 수와 다르다는 사실에 혼란을 겪는 경우.
- `WHERE AVG(Sal) > 2000`처럼, `WHERE` 절에 집계 함수를 사용하여 문법 오류를 발생시키는 것.
- `GROUP BY` 절에 명시하지 않은 일반 컬럼(집계 함수로 감싸지 않은)을 `SELECT` 목록에 포함하여 발생하는 오류.
- `ORDER BY` 절을 `GROUP BY`나 `WHERE` 절 앞에 작성하여 쿼리 실행 순서에 맞지 않는 문법 오류를 내는 경우.
- `BETWEEN` 연산자가 경계값을 포함(inclusive)한다는 것을 잊고, `>` 또는 `<`와 동일하다고 착각하는 것.
- `LIKE`의 와일드카드 `%`와 `_`의 차이를 혼동하는 경우 (`%`: 0개 이상의 모든 문자, `_`: 정확히 1개의 문자).

**[Q3] SQL 쿼리에서 `WHERE` 절과 `HAVING` 절의 기능적 차이와 올바른 사용법은 무엇인가? | `GROUP BY`, `HAVING`, `WHERE`**

## 정리
## **2025-09-22, 1교시 — 개선본**

지난 시간 `GROUP BY`와 정렬까지 기본 `SELECT` 문법을 다루었고, 오늘은 가장 많이 사용되는 `SELECT` 구문 중에서도 중첩 질의, 즉 서브쿼리(subquery)와 같은 고급 쿼리 부분을 학습하겠습니다. 쿼리 안에 또 다른 쿼리가 들어가는 중첩 구조는 반드시 이해해야 합니다.

지난번에 사용했던 실습 테이블을 준비된 상태에서 조인(join) 연산을 처리해 보도록 하겠습니다. (실습)

기본적인 조인(join) 연산은 두 테이블을 합치면서 공통 속성을 `WHERE` 조건절에 나열하는 방식입니다. `SELECT`, `FROM`, `WHERE` 순서로 사용하며, `GROUP BY`, `HAVING`, `ORDER BY` 절을 추가할 수 있습니다. `GROUP BY`에 사용된 속성은 반드시 `SELECT` 절에 포함되어야 하고, `WHERE` 절은 전체 레코드에 대한 조건, `HAVING` 절은 그룹화된 결과에 대한 조건을 지정합니다. 쿼리 실행 순서는 `WHERE` 필터링, `GROUP BY` 그룹화, `HAVING` 필터링, `SELECT` 프로젝션, `ORDER BY` 정렬 순입니다.

가장 일반적으로 사용되는 조인(join) 방식은 `JOIN` 키워드 없이 `WHERE` 조건절로 테이블을 연결하는 것입니다. `FROM` 절에는 조인할 테이블들을 나열하며, N개의 테이블을 조인(join)하기 위해서는 N-1개의 조인(join) 조건이 필요합니다. 만약 서로 다른 테이블에 동일한 이름의 컬럼이 존재한다면, `테이블명.속성명` 형식으로 명확하게 지정해야 합니다.

`EMPLOYEE` 테이블과 `DEPARTMENT` 테이블을 부서 번호(`DPTNO`)를 기준으로 조인(join)하는 실습을 진행하겠습니다. (실습) 두 테이블에 `DPTNO`라는 동일한 이름의 필드가 있으므로, `WHERE` 절에서 `테이블명.DPTNO`와 같이 소속 테이블을 명시해야 합니다.

예를 들어, 급여가 1500 이상인 사원의 이름, 부서명, 근무지를 조회하는 쿼리를 작성해 보겠습니다. 사원 이름은 `EMPLOYEE`, 부서명과 위치는 `DEPARTMENT` 테이블에 있으므로 조인(join)이 필요합니다. `FROM` 절에 두 테이블을 나열하고, `WHERE` 절에 조인(join) 조건과 급여 조건을 `AND`로 연결합니다. 이 쿼리도 작성해두시기 바랍니다. (실습) 테이블 설계 시 정규화를 통해 데이터를 분해하므로, 실제 업무에서는 단일 테이블 조회보다 여러 테이블을 조인(join)하는 경우가 훨씬 많습니다.

만약 조인(join) 대상 테이블들에서 컬럼 이름이 중복되지 않는다면, `SELECT` 절이나 `WHERE` 절에서 테이블명을 생략할 수 있습니다. 또한, 테이블 이름이 길 경우 별칭(alias)을 사용하여 쿼리를 간결하게 작성할 수 있습니다. `FROM` 절의 테이블명 뒤에 한 칸 띄고 별칭을 부여하면 됩니다. 이 별칭(alias)을 사용하는 방법도 실습합니다. (실습) `EMPLOYEE`는 `E`, `DEPARTMENT`는 `D`와 같이 짧은 별칭을 사용하면 `WHERE` 절의 긴 조인(join) 조건을 간결하게 표현할 수 있습니다.

실무에서는 `WHERE` 절을 이용한 조인(join)을 가장 많이 사용하지만, 표준 SQL에는 `JOIN` 키워드를 사용하는 문법도 존재하며 이는 정보처리기사 같은 시험에 자주 출제됩니다. 여기에는 `INNER JOIN`, `LEFT OUTER JOIN`, `RIGHT OUTER JOIN`, `FULL OUTER JOIN` 등이 있습니다.

`OUTER JOIN`을 실습하기 위해 T1, T2 테이블을 생성하여 실습을 준비합니다. (실습) `INNER JOIN`은 두 테이블에 공통으로 존재하는 값만 연결하는 일반적인 조인(join)입니다. 반면 `OUTER JOIN`은 조인(join) 조건에 만족하는 데이터가 없는 경우에도 특정 테이블의 모든 행을 결과에 포함시키고 싶을 때 사용하며, 대응하는 값이 없는 부분은 `NULL`로 채웁니다.

오라클에서는 `OUTER JOIN`을 표현하기 위해 `WHERE` 조건절에서 정보가 부족한 쪽에 `(+)` 기호를 붙이는 독자적인 문법을 제공합니다. 예를 들어 `WHERE T1.CODE = T2.CODE(+)`는 T1을 기준으로 T2의 정보를 붙이는 `LEFT OUTER JOIN`을 의미합니다. T2에 해당 코드가 없으면 T2의 컬럼 값들은 `NULL`로 표시됩니다. 표준 SQL 문법은 `FROM T1 LEFT OUTER JOIN T2 ON T1.CODE = T2.CODE`와 같이 작성합니다. 오라클의 `(+)` 문법이 더 간결하지만, 이는 오라클 DBMS에서만 사용 가능합니다. `LEFT`, `RIGHT`, `FULL OUTER JOIN` 세 가지를 모두 실습합니다. (실습)

하나의 테이블이 자기 자신을 참조하는 경우 셀프 조인(self-join)을 사용합니다. 예를 들어 `EMPLOYEE` 테이블에는 각 사원의 관리자 정보(MGR)가 사원 번호(EMPNO)로 저장되어 있습니다. 이때 사원 이름과 그 사원의 관리자 이름을 함께 조회하려면, `EMPLOYEE` 테이블에 두 개의 다른 별칭(alias)을 부여하여 조인(join)해야 합니다. 셀프 조인(self-join)에서는 별칭 사용이 필수적입니다. 이 셀프 조인(self-join)도 자주 사용되니 실습을 완료해주시기 바랍니다. (실습)

테이블 3개 이상을 조인(join)할 경우, 테이블 개수(N)보다 하나 적은 N-1개의 조인(join) 조건을 `AND`로 연결해야 합니다. 예를 들어 3개 테이블을 조인(join)하려면 2개의 조인(join) 조건이 필요합니다.

이제 다양한 조인(join) 사례를 실습해 보겠습니다. 'DALLAS'에 근무하는 사원의 이름, 부서명, 입사일자를 조회하는 쿼리를 작성합니다. (실습) 또한, 1981년 9월 1일 이전에 입사한 사원의 이름과 부서명을 조회하는 쿼리도 작성합니다. (실습) 다음으로, 관리자가 'BLAKE'인 부하 직원의 이름과 급여 정보를 셀프 조인(self-join)을 이용해 조회합니다. (실습) 마지막으로, 관리자가 'BLAKE'인 부하 직원의 이름, 급여, 그리고 '근무지' 정보까지 조회하려면 `EMPLOYEE` 테이블의 셀프 조인(self-join)과 `DEPARTMENT` 테이블의 조인(join), 즉 3개 테이블 조인이 필요합니다. (실습)

`UNION`(합집합), `INTERSECT`(교집합), `MINUS`(차집합)와 같은 집합 연산자도 있습니다. 두 질의 결과의 컬럼 개수와 데이터 타입이 일치해야 사용할 수 있습니다. 특히 `MINUS`는 어떤 결과 집합에서 특정 조건을 만족하는 부분을 제외할 때 유용하게 사용됩니다. 예를 들어, 급여 2500 이상인 사원 중에서 직무가 'MANAGER'인 사원을 제외한 나머지를 조회할 때 `MINUS`를 사용하면 `WHERE` 조건절보다 편리할 수 있습니다. 이 예제를 실습해 보시길 바랍니다. (실습)

고급 기법인 서브쿼리(subquery)는 쿼리문 안에 또 다른 `SELECT` 문을 포함하는 구조입니다. 서브쿼리는 `SELECT`, `UPDATE`, `INSERT`, `CREATE VIEW` 등 다양한 구문에서 사용될 수 있습니다. 서브쿼리의 핵심은 반환하는 값의 종류가 단일 값(single-row)인지 복수 값(multi-row)인지에 따라 사용하는 연산자가 달라진다는 점입니다.

서브쿼리가 단 하나의 값(예: `MIN(SAL)`, `AVG(SAL)`)을 반환할 경우, 외부 쿼리에서는 =, `>`, `<` 와 같은 비교 연산자를 사용합니다. 예를 들어, 특정 직무의 최저 급여보다 높은 급여를 받는 사원을 조회할 수 있습니다. 이때 `WHERE` 절에는 집계 함수(`MIN`, `MAX`, `AVG` 등)를 직접 쓸 수 없으므로 반드시 서브쿼리를 사용해야 합니다.

반면, 서브쿼리가 여러 개의 값(예: 특정 직무를 가진 모든 사원의 급여 목록)을 반환할 경우에는 `IN` 또는 `NOT IN` 연산자를 사용해야 합니다. `IN`은 목록에 포함된 값 중 하나와 일치하는 경우를 찾고, `NOT IN`은 목록에 없는 경우를 찾습니다. 단일 값 반환과 복수 값 반환 서브쿼리를 비교하며 실습해 보겠습니다. (실습)

끝.

## **2025-09-22, 1교시 — 개념**

### **한 줄 요약**

여러 테이블의 데이터를 결합하는 조인(Join), 쿼리 내부에 다른 쿼리를 포함하는 서브쿼리(Subquery), 그리고 결과 집합을 연산하는 집합 연산자를 통해 복잡한 데이터 관계를 조회하고 필터링하는 방법을 학습합니다.

---

### **핵심 TL;DR**

- **조인(Join)의 기본**: 두 개 이상의 테이블에서 연관된 데이터를 결합하기 위해 사용하며, N개의 테이블 조인 시 N-1개의 연결 조건이 필요합니다.
- **WHERE 절 조인**: 실무에서 가장 흔하게 사용하는 방식으로, `FROM` 절에 테이블을 나열하고 `WHERE` 절에 조인 조건을 명시합니다.
- **테이블 별칭(Alias)**: `FROM` 절에서 테이블에 짧은 별칭을 부여하면, 쿼리 내에서 컬럼을 명시할 때 코드를 간결하게 만들 수 있습니다. 셀프 조인(Self-Join) 시에는 필수입니다.
- **INNER JOIN**: 조인 조건에 완전히 일치하는 행들만 결과에 포함시키는 가장 일반적인 조인입니다.
- **OUTER JOIN**: 한쪽 테이블의 모든 행을 유지하고, 다른 쪽 테이블에 일치하는 데이터가 없을 경우 `NULL`로 표시하여 결과를 반환합니다. (`LEFT`, `RIGHT`, `FULL`)
- **SELF JOIN**: 하나의 테이블이 자기 자신을 참조하는 관계(예: 사원과 관리자)를 조회할 때 사용합니다.
- **서브쿼리(Subquery)**: 다른 SQL 문 안에 포함된 `SELECT` 문으로, 외부 쿼리의 `WHERE` 절 등에서 조건 값으로 활용됩니다.
- **서브쿼리 값 유형**: 서브쿼리가 단일 행(single-row)을 반환하면 비교 연산자(=, `>`, `<`)를 사용하고, 복수 행(multi-row)을 반환하면 `IN`, `NOT IN` 등의 연산자를 사용해야 합니다.
- **집계 함수와 서브쿼리**: `WHERE` 절에는 `MAX()`, `AVG()` 같은 집계 함수를 직접 사용할 수 없으므로, 서브쿼리를 통해 계산된 집계 값을 조건으로 사용해야 합니다.
- **집합 연산자**: `UNION`(합집합), `INTERSECT`(교집합), `MINUS`(차집합)를 사용해 두 쿼리의 결과 집합을 합치거나 비교할 수 있습니다.

---

### **표현 = 표준 용어**

- **Join (조인)**: 두 개 이상의 테이블로부터 관련된 행들을 결합하는 연산.
- **Inner Join (내부 조인)**: 두 테이블 간에 조인 조건이 일치하는 데이터만 반환.
- **Outer Join (외부 조인)**: 조인 조건 불일치 행도 `NULL`과 함께 포함. `LEFT`, `RIGHT`, `FULL`로 구분.
- **Self Join (셀프 조인)**: 한 테이블이 자기 자신과 조인하는 것.
- **Alias (별칭)**: 쿼리 내에서 테이블이나 컬럼에 부여하는 임시 이름.
- **Subquery / Nested Query (서브쿼리 / 중첩 질의)**: SQL 문 내에 포함된 또 다른 `SELECT` 문.
- **Set Operators (집합 연산자)**: 두 질의 결과를 집합처럼 다루는 연산자. (`UNION`, `INTERSECT`, `MINUS`)

---

### **정석 보강 (canon-std)**

조인(Join)은 관계형 데이터베이스의 핵심 연산으로, 정규화를 통해 분리된 테이블들의 데이터를 논리적으로 재결합합니다. **`INNER JOIN`**은 양쪽 테이블에 모두 존재하는 키 값을 기준으로 매칭되는 행만 반환하는 반면, **`OUTER JOIN`**은 한쪽 테이블의 모든 행을 보존하면서 다른 쪽 테이블에 매칭되는 값이 없으면 `NULL`로 채워 결과를 반환합니다. 표준 SQL에서는 `FROM tableA JOIN tableB ON tableA.key = tableB.key`와 같이 `JOIN`과 `ON` 키워드를 사용해 조인 조건과 유형을 명시적으로 선언하는 것이 권장됩니다.

---

### **실수·함정**

1. **조인 조건 누락**: `WHERE` 절에 조인 조건을 빠뜨리면 모든 행의 조합인 카티전 곱(Cartesian Product)이 발생하여 의도치 않은 대량의 데이터가 반환됩니다.
2. **모호한 컬럼명**: 여러 테이블에 동일한 이름의 컬럼이 있을 때 테이블명이나 별칭으로 한정하지 않으면 'column ambiguously defined' 오류가 발생합니다.
3. **서브쿼리 연산자 오용**: 복수 행을 반환하는 서브쿼리 결과에 = 연산자를 사용하면 오류가 발생합니다. 반드시 `IN` 연산자를 사용해야 합니다.
4. **`WHERE` 절의 집계 함수**: `WHERE sal = MAX(sal)`과 같이 `WHERE` 절에 집계 함수를 직접 사용하면 문법 오류가 발생합니다. `WHERE sal = (SELECT MAX(sal) FROM ...)` 형태의 서브쿼리를 사용해야 합니다.
5. **`NOT IN`과 `NULL`**: 서브쿼리 결과에 `NULL`이 포함된 경우, `NOT IN` 연산자는 예상과 다르게 아무 행도 반환하지 않을 수 있습니다.
6. **오라클 `OUTER JOIN` 기호 `(+)` 혼동**: `(+)` 기호는 데이터가 부족하여 `NULL`로 채워져야 하는 테이블의 조건 컬럼 쪽에 붙여야 합니다. (예: `t1.id = t2.id(+)`는 `t1`을 기준으로 함)
7. **셀프 조인 시 별칭 미사용**: 동일한 테이블을 조인할 때 별칭을 사용하지 않으면 테이블을 구분할 수 없어 쿼리 실행이 불가능합니다.

## **2025-09-22, 1교시 — 질문**

**[Q1] `WHERE`절 조인과 `JOIN...ON` 구문의 차이점은 무엇이며, 각각 언제 사용되나요? | 태그: 뷰/마스킹**

- **모범답(강의 기준)**: 실무에서는 `FROM`절에 테이블을 나열하고 `WHERE`절에 조인 조건을 쓰는 방식을 많이 사용하지만, `JOIN...ON`은 시험에 자주 나오는 표준 문법입니다.
- **정석체크(면접 30초)**: `JOIN...ON` 구문은 데이터 '연결 조건'과 `WHERE`의 '필터 조건'을 명확히 분리하여 쿼리의 가독성을 높입니다. 예를 들어, `FROM A JOIN B ON A.id = B.id`는 관계 정의를, `WHERE A.status = 'active'`는 데이터 필터링을 의미합니다. ANSI 표준인 `JOIN...ON`은 `OUTER JOIN` 등을 명시적으로 표현할 수 있어 실수를 줄여주므로 사용이 강력히 권장됩니다.

---

**[Q2] `INNER JOIN`과 `OUTER JOIN`의 근본적인 차이는 무엇인가요? | 태그: RLS/라벨 보안**

- **모범답(강의 기준)**: `INNER JOIN`은 두 테이블에 공통으로 존재하는 데이터만 반환하는 반면, `OUTER JOIN`은 한쪽 테이블의 모든 행을 기준으로 일치하는 값이 없으면 `NULL`로 채워서라도 결과를 포함시킵니다.
- **정석체크(면접 30초)**: `INNER JOIN`은 두 테이블의 교집합으로, 조인 조건이 완전히 일치하는 행만 반환합니다. `OUTER JOIN`은 기준 테이블(e.g., `LEFT JOIN`의 왼쪽 테이블)의 모든 행을 보존하여, 데이터 누락 여부를 확인하거나 관계없는 데이터를 식별하는 데 사용됩니다. 보안 관점에서 `OUTER JOIN`은 정보의 '존재' 자체를 노출할 수 있으므로 주의해야 합니다.

---

**[Q3] 셀프 조인(Self-Join)은 언제 사용하며, 왜 반드시 별칭(Alias)이 필요한가요? | 태그: 계정/역할/프로파일**

- **모범답(강의 기준)**: 사원과 관리자처럼 한 테이블 내의 데이터가 자기 자신을 참조하는 계층적 관계를 조회할 때 사용하며, 동일 테이블을 두 개의 다른 개체로 취급해야 하므로 별칭이 필수입니다.
- **정석체크(면접 30초)**: 셀프 조인은 계층 구조를 평면화할 때 사용합니다. `FROM employee e JOIN employee m ON e.manager_id = m.emp_id`와 같이 별칭이 없다면, SQL 엔진이 `manager_id`와 `emp_id`가 어느 테이블 인스턴스에 속하는지 구분할 수 없어 쿼리 해석이 불가능합니다. 따라서 별칭은 참조의 모호성을 제거하는 필수 문법입니다.

---

**[Q4] `WHERE` 절에 `MAX()` 같은 집계 함수를 쓸 수 없는 이유는 무엇이며, 해결 방법은 무엇인가요? | 태그: 감사/감사 정책/보존**

- **모범답(강의 기준)**: `WHERE` 절에는 문법적으로 집계 함수를 직접 사용할 수 없기 때문에, 서브쿼리를 이용해 `MAX(SAL)` 값을 먼저 계산하고 그 반환 값을 `WHERE` 절의 비교 조건으로 사용해야 합니다.
- **정석체크(면접 30초)**: SQL의 논리적 실행 순서상 `WHERE`절은 `GROUP BY`보다 먼저 처리되므로, `WHERE`절이 실행되는 시점에는 집계 값이 아직 존재하지 않습니다. `WHERE sal > (SELECT AVG(sal) FROM emp)`와 같이 서브쿼리를 통해 집계 값을 스칼라 값으로 미리 계산하고, 이를 외부 쿼리의 필터 조건으로 사용해야 합니다.

**[Q5] 서브쿼리가 여러 값을 반환할 때 = 대신 `IN` 연산자를 써야 하는 이유는 무엇인가요? | 태그: 권한(GRANT/REVOKE, system/object)**

## **2025-09-22, 2교시 — 개선본**

서브쿼리(subquery)에서 사용하는 테이블이 메인 쿼리(main query)의 테이블과 참조 관계가 있을 때, 즉 조인(join)이 가능할 때 `EXISTS` 연산자를 활용하여 검색 속도를 높일 수 있습니다.

`EXISTS`는 서브쿼리의 결과가 하나라도 존재하는지 여부만 확인합니다. 서브쿼리에서 조건을 만족하는 첫 번째 행을 찾으면, 나머지 행은 더 이상 검색하지 않고 즉시 `TRUE`를 반환하고 멈춥니다. 이 때문에 전체 레코드를 다 검색할 필요가 없는 특정 상황에서 탐색 효율을 크게 높일 수 있습니다. 이는 실무에서 성능 최적화를 위해 종종 사용되지만, 정보처리기사 같은 시험에는 거의 출제되지 않습니다.

`EXISTS`를 사용하기 위한 핵심 조건은 메인 쿼리와 서브쿼리 테이블 간의 조인(join) 조건이 서브쿼리의 `WHERE` 절 안에 명시되어야 한다는 점입니다. 예를 들어, `DEPARTMENT` 테이블의 특정 부서 정보를 조회할 때, `EMPLOYEE` 테이블에 해당 부서 소속의 사원이 한 명이라도 존재하는지만 확인하면 되는 경우에 유용합니다.

반대로 특정 조건을 만족하는 데이터가 하나도 존재하지 않는 것을 확인하려면 `NOT EXISTS`를 사용합니다. 예를 들어, 소속된 사원이 한 명도 없는 부서를 찾을 때 `NOT EXISTS`를 활용할 수 있습니다.

## **2025-09-22, 2교시 — 개념**

### **한 줄 요약**

메인 쿼리의 각 행과 연관된 데이터가 서브쿼리에 존재하는지 여부만 빠르게 확인하는 `EXISTS` 연산자의 동작 방식과 성능 최적화 활용법을 학습합니다.

---

### **핵심 TL;DR**

- **`EXISTS` 연산자**: 서브쿼리(Subquery)가 한 행 이상의 결과를 반환하면 `TRUE`, 아무 결과도 반환하지 않으면 `FALSE`를 반환합니다.
- **성능 최적화**: 조건을 만족하는 첫 번째 행을 찾는 즉시 검색을 중단하므로, 데이터 존재 유무만 확인하면 될 때 `IN`이나 `JOIN`보다 효율적일 수 있습니다.
- **연관 서브쿼리(Correlated Subquery)**: `EXISTS`는 대부분 메인 쿼리의 값을 서브쿼리의 `WHERE` 절에서 참조하는 '연관 서브쿼리' 형태로 사용해야 의미가 있습니다.
- **`NOT EXISTS`**: 서브쿼리의 결과가 존재하지 않을 때 `TRUE`를 반환하며, "어떤 A와도 관계를 맺지 않는 B를 찾는" 경우에 매우 유용합니다.
- **`EXISTS` vs. `IN`**: `IN`은 서브쿼리가 반환한 '값의 목록'과 비교하는 반면, `EXISTS`는 결과 집합의 '존재 여부'만 확인합니다. 서브쿼리 결과에 `NULL`이 있어도 `EXISTS`는 정상 동작합니다.
- **실습 문제**: 2교시의 실습 문제는 `EXISTS` 뿐만 아니라 조인, 일반 서브쿼리, `GROUP BY`, `HAVING` 등 1교시 내용을 포함한 종합적인 SQL 작성 능력을 요구합니다.

---

### **표현 = 표준 용어**

- **`EXISTS` Operator**: 서브쿼리에 결과 행이 존재하는지 확인하는 연산자.
- **`NOT EXISTS` Operator**: 서브쿼리에 결과 행이 존재하지 않는지 확인하는 연산자.
- **Correlated Subquery (연관 서브쿼리)**: 외부 쿼리(Main Query)의 컬럼을 참조하는 내부 쿼리(Subquery). 외부 쿼리의 각 행에 대해 내부 쿼리가 반복 실행됩니다.

---

### **정석 보강 (canon-std)**

`EXISTS`는 데이터의 내용을 비교하는 것이 아니라, 서브쿼리가 조건을 만족하는 행을 반환할 수 있는지 그 '존재' 자체를 확인하는 논리 연산자입니다. 주로 메인 쿼리 테이블과 서브쿼리 테이블 간에 1:N 관계가 있을 때, 1측의 데이터 중 N측에 관련된 데이터가 존재하는지를 필터링하는 데 사용됩니다. 표준 패턴은 `SELECT ... FROM T1 WHERE EXISTS (SELECT 1 FROM T2 WHERE T2.fk = T1.pk)`와 같이, 서브쿼리 내에 두 테이블을 연결하는 상관관계 조건을 명시하는 것입니다.

---

### **실수·함정**

1. **비연관 서브쿼리 사용**: `EXISTS (SELECT * FROM T2)` 와 같이 메인 쿼리와 아무 관계없는 서브쿼리를 사용하면, T2가 비어있지 않는 한 모든 행에 대해 `TRUE`를 반환하여 필터로서의 의미를 잃습니다.
2. **`IN`과의 혼동**: 데이터 '값'을 비교해야 하는 상황에서 `EXISTS`를 사용하거나, 단순히 '존재' 여부만 확인하면 되는데 `IN`을 사용하여 불필요한 성능 저하를 유발할 수 있습니다.
3. **서브쿼리 `SELECT` 절**: `EXISTS`는 반환되는 값의 내용을 무시하므로, 관례적으로 `SELECT *` 대신 `SELECT 1`, `SELECT 'X'` 와 같이 의미 없는 상수 값을 사용해 쿼리의 의도를 명확히 합니다.
4. **`NOT EXISTS`의 강력함 간과**: `LEFT JOIN ... WHERE key IS NULL`로 복잡하게 작성해야 하는 "관계 데이터가 없는 행 찾기" 쿼리는 `NOT EXISTS`를 사용하면 훨씬 직관적이고 효율적으로 작성할 수 있습니다.
5. **무조건적 성능 우위 착각**: `EXISTS`가 항상 `JOIN`이나 `IN`보다 빠른 것은 아닙니다. 데이터의 분포, 인덱스 유무, 옵티마이저의 실행 계획에 따라 성능이 달라지므로 실제 환경에서는 테스트가 필요합니다.

끝.

## 정리
## **2025-09-29, 1교시 — 개선본**

쿼리(Query) 처리 중 DDL과 DML의 남은 부분을 다루고, 보안과 관련된 DCL은 데이터베이스 보안 파트와 연결하여 실습을 진행하겠습니다. `CREATE VIEW`나 `CREATE INDEX` 같은 경우도 보안과 연계해서 처리할 수 있으므로 함께 살펴보도록 하겠습니다. 먼저 DDL 중 `CREATE`, `ALTER`, `DROP`과 DML인 `INSERT`, `UPDATE`, `DELETE` 관련 문법을 정리하겠습니다.

`CREATE TABLE`은 데이터베이스와 연동하여 프로그램을 개발하기 위해 필수적이므로 기본 문법을 알아두어야 합니다. (실습) 테이블명과 컬럼명은 변수명 규칙에 맞춰 작성합니다. 데이터 타입은 Oracle 기준에 맞춰 숫자, 문자, 날짜 패턴으로 지정하고, `NOT NULL` 키워드로 NULL 허용 여부를 설정합니다.

다음으로 관계형 테이블의 무결성 제약조건을 설정해야 합니다. 개체 무결성을 위해서는 `PRIMARY KEY`를, 참조 무결성을 위해서는 `FOREIGN KEY` 제약조건을 명시해야 데이터가 오류 없이 정확하게 관리됩니다. `FOREIGN KEY`는 다른 테이블의 `PRIMARY KEY`를 참조하므로, 원본 데이터가 삭제되거나 수정될 때의 처리 기준을 명시해야 합니다. 예를 들어 `ON DELETE`나 `ON UPDATE` 옵션을 통해 연계 삭제(`CASCADE`), 특정 값으로 변경, 혹은 작업을 막는(`NO ACTION`) 등의 정책을 설정할 수 있습니다.

Oracle에서는 `TABLESPACE`를 지정하여 테이블이 생성될 물리적 공간을 명시할 수 있습니다. 이를 생략하면 현재 접속한 사용자의 기본 테이블스페이스에 테이블이 생성됩니다. 관리자가 아닌 일반 사용자는 주로 기본값을 사용하므로 이 부분은 생략해도 무방합니다.

또한, 하위 질의(subquery)를 사용하여 테이블을 생성할 수 있습니다. `CREATE`, `INSERT`, `UPDATE`, `DELETE` 문 모두에서 `SELECT`를 활용한 하위 질의가 가능합니다. 예를 들어, 기존 테이블에서 연봉이 2000 이상인 직원 정보만 추출하여 새로운 테이블을 생성할 수 있습니다. (실습) 다만 이 경우 컬럼과 데이터만 복사될 뿐 제약조건 등은 상속되지 않으므로 별도로 다시 설정해야 합니다.

주요 자료형으로는 숫자(`NUMBER`), 문자(`VARCHAR2`, `CHAR`), 날짜(`DATE`) 타입이 가장 많이 사용됩니다. `NUMBER` 타입은 정수와 실수를 모두 표현할 수 있고, `CHAR`는 고정 길이 문자열, `VARCHAR2`는 가변 길이 문자열을 저장합니다. 유니코드 문자(한글, 한자 등)를 처리하기 위해서는 `NCHAR`나 `NVARCHAR2`를 사용합니다. `LONG` 타입은 2GB까지의 긴 가변 길이 문자열을 저장하는 데 사용됩니다. 날짜는 보통 `DATE` 형식을 사용하여 년/월/일/시/분/초까지 저장하며, 밀리초까지 필요할 경우 `TIMESTAMP`를 사용합니다.

`CREATE TABLE` 문 내에서 컬럼의 기본값을 지정하기 위해 `DEFAULT` 키워드를 사용할 수 있습니다. 예를 들어 성별(gender) 컬럼의 기본값을 'M'으로 설정할 수 있습니다.

중복 값을 허용하지 않아야 하는 컬럼에는 `UNIQUE` 제약조건을 사용합니다. `PRIMARY KEY`는 기본적으로 `UNIQUE` 속성을 포함하지만, `PRIMARY KEY`가 아닌 컬럼(예: 전화번호)에 유일성을 보장하고 싶을 때 사용합니다. `PRIMARY KEY`는 `NULL` 값을 허용하지 않지만, `UNIQUE` 제약조건이 걸린 컬럼은 `NULL` 값을 허용한다는 차이점이 있습니다.

제약조건을 명시적으로 관리하기 위해 `CONSTRAINT` 키워드를 사용하여 이름을 부여할 수 있습니다. `PRIMARY KEY`가 하나의 컬럼으로 구성될 때는 컬럼 정의 옆에 `PRIMARY KEY`라고만 적어도 되지만, 두 개 이상의 컬럼으로 구성된 복합 키(composite key)의 경우에는 반드시 `CONSTRAINT` 키워드를 사용하여 여러 컬럼을 하나로 묶어주어야 합니다.

`FOREIGN KEY`를 정의할 때는 `CONSTRAINT` 키워드, 제약조건 이름, `FOREIGN KEY`로 지정할 컬럼, 그리고 `REFERENCES` 키워드를 사용하여 참조할 부모 테이블과 컬럼을 명시해야 합니다. `ON DELETE SET NULL` 옵션은 참조하는 부모 테이블의 데이터가 삭제될 경우, 해당 외래 키 값을 `NULL`로 변경하라는 의미입니다. `CASCADE` 옵션보다 데이터 유실 위험이 적어 많이 사용됩니다.

이제 `my_dpt`와 `my_emp` 테이블을 직접 생성해 보겠습니다. (실습)

테이블 생성이 완료된 후 구조를 변경해야 할 때는 `ALTER TABLE`을, 삭제할 때는 `DROP TABLE`을 사용합니다. 테이블의 구조를 변경할 때는 만약을 대비해 대상 테이블을 임시로 복사해두고 작업하는 것이 안전합니다. 테이블의 컬럼을 삭제하면 해당 컬럼의 데이터도 함께 삭제되므로 주의해야 합니다.

먼저 `ALTER TABLE`을 사용하여 기존 테이블에 없던 컬럼을 추가해 보겠습니다. `ADD` 구문을 사용합니다. (실습) `ALTER TABLE my_dpt ADD (budget NUMBER(10, 2) DEFAULT 0);` 명령을 실행하면 `budget` 컬럼이 추가된 것을 확인할 수 있습니다.

컬럼명을 변경할 때는 `RENAME COLUMN`을 사용합니다. (실습) `ALTER TABLE my_dpt RENAME COLUMN budget TO dpt_budget;` 과 같이 실행합니다. 데이터 타입을 변경하거나 크기를 조절할 때는 `MODIFY`를 사용합니다. (실습) `ALTER TABLE my_dpt MODIFY (dpt_budget NUMBER(12, 2));` 와 같이 데이터의 전체 자릿수를 변경할 수 있습니다. 마지막으로 컬럼을 삭제할 때는 `DROP COLUMN`을 사용합니다. (실습) 이처럼 `ALTER TABLE` 문은 컬럼의 추가, 이름 변경, 타입 수정, 삭제 등 다양한 구조 변경 작업을 지원합니다.

## 2025-09-29, 1교시 — 개념

1. 한 줄 요약

    데이터베이스 객체의 구조를 정의하는 DDL(CREATE, ALTER, DROP)을 배우고, 테이블 생성과 변경 시 데이터 무결성을 보장하는 제약조건의 역할을 이해한다.

2. **핵심 TL;DR**
    
    - **SQL의 분류**: SQL은 데이터 구조를 정의하는 **DDL**, 데이터를 조작하는 **DML**, 접근 권한을 제어하는 **DCL**로 나뉜다.
    - **`CREATE TABLE`**: 데이터를 저장할 테이블의 구조(컬럼, 데이터 타입)를 정의하는 기본 명령어다.
    - **데이터 타입**: 컬럼에 저장될 데이터의 종류(숫자, 문자, 날짜 등)를 지정하여 도메인 무결성을 강제한다.
    - **`PRIMARY KEY`**: 테이블의 각 행을 고유하게 식별하며, `NULL`이 허용되지 않고 중복될 수 없다 (개체 무결성).
    - **`FOREIGN KEY`**: 다른 테이블의 `PRIMARY KEY`를 참조하여 테이블 간의 관계를 정의하고 데이터 일관성을 유지한다 (참조 무결성).
    - **`UNIQUE` vs `PRIMARY KEY`**: `UNIQUE`는 중복을 막지만 `NULL`을 허용하는 반면, `PRIMARY KEY`는 `NULL`을 허용하지 않는다.
    - **`ALTER TABLE`**: 이미 생성된 테이블의 구조를 변경할 때 사용하며, 컬럼 추가(`ADD`), 수정(`MODIFY`), 이름 변경(`RENAME`), 삭제(`DROP`)가 가능하다.
    - **참조 동작**: `FOREIGN KEY` 설정 시 `ON DELETE` 옵션으로 참조하는 데이터가 삭제될 때의 동작(`CASCADE` 동시 삭제, `SET NULL` Null로 변경)을 지정할 수 있다.
        
3. **표현 = 표준 용어**
    
    - **DDL (Data Definition Language)**: 데이터 구조 정의 언어 (`CREATE`, `ALTER`, `DROP`).
    - **DML (Data Manipulation Language)**: 데이터 조작 언어 (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
    - **DCL (Data Control Language)**: 데이터 제어 언어 (`GRANT`, `REVOKE`).
    - **Constraint (제약조건)**: 데이터의 무결성을 보장하기 위한 규칙 (`PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`).
    - **Entity Integrity (개체 무결성)**: 모든 행이 `PRIMARY KEY`에 의해 고유하게 식별되어야 한다는 원칙.
    - **Referential Integrity (참조 무결성)**: `FOREIGN KEY` 값은 반드시 참조하는 테이블의 `PRIMARY KEY` 값이거나 `NULL`이어야 한다는 원칙.
    - **Composite Key (복합 키)**: 두 개 이상의 컬럼을 조합하여 만든 `PRIMARY KEY`.
    - **`ON DELETE CASCADE`**: 부모 테이블의 행이 삭제될 때 이를 참조하는 자식 테이블의 행도 연쇄적으로 삭제.
    - **`ALTER TABLE ... ADD | MODIFY | RENAME | DROP`**: 테이블 구조 변경을 위한 하위 명령어 집합.
        
4. 정석 보강(canon-std)

    데이터 무결성(Integrity)은 데이터베이스의 정확성과 일관성을 유지하는 핵심 원칙이다. 개체 무결성은 PRIMARY KEY를 통해 각 행의 유일성을 보장하며, 참조 무결성은 FOREIGN KEY를 통해 테이블 간의 관계가 깨지지 않도록 보호한다. CONSTRAINT fk_name FOREIGN KEY (dept_id) REFERENCES departments(id) ON DELETE SET NULL; 구문은 departments 테이블에서 특정 부서가 삭제될 때, 해당 부서에 속한 직원들의 dept_id를 자동으로 NULL로 변경하여 관계의 일관성을 유지한다.

5. **실수·함정**
    
    - **`CHAR` vs `VARCHAR2`**: 길이가 고정된 코드(예: 'M'/'F')가 아닌 가변 길이 데이터에 `CHAR`를 사용하면 불필요한 공간이 낭비된다.
    - **`CASCADE`의 위험**: `ON DELETE CASCADE` 옵션은 의도치 않은 대량의 데이터 삭제로 이어질 수 있으므로 신중하게 사용해야 한다.
    - **제약조건 미복사**: `CREATE TABLE ... AS SELECT ...` 구문은 데이터는 복사하지만 `PRIMARY KEY`나 `FOREIGN KEY` 같은 제약조건은 복사하지 않는다.
    - **`ALTER TABLE`의 부하**: 운영 중인 대용량 테이블에 `ALTER TABLE`을 실행하면 테이블 전체에 잠금(lock)이 발생하여 서비스 장애로 이어질 수 있다.
    - **`UNIQUE`와 `NULL`**: `UNIQUE` 제약조건이 걸린 컬럼에는 `NULL` 값이 여러 번 삽입될 수 있다는 점을 간과하기 쉽다(Oracle 기준).
    - **복합 키 남용**: 불필요하게 많은 컬럼으로 복합 키를 구성하면 인덱스 효율과 쿼리 성능이 저하될 수 있다.

**[Q1] `PRIMARY KEY`와 `UNIQUE` 제약조건의 핵심적인 차이점은 무엇인가요? | 태그: 제약조건, 무결성**

- **모범답(강의 기준)**: `PRIMARY KEY`는 개체 무결성을 위해 `NULL` 값을 허용하지 않지만, `UNIQUE` 제약조건은 `NULL`을 허용합니다. 전화번호처럼 값이 있을 경우 유일해야 하지만 필수는 아닐 때 `UNIQUE`를 사용합니다.
- **정석체크(면접 30초)**: `PRIMARY KEY`는 테이블의 유일한 식별자로, `NOT NULL`과 `UNIQUE` 속성을 모두 가집니다. 반면 `UNIQUE`는 대체 키(Alternate Key)로 사용되며 중복만 방지할 뿐 `NULL` 값을 허용합니다. 따라서 테이블 당 하나의 `PRIMARY KEY`만 가능하지만, `UNIQUE` 제약조건은 여러 컬럼에 설정할 수 있습니다.

---

**[Q2] `FOREIGN KEY` 설정 시 `ON DELETE CASCADE`와 `ON DELETE SET NULL`은 어떻게 다르며, 보통 어떤 것을 더 많이 사용하나요? | 태그: FOREIGN KEY, 참조 무결성**

- **모범답(강의 기준)**: `CASCADE`는 참조되는 부모 데이터가 삭제되면 연관된 자식 데이터를 모두 함께 삭제하는 것이고, `SET NULL`은 부모 데이터가 삭제되면 자식 데이터의 해당 컬럼 값을 `NULL`로 변경하는 것입니다. 데이터 보존 측면에서 `SET NULL`이 더 많이 쓰입니다.
- **정석체크(면접 30초)**: `ON DELETE CASCADE`는 부모와 자식 데이터의 생명주기가 완전히 동일할 때 사용하지만, 의도치 않은 대량 삭제의 위험이 있습니다. `ON DELETE SET NULL`은 관계가 필수적이지 않을 때 연결만 끊고 데이터를 보존하므로 더 안전한 선택지로 여겨집니다. 단, `SET NULL`을 사용하려면 해당 `FOREIGN KEY` 컬럼이 `NULL`을 허용하도록 정의되어야 합니다.

---

**[Q3] `ALTER TABLE` 명령어를 사용하여 테이블 구조를 변경하는 주요 기능 4가지는 무엇인가요? | 태그: DDL, ALTER TABLE**

- **모범답(강의 기준)**: 테이블의 구조를 수정하는 기능으로, 컬럼을 추가하는 `ADD`, 컬럼명을 바꾸는 `RENAME COLUMN`, 데이터 타입이나 크기를 변경하는 `MODIFY`, 그리고 컬럼을 삭제하는 `DROP COLUMN`이 있습니다.
- **정석체크(면접 30초)**: `ALTER TABLE`은 테이블의 구조를 동적으로 변경하는 DDL입니다. 주요 기능으로는 `ADD` (컬럼 추가), `MODIFY` (타입/크기 변경), `DROP COLUMN` (컬럼 삭제), `RENAME COLUMN` (컬럼명 변경)이 있습니다. 또한 `ADD/DROP CONSTRAINT`를 통해 제약조건을 추가하거나 삭제하는 작업도 가능합니다.

---

**[Q4] `CREATE TABLE ... AS SELECT ...` 방식으로 테이블을 생성할 때의 장점과 가장 큰 주의점은 무엇인가요? | 태그: DDL, CREATE TABLE**

- **모범답(강의 기준)**: 기존 테이블의 데이터 중 일부를 필터링하여 새로운 테이블을 빠르고 쉽게 만들 수 있다는 장점이 있습니다. 하지만 제약조건(`PRIMARY KEY` 등)은 복사되지 않으므로, 필요하다면 수동으로 다시 설정해야 합니다.
- **정석체크(면접 30초)**: 이 방식은 대용량 데이터의 백업, 테스트용 데이터 생성, 또는 복잡한 쿼리 결과를 테이블로 만들어 둘 때 유용합니다. 컬럼 정의와 데이터는 그대로 복사되지만, `PRIMARY KEY`, `INDEX`, `DEFAULT` 값 등 원본 테이블의 제약조건과 속성은 상속되지 않는다는 점을 반드시 기억해야 합니다.

## **2025-09-29, 1교시 — 실습**

**[S1] DDL 기본 테이블 생성 — 제약조건 포함**

- **⚠️ 주의**: `FOREIGN KEY`를 생성하려면 참조 대상인 `my_dpt` 테이블이 먼저 존재해야 한다.

**[S2] 테이블 구조 변경 — ALTER TABLE 활용**

- **목적**: `ALTER TABLE` 명령어의 주요 구문(`ADD`, `RENAME`, `MODIFY`, `DROP`)을 순차적으로 사용하여 테이블의 구조를 동적으로 수정하는 과정을 익힌다.
- **단계요약**: 1) **ADD**: `my_dpt` 테이블에 숫자 타입의 `budget` 컬럼을 기본값 0으로 추가한다. 2) **RENAME**: 추가된 `budget` 컬럼명을 `dpt_budget`으로 변경한다. 3) **MODIFY**: `dpt_budget` 컬럼의 자릿수를 더 크게 수정한다. 4) **DROP**: `dpt_budget` 컬럼을 테이블에서 완전히 삭제한다.
- **⚠️ 주의**: 운영 중인 테이블의 구조 변경은 데이터 유실 위험이 있고 시스템에 부하를 줄 수 있으므로, 사전에 데이터를 백업하는 것이 안전하다.

**[S3] 하위 질의를 이용한 테이블 생성 — CTAS**

- **목적**: 기존 테이블의 `SELECT` 조회 결과를 바탕으로, 데이터가 채워진 새로운 테이블을 생성하는 방법을 이해한다.
- **단계요약**: 1) `CREATE TABLE ... AS` 구문을 준비한다. 2) 기존 테이블에서 특정 조건을 만족하는 데이터를 조회하는 `SELECT` 문을 작성하여 위 구문 뒤에 결합하고 실행한다.
- **⚠️ 주의**: 이 방식은 데이터와 컬럼 정의만 복사할 뿐, `PRIMARY KEY`나 `FOREIGN KEY` 같은 제약조건은 상속되지 않아 별도로 추가해야 한다.

## **2025-09-29, 2교시 — 개선본**

`PRIMARY KEY`나 `FOREIGN KEY` 같은 제약조건을 생성한 후에 추가하거나 삭제하려면, `CREATE TABLE` 시점에 `CONSTRAINT` 키워드를 사용하여 제약조건에 명시적으로 이름을 할당해야 합니다. 이름을 지정하지 않으면 나중에 해당 제약조건을 참조하여 수정하거나 삭제할 수 없습니다.

만약 제약조건 없이 테이블을 생성했다면, `ALTER TABLE` 문을 사용하여 나중에 추가할 수 있습니다. 이를 실습해 보기 위해, 먼저 기존의 `my_emp` 테이블을 삭제하고 제약조건이 없는 상태로 다시 생성해 보겠습니다. (실습) `DROP TABLE my_emp;`를 실행한 후, `CREATE TABLE` 문에서 `CONSTRAINT` 부분을 모두 제거하고 실행하십시오.

테이블이 제약조건 없이 생성된 상태에서 `ALTER TABLE ... ADD CONSTRAINT` 구문을 사용하여 `PRIMARY KEY`와 `FOREIGN KEY`를 추가할 수 있습니다. (실습) `ADD CONSTRAINT` 뒤에 제약조건명과 제약조건의 내용을 `CREATE TABLE` 구문에서처럼 그대로 기술하면 됩니다.

다음으로 테이블의 이름을 변경하는 방법입니다. `ALTER TABLE old_name RENAME TO new_name;` 구문을 사용합니다. 1교시에서 사용했던 `RENAME COLUMN`은 컬럼명을 변경하는 것이고, `RENAME TO`는 테이블명을 변경하는 것이니 혼동하지 않도록 주의해야 합니다. 테이블을 삭제할 때는 `DROP TABLE table_name;` 명령어를 사용합니다.

간단한 실습을 통해 이 세 가지 작업을 순서대로 진행해 보겠습니다. (실습)

1. `CREATE TABLE temp ...` 로 임시 테이블을 생성합니다.
2. `ALTER TABLE temp RENAME TO my_temp;` 로 테이블 이름을 변경합니다.
3. DROP TABLE my_temp; 로 이름이 변경된 테이블을 삭제합니다.

    각 단계를 실행한 후에는 좌측 객체 탐색기에서 새로고침하여 결과가 제대로 반영되었는지 확인하는 것이 좋습니다.

지금까지 DDL 명령어인 `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`에 대해 학습했습니다. `ALTER TABLE`에는 컬럼을 추가(`ADD`), 수정(`MODIFY`), 이름 변경(`RENAME COLUMN`)하는 기능과 제약조건을 추가(`ADD CONSTRAINT`)하는 기능이 포함됩니다.

이제 DML(Data Manipulation Language) 중 `SELECT`를 제외한 `INSERT`, `UPDATE`, `DELETE`에 대해 알아보겠습니다. DML은 테이블의 내용을 변경하기 때문에 신중하게 사용해야 합니다. DDL과 DML의 중요한 차이점은 트랜잭션 제어입니다. DDL 명령어는 실행 즉시 데이터베이스에 영구적으로 반영되지만, DML 명령어는 `COMMIT`을 실행해야만 영구 반영되며, `ROLLBACK`을 통해 이전 `COMMIT` 시점으로 작업을 취소할 수 있습니다. 이는 일반 사용자의 데이터 조작 실수로부터 원본 데이터를 보호하는 중요한 보안 장치입니다.

`INSERT` 문은 `INSERT INTO table_name (column1, ...) VALUES (value1, ...);` 형식을 따릅니다. 만약 테이블의 모든 컬럼에 순서대로 값을 삽입한다면 컬럼명 목록은 생략할 수 있습니다. (실습) `my_dpt` 테이블에 데이터를 삽입한 후, `COMMIT` 명령어로 변경 사항을 확정하십시오.

`ROLLBACK`의 동작을 확인하기 위해 다음 실습을 진행해 보겠습니다. (실습)

1. `my_dpt`에 부서번호 50번 데이터를 `INSERT`합니다.
2. `COMMIT` 없이 `ROLLBACK`을 실행합니다.
3. `SELECT` 문으로 데이터를 조회하여 50번 데이터가 삽입되지 않았음을 확인합니다.
4. 다시 50번 데이터를 `INSERT`하고 이번에는 `COMMIT`을 실행합니다.
5. SELECT 문으로 데이터가 영구적으로 반영된 것을 확인합니다.

    참고로 SQL Developer와 같은 툴을 종료할 때는 작업 내용이 자동으로 COMMIT될 수 있습니다.

하위 질의(subquery)를 사용하여 `INSERT`를 실행할 수도 있습니다. `SELECT` 문의 결과를 다른 테이블에 한 번에 삽입하는 방식입니다. 이를 위해 먼저 `my_emp`와 동일한 구조를 가진 `my_emp_hi` 테이블을 생성하겠습니다. (실습) 이때, 기존 `my_emp` 테이블에 사용된 제약조건 이름과 중복되지 않도록 새로운 이름(예: pk_emp_2)을 지정해야 합니다.

테이블 생성이 완료되면, `INSERT INTO my_emp_hi SELECT * FROM my_emp WHERE sal BETWEEN 1500 AND 3000;` 과 같은 명령어로 특정 조건을 만족하는 `my_emp` 테이블의 데이터를 `my_emp_hi`로 복사할 수 있습니다. (실습) 이 방식은 두 테이블의 스키마가 동일해야 성공적으로 실행됩니다.

다음은 `UPDATE`입니다. `UPDATE table_name SET column_name = new_value WHERE condition;` 형식을 사용합니다. 여기서 `WHERE` 조건절을 생략하면 테이블의 모든 행이 변경되므로 치명적인 데이터 오류를 유발할 수 있습니다. 반드시 수정 대상이 되는 행을 명확히 지정해야 합니다. (실습) 예를 들어, `job`이 'SALESMAN'인 직원의 연봉(`sal`)을 10% 인상하는 쿼리를 작성할 수 있습니다.

`UPDATE` 문 역시 하위 질의를 활용할 수 있습니다. `WHERE` 조건절뿐만 아니라 `SET` 절에도 하위 질의를 사용할 수 있어 복잡한 데이터 변경이 가능합니다. (실습)

1. WHERE 절 하위 질의: 연봉이 가장 적은 직원의 연봉을 10% 인상.

    UPDATE my_emp SET sal = sal * 1.1 WHERE sal = (SELECT MIN(sal) FROM my_emp);

2. `SET`, `WHERE` 절 모두 사용: 연봉이 가장 적은 직원의 연봉을 'BLAKE'라는 직원의 연봉과 동일하게 변경.

마지막 DML은 `DELETE`입니다. `DELETE FROM table_name WHERE condition;` 형식을 사용하며, `UPDATE`와 마찬가지로 `WHERE` 조건절이 없으면 테이블의 모든 레코드가 삭제되므로 극히 주의해야 합니다. `DROP TABLE`은 테이블 자체를 삭제하지만, `DELETE`는 테이블 구조는 남겨두고 내부 데이터만 삭제합니다. (실습) 특정 부서 번호(예: 60번)를 가진 레코드를 `DELETE` 문으로 삭제하는 예제를 통해 `WHERE` 조건절의 중요성을 확인합니다.

## **2025-09-29, 2교시 — 개념**

1. 한 줄 요약

    데이터 조작어(DML)인 INSERT, UPDATE, DELETE를 배우고, COMMIT과 ROLLBACK을 이용한 트랜잭션 제어로 데이터의 정합성과 안정성을 보장하는 방법을 이해한다.

2. **핵심 TL;DR**
    
    - **명명된 제약조건**: `CONSTRAINT` 키워드로 제약조건에 이름을 부여해야만, `ALTER TABLE`을 통해 나중에 수정하거나 삭제할 수 있다.
    - **트랜잭션의 시작**: `INSERT`, `UPDATE`, `DELETE` 같은 DML 명령어 실행 시 트랜잭션이 시작되며, 변경 내용은 임시 공간에 기록된다.
    - **`COMMIT`**: 트랜잭션 내의 모든 변경사항을 데이터베이스에 영구적으로 저장하는 명령어다.
    - **`ROLLBACK`**: 트랜잭션 내의 모든 변경사항을 취소하고, 마지막 `COMMIT` 상태로 되돌리는 명령어다.
    - **DDL vs DML**: DDL (`CREATE`, `ALTER`, `DROP`)은 실행 즉시 반영되는 'Auto-Commit' 방식이지만, DML은 수동으로 `COMMIT` 해야 반영된다.
    - **`INSERT`**: 테이블에 새로운 행(row)을 추가하며, 하위 질의(`SELECT`) 결과를 이용해 대량의 데이터를 한 번에 삽입할 수 있다.
    - **`UPDATE`**: 기존 행의 데이터를 수정하며, `WHERE` 절을 생략하면 모든 행이 수정되므로 극히 주의해야 한다.
    - **`DELETE`**: 기존 행을 삭제하며, `WHERE` 절이 없으면 모든 데이터가 삭제되므로 반드시 조건을 명시해야 한다.
    - **DML과 하위 질의**: `INSERT`, `UPDATE`, `DELETE` 문의 값 설정이나 조건절에 하위 질의를 사용하여 복잡하고 정교한 데이터 조작이 가능하다.
        
3. **표현 = 표준 용어**
    
    - **DML (Data Manipulation Language)**: 데이터를 조작(추가, 수정, 삭제, 조회)하는 언어.
    - **TCL (Transaction Control Language)**: 트랜잭션 제어 언어 (`COMMIT`, `ROLLBACK`, `SAVEPOINT`).
    - **Transaction (트랜잭션)**: 데이터베이스의 상태를 변화시키는 하나의 논리적 작업 단위.
    - **`COMMIT`**: 트랜잭션의 성공적인 완료를 선언하고 변경 내용을 영구 저장.
    - **`ROLLBACK`**: 트랜잭션의 실패 또는 취소를 선언하고 모든 변경 내용을 폐기.
    - **`ALTER TABLE ... ADD CONSTRAINT`**: 기존 테이블에 제약조건을 추가하는 명령어.
    - **`ALTER TABLE ... RENAME TO`**: 테이블의 이름을 변경하는 명령어.
    - **Subquery (하위 질의)**: 다른 SQL 문 안에 포함된 `SELECT` 문.
        
4. 정석 보강(canon-std)
    
    **트랜잭션 제어(TCL)**는 데이터베이스의 무결성을 지키는 핵심 기능이다. 트랜잭션은 '모두 성공하거나 모두 실패해야 한다'는 **원자성(Atomicity)**을 보장한다. 사용자가 DML 작업을 수행하면 변경 내용은 임시 버퍼에 저장되는데, 이때 COMMIT을 실행하면 모든 작업이 성공적으로 데이터베이스에 영구 반영된다(지속성, Durability). 만약 중간에 오류가 발생하거나 사용자가 ROLLBACK을 실행하면, 트랜잭션 내의 모든 작업이 취소되어 데이터베이스는 트랜잭션 시작 이전의 일관된 상태로 돌아간다.
    
5. **실수·함정**
    
    - **`WHERE` 절 누락**: `UPDATE`나 `DELETE` 문에서 `WHERE` 절을 빠뜨리는 것은 테이블 전체 데이터를 변경/삭제하는 치명적인 실수다.
    - **익명 제약조건**: `CONSTRAINT`로 제약조건에 이름을 지정하지 않으면, 나중에 이를 관리(수정/삭제)하기가 매우 까다로워진다.
    - **`DELETE`와 `TRUNCATE`의 혼동**: `DELETE`는 DML이라 롤백이 가능하고 행 단위 삭제지만, `TRUNCATE`는 DDL이라 롤백이 불가능하고 테이블 전체를 비우므로 복구할 수 없다.
    - **불필요한 대형 트랜잭션**: 너무 많은 DML 작업을 하나의 트랜잭션으로 묶어 `COMMIT` 없이 실행하면, 과도한 시스템 자원을 점유하고 다른 사용자의 작업을 방해할 수 있다.
    - **DDL의 롤백 불가**: `DROP TABLE`과 같은 DDL 명령어는 실행 즉시 적용되므로 `ROLLBACK`으로 되돌릴 수 없다.
    - **자동 커밋(Auto-Commit)**: SQL Developer 같은 클라이언트 툴은 기본적으로 Auto-Commit 모드가 비활성화되어 있지만, 설정을 변경했거나 다른 툴을 사용할 경우 의도치 않게 모든 DML이 즉시 반영될 수 있다.

**[Q1] 제약조건을 생성할 때 `CONSTRAINT` 키워드로 명시적인 이름을 부여하는 것이 왜 중요한가요? | 태그: DDL, 제약조건, ALTER TABLE**

- **모범답(강의 기준)**: 제약조건에 이름이 있어야만 나중에 `ALTER TABLE` 명령어를 사용해 해당 제약조건을 수정하거나 삭제할 수 있기 때문입니다. 이름이 없으면 관리할 대상 객체를 특정할 수 없습니다.
- **정석체크(면접 30초)**: `CONSTRAINT`로 제약조건을 명명하면 가독성이 높아지고, 오류 메시지 발생 시 원인을 명확히 파악할 수 있습니다. 또한 `ALTER TABLE table_name DROP CONSTRAINT constraint_name;` 구문을 통해 특정 제약조건을 정확하게 관리할 수 있어 시스템의 유지보수성이 크게 향상됩니다.

---

**[Q2] DML(`INSERT`, `UPDATE`, `DELETE`) 작업 후 `COMMIT`이나 `ROLLBACK`을 해야 하는 이유는 무엇인가요? | 태그: DML, TCL, 트랜잭션**

- **모범답(강의 기준)**: DML은 DDL과 달리 실행 즉시 데이터베이스에 영구 반영되지 않기 때문입니다. `COMMIT`으로 변경을 확정하거나, `ROLLBACK`으로 작업을 취소함으로써 사용자의 실수를 막고 원본 데이터를 보호할 수 있습니다.
- **정석체크(면접 30초)**: DML은 논리적 작업 단위인 트랜잭션 내에서 실행됩니다. `COMMIT`은 트랜잭션의 모든 변경사항을 영구적으로 반영해 데이터 일관성을 보장하는 반면, `ROLLBACK`은 문제가 발생했을 때 트랜잭션 시작 전 상태로 되돌려 원자성(Atomicity)을 지킵니다. 이는 데이터 무결성을 위한 핵심 메커니즘입니다.

---

**[Q3] `UPDATE`나 `DELETE` 문에서 `WHERE` 절을 생략하면 어떤 심각한 문제가 발생하나요? | 태그: DML, UPDATE, DELETE, 데이터 무결성**

- **모범답(강의 기준)**: `WHERE` 조건절을 생략하면 테이블의 모든 행(row)이 수정되거나 삭제됩니다. 이는 의도치 않은 대규모 데이터 변경/삭제로 이어지는 치명적인 실수이므로 반드시 `ROLLBACK`으로 되돌려야 합니다.
- **정석체크(면접 30초)**: `WHERE` 절은 DML 작업의 범위를 특정 행으로 제한하는 안전장치입니다. 이를 생략하면 테이블 전체가 작업 대상이 되어 대량의 데이터 손상이나 유실을 초래합니다. 이는 데이터베이스 운영에서 가장 주의해야 할 실수로, 항상 `WHERE` 조건절의 정확성을 먼저 확인하는 것이 중요합니다.

---

**[Q4] `DELETE FROM table`과 `DROP TABLE`은 어떻게 다른가요? | 태그: DML, DDL, DELETE, DROP**

- **모범답(강의 기준)**: `DELETE`는 테이블의 구조는 그대로 둔 채 내부의 데이터만 삭제하는 DML 명령어입니다. 반면 `DROP TABLE`은 테이블의 데이터는 물론, 구조 자체를 데이터베이스에서 완전히 삭제하는 DDL 명령어입니다.
- **정석체크(면접 30초)**: `DELETE`는 DML이므로 행 단위 삭제가 가능하고 `WHERE` 절을 사용하며, 트랜잭션에 포함되어 `ROLLBACK`이 가능합니다. `DROP`은 DDL이므로 테이블 객체 전체를 삭제하고 `ROLLBACK`이 불가능합니다. 참고로 모든 행을 삭제할 때 `ROLLBACK`이 필요 없다면, DDL인 `TRUNCATE TABLE`이 훨씬 빠르고 효율적입니다.

**[S2] 테이블 이름 변경 및 삭제**

- **목적**: 임시 테이블을 생성하고, `RENAME TO`로 이름을 변경한 뒤, `DROP TABLE`로 완전히 삭제하는 DDL의 전체 작업 흐름을 실습한다.
- **단계요약**: 1) `CREATE TABLE temp ...`로 간단한 테이블을 생성한다. 2) `ALTER TABLE temp RENAME TO my_temp;`로 이름을 변경한다. 3) DB 클라이언트의 객체 탐색기에서 이름 변경을 확인 후, `DROP TABLE my_temp;`로 삭제한다.
- **⚠️ 주의**: 각 DDL 명령어 실행 후에는 객체 탐색기를 새로고침하여 변경 사항이 시각적으로 어떻게 반영되는지 직접 확인하는 것이 좋다.

---

**[S3] DML과 트랜잭션 제어 (COMMIT/ROLLBACK)**

- **목적**: DML 작업이 `COMMIT`으로 영구 저장되고, `ROLLBACK`으로 취소되는 트랜잭션의 기본 동작 원리를 체험한다.
- **단계요약**: 1) `my_dpt` 테이블에 특정 데이터(예: 50번 부서)를 `INSERT`한다. 2) `ROLLBACK` 실행 후, 데이터가 삽입되지 않았음을 `SELECT`로 확인한다. 3) 다시 동일 데이터를 `INSERT`하고 `COMMIT`을 실행하여, 데이터가 영구 저장되었음을 확인한다.

---

**[S4] 하위 질의를 이용한 대량 데이터 삽입**

- **목적**: `INSERT INTO ... SELECT ...` 구문을 사용하여 한 테이블의 조회 결과를 다른 테이블에 한 번에 복사하는 방법을 실습한다.
- **단계요약**: 1) `my_emp`와 동일한 구조를 가진 `my_emp_hi` 테이블을 생성한다. 2) `INSERT INTO my_emp_hi SELECT * FROM my_emp WHERE sal < 3000;` 명령어로 조건에 맞는 데이터만 선택하여 복사한다.
- **⚠️ 주의**: `my_emp_hi` 생성 시, 기존 `my_emp`의 제약조건 이름과 충돌하지 않도록 `pk_emp_2`와 같이 새로운 이름을 부여해야 한다.

**[S5] 하위 질의를 이용한 데이터 수정 (UPDATE)**

- **목적**: `UPDATE` 문의 `SET` 절과 `WHERE` 절에 하위 질의를 사용하여, 다른 테이블의 값을 참조하는 등 복잡한 조건으로 데이터를 수정하는 고급 기법을 익힌다.
- **단계요약**: 1) `WHERE` 절에 `(SELECT MIN(sal) ...)` 하위 질의를 사용해 '최저 연봉자'의 연봉을 10% 인상한다. 2) `SET`과 `WHERE` 절 모두에 하위 질의를 사용하여 '최저 연봉자'의 연봉을 특정 직원('BLAKE')의 연봉과 동일하게 맞춘다.

---

**[S6] 특정 데이터 삭제 (DELETE)**

- **목적**: `DELETE` 문과 `WHERE` 절을 사용하여 테이블에서 불필요한 특정 행을 안전하게 삭제하는 방법을 연습한다.
- **단계요약**: 1) `INSERT` 문으로 삭제할 테스트 데이터(예: 60번 부서)를 `my_dpt`에 추가한다. 2) `SELECT`로 데이터가 삽입된 것을 확인한다. 3) `DELETE FROM my_dpt WHERE deptno = 60;`을 실행하여 해당 행만 정확히 삭제한다.

## **2025-10-13, 1교시 — 개선본**

오늘은 procedure와 function만 다룰 것이며, 시험 범위도 여기까지입니다. procedure와 function 코딩이 가능해야 데이터베이스 보안 관련 코딩을 할 수 있습니다. 기본적으로 query, procedure, function, trigger 코딩 능력이 필요하며, 특히 보안 설정을 위한 코딩에 필수적입니다. 지금까지는 DDL, DML 관련 query, 그중에서도 `SELECT` 위주로 학습했습니다. 관련 교안은 수정하여 업로드했고, 실습 문제 중 일부만 진행할 것입니다.

PL/SQL은 데이터베이스에 내장되어 처리되는 스토어드 프로그램(stored program)을 작성하는 데 사용됩니다. 기기에 심는 프로그램을 임베디드(embedded)라고 하지만, 데이터베이스에서는 저장시킨다는 의미에서 스토어드 프로그램이라고 부릅니다. 스토어드 프로그램은 크게 procedure, function, trigger 세 종류가 있습니다.

procedure를 생성하는 방법은 `CREATE PROCEDURE` 다음에 procedure 이름을 명시하는 방식입니다. 이는 파이썬에서 `def`로 함수를 정의하는 것과 유사합니다. procedure를 선언할 때는 `CREATE PROCEDURE procedure_name (parameter_name parameter_type, ...)` 형태로 작성합니다. 변수 선언 방식이 일반적인 프로그래밍 언어와 다른데, `int x`가 아닌 `x INT` 형식으로 변수명 뒤에 데이터 타입이 옵니다.

`AS` 키워드 뒤에는 지역 변수를 선언하고, 프로그램의 본문은 `BEGIN`과 `END` 사이에 작성합니다. 예외 처리를 위한 `EXCEPTION` 구문도 사용할 수 있습니다. 화면 출력은 `DBMS_OUTPUT.PUT_LINE` 함수를 사용하며, `SELECT` 문의 결과를 변수에 담을 때는 `INTO` 키워드를 활용합니다.

이제 간단한 예제를 통해 실행 방법을 알아보겠습니다. `(실습)` procedure를 실행할 때는 먼저 화면 출력을 위해 `SET SERVEROUTPUT ON` 설정을 하고, `EXEC` 명령어를 사용합니다. `(실습)` 지금부터 SQL Developer를 사용하여 간단한 실습을 시작하겠습니다. `(실습)`

SQL Developer를 실행하면 좌측에 테이블, 뷰, 인덱스 등의 객체가 있으며, 오늘 다룰 procedure와 function도 이곳에서 관리됩니다. `(실습)` 새 procedure를 생성하려면 해당 항목에서 마우스 오른쪽 버튼을 클릭하여 '새 프로시저'를 선택하면 됩니다. `(실습)` 물론 query 편집기에서 직접 코드를 작성할 수도 있지만, GUI 도구를 사용하는 것이 더 편리합니다. `(실습)`

procedure 생성 창이 뜨면 스키마는 현재 접속된 계정으로 자동 설정되며, procedure 이름(예: `p_emp_sel`)을 입력합니다. `(실습)` parameter를 추가하려면 '+' 버튼을 누릅니다. `(실습)` parameter 이름(예: `p_eid`)을 입력하고, 방향은 `IN`, `OUT`, `INOUT` 중 선택할 수 있습니다. `(실습)` 입력 전용은 `IN`, 출력 겸용은 `INOUT`을 사용하며, 여기서는 `IN`으로 설정하고 데이터 타입은 `NUMBER`로 지정합니다. `(실습)`

기본 템플릿이 생성되면 `AS`와 `BEGIN` 사이에 지역 변수를 선언합니다. `(실습)` 예를 들어 `v_ename EMP.ENAME%TYPE;`와 같이 특정 테이블의 컬럼과 동일한 타입으로 변수를 선언할 수 있습니다. `(실습)` 이는 `EMP` 테이블의 `ENAME` 컬럼에 저장될 값을 받을 변수이므로 타입을 일치시키는 것입니다. `(실습)` `SELECT ENAME, JOB INTO v_ename, v_job FROM EMP WHERE EMPNO = p_eid;` 구문은 `EMP` 테이블에서 `p_eid`로 전달된 사원 번호에 해당하는 `ENAME`과 `JOB`을 조회하여 각각 선언된 지역 변수에 할당하는 역할을 합니다. `(실습)`

`DBMS_OUTPUT.PUT_LINE`은 화면에 결과를 출력하는 함수로, `System.out.println`과 유사합니다. `(실습)` 문자열과 변수를 연결할 때는 `||` 연산자를 사용합니다. `(실습)` `EXCEPTION` 구문은 `try-catch`와 같이 오류가 발생했을 때 지정된 코드를 실행하여 예외를 처리합니다. `(실습)`

코딩이 완료되면 컴파일을 실행하여 오류 여부를 확인합니다. `(실습)` 컴파일이 성공하면 플레이 버튼을 눌러 procedure를 바로 실행할 수 있습니다. `(실습)` 실행 시 parameter 입력 창이 나타나면, 테스트할 사원 번호(예: 7698)를 입력하고 확인을 누릅니다. `(실습)` 결과는 하단의 출력 창에 표시됩니다. `(실습)` 이 방법 외에, 워크시트에서 직접 `SET SERVEROUTPUT ON;`과 `EXEC p_emp_sel(7698);`을 입력하고 스크립트로 실행하는 방법도 있습니다. `(실습)` 두 가지 방법 모두 테스트하여 실행 결과를 확인하시기 바랍니다. `(실습)`

procedure의 기본 문법을 정리하겠습니다. 한 줄 주석은 `--`, 여러 줄 주석은 `/* */` 입니다. 변수 선언은 `변수명 데이터타입;` 형식이며, 값을 할당할 때는 `:=` 연산자를 사용합니다. `SELECT` 문의 결과를 변수에 매핑할 때는 `INTO` 키워드를 순서에 맞춰 사용합니다. 변수명은 문자로 시작해야 하며, 키워드는 사용할 수 없는 등 일반적인 식별자 규칙을 따릅니다.

parameter를 선언할 때는 데이터 타입의 크기(size)를 생략하고 타입명만 명시해야 합니다. `(예: VARCHAR2(10) -> VARCHAR2)` 하지만 `AS` 절에서 지역 변수를 선언할 때는 크기를 명시해야 합니다. parameter의 모드는 `IN`(읽기 전용, 기본값), `OUT`(쓰기 전용), `INOUT`(읽기/쓰기) 세 가지가 있습니다.

제어문으로는 `IF-ELSIF-END IF`, `CASE-WHEN-END CASE`가 있습니다. 반복문은 `LOOP`, `FOR`, `WHILE`이 사용됩니다. `FOR` 루프는 `FOR i IN 1..10 LOOP ... END LOOP;` 와 같이 지정된 범위만큼 자동으로 반복하므로 편리합니다. `LOOP` 문에서는 `EXIT WHEN [조건]` 구문을 사용하여 반복을 종료해야 하며, 이는 `break`와 같습니다. `CONTINUE`는 현재 반복을 건너뛰고 다음 반복으로 넘어가는 역할을 합니다.

이러한 제어문을 활용하면 특정 조건에 맞는 데이터만 `INSERT`, `UPDATE`, `DELETE` 하는 등 복잡한 로직을 데이터베이스에 내장할 수 있습니다. `(실습)` 보안 정책에서는 특정 조건을 만족할 때만 데이터를 수정하도록 하는 등의 처리를 코딩으로 구현하는 경우가 많습니다. `(실습)` 이제 `FOR`문을 사용하여 1부터 100까지 홀수의 합을 구하는 예제를 실습해 보겠습니다. `(실습)`

## **2025-10-13, 2교시 — 개선본**

컴파일 후 확인하면 결과가 출력됩니다. 이제 함수(function)로 넘어가기 전에, 배운 내용을 활용하여 문제를 풀어보겠습니다. `(실습)`

입력받은 숫자에 해당하는 구구단을 출력하는 procedure `p_gugu`를 만들어 보겠습니다. `(실습)` 파라미터로 단을 받을 변수(예: `p_dan NUMBER`)를 선언하면 됩니다. `(실습)` `IN` 키워드는 생략 가능하며, 기본값으로 설정됩니다. 기존에 작성했던 구구단 예제를 참고하여 `FOR` 루프를 사용하면 간단히 구현할 수 있습니다. `(실습)`

`CREATE OR REPLACE PROCEDURE p_gugu (p_dan IN NUMBER) AS BEGIN FOR i IN 1..9 LOOP DBMS_OUTPUT.PUT_LINE(p_dan || ' * ' || i || ' = ' || p_dan * i); END LOOP; END;` 와 같이 작성할 수 있습니다. 지역 변수가 필요 없으므로 `AS`와 `BEGIN` 사이에 별도의 선언은 없습니다. `(실습)`

코드를 작성하고 컴파일한 뒤, 실행할 때 파라미터로 원하는 단(예: 5)을 입력하면 결과가 출력됩니다. `(실습)` 이처럼 `FOR`문과 `IF`문, 변수 선언, 파라미터 전달 및 출력 기능만 잘 활용할 수 있으면 응용 문제를 해결할 수 있습니다. `(실습)` 시험도 이 범위 내에서 응용하여 출제할 예정입니다.

이제 함수(Function)에 대해 알아보겠습니다. `SUM`, `AVG`와 같은 내장 집계 함수처럼, 사용자가 직접 함수를 정의하여 `SELECT` 구문이나 `HAVING` 절 등에서 사용할 수 있습니다. 함수 역시 데이터베이스에 저장되는 스토어드 프로그램(stored program)입니다.

프로시저(procedure)와의 가장 큰 차이점은 함수는 **반드시 값을 반환(return)해야 한다**는 것입니다. 따라서 함수 정의 시 `RETURN` 키워드를 사용하여 반환 타입을 명시해야 합니다. `CREATE FUNCTION` 구문을 사용하며, 생성 방법은 SQL Developer에서 '함수' 항목에 마우스 오른쪽 버튼을 클릭하여 '새 함수'를 선택하는 것으로 프로시저와 유사합니다. `(실습)`

함수를 생성할 때 이름과 파라미터를 정의하고, 추가로 반환 타입을 반드시 지정해야 합니다. `(실습)` 프로시저와 마찬가지로 파라미터와 리턴 타입 선언 시에는 데이터 타입의 크기(size)를 명시하지 않습니다. `(실 습)` 예를 들어, 연봉(salary)을 입력받아 2500보다 크면 'HIGH', 아니면 'LOW'를 반환하는 함수를 만들어 보겠습니다. `(실습)`

`CREATE OR REPLACE FUNCTION f_grade (p_sal IN NUMBER) RETURN VARCHAR2 AS v_grade VARCHAR2(10) := 'LOW'; BEGIN IF p_sal > 2500 THEN v_grade := 'HIGH'; END IF; RETURN v_grade; END;` 와 같이 작성합니다. `(실습)` 여기서 반환 타입은 `VARCHAR2`이며, 실제로 반환되는 변수 `v_grade`의 타입과 일치해야 합니다. `(실습)`

함수를 테스트할 때는 워크시트에서 `SELECT f_grade(3000) FROM DUAL;` 과 같이 `SELECT` 문을 통해 직접 호출하여 결과를 확인합니다. `(실습)`

이러한 PL/SQL 프로그래밍(procedure, function) 지식은 트리거(trigger), 뷰(view) 등 보안 관련 고급 기능을 구현하는 데 필수적입니다. 감사 로그를 기록하거나, 특정 조건에서만 데이터 수정/삭제를 허용하는 등의 보안 정책을 코드로 구현할 수 있습니다.

마지막으로, 함수를 활용하는 실습 문제를 하나 더 풀어보겠습니다. `(실습)` 부서 번호를 입력받아 부서명을 반환하는 함수를 만들고, 이 함수를 사용하여 급여가 1500 이상인 사원들의 이름, 부서명, 담당 업무, 급여를 조회하는 `SELECT` 문을 작성해 보세요. `(실습)` 이 함수를 사용하면 `DEPT` 테이블과 `JOIN`을 하지 않고도 부서명을 조회할 수 있어, 대용량 데이터 처리 시 성능상 이점을 가질 수 있습니다. `(실습)`

## **2025-10-13, 1교시 — 개념**

1. 한 줄 요약

    데이터베이스 보안 로직 구현의 기초로서, PL/SQL 저장 프로시저(Stored Procedure)의 기본 구문, 제어 흐름, 변수 사용 및 실행 방법을 학습합니다.

2. **핵심 TL;DR**

- **Stored Program**: 데이터베이스 내에 저장되어 재사용 가능한 코드 묶음으로, 프로시저(Procedure), 함수(Function), 트리거(Trigger)가 있습니다.
- **PL/SQL**: SQL을 절차적으로 확장한 언어로, 변수, 조건문, 반복문을 사용하여 복잡한 로직을 구현할 수 있습니다.
- **프로시저 생성**: `CREATE PROCEDURE [이름] (...) AS ...` 구문을 사용하여 정의합니다.
- **프로그램 블록**: 코드의 실행부는 `BEGIN`으로 시작하고 `END`로 끝나며, `AS`와 `BEGIN` 사이에서 지역 변수를 선언합니다.
- **데이터 조회 및 할당**: `SELECT ... INTO [변수]` 구문을 사용하여 쿼리 결과를 지역 변수에 저장합니다.
- **파라미터 (Parameter)**: 프로시저에 값을 전달하는 통로로, `IN`(읽기전용), `OUT`(쓰기전용), `INOUT`(읽기/쓰기) 모드가 있습니다.
- **화면 출력**: `SET SERVEROUTPUT ON`을 먼저 실행한 후, `DBMS_OUTPUT.PUT_LINE()`을 사용해 결과를 출력합니다.
- **프로시저 실행**: `EXECUTE` 또는 축약형인 `EXEC` 명령어로 프로시저를 호출합니다.
- **제어문**: `IF-ELSIF-END IF` 문으로 조건을 처리하고, `FOR`, `WHILE`, `LOOP` 문으로 반복을 제어합니다.
- **예외 처리**: `EXCEPTION` 블록을 사용하여 런타임 오류(e.g., 조회된 데이터 없음)를 처리합니다.

3. **표현 = 표준 용어**

- **PL/SQL (Procedural Language/SQL)**: SQL을 확장한 절차적 언어.
- **Stored Procedure**: 데이터베이스에 저장된 명명된 PL/SQL 블록.
- **Parameter Mode**: 파라미터의 동작 방식 (`IN`, `OUT`, `INOUT`).
- **Variable Declaration**: `변수명 데이터타입;` 또는 `변수명 테이블.컬럼%TYPE;` 형식으로 선언.
- **Assignment Operator**: `:=` (값을 변수에 할당하는 연산자).
- **Concatenation Operator**: `||` (두 문자열을 연결하는 연산자).
- **Conditional Control**: `IF condition THEN ... ELSIF ... ELSE ... END IF;`
- **Iterative Control (Loop)**: `FOR i IN start..end LOOP ... END LOOP;`
- **Exception Handler**: `EXCEPTION WHEN [오류 조건] THEN ...;`

4. 정석 보강(canon-std)

    저장 프로시저(Stored Procedure)는 복잡한 데이터 처리 로직을 캡슐화하고 최소 권한 원칙(principle of least privilege)을 강제하는 핵심 도구입니다. 사용자에게 테이블에 대한 직접적인 SELECT, UPDATE 권한 대신 프로시저에 대한 EXECUTE 권한만 부여하면, 허가된 방식으로만 데이터를 조작하게 할 수 있습니다. GRANT EXECUTE ON procedure_name TO user_or_role; 명령이 이 역할을 수행합니다. 다만, 프로시저가 기본적으로 **정의자 권한(definer's rights)**으로 실행될 경우, 의도치 않은 권한 상승이 발생할 수 있으므로 안전한 코딩이 필수적입니다.

5. **실수·함정**

- `SELECT ... INTO` 구문은 단 하나의 행이 반환될 때만 정상 작동합니다. 결과가 없으면 `NO_DATA_FOUND`, 두 개 이상이면 `TOO_MANY_ROWS` 예외가 발생합니다.
- 프로시저의 파라미터 선언 시 데이터 타입의 크기를 명시하지 않지만 (`VARCHAR2`), 내부 지역 변수 선언 시에는 반드시 크기를 지정해야 합니다 (`VARCHAR2(100)`).
- 값 할당 연산자는 `:=` 이며, 비교 연산자인 = 와 혼동하면 안 됩니다.
- `SET SERVEROUTPUT ON` 명령을 실행하지 않으면 `DBMS_OUTPUT.PUT_LINE`을 사용해도 결과가 화면에 보이지 않습니다.
- 나머지 연산은 `%`가 아닌 `MOD()` 함수를 사용해야 합니다.
- `IN` 모드 파라미터는 읽기 전용이므로 프로시저 내부에서 값을 수정할 수 없습니다.
- `LOOP`이나 `WHILE` 문에서 종료 조건(`EXIT WHEN`)을 잘못 설정하면 무한 루프에 빠질 수 있습니다.

**2025-10-13, 2교시 — 개념**

1. 한 줄 요약

    사용자 정의 함수(Stored Function)의 개념, 값을 반환하는 프로시저와의 핵심 차이점, 그리고 SELECT 문에 통합하여 JOIN 연산을 대체하는 등 실용적인 활용법을 학습합니다.

2. **핵심 TL;DR**

- **함수 (Function)**: 특정 계산을 수행하고 **반드시 단일 값을 반환**하는 스토어드 프로그램입니다.
- **프로시저 vs. 함수**: 프로시저는 독립적인 실행(`EXEC`)을 위한 코드 블록인 반면, 함수는 SQL 문 내에서 호출(`SELECT`)되어 결과 값을 반환하는 데 목적이 있습니다.
- **필수 반환 (Return)**: 함수는 `CREATE FUNCTION` 선언부에 `RETURN`으로 반환 타입을 명시해야 하며, 실행부(`BEGIN-END`) 내에 `RETURN [값];` 구문이 반드시 포함되어야 합니다.
- **SQL 통합 사용**: `SUM()` 같은 내장 함수처럼, 사용자가 정의한 함수도 `SELECT` 목록, `WHERE`, `HAVING` 절에서 직접 호출하여 사용할 수 있습니다.
- **선언 규칙**: 파라미터와 반환 타입 선언 시 프로시저와 동일하게 데이터 크기(예: `VARCHAR2(10)`)를 생략하고 타입명(`VARCHAR2`)만 명시합니다.
- **타입 일치**: 함수 선언부에 명시된 `RETURN` 데이터 타입과, 본문에서 실제로 반환하는 값의 데이터 타입은 반드시 일치해야 합니다.
- **`JOIN` 대체 활용**: 다른 테이블의 값을 조회하는 함수를 만들면, `JOIN` 구문을 사용하지 않고도 `SELECT` 문에서 관련 정보를 표시할 수 있어 쿼리가 단순해집니다.
- **보안 기반**: 함수와 프로시저는 복잡한 보안 규칙(예: 조건부 데이터 접근, 감사 로직)을 캡슐화하고 코드 레벨에서 강제하는 중요한 기반 기술입니다.

3. **표현 = 표준 용어**

- **Stored Function**: 데이터베이스에 저장되어 `SELECT` 등 SQL문에서 호출되며, 반드시 값을 반환하는 명명된 PL/SQL 블록.
- **Return Type**: `RETURN [데이터타입]` (함수 선언부에 명시하는 반환 값의 자료형).
- **Return Statement**: `RETURN [변수 또는 값];` (함수 실행부에서 특정 값을 호출 지점으로 반환하는 구문).
- **Function Call in SQL**: `SELECT function_name(column) FROM table;` (SQL 문 내에서 함수를 호출하는 표준 패턴).
- **User-Defined Function (UDF)**: 사용자가 직접 정의한 함수.
- **Join Elimination**: 복잡한 `JOIN` 연산을 함수 호출로 대체하여 쿼리를 단순화하거나 특정 상황에서 성능을 개선하는 기법.

4. 정석 보강(canon-std)

    사용자 정의 함수(UDF)는 로직 캡슐화에 유용하지만, SELECT 문의 행마다 호출될 경우 반복 실행으로 인한 컨텍스트 스위칭(context switching) 비용으로 성능 저하를 유발할 수 있습니다. 특히 WHERE 절에 사용된 함수는 옵티마이저가 인덱스를 효율적으로 사용하지 못하게 만들 수 있습니다. 안정적인 시스템에서는 함수 내에서 DML(INSERT, UPDATE 등)이나 트랜잭션 제어(COMMIT)를 수행하는 것을 피해야 합니다.

5. **실수·함정**

- `CREATE FUNCTION` 선언부에 `RETURN` 타입을 명시하고, 본문 `END` 키워드 전에 `RETURN [값];` 구문을 누락하는 경우.
- 선언된 `RETURN` 타입과 실제 반환하는 값의 데이터 타입이 일치하지 않는 오류.
- 함수는 독립적으로 실행할 수 없으므로 `EXEC` 명령어로 호출 시도. (반드시 `SELECT` 문 등에서 호출해야 함)
- 파라미터나 리턴 타입 선언에 `VARCHAR2(20)`처럼 크기를 지정하여 컴파일 오류를 발생시키는 경우.
- 대용량 테이블을 조회하는 `SELECT` 목록에서 함수를 사용하면, 매 행마다 함수가 호출되어 심각한 성능 저하를 초래할 수 있음.
- 함수 내부에 `COMMIT`이나 `ROLLBACK` 같은 트랜잭션 제어 구문을 포함하여 트랜잭션의 원자성을 해치는 경우.

**[Q1] 저장 프로시저(Stored Procedure)란 무엇이며, 이것이 데이터베이스 보안에 왜 중요한가요? | `인증/인가`, `definer vs invoker`, `least privilege`**

- **모범답(강의 기준)**: 프로시저는 데이터베이스에 저장된 코드 묶음으로, 복잡한 로직을 캡슐화합니다. 보안 측면에서는 사용자에게 테이블 직접 접근 권한 대신 프로시저 실행 권한만 부여하여, 정해진 방식으로만 데이터를 조작하도록 통제할 수 있습니다.

- **정석체크(면접 30초)**: 파라미터 선언 시 크기를 생략하는 것은 유연성을 확보하기 위함입니다. 반면, 지역 변수는 명시적인 크기 선언을 통해 내부적으로 할당될 메모리 양을 확정하고 데이터 잘림(truncation) 오류를 방지합니다. `테이블.컬럼%TYPE`을 사용하면 원본 컬럼의 타입을 그대로 상속받아 유지보수성을 높일 수 있습니다.

**[Q3] 프로시저 내에서 `SELECT ... INTO` 구문을 사용할 때 발생할 수 있는 주요 예외(exception)는 무엇이며, 어떻게 처리해야 하나요? | `감사/감사 정책/보존`**

**[S2] User-Defined Function 생성 — 조건부 값 반환**

- **목적**: 연봉(salary)을 입력받아 2500을 초과하면 'HIGH', 아니면 'LOW'를 반환하는 사용자 정의 함수(`f_grade`)를 생성하고 테스트한다.
- **단계요약**: 1) `CREATE FUNCTION f_grade`를 정의하고, `p_sal IN NUMBER` 파라미터와 `RETURN VARCHAR2` 반환 타입을 명시한다. 2) `IF p_sal > 2500 THEN ...` 조건문을 사용하여 반환할 값을 결정하고 지역 변수에 할당한다. 3) `RETURN` 키워드로 최종 값을 반환한다. 4) `SELECT f_grade(3000) FROM DUAL;`과 같은 SQL 쿼리로 함수를 호출하여 결과를 확인한다.
- **⚠️ 주의**: 함수 선언 시 파라미터와 리턴 타입에는 `VARCHAR2`처럼 크기를 명시하지 않는다.

**[S3] Function 활용 — `JOIN` 연산 대체**

- **목적**: 부서 번호를 인자로 받아 부서명을 반환하는 함수를 만들고, 이를 활용하여 `JOIN` 없이 여러 테이블의 정보를 조회하는 쿼리를 작성한다.
- **단계요약**: 1) 부서 번호를 파라미터로 받고 부서명을 `VARCHAR2`로 반환하는 함수(예: `f_get_dname`)를 생성한다. 2) 함수 내에서 `SELECT DNAME INTO v_dname FROM DEPT WHERE DEPTNO = p_deptno;` 구문으로 부서명을 조회하고 반환한다. 3) `SELECT ENAME, f_get_dname(DEPTNO), JOB, SAL FROM EMP WHERE SAL >= 1500;`과 같이 메인 쿼리의 `SELECT` 목록에서 함수를 직접 호출한다.
