## (**2025-09-05, 1교시**)

데이터베이스 시험의 첫 번째 주제는 데이터베이스 설계입니다. 데이터를 효과적으로 구조화하는 것이 목표이며, 이 설계 과정은 **개념적 설계**, **논리적 설계**, **물리적 설계** 단계로 나뉩니다. 이 개념을 이해하기 위해 먼저 과학적 모델링에 대해 설명하겠습니다. 과학적 모델링이란 현실 세계의 복잡한 문제를 여러 단계를 거쳐 해결하는 방식입니다.

예를 들어, 특정 문제 상황이 주어졌을 때, 우리는 문제 해결과 관련 없는 정보를 제거하고 핵심적인 요소만 추출합니다. 문제의 전체적인 배경이나 맥락을 '도메인(Domain)' 또는 '컨텍스트(Context)'라고 하며, 이 안에서 불필요한 세부사항을 제거하고 문제의 본질만 남기는 과정을 **추상화(Abstraction)**라고 합니다. 공학에서 추상화는 문제의 핵심만 정확히 추출하는 것을 의미합니다.

복잡한 문제는 한 번에 해결하기 어렵기 때문에 여러 단계의 모델링을 거칩니다.
1.  **실세계(Real World)**: 자연어로 표현된 문제 그 자체입니다.
2.  **개념적 단계(Conceptual Level)**: 실세계의 문제를 사람이 이해하기 쉬운 표, 그림, 모형 등으로 정리하는 단계입니다. 이 단계의 산출물은 여전히 사람이 이해하기 좋은 형태를 유지합니다.
3.  **논리적 단계(Logical Level)**: 개념적 모델을 수학과 유사한 형태로 변환하는 단계입니다. 이 단계부터는 특정 분야의 전문 지식이 필요하며, 사람이 직관적으로 이해하기 어려워집니다. 학문적 엄밀성을 위해 오해의 소지를 줄이는 수식 형태의 표현이 사용됩니다.
4.  **물리적 단계(Physical Level)**: 논리적 모델을 실제 컴퓨터 시스템에 적용하는 단계입니다. 이 단계는 수학적(Mathematical) 또는 형식적(Formal) 단계라고도 부르며, 모든 것이 수학적 형태로 엄격하게 정의됩니다.

이러한 모델링 과정은 모든 공학 분야에 적용되며, 다루는 주제(Subject)에 따라 모델의 이름이 달라집니다. 데이터베이스 설계에서는 이 과정을 '관계형 데이터 모델링'이라고 부릅니다. 현재 사용되는 대부분의 데이터베이스는 **관계형 데이터베이스(Relational Database)**입니다. 과거에 객체지향형이나 네트워크형 모델도 있었지만, 성능과 효율성 문제로 현재는 관계형 모델이 주류가 되었습니다. 최근에는 관계형 모델에 객체지향 개념을 일부 도입한 **객체-관계형 데이터베이스**도 사용되고 있습니다.

데이터베이스 설계 과정에 과학적 모델링 단계를 적용하면 다음과 같습니다.
* **개념적 설계 단계**: 이 단계의 산출물은 **ERD(Entity-Relationship Diagram)**입니다. ERD는 데이터의 구성 요소(Entity)와 그들 간의 관계(Relationship)를 그림으로 표현한 것입니다.
* **논리적 설계 단계**: ERD를 **관계형 모델(Relational Model)**, 즉 표(Table)의 집합으로 변환합니다. 여기서 '관계(Relation)'는 수학 용어로서 '표'를 의미하며, 모든 데이터를 표 형태로 구성하는 것이 핵심입니다.
* **물리적 설계 단계**: 관계형 모델을 실제 DBMS(Database Management System)에 구현하는 단계입니다. 여기서는 하드디스크의 용량, 파일 시스템 배치 등 물리적 요소를 고려하지만, 대부분의 현대 DBMS가 이 부분을 자동화하므로 설계자는 주로 논리적 설계까지 집중합니다.

설계가 완료된 모델은 **SQL(Structured Query Language)**이라는 언어를 통해 DBMS와 상호작용합니다. SQL은 데이터를 입력, 검색, 수정, 삭제하는 명령어로 구성되며, 파이썬과 같은 범용 프로그래밍 언어에 비해 매우 단순하여 단기간에 학습할 수 있습니다. `SELECT`, `INSERT`, `UPDATE`, `DELETE`와 같은 핵심 구문만 이해하면 충분합니다.

이번 학기 과제는 각자 주변에서 데이터를 조직화할 필요가 있는 대상을 찾아 직접 데이터베이스를 설계해 보는 것입니다. 이를 위해 MySQL, Oracle, PostgreSQL 같은 DBMS를 개인적으로 설치하여 진행해야 합니다. (실습) 중간고사 전까지 이러한 데이터베이스 설계의 전 과정을 학습하게 될 것입니다.

### **데이터베이스 개념 요약 (1교시)**

#### **1. 한 줄 요약**
데이터베이스 설계는 실세계 문제를 **추상화**하여 **개념적, 논리적, 물리적 단계**로 구체화하는 과학적 모델링 과정을 따르며, 최종적으로 **관계형 모델(표)**과 **SQL**로 구현됩니다.

---

#### **2. 핵심 TL;DR**
* 데이터베이스 설계는 **과학적 모델링** 절차를 따릅니다. [P01]
* 설계의 핵심은 **추상화(Abstraction)**, 즉 문제의 본질만 추출하는 것입니다. [P02]
* 설계는 **개념적 → 논리적 → 물리적** 3단계로 진행됩니다. [P03]
* **개념적 단계**에서는 사람이 이해하기 쉬운 **ERD(Entity-Relationship Diagram)**를 만듭니다. [P05]
* **논리적 단계**에서는 ERD를 **관계형 모델**, 즉 **표(Table)**의 집합으로 변환합니다. [P05]
* **물리적 단계**는 실제 컴퓨터에 데이터를 저장하는 방법을 다루며, 대부분 DBMS가 자동화합니다. [P05]
* 데이터베이스의 **'관계(Relation)'**는 수학 용어로 **'표(Table)'**를 의미하며, 일반적인 '관계(Relationship)'와 다릅니다. [P04]
* **SQL**은 데이터베이스와 소통하기 위한 단순하고 강력한 표준 언어입니다. [P06]

---

#### **3. 주요 용어 및 개념**
* **과학적 모델링 (Scientific Modeling)** = 실세계 문제를 여러 단계를 거쳐 공학적으로 해결하는 접근법. [P01]
* **추상화 (Abstraction)** = 문제 해결에 불필요한 세부 정보를 제거하고 핵심 요소만 명확히 정의하는 과정. [P02]
* **개념적 설계 (Conceptual Design)** = 실세계 요구사항을 ERD와 같이 사람이 이해하기 쉬운 추상적인 모델로 표현하는 단계. [P03, P05]
* **논리적 설계 (Logical Design)** = 개념적 모델을 특정 데이터 모델(예: 관계형 모델)의 논리적 구조로 변환하는 단계. [P03, P05]
* **물리적 설계 (Physical Design)** = 논리적 데이터 구조를 실제 저장 장치에 어떻게 저장할지 결정하는 단계. [P03, P05]
* **관계 (Relation)** = 데이터베이스의 핵심 구성 요소인 **표(Table)**를 의미하는 수학적 용어. [P04]
* **관계형 모델 (Relational Model)** = 모든 데이터를 2차원 **표(Relation)**의 집합으로 표현하는 데이터 모델. [P05]
* **ERD (Entity-Relationship Diagram)** = 개념적 설계의 대표적인 산출물로, 데이터 개체(Entity)와 그들 간의 관계(Relationship)를 도식화한 그림. [P05]
* **SQL (Structured Query Language)** = 데이터베이스의 데이터를 정의, 조작, 제어하기 위해 사용하는 표준 질의 언어. [P06]

---

#### **4. 심화 학습: 데이터베이스 설계 흐름**
이번 강의의 핵심은 데이터베이스가 구축되는 전체적인 흐름을 이해하는 것입니다. 이 흐름은 다음과 같이 정리할 수 있습니다.

**`실세계 문제 인식 → (추상화) → 개념적 설계 (ERD) → 논리적 설계 (관계형 모델/테이블) → 물리적 설계 (SQL로 DBMS에 구현)`**

* 각 단계는 이전 단계의 산출물을 입력으로 받습니다. 예를 들어, 논리적 설계는 개념적 설계에서 완성된 ERD 없이는 진행할 수 없습니다. [P05]
* 이처럼 체계적인 단계를 거치는 이유는 복잡한 요구사항을 누락 없이 정확하게 반영하고, 향후 유지보수가 용이한 안정적인 데이터 구조를 만들기 위함입니다. [P01, P03]

---

#### **5. 실수 및 함정 포인트**
1.  **'관계(Relation)'의 혼동**: 데이터베이스에서 '관계'는 '표'를 의미합니다. ERD의 '관계(Relationship)'와는 다른 개념이므로 명확히 구분해야 합니다. [P04]
2.  **추상화의 오해**: 공학에서 추상화는 '모호하게 만드는 것'이 아니라, 오히려 '불필요한 것을 제거해 핵심을 명확히 하는 과정'입니다. [P02]
3.  **설계 단계 건너뛰기**: 간단해 보인다고 개념적/논리적 설계를 생략하고 바로 테이블을 만들면, 데이터 중복이나 불일치 등 심각한 구조적 문제를 유발할 수 있습니다. [P03]
4.  **물리적 설계에 대한 부담**: 현대의 DBMS는 대부분의 물리적 최적화를 자동으로 처리하므로, 설계자는 개념적, 논리적 설계에 더 집중하는 것이 효율적입니다. [P05]
5.  **SQL에 대한 오해**: SQL은 `C`나 `Java` 같은 절차적 프로그래밍 언어가 아니라, '무엇을 원하는지'를 선언하는 선언적 언어입니다. [P06]

#### **[Q1] 데이터베이스 설계의 목표와 방법**
  * **태그**: \#DB개요, \#ER→관계 사상, \#정규화
  * **정제문**: 데이터베이스 설계의 궁극적인 목표는 무엇이며, 데이터를 효과적으로 구조화하려면 어떻게 해야 하는가?
  * **교수 의도 (이해)**: 데이터베이스 설계라는 행위의 근본적인 목적과 필요성을 이해시키는 것을 목표로 합니다.
  * **최소 답 (10초)**: 검색, 삽입, 수정, 삭제와 같은 데이터 연산의 성능이 좋게 나오도록 데이터를 조직화하는 것입니다. [P05]
  * **모범 답 (canonical)**: 실세계의 데이터를 **중복과 불일치 없이** 저장하고, 검색, 삽입, 수정, 삭제 연산이 **빠르게 수행**될 수 있도록 논리적, 물리적 구조를 만드는 것입니다. 이를 위해 \*\*정규화(Normalization)\*\*와 같은 기법을 체계적으로 적용합니다.
  * **오해 포인트**:
    1.  단순히 데이터를 모아두는 행위를 '설계'라고 착각하는 것.
    2.  '잘 구조화'를 단순히 보기 좋게 정리하는 것으로만 이해하는 것.
    3.  성능 고려 없이 논리적 완결성에만 집착하는 것.

  * **꼬리질문**: '잘 조직화된' 데이터 구조가 가져오는 구체적인 성능상의 이점은 무엇인가?

## (**2025-09-05, 2교시**)

데이터베이스 시스템(DBS: Database System)은 **데이터베이스 관리 시스템(DBMS)**와 실제 데이터의 집합인 **데이터베이스(DB)**의 조합으로 구성됩니다. DBMS는 MySQL이나 Oracle과 같이 데이터를 관리해 주는 시스템 소프트웨어 패키지이며, 데이터베이스는 이 DBMS를 통해 저장되고 관리되는 구조화된 데이터 그 자체를 의미합니다.

DBMS를 사용하는 주된 이유는 다음과 같습니다.
* **데이터 독립성(Data Independence)**: 응용 프로그램과 데이터를 분리하여, 데이터의 구조가 변경되어도 관련된 응용 프로그램을 수정할 필요가 없도록 하는 특성입니다. 한 부분의 수정이 다른 부분의 연쇄적인 수정을 유발하지 않는 상태를 의미합니다.
* **데이터 무결성(Data Integrity)**: 데이터베이스의 데이터가 현실 세계의 값과 항상 일관되고 정확하게 유지되어야 한다는 원칙입니다. 예를 들어, 은행 계좌의 잔액이 전산 시스템에서도 실제와 동일하게 표현되어야 합니다.
* **보안(Security)**: DBMS는 자체적인 보안 기능을 내장하고 있어, 허가되지 않은 접근이나 침입으로부터 데이터를 보호하는 방어 체계를 구축할 수 있습니다.
* **동시성 제어(Concurrency Control)**: 여러 사용자가 동시에 데이터베이스에 접근하여 작업을 수행할 수 있도록 지원합니다.

'동시성'과 관련하여 **병행(Concurrency)**과 **병렬(Parallelism)**의 차이를 이해해야 합니다.
* **병행(Concurrency)**: **하나의 CPU**가 여러 작업을 매우 짧은 시간 간격으로 번갈아 처리하여 마치 동시에 실행되는 것처럼 보이게 하는 방식입니다. Windows와 같은 대부분의 현대 운영체제는 이러한 시분할(Time-sharing) 또는 멀티프로세싱(Multi-processing) 시스템이며, 데이터베이스 분야에서는 이를 '병행'이라고 부릅니다.
* **병렬(Parallelism)**: **여러 개의 CPU**가 실제로 각기 다른 작업을 동시에 처리하는 방식입니다. 이는 주로 슈퍼컴퓨터와 같이 고성능 연산이 필요한 시스템에서 사용됩니다.

데이터베이스의 구성 요소를 설명하는 핵심 용어로 **스키마(Schema)**와 **인스턴스(Instance)**가 있습니다.
* **스키마(Schema)**: 데이터베이스의 구조, 즉 데이터를 담을 틀이나 껍데기를 의미합니다. 예를 들어, 학생 성적 표에서 '학번', '이름', '과목', '총점'과 같은 열(Column)의 정의가 스키마에 해당합니다. 이러한 각 열을 **필드(Field)** 또는 **애트리뷰트(Attribute)**라고 부릅니다.
* **인스턴스(Instance)**: 스키마라는 구조에 실제로 저장된 데이터 값들을 의미합니다. '1번 학생 갑동이의 성적 데이터' 한 줄과 같은 개별 데이터 행(Row)을 지칭하거나, 테이블에 포함된 전체 데이터 집합을 의미할 수 있습니다. 이 개별 데이터 행은 문맥에 따라 **레코드(Record)** 또는 **튜플(Tuple)**이라고도 불립니다.

데이터베이스에서 실행되는 작업의 논리적 단위를 **트랜잭션(Transaction)**이라고 합니다. 이는 운영체제의 '프로세스(Process)'와 유사한 개념으로, 데이터베이스 상에서 실행되고 있는 프로그램의 한 덩어리입니다. 트랜잭션은 **ACID**라는 네 가지 특성을 만족해야 하며, 그중 첫 번째인 **원자성(Atomicity)**은 작업이 전부 성공적으로 실행되거나(All) 혹은 전부 실패하여 원상 복구(Nothing)되어야 한다는 'All or Nothing' 원칙을 의미합니다. ATM 인출 과정에서 오류 발생 시 모든 것이 초기 상태로 돌아가는 것이 대표적인 예입니다.

데이터베이스 시스템에서는 변경 사항이나 접근 기록을 **로그(Log)** 파일에 순차적으로 기록하여 문제 발생 시 복구나 추적에 사용합니다.

마지막으로, 시스템 관리자와 데이터베이스 관리자는 역할이 다릅니다.
* **시스템 관리자(System Administrator)**: 하드웨어, 운영체제 설치, 사용자 계정 관리 등 전반적인 컴퓨터 시스템을 관리합니다.
* **데이터베이스 관리자(DBA: Database Administrator)**: DBMS를 설치하고, 설계된 데이터베이스를 시스템에 적용하며, 운영 및 백업을 책임지는 데이터베이스 전문가입니다.

과제 수행을 위해 여러분은 MySQL과 같은 DBMS를 직접 설치하고, 지난 시간에 배운 설계 단계를 거쳐 ERD와 관계형 모델을 만든 후, SQL을 사용하여 DBMS에 데이터를 입력하게 될 것입니다. (실습)

#### **3. 주요 용어 및 개념**
* **DBS (Database System)** = DBMS(소프트웨어)와 DB(데이터)를 포괄하는 전체 시스템. [P01]
* **DBMS (Database Management System)** = MySQL, Oracle과 같이 데이터베이스를 효율적으로 관리하고 운영하는 시스템 소프트웨어. [P01]
* **데이터 독립성 (Data Independence)** = 데이터의 물리적/논리적 구조가 변경되어도 응용 프로그램은 영향을 받지 않는 중요한 특성. [P02]
* **데이터 무결성 (Data Integrity)** = 데이터가 현실 세계의 값과 일치하도록 정확성과 일관성을 유지하는 성질. [P02]
* **병행 (Concurrency)** = CPU 하나가 여러 작업을 시분할(Time-sharing)하여 동시에 처리되는 것처럼 보이게 하는 기술. OS의 '멀티프로세싱'과 유사. [P04]
* **병렬 (Parallelism)** = 둘 이상의 CPU가 물리적으로 동시에 여러 작업을 처리하는 기술. [P05]
* **스키마 (Schema)** = 데이터베이스의 구조와 제약 조건에 대한 명세. 즉, 데이터의 '설계도' 또는 '틀'. [P07]
* **인스턴스 (Instance)** = 스키마의 구조에 따라 실제로 저장된 데이터 값들의 집합. [P08]
* **튜플/레코드 (Tuple/Record)** = 테이블의 한 행(Row)을 가리키는 용어. [P08]
* **트랜잭션 (Transaction)** = 'All or Nothing' 원칙으로 수행되는 데이터베이스 작업의 논리적 단위. OS의 '프로세스'에 해당. [P09]
* **원자성 (Atomicity)** = 트랜잭션의 모든 연산이 완전히 실행되거나, 하나라도 실패하면 모두 취소되어 원래 상태로 복구되어야 하는 성질. [P09]
* **DBA (Database Administrator)** = DBMS 설치, 데이터베이스 설계, 운영, 보안 등을 책임지는 데이터베이스 관리 전문가. [P11]

#### **4. 심화 학습: 핵심 개념 구분**
* **병행 vs. 병렬**: 핵심 구분 기준은 **CPU의 개수**입니다. 병행은 CPU 1개로 동시 실행의 '환상'을, 병렬은 CPU 여러 개로 '실제' 동시 실행을 구현합니다. 데이터베이스의 동시 접근 제어는 '병행'의 개념에 기반합니다. [P03]
* **스키마 vs. 인스턴스**: **구조와 실제 데이터**의 분리입니다. 스키마는 한번 정의되면 잘 바뀌지 않는 '정적인 틀'인 반면, 인스턴스는 데이터의 삽입, 수정, 삭제에 따라 계속 변하는 '동적인 내용물'입니다. [P06]
* **시스템 관리자 vs. DBA**: **관리 범위**의 차이입니다. 시스템 관리자가 건물 전체(하드웨어, OS)를 관리한다면, DBA는 그 건물 안의 핵심 시설인 금고실(데이터베이스)을 전문적으로 관리하는 역할에 비유할 수 있습니다. [P11]

#### **5. 실수 및 함정 포인트**
1.  **DBS와 DBMS의 혼동**: DBS는 DBMS를 포함하는 더 넓은 개념(시스템 전체)입니다. DBMS는 DBS의 핵심 소프트웨어 구성 요소입니다. [P01]
2.  **병행과 병렬의 오용**: 두 용어는 CPU 개수에 따라 명확히 구분되므로, '동시 작업'이라는 말로 뭉뚱그려 이해해서는 안 됩니다. [P03]
3.  **용어의 분야별 차이 무시**: 운영체제의 '프로세스'가 DB의 '트랜잭션'에, '멀티프로세싱'이 '병행'에 대응되는 것처럼, 같은 개념이라도 학문 분야에 따라 용어가 다를 수 있음을 인지해야 합니다.
4.  **스키마와 인스턴스의 혼동**: 스키마는 '정적'인 구조이고, 인스턴스는 '동적'으로 계속 변하는 실제 데이터 값입니다. [P06]
5.  **트랜잭션의 원자성 간과**: 트랜잭션 내 여러 작업 중 일부만 성공하고 일부는 실패한 상태로 남는 것은 원자성 위반이며, 데이터베이스의 일관성을 깨뜨리는 심각한 오류입니다. [P09]

  * **교수 의도 (이해)**: 단순 파일 시스템과 비교하여 DBMS가 제공하는 시스템적 이점(독립성, 무결성 등)을 이해시킵니다.
  * **최소 답 (10초)**: **데이터 독립성, 무결성, 보안,** 그리고 여러 사용자가 동시에 사용하는 **동시성 제어**를 보장하기 위해서입니다. [P02]
  * **모범 답 (transcript)**: DBMS는 **데이터 독립성**을 제공하여 데이터 구조가 변경되어도 응용 프로그램을 수정할 필요가 없게 합니다. 또한 **데이터 무결성**을 통해 데이터의 정확성을 유지하고, 내장된 **보안** 기능과 여러 사용자가 동시에 접근할 수 있도록 하는 **동시성 제어** 기능을 제공하여 데이터를 안정적이고 효율적으로 관리합니다. [P02]
  * **오해 포인트**:
    1.  DBMS를 단순히 데이터를 많이 저장할 수 있는 엑셀 정도로 생각하는 것.
    2.  DBMS가 제공하는 시스템 관리 기능의 중요성을 간과하는 것.
  * **꼬리질문**: 만약 '데이터 독립성'이 없다면, 데이터베이스 테이블에 열(column)을 하나 추가할 때 어떤 추가 작업이 필요할까요?

#### **[Q3] 병행과 병렬의 차이**
  * **정제문**: 병행(Concurrency)과 병렬(Parallelism)은 어떻게 다른가요?
  * **태그**: \#트랜잭션, \#고립화수준
  * **교수 의도 (분석)**: 유사하지만 다른 두 개념을 핵심 기준(CPU 개수)에 따라 명확히 분석하고 구분하도록 합니다.
  * **최소 답 (10초)**: **병행**은 CPU 1개가 여러 일을 번갈아 하는 것이고, **병렬**은 CPU 여러 개가 동시에 여러 일을 처리하는 것입니다. [P03]
  * **모범 답 (transcript)**: \*\*병행(Concurrency)\*\*은 **CPU가 하나**일 때, 시분할(Time-sharing) 기술로 여러 작업을 매우 빠르게 번갈아 처리하여 사용자가 보기에는 동시에 실행되는 것처럼 느끼게 하는 방식입니다. 반면, \*\*병렬(Parallelism)\*\*은 **CPU가 여러 개**일 때, 각 CPU가 작업을 나눠 맡아 물리적으로 완전히 동시에 처리하는 방식입니다. [P04, P05]
  * **오해 포인트**:
    1.  두 용어를 '동시에 처리한다'는 모호한 표현으로 동일시하는 것.
    2.  데이터베이스의 동시성 제어(Concurrency Control)를 병렬 처리(Parallelism)와 혼동하는 것.
  * **꼬리질문**: 우리가 사용하는 일반적인 PC에서 여러 프로그램을 동시에 켜놓고 작업하는 것은 병행에 가까울까요, 병렬에 가까울까요?

#### **[Q4] 스키마와 인스턴스의 차이**
  * **정제문**: 데이터베이스에서 스키마(Schema)와 인스턴스(Instance)는 각각 무엇이며, 어떻게 다른가요?
  * **태그**: \#DB개요, \#3-스키마
  * **교수 의도 (지식)**: 데이터베이스의 '구조'와 '실제 데이터'를 나타내는 두 가지 기본 용어를 정의하고 구분하도록 합니다.
  * **최소 답 (10초)**: **스키마**는 데이터베이스의 구조, 즉 \*\*'틀' 또는 '설계도'\*\*이고, **인스턴스**는 그 틀에 담긴 \*\*'실제 데이터 값'\*\*입니다. [P06]
  * **모범 답 (transcript)**: \*\*스키마(Schema)\*\*는 테이블의 열(Column) 이름, 데이터 타입, 제약 조건 등 데이터베이스의 구조를 정의한 '설계도'입니다. 반면, \*\*인스턴스(Instance)\*\*는 이 스키마라는 틀에 따라 실제로 저장된 데이터의 집합, 즉 테이블의 모든 행(Row)들을 의미합니다. 스키마는 정적이고, 인스턴스는 계속 변합니다. [P07, P08]
  * **오해 포인트**:
    1.  테이블을 만드는 `CREATE TABLE` 구문 자체를 인스턴스로 착각하는 것.
    2.  데이터가 추가되면 스키마도 함께 변한다고 생각하는 것.

  * **꼬리질문**: 학생 테이블에 학생 한 명을 새로 추가(`INSERT`)하면, 스키마가 변하는 건가요, 인스턴스가 변하는 건가요?

#### **[Q5] 트랜잭션의 개념과 핵심 특징**
  * **인용**: "...트랜잭션이라고 하면... 운영 체제에서는 이걸 프로세스라고 하면 돼요."
  * **정제문**: 트랜잭션(Transaction)이란 무엇이며, 가장 중요한 특징은 무엇인가요?
  * **태그**: \#트랜잭션, \#ACID
  * **교수 의도 (지식)**: 데이터베이스 작업의 기본 단위인 트랜잭션의 개념과 그 핵심 속성인 원자성을 소개합니다.
  * **최소 답 (10초)**: 데이터베이스 작업의 논리적 단위이며, \*\*'전부 성공 아니면 전부 실패'\*\*하는 **원자성(Atomicity)** 특징을 가집니다. [P09]
  * **모범 답 (transcript)**: 트랜잭션은 데이터베이스에서 수행되는 작업의 논리적 단위로, 운영체제의 '프로세스'와 유사합니다. 가장 중요한 특징은 \*\*원자성(Atomicity)\*\*인데, 이는 트랜잭션에 포함된 모든 작업이 100% 성공적으로 완료되거나(All), 하나라도 실패하면 모든 작업이 취소되어 원래 상태로 완벽하게 돌아가야 함(Nothing)을 의미합니다. [P09]
  * **오해 포인트**:
    1.  SQL 문 하나하나가 모두 개별 트랜잭션이라고 생각하는 것 (여러 SQL 문이 하나의 트랜잭션을 구성할 수 있음).
    2.  트랜잭션이 실패했을 때, 실패 직전까지의 작업은 저장될 수 있다고 착각하는 것.
  * **꼬리질문**: 계좌 이체(A에서 출금, B로 입금) 트랜잭션에서, B로 입금이 실패하면 왜 A의 출금 기록도 반드시 취소되어야 하나요?
