## 📜 정리: SQL, 로직, 그리고 옵티마이저

### 종합 요약 (Logic Flow)

> [!note]- 데이터베이스 작동 메커니즘의 핵심
>
> 1. **역할의 분리:**
> 	- 사용자가 작성한 **SQL은** 데이터 요구사항을, **함수와 프로시저는** 구체적인 비즈니스 로직을 구현합니다.
> 	- **DBMS의 옵티마이저**는 이를 수행하기 위한 최적의 **방법**(실행순서,접근경로)을 결정하여 데이터 처리를 실행합니다.
> 		<br>
> 1. **로직의 구현 (User):**
> 	사용자는 **연산 중심의 읽기(Read)** 로직은 **함수**로,
> 	**상태 변경 및 트랜잭션 제어(Write)** 로직은 **프로시저**로 구분하여 구현합니다
> 		<br>
> 2. **실행의 최적화 (System):**
> 	옵티마이저는 전달받은 로직(Target)을 분석하고, 인덱스 등(Tool)을 활용하여 비용이 가장 낮은 경로(Plan)를 수립해 실행합니다.
>

## 1. 사용자의 영역: 요구사항과 로직의 정의 (What & Logic)

사용자는 데이터베이스에게 "무엇을(What)" 원하고 "어떤 로직(Logic)"으로 처리할지를 정의합니다.

### A. SQL (요구사항 정의)

- **역할:** 데이터의 추출, 조작, 제어에 대한 최종 **결과물(Requirement)** 을 기술합니다.
- **특징:** 구체적인 탐색 경로(How)는 기술하지 않는 선언형 언어입니다.

### B. 함수와 프로시저 (비즈니스 로직 정의)

SQL만으로 표현하기 힘든 절차적 흐름이나 복잡한 연산을 정의합니다. **'상태 변경 필요성'**에 따라 두 가지 컨테이너로 구분됩니다.

#### 🚨 기술적 전제: FETCH의 쓰기 차단
조회 명령(SELECT)이거나, WRITE(UPDATE, DELETE) 명령중 무조건 선행되는 과정인 FETCH 단계
- DBMS 엔진이 저장장치에서 현재 읽는 행의 위치를 커서라는 포인터를 사용합니다 이때 다음행을 읽기 위해 커서를 다음줄로 이동하는걸 FETCH라고 합니다.
- **제약 사항:** 엔진이 `FETCH`를 수행하는 도중(읽는 중)에 데이터를 변경하면, **읽은 데이터가 다시 읽히거나(Halloween Problem)** 데이터의 시점이 뒤섞이는 문제가 발생합니다. 따라서 **FETCH 단계에서의 상태 변경은 엄격히 차단**됩니다.

#### 1) 함수 (Function) - 계산 및 조회 보조
**위치:** `FETCH` 단계에서 호출되는 **연산 작업 단위**입니다.
- 그러므로 SQL(`SELECT`, `WHERE` 절 등) 내부에서 호출합니다
- **특징 (읽기 전용):**
    - 데이터를 퍼 올리는 도중에 실행되므로, 위 기술적 전제에 의해 테이블의 값 변경이 불가능합니다.

#### 2) 프로시저 (Procedure) - 비즈니스 흐름 제어, 트렌잭션
**위치:** `FETCH` 단계가 끝난 후, 전체 로직을 제어하는 **독립 실행 컨테이너**입니다.
- **특징 (읽기 및 쓰기):**
    - `FETCH` 문맥(행 단위 읽기)이 아니므로, `INSERT`, `UPDATE`, `DELETE` 등 상태 변경이 자유롭습니다.
    - 트랜잭션(`COMMIT`, `ROLLBACK`)을 소유하여 비즈니스 로직의 완결성을 보장합니다.
    - 값을 산출하는게 아니므로 반환값 생략이 가능합니다

## 2. DBMS의 영역: 실행 경로의 결정 (How & Optimization)

옵티마이저는 사용자가 정의한 SQL과 로직을 받아, 실제 하드웨어 리소스를 어떻게 사용할지 결정합니다.

### A. 옵티마이저의 대상 (Targets)

옵티마이저가 분석하고 처리해야 할 **작업물**은 개발자로부터 받는다.

- **SQL 문장:** 처리해야 할 기본 요청 단위입니다.
- **프로시저 (Container):**
    - 옵티마이저는 생성(컴파일) 시점에 내부 SQL들을 미리 분석하여 **실행 계획을 수립(Pre-compile)**해 둡니다.
    - 실행 시 저장된 계획을 재사용하므로 파싱 부하가 감소합니다.
- **함수 (Workload):**
    - 옵티마이저 입장에서 함수는 **"행(Row)마다 CPU를 사용하여 계산해야 하는 비용"**으로 간주됩니다.
        

### B. 옵티마이저의 도구 (Tools)

옵티마이저가 "어떻게 하면 데이터를 가장 빠르게 가져올까?"를 판단할 때 **참조하는 자원**입니다.

- **인덱스 (Index):** 데이터를 빠르게 찾기 위한 자료구조(B-Tree 등).
- **통계 정보 (Statistics):** 데이터의 분포도, 행의 개수, 블록 수 등 판단의 근거.
- **시스템 지표 (System Metrics):** CPU 속도, 디스크 I/O 속도 등 하드웨어 환경 정보.
    

### 🚨 주의: 로직(대상)이 도구(인덱스)를 방해하는 경우

사용자가 정의한 로직(함수)이 부적절하게 사용되면, 옵티마이저는 도구(인덱스)를 사용할 수 없게 됩니다.

- **Index Suppression (인덱스 억제):**
    - **상황:** `WHERE YEAR(date) = '2024'`와 같이 컬럼을 함수로 감싸는 경우(좌변 가공).
    - **원인:** 인덱스는 원본 `date` 값 순서로 정렬되어 있습니다. 함수로 가공된 `YEAR(date)` 값은 인덱스 트리에 존재하지 않아 매칭이 불가능합니다.
    - **결과:** 옵티마이저는 인덱스를 포기하고, **전체 테이블 스캔(Full Table Scan)**을 수행하여 성능 저하를 유발합니다.

## 1. 핵심 메커니즘: Read before Write (모든 작업의 시작)

데이터베이스의 모든 작업은 **"대상을 찾는 것(Fetch)"**에서 시작됩니다. 데이터를 수정하거나 삭제(`UPDATE`,`DELETE`)하는 DML 작업조차도 내부적으로는 반드시 **Fetch**(읽기) 과정이 선행되어야 합니다.

### A. DML(수정/삭제)의 내부 동작 단계

사용자가 `UPDATE` 문을 실행하면 엔진은 다음과 같은 순서로 움직입니다.

1. **FETCH (읽기 단계):** `WHERE` 조건에 맞는 데이터를 인덱스나 테이블 스캔을 통해 찾아 메모리(Buffer Cache)로 퍼 올리고 커서를 다음 줄로 옮깁니다.
	- 커서: 현재 읽는 행의 위치를 가리키는 포인터
2. **LOCK (잠금 단계):** 다른 트랜잭션이 건드리지 못하게 해당 행(Row)을 잠급니다.
3. **WRITE (쓰기 단계):** 메모리 상의 값을 변경하고 로그(Redo Log)를 기록합니다.
    

> **예시:** `UPDATE users SET salary = salary * 1.1 WHERE id = 100`
> 1. **(Fetch)** `id` 인덱스를 뒤져 `100`번 위치를 찾고 메모리에 로딩합니다.
> 2. **(Write)** 메모리에 있는 `salary` 값을 수정합니다.
>     

### B. 기술적 제약: FETCH 단계의 쓰기 차단

- 엔진이 데이터를 읽어 들이는 **FETCH 진행 중(Cursor 이동 중)에는 테이블 상태 변경이 엄격히 차단**됩니다.
- **이유:** 읽는 도중 데이터가 변경되면, 이미 읽은 데이터를 또 읽거나 순서가 뒤섞이는 **할로윈 문제(Halloween Problem)**가 발생할 수 있기 때문입니다.
- **결론:** 이 제약 때문에 **"읽기 전용 로직"**과 **"쓰기/제어 로직"**의 분리가 필요합니다. 즉 함수와 프로시저로 분리되여 쓰이게 됩니다

## 2. 사용자의 영역: 로직의 구현 (User's Logic)

사용자는 'Read before Write' 원칙에 따라 로직을 두 가지 형태로 나누어 구현해야 합니다.

### A. 함수 (Function): 연산과 조회의 보조

- **위치 & 역할:** 주로 **FETCH(읽기) 단계**나 값을 계산하는 과정에서 호출되는 **연산의 단위**입니다.
- **DML 내에서의 위치:**
    - `UPDATE … WHERE 함수(col)`: 대상을 찾기 위한 **필터(Fetch)** 역할.
    - `UPDATE … SET col = 함수(val)`: 값을 변경하기 전 **계산(Calculation)** 역할.
- **특징 (Read-Only):** FETCH 도중에 실행되므로, 내부에서 `INSERT/UPDATE` 같은 상태 변경을 수행할 수 없습니다.
    

### B. 프로시저 (Procedure): 트랜잭션과 흐름 제어

- **위치 & 역할:** FETCH가 끝난 후, 비즈니스 로직의 전체 흐름을 제어하는 **독립 실행 컨테이너**입니다.
- **특징 (Read & Write):**
    - FETCH 문맥(행 단위 읽기) 밖에서 실행되므로 상태 변경이 자유롭습니다.
    - `COMMIT`, `ROLLBACK`을 통해 트랜잭션의 완결성을 보장합니다.

## 3. DBMS의 영역: 실행 계획과 최적화 (Optimizer)

옵티마이저는 사용자의 SQL을 분석하여 가장 저렴한 비용의 실행 경로(Plan)를 수립합니다.

### A. 옵티마이저의 동작 원리

- **대상 (Target):** SQL 문장, 미리 컴파일된 프로시저, 계산 비용으로서의 함수.
- **도구 (Tools):** 인덱스(Index), 통계 정보(Statistics), 시스템 지표.
    

### 🚨 주의: 로직이 도구를 망가뜨리는 경우 (Index Suppression)

옵티마이저가 인덱스라는 강력한 도구를 쓰지 못하게 만드는 대표적인 실수가 **"좌변 가공"**입니다.

- **상황:** `WHERE YEAR(date_col) = '2024'`
    - 컬럼(`date_col`)이 함수(`YEAR`) 안에 갇혀 있습니다.
- **원인:** 인덱스는 원본 `date_col` 순서로 정렬되어 있는데, 가공된 `YEAR` 값은 인덱스 트리에 없으므로 매칭이 불가능합니다.
- **결과:** 옵티마이저는 인덱스를 포기하고 **Full Table Scan(전체 뒤지기)**을 수행하여 성능이 폭락합니다.

## 4. 실전 가이드: 함수와 프로시저의 올바른 사용

### A. 함수의 위치에 따른 성능 차이 (치명적 vs 안전)

|**위치**|**예시 SQL**|**영향 및 결과**|
|---|---|---|
|**WHERE 절**<br><br>  <br><br>(Fetch 단계)|`WHERE fn(col) > 100`|**치명적.**<br><br>  <br><br>1. 인덱스 사용 불가 (Full Scan).<br><br>  <br><br>2. 모든 행마다 함수 실행 (CPU 부하 급증).|
|**SELECT/SET 절**<br><br>  <br><br>(After Fetch)|`SELECT fn(col) …`<br><br>  <br><br>`WHERE col > 100`|**상대적 안전.**<br><br>  <br><br>1. `WHERE`절이 인덱스로 데이터를 먼저 줄임.<br><br>  <br><br>2. 남은 데이터만큼만 함수가 실행됨.|

### B. 프로시저와 옵티마이저의 관계 (Black Box)

- **개별 최적화:** 옵티마이저는 프로시저 전체를 하나로 보지 않고, 내부의 개별 SQL(`SELECT`, `INSERT` 등) 단위로 최적화합니다.
- **한계:** 옵티마이저는 `IF`, `LOOP` 같은 제어 로직을 이해하지 못하므로, 로직 흐름에 따른 동적인 최적화는 불가능합니다.

### 💡 요약: 최적의 로직 설계를 위한 3계명

1. **Write는 Read를 포함한다:** 수정/삭제 성능을 높이려면, 먼저 **대상을 빨리 찾는(Fetch)** 인덱스 튜닝부터 시작하십시오.
2. **컬럼은 가공하지 마라:** `WHERE` 절의 컬럼을 함수로 감싸면 인덱스는 무용지물이 됩니다.
3. **역할을 분리하라:** 단순 계산은 **함수**로, 데이터 변경과 트랜잭션 제어는 **프로시저**로 명확히 구분하십시오.


수정(`UPDATE`)이나 삭제(`DELETE`)를 수행하기 위해서는, 반드시 **"어떤 행을 고칠지 찾아내는 과정"**이 선행되어야 합니다. 즉, 내부적으로는 **FETCH(읽기)**가 먼저 발생하고, 그 후에 **WRITE(쓰기)**가 일어납니다.

이를 데이터베이스 엔진 관점에서 **'Read before Write'** 메커니즘이라고 하며, 구체적인 작동 방식은 다음과 같습니다.

---

### 1. DML(수정/삭제)의 내부 동작
`UPDATE`나 `DELETE` 문이 실행될 때, DBMS의 엔진은 두 순서로 작업을 진행합니다.
1. Fetch: `WHERE` 조건에 맞는 데이터를 찾아서 메모리(Buffer Cache)로 퍼 올립니다.
2. write: 찾아낸 데이터에 **Lock(잠금)**을 걸고 실제 값을 변경하거나 삭제 마킹을 합니다.
사용자가 다음과 같은 SQL을 실행했다고 가정합니다.

```SQL
UPDATE users 
SET salary = salary * 1.1 
WHERE id = 100;
```

#### DBMS엔진의 실행 순서

1. **Index 탐색 (FETCH):** `id` 인덱스를 뒤져서 `100`번이 저장된 위치(Block Address)를 찾습니다.
2. **데이터 로딩 (FETCH):** 해당 블록을 디스크에서 메모리로 가져옵니다. (여기까지는 `SELECT`와 동일)
3. **행 잠금 (Locking):** 다른 트랜잭션이 건드리지 못하게 해당 행을 잠급니다.
4. **값 변경 (WRITE):** 메모리 상의 `salary` 값을 수정하고, 로그(Redo Log)를 기록합니다.
    

### 3. 결론: 함수의 위치와 영향
- **`UPDATE`문의 `WHERE` 절에 쓰인 함수:**
    - **1단계(FETCH)**에서 사용됩니다.
    - 대상을 찾기 위한 **필터 역할(읽기 전용)**을 수행합니다.
    - _예:_ `WHERE UPPER(name) = 'KIM'` $\rightarrow$ 이름을 읽어서 대문자로 변환해 비교함.
- **`UPDATE`문의 `SET` 절에 쓰인 함수:**
    - **2단계(WRITE)** 직전에 값을 계산하기 위해 사용됩니다.
    - _예:_ `SET salary = ROUND(salary * 1.1)` $\rightarrow$ 값을 변경하기 위해 계산함.
결국 **"모든 쓰기 작업(UPDATE/DELETE)은 읽기(FETCH)를 포함한다"**는 것이 핵심입니다. 따라서 수정 쿼리의 성능을 높일 때도, 변경 속도보다는 **대상을 빨리 찾는(FETCH) 속도를 높이기 위해 인덱스를 튜닝**하는 것이일반적입니다.

## 1. SQL의 논리적 실행 순서 (Logical Execution Order)

DBMS 옵티마이저는 SQL 문장을 작성된 순서(SELECT → FROM)가 아닌, 논리적 처리 순서에 따라 해석하고 실행 계획을 수립합니다.

1. **FROM / JOIN:** 대상 테이블을 참조하고 데이터 집합을 생성합니다.
2. **WHERE:** 조건에 맞지 않는 행(Row)을 필터링합니다.
3. **GROUP BY:** 데이터를 그룹화합니다.
4. **HAVING:** 그룹화된 데이터에 조건을 적용합니다.
5. **SELECT:** 결과로 출력할 컬럼을 선택하거나 계산합니다.
6. **ORDER BY:** 최종 결과를 정렬합니다.

## 2. 사용자 정의 함수(Function)의 위치와 영향

함수는 **반환값(Return Value)**이 존재하며, SQL 문장 내의 표현식(Expression)으로 사용됩니다.

### 예시 시나리오: `fn_calc_tax(price)` (가격에 따른 세금 계산 함수)

#### A. WHERE 절에 위치한 경우 (치명적 성능 영향 가능성)

```SQL
SELECT product_id, price
FROM products
WHERE fn_calc_tax(price) > 1000;
```

- **실행 시점:** `FROM` 단계 직후, `WHERE` 필터링 단계에서 실행됩니다.
- **옵티마이저 영향:**
    - **인덱스 미사용:** `price` 컬럼에 인덱스가 있더라도, 가공된 값(`fn_calc_tax(price)`)을 기준으로 검색하므로 인덱스를 타지 못하고 **Full Table Scan**이 발생할 가능성이 높습니다.
    - **부하 증가:** 테이블의 모든 행(Row)마다 함수를 호출하여 실행하므로 **문맥 교환(Context Switching)** 비용이 급증합니다.
        

#### B. SELECT 절에 위치한 경우 (상대적 안전)

```SQL
SELECT product_id, fn_calc_tax(price) as tax
FROM products
WHERE price > 10000;
```

- **실행 시점:** `WHERE` 절로 데이터가 필터링된 **후**, `SELECT` 단계에서 실행됩니다.
- **옵티마이저 영향:**
    - **효율성:** `price > 10000` 조건은 인덱스를 활용하여 데이터를 먼저 줄입니다.
    - **최소 호출:** 필터링된 결과 건수만큼만 함수가 실행되므로 부하가 적습니다.

## 3. 저장 프로시저(Stored Procedure)의 위치와 영향

프로시저는 **비즈니스 로직의 집합(Container)**이며, 여러 SQL 문장을 순차적으로 제어합니다. `SELECT` 문 내부에서 호출되지 않고, 별도의 `EXECUTE` 명령으로 실행됩니다.

### 예시 시나리오: `SP_ORDER_PROCESS` (주문 처리 프로시저)

```SQL
CREATE PROCEDURE SP_ORDER_PROCESS (p_user_id INT, p_item_id INT)
AS
BEGIN
    -- 1. 재고 확인 (SELECT)
    DECLARE v_stock INT;
    SELECT stock INTO v_stock FROM items WHERE item_id = p_item_id;

    -- 2. 비즈니스 로직 (IF 제어문)
    IF v_stock > 0 THEN
        -- 3. 주문 생성 (INSERT)
        INSERT INTO orders (user_id, item_id) VALUES (p_user_id, p_item_id);
        -- 4. 재고 감소 (UPDATE)
        UPDATE items SET stock = stock - 1 WHERE item_id = p_item_id;
    END IF;
END;
```

- **위치:** SQL 내부가 아닌, 애플리케이션 레벨에서 호출되는 **최상위 실행 단위**입니다.
- **옵티마이저 영향:**
    - **개별 최적화:** 옵티마이저는 프로시저 전체를 하나의 쿼리로 보지 않습니다. 내부의 `SELECT`, `INSERT`, `UPDATE` 문을 **각각 개별적으로 최적화**하여 실행 계획을 수립합니다.
    - **블랙박스:** 옵티마이저는 `IF` 문과 같은 제어 로직(Flow Control)을 해석하지 못합니다. 따라서 프로시저 내부 로직에 따라 실행 경로가 달라져도, 이를 예측하여 최적화하지는 못합니다.

## 4. 요약 비교 (Summary)

| **구분**       | **함수 (Function)**              | **프로시저 (Procedure)**     |
| ------------ | ------------------------------ | ------------------------ |
| **주 목적**     | 값의 계산 및 반환                     | 비즈니스 로직 수행 및 트랜잭션 관리     |
| **SQL 내 위치** | SELECT, WHERE, HAVING 등 표현식 위치 | 독립적으로 실행 (SQL 내부 포함 불가)  |
| **실행 엔진**    | 쿼리 실행 도중 행(Row) 단위로 호출         | 절차적 엔진이 SQL 엔진을 순차적으로 호출 |
| **옵티마이저**    | 인덱스 사용을 방해할 수 있음 (특히 WHERE절)   | 내부의 개별 SQL 단위로 최적화 수행    |
