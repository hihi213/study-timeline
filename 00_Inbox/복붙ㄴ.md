## TL;DR

- **쓰기/읽기 분리(CQRS lite)**: 쓰기(커맨드)는 **엔티티를 반환하지 말고 ID**만. 읽기는 DTO 전용 경로. 동일 트랜잭션 내 강결합을 줄이고 **부작용을 통제**.
- **영속성 컨텍스트**: 1차 캐시/동일성 보장/쓰기 지연/변경 감지/플러시. 변경은 **@Transactional 내부**에서 엔티티 메서드로 의도를 표현.
- **연관관계 주인 = FK 가진 쪽**. 양방향이면 **한쪽만 주인**, 반대는 `mappedBy`. **편의 메서드**로 양쪽 동기화 필수.
- **매핑 기본값**: N:1, 1:1(주인) → `@JoinColumn`이 단순·명확. N:N은 학습용만, 실무는 **연결 엔티티**로 분해.
- **생명주기 전파**: `cascade`/`orphanRemoval`은 **애그리거트 내부, 공유되지 않는 자식**에만. DB `ON DELETE CASCADE`와 혼용 주의(보통 택1).
- **성능 원칙**: **기본 LAZY** + **명시적 로딩(fetch join/EntityGraph/BatchSize)**. 컬렉션 fetch join + 페이징 금지. DTO 투명 계층화.
- **equals/hashCode, toString**: 연관 필드 넣지 말기. 식별자(또는 명확한 비즈니스 키) 위주. 순환참조/지연로딩 폭탄 방지.

## 1) 영속성 컨텍스트 핵심

### 1-1. 개념과 효과

- **1차 캐시**: 동일 트랜잭션/영속성 컨텍스트 범위에서 엔티티를 캐싱 → **동일성(\==)** 보장, 중복 쿼리 방지.
- **쓰기 지연**: `persist` 시 즉시 INSERT가 아니라 **쓰기 지연 저장소**에 모았다가 **flush/commit**에 반영.
- **변경 감지(Dirty Checking)**: 영속 상태 엔티티의 스냅샷 대비 변경분을 **자동 UPDATE**.
- **플러시**: 변경 SQL 동기화. 트랜잭션 경계에서 자동, JPQL 실행 전 자동. 수동 `em.flush()`는 **쿼리 타이밍 제어**용도.

### 1-2. 상태 전이 & 준영속

- **비영속 → 영속**: `persist`로 1차 캐시에 등록(식별자 필요).
- **영속 → 준영속**: `detach`/`clear`/`close`로 관리 해제 → 변경 감지 비대상.
- **병합(merge)**: 준영속 인스턴스의 상태를 새 영속 엔티티에 **복사**(주의: 파라미터 자체는 계속 준영속).

### 1-3. 트랜잭션 & 모델링 규율

- 변경은 **항상 @Transactional 내부**에서, **엔티티 메서드**로 의도를 드러낸다.
    - ex) `order.cancel()`, `orderItem.changeQuantity(qty)`
- **값 타입은 불변**으로 설계(세터 제거, 생성자/팩토리). 변경은 통째 교체.
- **기본 생성자**: public/protected 필요(권장: protected).

## 2) 연관관계 기초(모델링 원칙)

- **FK 있는 쪽이 연관관계 주인(owner)**. 반대쪽은 **거울(inverse)** → `mappedBy`.
- **단방향**: 한쪽만 참조. **양방향**: 양쪽 참조 + **주인은 하나**.
- **객체 그래프 탐색** 요구가 있는 **자주 조회 방향** 위주로 양방향을 열어라.
- **편의 메서드**로 양쪽 세팅:
    
    ```java
    public void addOrderItem(OrderItem item){
        orderItems.add(item);
        item.setOrder(this);
    }
    ```
    
- **일대다 단방향**은 신중히(추가 UPDATE 발생, 관리 복잡). 가능하면 **다대일 양방향**으로 단순화.

## 3) 연관관계 매핑 전략(실전 선택지)

### 3-1. 단골 조합

- **N:1 / 1:N(반대)**: 기본은 `@ManyToOne(fetch = LAZY)` + `@JoinColumn(name = "...")`.
- **1:1**: FK 소유자 쪽을 주인으로. 성능/도메인 주도 방향 기준으로 택.
- **N:N**: 학습용만 `@ManyToMany`. 실무는 **연결 엔티티(Association Entity)** 로 분해(N:1 + 1:N)하여 속성/제약 관리.

### 3-2. 키/테이블 전략

- **@JoinColumn(FK)** 가 **기본값**이자 가장 명확한 선택.
- **@JoinTable(연결 테이블)** 은 레거시/특수 케이스 외엔 지양. 필요한 경우 연결 엔티티를 만드는 편이 테스트/제약/확장에 유리.
- **복합키 남용 금지**: 가능하면 **대리키(PK)** + **유니크 제약**으로 단순화.

### 3-3. 매핑 체크포인트

- FK 가진 쪽이 주인으로 설정됐는가?
- 양방향이면 한쪽만 주인, 반대는 `mappedBy` 인가?
- 자주 탐색되는 방향만 양방향 열었는가?
- **LAZY 기본화**(특히 `@ManyToOne`, `@OneToOne`는 기본 EAGER이므로 명시적으로 LAZY로).

## 4) 생명주기 관리(cascade & orphanRemoval)

### 4-1. 개념

- **cascade**: 부모 동작을 자식으로 전파(PERSIST/REMOVE/MERGE/REFRESH/DETACH/ALL).
- **orphanRemoval = true**: 관계 끊긴 **고아 자식 자동 DELETE**.
- **원칙**: **애그리거트 내부**, **공유되지 않는 자식**에만 적용.
- **혼동 금지**: JPA `cascade` ≠ DB `ON DELETE CASCADE` (일반적으로 **둘 중 하나만** 채택).

### 4-2. 권장/비권장

- ✅ **권장**: `Order -> OrderItem`, `Order -> Delivery` 처럼 **부모에 종속**되고 **독립 사용하지 않는 자식**.
- ❌ **비권장**: `@ManyToOne(자식→부모)`에 cascade, `Member/Product/Category` 처럼 **여러 곳에서 공유되는 엔티티**.

### 4-3. persist/remove의 의미

- `persist(e)`: 새 엔티티를 **영속성 컨텍스트에 등록**(보통 flush/commit 시 INSERT).
- `remove(e)`: **삭제 예약**(flush/commit 시 DELETE). 관계만 끊고 삭제하지 않으려면 `orphanRemoval` 사용하지 말 것.

## 5) 성능 & 운영 가이드

### 5-1. 조회 전략

- **기본 LAZY**. 필요할 때만 **명시적 로딩**:
    - JPQL **fetch join**
    - `@EntityGraph(attributePaths = { ... })`
    - **배치 페치**: `hibernate.default_batch_fetch_size` 설정(예: 100~200)
- **주의**: 컬렉션 fetch join + **페이징 금지**(카디널리티 폭발). 대안: 배치 페치/두 단계 조회.

### 5-2. API 계층화

- 엔티티를 API로 직접 노출하지 말고 **DTO 변환**. 무한루프/LAZY 예외 방지, 스키마 안정성 ↑.
- 조회 전용은 **리포지토리→쿼리 서비스→DTO**로 분리(CQRS Lite 구조와 궁합).

### 5-3. 트랜잭션/컨텍스트 범위

- 서비스 계층에서 트랜잭션을 짧고 명확하게.
- OSIV(영속성 컨텍스트의 뷰까지 확장) 기본 OFF 권장(서비스 내에서 모든 로딩을 끝내고 DTO로 반환).

### 5-4. 기타 팁

- **쓰기 지연 최적화**: 벌크 저장/삭제 시 플러시 타이밍을 조절.
- **락/동시성**: 비즈니스 요구에 맞춰 낙관/비관 락 선택.
- **테스트**: 데이터 슬라이스(`@DataJpaTest`) + 통합테스트 조합.

## 7) 안티패턴 & 위험 구간

- **1:N 단방향의 남용**: 추가 UPDATE/복잡도 상승. 가급적 N:1 양방향으로.
- **@ManyToMany 실무 사용**: 제약/속성 확장 어려움 → **연결 엔티티** 사용.
- **연관 필드를 포함한 `toString()/equals()/hashCode()`**: 순환참조/LAZY 폭탄.
- **컬렉션 fetch join + 페이징**: 결과 증폭/메모리 폭발.
- **공유 엔티티에 cascade/orphanRemoval**: 데이터 손실 위험.

## 8) 설정/코드 스니펫

### 8-1. 전역 배치 페치 예시 (application.yml)

```yml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 200
```

### 8-2. 양방향 편의 메서드 패턴

```java
@Entity
class Order {
  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
  private List<OrderItem> orderItems = new ArrayList<>();

  public void addOrderItem(OrderItem item){
    orderItems.add(item);
    item.setOrder(this);
  }
}
```

### 8-3. equals/hashCode 가이드(예)

```java
@Override
public boolean equals(Object o){
  if (this == o) return true;
  if (!(o instanceof Member)) return false;
  Member other = (Member) o;
  return id != null && id.equals(other.id); // 식별자 기반, 연관 필드 배제
}
@Override public int hashCode(){ return 31; } // 영속 전 안전
```

## 9) FAQ

**Q. 준영속 엔티티를 갱신하려면?**  
A. `merge()`가 새 영속 인스턴스에 상태를 복사한다(파라미터는 여전히 준영속). 가능하면 **식별자 조회→수정**이 더 명료.

**Q. flush는 언제 호출하나?**  
A. 주로 자동(트랜잭션 커밋/JPQL 실행 전). 쿼리 타이밍 제어가 필요할 때만 수동 호출.

**Q. DB의 ON DELETE CASCADE와 함께 써도 되나?**  
A. 중복 전파/예상치 못한 삭제 위험. 일반적으로 **택1**.
