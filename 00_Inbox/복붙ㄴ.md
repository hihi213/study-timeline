## 0) TL;DR (한 장 요약)

- **트랜잭션 경계 = 서비스 계층**
    - 쓰기/테스트는 `@Transactional` **필수**, 읽기는 `readOnly = true`.
- **CQRS lite**
    - **커맨드(쓰기)**: **ID만 반환**(엔티티 반환 금지).
    - **쿼리(읽기)**: 전용 DTO 경로.
- **Dirty Checking**
    - 영속 엔티티의 필드만 바꾸면 **커밋 시 자동 UPDATE** → `save()` 불필요.
- **연관관계 주인 규칙**
    - **FK 가진 쪽 = 주인(owner)**, 반대편은 `mappedBy`(조회용). **편의 메서드**로 양쪽 동기화.
- **로딩 전략**
    - 전부 **LAZY 기본화**, N+1은 **fetch join(ToOne만) / @EntityGraph / BatchSize**.
- **Enum = STRING**, **ORDINAL 금지**.
- **값 타입은 불변**, **Setter 금지**, 의도가 드러나는 메서드로만 변경.
- **컬렉션은 필드에서 즉시 초기화**, 재할당 금지.
- **Cascade + orphanRemoval**은 **“프라이빗 + 수명 동일” 자식**에만.
- **ID 전략**: 대량 쓰기면 **SEQUENCE(+allocationSize)** 선호.
- **OSIV OFF 권장**: 서비스에서 끝내고 **DTO**로 반환.
- **equals/hashCode**: 연관 미포함, **식별자/불변 키만**.
- **DI**: **생성자 주입 + Lombok**(final 필드).

## 1) 트랜잭션 & 영속성 컨텍스트

### 1-1. `@Transactional` 규칙

- **쓰기/테스트**: 지연 쓰기·flush·1차 캐시 일관성은 **트랜잭션 내부**에서만 보장.
- **읽기 최적화**: `@Transactional(readOnly = true)` → 스냅샷/더티체킹 생략 등(벤더 차).
- **어노테이션 선택**: `org.springframework.transaction.annotation.Transactional` 사용.
- **AOP 한계(매우 중요)**
    - `private/final` 메서드, **자기 호출(self-invocation)**에는 트랜잭션 미적용.
    - **서비스 public 메서드**에 선언, 공용 로직은 분리.

### 1-2. 상태/생명주기 요약

- **비영속(Transient)**: `new` 만 한 상태.
- **영속(Managed)**: 같은 트랜잭션의 영속성 컨텍스트가 관리.
- **준영속(Detached)**: 트랜잭션 종료 등으로 관리 해제.
- **삭제(Removed)**: 삭제 예약.
- 트랜잭션 종료 = **flush → commit → close**.

### 1-3. Dirty Checking & `save()` 기준

- **Dirty Checking 조건**: (1) 현재 컨텍스트의 **영속 엔티티**, (2) **트랜잭션 안** 변경, (3) **flush 시점** 스냅샷 비교.
- **`save()` 불필요**: DB에서 조회한 영속 엔티티 수정만 했다면 자동 반영.
- **`save()/merge()` 필요한 경우**
    - 신규 엔티티 최초 저장(**persist**).
    - **준영속(detached)** 변경 반영: **merge** 또는 **재조회 후 변경**.
- **주의**: `readOnly = true`에선 업데이트가 **안 나갈 수 있음**(벤더 차).

```java
@Transactional
public void cancelOrder(Long id) {
    Order o = orderRepo.findById(id).orElseThrow();
    o.cancel();             // 상태만 변경
    // save() 불필요 — 커밋 시 UPDATE
}
```

### 1-4. 운영 팁

- **벌크 JPQL(update/delete)**: 1차 캐시 무시 → **실행 후 `clear()` 필수**.
- **동시성**: 민감 구간은 `@Version`(낙관적 락) 검토.
- **OSIV**: ON은 편하지만 계층 침식 위험 → **OFF 권장**(서비스에서 모두 로딩 후 DTO 반환).

## 2) 연관관계 매핑 원칙

### 2-1. Owner / Inverse

- **Owner(주인)** = **FK 가진 쪽**(DB 갱신 기준).
- **Inverse(거울)** = `mappedBy`(조회 전용, 여기만 바꿔선 DB 안 변함).
- 규칙: **“FK 있는 곳을 주인으로.”**

### 2-2. 안전한 기본 패턴

- **N:1 양방향(표준)**
    - N측(자식): `@ManyToOne(fetch = LAZY) @JoinColumn(...)` **← 주인**
    - 1측(부모): `@OneToMany(mappedBy = "...")` **← 거울(컬렉션 뷰)**
- **1:1**: 의존/자식이 주인인 경우 흔함. 필요 시 `@MapsId`로 **공유 PK**.
- **N:N**: 학습용만. 실무는 **연결 엔티티**로 분해(N:1 + 1:N).
- **1:N 단방향**보다 **N:1 양방향**이 관리 용이.

### 2-3. 양방향 편의 메서드(주인 갱신 동반)

```java
public void addOrderItem(OrderItem oi) {
  orderItems.add(oi); // 컬렉션(거울)
  oi.setOrder(this);  // ★ 주인(FK) 갱신
}
public void setDelivery(Delivery d) {
  this.delivery = d;
  d.setOrder(this);
}
```

### 2-4. 1:1 FK 위치 가이드

- **더 자주 접근하는 테이블**에 FK 두기.
    - 예) Delivery보다 Order 접근 빈도 ↑ → **Order.delivery_id**.

## 3) 로딩 전략 & N+1 대응

### 3-1. 기본 로딩

- `@ManyToOne`/`@OneToOne`: 기본 EAGER → **LAZY로 명시 변경 권장**.
- `@OneToMany`/`@ManyToMany`: 기본 LAZY.

### 3-2. N+1 회피 3종

1. **fetch join (JPQL)**
    
    - **컬렉션 fetch join + 페이징 금지**(중복행·메모리 페이징).
    - **ToOne만 fetch join**하면 페이징 안전.

```sql
select o from Order o
  join fetch o.member
  join fetch o.delivery
where o.status = :status
```

2. **`@EntityGraph`**

```java
@EntityGraph(attributePaths = {"member","delivery"})
List<Order> findByStatus(OrderStatus s);
```

3. **배치 페치** (`@BatchSize` / `default_batch_fetch_size`)

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 200
```

### 3-3. 컬렉션 + 페이징 안전 패턴(두 단계)

```java
// 1) 페이지 대상의 PK만 추출
Page<Long> ids = orderRepo.findIdsByStatus(s, pageable);

// 2) IN 조회 + ToOne은 fetch join, 컬렉션은 배치 페치
List<Order> orders = orderRepo.findWithMemberDeliveryByIds(ids.getContent());
```

## 4) Aggregate 쓰기/삭제 규칙 (Cascade & 고아)

### 4-1. 언제 `cascade = ALL`, `orphanRemoval = true`?

- **프라이빗 오너(Private Owner)**: 자식이 **그 부모에서만** 참조.
- **수명주기 동일**: 부모 생성/삭제 시 자식도 항상 함께.
- 위 두 조건이면 보통 `cascade = ALL` + 필요 시 `orphanRemoval = true`.

> 체크리스트
>
> -  자식이 부모 **전용**인가?
>     
> -  부모와 **항상 함께** 생성/삭제되는가?
>     
> -  부모 컬렉션에서 빠지면 **삭제가 규칙**인가? → `orphanRemoval = true`
>     
> -  자식을 다른 곳에서 **재사용/독립 저장**하나? → **cascade 금지**(별도 repo)
>     

### 4-2. 피해야 할 경우

- 자식을 **여러 애그리거트에서 공유**(예: Member, Product).
- 대형 그래프 삭제 전파의 락/성능 리스크.
- `@ManyToOne`에 무지성 cascade(부모까지 의도치 않게 persist/remove).

### 4-3. 전파의 의미 & 오해 방지

- **JPA 전파**는 **DB의 ON DELETE CASCADE와 다름**(연산 전파일 뿐).
- **컬렉션에서 제거 ≠ DB 삭제** → `orphanRemoval = true`일 때만 고아 자동 삭제.

### 4-4. 생성 지점 단일화 + 전파 활용 패턴

```java
@Transactional
public Long placeOrder(Member m, Delivery d, List<OrderItem> items) {
  Order o = Order.placeOrder(clock, m, d, items); // 정적 팩토리: 검증/초기화/양방향 동기화
  orderRepository.save(o);                        // cascade로 자식까지 persist
  return o.getId();
}
```

## 5) 매핑 전략 & 스키마 팁

- **기본은 `@JoinColumn(FK)`**: 단순·빠름·제약 명확.
- **`@JoinTable`**: 1:N 단방향 강제, 레거시 수용 등 특수.
- **연결 엔티티**: 실무 N:N 정석(메타필드/감사/UNIQUE/인덱스 유연성).

**네이밍/제약 권장**

- 스키마/컬럼: **소문자 + 스네이크**(예: `member_point`).
- FK 컬럼: `member_id`, `order_id` 식.
- 연결 테이블: `parent_child`, `category_item`.
- **1:1**: FK 컬럼 **UNIQUE**(또는 공유 PK).
- 인덱스: FK 컬럼, 연결 테이블은 `(fk1, fk2)` **복합 인덱스**.

**FK를 꼭 걸어야 하나?**

- **정합성 최우선(금융/정산)**: **FK 걸기**.
- **고트래픽/가용성 우선**: FK 없이 인덱스로 운영 + **애플리케이션/배치/모니터링 보완**(조직 SLA에 따름).
- **유니크 제약**으로 최종 방어(등록 경쟁 조건 등).

## 6) ID 전략 & 쓰기 흐름

- **IDENTITY**: 키 생성을 위해 **즉시 INSERT**(조기 flush) → **배치 쓰기 불리**.
- **SEQUENCE**(+ `allocationSize` 튜닝) 권장: INSERT **뭉치기** 유리.
- 연관 저장은 보통 **부모만 persist**(cascade 전파) → INSERT 순서 안정화.

> 메모: persist 순간 JPA는 캐시 키(PK)가 필요 → 전략에 따라 **즉시 INSERT(IDENTITY)** 또는 **키 선점(SEQUENCE/TABLE)**.

## 7) 엔티티 설계 원칙

### 7-1. Setter 금지 & 의도 드러내기

- Setter 남발 금지. **의도 메서드**로 변경(`order.cancel()`, `orderItem.changeQuantity(...)`).
- 변경은 항상 **트랜잭션 내부**에서.

### 7-2. 값 타입은 불변

- 생성자/정적 팩토리로만 초기화, 변경은 **교체**.
- 사이드이펙트 감소, 동시성 안전성 ↑.

### 7-3. 기본 생성자

- **JPA 스펙**: 엔티티/임베디드에 **기본 생성자 `public` 또는 `protected`** 필요 → **`protected` 권장**.

### 7-4. 컬렉션 초기화 & 재할당 금지

```java
private final List<OrderItem> orderItems = new ArrayList<>();
```

- `null` 안전 + 하이버네이트 래핑 충돌 방지. 이후 **재할당 금지**.

### 7-5. equals/hashCode

- **연관 포함 금지**, **식별자(또는 불변 비즈니스 키)만 포함**.
- Lombok: `@EqualsAndHashCode(onlyExplicitlyIncluded = true)` 등 명시.

### 7-6. 의존성 주입(DI)

- **생성자 주입 + Lombok** 권장: `final` 필드, 불변성 ↑, 테스트 용이.

### 7-7. 엔티티에 비즈니스 로직(DDD 스타일)

- 데이터와 행위를 **한 곳**에: 엔티티가 스스로 상태 변경. 서비스는 **조율자**.

### 7-8. 생성 메서드(정적 팩토리)

- **생성·초기화 규칙 단일화**: 규칙 변경 시 이 메서드만 수정.
- 다른 곳의 `new` 남용 방지 → `@NoArgsConstructor(access = PROTECTED)`로 제어.

```yaml
spring:

Order o = new Order();

int updated = em.createQuery("update Product p set p.price = p.price * 1.1")

```

## 13) 빠른 의사결정 트리

1. **관계 수**: N:1 / 1:N / 1:1 / N:N ?
2. **자식 테이블에 FK 가능?**
    
    - 가능: **`@JoinColumn` 기본**
    - 불가: **`@JoinTable`/연결 엔티티**
        
3. **탐색 방향**: 단방향으로 충분?
    
    - 반대 탐색도 잦으면 **양방향 + 주인 하나**
        
4. **메타필드·감사 필요?** → **연결 엔티티**
5. **성능/페이징**: 컬렉션 fetch join은 **페이징 금지** → **두 단계 조회/배치 페치**

## 14) 최종 체크리스트 (실무용)

-  커맨드 핸들러는 **ID만 반환**(엔티티 반환 금지)
-  **`@Transactional` 경계 안**에서만 쓰기/테스트
-  **FK 있는 쪽 = 주인**, **편의 메서드**로 양쪽 동기화
-  **LAZY 기본화**, N+1은 **fetch join/EntityGraph/BatchSize**
-  **Enum = STRING**, ORDINAL 금지
-  **Setter 금지**, 의도 메서드로 변경
-  **값 타입 불변**, 교체로 변경
-  **컬렉션 즉시 초기화**, 재할당 금지
-  1:1 FK는 **접근 빈도 높은 곳**에
-  FK 사용 여부는 **정합성 vs 가용성** 요구로 결정
-  **Cascade는 ‘프라이빗 + 수명 동일’**에만 (`orphanRemoval` 규칙 반영)
-  생성은 **정적 팩토리**로 단일화 → `save(root)` 한 번 + Cascade
-  **영속 엔티티 수정 = Dirty Checking**, `save()` 호출 금지
-  **신규/병합만 `save()`**, 벌크 후 `clear()`
-  **OSIV OFF**, 컨트롤러 이전에 DTO로 완결
-  **equals/hashCode**는 연관 제외, 식별자/불변 키만
-  **DI**는 생성자 주입 + Lombok(final)

## 15) 부록: 실용 설계 메모

- **단순 조회의 서비스 강제 통과에 집착하지 말자**:
    - 트랜잭션/정책이 개입되지 않는 **아주 단순한 읽기**는,  
        별도 **쿼리 서비스**(readOnly) 또는 리포지토리 직접 주입으로 **실용성**을 택할 수 있음.
        
    - 단, **계층 규율과 일관성**이 우선. 팀 규칙에 맞춰 선택.
