## 📝 결론 및 요약

데이터베이스 활용 능력은 **메모리 상의 데이터 이동(Fetch)**을 얼마나 효율적으로 통제하느냐에 달려 있습니다.

> [!note]- 데이터베이스 작동 메커니즘의 핵심
>
> 1. **역할의 분리 (Role Definition)**
>     
>     - **User:** SQL로 결과물을 정의하고, 함수/프로시저로 비즈니스 로직을 구현합니다.
>         
>     - **DBMS의 옵티마이저:** 최적의 접근 경로(Plan)와 실행 방법(Method)을 결정합니다.
>         
> 2. **사용자의 로직 구현 (Implementation)**
>     
>     - **함수:** 단순 연산 및 읽기(Read) 로직을 담당하며, Fetch Loop 내부에서 동작합니다.
>         
>     - **프로시저:** 상태 변경(Write) 및 트랜잭션 제어를 담당하며, Fetch Loop 외부에서 전체 흐름을 관장합니다.
>         
> 3. **실행의 최적화 (Optimization)**
>     
>     - `WHERE` 절의 좌변을 보존하여 인덱스 활용도를 높입니다.
>         
>     - 불필요한 I/O를 줄여 메모리 효율을 극대화하는 것이 튜닝의 본질입니다.
>


# 📖 DBMS 심층 분석: 엔진 메커니즘과 SQL 최적화

데이터베이스 성능 최적화는 엔진이 데이터를 **물리적으로 메모리에 적재(Physical)**하고, **논리적 순서로 처리(Logical)**하며, **구조적 제약(Constraint)**을 해결하는 과정을 이해하는 것에서 시작됩니다.

---

## 1. [Physical] 물리적 한계와 버퍼 캐시

DBMS 튜닝의 핵심 목표는 디스크 I/O 최소화 및 메모리 히트율(Hit Ratio) 극대화입니다. 이는 하드웨어의 물리적 특성 차이에서 기인합니다.

### 🛑 하드웨어 속도의 간극

- **속도 차이:** CPU는 나노초($ns$) 단위로 연산하나, 디스크는 물리적 구동(HDD) 또는 셀 접근(SSD)으로 인해 밀리초($ms$) 단위로 동작합니다.
- **I/O 단위:** CPU는 바이트(Byte) 단위 처리를 수행하나, 디스크는 블록(Block, 통상 $8KB \sim$) 단위로 데이터를 전송합니다.
    

### ⚙️ 버퍼 캐시(Buffer Cache)의 역할

속도 간극을 해결하기 위해 DBMS는 메모리 영역인 버퍼 캐시를 활용합니다.

1. **적재 (Block I/O):** 디스크의 데이터 블록을 메모리(버퍼 캐시)로 복사합니다.
2. **연산 (Memory Access):** CPU는 오직 버퍼 캐시에 적재된 데이터만 읽거나 수정합니다.
3. **기록 (Dirty Write):** 변경 사항은 즉시 디스크에 쓰지 않고, 체크포인트 시점에 일괄 기록합니다.
    

> [!TIP] SQL은 디스크가 아닌 메모리를 조작하는 언어입니다.
>
>  모든 성능은 "얼마나 적은 블록을 메모리로 호출하여 효율적으로 재사용하는가"에 의해 결정됩니다.

---

## 2. [Logical] SQL 실행과 FETCH 메커니즘

물리적 적재 후, 논리적으로 데이터를 선별하는 **FETCH** 과정이 수행됩니다.

### 🔄 FETCH와 커서(Cursor)

DBMS는 데이터를 한 번에 처리하지 않고, 내부 포인터인 **커서(Cursor)**를 이동시키며 한 행(Row)씩 읽어들이는 루프(Loop) 방식을 사용합니다.

1. **커서 이동:** 포인터를 다음 행으로 이동.
2. **로드 (Load):** 해당 행의 데이터 획득.
3. **처리 (Process):** 필터링 및 연산 수행. (성능 병목의 주요 지점)
    

### 📋 옵티마이저의 실행 순서

개발자가 작성한 구문 순서와 달리, 옵티마이저는 **데이터 확보 및 필터링**을 우선하는 순서로 실행 계획을 수립합니다.

|**순서**|**절 (Clause)**|**역할 및 최적화 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업 대상 테이블을 메모리에 적재|
|**2**|**WHERE**|**(필터링)** 조건에 부합하지 않는 행 제거 (데이터 양 감소)|
|**3**|**GROUP BY**|**(집계)** 잔여 데이터를 기준별로 그룹핑|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 조건 선별|
|**5**|**SELECT**|**(표현)** 최종 결과 출력 / **함수 실행 시점**|
|**6**|**ORDER BY**|**(정렬)** 결과 데이터의 순서 나열|

> **핵심:** `WHERE` 절에서 데이터 양을 최소화해야 이후 단계(`SELECT` 등)에서 수행되는 연산 부하가 감소합니다.

## 3. [Constraint] 선행적 읽기 (Read before Write)

데이터베이스의 모든 변경 작업(`UPDATE`, `DELETE`)은 대상을 찾는 **읽기(Fetch)** 과정이 반드시 선행되어야 합니다.

### ⚙️ DML의 내부 동작 단계

예시: `UPDATE users SET salary = salary * 1.1 WHERE id = 100` 수행 시

1. **FETCH (읽기):** 인덱스 또는 전체 스캔을 통해 `id = 100`인 블록을 메모리에 적재합니다.
2. **LOCK (잠금):** 해당 행(Row)에 대해 트랜잭션 잠금을 획득합니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 Redo Log를 기록합니다.
    

### 🔍 SQL 내 함수 실행 시점의 구분

- **`WHERE` 절의 함수:** 대상을 식별하기 위한 **필터(Filter)** 역할. (Read 단계)
- **`SET` 절의 함수:** 값을 변경하기 위한 **계산(Calculation)** 역할. (Write 단계)
    

---

## 4. [Roles] 개발자와 시스템의 역할 분담

### 👤 User (개발자): 정의(Definition)

개발자는 데이터의 결과물(What)과 비즈니스 로직을 정의합니다.

- **SQL:** 요구하는 데이터 결과 집합을 선언.
- **함수 (Function):** SQL의 FETCH 루프 **과정 중**에 개입하여 값을 계산.
- **프로시저 (Procedure):** 독자적인 **FETCH(조회) $\rightarrow$ LOGIC(판단) $\rightarrow$ DML(처리)** 과정을 수행하여 트랜잭션을 완결.
    

### 🤖 System (옵티마이저): 실행(Execution)

옵티마이저는 정의된 로직을 분석하여 최적의 경로(Plan)를 수립합니다.

- **Target (대상):**
    - **SQL 문장:** 최적화의 기본 단위.
    - **프로시저:** 생성 시점에 내부 SQL에 대한 실행 계획을 미리 수립(Pre-compile)하여 재사용.
    - **함수:** 행(Row)마다 CPU 비용을 소모하는 연산 작업으로 간주.
- **Tools (도구):** 인덱스(Index), 통계 정보(Statistics), 시스템 지표(System Metrics).
    

---

## 5. [Actors] 실행 주체: 함수 vs 프로시저

데이터 정합성과 '할로윈 문제(Halloween Problem)' 방지를 위해 실행 객체의 역할은 엄격히 구분됩니다.

> **할로윈 문제:** 갱신 작업 중, 수정된 데이터가 인덱스 순서 변경으로 인해 다시 조회되어 중복 갱신되는 현상.

| **구분**     | **함수 (Function)**                                                        | **프로시저 (Procedure)**                                    |
| ---------- | ------------------------------------------------------------------------ | ------------------------------------------------------- |
| **실행 위치**  | SQL 구문 내부 (Fetch Loop **안**)                                             | 애플리케이션/배치 호출 (Fetch Loop **밖**)                         |
| **실행 빈도**  | SQL의 **Fetch Loop에 종속됨**<br>(Loop 돌 때마다 반복 실행)<br>조회되는 **행(Row) 수만큼** 반복 | **자체적인 Fetch Loop 보유**<br>(내부에서 `SELECT INTO`로 조회 후 판단) |
| **데이터 변경** | **불가능** (Read Only 권장)                                                   | **가능** (Transaction Control)                            |
| **핵심 역할**  | 값의 연산 및 변환                                                               | 비즈니스 로직 및 트랜잭션 총괄                                       |
> **핵심 차이:** 함수는 "데이터를 가져오는 과정(Fetch)"의 부품으로 쓰이고, 프로시저는 "데이터를 가져와서 처리하는(Fetch & Do)" 전체 공장 역할을 합니다.
---

## 6. [Optimization] 최적화 핵심: 인덱스 활용

최적화의 핵심은 인덱스를 활용하여 Fetch 대상을 줄이는 것입니다. 이를 위해 **좌변(컬럼) 가공 금지** 원칙을 준수해야 합니다.

### ⚡ 인덱스 튜닝 원칙

인덱스는 컬럼의 원본 값을 기준으로 정렬되어 있습니다. 컬럼을 함수로 감싸거나 연산할 경우, 정렬 순서가 불일치하여 인덱스 사용이 불가능합니다.

#### ❌ Bad Case (좌변 가공: 인덱스 불가)

```SQL
-- 엔진: 데이터 가공 후 비교가 필요하므로 전체 스캔(Full Scan) 수행
WHERE YEAR(date_col) = '2024'
```

#### ✅ Good Case (우변 가공: 인덱스 활용)

```SQL
-- 엔진: 인덱스 정렬 순서를 활용하여 범위 검색(Range Scan) 수행
WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
```
