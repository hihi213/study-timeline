# 📖 DBMS 심층 분석: 메커니즘, 역할, 그리고 최적화

데이터베이스를 잘 다루기 위해서는 단순히 SQL 문법을 아는 것을 넘어, 엔진이 데이터를 어떻게 **'퍼올리고(Fetch)'**, 어떻게 **'처리(Process)'**하는지 그 내부 흐름을 이해해야 합니다.

이 글에서는 DBMS의 물리적/논리적 작동 원리를 바탕으로 함수와 프로시저의 역할을 명확히 구분하고, 이를 통한 성능 최적화 전략까지 하나의 흐름으로 정리합니다.

---

## 1. 물리적 기반: DBMS는 어떻게 움직이는가? (The Engine)

### **"디스크에 있는 데이터를 어떻게 CPU로 가져올 것인가?"**

1. **속도의 차이 (Speed Gap):** 디스크는 CPU에 비해 너무 느립니다.
2. **단위의 차이 (Unit Gap):** CPU는 바이트(Byte) 단위의 정밀한 데이터를 원하지만, 디스크는 블록(Block) 단위의 뭉텅이 데이터만 제공합니다.

### CPU는 디스크를 직접 연산하지 않는다. 메모리.

이 간극을 메우기 위해 **버퍼 캐시(Buffer Cache)**가 존재합니다.
- **Block I/O (적재):** 디스크의 데이터 블록을 통째로 메모리(Buffer Cache)로 복사합니다.
- **Memory Access (연산):** CPU는 오직 메모리에 올라와 있는 데이터만 읽거나 수정합니다.
- **Flush (기록):** 변경된 데이터는 즉시 디스크에 쓰지 않고, 나중에 일괄 기록(Dirty Write)합니다.

> [!tip] **핵심 원리:**
>
> **SQL의 대상:** 우리가 작성한 SQL은 디스크가 아닌 **메모리(Buffer Cache)**를 조작하는 명령어입니다.
>
> **성능의 척도:** 결국 "누가 더 적은 블록을 메모리로 불러와서 효율적으로 쓰느냐"가 성능을 결정합니다.


---

## 2. 핵심 동작: FETCH와 커서 (The Action)

데이터가 메모리(버퍼 캐시)에 올라왔다면, 이제 사용자가 원하는 데이터를 골라내는 작업이 필요합니다. 이 과정을 **FETCH**라고 합니다.

### 🔍 FETCH란 무엇인가?

DBMS가 `WHERE` 조건에 맞는 데이터를 찾아서 사용자에게 보여줄 때, 한 번에 '뿅' 하고 가져오는 것이 아닙니다. 내부적으로는 **커서(포인터)**를 이동시키며 한 줄(Row)씩 읽어들이는 반복 과정(Loop)이 일어납니다.

> [!note]- **🔄 The FETCH Cycle:**
>
> 1. 커서를 다음 행으로 이동
> 2. 행을 읽음 (Load)
> 3. **[⚡ 이 시점]** $\leftarrow$ **이 찰나의 순간에 무엇을 하느냐가 핵심**
> 4. 다음 행으로 이동 (반복)

이 **FETCH Loop의 안쪽**에 있느냐, **바깥쪽**에 있느냐에 따라 **함수(Function)** 와 **프로시저(Procedure)** 의 운명이 결정됩니다.

---

## 3. 실행의 주체: 함수 vs 프로시저 (The Actors)

FETCH 메커니즘 위에서 작동하는 두 가지 핵심 객체, 함수와 프로시저
"읽으면서 동시에 쓰는 것"은 데이터의 위치 변경을 유발하여, 커서가 이미 읽은 행을 또 읽거나 건너뛰는 **할로윈 문제**를 발생시킵니다.
이를 방지하기 위해 DB 개발 로직은 읽기와 쓰기 로직으로 엄격히 분리됩니다.

### A. 함수 (Function): 연산과 조회의 보조

함수는 **FETCH 과정의 한복판(Loop 내부)**안에 끼어있습니다.

- **작동 위치:** SQL 문장(`SELECT`, `WHERE`) 안에 포함되어, 엔진이 행(Row)을 하나 건져 올릴 때마다 실행됩니다. (100만 건 Fetch $\rightarrow$ 100만 번 실행)
- **제약 (Read Only):** 패치중 쓰게 된다면 데이터의 위치 변경을 유발하여, 커서가 이미 읽은 행을 또 읽거나 건너뛰는 **할로윈 문제**를 발생시킵니다.
- **결론:** 함수는 Fetch의 **'부속품'** 이므로, **데이터의 상태를 변경할 수 없습니다.** 오직 값을 가공해서 리턴하는 것만 허용됩니다.

|**핵심 역할**|값의 계산 및 변환 (**Read Only**)|비즈니스 흐름 제어 (**Transaction Control**)|

## 4. 논리적 실행과 최적화 (Optimization)

이제 엔진의 원리와 실행 주체의 역할을 알았으니, 이를 바탕으로 성능을 최적화하는 방법을 알아보겠습니다.

### A. 실행 순서: 순서가 제약을 만든다

옵티마이저는 개발자가 SQL을 작성한 순서가 아닌, **"대상을 먼저 메모리로 가져오는 순서"**로 계획을 짭니다.

|**순서**|**절 (Clause)**|**설명 및 튜닝 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업할 테이블을 메모리로 가져올 준비|
|**2**|**WHERE**|**(필터링)** 조건에 안 맞는 행을 버림. **성능의 90% 결정**|
|**3**|**GROUP BY**|**(집계)** 남은 데이터를 기준에 따라 묶음|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 조건 선별|
|**5**|**SELECT**|**(표현)** 최종 결과 출력 / **함수 실행 시점**|
|**6**|**ORDER BY**|**(정렬)** 순서 나열|

> **💡 Insight:** `WHERE` 절에서 데이터 양을 획기적으로 줄여야, 이후 `SELECT` 절에서 실행되는 **함수의 실행 횟수**도 줄어듭니다.

### B. 필연적 제약: 읽어야 쓸 수 있다 (Read before Write)

데이터를 수정(UPDATE/DELETE)하고 싶어도, 먼저 대상을 메모리로 가져오는 **읽기(Fetch)**가 선행되어야 합니다.

1. **FETCH:** `FROM` $\rightarrow$ `WHERE`을 수행하여 대상을 찾아 메모리로 로딩.
2. **LOCK:** 찾은 행을 잡음.
3. **WRITE:** 메모리 상의 데이터를 변경하고 로그 기록.
    

쓰기 성능이 느리다면, 역설적으로 **"대상을 빨리 찾는 읽기 튜닝(인덱스 최적화)"**이 선행되어야 합니다.

### C. 핵심 튜닝: 인덱스를 태워라 (좌변 가공 금지)

옵티마이저가 가장 먼저 수행하는 `WHERE` 절에서 인덱스를 타게 하는 것이 튜닝의 시작과 끝입니다. 인덱스는 **컬럼의 원본 값**을 기준으로 정렬되어 있습니다.

#### ❌ Bad Case (좌변 가공: 인덱스 미사용)

SQL

```Java
WHERE YEAR(date_col) = '2024'
```

- **문제:** 컬럼(`date_col`)을 함수로 가공하면 정렬이 깨집니다.
- **결과:** 인덱스를 포기하고 **Full Table Scan(전체 뒤지기)** 발생.
    

#### ✅ Good Case (우변 가공: 인덱스 사용)

SQL

```Java
WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
```

- **해결:** 컬럼은 그대로 두고, 비교할 값(우변)을 가공하여 **Range Scan** 유도.

## 📝 종합 결론 (Summary & Action Plan)

데이터베이스 성능과 안정성은 **"메모리 위에서의 데이터 이동(Fetch)"**을 얼마나 잘 이해하고 통제하느냐에 달려 있습니다.

> [!TIP] **Action Plan**
>
> 1. **역할 분리:** 단순 값 계산은 **함수**로, 트랜잭션(CUD) 관리는 **프로시저**로 명확히 나누십시오.
>     
> 2. **가공 금지:** `WHERE` 절의 컬럼(좌변)은 절대 건드리지 말고, 비교값(우변)을 맞추십시오.
>     
> 3. **양 줄이기:** `WHERE` 절에서 효율적인 인덱싱으로 데이터 양을 줄이는 것이, 이후 수행될 모든 부하(함수 실행, 정렬, I/O)를 줄이는 열쇠입니다.
>     

이 구조적 이해를 바탕으로 쿼리를 작성하면, 엔진이 가장 좋아하는(가장 빠른) 길을 안내할 수 있습니다.
