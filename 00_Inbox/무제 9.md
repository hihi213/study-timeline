# 📖 DBMS 심층 분석: 엔진의 원리부터 SQL 최적화까지

데이터베이스 성능 최적화는 단순히 쿼리를 짧게 줄이는 기술이 아닙니다. 엔진이 데이터를 **어떻게 메모리로 가져오고(Physical)**, **어떤 순서로 처리하며(Logical)**, 그 과정에서 **어떤 제약(Constraint)**이 발생하는지를 이해할 때 비로소 근본적인 튜닝이 가능합니다.

---

## 1. [Physical] 물리적 한계와 버퍼 캐시 (The Bottleneck)

DBMS 튜닝의 대전제는 **"디스크 I/O를 최소화하고, 메모리 히트율을 극대화하는 것"**입니다. 이는 하드웨어의 근본적인 속도 차이에서 때문입니다.

### 🛑 속도의 간극: CPU vs Disk

1. **속도 차이:** CPU는 나노초(ns) 단위로 동작하는 초고속 장치이지만, 디스크는 물리적인 회전(HDD)이나 셀 접근(SSD)이 필요하여 밀리초(ms) 단위로 매우 느립니다.
2. **단위 차이:** CPU는 바이트(Byte) 단위의 정밀한 처리를 원하지만, 디스크는 블록(Block, 보통 $8KB \sim$) 단위의 뭉텅이 데이터만 제공합니다.
    

### ⚙️ 해결책: 버퍼 캐시 (Buffer Cache)

이 간극을 메우기 위해 DBMS는 **버퍼 캐시**라는 메모리 공간을 둡니다.

- **적재 (Block I/O):** 디스크의 데이터 블록을 통째로 메모리에 복사합니다.
- **연산 (Memory Access):** CPU는 오직 메모리에 올라온 데이터만 읽거나 수정합니다.
- **기록 (Dirty Write):** 변경 사항은 즉시 디스크에 쓰지 않고, 나중에 일괄 기록합니다.
    

> [!TIP] SQL은 디스크가 아닌 '메모리'를 조작하는 명령어입니다.
>
> 성능은 결국 "누가 더 적은 블록을 메모리로 불러와서(I/O 감소), 효율적으로 재사용하느냐"에 달려 있습니다.

## 2. [Logical] SQL의 실행과 FETCH 메커니즘

물리적으로 메모리에 데이터가 올라왔다면, 논리적으로는 데이터를 골라내는 작업인 **FETCH**가 수행됩니다.

### 🔄 FETCH와 커서 (The Action)

DBMS가 데이터를 사용자에게 보여줄 때, 한 번에 가져오는 것이 아니라 내부적으로 **커서(포인터)** 를 한 줄(Row)씩 이동시키며 반복(Loop) 처리를 합니다.

1. **커서 이동:** 포인터를 다음 행(Row)으로 이동.
2. **로드 (Load):** 해당 행을 읽음.
3. **⚡ 처리:** **이 찰나의 순간(Fetch Loop 내부)에 무엇을 하느냐가 성능과 정합성을 결정합니다.**
    

### 📋 옵티마이저의 실행 순서

DBMS 엔진(옵티마이저)은 SQL작성 순서가 아닌 **데이터를 메모리로 가져오는 순서**로 실행 계획을 짭니다.

|**순서**|**절 (Clause)**|**역할 및 튜닝 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업할 테이블을 메모리에 올릴 준비|
|**2**|**WHERE**|**(필터링)** 조건에 안 맞는 행을 버림. **성능의 90%가 결정되는 곳**|
|**3**|**GROUP BY**|**(집계)** 남은 데이터를 기준별로 묶음|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 조건 선별|
|**5**|**SELECT**|**(표현)** 최종 결과 출력 / **함수가 실행되는 시점**|
|**6**|**ORDER BY**|**(정렬)** 결과를 순서대로 나열|
> **💡 Insight:** `WHERE` 절에서 데이터 양을 획기적으로 줄여야, 이후 `SELECT` 절에서 실행되는 **함수의 실행 횟수**도 줄어듭니다.

## 3. [Constraint] 제약에 따른 역할 분리: 함수 vs 프로시저
"데이터를 읽어야 쓸 수 있다(Read before Write)"
> **Insight:** 쓰기 성능이 느리다면, 역설적으로 **"대상을 빨리 찾는 읽기 튜닝(인덱스)"**이 선행되어야 합니다.

### 🚫 할로윈 문제 (Halloween Problem)

데이터를 **읽는 도중에(Fetch Loop 안에서)** 수정하면 어떻게 될까요? 수정된 데이터가 인덱스 순서상 뒤로 이동하여, 커서가 **이미 읽은 행을 또 읽거나 건너뛰는 현상**이 발생합니다. 이를 방지하기 위해 DBMS는 읽기와 쓰기 로직을 분리합니다.

### A. 함수 (Function): Fetch의 부속품

- **위치:** `SELECT`나 `WHERE` 절 내부 (Fetch Loop **안**)
- **실행 빈도:** 조회되는 **행(Row)의 수만큼** 반복 실행 (100만 건 조회 $\rightarrow$ 100만 번 실행)
- **제약:** Fetch 도중이므로 데이터 위치를 바꾸는 `INSERT`, `UPDATE` 불가.
- **역할:** 값을 가공하여 리턴하는 **Read Only 계산기**
    

### B. 프로시저 (Procedure): 트랜잭션의 지휘자

- **위치:** SQL문 외부, 애플리케이션 호출 (Fetch Loop **밖**)
- **실행 빈도:** 호출 시 **1회** 실행
- **특징:** Fetch가 끝난 후, 혹은 Fetch를 명령하는 입장이므로 `COMMIT`, `ROLLBACK` 등 제어 가능.
- **역할:** 비즈니스 로직(CRUD)을 총괄하는 **Control Tower**
    

|**구분**|**함수 (Function)**|**프로시저 (Procedure)**|
|---|---|---|
|**FETCH와의 관계**|**종속됨** (Loop 안에서 실행)|**명령함** (Loop 밖에서 제어)|
|**데이터 변경**|**불가능** (할로윈 문제 방지)|**가능** (트랜잭션 관리)|
|**핵심 역할**|단순 연산 및 변환|비즈니스 흐름 제어|

## 4. [Optimization] 성능 최적화의 핵심 전략

위의 원리들을 종합했을 때, 최적화의 핵심은 **"인덱스를 활용해 Fetch 대상을 줄이는 것"**으로 귀결됩니다.

### ⚡ 인덱스 튜닝: 좌변을 가공하지 말라

인덱스는 **컬럼의 원본 값**을 기준으로 정렬되어 있습니다. `WHERE` 절에서 컬럼(좌변)을 함수로 감싸면 정렬된 순서가 깨져 인덱스를 사용할 수 없습니다.

#### ❌ Bad Case (좌변 가공: 인덱스 불가)

```SQL
-- 엔진: "값을 연산해봐야 아니까, 미리 정렬된 인덱스는 쓸모가 없군. 전체를 뒤져라(Full Scan)."
WHERE YEAR(date_col) = '2024'
```

#### ✅ Good Case (우변 가공: 인덱스 활용)

```SQL
-- 엔진: "컬럼이 깨끗하군. 인덱스를 타고 범위 검색(Range Scan)으로 바로 찾아가자."
WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
```

## 5. 📝 종합 결론 (Action Plan)

데이터베이스를 잘 다룬다는 것은 **"메모리 위에서의 데이터 이동(Fetch)"**을 이해하고 통제한다는 뜻입니다.

> [!TIP] **Action Plan**
>
> 1. **역할 분리:** 단순 값 계산은 **함수**로, 데이터 변경 및 트랜잭션 관리는 **프로시저**로 명확히 나누십시오.
>     
> 2. **가공 금지:** `WHERE` 절의 컬럼(좌변)은 절대 건드리지 말고, 비교값(우변)을 맞추십시오.
>     
> 3. **양 줄이기:** 쿼리 튜닝의 시작과 끝은 `WHERE` 절에서 인덱스를 통해 **메모리에 올릴 데이터 블록 수를 줄이는 것**입니다.

===핵심을 선별해 추가 시작==

. 개발자와 데이터베이스의 역할분담

개발자는 하단을 정의해 전달한다
#### SQL (요구사항 정의)

- **역할:** 데이터의 추출, 조작, 제어에 대한 최종 **결과물(Requirement)** 을 기술합니다.
- **특징:** 구체적인 탐색 경로(How)는 기술하지 않는 선언형 언어입니다.

#### 함수와 프로시저 (비즈니스 로직 정의)

SQL만으로 표현하기 힘든 절차적 흐름이나 복잡한 연산을 정의합니다.


1. 개발자가 할것: 무엇을 받을지 SQL를 작성하고, 함수와 프로시저로 비즈니스 로직을 구현
    - 사용자가 작성한 **SQL은** 받을 최종 데이터을, **함수와 프로시저는** 구체적인 비즈니스 로직을 구현합니다.
    - **DBMS의 옵티마이저**는 이를 수행하기 위한 최적의 **방법**(실행순서,접근경로)을 결정하여 데이터 처리를 실행합니다.  
2. **로직의 구현 (User):**  
    사용자는 **연산 중심의 읽기(Read)** 로직은 **함수**로,  
    **상태 변경 및 트랜잭션 제어(Write)** 로직은 **프로시저**로 구분하여 구현합니다  
3. **실행의 최적화 (System):**  
    옵티마이저는 전달받은 로직(Target)을 분석하고, 인덱스 등(Tool)을 활용하여 비용이 가장 낮은 경로(Plan)를 수립해 실행합니다.

> SQL은 구체적인 탐색 경로(How)는 기술하지 않는 선언형 언어이다.
> 옵티마이저는 최종 결과물만 정의한 SQL를 토대로 탐색경로를 계획하고 수행한다.


1. **FETCH (읽기):** `FROM` $\rightarrow$ `WHERE`을 수행하여 대상을 찾아 **메모리로 로딩**합니다. (인덱스가 없으면 전체를 뒤져야 합니다.)
2. **LOCK (잠금):** 찾은 행(Row)을 다른 트랜잭션이 건드리지 못하게 잡습니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 로그(Redo/Undo)를 남깁니다.

> [!tip] **💡 Insight:**
> - 단순 연산은 **함수**로 처리하되, `WHERE` 절 사용 시 인덱스 방해를 주의하십시오.
> - 데이터 변경과 트랜잭션 관리는 반드시 **프로시저** 영역에서 수행해야 합니다.

> [!note] **구조적 이해를 통한 최적화**
>
> 1. **Mechanics:** DB는 디스크가 아닌 **메모리**에서 일합니다. `UPDATE`가 느리다면, 먼저 대상을 메모리로 퍼올리는 **읽기(Fetch)** 과정부터 튜닝하십시오.
>     
> 2. **Flow:** SQL은 `FROM` $\rightarrow$ `WHERE` $\rightarrow$ `SELECT` 순입니다. 초반(`WHERE`)에 데이터를 얼마나 잘라내느냐가 승부처입니다.
>     

> [!tip] **Action Plan**
>
> 1. **컬럼은 신성불가침:** `WHERE` 절의 컬럼을 함수로 감싸지 마십시오. (우변을 가공할 것)
>     
> 2. **역할 분리:** 값의 계산은 **함수**, 트랜잭션과 데이터 변경은 **프로시저**로 명확히 나누십시오.
>

1. **FROM / JOIN:** 대상 테이블을 참조하고 데이터 집합을 생성합니다.
2. **WHERE:** 조건에 맞지 않는 행(Row)을 필터링합니다.
3. **GROUP BY:** 데이터를 그룹화합니다.
4. **HAVING:** 그룹화된 데이터에 조건을 적용합니다.
5. **SELECT:** 결과로 출력할 컬럼을 선택하거나 계산합니다.
6. **ORDER BY:** 최종 결과를 정렬합니다.
> **핵심:** 옵티마이저는 따라 데이터를 단계별로 걸러내며 비용을 계산합니다.


| **구분**       | **함수 (Function)**              | **프로시저 (Procedure)**     |
| ------------ | ------------------------------ | ------------------------ |
| **주 목적**     | 값의 계산 및 반환                     | 비즈니스 로직 수행 및 트랜잭션 관리     |
| **SQL 내 위치** | SELECT, WHERE, HAVING 등 표현식 위치 | 독립적으로 실행 (SQL 내부 포함 불가)  |
| **실행 엔진**    | 쿼리 실행 도중 행(Row) 단위로 호출         | 절차적 엔진이 SQL 엔진을 순차적으로 호출 |
| **옵티마이저**    | 인덱스 사용을 방해할 수 있음 (특히 WHERE절)   | 내부의 개별 SQL 단위로 최적화 수행    |
프로시저는 **비즈니스 로직의 집합(Container)**이며, 여러 SQL 문장을 순차적으로 제어합니다. `SELECT` 문 내부에서 호출되지 않고, 별도의 `EXECUTE` 명령으로 실행됩니다.

### 예시 시나리오: `SP_ORDER_PROCESS` (주문 처리 프로시저)

```SQL
CREATE PROCEDURE SP_ORDER_PROCESS (p_user_id INT, p_item_id INT)
AS
BEGIN
    -- 1. 재고 확인 (SELECT)
    DECLARE v_stock INT;
    SELECT stock INTO v_stock FROM items WHERE item_id = p_item_id;

    -- 2. 비즈니스 로직 (IF 제어문)
    IF v_stock > 0 THEN
        -- 3. 주문 생성 (INSERT)
        INSERT INTO orders (user_id, item_id) VALUES (p_user_id, p_item_id);
        -- 4. 재고 감소 (UPDATE)
        UPDATE items SET stock = stock - 1 WHERE item_id = p_item_id;
    END IF;
END;
```

- **위치:** SQL 내부가 아닌, 애플리케이션 레벨에서 호출되는 **최상위 실행 단위**입니다.
- **옵티마이저 영향:**
    - **개별 최적화:** 옵티마이저는 프로시저 전체를 하나의 쿼리로 보지 않습니다. 내부의 `SELECT`, `INSERT`, `UPDATE` 문을 **각각 개별적으로 최적화**하여 실행 계획을 수립합니다.
    - **블랙박스:** 옵티마이저는 `IF` 문과 같은 제어 로직(Flow Control)을 해석하지 못합니다. 따라서 프로시저 내부 로직에 따라 실행 경로가 달라져도, 이를 예측하여 최적화하지는 못합니다.
### 1. DML(수정/삭제)의 내부 동작
`UPDATE`나 `DELETE` 문이 실행될 때, DBMS의 엔진은 두 순서로 작업을 진행합니다.
1. Fetch: `WHERE` 조건에 맞는 데이터를 찾아서 메모리(Buffer Cache)로 퍼 올립니다.
2. write: 찾아낸 데이터에 **Lock(잠금)**을 걸고 실제 값을 변경하거나 삭제 마킹을 합니다.
사용자가 다음과 같은 SQL을 실행했다고 가정합니다.

```SQL
UPDATE users 
SET salary = salary * 1.1 
WHERE id = 100;
```



### 3. 결론: 함수의 위치와 영향
- **`UPDATE`문의 `WHERE` 절에 쓰인 함수:**
    - **1단계(FETCH)**에서 사용됩니다.
    - 대상을 찾기 위한 **필터 역할(읽기 전용)**을 수행합니다.
    - _예:_ `WHERE UPPER(name) = 'KIM'` $\rightarrow$ 이름을 읽어서 대문자로 변환해 비교함.
- **`UPDATE`문의 `SET` 절에 쓰인 함수:**
    - **2단계(WRITE)** 직전에 값을 계산하기 위해 사용됩니다.
    - _예:_ `SET salary = ROUND(salary * 1.1)` $\rightarrow$ 값을 변경하기 위해 계산함.
