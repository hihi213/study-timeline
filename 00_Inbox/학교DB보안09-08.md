## **2025-09-08, 1교시 — 개선본**

DB 보안 프레임워크의 구성 요소와 보안 관리 단계에 대해 알아보겠습니다. 보안 프레임워크 구축의 필요성, 구성 기술 요소 도출 방법, 그리고 여러 보안 통제 사례와 매핑하여 접근 제한, 암호화, 작업 결재, 취약점 분석을 기준으로 구성 요소를 정의했습니다. 이제 이 구성 요소들을 이용해 보안 구축 단계를 살펴보겠습니다.

먼저 **기획 단계**입니다. 이 단계는 보안 구축 계획을 수립하고, 보안 정책의 지침과 가이드라인을 개발하는 과정입니다. 결과물로는 구축 계획서, 보안 지침서, 가이드라인이 산출됩니다. 보호할 데이터를 분류하고, 해당 데이터를 어떤 원칙과 지침으로 보호할지 정의하며, 담당 조직의 역할과 책임을 명확히 합니다. 또한, 기술 요소의 개선이나 변경, 추가 절차에 대한 가이드라인도 이 단계에서 수립합니다.

다음은 **설계 단계**입니다. 기획 단계가 전체적인 그림을 그렸다면, 설계 단계에서는 `DB` 접근 제어 규칙이나 작업 결재 규칙처럼 각 기술 요소별로 상세한 구현 방안을 구체화합니다. 사용자 인증, 로그인 과정, 모니터링 지표, 운영 방안 등을 상세히 설계합니다. 암호화의 경우, 복호화 권한 통제, 암호화 알고리즘 정의 등 기술적인 설계서가 작성됩니다. 작업 결재는 결재 경로 규칙과 모니터링 지표를, 취약점 분석은 분석 계획서를 포함하여 각 구성 요소에 필요한 기술적 설계를 진행합니다.

이후 **구축 단계**로 넘어갑니다. 이는 설계 단계의 결과를 바탕으로 각 기술 요소를 실제 시스템에 구현하고 테스트하는 과정입니다. 설계된 접근 제어 규칙을 구현하고, 일반적인 로그인 외에 우회 접근 시도를 방어하는지 테스트해야 합니다. 암호화의 경우, 주민등록번호와 같은 민감 정보가 저장 시점에 올바르게 암호화되는지, 원본 데이터는 안전하게 삭제되는지 확인합니다. 또한, 암호화된 데이터가 필요시 정상적으로 복호화되어 사용자가 판독할 수 있는지도 검증합니다. 설계 단계에서 도출된 취약점을 실제로 테스트하여 보안 솔루션을 적용하고, 개선 여부를 모니터링하며 내부 보안 감사를 실행합니다. 이 단계의 결과물은 구현 내역서와 테스트 결과서입니다.

마지막으로 **운영 단계**입니다. 구축된 프레임워크가 지속적으로 정상 작동하는지 모니터링하고 문제점을 개선하는 유지 관리 단계입니다. 보안 규칙 변경 사항을 관리하고, 로그를 주기적으로 점검하여 부적절한 접근 시도 등을 파악하고 보안을 강화해야 합니다. 정기적인 점검을 위해 체크리스트를 만들어 관리하는 것이 효과적이며, 운영 보고서와 개선 사항 보고서를 통해 지속적인 관리가 이루어져야 합니다.

구축보다 더 중요한 것이 운영입니다. 구축 이후의 보안 관리는 보안 조직, 보안 준비, 보안 통제 구축, 보안 통제 활동, 보안 교육 등으로 구성됩니다. 먼저 전담 **보안 조직**을 구성하고, 솔루션 도입 시기와 선정 기준을 정하는 **보안 준비**를 합니다. 이 과정에서 구성원들의 보안 인식을 높이기 위한 교육도 필요합니다. 이후, 프레임워크 프로세스에 따라 기술 요소를 구축하고 운영하는 **보안 통제 구축**을 진행합니다.

**보안 통제 활동**은 운영 단계에서 지속적으로 수행하는 관리 감독 활동으로, 로그 검토, 취약점 테스트 등을 통해 개선점을 찾아 반영합니다. 마지막으로 **보안 교육**은 각 단계별로 필요한 기술 교육, 관리 방법 교육 등을 시행하여 조직의 보안 역량을 높이고, 보안 시스템 도입에 대한 거부감을 최소화하는 것을 목표로 합니다.

`DB` 보안을 고려할 때는 `DB` 가용성을 위한 백업 및 복구 절차, 비인가 접근 제어, 동시성 제어, 불법 침입 차단, 분산 환경에서의 로그 추적, 애플리케이션을 통한 정보 유출, 그리고 모든 업무를 중앙 서버에서 관리하는 씬 클라이언트(thin client)의 정보 유출 가능성 등을 고려해야 합니다. 경영진과 임직원의 보안 의식 또한 매우 중요합니다. 이러한 고려 사항들은 `DB` 보안의 3대 요소인 기밀성, 무결성, 가용성에 미치는 영향을 분석하여 프레임워크 솔루션에 반영되어야 합니다.

정보 침해 요소를 분석하고 평가하는 절차는 다음과 같습니다.
1.  **자산 식별**: 데이터의 가치와 민감성에 따라 보호 대상을 등급별로 분류합니다.
2.  **위협 식별**: 각 데이터 자산에 발생할 수 있는 위협(자연적, 인적, 환경적)의 종류를 식별합니다.
3.  **발생 가능성 식별**: 식별된 위협이 실제로 발생할 확률을 '상, 중, 하'로 평가합니다.
4.  **영향도 식별**: 위협 발생 시 기밀성, 무결성, 가용성에 미치는 손실 수준을 평가합니다.
5.  **위험도 산정**: 발생 가능성과 영향도를 조합하여 위험의 수준을 결정합니다.
6.  **보안 대책 식별**: 산출된 위험도에 따라 접근 제어, 암호화 등 필요한 보안 대책을 수립합니다.
7.  **결과 기록 및 보고**: 분석 결과를 기록하고 보고하여 보안 투자 등 의사결정에 반영합니다.

이러한 분석을 통해 도출된 위험도에 따라 개선 활동이 필수적인 영역, 개선이 필요한 영역, 지속적인 모니터링이 필요한 영역으로 나누어 솔루션을 차등 적용합니다.

`DB` 보안 관리 체계는 이러한 모든 과정을 포괄하며, 데이터의 일관성과 합리성을 증대시키는 것을 목적으로 합니다. 이 체계는 **관리 조직**, **관리 절차**, **관리 인력**으로 구성됩니다. 관리 조직은 경영진부터 `DBA`, 임직원까지 역할과 책임을 분담합니다. 관리 절차는 로그 및 백업 관리, 권한 관리, 취약점 관리 등 모든 활동을 표준화하고 문서화하여 일관성을 유지하는 것입니다. 관리 인력은 리더십, 기술적 역량, 적용 역량으로 구분하여 각 직무에 맞는 역량을 정의하고 확보하는 것을 의미합니다.

결론적으로, `DB` 보안 관리 체계 구축을 위해서는 조직, 프로세스, 인력이 조화를 이루어야 하며, 주기적인 교육과 점검을 통해 지속적으로 개선해 나가는 것이 중요합니다.

## **2025-09-08, 1교시 — 개념**

1) **한 줄 요약**(≤120자)
DB 보안 프레임워크의 기획, 설계, 구축, 운영 단계를 이해하고, 정보 침해 위험을 체계적으로 분석하여 효과적인 관리 체계를 수립하는 전 과정을 학습합니다.

2) **핵심 TL;DR**
* **보안 프레임워크 수명주기**: 보안은 **기획 → 설계 → 구축 → 운영**의 4단계 생명주기를 가지며, 구축 후 지속적인 모니터링과 개선이 핵심입니다.
* **위험 평가 절차**: **자산 식별**에서 시작해 **위협 분석**, **발생 가능성 및 영향도 평가**를 거쳐 **위험도**를 산정하고 **보안 대책**을 수립하는 체계적 과정입니다.
* **위험 매트릭스**: 발생 가능성과 영향도를 기준으로 위험도를 '상-중-하'로 등급화하여, 즉시 개선이 필요한 영역과 지속 관찰이 필요한 영역을 구분하고 자원을 배분합니다.
* **보안 관리의 3요소**: 효과적인 보안 관리 체계는 **조직(역할과 책임), 절차(표준화된 활동), 인력(역량과 교육)**의 세 가지 축으로 구성됩니다.
* **위협의 분류**: `DB`에 가해지는 위협은 **자연재해(자연적), 인적 실수나 악의적 공격(인적), 정전 등(환경적)**으로 분류하여 다각도로 대비해야 합니다.
* **보안의 근본 목표**: 모든 보안 활동은 데이터의 **기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)**을 보장하는 것을 최종 목표로 합니다.
* **비용-효과성 원칙**: 보안 솔루션은 무조건적인 고비용이 아닌, 조직이 감수할 위험 수준과 보호 대상의 가치를 고려하여 비용 대비 효과가 가장 높은 대책을 선택해야 합니다.
* **보안 교육의 중요성**: 기술적 통제만큼이나 중요한 것은 모든 단계(준비, 구축, 운영)에서 임직원의 보안 인식을 높이는 지속적인 교육입니다.

3) **표현 = 표준 용어**
* **보안 프레임워크 (Security Framework)**: 보안 목표 달성을 위한 정책, 절차, 기술의 구조화된 집합체.
* **위험 평가 (Risk Assessment)**: 자산, 위협, 취약점을 식별하고 위험 수준을 분석 및 평가하는 과정.
* **기밀성, 무결성, 가용성 (Confidentiality, Integrity, Availability - CIA Triad)**: 정보 보안의 3대 기본 원칙.
* **위험 매트릭스 (Risk Matrix)**: 위험의 발생 가능성과 영향도를 시각적으로 표현하여 우선순위를 정하는 도구.
* **씬 클라이언트 (Thin Client)**: 최소한의 자원으로 중앙 서버에 의존하여 동작하는 업무용 PC. 중앙 관리의 이점이 있으나, 서버 자체가 유출 경로가 될 수 있음.

4) **정석 보강(canon-std)**
정보보안 위험 평가는 조직의 자산을 식별하고, 해당 자산에 대한 **위협(Threat)**과 **취약점(Vulnerability)**을 분석하여 **위험(Risk)**을 정량적·정성적으로 산정하는 체계적 과정입니다. 핵심은 `위험 = 발생 가능성(Likelihood) × 영향도(Impact)` 공식을 통해 위험 수준을 도출하고, 이를 기반으로 허용 가능한 수준까지 위험을 감소시키기 위한 보안 통제(Control)의 우선순위를 결정하는 것입니다.

5) **실수·함정**
* **구축 후 방치**: 프레임워크 구축에만 집중하고, 가장 중요한 운영 및 지속적 개선 단계를 소홀히 하는 것.
* **일회성 평가**: 위험 평가는 비즈니스 환경 변화에 따라 주기적으로 갱신되어야 함에도 불구하고, 최초 1회만 수행하고 마는 실수.
* **기술 만능주의**: 암호화, 접근 제어 등 기술적 보안에만 치중하고 관리적·물리적 보안(정책, 교육, 조직)을 간과하는 함정.
* **내부자 위협 무시**: 외부 해킹 등 인적 위협을 외부 위협으로만 한정하고, 내부자의 실수나 악의적 행위 가능성을 낮게 평가하는 오류.
* **문서화 부실**: 관리 절차나 점검 결과를 문서로 남기지 않아, 보안 활동의 일관성이 깨지고 인수인계 시 문제가 발생하는 경우.
* **모든 데이터 동일 취급**: 데이터의 중요도나 민감성을 등급화하지 않고 모든 자산에 동일한 보안 수준을 적용하여 비효율을 초래하는 것.
* **보안 교육 형식화**: 실제 사례나 기술적 이해 없이 형식적으로만 보안 교육을 진행하여 구성원의 인식 개선에 실패하는 경우.

**[Q1] DB 보안 프레임워크의 전체 수명주기(Life Cycle)는 어떻게 구성되며, 각 단계의 핵심 목표는 무엇인가요? | 태그: 보안 프레임워크, 수명주기**
* **모범답(강의 기준)**: DB 보안 프레임워크는 **기획, 설계, 구축, 운영**의 4단계로 구성됩니다. 기획은 정책 수립, 설계는 기술적 구체화, 구축은 구현 및 테스트, 운영은 지속적인 모니터링과 개선을 목표로 합니다.
* **정석체크(면접 30초)**: 보안 프레임워크는 **PDCA(Plan-Do-Check-Act)** 사이클에 기반합니다. **계획(Plan)** 단계에서 정책과 목표를 수립하고, **실행(Do)** 단계에서 통제를 구현하며, **검토(Check)** 단계에서 모니터링 및 감사를 수행합니다. 마지막으로 **개선(Act)** 단계에서 검토 결과를 반영하여 지속적으로 보안 수준을 향상시키는 것이 핵심입니다.

**[Q2] 정보 침해 위험을 평가하는 구체적인 절차는 어떻게 되나요? | 태그: 위험 평가, 자산 식별, 영향도 분석**
* **모범답(강의 기준)**: 위험 평가는 **자산 식별 → 위협 식별 → 발생 가능성 분석 → 영향도 분석 → 위험도 산정 → 보안 대책 수립 → 결과 보고**의 순서로 진행됩니다. 이 과정을 통해 보호 대상과 위협 수준을 파악하고 대응 우선순위를 결정합니다.
* **정석체크(면접 30초)**: 위험 평가는 먼저 보호할 **자산(Asset)을 식별하고 등급을 부여**하는 것에서 시작합니다. 이후 해당 자산의 **취약점(Vulnerability)**을 악용할 수 있는 **위협(Threat)**을 분석하여 위험 시나리오를 정의하고, **발생 가능성과 영향도**를 평가하여 최종 위험 수준을 결정합니다.

**[Q3] 위험도(Risk Level)는 어떻게 산정하고, 그 결과는 어떻게 활용되나요? | 태그: 위험 평가, 위험 매트릭스**
* **모범답(강의 기준)**: 위험도는 **발생 가능성과 영향도를 곱하여** 산정합니다. 산정된 위험도는 위험 매트릭스에 따라 '필수 개선', '개선 고려', '지속 모니터링' 등급으로 분류되어, 보안 대책 수립의 우선순위를 정하는 데 직접 활용됩니다.
* **정석체크(면접 30초)**: 위험도는 일반적으로 `위험도 = 발생 가능성(Likelihood) × 영향도(Impact)` 공식으로 산정하며, 이는 정량적·정성적 평가를 통해 이루어집니다. 평가 결과는 조직이 **수용 가능한 위험 수준(Acceptable Risk Level)**을 초과하는 위험에 대해 회피, 전가, 완화, 수용 중 어떤 처리 전략을 적용할지 결정하는 근거가 됩니다.

**[Q4] 효과적인 DB 보안 관리 체계를 구성하는 세 가지 핵심 요소는 무엇인가요? | 태그: 보안 관리 체계, 조직/절차/인력**
* **모범답(강의 기준)**: 효과적인 `DB` 보안 관리 체계는 **관리 조직(역할 분담), 관리 절차(문서화된 표준), 관리 인력(직무 역량 및 교육)**이라는 세 가지 핵심 요소로 구성됩니다. 이 요소들이 조화를 이룰 때 체계가 성공적으로 운영될 수 있습니다.
* **정석체크(면접 30초)**: 성공적인 보안 거버넌스는 **사람(People), 프로세스(Process), 기술(Technology)**의 통합에 달려있습니다. **사람**은 보안 인식과 전문성을, **프로세스**는 일관된 정책과 절차를, **기술**은 자동화된 통제 수단을 의미하며, 이 중 하나라도 부재 시 보안 체계는 제대로 작동하기 어렵습니다.

**[Q5] 보안 투자의 비용 대비 효과(ROI)를 어떻게 판단하고 최적의 수준을 결정하나요? | 태그: 위험 평가, 보안 투자**
* **모범답(강의 기준)**: 강의에서는 비용과 효과적인 측면을 잘 고려해야 한다고 강조합니다. 너무 비용을 아끼면 보안 수준이 떨어지고, 과도한 비용은 효과를 보지 못할 수 있으므로, 위험 분석 결과를 바탕으로 적절한 분기점을 찾는 것이 중요합니다.
* **정석체크(면접 30초)**: 보안 투자의 ROI는 **연간 예상 손실액(ALE, Annualized Loss Expectancy)**을 기반으로 평가합니다. `ALE = 단일 손실 예상액(SLE) × 연간 발생률(ARO)`로 계산하며, 보안 솔루션 도입 비용이 감소시키는 ALE보다 낮을 때 투자의 타당성을 확보합니다. 이를 통해 위험을 합리적인 수준으로 낮추는 최적의 투자 지점을 결정합니다.

## **2025-09-08, 2교시 — 개선본**

지난 시간에는 보안 프레임워크 개념을 다루었고, 이번에는 실제 `DBMS` 내에서 보안을 적용하는 실습 방법을 개괄적으로 살펴보겠습니다.

데이터베이스는 정보가 집약된 중요한 자산이므로 보안이 필수적입니다. 데이터 유출, 무단 접근, 무결성 훼손 등의 위협으로부터 데이터를 보호하는 것이 목표이며, 크게 `DB` 데이터 보안과 관리자 보안으로 나눌 수 있습니다. 데이터 유출의 가장 큰 원인은 내부자로, 권한 있는 사용자의 악의적인 행위가 약 80~90%를 차지합니다. 그 외에 `SQL Injection`, 피싱(phishing), 사회 공학적 공격 등도 주요 위협입니다. `SQL Injection`은 `SQL` 쿼리 내부에 악의적인 코드를 주입하는 공격 기법이며, 피싱은 사용자를 속여 정보를 입력하게 만드는 방식입니다.

이러한 위협으로부터 데이터베이스를 보호하기 위한 주요 보안 기법은 다음과 같습니다.

첫째, **사용자 인증(Authentication)**입니다. ID/패스워드, 생체 인식, 2단계 인증 등을 통해 인가된 사용자만 시스템에 접근하도록 통제합니다. 패스워드는 주기적으로 변경하도록 정책을 설정할 수 있으며, `DBMS`가 제공하는 인증 메커니즘을 이용해 인증 시스템을 실습할 수 있습니다. `(실습)`

둘째, **권한 관리(Authorization)**입니다. 역할 기반 접근 제어(RBAC)를 통해 사용자별로 접근 가능한 데이터와 수행할 수 있는 작업을 세분화하여 통제합니다. 특정 테이블의 `SELECT` 권한만 부여하거나, 특정 컬럼에만 접근하도록 제한할 수 있습니다. `(실습)` 또한, 뷰(View)를 이용해 테이블의 특정 행이나 컬럼만 노출시키는 것도 가능합니다. `(실습)`

셋째, **데이터 암호화(Encryption)**입니다. 전송 중인 데이터를 보호하기 위해 TLS(Transport Layer Security)나 SSL(Secure Sockets Layer) 같은 프로토콜을 사용합니다. 이는 클라이언트와 서버 간의 통신을 암호화하여 중간에서 데이터를 탈취하거나 변조하는 것을 방지하며, `HTTPS`가 대표적인 예입니다. 저장된 데이터 자체를 암호화하는 것도 중요하며, 디스크, 테이블, 컬럼 단위로 암호화를 적용할 수 있습니다. `(실습)` 암호화 키의 생성, 저장, 회전, 폐기 등 키 관리 절차 또한 `DBMS` 내에서 관리 가능합니다.

넷째, **데이터 무결성(Integrity) 및 가용성(Availability) 보장**입니다. 무결성은 데이터가 항상 정확하고 일관된 상태를 유지하는 것을 의미합니다. 이를 위해 **트랜잭션(Transaction)** 개념이 사용되며, 트랜잭션은 ACID 속성(원자성, 일관성, 고립성, 영속성)을 가집니다. 특히 여러 사용자가 동시에 데이터에 접근할 때 발생하는 문제를 막기 위해 병행 제어(Concurrency Control)가 필요하며, 이는 데이터 보안의 중요한 요소입니다. `(실습)` 또한, 주기적인 **백업과 복구** 절차를 통해 재해나 장애 발생 시 데이터를 보호하고 서비스의 연속성을 보장해야 합니다. `(실습)`

가용성 측면에서는 서버 중단을 방지하고 최적의 성능을 유지하는 것이 중요합니다. **인덱스(Index)**를 활용해 검색 효율을 높이고, **쿼리 최적화**를 통해 `SQL` 실행 속도를 개선할 수 있습니다. `(실습)`

다섯째, **네트워크 기반 접근 제어**입니다. 방화벽, 침입 탐지 시스템(IDS), 침입 방지 시스템(IPS) 등을 통해 네트워크 레벨에서부터 비인가 접근을 차단할 수 있습니다.

여섯째, **감사와 모니터링**입니다. `DBMS`의 로그 기록 기능을 활용하여 사용자의 모든 활동(로그인, 데이터 접근, 쿼리 실행 등)을 추적하고 분석할 수 있습니다. `(실습)` 누가, 언제, 무엇을 했는지 추적하여 이상 행위를 탐지하고, 민감 데이터에 대한 접근은 실시간으로 모니터링하여 보안을 강화할 수 있습니다.

최신 보안 이슈로는 클라우드 환경에서의 데이터 보안, 그리고 GDPR(유럽 개인정보보호법)이나 CCPA(캘리포니아 소비자 개인정보보호법) 같은 데이터 보호 규정 준수가 중요해지고 있습니다. 이러한 법규를 준수하지 않으면 막대한 벌금이나 법적 책임을 질 수 있습니다.

향후 실습할 내용들은 다음과 같습니다.
* **사용자 및 권한 관리**: `CREATE USER`로 계정을 만들고 `GRANT`, `REVOKE`로 권한을 부여 및 회수합니다. `(실습)`
* **프로파일(Profile) 활용**: 프로파일을 생성하여 사용자의 로그인 실패 횟수 제한이나 비밀번호 유효 기간을 설정합니다. `(실습)`
* **객체 권한 관리**: 특정 테이블이나 뷰에 대해 `SELECT`, `INSERT` 등 특정 작업만 허용하는 권한을 부여합니다. `(실습)`
* **감사(Auditing)**: `AUDIT` 명령어를 사용해 특정 테이블에 대한 접근 기록을 남기도록 설정합니다. `(실습)`
* **데이터 암호화**: `DBMS_CRYPTO`와 같은 패키지를 사용해 특정 컬럼의 데이터를 `AES` 알고리즘으로 암호화하여 저장합니다. `(실습)`
* **뷰(View) 생성**: `CREATE VIEW`를 통해 민감한 정보(주민등록번호 뒷자리 등)를 마스킹 처리한 가상 테이블을 만듭니다. `(실습)`
* **트랜잭션과 백업/복구**: `COMMIT`, `ROLLBACK`, `SAVEPOINT` 등을 사용해 트랜잭션을 제어하고, 데이터 복구 상황을 실습합니다. `(실습)`

이러한 실습은 오라클 `DBMS` 환경에서 진행될 예정입니다.

## **2025-09-08, 2교시 — 질문**

**[Q1] 데이터 무결성을 보장하기 위해 트랜잭션이 가져야 할 ACID 속성이란 무엇인가요? | 태그: 트랜잭션, 무결성, ACID**
* **모범답(강의 기준)**: ACID는 원자성, 일관성, 고립성, 영속성을 의미합니다. 트랜잭션은 분해되지 않는 하나의 단위(원자성)로 처리되어야 하고, 처리 후에도 데이터는 일관성을 유지해야 하며(일관성), 한 트랜잭션이 실행되는 동안 다른 트랜잭션이 개입할 수 없어야 합니다(고립성).
* **정석체크(면접 3초)**: ACID는 데이터베이스 트랜잭션의 신뢰성을 보장하는 4가지 핵심 속성입니다. **원자성(Atomicity)**은 'All or Nothing', **일관성(Consistency)**은 유효한 데이터만 기록, **고립성(Isolation)**은 트랜잭션 간의 독립성, **영속성(Durability)**은 `COMMIT` 후 결과의 영구 보장을 의미합니다.

**[Q2] 여러 사용자가 동시에 동일 데이터를 수정할 때 어떤 문제가 발생하며, 이를 어떻게 방지하나요? | 태그: 트랜잭션, 병행 제어, 무결성**
* **모범답(강의 기준)**: 한 사용자가 데이터를 수정하는 도중에 다른 사용자가 접근하면 데이터 일관성이 깨지는 문제가 발생합니다. 이를 방지하기 위해 트랜잭션의 고립성을 보장하는 병행 제어가 필요하며, 한 작업이 끝날 때까지 다른 작업이 접근하지 못하도록 막아야 합니다.
* **정석체크(면접 3초)**: 동시성 문제는 **갱신 손실(Lost Update)**이나 **현황 파악 오류(Dirty Read)** 등을 유발하여 데이터 무결성을 훼손합니다. 이를 방지하기 위해 `DBMS`는 **락(Locking)** 기법을 사용하여 트랜잭션의 공유 데이터 접근을 제어합니다. 하지만 락을 과도하게 사용하면 **교착상태(Deadlock)**가 발생할 수 있으므로 주의해야 합니다.

**[Q3] 사용자 계정의 비밀번호 정책(예: 유효기간, 실패 횟수)은 어떻게 강제할 수 있나요? | 태그: 계정 관리, 프로파일, 비밀번호 정책**
* **모범답(강의 기준)**: 오라클의 **프로파일(Profile)** 객체를 생성하여 로그인 실패 횟수나 비밀번호 유효 기간 등을 설정할 수 있습니다. 이 프로파일을 특정 사용자 계정에 적용하면 해당 보안 정책이 강제됩니다. `(실습)`
* **정석체크(면접 3초)**: `CREATE PROFILE` 명령어로 패스워드 정책을 정의하고, `ALTER USER ... PROFILE` 구문을 통해 사용자에게 해당 프로파일을 할당합니다. 예를 들어 `ALTER PROFILE app_user_profile LIMIT FAILED_LOGIN_ATTEMPTS 5 PASSWORD_LIFE_TIME 90;` 처럼 설정할 수 있습니다. `DEFAULT` 프로파일을 그대로 사용하면 보안에 취약할 수 있습니다.

**[Q4] 데이터 암호화는 '전송 중'인 데이터와 '저장된' 데이터에 대해 어떻게 다르게 적용되나요? | 태그: 암호화, TDE, TLS**
* **모범답(강의 기준)**: **전송 중인 데이터**는 중간 탈취를 막기 위해 TLS/SSL 프로토콜을 사용해 암호화합니다(`HTTPS`가 예시). **저장된 데이터**는 디스크나 테이블, 컬럼 단위로 `DBMS`가 제공하는 암호화 기능(예: `DBMS_CRYPTO`)을 사용해 데이터 파일 자체를 보호합니다.
* **정석체크(면접 3초)**: 전송 중인 데이터(in-transit)는 **TLS**를 통해 네트워크 구간을 암호화하여 보호합니다. 저장된 데이터(at-rest)는 **TDE(Transparent Data Encryption)**로 데이터 파일 전체를 암호화하거나, 특정 컬럼만 암호화 함수(`AES_ENCRYPT`)를 이용해 보호합니다. 두 가지 모두 적용해야 완전한 데이터 보호가 가능합니다.

**[Q5] 사용자에게 테이블의 모든 정보가 아닌 특정 컬럼에 대한 `SELECT` 권한만 부여하는 등, 세분화된 권한 설정이 가능한가요? | 태그: 권한(GRANT/REVOKE), 객체 권한, 최소 권한 원칙**
* **모범답(강의 기준)**: 네, 가능합니다. 특정 테이블의 특정 컬럼에 대해서만 `SELECT`나 `UPDATE` 같은 특정 명령어만 수행할 수 있도록 권한을 세분화하여 부여할 수 있습니다. 이는 객체 보안의 일부입니다.
* **정석체크(면접 3초)**: **객체 권한(Object Privilege)**을 통해 세분화된 통제가 가능합니다. 예를 들어, `GRANT SELECT (emp_name, salary) ON employees TO analyst_role;` 과 같이 특정 컬럼에 대한 조회 권한만 부여할 수 있습니다. 이는 **최소 권한 원칙(Principle of Least Privilege)**을 준수하는 중요한 방법입니다.
