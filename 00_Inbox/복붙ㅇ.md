### **폴더(패키지) 구조 -기능(도메인)별 모듈링**

```
com.example.order
 ├─ domain //ex) order
 │   ├─ Order.java                // 엔티티(애그리거트 루트)
 │   ├─ OrderLine.java            // 엔티티/값 객체
 │   ├─ OrderId.java              // 값 객체(식별자)
 │   ├─ OrderRepository.java      // ← 인터페이스(도메인에 둠)
 │   └─ OrderPlaced.java          // 도메인 이벤트
 ├─ application
 │   └─ PlaceOrderService.java    // 유스케이스(트랜잭션, 도메인 조립)
 ├─ infra
 │   └─ JpaOrderRepository.java   // ← 구현체(영속화 기술, JPA)
 └─ api
     └─ OrderController.java
```

- **규칙**: domain은 **어느 것도 의존하지 않음**(핵심 규칙 보호). infra가 domain 인터페이스를 **구현**해서 기술에 붙여 줌(헥사고날/클린 아키텍처).

## **한 줄 정리**

- **도메인**: 비즈니스 세계 + 규칙.
- **엔티티**: 도메인 모델의 핵심 객체(식별자·상태·행위), DB에 저장.
- **리포지토리**: 애그리거트를 저장/조회하는 **도메인 인터페이스**(구현은 인프라).
- **DTO**: 전달용 데이터. 즉 비즈니스 로직/영속성 X.
- **값 객체**: 식별자 없이 값 동등성, 보통 불변.

## **한 눈 비교표**

| **구분**   | **엔티티 (Entity)**                             | **스프링 빈 (Bean)**                                  | **DTO**                         | **값 객체 (Value / 임베디드)**        |
| -------- | -------------------------------------------- | ------------------------------------------------- | ------------------------------- | ------------------------------ |
| 누가 관리?   | **JPA/영속성 컨텍스트** (EntityManager)             | **Spring IoC 컨테이너**                               | 아무도 X(프레임워크가 생성/매핑만)            | JPA가 엔티티 **내부에 내장**하여 함께 관리    |
| 대표 대상    | **DB의 행(Row)**                               | **애플리케이션 구성요소/서비스**                               | **전달 데이터**                      | **개념적 값**(주소/기간/돈 등)           |
| 주요 어노테이션 | @Entity, @Id, @Table                         | @Component, @Service, @Repository, @Configuration | 보통 없음(레코드/POJO), 검증용 @NotNull 등 | @Embeddable, 엔티티 필드에 @Embedded |
| 저장 위치    | **DB 테이블**                                   | 메모리(컨테이너)                                         | 직렬화/HTTP/메시지/뷰모델                | **엔티티 테이블의 컬럼들**(별도 테이블 X)     |
| 식별/동등성   | **식별자(@Id)로 동일성**; equals/hashCode는 보통 ID 기반 | 빈 이름/타입(컨테이너 식별)                                  | 값 기반(필드 동일)                     | **값 기반 동등성**(불변 추천)            |
| 라이프사이클   | 트랜잭션/PC 경계에 의존(지연 로딩/변경감지)                   | 컨텍스트 시작~종료(기본 **싱글톤**)                            | 요청/응답 단발                        | 엔티티와 함께 로드/저장                  |
| 스레드 안전   | 엔티티 인스턴스 **스레드-세이프 전제 아님**                   | **싱글톤 권장 ⇒ 상태 없게 설계**                             | 해당 없음                           | 값 자체는 **불변 권장**                |
| 책임       | **도메인 상태/행위**(비즈니스 규칙)                       | **조립/조정/유스케이스/인프라**                               | 표현/전달                           | 개념/규칙(불변·검증)                   |
| 생성 방식    | 보통 JPA가 프록시/리플렉션으로 생성(기본 생성자 필요)             | 스프링이 생성/주입                                        | 매퍼/컨트롤러에서 수동 생성                 | 엔티티가 포함하여 생성                   |
| 언제 사용?   | “DB에 저장되는 도메인 모델”이 필요할 때.                    | “유스케이스/서비스/인프라”를 조립/조정할 때.                        | “API 입출력/계층 경계”에서 전송할 때.        |  “한 덩어리의 도메인 값”을 모델링할 때.       |

- **엔티티(Entity)**: 식별자(@Id)로 구분되는 **도메인 객체**. 상태+행위(규칙)를 가짐. DB에 저장됨 **JPA(영속성 컨텍스트)** 가 수명·상태를 관리
- **값 객체(Value/임베디드)**: **식별자 없이 값으로 동등성**을 판단하는 도메인 값. @Embeddable, @Embedded. 보통 불변.
- **애그리거트(Aggregate)**: 규칙을 함께 지키는 도메인 객체 묶음. **루트 엔티티**가 외부 공개 창구.
- **리포지토리(Repository)**: **애그리거트 단위**로 저장/조회하는 **추상화**(인터페이스). “저장소”가 아니라 **도메인 모델을 영속화하는 계약**.
- **스프링 빈**: **스프링 IoC 컨테이너가 관리**하는 애플리케이션 구성요소(서비스/설정/리포지토리 등). @Service, @Component, @Repository, @Configuration.
- **도메인 서비스**: 엔티티 하나에 넣기 애매한 **순수 비즈니스 연산**.
- **도메인 이벤트**: “주문완료됨” 같은 **비즈니스 사건**.
### **도메인 = 비즈니스 문제 영역**

- 예) 쇼핑몰이라면 “주문, 결제, 배송, 회원, 상품” 같은 **업무 개념**과 **규칙(유효성/불변식/상태전이)**.
- **도메인 모델** = 그 개념을 코드로 표현한 것(엔티티, 값 객체, 도메인 서비스, 도메인 이벤트, 애그리거트 등). 단순 DB그릇이 아니라 의미있는 메서드로 규칙까지 포함해 엔티티를 도메인 모델이라고도 한다.
- **DTO**는 도메인 모델이 아님. **입출력/전달용** 구조체. 보통 api(컨트롤러 인/아웃)나 application 경계에서 쓴다.
- **도메인(서비스/레포지토리)의 도메인 모델 (Domain Model):**
	- **핵심 비즈니스 객체**
	- Setter 대신 의미있는 메서드를 포함하는걸 권장한다
	- `@Entity`가 붙는다
	- DB 테이블과 1:1 매핑
- 컨트롤러의 **DTO (Data Transfer Object):** 계층간 데이터 전송 객체
	- 화면에 필요한 데이터만 포함 • 유효성 검증(`@NotEmpty` 등) 로직 포함 • 보통 순수한 데이터 전달이 목적
	- 유효성 로직을 엔티티에 작성하는게 아니라 DTO에 작성해 관리한다.
- 컨트롤러 메서드의 파라미터의 **`Model`**: Controller에서 View로 데이터를 넘겨주기 위한 **'연결고리' 또는 '쟁반'**.
	- `addAttribute()`로 데이터 추가 • Controller에서 View로 데이터를 넘기는 '다리' 역할 • Spring MVC 프레임워크 기능

## **헷갈리기 쉬운 포인트 정리**

### **1) “엔티티도 스프링이 관리하나요?”**

- **아니요.** 엔티티는 **스프링 빈이 아닙니다**. 컨테이너가 아닌 **영속성 컨텍스트**가 관리
- 엔티티 인스턴스는 **JPA(영속성 컨텍스트)** 가 상태를 추적하고, 변경 감지/지연 로딩 등을 처리합니다.
- 반면 **리포지토리**(ex. JpaRepository)는 **스프링 빈**입니다. 엔티티를 DB와 주고받는 **컴포넌트**죠.

### **2) “DTO vs 엔티티, 어디에 로직을 둬야 하나?”**

- **엔티티**: **도메인 규칙/불변식**(ex. “재고 감소는 0 미만 불가”).
- **DTO**: 직렬화/검증/표현 전환(Controller 경계). **비즈니스 로직 X**.

### **3) “값 객체(임베디드)는 엔티티랑 뭐가 달라?”**

- **값 객체(임베디드)**는 **식별자(@Id) 없음**, **값으로 동등성**.

    예: Address(city, street, zip)

    - @Embeddable로 정의, 엔티티에 @Embedded로 사용 ⇒ **별도 테이블 없이** 컬럼들로 함께 저장.
    - **불변(immutable)** + **자기 유효성 보장**이 베스트 프랙티스.

### **4) “빈은 왜 싱글톤을 권장?”**

- 스프링 빈은 **기본 싱글톤**. 요청마다 만들어지는 게 아니라 **하나를 공유**하니, **상태를 들고 있지 않게(Stateless)** 설계해야 안전합니다.
- 상태가 필요하면 **메소드 지역 변수**로 두거나, **프로토타입/리퀘스트 스코프**를 고려.

## 실무 구현

- **컨트롤러** : DTO를 받아서 서비스에 넘기는 역할만 충실
    - 폼 → **DTO(Command)** 로 변환만
    - 엔티티 **생성·변경 금지**
- **서비스(트랜잭션 경계)**
    - **조회 → 변경감지** 수행
    - 파라미터 많으면 **전용 Command DTO** 도입
- **엔티티** :
    - 엔티티 내부에 **setter 대신 의미 있는 도메인 변경 메서드**
    - 컬렉션/연관관계는 **편의 메서드**로 일관성 유지
- 왜?
	- 컨트롤러가 엔티티 생성/변경하는 비즈니스 로직까지 하면 역할을 나눈의미가 없어 유지보수가 힘듬
    - 파라미터 많으면 **전용 Command DTO** 로 받기
	    - updateProfile(String nickname, String email, String address, ...) -> `updateProfile(ProfileUpdateDto dto)`
	    - 프로필에 '전화번호'를 추가해야 할 때, DTO에 필드 하나만 추가하면 끝나요. 만약 DTO를 안 썼다면 이 기능을 사용하는 모든 메서드의 파라미터를 일일이 수정해야 하죠.
	- setter, 의미메서드 모두 메서드이다. 그러나 비즈니스 규칙과 책임이 어디에 있는가에 따라 다르다
		- `setPoint(1000)`: 받은값 그대로 저장하기만 한다.
			- setter를 사용할때마다 서비스에 포인트 저장규칙 대한 로직을 추가적으로 작성해야한다.
			- 만일 포인트 저장규칙이 바뀌면 찾아다니며 일일히 바꿔야한다
		- addPointsForPurchase(20)`, `addPointsForCoupons(10)`:
			- 서비스에서 로직대신 이름으로 기능을 유추가능한 메서드를 호출해 한줄처리
			- 포인트 정책이 바뀌어도 `User` 엔티티만 수정하면 된다

- 반면 **리포지토리**(ex. JpaRepository)는 **스프링 빈**입니다. 엔티티를 DB와 주고받는 **컴포넌트**죠.

## 실무 구현

- **컨트롤러** : DTO를 받아서 서비스에 넘기는 역할만 충실
    - 폼 → **DTO(Command)** 로 변환만
    - 엔티티 **생성·변경 금지**
- **서비스(트랜잭션 경계)**
    - **조회 → 변경감지** 수행
    - 파라미터 많으면 **전용 Command DTO** 도입
- **엔티티** :
    - 엔티티 내부에 **setter 대신 의미 있는 도메인 변경 메서드**
    - 컬렉션/연관관계는 **편의 메서드**로 일관성 유지
- 왜?
	- 컨트롤러가 엔티티 생성/변경하는 비즈니스 로직까지 하면 역할을 나눈의미가 없어 유지보수가 힘듬
    - 파라미터 많으면 **전용 Command DTO** 로 받기
	    - updateProfile(String nickname, String email, String address, ...) -> `updateProfile(ProfileUpdateDto dto)`
	    - 프로필에 '전화번호'를 추가해야 할 때, DTO에 필드 하나만 추가하면 끝나요. 만약 DTO를 안 썼다면 이 기능을 사용하는 모든 메서드의 파라미터를 일일이 수정해야 하죠.
	- setter, 의미메서드 모두 메서드이다. 그러나 비즈니스 규칙과 책임이 어디에 있는가에 따라 다르다
		- `setPoint(1000)`: 받은값 그대로 저장하기만 한다.
			- setter를 사용할때마다 서비스에 포인트 저장규칙 대한 로직을 추가적으로 작성해야한다.
			- 만일 포인트 저장규칙이 바뀌면 찾아다니며 일일히 바꿔야한다
		- addPointsForPurchase(20)`, `addPointsForCoupons(10)`:
			- 서비스에서 로직대신 이름으로 기능을 유추가능한 메서드를 호출해 한줄처리
			- 포인트 정책이 바뀌어도 `User` 엔티티만 수정하면 된다
