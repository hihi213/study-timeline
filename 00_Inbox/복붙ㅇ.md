## JPA 영속성 컨텍스트 최종 정리: 6단계
### 1. 영속성 컨텍스트 오픈: 서비스 메서드에서 **@Transactional 시작**
- 논리적 관리 영역인 영속성 컨텍스트가 생성됩니다.

### 2. 1차 캐시 조회 및 로딩 (데이터 확보)

- **목적**: DB 접근을 최소화하고 성능을 최적화하기 위함입니다.
- **작동**: 엔티티 ID를 기준으로 **1차 캐시**에 먼저 접근합니다.
- **캐시 미스(Miss) 시**: 캐시에 없으면 **DB에 `SELECT` 쿼리**를 실행하여 데이터를 가져옵니다. 가져온 데이터는 **영속 상태**로 전환되어 1차 캐시에 저장되고 **스냅샷**이 찍힙니다.

---

### 3. 신규 데이터 처리 방식의 분기

ID를 기준으로 **DB에 데이터 자체가 없는 경우** (즉, 신규 데이터) 두 메커니즘은 다르게 작동합니다.

| 메커니즘          | 입력 객체 상태                  | 결과                                                     |
| ------------- | ------------------------- | ------------------------------------------------------ |
| **조회 → 변경**   | ID로 `find()` 시도           | DB에 없으므로 **`null`을 반환**하고 작업 종료. ->개발자가 Persist 경로처리해야 |
| **`merge()`** | ID가 없는 **비영속 객체**를 인자로 받음 | **`persist`와 동일하게** 새로운 영속 엔티티를 생성하고, `INSERT`를 준비함.   |

- merge에 persist 기능있다고해도 명시적으로 persist 코드에 사용해 의도 드러내기
---

### 4. 변경 감지 (Dirty Checking)의 역할과 차이

데이터 변경을 감지하고 DB에 반영하는 과정은 **엔티티의 상태를 어떻게 변경했는지**에 따라 나뉩니다.

| 메커니즘             | Dirty 생성 방식                                    | SQL 생성 유형                                             |
| ---------------- | ---------------------------------------------- | ----------------------------------------------------- |
| **조회 → 변경 (권장)** | **개발자가 영속 엔티티를 직접 선택적으로 필드 수정**                | Dirty Checking으로 **수정된 필드**만 감지하여 **`UPDATE`** 쿼리 생성. |
| **`merge()`**    | **준영속 객체의 모든 필드를 복사**하여 영속 객체를 강제로 변경 상태로 만듦.  | **`UPDATE(기존변경)`** 또는 **`INSERT(신규생성)`** 쿼리 생성        |

- 이때 merge의 반환값은 영속객체, 데이터를 넘겼던 준영속객체는 계속준영속인 별개의 객체
---

### 5. 최종 반영 (Flush & Commit)

- **Flush 시점**: 트랜잭션 커밋(`commit()`) 직전 또는 JPQL 쿼리 실행 직전에 `flush()`가 자동 호출됩니다.
- **SQL 전송**: `flush` 시점에 **Dirty Checking** 결과(UPDATE)와 **쓰기 지연 저장소**의 모든 DML 쿼리(`INSERT`, `UPDATE`, `DELETE`)가 DB에 한 번에 전송 및 실행됩니다.
- **Commit**: 모든 SQL 실행이 완료된 후, `commit()`을 통해 트랜잭션이 **영구적으로 확정**

### 6. 컨텍스트 종료
- **`commit` 완료** 후 영속성 컨텍스트가 닫히며, 여기서 관리되던 모든 엔티티는 **준영속 상태(Detached)** 로 전환됩니다.
