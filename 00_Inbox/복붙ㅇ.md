# 스프링 도메인 주도 설계
## 1. **도메인형 폴더 구조와 의존 규칙**

스프링의 폴더구조는 대표적으로 2가지 방식이 있다 계층형구조, 도메인형 구조 나는 도메인(비즈니스)기능을 기준으로 묶는 도메인형 구조를 선택했다(실무에서 많이씀)

```
com.example
 ├─ order
 │   ├─ domain
 │   │   ├─ Order.java                // 애그리거트 루트
 │   │   ├─ OrderLine.java            // 엔티티/값 객체
 │   │   ├─ OrderId.java              // 값 객체(식별자)
 │   │   ├─ OrderRepository.java      // 도메인 인터페이스(포트)
 │   │   └─ OrderPlaced.java          // 도메인 이벤트
 │   ├─ application
 │   │   └─ PlaceOrderService.java    // 유스케이스(트랜잭션, 도메인 조립)
 │   ├─ adapter
 │   │   ├─ in
 │   │   │   └─ web
 │   │   │       └─ OrderController.java // REST/GraphQL 등 인바운드 어댑터
 │   │   └─ out
 │   │       └─ jpa
 │   │           └─ JpaOrderRepository.java // 리포지토리 구현(JPA)
 │   └─ config                            // (선택) 스프링 설정/빈 구성
 └─ book
     ├─ domain
     ├─ application
     ├─ adapter
     └─ config
```

)

## **4가지 계층 레이어의 명확한 역할분리**
- **도메인(domain)**: 비즈니스 문제영역, 어떤 것도 **의존하지 않는다**. 규칙·상태·행위를 담는다.
- **애플리케이션(application)**: **트랜잭션 경계**에서 도메인을 **조립·조정**한다.
- **인프라(adapter/out)**: 도메인 **인터페이스(포트)**를 **구현**하여 JPA·메시징 등 **기술**을 붙인다.
- **API(adapter/in)**: **입·출력과 검증**만. 얇게 받아서 서비스 호출, DTO로 반환.
> 요약 **규칙은 안쪽(도메인), 기술은 바깥(어댑터)**, 흐름은 애플리케이션

### 네 가지 계층의 명확한 역할 분리(상세)
- **domain** : 규칙·상태·행위 + 포트(리포지토리 인터페이스)
    - 엔티티/값 객체/도메인 서비스/도메인 이벤트.
    - 의미 있는 메서드로 동작 노출(예: order.cancel()).
    - 리포지토리 **인터페이스만** 선언
- **application**
    - 트랜잭션 경계에서 도메인을 조립, 조정한다
    - 여러 도메인(엔티티/리포지토리/서비스)객체 협력 orchestration.
    > Don't: 규칙은 넣지 말 것(규칙은 도메인으로!).
- **adapter/out (infra)**
    - 도메인 계층이 정의한 **'port(인터페이스)'를 실제로 구현하는 '어댑터(Adapter)'들이 모여있는 곳**
	    - JPA, MyBatis, 메시지 큐, 외부 API 호출 등 **구체적인 기술을 사용해 실제로 구현**
- **adapter/in (api)**
    - HTTP 입·출력, DTO 매핑/검증(@Valid).
    - 데이터 받아 서비스 호출, 결과를 DTO로 반환.
    - Don’t: 엔티티를 직접 다루거나 규칙을 담지 말 것.
## **관리 주체별 개념 정리**

### 개발자가 관리
- **도메인 모델**: 도메인을 코드로 표현한것
	- 엔티티, 값 객체, 도메인 서비스, 도메인 이벤트, 애그리거트 등
- **도메인 서비스**: 엔티티 하나에 넣기 애매한 **순수 비즈니스 연산**.
- **도메인 이벤트**: “주문완료됨” 같은 **비즈니스 사건**.
- **DTO**: 계층 경계의 **전달용 데이터**(직렬화/검증). 즉 비즈니스 로직,영속성 X
### 스프링 IOC컨테이너가 관리

- **리포지토리**: “애그리거트 단위”로 저장/조회를 추상화한 **도메인 인터페이스**. 구현은 인프라가 한다. “저장소”가 아니라 **도메인 모델을 영속화하는 계약**. 엔티티를 DB와 주고받는 **컴포넌트**
- Model: 표준화된 타입으로 `addAttribute()`로 데이터를 감싸 일관되게 전달하는 운반도구. **DTO**를 담아 다른계층에 전달하거나, 문자열, 숫자, 객체목록..등 다양한 종류의 데이터를 담을수있다
- **스프링 빈**: IoC 컨테이너가 관리하는 컴포넌트(@Service/@Component/@Repository 등). **기본 싱글톤**이므로 상태 없음이 원칙.

### **영속성 컨텍스트**가 관리(JPA)
- **엔티티(Entity)**: 식별자(@Id)로 구분되는 도메인 객체(상태+행위). DB에 저장됨.
	- 단순 DB그릇이 아니라 의미있는 메서드로 규칙까지 포함해 엔티티
	- Setter 대신 의미있는 메서드를 포함하는걸 권장한다
	- `@Entity`가 붙는다
	- DB 테이블과 1:1 매핑
- **값 객체(임베디드)**: **식별자 없이 값으로 동등성**을 판단하는 도메인 값. 대개 **불변**. @Embeddable/@Embedded. JPA가 엔티티 **내부에 내장**하여 함께 관리
- **애그리거트**(Aggregate): 규칙을 함께 지키는 도메인 객체 묶음. **루트 엔티티**만 외부 공개된 창구.

### 빠른 비교표
**핵심 기억 포인트**
- 엔티티 = **비즈니스 규칙의 주체**(DB에 저장).
- 빈 = **조립자/오케스트레이터**(싱글톤, 상태 없음).
- DTO = **전달용 그릇**(로직 X, 검증 O).
- 값 객체 = **불변 값**(자기 유효성, 값으로 비교, 엔티티에 내장).

| **구분**       | **엔티티 (Entity)**                        | **스프링 빈 (Bean)**                  | **DTO**              | **값 객체 (Value/임베디드)**       |
| ------------ | --------------------------------------- | --------------------------------- | -------------------- | --------------------------- |
| **목적**       | DB에 저장되는 **도메인 모델**(규칙·상태·행위)           | **유스케이스/인프라 조립·조정**하는 앱 컴포넌트      | **계층 경계에서 데이터 전달**   | **개념적 값**을 표현(주소/기간/돈 등)    |
| **관리 주체**    | **JPA/영속성 컨텍스트**                        | **Spring IoC 컨테이너**               | 없음(컨트롤러/매퍼가 생성)      | 엔티티에 **내장되어 JPA가 함께 관리**    |
| **저장 위치**    | **DB 테이블의 행(Row)**                      | 메모리(컨테이너)                         | 직렬화/HTTP/메시지/뷰모델     | **엔티티 테이블 컬럼으로 함께 저장**      |
| **식별/동등성**   | **@Id로 동일성**, equals/hashCode는 보통 ID 기반 | 빈 이름/타입                           | **값 동등성**            | **값 동등성**, **불변 권장**        |
| **생성/관리 방식** | 보통 JPA가 프록시/리플렉션으로 생성(기본 생성자 필요)        | 스프링이 생성·주입(DI)                    | 컨트롤러/매퍼가 수동 생성       | 엔티티가 포함해 생성(생성자/팩토리)        |
| **생명주기**     | 트랜잭션/영속성 컨텍스트 경계에 좌우(지연 로딩/변경감지)        | 애플리케이션 시작~종료(기본 **싱글톤**)          | 요청/응답 단발(짧음)         | **소유 엔티티 생명주기**에 종속         |
| **스레드 특성**   | 개별 인스턴스는 **스레드-세이프 전제 아님**              | **싱글톤 → 상태 없음**으로 설계 권장           | 보통 요청 범위, 공유 안 함     | **불변이면 안전**(권장)             |
| **대표 어노테이션** | @Entity, @Id, @Table                    | @Component, @Service, @Repository | (없음, 검증용 @NotNull 등) | @Embeddable / 필드에 @Embedded |
| **책임**       | **도메인 상태·행위(비즈니스 규칙)**                  | **조립/조정/유스케이스/인프라**               | **표현·전달·검증**         | **개념·불변성·자기 검증**            |

## 요청예시 회원가입 흐름(축약)

1. **GET /members/new**: 컨트롤러가 빈 **Form DTO**를 뷰에 전달.
2. **POST /members**: 요청 DTO 검증 → 서비스 **register()** 호출.
3. **Application**: **트랜잭션 시작**, **Member.create(…)**로 엔티티 생성·검증 → **리포지토리**에 저장 → (선택) **도메인 이벤트 발행**.
4. **Infra(JPA)**: INSERT 수행, 커밋.
5. **Controller**: **Response DTO**로 응답/리다이렉트.

### **1단계: 회원가입 화면 요청 (GET)**

1. **사용자 행동**: "회원가입" 버튼 클릭
2. Presentation(**Controller**) :`GET /members/new` 요청을 받습니다.
    - `MemberController`는 화면을 그리는데 필요한 빈 껍데기 객체인 `MemberForm` DTO를 생성합니다.
    - 생성한 DTO를 `Model`에 담아 return를 통해 뷰로 전달합니다.
3. **View (화면)**
    - 컨트롤러가 전달한 DTO를 기반으로 사용자가 정보를 입력할 빈 폼을 그립니다.

### **2단계: 회원가입 정보 제출 및 처리 (POST)**

1. **사용자 행동**: 폼에 정보를 입력 후 "제출" 클릭
2. Presentation(**Controller**) :`POST /members` 요청을 받습니다
    - 사용자가 입력한 폼 데이터는 `@Valid` 어노테이션과 함께 `MemberForm` **요청(Request) DTO**로 변환되어 들어옵니다.
    - 받은 DTO를 Application 계층(서비스)의 `register()` 같은 메서드로 전달하여 회원가입 처리를 위임합니다.
		- **핵심 원칙**: 컨트롤러는 **DTO로** 데이터를 받고 보냅니다. 컨트롤러는 엔티티를 다루지 않습니다
3. **Application (Service)**
    - `@Transactional`에 의해 **트랜잭션이 시작됩니다.**
    - 컨트롤러에서 받은 DTO를 기반으로 실제 `Member` **도메인 엔티티를 생성**합니다.
    - **핵심 원칙**: 엔티티 생성 및 데이터 검증 로직은 `Member.create(...)`와 같이 엔티티 스스로가 책임집니다. (도메인 주도 설계)
    - `Repository` 인터페이스를 통해 엔티티 저장을 요청합니다.
    - (선택) 회원가입이 완료되었다는 **도메인 이벤트**(예: `MemberRegisteredEvent`)를 발행하여, 이메일 발송, 쿠폰 지급 등 다른 모듈에서 비동기적으로 처리하도록 할 수 있습니다.
        
4. **Infrastructure (Repository / JPA)**
    - 서비스의 저장 요청을 받은 JPA 구현체(Hibernate 등)가 실제 DB에 **INSERT 쿼리를 실행**합니다.
    - Application 서비스의 트랜잭션이 정상적으로 끝나면, 변경 사항이 **DB에 최종 반영(Commit)**됩니다.
        
5. **Presentation (Controller - 응답 처리)**
    - 서비스 계층으로부터 처리 결과를 돌려받습니다.
    - 결과를 사용자에게 보여줄 **응답(Response) DTO**로 변환하거나, 가입 완료 페이지로 리다이렉트(Redirect)시켜 최종 응답을 반환합니다.

> 포인트: 컨트롤러는 “데이터 운반/검증”만, 규칙은 **도메인**이 들고, 트랜잭션/조립은 **애플리케이션**이 책임.

## **Use Case**로 흐름 재정의

- **Use Case**: “사용자/시스템의 목표 단위”. **하나의 업무 흐름**을 정의·실행하는 **작업 단위**. -> 트랜잭션이라는 기술을 사용해 구현
	- ex) 회원가입, 주문 생성, 비밀번호 재설정
- **Application**: 유스케이스 실행자. **트랜잭션 경계 + 오케스트레이션(흐름 제어)**.
- **Presentation**: 요청/응답 경계. **입·출력, 검증, 바인딩, 예외→HTTP 변환**.
- 클라이언트 요청이 들어오면 **Presentation** 계층이 입력을 검증해 요청 DTO로 묶고 **Application** 계층의 특정 **유스케이스**를 호출한다;
- Application 서비스는 유스케이스를 중심으로 필요한 도메인 객체·리포지토리를 순서대로 호출하는 **오케스트레이션**을 수행하면서 @Transactional로 **트랜잭션** 경계를 연다.
- 이때 저장/조회 같은 영속화 작업은 도메인 포트를 통해 어댑터(out)로 위임된다
- 어뎁터 내부에서 기술인 **JPA**을 이용해 **영속성 컨텍스트**를 사용해 엔티티를 1차 캐시에 관리하며 변경 감지로 적절한 INSERT/UPDATE SQL을 만든다.
- 유스케이스가 성공하면 커밋 시점에 영속성 컨텍스트가 flush되어 SQL이 DB에 반영되고, Application은 결과를 응답 DTO로 변환해 Presentation이 최종 **HTTP 응답**으로 반환한다.

결론: Use Case(목표)를 Application(구현)하고, Presentation/Controller(창구)를 통해 요청을 받아 Transaction(안전장치) 위에서 영속성 컨텍스트(작업대)를 이용해 처리하는 것입니다

- **"무엇을 만들어야 하지?" (목표 정의)**
    - ➡️ **Use Case**를 정의합니다. (예: "회원을 가입시킨다.")
- **"사용자가 어떻게 요청을 보내지?" (입구 설계)**
    - ➡️ **Presentation** 계층을 설계하고, `/members` 같은 URI를 담당할 **Controller**를 만듭니다.
- **"실제 일은 누가 총괄하지?" (작업 총괄자 지정)**
    - ➡️ **Application** 계층의 서비스(`MemberService`)가 Use Case를 구현하도록 합니다.
- **"일을 안전하게 처리하려면?" (안전장치 부착)**
    - ➡️ Application 서비스 메서드에 `@Transactional`을 붙여 **Transaction** 범위를 설정합니다.
- **"JPA는 어떻게 효율적으로 일하지?" (내부 동작 이해)**
    - ➡️ Transaction 범위 내에서 JPA가 **영속성 컨텍스트**를 활용해 엔티티를 관리하고 DB에 반영할 것을 인지합니다.
## **단방향 데이터 흐름 원칙**

요청은 항상 바깥에서 안쪽으로, **`API(in)` → `Application` → `Domain`** 순서로 흐릅니다. Domain은 다시 **인터페이스(Port)를 통해 `Infra(out)`** 계층에 영속성을 위임하며, 이 흐름은 절대 역행하지 않습니다.

## **5) 구현 원칙(실무 체크리스트)**

- **컨트롤러** :DTO를 받아서 서비스에 넘기는 역할만 충실
    - 요청 DTO(폼/커맨드) ↔ 응답 DTO(뷰/API) 변환 전담.
    - 컨트롤러내에선 엔티티 생성/변경 로직 **금지**.
- **서비스(애플리케이션)**
    - **트랜잭션 경계**.
    - 파라미터 많으면 **전용 Command DTO** 도입
        - 예) updateProfile(a,b,c,d,......)
	        -> updateProfile(ProfileUpdateCommand cmd)
- **엔티티/값 객체(도메인)**
    - **Setter 대신 의미 메서드**:
        - 나쁨) setPoint(1000)
        - 좋음) addPointsForPurchase(20), applyCoupon(10)
    - 정책 변경 시 **엔티티만 수정하면** 서비스 호출부는 그대로.
    - 값 객체는 **불변** + **자기 유효성 보장**(생성 시 검증).
- **리포지토리**
    - **도메인 인터페이스**(예: OrderRepository)는 domain에,
    - **구현체**(예: JpaOrderRepository)는 infra에.
- **이벤트**
    - 중요한 상태 전이엔 **도메인 이벤트** 발행(후처리/통합에 유용).
- **네이밍/분리**
    - 요청: SomethingCommand/Request, 응답: SomethingResponse.
    - 엔티티/DTO 속성명이 달라져도 **도메인 규칙 우선**(DTO는 표현 최적화).
- 왜?
	- 컨트롤러가 엔티티 생성/변경하는 비즈니스 로직까지 하면 역할을 나눈의미가 없어 유지보수가 힘듬
    - 파라미터 많으면 **전용 Command DTO** 로 받기
	    - updateProfile(String nickname, String email, String address, ...) -> `updateProfile(ProfileUpdateDto dto)`
	    - 프로필에 '전화번호'를 추가해야 할 때, DTO에 필드 하나만 추가하면 끝나요. 만약 DTO를 안 썼다면 이 기능을 사용하는 모든 메서드의 파라미터를 일일이 수정해야 하죠.
	- setter, 의미메서드 모두 메서드이다. 그러나 비즈니스 규칙과 책임이 어디에 있는가에 따라 다르다
		- `setPoint(1000)`: 받은값 그대로 저장하기만 한다.
			- setter를 사용할때마다 서비스에 포인트 저장규칙 대한 로직을 추가적으로 작성해야한다.
			- 만일 포인트 저장규칙이 바뀌면 찾아다니며 일일히 바꿔야한다
		- addPointsForPurchase(20)`, `addPointsForCoupons(10)`:
			- 서비스에서 로직대신 이름으로 기능을 유추가능한 메서드를 호출해 한줄처리
			- 포인트 정책이 바뀌어도 `User` 엔티티만 수정하면 된다

## **6) 헷갈리는 포인트, 바로 답합니다**

- **Q. 엔티티도 스프링이 관리하나요?**

    A. **아니요.** 엔티티는 스프링 빈이 아니라 **영속성 컨텍스트(JPA)** 가 변경감지/지연로딩 등을 처리하며 관리합니다.

- **Q. “DTO vs 엔티티"

    A. DTO는 도메인 모델이 아님. 순수한 데이터 전달이 목적으로, **입출력/전달용** 구조체이다. 보통 컨트롤러나 application 경계에서 직렬화/검증/표현 전환 전용으로 사용된다. 유효성 로직을 엔티티에 작성하는게 아니라 DTO에 작성해 관리해서 유지보수를 좋게 한다 (비즈니스 로직 x)

    엔티티 : 도메인 규칙/불변식

- **Q. 값 객체와 엔티티 차이?**

    A. **식별자 유무**와 **동등성 기준**. 값 객체는 식별자(@Id) 없이 **값 동등성**, 대체로 **불변**이며 엔티티에 **내장**되어 함께 저장.

	    예: Address(city, street, zip)

    - @Embeddable로 정의, 엔티티에 @Embedded로 사용 ⇒ **별도 테이블 없이** 컬럼들로 함께 저장.
    - **불변(immutable)** + **자기 유효성 보장**이 베스트 프랙티스.
- **Q. 스프링 빈은 왜 싱글톤?**
	- 스프링 빈은 **기본 싱글톤**. 요청마다 만들어지는 게 아니라 **하나를 공유**하니, **상태를 들고 있지 않게(Stateless)** 설계해야 안전합니다.
	- 상태가 필요하면 **메소드 지역 변수**로 두거나, **프로토타입/리퀘스트 스코프**를 고려.

## **7) 작은 예시로 보는 차이**

- **나쁜 서비스 코드**

```
user.setPoint(1000); // 규칙 부재, 중복/누락 위험
```
    
- **좋은 도메인 메서드 중심**

```
user.addPointsForPurchase(20);
user.addPointsForCoupons(10);
// 포인트 정책 변경 시 User 엔티티만 수정하면 됨
```
    
- **Command DTO로 확장 여지 확보**

```
// 컨트롤러
@PostMapping("/profile")
public void update(@Valid ProfileUpdateRequest req) {
    appService.updateProfile(req.toCommand());
}

// 서비스
public void updateProfile(ProfileUpdateCommand cmd) { ... }
// 전화번호 추가돼도 Command/매핑만 수정하면 서비스 시그니처 유지
```

## **8) 마무리 체크리스트**

- 도메인은 어떤 기술에도 **의존하지 않는다**
- 엔티티는 **의미 있는 메서드**로만 상태를 바꾼다
- 값 객체는 **불변**이며 **자기 검증**을 수행한다
- 리포지토리는 **도메인 인터페이스**, 구현은 **인프라**
- 애플리케이션 서비스는 **트랜잭션/오케스트레이션**만
- 컨트롤러는 **DTO 매핑/검증**에만 집중한다
- 도메인 이벤트로 **중요한 상태 전이**를 외부로 알린다
- DTO와 엔티티를 **혼용하지 않는다**
- 스프링 빈은 **상태 없음**(싱글톤 전제)
- 테스트는 **도메인 단위**로(기술 격리) 먼저 작성한다
