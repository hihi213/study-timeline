# 📖 DBMS 심층 분석: 엔진의 원리부터 SQL 최적화까지

데이터베이스 성능 최적화는 단순히 쿼리를 짧게 줄이는 기술이 아닙니다. 엔진이 데이터를 **어떻게 메모리로 가져오고(Physical)**, **어떤 순서로 처리하며(Logical)**, 그 과정에서 **어떤 제약(Constraint)**이 발생하는지를 이해할 때 비로소 근본적인 튜닝이 가능합니다.

---

## 1. [Physical] 물리적 한계와 버퍼 캐시 (The Bottleneck)

DBMS 튜닝의 대전제는 **"디스크 I/O를 최소화하고, 메모리 히트율을 극대화하는 것"**입니다. 이는 하드웨어의 태생적 속도 차이에서 기인합니다.

### 🛑 속도의 간극: CPU vs Disk

1. **속도 차이:** CPU는 나노초(ns) 단위로 동작하는 초고속 장치이지만, 디스크는 물리적인 회전(HDD)이나 셀 접근(SSD)이 필요하여 밀리초(ms) 단위로 매우 느립니다.
2. **단위 차이:** CPU는 바이트(Byte) 단위의 정밀한 처리를 원하지만, 디스크는 블록(Block, 보통 $8KB \sim$) 단위의 뭉텅이 데이터만 제공합니다.
    

### ⚙️ 해결책: 버퍼 캐시 (Buffer Cache)

이 간극을 메우기 위해 DBMS는 **버퍼 캐시**라는 메모리 공간을 둡니다.

- **적재 (Block I/O):** 디스크의 데이터 블록을 통째로 메모리에 복사합니다.
- **연산 (Memory Access):** CPU는 오직 메모리에 올라온 데이터만 읽거나 수정합니다.
- **기록 (Dirty Write):** 변경 사항은 즉시 디스크에 쓰지 않고, 나중에 일괄 기록합니다.
    

> [!TIP] SQL은 디스크가 아닌 '메모리'를 조작하는 명령어입니다.
> 성능은 결국 "누가 더 적은 블록을 메모리로 불러와서(I/O 감소), 효율적으로 재사용하느냐"에 달려 있습니다.

---

## 2. [Logical] SQL의 실행과 FETCH 메커니즘

물리적으로 메모리에 데이터가 올라왔다면, 논리적으로는 데이터를 골라내는 작업인 **FETCH**가 수행됩니다.

### 🔄 FETCH와 커서 (The Action)

DBMS가 데이터를 사용자에게 보여줄 때, 한 번에 가져오는 것이 아니라 내부적으로 **커서(Cursor)**를 이동시키며 한 줄(Row)씩 읽어들이는 반복 과정(Loop)이 일어납니다.

1. **커서 이동:** 포인터를 다음 행(Row)으로 이동.
2. **로드 (Load):** 해당 행을 읽음.
3. **⚡ 처리:** **이 찰나의 순간(Fetch Loop 내부)에 무엇을 하느냐가 성능과 정합성을 결정합니다.**
    

### 📋 옵티마이저의 실행 순서

DBMS 엔진(옵티마이저)은 **데이터를 메모리로 가져오는 순서**로 SQL 실행 계획을 짭니다.

|**순서**|**절 (Clause)**|**역할 및 튜닝 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업할 테이블을 메모리에 올릴 준비|
|**2**|**WHERE**|**(필터링)** 조건에 안 맞는 행을 버림. **성능의 90%가 결정되는 곳**|
|**3**|**GROUP BY**|**(집계)** 남은 데이터를 기준별로 묶음|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 조건 선별|
|**5**|**SELECT**|**(표현)** 최종 결과 출력 / **함수가 실행되는 시점**|
|**6**|**ORDER BY**|**(정렬)** 결과를 순서대로 나열|
> **💡 Insight:** `WHERE` 절에서 데이터 양을 획기적으로 줄여야, 이후 `SELECT` 절에서 실행되는 **함수의 실행 횟수**도 줄어듭니다.

## 3. [Constraint] 핵심 메커니즘: Read before Write


### "데이터를 읽어야 쓸 수 있다(Read before Write)"

데이터베이스의 모든 작업은 **"대상을 찾는 것(Fetch)"**에서 시작됩니다.
데이터를 수정하거나 삭제(`UPDATE`,`DELETE`)하는 DML 작업조차도 내부적으로는 반드시 **Fetch(읽기)** 과정이 선행되어야 합니다.
### ⚙️ DML(수정/삭제)의 내부 동작 단계

사용자가 `UPDATE users SET salary = salary * 1.1 WHERE id = 100`을 실행하면 엔진은 다음과 같이 움직입니다.

1. **FETCH (읽기):** `id` 인덱스를 뒤져 `100`번 위치를 찾아 **메모리로 로딩**합니다. (인덱스가 없으면 전체를 뒤져야 합니다.)
2. **LOCK (잠금):** 찾은 행(Row)을 다른 트랜잭션이 건드리지 못하게 잡습니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 로그(Redo Log)를 남깁니다.
    

> [!NOTE] 구조적 이해를 통한 최적화
> Mechanics: DB는 디스크가 아닌 메모리에서 일합니다. UPDATE가 느리다면, 쓰기 속도 문제라기보다 대상을 메모리로 퍼올리는 읽기(Fetch) 과정이 느린 경우가 많습니다. 먼저 인덱스 튜닝을 고려하십시오.

### 🚫 할로윈 문제 (Halloween Problem)

데이터를 **읽는 도중에(Fetch Loop 안에서)** 수정하면 어떻게 될까요? 수정된 데이터가 인덱스 순서상 뒤로 이동하여, 커서가 **이미 읽은 행을 또 읽거나 건너뛰는 현상**이 발생합니다. 이를 방지하기 위해 DBMS는 읽기와 쓰기 로직을 분리합니다. (함수와 프로시저)

## 4. [Roles] 개발자와 시스템의 역할 분담

최적화된 시스템을 구축하기 위해서는 사용자와 시스템(DBMS)의 역할을 명확히 이해해야 합니다.

### 👤 User (개발자): 로직의 구현 (Definition)

개발자는 **"무엇을(What)"** 원하고 **"어떤 로직(Logic)"**으로 처리할지를 정의합니다.

- **SQL (요구사항):** 최종 결과물(데이터)을 정의합니다. (선언형)
- **함수 (연산):** FETCH 루프 **안**에서 실행되는 계산 로직. (Read-Only)
- **프로시저 (제어):** FETCH 루프 **밖**에서 실행되는 비즈니스 흐름 및 트랜잭션 제어. (Read & Write)
    

### 🤖 System (옵티마이저): 실행의 최적화 (Execution)

옵티마이저는 개발자가 정의한 로직(Target)을 분석하고, 도구(Tool)를 활용하여 최적의 경로(Plan)를 짭니다.

- **Target:** SQL 문장, 프로시저(미리 컴파일됨), 함수(CPU 비용으로 계산됨).
- **Tools:** 옵티마이저가 "어떻게 하면 데이터를 가장 빠르게 가져올까?"를 판단할 때 **참조하는 자원**입니다.
	- **인덱스 (Index):** 데이터를 빠르게 찾기 위한 자료구조(B-Tree 등).
	- **통계 정보 (Statistics):** 데이터의 분포도, 행의 개수, 블록 수 등 판단의 근거.
	- **시스템 지표 (System Metrics):** CPU 속도, 디스크 I/O 속도 등 하드웨어 환경 정보.

## 5. [Actors] 실행의 주체: 함수 vs 프로시저

"읽어야 쓸 수 있다"는 제약과 "할로윈 문제(읽는 도중 수정되어 순서가 꼬임)"를 방지하기 위해, 개발 객체는 엄격히 분리됩니다.

### A. 함수 (Function): Fetch의 부속품
Fetch 도중이므로 데이터 위치를 바꾸는 `INSERT`, `UPDATE` 불가.
- **위치:** `SELECT`나 `WHERE` 절 내부 (Fetch Loop **안**)
- **빈도:** 조회되는 **행(Row)의 수만큼** 반복 실행.
- **역할:** 값을 가공하여 리턴하는 **Read Only 계산기**.


### B. 프로시저 (Procedure): 트랜잭션의 지휘자

- **위치:** SQL문 외부, 애플리케이션 호출 (Fetch Loop **밖**)
- **빈도:** 호출 시 **1회** 실행.
- **역할:** 비즈니스 로직(CRUD)을 총괄하고 `COMMIT/ROLLBACK`을 수행
 

|**구분**|**함수 (Function)**|**프로시저 (Procedure)**|
|---|---|---|
|**FETCH와의 관계**|**종속됨** (Loop 안에서 실행)|**명령함** (Loop 밖에서 제어)|
|**데이터 변경**|**불가능** (할로윈 문제 방지)|**가능** (트랜잭션 관리)|
|**핵심 역할**|단순 연산 및 변환|비즈니스 흐름 제어|

## 6. [Optimization] 성능 최적화의 핵심 전략

위의 원리들을 종합했을 때, 최적화의 핵심은 **"인덱스를 활용해 Fetch 대상을 줄이는 것"**으로 귀결됩니다.

### ⚡ 인덱스 튜닝: 좌변을 가공하지 말라

인덱스는 **컬럼의 원본 값**을 기준으로 정렬되어 있습니다. `WHERE` 절에서 컬럼(좌변)을 함수로 감싸면 정렬된 순서가 깨져 인덱스를 사용할 수 없습니다.

#### ❌ Bad Case (좌변 가공: 인덱스 불가)



```SQL
-- 엔진: "값을 연산해봐야 아니까, 미리 정렬된 인덱스는 쓸모가 없군. 전체를 뒤져라(Full Scan)."
WHERE YEAR(date_col) = '2024'
```

#### ✅ Good Case (우변 가공: 인덱스 활용)



```SQL
-- 엔진: "컬럼이 깨끗하군. 인덱스를 타고 범위 검색(Range Scan)으로 바로 찾아가자."
WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'
```

## 7. 📝 종합 결론 (Action Plan)

데이터베이스를 잘 다룬다는 것은 **"메모리 위에서의 데이터 이동(Fetch)"**을 이해하고 통제한다는 뜻입니다.

> [!TIP] **Action Plan**
>
> 1. **역할 분리:** 단순 값 계산은 **함수**로, 데이터 변경 및 트랜잭션 관리는 **프로시저**로 명확히 나누십시오.
>     
> 2. **가공 금지 (Left-Side):** `WHERE` 절의 컬럼(좌변)은 절대 건드리지 말고, 비교값(우변)을 맞추십시오.
>     
> 3. **양 줄이기 (Filter Early):** 쿼리 튜닝의 시작과 끝은 `WHERE` 절에서 인덱스를 통해 **메모리에 올릴 데이터 블록 수를 줄이는 것**입니다.
>


옵티마이저가 분석하고 처리해야 할 **작업물**은 개발자로부터 받는다.
- **SQL 문장:** 처리해야 할 기본 요청 단위입니다.
- **프로시저 (Container):**
    - 옵티마이저는 생성(컴파일) 시점에 내부 SQL들을 미리 분석하여 **실행 계획을 수립(Pre-compile)**해 둡니다.
    - 실행 시 저장된 계획을 재사용하므로 파싱 부하가 감소합니다.
- **함수 (Workload):**
    - 옵티마이저 입장에서 함수는 **"행(Row)마다 CPU를 사용하여 계산해야 하는 비용"**으로 간주됩니다.
> [!note]- 데이터베이스 작동 메커니즘의 핵심
>
> 1. **역할의 분리:**
> 	- 사용자가 작성한 **SQL은** 데이터 요구사항을, **함수와 프로시저는** 구체적인 비즈니스 로직을 구현합니다.
> 	- **DBMS의 옵티마이저**는 이를 수행하기 위한 최적의 **방법**(실행순서,접근경로)을 결정하여 데이터 처리를 실행합니다.
> 		<br>
> 1. **로직의 구현 (User):**
> 	사용자는 **연산 중심의 읽기(Read)** 로직은 **함수**로,
> 	**상태 변경 및 트랜잭션 제어(Write)** 로직은 **프로시저**로 구분하여 구현합니다
> 		<br>
> 2. **실행의 최적화 (System):**
> 	옵티마이저는 전달받은 로직(Target)을 분석하고, 인덱스 등(Tool)을 활용하여 비용이 가장 낮은 경로(Plan)를 수립해 실행합니다.
