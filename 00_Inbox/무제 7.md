# 🏗️ [Deep Dive] DBMS 메커니즘과 SQL 최적화 가이드

데이터베이스 성능 최적화는 단순히 쿼리를 짧게 쓰는 것이 아닙니다. **"엔진이 데이터를 어떻게 메모리로 가져오고(Physical), 어떤 순서로 처리하며(Logical), 그 과정에서 어떤 제약이 발생하는지"** 를 이해하는 것이 핵심입니다.

## 1. 물리적 기반: 메모리 중심의 작동 (Mechanism)
### CPU는 디스크에 직접 접근해 데이터를 다루지 않는다.
디스크는 느리고, 메모리 너무 빠릅니다
디스크는 데이터를 다루는 최소단위가 cpu에 비해 너무 큽니다.
그래서 **버퍼 캐시(Buffer Cache)** 라는 메모리가 중간 역할을 합니다.
그래서 모든 튜닝의 제1원칙은 **"디스크 I/O를 줄이고 메모리 히트율을 높이는 것"**입니다.
### ⚙️ 작동 메커니즘 (Mechanism)

1. **Block I/O(적재):** 디스크의 데이터 블록을 메모리(Buffer Cache)로 적재합니다.
2. **Memory Access(연산):** CPU는 메모리에 올라와 있는 데이터만 읽거나 수정할 수 있습니다.
3. **Flush:** 변경된 데이터는 즉시 디스크에 쓰지 않고, 나중에 일괄 기록(Dirty Write)합니다.

> - **SQL의 대상:** 우리가 작성한 SQL은 디스크가 아닌 **메모리(Buffer Cache)**를 조작하는 명령어입니다.
> - **성능의 척도:** 결국 "누가 더 적은 블록을 메모리로 불러와서 효율적으로 쓰느냐"가 성능을 결정합니다.
## 2. 논리적 실행 체계: 순서가 제약을 만든다

물리적으로 메모리 위에서 동작한다는 것을 알았다면, 이제 엔진이 **"어떤 순서로 계획을 짜고(Plan), 실행하며(Action), 그로 인해 어떤 제약(Constraint)이 생기는지"** 이해해야 합니다.
### A. 개발자와 데이터베이스의 역할분담

개발자는 하단을 정의해 전달한다
#### SQL (요구사항 정의)

- **역할:** 데이터의 추출, 조작, 제어에 대한 최종 **결과물(Requirement)** 을 기술합니다.
- **특징:** 구체적인 탐색 경로(How)는 기술하지 않는 선언형 언어입니다.

#### 함수와 프로시저 (비즈니스 로직 정의)

SQL만으로 표현하기 힘든 절차적 흐름이나 복잡한 연산을 정의합니다.

### B. 계획과 순서: 옵티마이저와 SQL 실행 순서

 엔진은 개발자가 작성한 순서가 아닌, 위의 메모리기반 작동에 따라, **"대상을 메모리로 가져오는 것"** 이 먼저 선행되어야 합니다.
 물리적으로 메모리에 데이터를 올렸다면, 이제 논리적으로 데이터를 걸러낼 차례입니다.

> **핵심:** 옵티마이저는 이 순서에 따라 데이터를 단계별로 걸러내며 비용을 계산합니다.

|**실행 순서**|**절 (Clause)**|**설명 및 튜닝 포인트**|
|---|---|---|
|**1**|**FROM / JOIN**|**(대상 선정)** 작업할 테이블과 데이터셋을 메모리로 가져올 준비를 합니다.|
|**2**|**WHERE**|**(필터링)** 조건에 안 맞는 행을 버립니다. **여기서 데이터 양을 얼마나 줄이느냐가 성능의 90%를 결정**합니다.|
|**3**|**GROUP BY**|**(집계)** 남은 데이터를 기준에 따라 묶습니다.|
|**4**|**HAVING**|**(2차 필터링)** 그룹핑된 데이터 중 특정 조건만 남깁니다.|
|**5**|**SELECT**|**(표현)** 최종 결과를 출력하거나 계산식을 수행합니다.|
|**6**|**ORDER BY**|**(정렬)** 사용자에게 보여주기 위해 순서를 나열합니다.|

### C. 실행의 본질: 선(先)조회 후(後)조작 (Read before Write)

위의 메모리기반 작동에 따라, 데이터를 조작하는 DML 작업도 **"대상을 메모리로 가져오는 것"** 이 먼저 선행되어야 합니다.

1. **FETCH (읽기):** `FROM` -> `WHERE`을 수행하여 대상을 찾아 **메모리(Buffer Cache)로 로딩**합니다.
    - 로딩후 커서를 움직입니다. _커서(Cursor): 현재 읽고 있는 행을 가리키는 포인터_
    - _이 단계에서 인덱스가 없다면 테이블 전체를 뒤지는 비효율이 발생합니다._
        
2. **LOCK (잠금):** 찾은 행(Row)을 다른 사람(트랜잭션)이 건드리지 못하게 잡습니다.
3. **WRITE (쓰기):** 메모리 상의 데이터를 변경하고 장애 복구를 위해 로그(Redo/Undo)를 남깁니다.
    

> **💡 Insight:** 쓰기 성능을 높이고 싶다면, 역설적으로 **"대상을 빨리 찾는 읽기 튜닝(인덱스 최적화)"**이 선행되어야 합니다..

### D. 필연적 제약: 할로윈 문제와 역할 분리

"읽어야 쓸 수 있다(Read before Write)"는 메커니즘 때문에, **"읽고 있는 도중(Fetch 진행 중)"**에는 데이터 변경이 엄격히 제한됩니다.

- 문제 (The Halloween Problem):
    
    만약 읽는 도중 데이터의 위치나 값이 바뀌면, 커서(Cursor)가 이미 읽은 행을 또 읽거나 건너뛰는 현상이 발생합니다.
    
- 해결 (Implementation Strategy):
    
    이 제약 때문에 개발 로직은 읽기 전용과 제어 전용으로 명확히 나뉩니다.
할로윈 문제를 피하고 엔진의 특성에 맞게 로직을 설계해야 합니다.

### A. 함수 (Function) - Read Only

- **위치:** SQL 문장 내(`SELECT`, `WHERE` 절 등) 표현식으로 사용됩니다.
- **실행 시점:** Fetch(읽기) 단계 내부.
    - Fetch 단계이므로 내부에서 `INSERT`, `UPDATE` 등 **상태 변경 불가**
- **위험성:** `WHERE` 절에 사용 시 인덱스 사용을 방해하거나, 모든 행마다 실행되어 성능 저하 유발 가능.
    

### B. 프로시저 (Procedure) - Transaction Control

- **성격:** 비즈니스 로직의 **전체 흐름을 제어**하는 실행 컨테이너입니다.
- **위치:** 애플리케이션에서 호출하는 최상위 진입점입니다. (SQL 내부에서 호출 불가)
- **실행 시점:** Fetch가 끝난 후 독립적으로 실행.
    - Fetch가 끝난 후이므로 트랜잭션(`COMMIT`/`ROLLBACK`) 제어 가능, 자유로운 데이터 변경(`DML`) 가능.

## 4. 성능 최적화: 인덱스를 태워라

옵티마이저가 가장 먼저 수행하는 `WHERE` 절에서 인덱스를 제대로 타게 하는 것이 튜닝의 시작과 끝입니다.

### 🚨 핵심 튜닝: 좌변 가공 금지 (No Left-side Manipulation)

DB의 인덱스는 **컬럼의 원본 값**을 기준으로 정렬되어 있습니다. 컬럼(좌변)을 가공하는 순간, 인덱스 정렬이 깨져 **Full Table Scan(전체 뒤지기)**이 발생합니다.

- **Bad Case:** `WHERE YEAR(date_col) = '2024'`
    - **원인:** 인덱스는 `date_col` 원본 값 기준으로 정렬되어 있습니다. 이를 `YEAR()` 함수로 2차 가공하면, 정렬 순서가 깨져 인덱스 매칭이 불가능해집니다.
    - **결과:** 인덱스를 포기하고 전체 데이터를 뒤지며 모든 행에 대해 함수를 실행합니다.
- **Good Case:** `WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31'`
    - **해결:** 컬럼은 그대로 두고, 비교할 값(우변)을 가공하여 **인덱스 범위 스캔(Range Scan)**을 유도해야 합니다.
    - **효과:**
        
        1. `WHERE` 절이 인덱스를 통해 대상을 먼저 줄임.
        2. 필터링된 결과 집합에 대해서만 필요한 함수가 실행됨.

## 💡 종합 요약 (Summary)

> [!note] **구조적 이해를 통한 최적화**
>
> 1. **Mechanics:** DB는 디스크가 아닌 **메모리**에서 일합니다. 따라서 수정(`UPDATE`)하려 해도 먼저 메모리로 불러오는 **읽기(Fetch)** 과정이 필수입니다.
>     
> 2. **Flow:** SQL은 `FROM` $\rightarrow$ `WHERE` $\rightarrow$ `SELECT` 순으로 작동합니다. 데이터가 걸러지는 `WHERE` 절에서의 효율이 성능을 좌우합니다.
>     
> 3. **Optimization:**
>     
>     - `WHERE` 절의 컬럼을 가공하지 마십시오. (인덱스 보호)
>         
>     - 단순 연산은 **함수**, 데이터 변경 흐름은 **프로시저**로 역할을 분리하십시오.
>         

> [!tip] **핵심 정리**
>
> 1. **Write는 Read를 포함한다:** 수정/삭제가 느리다면, 타겟 데이터를 찾는 **인덱스(Read)**부터 점검하십시오.
>     
> 2. **컬럼은 신성불가침이다:** `WHERE` 절의 컬럼을 함수로 감싸는 순간 인덱스는 무용지물이 됩니다. (항상 비교 값을 가공할 것)
>     
> 3. **역할을 분리하라:**
>     
>     - 값의 계산/변환 $\rightarrow$ **함수 (Function)**
>         
>     - 데이터 변경/트랜잭션 제어 $\rightarrow$ **프로시저 (Procedure)**
>
