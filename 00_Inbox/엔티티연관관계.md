# **JPA 연관관계 레시피 & 체크리스트(Owner/mappedBy/cascade)**

## **TL;DR**

- **화살표 시작점 = FK = 주인(owner)**. 주인 쪽 필드를 바꿔야 DB FK가 갱신됨.
- **mappedBy = 거울(inverse)**. DB 수정 X, 조회용.
- **cascade/orphanRemoval**은 “부모만 건드려도 자식까지 같이”가 필요할 때만, 애그리거트 내부에 한정.
- **단방향**: 한쪽만 참조. **양방향**: 양쪽 참조하되 주인은 하나

## **결정 순서(5단계)**

1. **관계 종류** 결정: N:1, 1:1, N:N(→실무는 연결 엔티티).
2. **FK 위치 = 주인** 결정(대부분 N측, 1:1은 의존/자식).
3. **단/양방향** 결정(양방향이면 한쪽만 주인, 반대는 mappedBy).
4. **매핑 방식** 선택: @JoinColumn vs @JoinTable(특수 케이스).
5. **전파/삭제 규칙**: cascade, orphanRemoval(애그리거트 내부만).

## **관계별 레시피(최소 예시)**

### **N:1 양방향(가장 흔함)**

```java
// N측 = 주인
@ManyToOne(fetch = LAZY) @JoinColumn(name="member_id")
private Member member;

// 1측 = 거울
@OneToMany(mappedBy = "member")
private List<Order> orders = new ArrayList<>();
```

### **1:N 단방향(가급적 지양, 불가피할때 시)**
- 1:N 단방향이 꼭 필요하면 부모 컬렉션에 @OneToMany @JoinColumn(자식 FK 생성) 또는 @JoinTable 사용
```java
@OneToMany
@JoinColumn(name="parent_id") // 자식 테이블에 FK 생성
private List<Child> children = new ArrayList<>();
```

> 단점: 자식 업데이트 SQL이 추가로 나갈 수 있음. 가능하면 N:1 양방향로.

### **1:1(의존 쪽에 FK, 필요시 공유 PK)**

```java
// 주인(의존/자식)
@OneToOne(fetch = LAZY) @JoinColumn(name="delivery_id")
private Delivery delivery;

// 또는 공유 PK
@OneToOne @MapsId @JoinColumn(name="order_id")
private Delivery delivery;
```

### **N:N(학습용만, 실무는 분해)**

```java
// 연결 엔티티 권장
class CategoryItem {
  @ManyToOne @JoinColumn(name="category_id") Category category;
  @ManyToOne @JoinColumn(name="item_id")     Item item;
  // 필요 메타필드: 순번, 기간, 생성자 등
}
```

## **주인/거울 표기**

- @JoinColumn(...) = “**여기가 주인(FK 칼럼)**, INSERT/UPDATE 여기서 한다.”
- mappedBy="..." = “**FK는 저쪽 필드**. 나는 거울(읽기 전용).”

## **캐스케이드(Cascade) — “부모만 persist/remove 해도 자식까지 같이 전파”**
- 어디에? → @OneToOne/@OneToMany/@ManyToOne/@ManyToMany의 속성으로.
- 종류: PERSIST/REMOVE/MERGE/REFRESH/DETACH/ALL.
- orphanRemoval=true : 컬렉션에서 제거하거나 FK 끊어 **고아**가 되면 자동 DELETE.
- 권장 사용처:
    - Order → OrderItem: cascade=ALL, orphanRemoval=true ✅
    - Order ↔ Delivery(1:1 의존): cascade=ALL ✅
    - @ManyToOne(자식→부모): 보통 ❌ (부모는 독립 생명주기)
    - **공유 엔티티**에는 REMOVE/ALL ❌(연쇄 삭제 위험)
- 주의: **JPA cascade ≠ DB ON DELETE CASCADE**(혼용 시 동작이 겹쳐 예측 어려움).
- 기본적으로는 연관된 엔티티마다 em.persist(...)를 **각자** 호출해야 해요.
    예) em.persist(orderItemA); em.persist(orderItemB); em.persist(order); …
- @OneToMany(mappedBy="order", cascade = CascadeType.ALL) 처럼 **캐스케이드**를 켜면,
    - em.persist(order) 한 번으로 order.orderItems에 들어있는 A,B,C, 그리고
        @OneToOne(cascade = ALL)인 delivery까지 **자동으로 같이 persist** 됩니다.
    - em.remove(order) 하면 자식들도 **같이 remove**가 전파됩니다(= CascadeType.REMOVE 포함 시).
    - **컬렉션에서 빼면 자동 삭제**되길 원하면 orphanRemoval = true도 함께 사용하세요.
        - order.getOrderItems().remove(a) → DB에서 a 삭제.

> 즉, “각 엔티티를 하나씩 persist 해야 하는 번거로움”을 줄여 주는 게 캐스케이드.

- **언제 캐스케이드를 써야 해?**
	- 자식이 **부모에 종속**되고 **다른 곳에서 독립적으로 쓰지 않는** 경우에만 (Order ↔ OrderItem, Order ↔ Delivery 처럼).
	- 여러 Aggregate에서 공유되는 엔티티(예: Member, Product)는 보통 **캐스케이드 사용 X**.
## **persist / remove 가 뭐냐?**

- **EntityManager.persist(entity)**
    - 새 엔티티를 **영속성 컨텍스트(1차 캐시)에 등록**.
    - 트랜잭션 **flush/commit 시점**에 DB에 **INSERT**가 나감.
    - **Cascade.PERSIST/ALL**이 걸려 있으면 연관된 자식에게도 함께 전파.
    - 주의: GenerationType.IDENTITY(AUTO_INCREMENT)면 **ID를 받기 위해 즉시 INSERT**가 나갈 수 있음.
- **EntityManager.remove(entity)**
    - 관리 중인 엔티티를 **삭제 상태로 표시**.
    - flush/commit 시점에 DB에 **DELETE**가 나감.
    - **Cascade.REMOVE/ALL**이 걸려 있으면 자식도 같이 삭제.
    - **orphanRemoval = true**면 부모 컬렉션에서 빼거나 FK를 null로 만들어 **고아가 되면 자동 DELETE**.

## **함께 알아두면 좋은 것**

- **상태 전이**
    - _Transient_ (순수 객체) → persist → _Managed_ (영속)
    - _Managed_ → remove → _Removed_
    - _Detached_ (분리됨) → merge → _Managed_ (재관리)
- **flush**: 영속성 컨텍스트의 변경을 **DB와 동기화**(SQL 전송). 보통 **commit 전에 자동**으로 호출됨.
- **Spring Data JPA의 save(...)**
    - 새 엔티티(id 없음)는 내부적으로 **persist** 사용,
    - 기존/분리 엔티티(id 있음)는 **merge** 성격이라 주의(원치 않는 업데이트가 붙을 수 있음).

## 참고

- persist = “**새로 저장 예약**(INSERT)”
- remove = “**삭제 예약**(DELETE)”
- 둘 다 **즉시 DB 반영이 아니라 flush/commit 때 SQL**이 나간다(IDENTITY 예외 가능).
- **Cascade**가 있으면 부모 호출만으로 자식까지 같이 전파된다.
## **양방향 편의 메서드 패턴** - “양쪽 필드를 한 번에 맞춰주는 도우미”

왜 필요? 
- 주인 쪽 필드를 안 채우면 **DB FK가 갱신되지 않아서** 관계가 저장되지 않음.

헷갈리지 않게 아래처럼 **편의 메서드**를 부모(컨트롤하는 쪽)에 두고, **양쪽을 동시에** 세팅합니다.

```java
// Order 쪽
public void addOrderItem(OrderItem item) {
    orderItems.add(item);    // 1) 부모 컬렉션에 추가 (뷰)
    item.setOrder(this);     // 2) 주인(자식)의 FK 필드 세팅 ★중요
}

public void setDelivery(Delivery delivery) {
    this.delivery = delivery;
    delivery.setOrder(this); // 1:1에서도 주인(FK 가진 쪽)에 역참조 세팅
}
```

카테고리 트리처럼 부모-자식도 동일해요:

```java
public void addChild(Category child) {
    children.add(child);     // 부모 컬렉션 갱신
    child.setParent(this);   // 주인 쪽(FK) 세팅
}
```

> 스크린샷의 “연관관계 편의 메서드”가 바로 이 패턴을 말합니다.

> 한 메서드 호출로 **컬렉션 쪽(뷰)** 과 **주인 쪽(FK)** 을 **동시에** 일관되게 맞춰주는 것.

## **로딩/튜닝 팁**

- @ManyToOne, @OneToOne 기본 EAGER → **LAZY 권장**.
- N+1 완화: **fetch join**, @EntityGraph, @BatchSize.

## **네이밍 컨벤션(예시)**

- FK 컬럼: member_id, order_id 등 소문자+스네이크.
- 연결 테이블: category_item, FK: category_id, item_id.

## **안티패턴 체크리스트**

- 1→N 단방향 남발 ❌(불필요한 업데이트 발생 가능).
- 공유 엔티티에 cascade=ALL ❌.
- 양방향에서 **주인/거울 혼동** ❌(FK 있는 곳만 수정).
- EAGER 기본값 방치 ❌(예상치 못한 N+1).
