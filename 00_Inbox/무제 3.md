## Core Principles (Non-negotiable)

  

### 1. Data Modeling

- ✅ MUST use Pydantic models for business data

- ❌ Avoid plain dicts for domain entities

- ✅ Data normalization in model validators (e.g., "1,000,000원" → int)

- ✅ Type hints on public functions and core logic

  

**Why**: Data integrity at model level prevents bugs downstream

  

### 2. Architecture

**Strict layering**:

```Plaintext

CLI → Service → Repository → Scraper → Domain

```

  

**Why**: Single responsibility → easier to test, replace, understand

  

### 3. Logging & Error Handling

- ❌ NEVER use `print()`

- ✅ structlog 우선 (JSON 구조화 로그)

- **대안**: logging도 허용 (간단 구현 시)

- ✅ tenacity retry 필수

- ✅ Graceful degradation: Skip failed items

  

**Why**: Production needs structured logs, retries reduce manual intervention

  

### 4. Configuration

- ❌ NEVER hardcode URLs, timeouts, paths

- ✅ ALL settings in `config.yaml`

  

**Why**: Environment changes shouldn't require code changes

  

### 5. Resumability (Top Priority)

- ✅ Save checkpoint after every page

- ✅ Atomic checkpoint writes when feasible

  

**Why**: Real-world scrapers crash. Resume saves hours

  

### 6. Duplication Prevention

- ✅ DB unique constraint 필수

- ✅ in-memory set은 **옵션** (핫 듀플리케이트 대응 시)

  

**Why**: Network I/O expensive. O(1) check can save time, but memory growth risk exists

  

### 7. "제품 수준" 구현 (우대 항목)

- ✅ 오류 중단 후 재실행 (checkpoint + resume)

- ✅ interval/cron 실행 모드 (CLI 옵션)

- ✅ Click CLI 우대 (argparse도 허용)

- ✅ 유지보수 관점 리팩토링

- ✅ 테스트 코드 권장 (pytest)

  

**Why**: 리코 CTO가 요구하는 "제품 수준" 기준


**Naming**: PascalCase classes, snake_case functions, UPPER_SNAKE_CASE constants

## Prohibited Patterns

  

1. ❌ `print()` → use logger

2. ❌ Plain `dict` for domain entities → use Pydantic

3. ❌ Hardcoded values → use config.yaml

4. ❌ Cross-layer imports

5. ❌ Missing type hints in core logic

6. ❌ Missing checkpoint

## Response Format (When Asked to Implement)

  

### Response Style (Mentoring Flow)

- Provide a short plan when needed (3-6 steps).

- Implement step-by-step and explain "why" briefly after each change.

- Wait for user confirmation before moving to the next step.

## User Control Instructions

  

**For step-by-step implementation, the USER should:**

```Plaintext

# Option 1: Explicit step request

"Step 1만 구현해줘"

"Step 2 구현해줘"

  

# Option 2: Request plan first

"구현 계획만 먼저 보여줘"

"계획 승인, Step 1부터 시작"

  

# Option 3: Request review before next

"이 단계 검토 후 다음 제안해줘"

```

  

**Agent should:**

- Never assume user approval (no "proceeding to next step")

- End with clear "next steps" suggestion

- Wait for explicit user instruction
