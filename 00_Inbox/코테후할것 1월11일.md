 스스로 해보고 싶으시다는 마음가짐, 정말 훌륭합니다! 👏

백엔드 개발자의 진짜 실력은 코드를 치는 속도가 아니라, **"요구사항(API)을 보고 데이터의 구조(DB)를 머릿속으로 그려내는 능력"**에서 나옵니다.

막막해 보이는 API 목록을 보면서 **어떻게 DB 설계로 변환하는지**, 그 **사고의 흐름(Thinking Process)**을 3단계 공식으로 알려드릴게요. 이대로만 따라가면 혼자서도 충분히 설계할 수 있습니다.

---

### 🧠 API를 DB로 바꾸는 3단계 공식

#### 1단계: 명사(Noun)를 찾아라 ➡️ "테이블 후보"

API URL과 설명에서 **"관리해야 할 핵심 주체"**가 무엇인지 찾으세요. 보통 URL의 뒷부분에 복수형(`s`)으로 적혀 있습니다.

- `GET /fridge/slots` ➡️ **Slot (냉장고 칸)**
- `GET /fridge/bundles` ➡️ **Bundle (포장/꾸러미)**
- `POST …/items` ➡️ **Item (물품)**
    

> **결과:** 아하, 일단 테이블은 **`Slot`, `Bundle`, `Item`** 이렇게 최소 3개가 필요하겠구나!

---

#### 2단계: URL 경로(Path)를 뜯어라 ➡️ "관계(FK) 찾기"

URL의 구조는 데이터가 **어디에 소속되는지**를 알려줍니다. 부모-자식 관계를 여기서 파악합니다.

- `POST /fridge/bundles/{bundleId}/items`
    - 해석: "Item을 만들려면 Bundle ID가 필요하네?"
    - **설계:** `Item` 테이블은 `bundle_id`라는 컬럼(FK)을 가져야겠군. (부모가 Bundle이구나)
- `POST /fridge/bundles` (설명: 배정된 칸에 추가)
    - 해석: "Bundle을 만들 때 어느 칸(Slot)에 넣을지 정해야 하네?"
    - **설계:** `Bundle` 테이블은 `slot_id`라는 컬럼(FK)을 가져야겠군.
        

> 결과:
>
> Slot (할아버지) 1 : N Bundle (아버지) 1 : N Item (자식)
>
> 이라는 3단 계층 구조가 완성되었습니다.

---

#### 3단계: 파라미터(Filter)와 에러(Error)를 봐라 ➡️ "컬럼(Column) 찾기"

API가 **"무엇으로 검색하는지"**와 **"어떤 조건에서 에러를 뱉는지"**를 보면 필요한 컬럼이 보입니다.

**① `GET /fridge/slots` (필터: floor)**

- "층수로 조회하네?" ➡️ `Slot` 테이블에 **`floor`** 컬럼 필요.
    

**② `POST /fridge/bundles` (에러: 허용량 초과 시 422)**

- "허용량을 넘으면 에러? 그럼 허용량이 몇 개인지 어디 적혀 있어야겠네?" ➡️ `Slot` 테이블에 **`capacity`** (최대 개수) 컬럼 필요.
- "누가 만들었는지 알아야 필터링(`owner`)하지?" ➡️ `Bundle` 테이블에 **`owner_id`** 필요.
- "상태(`status`)로도 조회하네?" ➡️ `Bundle` 테이블에 **`status`** (ACTIVE, DELETED) 컬럼 필요.
    

**③ `PATCH /fridge/items` (물품 수정)**

- "물품은 뭘 수정할까? 이름, 유통기한, 개수겠지?" ➡️ `Item` 테이블에 **`name`, `expiry_date`, `quantity`** 필요.

### 📝 실전 적용: 님의 생각 노트

위 공식을 적용해서 **노트패드나 종이에 이렇게 끄적여보세요.** 이게 바로 설계입니다.

**1. FridgeSlot (칸)**

- `id`: PK
- `floor`: (API 필터 때문에 필요)
- `capacity`: (422 에러 체크하려면 기준값이 있어야 함)
- `code`: (API엔 안 보이지만, 'A칸', 'B칸' 이름은 있어야 할 것 같음 -> 추가)
    

**2. FridgeBundle (포장)**

- `id`: PK
- `slot_id`: (어느 칸에 있는지 알아야 함 -> FK)
- `owner_id`: (누구 건지 필터링해야 함)
- `status`: (삭제된 건지 확인해야 함)
- `name`: (당연히 있어야 함)
    

**3. FridgeItem (물품)**

- `id`: PK
- `bundle_id`: (어느 포장에 들었는지 알아야 함 -> FK)
- `name`: 물품명
- `expiry_date`: 유통기한

### 💡 팁: 초보자가 자주 하는 실수 (이것만 피하세요!)

**"API Response(DTO)에 `dDay`가 있으니까 DB에도 `dDay` 컬럼을 만들어야지!"** ❌

- **판단 기준:** `dDay`(남은 날짜)는 매일 바뀝니다. 어제는 D-3, 오늘은 D-2.
- **DB 설계 원칙:** DB에는 **"변하지 않는 사실(Fact)"**만 저장합니다. 즉, **`expiryDate`(유통기한)**만 저장하고, `dDay`는 조회할 때 자바 코드에서 `유통기한 - 오늘날짜`로 계산해서 보여주는 겁니다.

### 📂 2. Entity (저장소 설계)

**위치:** `backend/src/main/java/com/dormmate/backend/domain/bundle/entity/FridgeBundle.java`

DB 테이블 모양입니다. 복잡한 관계(연관관계) 다 빼고, 일단 **저장**만 되게 짰습니다.



```Java
package com.dormmate.backend.domain.fridge.entity;

import jakarta.persistence.*;
import lombok.*;
import java.util.UUID;
import java.time.LocalDateTime;

@Entity
@Getter
@Builder // 이걸 쓰면 객체 생성이 쉬워짐
@NoArgsConstructor
@AllArgsConstructor
public class FridgeBundle {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    // 원래는 @ManyToOne으로 Slot 객체를 넣어야 하지만, 일단 ID만 저장해봅시다.
    private UUID slotId; 

    private UUID ownerId; // 로그인한 사용자 ID

    private String name;

    private String memo;
    
    private LocalDateTime createdAt;
}
```

### 📂 4. Service (핵심 로직)

**위치:** `backend/src/main/java/com/dormmate/backend/domain/bundle/service/BundleService.java`

DTO를 받아서 Entity로 바꾸고 저장하는 **공장**입니다.



```Java
package com.dormmate.backend.domain.fridge.service;

import com.dormmate.backend.domain.fridge.dto.CreateBundleRequest;
import com.dormmate.backend.domain.fridge.entity.FridgeBundle;
import com.dormmate.backend.domain.fridge.repository.BundleRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.util.UUID;

@Service
@RequiredArgsConstructor
public class BundleService {

    private final BundleRepository bundleRepository;

    @Transactional
    public void createBundle(CreateBundleRequest request) {
        
        // 1. DTO 데이터를 Entity로 옮겨 담기 (빌더 패턴 사용)
        FridgeBundle newBundle = FridgeBundle.builder()
                .slotId(request.getSlotId())
                .name(request.getBundleName()) // DTO는 bundleName, DB는 name
                .memo(request.getMemo())
                .ownerId(UUID.randomUUID()) // 임시로 가짜 ID 넣음 (로그인 구현 전이라)
                .createdAt(LocalDateTime.now())
                .build();

        // 2. DB에 저장!
        bundleRepository.save(newBundle);
        
        System.out.println("🎉 저장 성공! ID: " + newBundle.getId());
    }
}
```

### 📂 5. Controller (문 열기)

**위치:** `backend/src/main/java/com/dormmate/backend/domain/bundle/controller/BundleController.java`

인터넷(Postman)이랑 연결해주는 문지기입니다.



```Java
package com.dormmate.backend.domain.fridge.controller;

import com.dormmate.backend.domain.fridge.dto.CreateBundleRequest;
import com.dormmate.backend.domain.fridge.service.BundleService;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.*;

@RestController
@RequiredArgsConstructor
public class BundleController {

    private final BundleService bundleService;

    // POST http://localhost:8080/fridge/bundles 로 요청이 오면 실행됨
    @PostMapping("/fridge/bundles")
    public String createBundle(@RequestBody CreateBundleRequest request) {
        
        bundleService.createBundle(request);
        
        return "포장 생성 완료!";
    }
}
```
