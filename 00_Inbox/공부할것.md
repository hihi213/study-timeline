파일 다운로드 흐름이 HAR로 확인돼서 docs/schema.md에 정리했어.
핵심은 실제 다운로드가 fileUpload.do POST로 이루어지고, 응답 헤더에 content-disposition: attachment와 application/zip이 온다는 점

주소창의 URL은 계속 `https://nuri.g2b.go.kr/`로 유지되는데 데이터만 바뀌는 이유는, 이 사이트가 **SPA(Single Page Application)**처럼 동작하는 WebSquare 기반이기 때문입니다. 즉, 브라우저는 '껍데기'만 한 번 로드하고, 알맹이(데이터)는 사용자님이 찾아내신 `.do` 혹은 `.wq` 형태의 **API 호출**을 통해 비동기적으로 채워넣는 방식입니다.

"제품 수준"의 크롤러를 위해 이 URL들을 기능별로 분류하고, 어떤 순서로 공략해야 할지 전략을 짜드리겠습니다.

## 🗺️ 누리장터 API 통신 지도 분석

### 1. 세션 및 메타데이터 계층 (준비 단계)

개발자가 직접 호출할 필요는 없지만, **Playwright 세션 유지**를 위해 배경에서 흘러가야 하는 데이터들입니다.

- **`getSession.do`**: 현재 접속 세션이 유효한지 확인합니다. (크롤링 중 튕김 방지용)
- **`selectCommCdList.do`**: '공통 코드'를 가져옵니다. (예: JSON의 `조070004`가 왜 '공사'인지 매핑하는 사전 데이터)
- **`serverTime.wq`**: 서버의 현재 시간을 가져옵니다. (입찰 마감 시간 계산 시 기준점)
    

### 2. 핵심 데이터 계층 (수집 대상) ⭐

우리가 실제로 데이터를 가로채서(Interception) 저장해야 할 **'돈이 되는'** 엔드포인트입니다.

|**단계**|**핵심 URL (Endpoint)**|**데이터 역할**|
|---|---|---|
|**목록**|`selectBidPbancList.do`|검색 결과 목록 (ID, 제목, 게시일 등)|
|**상세 1**|`selectBidPbancPrgsDetl.do`|공고의 진행 상세 정보 (기초금액, 장소 등)|
|**상세 2**|`selectBidNoceDetl.do`|공고문 본문 및 계약 조건 상세|
|**파일**|`selectUntyAtchFileList.do`|**첨부파일 목록** (파일명, 다운로드 경로)|

## 🛠️ "제품 수준"의 크롤러 아키텍처 설계

이 로그들을 보니 아키텍처를 다음과 같이 설계하면 리코(RiCO) CTO에게 최고의 점수를 받을 수 있습니다.

### 1. `Scraper` 계층: API Interceptor

Playwright의 `page.on("response", ...)` 기능을 사용하여, 브라우저가 위 URL들에 응답을 받을 때마다 데이터를 가로챕니다.

- **이유**: 껍데기(HTML)를 파싱하는 것보다 서버가 주는 날 것의 데이터(JSON)를 받는 것이 **정확도가 100%**이기 때문입니다.
    

### 2. `Service` 계층: 수집 파이프라인 (Flow)

1. **목록 호출**: `selectBidPbancList.do` 응답에서 공고 ID들을 추출.
2. **상세 진입**: 목록의 공고명을 클릭(Click) 액션 수행.
3. **상세/파일 가로채기**: 클릭 후 발생하는 `selectBidNoceDetl.do`와 `selectUntyAtchFileList.do` 응답을 기다렸다가 가로채서 하나의 객체로 합침.
    

### 3. `Repository` 계층: 원자적 저장 (Atomic Save)

상세 정보와 파일 목록까지 모두 가로챘을 때만 DB(SQLite/CSV)에 **한 번에(Transaction)** 저장합니다. 도중에 멈춰도 '상세 정보가 없는 불완전한 데이터'가 남지 않도록 설계합니다.

## 💡 리코 CTO를 위한 "한 끗 차이" 디테일 제안

찾아내신 URL 중 `selectUntyAtchFileList.do`가 특히 중요합니다.

> "저는 단순히 공고 텍스트만 긁지 않고, `selectUntyAtchFileList.do`를 통해 **실제 공고문 파일(PDF/HWP)의 메타데이터까지 연동**하여 수집 성능과 데이터 활용도를 극대화했습니다."

    3. **`Payload`** 탭도 복사하세요. (목록에서 어떤 값을 넘겨야 이 상세 페이지가 열리는지 파악하기 위함입니다.)

## 🧐 왜 이걸 복사해야 하나요? (백엔드 설계 관점)

사용자님이 이 데이터를 주시면 제가 다음과 같은 **"신입 이상의 코드"**를 짜드릴 수 있습니다.

1. **통합 Pydantic 모델:** 목록에서 가져온 데이터와 상세 페이지의 데이터를 하나로 합치는 `NoticeDetail` 모델을 설계할 수 있습니다.
2. **자동 파이프라인:** 목록 JSON에서 ID를 뽑아 → 자동으로 상세 API를 호출하고 → 파일 목록까지 한 번에 매핑하는 **비즈니스 로직(Service Layer)**을 완성합니다.
3. **데이터 정규화:** 상세 JSON에 들어있는 지저분한 값들을 리코 영업팀이 보기 좋게 정제하는 로직을 미리 심어둘 수 있습니다.

# 1. 필드 수집

### 상세 스키마 확정 + JSON↔도메인 매핑 확장

이 작업은 단순히 데이터의 이름을 바꾸는 과정이 아니라, **'외계어'를 '개발자의 언어'로 번역하고 데이터의 무결성을 확보**하는 아주 핵심적인 과정입니다.

승현님처럼 자바 백엔드(Spring Boot, JPA)를 공부하신 분들이라면, 이 작업이 왜 필요한지 3가지 관점에서 명확히 이해되실 거예요.

---

## 1. 외부 시스템과의 의존성 분리 (Decoupling)

누리장터 같은 공공기관 시스템의 내부 필드명(`bidPbancNo`, `prcmBsneSeCd`)은 개발자가 한눈에 이해하기 어렵고, 설계 의도와 다를 때가 많습니다.

- **문제:** 코드 곳곳에 `bidPbancNo`라는 이름을 그대로 쓰면, 나중에 누리장터 API의 필드명이 바뀌었을 때 프로젝트 전체의 코드를 수정해야 합니다.
    
- **해결:** **도메인 매핑**을 통해 내부적으로는 `notice_id`라는 깔끔한 이름을 사용하세요. API가 바뀌어도 매핑 로직(Pydantic의 Alias나 JPA의 `@Column`) 한 곳만 고치면 됩니다. 이것이 유지보수가 쉬운 **'제품 수준'**의 코드입니다.
    

---

## 2. 데이터 타입의 안정성 (Type Safety)

웹에서 긁어온 데이터는 기본적으로 모두 **문자열(String)**입니다. 하지만 비즈니스 로직에서는 이를 숫자나 날짜로 다뤄야 하죠.

|**구분**|**Raw 데이터 (JSON/HTML)**|**도메인 모델 (Domain)**|**변환의 이점**|
|---|---|---|---|
|**금액**|`"1,030,000,000"` (String)|`1030000000` (Long)|산술 연산, 크기 비교 가능|
|**날짜**|`"2026/02/07 17:00"` (String)|`LocalDateTime`|기간 조회, 요일 계산 가능|
|**상태**|`"입찰개시"` (String)|`Enum` (STARTED, CLOSED)|오타 방지 및 조건 분기 명확화|

---

## 3. 1:N 관계의 구조화 (Structural Integrity)

누리장터 상세 페이지를 보면 하나의 공고 아래에 **여러 개의 첨부파일, 여러 개의 개찰결과**가 붙습니다.

- **왜 하는가?** 단순히 텍스트 덩어리로 저장하면 나중에 "특정 파일만 다운로드" 하거나 "순위별로 정렬" 하는 기능 구현이 불가능합니다.
    
- **매핑 확장:** `BidNoticeDetail` 모델 안에 `List<Attachment>`와 같은 구조를 미리 정의해두면, 나중에 **JPA의 `@OneToMany` 관계로 그대로 이식**할 수 있습니다. 즉, 파이썬으로 짠 크롤링 스크마가 그대로 자바 서버의 **DB 설계도**가 되는 셈이죠.

지원하신 곳의 시니어 개발자(CTO)님은 승현님이 **"데이터를 얼마나 견고하게 다루는지"**를 보고 싶어 합니다.

> "그냥 긁어왔어요"라고 하는 지원자와, **"누리장터의 복잡한 응답 구조를 분석해 표준 스키마를 설계했고, 데이터 무결성을 위해 Pydantic으로 엄격한 매핑과 검증 과정을 거쳤습니다"**라고 말하는 지원자의 차이는 하늘과 땅 차이입니다.
