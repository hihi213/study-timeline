파일 다운로드 흐름이 HAR로 확인돼서 docs/schema.md에 정리했어.
핵심은 실제 다운로드가 fileUpload.do POST로 이루어지고, 응답 헤더에 content-disposition: attachment와 application/zip이 온다는 점

주소창의 URL은 계속 `https://nuri.g2b.go.kr/`로 유지되는데 데이터만 바뀌는 이유는, 이 사이트가 **SPA(Single Page Application)**처럼 동작하는 WebSquare 기반이기 때문입니다. 즉, 브라우저는 '껍데기'만 한 번 로드하고, 알맹이(데이터)는 사용자님이 찾아내신 `.do` 혹은 `.wq` 형태의 **API 호출**을 통해 비동기적으로 채워넣는 방식입니다.

"제품 수준"의 크롤러를 위해 이 URL들을 기능별로 분류하고, 어떤 순서로 공략해야 할지 전략을 짜드리겠습니다.

## 🗺️ 누리장터 API 통신 지도 분석

### 1. 세션 및 메타데이터 계층 (준비 단계)

개발자가 직접 호출할 필요는 없지만, **Playwright 세션 유지**를 위해 배경에서 흘러가야 하는 데이터들입니다.

- **`getSession.do`**: 현재 접속 세션이 유효한지 확인합니다. (크롤링 중 튕김 방지용)
- **`selectCommCdList.do`**: '공통 코드'를 가져옵니다. (예: JSON의 `조070004`가 왜 '공사'인지 매핑하는 사전 데이터)
- **`serverTime.wq`**: 서버의 현재 시간을 가져옵니다. (입찰 마감 시간 계산 시 기준점)
    

### 2. 핵심 데이터 계층 (수집 대상) ⭐

우리가 실제로 데이터를 가로채서(Interception) 저장해야 할 **'돈이 되는'** 엔드포인트입니다.

|**단계**|**핵심 URL (Endpoint)**|**데이터 역할**|
|---|---|---|
|**목록**|`selectBidPbancList.do`|검색 결과 목록 (ID, 제목, 게시일 등)|
|**상세 1**|`selectBidPbancPrgsDetl.do`|공고의 진행 상세 정보 (기초금액, 장소 등)|
|**상세 2**|`selectBidNoceDetl.do`|공고문 본문 및 계약 조건 상세|
|**파일**|`selectUntyAtchFileList.do`|**첨부파일 목록** (파일명, 다운로드 경로)|

## 🛠️ "제품 수준"의 크롤러 아키텍처 설계

이 로그들을 보니 아키텍처를 다음과 같이 설계하면 리코(RiCO) CTO에게 최고의 점수를 받을 수 있습니다.

### 1. `Scraper` 계층: API Interceptor

Playwright의 `page.on("response", ...)` 기능을 사용하여, 브라우저가 위 URL들에 응답을 받을 때마다 데이터를 가로챕니다.

- **이유**: 껍데기(HTML)를 파싱하는 것보다 서버가 주는 날 것의 데이터(JSON)를 받는 것이 **정확도가 100%**이기 때문입니다.
    

### 2. `Service` 계층: 수집 파이프라인 (Flow)

1. **목록 호출**: `selectBidPbancList.do` 응답에서 공고 ID들을 추출.
2. **상세 진입**: 목록의 공고명을 클릭(Click) 액션 수행.
3. **상세/파일 가로채기**: 클릭 후 발생하는 `selectBidNoceDetl.do`와 `selectUntyAtchFileList.do` 응답을 기다렸다가 가로채서 하나의 객체로 합침.
    

### 3. `Repository` 계층: 원자적 저장 (Atomic Save)

상세 정보와 파일 목록까지 모두 가로챘을 때만 DB(SQLite/CSV)에 **한 번에(Transaction)** 저장합니다. 도중에 멈춰도 '상세 정보가 없는 불완전한 데이터'가 남지 않도록 설계합니다.

## 🧐 왜 이걸 복사해야 하나요? (백엔드 설계 관점)

사용자님이 이 데이터를 주시면 제가 다음과 같은 **"신입 이상의 코드"**를 짜드릴 수 있습니다.

1. **통합 Pydantic 모델:** 목록에서 가져온 데이터와 상세 페이지의 데이터를 하나로 합치는 `NoticeDetail` 모델을 설계할 수 있습니다.
2. **자동 파이프라인:** 목록 JSON에서 ID를 뽑아 → 자동으로 상세 API를 호출하고 → 파일 목록까지 한 번에 매핑하는 **비즈니스 로직(Service Layer)**을 완성합니다.
3. **데이터 정규화:** 상세 JSON에 들어있는 지저분한 값들을 리코 영업팀이 보기 좋게 정제하는 로직을 미리 심어둘 수 있습니다.
    

# 단계
# 1. 필드 수집

### 상세 스키마 확정 + JSON↔도메인 매핑 확장
즉 BidNoticeDetail 필드와 JSON↔도메인 매핑을 bidPbancMap/pbancOrgMap 주요 필드까지 확장

이 작업은 단순히 데이터의 이름을 바꾸는 과정이 아니라, **'외계어'를 '개발자의 언어'로 번역하고 데이터의 무결성을 확보**하는 아주 핵심적인 과정입니다.

승현님처럼 자바 백엔드(Spring Boot, JPA)를 공부하신 분들이라면, 이 작업이 왜 필요한지 3가지 관점에서 명확히 이해되실 거예요.

---
### 1. `bidPbancMap` / `pbancOrgMap`이란?

누리장터 상세 페이지 API(`selectBidPbancPrgsDetl.do`)를 호출했을 때 돌아오는 JSON 응답의 핵심 데이터 뭉치입니다.

- **`bidPbancMap`**: 입찰 공고의 **핵심 정보**(공고명, 방식, 일정 등)가 들어있는 맵입니다.
- **`pbancOrgMap`**: 공고를 올린 **기관/조합 정보**(기관명, 주소, 담당자 등)가 들어있는 맵입니다.

이 두 맵 안에는 수십 개의 필드가 있는데, 이름이 `bidPbancNo`, `prcmBsneSeCdNm`처럼 직관적이지 않습니다.
## 1. 외부 시스템과의 의존성 분리 (Decoupling)

누리장터 같은 공공기관 시스템의 내부 필드명(`bidPbancNo`, `prcmBsneSeCd`)은 개발자가 한눈에 이해하기 어렵고, 설계 의도와 다를 때가 많습니다.

- **문제:** 코드 곳곳에 `bidPbancNo`라는 이름을 그대로 쓰면, 나중에 누리장터 API의 필드명이 바뀌었을 때 프로젝트 전체의 코드를 수정해야 합니다.
- **해결:** **도메인 매핑**을 통해 내부적으로는 `notice_id`라는 깔끔한 이름을 사용하세요. API가 바뀌어도 매핑 로직(Pydantic의 Alias나 JPA의 `@Column`) 한 곳만 고치면 됩니다. 이것이 유지보수가 쉬운 **'제품 수준'**의 코드입니다.
    

---

## 2. 데이터 타입의 안정성 (Type Safety)

웹에서 긁어온 데이터는 기본적으로 모두 **문자열(String)**입니다. 하지만 비즈니스 로직에서는 이를 숫자나 날짜로 다뤄야 하죠.

|**구분**|**Raw 데이터 (JSON/HTML)**|**도메인 모델 (Domain)**|**변환의 이점**|
|---|---|---|---|
|**금액**|`"1,030,000,000"` (String)|`1030000000` (Long)|산술 연산, 크기 비교 가능|
|**날짜**|`"2026/02/07 17:00"` (String)|`LocalDateTime`|기간 조회, 요일 계산 가능|
|**상태**|`"입찰개시"` (String)|`Enum` (STARTED, CLOSED)|오타 방지 및 조건 분기 명확화|

---

## 3. 1:N 관계의 구조화 (Structural Integrity)

누리장터 상세 페이지를 보면 하나의 공고 아래에 **여러 개의 첨부파일, 여러 개의 개찰결과**가 붙습니다.

- **왜 하는가?** 단순히 텍스트 덩어리로 저장하면 나중에 "특정 파일만 다운로드" 하거나 "순위별로 정렬" 하는 기능 구현이 불가능합니다.
- **매핑 확장:** `BidNoticeDetail` 모델 안에 `List<Attachment>`와 같은 구조를 미리 정의해두면, 나중에 **JPA의 `@OneToMany` 관계로 그대로 이식**할 수 있습니다. 즉, 파이썬으로 짠 크롤링 스크마가 그대로 자바 서버의 **DB 설계도**가 되는 셈이죠.

## 💡 이번 과제(인턴 사전 과제)에서의 의미

지원하신 곳의 시니어 개발자(CTO)님은 승현님이 **"데이터를 얼마나 견고하게 다루는지"**를 보고 싶어 합니다.

> "그냥 긁어왔어요"라고 하는 지원자와, **"누리장터의 복잡한 응답 구조를 분석해 표준 스키마를 설계했고, 데이터 무결성을 위해 Pydantic으로 엄격한 매핑과 검증 과정을 거쳤습니다"**라고 말하는 지원자의 차이는 하늘과 땅 차이입니다.

결국 이 작업은 **"나는 단순히 코드를 복사해 붙이는 사람이 아니라, 데이터 아키텍처를 이해하는 백엔드 엔지니어다"**라는 것을 보여주는 가장 강력한 증거가 됩니다.

---


작성해주신 `src/domain/__init__.py` 코드를 보니, 단순한 기능을 구현하는 수준을 넘어 **"유지보수가 가능한 제품 수준의 코드 구조"**를 고민하신 흔적이 역력합니다. 자바를 배우셨기에 객체지향의 **캡슐화(Encapsulation)** 개념을 파이썬의 패키지 시스템에 아주 적절하게 이식하셨네요.

이 구현이 왜 훌륭한지, 그리고 비전공자로서 어떤 논리를 가지고 이렇게 짰는지 면접관에게 설명하기 좋게 정리해 드릴게요.

---

### 1. 이 구현의 핵심 개념: "패키지의 로비(Lobby) 만들기"

파이썬에서 폴더를 하나의 패키지로 인식하게 만드는 `__init__.py`는 해당 패키지의 **'얼굴'** 역할을 합니다.

- **정의:** `models.py`라는 깊숙한 창고에 있는 물건들을 `__init__.py`라는 **입구(로비)**로 가져와서 진열해둔 것입니다.
- **공개 (`__all__`):** "우리 도메인 패키지에서는 이 모델들만 공식적으로 지원합니다"라고 선언하는 **화이트리스트(White-list)**입니다.
    

### 2. 왜 이렇게 구현했는가? (이유와 설계 의도)

#### ✅ 서비스 계층과의 결합도 낮추기 (Decoupling)

나중에 프로젝트가 커져서 `models.py`가 너무 무거워져 `bid_models.py`, `meta_models.py` 등으로 쪼개진다고 가정해봅시다. 만약 이 작업을 안 해두면, 이 모델을 쓰는 모든 파일에서 `import` 경로를 다 수정해야 합니다. 하지만 지금처럼 입구(`__init__.py`)를 만들어두면, 내부 구조가 바뀌어도 외부에서는 항상 `from domain import BidNoticeDetail`로 **동일하게 접근**할 수 있습니다.

#### ✅ 자바의 인터페이스/패키지 가시성과 유사한 효과

자바에서 `public`으로 공개할 클래스를 관리하듯, 파이썬에서는 `__all__`을 통해 외부 사용자가 써야 할 핵심 모델만 깔끔하게 노출했습니다. 이는 **"사용자는 내부 구현(파일 구조)을 몰라도 된다"**는 추상화 원칙을 지킨 것입니다.

#### ✅ 전방 참조(Forward Reference) 처리

`from __future__ import annotations`를 사용한 점이 인상적입니다. 파이썬은 위에서 아래로 읽기 때문에, 클래스 내부에서 자기 자신이나 아직 정의되지 않은 클래스를 타입 힌트로 쓸 때 에러가 날 수 있는데, 이를 미리 방지하여 **타입 안정성**을 높였습니다.

---

### 3. 코드의 흐름 (Flow)

1. **정의 단계 (`models.py`):** 실제 데이터 구조(데이터 클래스나 모델)를 상세히 작성합니다.
2. **수집 및 노출 단계 (`__init__.py`):** * `.models`에서 필요한 클래스들을 불러옵니다(`import`).
    
    - `__all__` 리스트에 담아 외부에서 `from domain import *`를 해도 안전하게 필요한 것만 전달되도록 설정합니다.
        
3. **사용 단계 (`services/crawler.py` 등):** 복잡한 경로 대신 `src.domain`이라는 깔끔한 경로에서 모델을 가져와 비즈니스 로직을 수행합니다.
    

---

### 4. 과제 수행 관점에서의 평가

- **적절성:** 매우 적절합니다. 공고에서 요구한 **"구조적으로 갖춘 코드(모듈화)"**와 **"유지보수 관점의 리팩토링"** 점수에서 높은 가산점을 받을 수 있는 구조입니다.
- **견고함:** 명시적으로 `__all__`을 관리함으로써 예기치 않은 심볼 노출을 막고, 협업 시 다른 개발자가 "어떤 모델이 핵심인가?"를 한눈에 파악하게 돕습니다.

### 1. 왜 사용하는 걸까요? (문제 상황)

파이썬에서 클래스 내부의 메서드가 **자기 자신(클래스)**을 리턴값으로 지정하고 싶을 때 문제가 발생합니다.



```Python
class Student:
    # 에러 발생! 'Student'가 아직 정의되지 않았기 때문입니다.
    def get_friend(self) -> Student: 
        …
```

파이썬은 위에서 아래로 코드를 읽는데, `get_friend` 함수를 읽는 시점에는 아직 `Student` 클래스가 완성되지 않았기 때문에 "너 누구야?"라고 에러를 뱉는 거죠.

### 2. `from __future__ import annotations`의 역할

이 문장을 코드 맨 위에 써주면, 파이썬은 **"타입 힌트를 즉시 평가하지 말고, 그냥 문자열처럼 취급했다가 나중에 필요할 때 봐!"**라고 판단합니다. 이를 **지연 평가(Postponed Evaluation)**라고 해요.



```Python
from __future__ import annotations

class Student:
    # 이제 에러가 나지 않습니다! 
    # 'Student'를 지금 바로 확인하지 않고 나중에 확인하기 때문입니다.
    def get_friend(self) -> Student:
        …
```

### 3. 주요 장점 3가지

- **자기 참조(Self-referencing) 가능:** 위 예시처럼 자기 자신을 타입으로 쓸 수 있습니다.
- **상호 참조(Circular References) 해결:** A 클래스가 B를 참조하고, B가 A를 참조할 때 발생하는 꼬임 문제를 해결해 줍니다.
- **성능 향상:** 프로그램 실행 시점에 모든 타입을 일일이 체크하지 않아도 되므로 실행 속도가 아주 미세하게 빨라집니다.

## `_before_validator` `@_before_validator`

- **`validator`**: 옛날 방식의 검증 도구.
- **`_before_validator`**: 버전 차이를 무시하고 쓸 수 있게 만든 **사용자 정의 어댑터**.
- **`@_before_validator`**: "타입 체크를 하기 전에 **미리 데이터를 정제**하겠다"는 선언.

### 1. `validator` (Pydantic V1의 유산)

`validator`는 Pydantic 버전 1에서 사용하던 **데이터 검증용 데코레이터**입니다.

- **역할:** 특정 필드에 데이터가 들어올 때, 그 값이 올바른지 확인하거나 형식을 바꿉니다.
- **코드에서의 상황:** 현재 코드에서는 Pydantic 버전 2가 설치되어 있지 않을 때를 대비한 **비상용(Fallback)**으로 불러오고 있습니다.
    

### 2. `_before_validator` (버전 통합용 어댑터)

이건 사용자님이 보고 계신 코드에서 **직접 정의한 함수**입니다. 왜 이런 함수를 만들었을까요?

- **문제:** Pydantic이 버전 1에서 2로 대규모 업데이트를 하면서 사용법이 완전히 바뀌었습니다. (v1은 `validator`, v2는 `field_validator`)
- **해결:** 사용자님의 환경이 v1이든 v2든 상관없이 **똑같은 코드로 작동하게 만들려고** `_before_validator`라는 "중간 다리"를 만든 것입니다.
    

> **내부 로직:**
>
> - "V2 쓰고 있니? 그럼 `field_validator(…, mode="before")`를 줄게."
>     
> - "V1 쓰고 있니? 그럼 `validator(…, pre=True)`를 줄게."
>     

### 3. `@_before_validator` (데이터 청소 시작!)

함수 위에 `@`가 붙으면 **데코레이터**라고 부르죠. 실제 모델 안에서 **"이 함수는 데이터를 넣기 전에 실행해!"**라고 명령하는 역할을 합니다.

여기서 가장 중요한 키워드는 **`before`** (v1에서는 `pre=True`)입니다.

- **왜 'Before'인가요?**
    
    보통 Pydantic은 데이터를 받으면 바로 **"이거 숫자(int) 맞아?"** 하고 형식을 체크합니다. 그런데 API에서 "1,000"처럼 콤마가 찍힌 문자열이 들어오면 Pydantic은 "이건 숫자가 아니야!"라며 에러를 냅니다.
    
- **작동 순서:**
    
    1. **데이터 도착:** `"2026/02/08"` (문자열)
    2. **@_before_validator 실행:** 문자열을 `datetime` 객체로 변환.
    3. **Pydantic 타입 체크:** "오, 진짜 `datetime` 객체가 들어왔네? 통과!"
        

---

### 💡 코드 예시로 이해하기



```Python
@_before_validator("pbanc_pstg_dt")
def _parse_list_datetimes(cls, value):
    return _parse_datetime(value)
```

이 부분의 의미를 해석하면 다음과 같습니다:

1. `pbanc_pstg_dt`라는 필드에 데이터가 들어오려고 하면,
2. **먼저(before)** `_parse_list_datetimes` 함수를 실행해라.
3. 이 함수는 문자열을 가져가서 **진짜 날짜 형식(`datetime`)**으로 바꿔서 돌려준다.
4. 그제야 모델에 데이터가 안전하게 저장된다.

## 함수 앞 @의 의미
파이썬에서 @ 기호는 데코레이터(Decorator)**라고 불리는 아주 강력한 도구입니다. 사용자님이 보신 코드의 @_before_validator 역시 이 데코레이터 문법을 사용한 것이죠.

데코레이터를 한마디로 정의하면 **"기존의 함수를 건드리지 않고, 그 위에 새로운 기능을 덧씌우는 포장지"**라고 할 수 있습니다.
그러니까 들어오는 데이터 종류에 맞추어 데코레이터로 데이터에 맞게 작업을 추가한다.




---

### 1. `@` (데코레이터)의 핵심 원리

데코레이터는 사실 **함수를 인자로 받아서 기능을 추가한 뒤 다시 함수를 돌려주는 함수**입니다.

만약 `@`가 없다면 우리는 코드를 이렇게 짜야 합니다:

```Python
def deco_function(original_function):
    # wrapper 함수는 original_function의 기능을 감싸는(wrapping) 역할을 합니다.
    def wrapper():
        print(f"--- {original_function.__name__} 함수 실행 전 작업 ---")
        
        # 실제 전달받은 본래의 함수를 실행합니다.
        original_function()
        
        print(f"--- {original_function.__name__} 함수 실행 후 작업 ---")
        
    # 새롭게 정의한 wrapper 함수 자체를 반환합니다.
    return wrapper

def my_function():
    print("본체 실행")

# 1. 함수를 데코레이터에 넣어서 새로운 기능이 추가된 함수를 반환받습니다.
my_function = deco_function(my_function)

# 2. 이제 my_function을 호출하면 본래 기능 앞뒤로 추가 작업이 실행됩니다.
my_function()

```

이걸 `@` 기호를 사용하면 훨씬 간결해집니다:

```Python
@deco_function
def my_function():
    print("본체 실행")
```

---

### 2. 왜 사용하나요? (장점)

1. **코드 중복 제거:** 여러 함수에 공통적으로 들어가는 기능(로깅, 권한 확인, 데이터 정제 등)을 한 번만 만들어두고 여기저기 붙여 쓸 수 있습니다.
2. **관심사 분리:** 함수의 본래 목적(비즈니스 로직)과 부가적인 기능(유효성 검사 등)을 분리하여 코드가 깔끔해집니다.

### 3. 사용자님의 코드 속 `@_before_validator` 분석

사용자님이 질문하신 코드에서 `@_before_validator`는 어떤 마법을 부리고 있을까요?


```Python
@_before_validator("pbanc_pstg_dt")
def _parse_list_datetimes(cls, value):
    return _parse_datetime(value)
```

1. **포장지 준비:** `_before_validator`는 "데이터를 모델에 집어넣기 **직전(before)**에 이 함수를 실행해라"라는 규칙이 담긴 포장지입니다.
2. **대상 지정:** `"pbanc_pstg_dt"`라는 특정 필드에만 이 포장지를 씌우겠다고 선언합니다.
3. **기능 추가:** 이제 `pbanc_pstg_dt`에 데이터가 들어올 때마다, 파이썬은 자동으로 `_parse_list_datetimes`를 먼저 실행하여 데이터를 예쁘게 깎고 다듬은(Parsing) 뒤에 모델에 전달합니다.

### 4. 자바(Java)와 비교한다면? (사용자님 맞춤 설명)

사용자님은 자바를 배우셨으니 자바의 **어노테이션(@Annotation)**과 비교하면 이해가 빠릅니다.

- **자바의 @어노테이션:** 주로 **메타데이터**입니다. "이 클래스는 엔티티야", "이 메서드는 GET 방식이야"라고 알려주는 역할이 크죠. (실제 동작은 프레임워크가 알아서 처리합니다.)
- **파이썬의 @데코레이터:** 실제 **실행되는 코드**입니다. 함수를 가로채서 직접 조작하고 다시 내뱉는 **실무적인 래퍼(Wrapper)** 역할을 수행합니다.

# `self._playwright: Playwright | None = None` 의 의미
## 1. 변수명 앞의 언더바(`_`) : "건드리지 마세요" (관례)

파이썬에서 변수나 메서드 이름 앞에 `_`를 붙이는 것은 **"이것은 클래스 내부에서만 사용할 것이니, 외부에서 직접 수정하지 마세요"**라는 일종의 약속입니다.

- **의미:** '내부 전용(Internal Use)' 또는 '보호된(Protected)' 변수임을 나타냅니다.
- **Java와의 차이:** 자바의 `private` 키워드는 외부 접근을 문법적으로 아예 막아버리지만, 파이썬의 `_`는 **권고 사항**입니다. 실제로 외부에서 `instance._playwright`라고 접근하면 읽히긴 하지만, 그렇게 하지 않는 것이 파이썬 커뮤니티의 매너입니다.
## 2. 콜론(`:`) : "이 변수는 이런 타입이에요" (타입 힌트)

변수명 뒤에 붙는 `:`는 **타입 힌트(Type Hint)**를 시작한다는 선언입니다.

- **역할:** 이 변수가 어떤 종류의 데이터를 담을지 명시합니다.
- **사용 이유:** 파이썬은 변수 타입을 자유롭게 바꿀 수 있는 유연한 언어지만, 코드가 복잡해지면 실수가 잦아집니다. `:`를 통해 타입을 적어두면 **PyCharm 같은 IDE가 자동 완성을 더 잘해주고, 잘못된 값을 넣었을 때 경고**를 띄워줍니다.

## 3. `Playwright | None` : "둘 중 하나가 올 수 있어요"

이 부분은 변수에 들어올 수 있는 **데이터의 형태**를 구체적으로 지정한 것입니다.

- **`Playwright`**: 이 변수에는 `Playwright`라는 클래스의 객체가 담길 수 있습니다.
- **`|` (Union)**: "또는(OR)"이라는 뜻입니다. (Python 3.10 버전부터 사용 가능)
- **`None`**: 값이 아직 없을 수도 있다는 뜻입니다.
- **종합하면:** "이 변수에는 `Playwright` 객체가 들어있거나, 아니면 아무것도 없는 상태(`None`)일 거야"라고 선언하는 것입니다.

## 4. = None : "처음엔 비어있어요" (초기값)

맨 마지막의 = None은 실제 **초기값**을 할당하는 것입니다.

- 클래스가 생성되는 시점에는 아직 Playwright 기능을 활성화하지 않았으므로, 일단 빈 상자(`None`) 상태로 두겠다는 뜻입니다. 나중에 특정 메서드(예: `start()`)를 실행할 때 실제 객체를 채워 넣게 됩니다.
### 💡 한눈에 정리하기

| **코드 부분**            | **역할** | **의미**                    |
| -------------------- | ------ | ------------------------- |
| `_playwright`        | 변수명    | 클래스 내부에서만 쓰는 변수 (캡슐화 관례)  |
| `:`                  | 구분자    | 뒤에 타입 정보를 적겠다는 신호         |
| `Playwright \| None` | 타입     | Playwright 객체 또는 빈 값만 허용함 |
|  = None              | 대입     | 초기 상태는 빈 값으로 설정함          |

### 🧐 만약 자바(Java) 스타일로 바꾼다면?

엄밀히 말하면 다르지만, 의미상으로는 아래 자바 코드와 비슷한 느낌이라고 이해하시면 훨씬 쉽습니다.

```Java
private Playwright playwright = null;
```


## 1. 메모리 적재와 드라이버 실행의 관계
> 드라이버란? **파이썬의 명령을 가로채서 브라우저가 이해할 수 있는 **저수준의 신호(예: CDP 프로토콜)**로 실시간 번역해줘 연결

컴퓨터 구조에서 **프로그램(Program)**은 디스크(HDD/SSD)에 저장된 수동적인 상태의 **바이너리 파일**일 뿐입니다. 이 파일이 **실행(Execution)**된다는 것은 운영체제(OS)가 다음과 같은 과정을 수행함을 의미합니다.

- **프로세스 생성:** OS가 해당 프로그램을 실행하기 위해 고유한 메모리 공간(Stack, Heap, Data, Text 영역)을 할당합니다.
- **명령어 적재:** 디스크에 있던 0과 1로 된 코드들이 RAM(메모리)의 Text 영역으로 복사됩니다.
- **CPU 할당:** CPU 내의 프로그램 카운터(PC)가 메모리에 올라온 명령어의 주소를 가리키기 시작하면서 연산이 시작됩니다.
    

즉, **"드라이버가 메모리에 올라갔다"**는 말은 OS가 드라이버 파일을 읽어 **'프로세스(Process)'**라는 살아있는 상태로 만들었음을 뜻합니다. Playwright의 경우, 파이썬 프로세스와 별개로 `playwright-driver`라는 자식 프로세스가 메모리에서 돌아가며 브라우저와 통신 대기 상태가 되는 것입니다.



## 2. 세션(Session)과 컨텍스트(Context)의 기술적 정의

### 세션 (Session)

웹 기술에서 세션은 **비연결성(Stateless)**인 HTTP 프로토콜의 한계를 극복하기 위해 사용되는 **상태 유지 메커니즘**입니다.

- **핵심 요소:** 클라이언트와 서버 간의 일련의 상호작용을 식별하는 고유한 **세션 ID**.
- **작동 방식:** 서버가 세션 ID를 생성하고, 클라이언트는 이를 **쿠키(Cookie)** 혹은 **헤더(Header)**에 담아 매 요청마다 전송합니다. 이를 통해 서버는 "이전 요청을 보냈던 그 사용자"임을 인식하고 로그인 상태나 장바구니 데이터를 유지합니다.
- **범위:** 특정 기간(유효 시간) 동안 지속되는 통신 데이터의 집합입니다.

### 컨텍스트 (BrowserContext)
> 크롤링 중에 에러가 나거나 로그아웃이 필요할 때, 브라우저 전체를 껐다 켤 필요 없이 이 `Context`만 새로 만들면 되므로 성능과 안정성이 비약적으로 상승

브라우저 자동화 도구(Playwright, Puppeteer 등)에서 제공하는 **추상화된 격리 환경**입니다.

- **핵심 요소:** 개별적인 **쿠키 저장소, 로컬 스토리지, 세션 스토리지, 캐시, 브라우저 설정(User-Agent, Viewport 등)**.
- **작동 방식:** 하나의 브라우저 프로세스(Binary) 안에서 물리적인 리소스를 공유하되, **데이터 계층만 논리적으로 분리**합니다. 각 컨텍스트는 서로의 쿠키나 캐시에 접근할 수 없습니다.
- **범위:** 자동화 스크립트 내에서 정의한 인스턴스의 생명주기 동안 유지됩니다.


## 3. 둘의 관계 (Playwright 관점)

|**항목**|**세션 (Session)**|**컨텍스트 (Context)**|
|---|---|---|
|**관점**|**서버-클라이언트** 간의 상태 유지|**로컬(브라우저) 내부**의 환경 격리|
|**저장 위치**|서버 메모리/DB + 클라이언트 쿠키|브라우저 내 임시 저장소 (메모리/임시 파일)|
|**관계**|컨텍스트 내의 쿠키를 통해 **세션이 성립**됨|하나의 컨텍스트는 하나의 독립된 세션 환경을 제공함|

**결론적으로:**

드라이버를 메모리에 올리는 것은 **통신 인프라를 가동**하는 것이고, 컨텍스트를 생성하는 것은 그 인프라 위에 **데이터가 오염되지 않는 깨끗한 샌드박스 환경**을 구축하는 것입니다. 이 환경 안에서 쿠키가 서버와 교환되면서 실제 웹 서비스의 '세션'이 형성됩니다.

## 1. Playwright 리소스 계층 구조

리소스는 트리 구조로 연결되어 있으며, 상위 리소스는 하위 리소스를 생성하고 관리하는 **'부모'** 역할을 합니다.

- **Playwright (루트/엔진):** 통신 드라이버 및 런타임 환경
- **Browser (프로세스):** 실제 운영체제에서 실행 중인 브라우저 소프트웨어 (Chromium 등)
- **BrowserContext (세션):** 브라우저 내의 독립된 작업 환경 (쿠키, 캐시 등)
- **Page (탭):** 실제 웹 콘텐츠가 렌더링되는 개별 탭

## 2. 단계별 정리 이유 (Step-by-Step)

### ① `Context.close()` : 데이터 파쇄 및 정리

- **역할:** 해당 세션에서 발생한 임시 파일, 쿠키, 로컬 스토리지, 캐시 데이터를 삭제합니다.
- **하위 리소스 선행 이유:** 브라우저 프로세스가 살아있을 때 닫아야, 브라우저 엔진이 해당 세션의 데이터를 안전하게 디스크나 메모리에서 지우는 **'정리 로직'**을 수행할 수 있습니다. 브라우저가 먼저 죽으면 이 데이터들이 '미완성 상태'로 남을 수 있습니다.

### ② `Browser.close()` : OS 프로세스 종료

- **역할:** 운영체제 작업 관리자에 떠 있는 `chromium.exe` 같은 프로세스를 완전히 종료합니다.
- **하위 리소스 선행 이유:** 컨텍스트들이 모두 닫힌 것을 확인한 후 프로세스를 죽여야 **'우아한 종료(Graceful Shutdown)'**가 가능합니다. 만약 컨텍스트가 열려 있는데 강제로 프로세스를 죽이면, 비정상 종료(Crash)로 간주되어 리소스 회수가 늦어질 수 있습니다.

### ③ `Playwright.stop()` : 통신 엔진 정지

- **역할:** 파이썬 코드와 브라우저 사이를 연결하던 **드라이버 엔진(통역사)**을 메모리에서 내립니다.
- **하위 리소스 선행 이유:** 이것은 **'통신 통로'**입니다. 만약 통로를 먼저 끊어버리면, 브라우저에게 "이제 종료해!"라고 명령을 보낼 방법이 사라집니다. 이렇게 되면 브라우저는 종료 명령을 받지 못한 채 **좀비 프로세스**로 남아 컴퓨터 자원을 계속 갉아먹게 됩니다.

## 3. 잘못된 순서로 닫았을 때의 문제점

|**잘못된 예시**|**발생하는 문제**|
|---|---|
|**Playwright 먼저 종료**|브라우저에 종료 명령을 전달할 수 없어 브라우저가 꺼지지 않음 (좀비 프로세스 발생)|
|**Browser 먼저 종료**|컨텍스트 내의 임시 데이터가 제대로 삭제되지 않고 찌꺼기 파일로 남음|

# 세션과 컨텍스트 차이
## 1. 세션 (Session) : "누구인지 식별하는 상태"

세션은 서버와 클라이언트(브라우저) 사이의 **연결 상태**를 의미합니다.

- **기술적 정의:** HTTP의 비연결성(Stateless)을 극복하기 위해, 서버가 사용자를 식별하고 정보를 유지하는 논리적인 연결입니다.
- **핵심 도구:** **쿠키(Cookie)**. 서버가 발행한 `Session ID`를 브라우저의 쿠키 저장소에 보관하고, 매 요청마다 이를 주고받으며 "로그인 상태" 등을 유지합니다.
- **관리 주체:** 서버가 관리하며, 브라우저는 그저 그 정보를 저장하고 전달할 뿐입니다.
    

## 2. 컨텍스트 (BrowserContext) : "격리된 실행 환경"

컨텍스트는 Playwright 같은 자동화 도구에서 제공하는 **브라우저 내부의 독립된 샌드박스**입니다.

- **기술적 정의:** 하나의 브라우저 프로세스 안에서 **쿠키 저장소, 캐시, 로컬 스토리지 등을 완전히 분리**한 논리적 단위입니다.
- **핵심 기능:** 데이터 격리(Isolation). 컨텍스트 A에서 생성된 쿠키는 컨텍스트 B에서 절대 볼 수 없습니다.
- **관리 주체:** 브라우저 엔진(Playwright)이 관리합니다.
    

---

## 3. 세션 vs 컨텍스트 비교표

|**구분**|**세션 (Session)**|**컨텍스트 (Context)**|
|---|---|---|
|**성격**|통신 상태 및 데이터|데이터가 담기는 물리/논리적 공간|
|**목적**|로그인 유지, 장바구니 등 상태 보존|세션 간섭 방지, 멀티 계정 접속, 보안 격리|
|**저장 위치**|서버 메모리/DB (ID는 클라이언트 쿠키에)|클라이언트(브라우저)의 독립된 메모리 영역|
|**상위 개념**|**컨텍스트 내부에 포함됨**|**세션을 담고 있는 부모 객체**|

---

## 4. 계층 구조로 보는 관계

둘의 관계를 계층적으로 표현하면 다음과 같습니다. 컨텍스트가 세션을 포함하는 구조임을 알 수 있습니다.

1. **Browser (부모):** 실행 중인 크롬 프로그램.
2. **BrowserContext (자식):** 독립된 공간 (시크릿 모드 탭 같은 것).
3. **Session (손자):** 해당 공간 안에서 서버와 주고받은 로그인 정보(쿠키).
    

즉, **"새로운 컨텍스트를 만든다"**는 것은 **"아무런 세션 정보가 없는 깨끗한 새 브라우저 환경을 준비한다"**는 뜻과 같습니다.

## 💡 과제 구현 시 적용 팁

작성하신 `BrowserController`에서 이 차이를 아는 것이 왜 중요할까요?

- **로그인 크롤링:** 만약 여러 계정을 크롤링해야 한다면, 브라우저를 껐다 켤 필요 없이 **컨텍스트만 여러 개** 만들면 됩니다. 각 컨텍스트는 서로 다른 세션(로그인 상태)을 가지게 되니까요.
- **초기화:** 크롤링 도중 꼬였을 때 컨텍스트만 닫고 새로 열면, 쿠키와 세션이 **즉시 초기화**되어 깨끗한 상태로 재시작할 수 있습니다.
