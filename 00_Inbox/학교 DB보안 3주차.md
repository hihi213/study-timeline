## 정리
(**2025-09-08, 1교시**)

데이터베이스 보안 프레임워크의 구성 요소와 보안 관리 단계를 살펴보겠습니다. 보안 프레임워크 구축의 필요성과 구성 기술 요소를 도출하는 방법을 이해하고, 여러 보안 통제 사례와 연관 지어 접근 제한, 암호화, 작업 결제, 취약점 분석을 기준으로 프레임워크를 구성합니다.

먼저 **기획 단계**입니다. 이 단계는 보안 구축 계획을 수립하고, 보안 정책의 지침과 가이드라인을 개발하는 과정입니다. 결과물로는 구축 계획서, 보안 지침서, 가이드라인이 산출됩니다. 보호할 데이터를 분류하고, 그 데이터에 적용할 보안 원칙과 지침을 정의합니다. 또한, 이를 담당할 조직의 역할과 책임을 정의하는 것도 기획 단계에 포함됩니다. 기술 요소의 개선이나 변경, 추가에 관한 절차와 가이드라인도 이 단계에서 수립합니다.

다음은 **설계 단계**입니다. 기획 단계를 바탕으로 DB 접근 제어 규칙, 작업 결제 규칙 등 각 기술별 내용을 상세하게 구현하기 위한 설계를 진행합니다. 이 단계의 산출물은 기술 요소별 설계서와 시행 계획서입니다. 예를 들어 DB 접근 제어 설계에서는 사용자 인증, 로그인 과정, 모니터링 지표, 운영 방안 등을 상세히 정의합니다. 암호화의 경우, 복호화 권한 통제, 암호화 알고리즘 정의 등 기술적인 설계가 이루어집니다. 작업 결제 규칙, 취약점 분석 계획 등 프레임워크의 각 구성 요소에 필요한 기술적 설계를 수행합니다.

세 번째는 **구축 단계**입니다. 설계 단계의 결과에 따라 각 기술 요소를 실제로 구현하고 테스트하는 단계입니다. 설계된 접근 제어 규칙을 구현하고, 정상적인 접근 외에 우회 접근 시나리오에 대한 방어 테스트도 수행해야 합니다. 암호화의 경우, 주민등록번호나 패스워드 같은 민감 데이터가 저장될 때 암호화가 올바르게 수행되는지 구현하고, 원본 데이터와 암호화 결과를 대조하여 신뢰성을 확인합니다. 또한, 암호화된 데이터가 필요시 정상적으로 복호화되어 사용자가 판독할 수 있는지도 점검합니다. 설계 단계에서 도출된 취약점을 기반으로 모의 해킹을 실시하여 실제 위험도를 파악하고, 이를 해결하기 위한 보안 솔루션을 적용합니다. 구축 단계의 결과물은 구현 내역서와 테스트 결과서입니다.

마지막은 **운영 단계**입니다. 구현된 프레임워크와 기술 요소들이 정상적으로 작동하는지 지속적으로 모니터링하고 문제점을 개선하는 유지 관리 단계입니다. 보안 규칙의 변경 사항을 관리하고, 로그를 주기적으로 점검하여 부적절한 접근 시도나 이상 징후를 파악 후 보안을 강화해야 합니다. 이를 위해 운영 체크리스트를 만들어 정기적으로 점검하고, 지속적인 모니터링을 통해 개선 사항 보고서를 작성하는 것이 중요합니다. 구축보다 더 중요한 것이 운영이며, 이는 관리와 밀접한 관련이 있습니다.

프레임워크 구축 이후에는 **보안 관리**가 중요합니다. 이는 보안 전담 조직 구성, 보안 준비, 보안 통제 구축, 보안 통제 활동, 보안 교육 등으로 이루어집니다. 전담 조직을 구성하고, 솔루션 도입 시기와 선정 기준을 정하는 등 사전 준비를 합니다. 또한, 구성원들의 보안 인식을 높이기 위한 교육을 시행합니다. 보안 통제 활동은 운영 단계에서 지속적으로 수행할 관리 감독 활동으로, 모니터링, 로그 검토, 취약점 테스트 등을 포함합니다. 각 단계별로 필요한 기술 교육과 관리자 교육을 통해 보안 수준을 유지하고 구멍이 생기지 않도록 하는 것이 최종 목표입니다.

전체적으로 DB 보안을 고려할 때는 가용성 보증을 위한 백업 및 복구 절차, 비인가 접근 제어, 동시성 제어, 불법 침입 방지, 분산 환경에서의 로그 추적, 내부 정보 유출 방지 등을 모두 고려해야 합니다. 이러한 위험 요소들이 기밀성, 무결성, 가용성에 미치는 영향을 분석하여 프레임워크 솔루션을 개발해야 합니다.

정보 침해 요소를 분석하고 위험을 평가하는 과정도 중요합니다. 이 절차는 자산 식별, 위협 식별, 발생 가능성 및 영향도 분석, 위험도 산출, 보안 대책 수립 순으로 진행됩니다. 먼저 법규, 조직의 비전 등을 기준으로 데이터의 가치와 민감성에 따라 자산을 등급별로 분류합니다. 각 자산에 발생할 수 있는 자연적, 인적, 환경적 위협을 식별하고, 해당 위협의 발생 가능성(상/중/하)과 현실화되었을 때의 영향도를 평가합니다. 이 두 값을 곱하여 위험도를 산출하고, 위험도 매트릭스를 통해 개선이 필수적인 영역, 개선이 필요한 영역, 지속적인 모니터링이 필요한 영역으로 구분합니다. 이 분석 결과를 바탕으로 접근 제어, 암호화 등의 보안 대책을 수립하고 프레임워크 설계에 반영하는 것입니다.

이러한 모든 과정을 포함하는 것이 **DB 보안 관리 체계**입니다. 이 체계는 데이터의 일관성과 합리성을 증대시키는 것을 목적으로 하며, 관리 조직, 관리 절차, 관리 인력으로 구성됩니다. 경영진부터 실무자까지 역할이 분담된 조직을 구성하고, 정책 변경, 운영, 백업, 권한 관리 등 모든 활동을 표준화된 절차에 따라 문서화해야 합니다. 또한 리더십, 기술적 역량, 적용 능력 등 각 담당자에게 필요한 역량을 정의하고, 주기적인 교육과 점검을 통해 보안 관리 체계의 품질을 지속적으로 개선하는 것이 중요합니다.

| **출처** | transcript |

* **핵심 개념**: 보안 프레임워크(Security Framework)의 필요성
* **교수 의도**: 학생들이 단편적인 보안 기술이 아닌, 체계적인 관리 구조의 중요성을 이해하도록 함.

* **오해 포인트**: '보안 솔루션(방화벽, 암호화 툴)만 도입하면 안전하다'는 생각은 오해입니다. 프레임워크 없는 기술 도입은 보안 공백을 만들 수 있습니다.
* **꼬리 질문**: 만약 프레임워크 없이 개별 보안 기술만 도입할 경우 어떤 문제가 발생할 수 있나요?

**[Q2]** 인용: "접근 제한, 암호화 작업 결제 취약점 분석 기준으로 구성 요소를 잡아서..."
| **정제된 질문** | **DB 보안 프레임워크를 구성하는 핵심 기술 요소는 무엇인가요?**
|---|---|
| **태그** | 접근통제, 데이터 보호(암호화), 감사/로깅 |
| **출처** | transcript |

* **핵심 개념**: 보안 프레임워크의 4대 구성 요소
* **교수 의도**: 학생들이 보안의 주요 기술 영역을 식별하고 분류할 수 있도록 함.
* **최소 답(10초)**: **접근 제어, 암호화, 작업 결제, 취약점 분석**의 네 가지가 핵심 구성 요소입니다. [P01]
* **모범 답**: 강의에서 제시된 DB 보안 프레임워크의 핵심 기술 요소는 다음과 같습니다.
    1.  **접근 제어**: 승인되지 않은 사용자의 DB 접근을 막고, 승인된 사용자라도 허용된 범위 내에서만 활동하도록 통제합니다. [P07]
    2.  **암호화**: 패스워드나 주민등록번호 같은 민감 데이터를 암호화하여 저장함으로써 유출 시에도 내용을 파악할 수 없게 보호합니다. [P04]
    3.  **작업 결제**: 중요한 데이터를 변경하거나 삭제하는 등의 작업에 대해 사전에 정해진 결재 경로를 거치도록 하여 무결성을 보장합니다. [P03]
    4.  **취약점 분석**: 시스템의 잠재적인 보안 약점을 찾아내고, 모의 해킹 등을 통해 위험도를 평가하여 사전에 보완합니다. [P04]
* **오해 포인트**: 암호화만 잘하면 모든 보안 문제가 해결될 것이라고 생각하기 쉽지만, 접근 제어나 취약점 관리 없이는 무용지물이 될 수 있습니다.
* **꼬리 질문**: 이 네 가지 요소 중, 일반적으로 가장 먼저 구축해야 할 우선순위가 높은 요소는 무엇인가요?

**[Q3]** 인용: "구축보다 더 중요한 게 바로 운영입니다."
| **정제된 질문** | **왜 '구축' 단계보다 '운영' 단계가 더 중요하다고 강조하나요?**
|---|---|
| **태그** | 정책/거버넌스, 감사/로깅 |
| **출처** | transcript |

* **핵심 개념**: 운영(Operation) 단계의 중요성
* **교수 의도**: 보안이 일회성 이벤트가 아니라 지속적인 활동임을 강조하기 위함.
* **최소 답(10초)**: 시스템 구축은 한 번으로 끝나지만, **새로운 위협은 계속 발생**하므로 지속적인 모니터링과 개선 없이는 보안을 유지할 수 없기 때문입니다. [P05]
* **모범 답**: 구축은 설계된 시점의 위협을 방어하는 정적인 활동이지만, 운영은 끊임없이 변화하는 외부 위협과 새로운 취약점에 대응하는 동적인 활동입니다. 따라서 **지속적인 모니터링, 로그 점검, 정기적인 취약점 분석, 개선 사항 보고** 등이 포함된 운영 단계가 장기적인 데이터 보호의 성패를 좌우하기 때문에 구축보다 더 중요하다고 할 수 있습니다. [P05, P06]
* **오해 포인트**: '한 번 잘 구축해 놓으면 신경 쓰지 않아도 된다'는 안일한 생각은 매우 위험합니다.
* **꼬리 질문**: 운영 단계에서 가장 중점적으로 수행해야 할 활동은 구체적으로 무엇이 있나요?

**[Q4]** 인용: "위험 평가 분석하는 과정은... 식별해서 각각 적절한 대책을 수립해야 되니까..."
| **정제된 질문** | **보안 위협에 대한 '위험도'는 어떻게 분석하고 계산하나요?**
|---|---|
| **태그** | 정책/거버넌스 |
| **출처** | transcript |

* **핵심 개념**: 위험도(Risk Level) 산출 방법
* **교수 의도**: 학생들이 감에 의존하는 것이 아니라, 정량적이고 체계적인 방법으로 보안 우선순위를 결정하는 과정을 이해하도록 함.
* **최소 답(10초)**: 해당 위협의 **'발생 가능성'**과, 발생했을 때의 **'영향도(손실 규모)'**를 곱해서 위험도를 계산합니다. [P08]
* **모범 답**: 위험도 분석은 다음과 같은 절차로 이루어집니다.
    1.  **자산 식별**: 보호할 데이터의 가치와 민감도 등급을 매깁니다.
    2.  **위협 식별**: 자산에 해를 끼칠 수 있는 위협(해킹, 재해 등)을 식별합니다.
    3.  **가능성/영향도 평가**: 위협이 발생할 **가능성**(상/중/하)과, 발생 시 업무에 미칠 **영향도**(상/중/하)를 각각 평가합니다.
    4.  **위험도 산출**: `위험도 = 발생 가능성 × 영향도` 공식을 적용하여 최종 위험도를 산출합니다. 이 값을 기준으로 '필수 개선', '개선 권고', '지속 관찰' 등급을 나누어 보안 대책의 우선순위를 정합니다. [P08]
* **오해 포인트**: 발생 가능성이 낮다고 해서 위험하지 않은 것은 아닙니다. 발생 가능성은 낮아도 영향도가 치명적이라면 높은 위험도를 가질 수 있습니다.
* **꼬리 질문**: 위험도 평가 결과, '필수 개선' 영역으로 판단된 위협에 대해서는 어떤 조치를 취해야 하나요?


(**2025-09-08, 2교시**)

데이터베이스 보안은 정보의 가치를 지키는 핵심이며, 데이터 유출, 무단 접근, 무결성 훼손 등의 위협으로부터 데이터를 보호하는 것을 목적으로 합니다. 데이터베이스 보안은 크게 DB 데이터 자체의 보안과 관리자 보안으로 나눌 수 있습니다. 데이터 유출의 80~90%는 권한을 가진 내부자에 의해 악의적으로 발생하는 경우가 많으며, 그 외에는 SQL 인젝션, 피싱, 사회 공학적 공격과 같은 외부 공격이나 재해 및 재난과 같은 환경적 요인이 원인이 됩니다.

이러한 위협으로부터 데이터베이스를 보호하기 위한 첫 번째 방법은 **인증(Authentication)**입니다. ID와 비밀번호, 생체 인식, 2단계 인증 등을 통해 허가된 사용자만 시스템에 접근할 수 있도록 통제합니다. DBMS가 제공하는 인증 메커니즘을 활용하여 보안을 강화할 수 있습니다. (실습)

두 번째는 **권한 관리(Authorization)**입니다. 역할 기반 접근 제어(RBAC)를 통해 사용자마다 특정 데이터베이스의 테이블이나 칼럼에 대해 `SELECT`, `INSERT` 등 특정 작업만 수행할 수 있도록 권한을 세분화하여 부여합니다. `VIEW`를 사용하여 테이블의 특정 행이나 칼럼만 노출시키는 방법도 가능합니다. (실습)

세 번째는 **데이터 암호화(Data Encryption)**입니다. 데이터 암호화는 전송 중인 데이터를 보호하는 방식과 저장된 데이터를 보호하는 방식으로 나뉩니다.
* **전송 계층 보안(TLS, Transport Layer Security)**: 과거 SSL(Secure Sockets Layer)에서 발전한 형태로, 클라이언트와 서버 간에 전송되는 데이터를 암호화하여 중간에서 탈취되거나 변조되는 것을 방지합니다. `HTTPS`가 대표적인 예입니다.
* **저장 데이터 암호화**: 패스워드나 개인정보와 같은 민감한 데이터를 디스크, 테이블, 칼럼 단위로 암호화하여 저장합니다. 암호화 키의 생성, 저장, 폐기 등 키 관리 절차 역시 중요하며, DBMS 내에서 관리할 수 있습니다. (실습)

데이터의 **무결성(Integrity)**과 **가용성(Availability)**을 보장하는 것도 보안의 중요한 요소입니다.
* **무결성**: 데이터가 항상 정확하고 일관된 상태를 유지하도록 보장하는 것입니다. 이를 위해 **트랜잭션(Transaction)** 개념이 사용됩니다. 트랜잭션은 하나의 작업 단위(예: 입금)를 구성하는 SQL 명령어들의 집합으로, **ACID(원자성, 일관성, 고립성, 영속성)** 속성을 만족해야 합니다. 여러 사용자가 동시에 데이터에 접근할 때 데이터 일관성이 깨지지 않도록 하는 **병행 제어(Concurrency Control)**도 무결성 유지를 위해 필수적입니다. 또한, 주기적인 **백업과 복구** 절차를 통해 재해나 장애 발생 시 데이터를 보존해야 합니다. (실습)
* **가용성**: 시스템 장애가 발생하더라도 서비스가 중단되지 않고 지속적으로 제공되도록 보장하는 것입니다. 데이터 복제, 로드 밸런싱, 장애 조치(Failover) 시스템을 구축하고, 인덱싱이나 쿼리 최적화를 통해 시스템 성능을 최적 상태로 유지해야 합니다. (실습)

네트워크 단에서는 방화벽, 침입 탐지 시스템 등을 통해 접근을 제어하고, DBMS 단에서는 사용자 레벨별, 객체별로 권한을 상세히 설정하여 다층적인 보안을 구현합니다.

또한, **감사 및 모니터링(Audit & Monitoring)**을 통해 데이터베이스 내의 모든 활동(로그인, 쿼리 실행 등)을 로그로 기록하고 추적해야 합니다. 민감 데이터에 대한 접근은 실시간으로 감시하고, 이상 징후가 탐지되면 자동으로 경고를 발생시키는 시스템을 활용할 수 있습니다. 로그 기록을 분석하고 감사하는 기능을 실습할 예정입니다. (실습)

마지막으로, 클라우드 환경에서의 데이터 보호 전략, GDPR(유럽 개인정보보호법)이나 CCPA(미국 캘리포니아 소비자 개인정보보호법)와 같은 최신 데이터 보호 규정을 준수하는 것이 중요합니다. 향후에는 AI와 머신러닝을 활용한 보안 자동화 기술이 더욱 발전할 것입니다.

다음 주부터 오라클 DBMS를 사용하여 다음 내용들을 실습할 것입니다.
* 사용자 계정 생성, 비밀번호 설정, `GRANT`와 `REVOKE`를 이용한 권한 부여 및 회수. (실습)
* `PROFILE`을 활용하여 로그인 실패 횟수 제한 및 비밀번호 유효 기간 설정. (실습)
* 특정 테이블이나 뷰 같은 객체에 대해 `SELECT`, `UPDATE` 등 특정 명령어만 허용하는 객체 보안 설정. (실습)
* `AUDIT` 명령어를 사용하여 특정 작업에 대한 감사 기록을 남기고 확인. (실습)
* 중요한 칼럼의 데이터를 암호화하여 테이블에 저장. (실습)
* `VIEW`를 생성하여 민감 정보를 숨기거나 일부 데이터만 노출. (실습)
* `COMMIT`, `ROLLBACK`, `SAVEPOINT`를 이용한 트랜잭션 제어 및 데이터 백업/복구 개념 실습. (실습)

### ## 핵심 요약 (TL;DR)
* **보안의 시작은 인증**: 허가된 사용자만 접근하도록 **ID/PW, 2단계 인증** 등으로 1차 방어선을 구축합니다. [P02]
* **최소 권한의 원칙**: 인증된 사용자라도 역할(Role)에 따라 **필요한 데이터와 작업(SELECT, UPDATE 등)에만 접근**하도록 권한을 세밀하게 제어해야 합니다. [P03]
* **데이터는 항상 암호화**: 네트워크를 통해 전송될 때(**TLS**)와 디스크에 저장될 때(**저장 데이터 암호화**) 모두 암호화하여 탈취되더라도 내용을 보호해야 합니다. [P04]
* **무결성은 보안의 핵심**: 데이터의 정확성을 지키는 **트랜잭션(ACID)**, 동시 접근을 제어하는 **병행 제어**, 장애 복구를 위한 **백업**은 중요한 보안 기능입니다. [P05]
* **모든 활동은 기록**: 누가, 언제, 무엇을 했는지 **로그를 기록하고 감사(Audit)**하여 이상 행위를 추적하고 문제를 파악하는 것이 필수적입니다. [P07]
* **법규 준수는 의무**: **GDPR, CCPA** 등 국내외 개인정보보호 법률을 이해하고 준수하는 것은 이제 선택이 아닌 필수입니다. [P08]

### ## 주요 개념 및 용어
* **SQL 인젝션 (SQL Injection)** = 악의적인 SQL 코드를 애플리케이션에 주입하여 데이터베이스를 비정상적으로 조작하는 공격 기법입니다. [P01]
* **인증 (Authentication)** = 사용자가 누구인지 확인하는 절차입니다. (예: ID/비밀번호, 생체 인식, 2단계 인증) [P02]
* **권한 관리 (Authorization / RBAC)** = 인증된 사용자가 시스템 내에서 무엇을 할 수 있는지 정의하고 통제하는 절차입니다. 역할 기반 접근 제어(RBAC)가 대표적입니다. [P03]
* **TLS (Transport Layer Security)** = 네트워크를 통해 데이터를 전송할 때, 제3자가 도청하거나 변조하지 못하도록 암호화하는 인터넷 보안 프로토콜입니다. `HTTPS`의 기반 기술입니다. [P04]
* **무결성 (Integrity)** = 데이터가 부정확하거나 불일치 없이 항상 정확한 상태로 유지되는 성질입니다. [P05]
* **트랜잭션 (Transaction) & ACID** = 데이터베이스의 상태를 변화시키는 하나의 논리적 작업 단위. **원자성(Atomicity), 일관성(Consistency), 고립성(Isolation), 영속성(Durability)** 이라는 ACID 원칙을 따라 데이터 무결성을 보장합니다. [P05]
* **병행 제어 (Concurrency Control)** = 여러 사용자가 동시에 같은 데이터에 접근할 때 발생할 수 있는 데이터 불일치 문제를 막는 기술입니다. (예: `LOCK`) [P05]
* **감사 (Audit)** = 데이터베이스에서 발생하는 모든 중요한 활동(로그인, 데이터 조회/변경 등)을 추적할 수 있도록 로그를 기록하고 검토하는 기능입니다. [P07]
* **뷰 (VIEW)** = 하나 이상의 테이블에서 유도된 가상 테이블. 민감한 정보를 숨기거나 복잡한 쿼리를 단순화하는 등 보안 목적으로 사용됩니다. [P03]
* **GDPR / CCPA** = 각각 유럽연합과 미국 캘리포니아의 대표적인 개인정보보호 법률로, 기업이 데이터를 처리할 때 준수해야 할 엄격한 규정을 담고 있습니다. [P08]

### ## 실수 및 함정 (Mistakes & Pitfalls)
* **내부자 위협 간과**: 대부분의 데이터 유출은 외부 해커가 아닌 권한을 가진 내부자에 의해 발생한다는 사실을 잊기 쉽습니다. 따라서 내부자 권한 통제가 매우 중요합니다. [P01]
* **인증만으로 충분하다는 착각**: 사용자가 로그인에 성공했더라도, 최소한의 권한만 부여하는 것이 원칙입니다. `DBA` 같은 강력한 권한을 남발해서는 안 됩니다. [P03]
* **평문 데이터 전송**: `HTTPS`가 아닌 `HTTP`를 사용하거나 암호화되지 않은 프로토콜로 DB에 접속하는 것은 중간에서 데이터를 모두 탈취당할 수 있는 위험한 행위입니다. [P04]
* **백업의 부재**: 시스템 장애나 재해는 언제든 발생할 수 있습니다. 주기적인 백업과 복구 절차 없이는 데이터의 가용성과 무결성을 지킬 수 없습니다. [P05]
* **감사 기능을 비활성화하는 경우**: 성능에 미미한 영향을 준다는 이유로 감사(Audit) 기능을 꺼두면, 보안 사고 발생 시 원인을 추적하고 대응하기가 거의 불가능해집니다. [P07]
