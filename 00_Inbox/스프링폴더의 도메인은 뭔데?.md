## 정리
### **도메인 = 비즈니스 문제 영역**

- 예) 쇼핑몰이라면 “주문, 결제, 배송, 회원, 상품” 같은 **업무 개념**과 **규칙(유효성/불변식/상태전이)**.
- **도메인 모델** = 그 개념을 코드로 표현한 것(엔티티, 값 객체, 도메인 서비스, 도메인 이벤트, 애그리거트 등).

### **각 용어 한 줄 정의**

- **엔티티(Entity)**: 식별자(@Id)로 구분되는 **도메인 객체**. 상태+행위(규칙)를 가짐. DB에 저장됨.
- **값 객체(Value/임베디드)**: 식별자 없이 **값으로 동등성** 판단(예: Address, Money). 보통 불변.
- **애그리거트(Aggregate)**: 규칙을 함께 지키는 도메인 객체 묶음. **루트 엔티티**가 외부 공개 창구.
- **도메인 서비스**: 엔티티 하나에 넣기 애매한 **순수 비즈니스 연산**.
- **도메인 이벤트**: “주문완료됨” 같은 **비즈니스 사건**.
- **리포지토리(Repository)**: **애그리거트 단위**로 저장/조회하는 **추상화**(인터페이스). “저장소”가 아니라 **도메인 모델을 영속화하는 계약**.

### **왜 “엔티티 = 도메인 모델”이라고 할까?**

- 엔티티는 **비즈니스 규칙을 담는 주체**이기 때문. (단순히 DB Row의 그릇이 아니라, “취소는 이 상태에서만 가능” 같은 규칙까지 품는 게 이상적)

### **폴더(패키지) 구조 예시**

#### **1) 기능(도메인)별 모듈링 – 추천**

```
com.example.order
 ├─ domain
 │   ├─ Order.java                // 엔티티(애그리거트 루트)
 │   ├─ OrderLine.java            // 엔티티/값 객체
 │   ├─ OrderId.java              // 값 객체(식별자)
 │   ├─ OrderRepository.java      // ← 인터페이스(도메인에 둠)
 │   └─ OrderPlaced.java          // 도메인 이벤트
 ├─ application
 │   └─ PlaceOrderService.java    // 유스케이스(트랜잭션, 도메인 조립)
 ├─ infra
 │   └─ JpaOrderRepository.java   // ← 구현체(영속화 기술, JPA)
 └─ api
     └─ OrderController.java
```

- **규칙**: domain은 **어느 것도 의존하지 않음**(핵심 규칙 보호). infra가 domain 인터페이스를 **구현**해서 기술에 붙여 줌(헥사고날/클린 아키텍처).

#### **2) 전통 레이어드**

```
domain/ (엔티티, 값 객체, 도메인 서비스, Repo 인터페이스)
application/ (서비스, use case)
infrastructure/ (JPA 구현, 외부 연동)
api/ (컨트롤러, DTO)
```

## **코드로 보는 리포지토리 위치**

```
// domain
public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    void save(Order order);
}

// infra
@Repository
@RequiredArgsConstructor
class JpaOrderRepository implements OrderRepository {
    private final EntityManager em;
    public Optional<Order> findById(OrderId id){ return Optional.ofNullable(em.find(Order.class, id)); }
    public void save(Order order){ if(order.getId()==null) em.persist(order); else em.merge(order); }
}
```

> **포인트**: 인터페이스는 **도메인**에, 구현은 **인프라**에 둔다.

> (Spring Data JPA를 쓴다면, 인프라에서 JpaRepository를 어댑터처럼 활용해 OrderRepository를 충족시키는 방식도 가능)

## **DTO는 어디에?**

- **DTO**는 도메인 모델이 아님. **입출력/전달용** 구조체. 보통 api(컨트롤러 인/아웃)나 application 경계에서 쓴다.

## **빠른 감별법**

- 회의에서 비즈니스 사람들이 쓰는 단어(주문, 환불, 재고)… → **도메인**
- 기술 용어(Controller, EntityManager, KafkaClient)… → **인프라/어댑터**
- 요청/응답 스펙(필드만 잔뜩)… → **DTO**
- “돈, 주소, 기간”처럼 한 덩어리 값 규칙… → **값 객체**

---

## **한 줄 정리**

- **도메인**: 비즈니스 세계 + 규칙.
- **엔티티**: 도메인 모델의 핵심 객체(식별자·상태·행위), DB에 저장.
- **리포지토리**: 애그리거트를 저장/조회하는 **도메인 인터페이스**(구현은 인프라).
- **DTO**: 전달용 데이터.
- **값 객체**: 식별자 없이 값 동등성, 보통 불변.

원하면 너의 현재 프로젝트 구조를 가지고 **도메인 기준 리팩토링 플랜**도 짜줄게!
