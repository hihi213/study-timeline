## Core Principles (Non-negotiable)

### 1. Data Modeling
- ✅ MUST use Pydantic models for all data structures
- ❌ NEVER use plain dict for business data
- ✅ Data normalization in model validators (e.g., "1,000,000원" → int)
- ✅ Type hints on ALL functions

**Why**: Data integrity at model level prevents bugs downstream, self-documenting code

### 2. Architecture
**Strict layering** (no cross-layer violations):
```
CLI → Service → Repository → Scraper → Domain
```
- Service: Business logic orchestration only
- Repository: Data persistence abstraction only
- Scraper: Playwright + HTML parsing only
- Domain: Pure Pydantic models (zero imports from other layers)

**Why**: Single responsibility → easier to test, replace, and understand each component

### 3. Logging & Error Handling
- ❌ NEVER use `print()` (use structlog only)
- ✅ Custom exceptions (NetworkError, ParsingError) with proper inheritance
- ✅ Retry with exponential backoff (use tenacity library)
- ✅ Graceful degradation: Skip failed items, don't crash entire process

**Why**: Production systems need structured logs for debugging, retries reduce manual intervention

### 4. Configuration
- ❌ NEVER hardcode URLs, timeouts, paths
- ✅ ALL settings in `config.yaml`
- ✅ Validate config with Pydantic

**Why**: Environment changes shouldn't require code changes, config errors caught early

### 5. Resumability (Top Priority)
- ✅ Save checkpoint after every page (last_notice_id, page_number)
- ✅ CLI `--mode resume` must continue from checkpoint
- ✅ Atomic checkpoint writes (write to temp, then rename)

**Why**: Real-world scrapers crash. Resume saves hours of re-scraping, atomic writes prevent corruption

### 6. Duplication Prevention
- ✅ In-memory set for O(1) existence check
- ✅ Check before scraping (skip if exists)

**Why**: Network I/O is expensive. O(1) check saves 2-3 seconds per duplicate

## File Structure (MUST follow exactly)

```
src/
├── domain/          # Pydantic models ONLY
├── repository/      # ABC interface + CSV implementation
├── scraper/         # Playwright driver + selectolax parser
├── service/         # Business logic orchestration
├── utils/           # logger, exceptions, config loader
└── constants.py

cli.py               # Click-based CLI
config.yaml          # All settings
tests/               # Mirror src/ structure
```

**Why this structure**: 
- domain/ has zero dependencies → portable to any project
- repository/ abstracts storage → swap CSV for DB without touching Service
- scraper/ isolates slow I/O → easy to mock in tests

**Naming**: PascalCase classes, snake_case functions/files, UPPER_SNAKE_CASE constants

---

## Prohibited Patterns

### Absolutely Forbidden
1. ❌ `print()` anywhere (use logger) → production needs structured logs
2. ❌ Plain `dict` for business data → no validation, typo bugs
3. ❌ Hardcoded values → environment changes break code
4. ❌ Cross-layer imports → tight coupling, can't test in isolation
5. ❌ Functions without type hints → IDE can't help, bugs hide
6. ❌ Missing checkpoint → crashes waste hours

#
# 에러 처리 전략 (Error Handling):
#   - [에러 타입1]: [복구 방법]
#   - [에러 타입2]: [로그 후 스킵]
# ============================================

from typing import TYPE_CHECKING
from abc import ABC, abstractmethod

class ExampleRepository(ABC):
    """
    저장소 추상 인터페이스
    
    Why abstract?
    - CSV, DB, API 등 구현체 교체 가능
    - Service는 저장 방식 몰라도 됨
    - 테스트 시 Mock 주입 쉬움
    """
    
    @abstractmethod
    def save(self, notice: BidNotice) -> None:
        """
        공고 저장
        
        Why separate method?
        - 중복 체크와 분리 (단일 책임)
        - 트랜잭션 단위 명확
        - 테스트 시 검증 포인트
        
        Args:
            notice: 검증된 Pydantic 모델 (무결성 보장)
        
        Raises:
            IOError: 저장 실패 시 (호출자가 처리)
        """
        pass
    
    @abstractmethod
    def exists(self, notice_id: str) -> bool:
        """
        중복 체크 (O(1) 성능 필수)
        
        Why O(1)?
        - 공고마다 호출 → O(n) 이면 전체 O(n²)
        - set/dict 캐싱으로 해결
        
        Args:
            notice_id: 공고 고유 ID
            
        Returns:
            존재 여부 (True면 스킵)
        """
        pass

# 실제 구현
class CSVRepository(ExampleRepository):
    def __init__(self, csv_path: Path):
        # 왜 초기화 시 로드?
        # - 매번 파일 읽기 vs 한 번 메모리 캐싱
        # - 트레이드오프: 메모리 [N]MB vs 디스크 I/O 반복
        # - 선택: 메모리 (공고 10만개 = 약 10MB, 허용 가능)
        self._existing_ids: Set[str] = self._load_ids(csv_path)
    
    def _load_ids(self, path: Path) -> Set[str]:
        """
        기존 ID를 set으로 로드
        
        Why set?
        - list는 O(n), set은 O(1)
        - 10만개 공고 시 100배 속도 차이
        """
        if not path.exists():
            return set()
        
        df = pd.read_csv(path)
        return set(df['notice_id'])  # O(n) 초기화, 이후 O(1) 조회
```

**코드 밖 보충 설명 (주석으로 표현 안 되는 것)**:

1. **알고리즘 선택 근거**:
   "set 대신 dict 안 쓴 이유: 값(value) 필요 없음, set이 메모리 20% 절약"

2. **실무 시나리오**:
   "공고 10만개 기준: list O(n) = 0.1초/체크 → 10만번 = 2.7시간
                      set O(1)  = 0.00001초/체크 → 10만번 = 1초"

3. **트레이드오프 결정**:
   "초기 로드 1초 vs 매번 파일 읽기: 초기 로드 선택 (99% 시간 절약)"

4. **유지보수 포인트**:
   "나중에 DB 전환 시: self._existing_ids를 SELECT id 쿼리로 교체만 하면 됨"
