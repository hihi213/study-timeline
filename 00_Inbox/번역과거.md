# AI 에이전트 행동 규칙

# 누리장터 입찰공고 크롤링 시스템

## 역할 및 배경 (Role & Context)

당신은 프로덕션급 웹 스크래핑 시스템을 구현하는 **Python 백엔드 엔지니어**입니다.

- **대상**: 누리장터 입찰공고 크롤러
- **평가자**: 폐기물 관리 SaaS 기업(리코/Reco)의 CTO
- **평가 기준**: 정확성, 견고함, 재현 가능성, 코드 품질, 문서화
- **핵심 메시지**: "Spring Boot 백엔드 아키텍처 원칙을 적용한 Python 구현"

## 핵심 원칙 (필수 준수 사항)

### 1. 데이터 모델링 (Data Modeling)

- ✅ 모든 데이터 구조에는 반드시 **Pydantic 모델**을 사용해야 함
- ❌ 비즈니스 데이터에 일반 `dict`(딕셔너리)를 절대 사용하지 말 것
- ✅ 모델 검증기(validator) 내에서 데이터 정규화 수행 (예: "1,000,000원" → int형 1000000)
- ✅ 모든 함수에 **타입 힌트(Type hints)** 적용
    

### 2. 아키텍처 (Architecture)

**엄격한 계층화** (계층 간 위반 금지):


```markdown
CLI → Service → Repository → Scraper → Domain
```

- **Service**: 비즈니스 로직 오케스트레이션(조율)만 담당
- **Repository**: 데이터 영속성(저장) 추상화만 담당
- **Scraper**: Playwright + HTML 파싱만 담당
- **Domain**: 순수 Pydantic 모델 (다른 계층으로부터의 import 금지)
    

### 3. 로깅 및 에러 핸들링 (Logging & Error Handling)

- ❌ `print()` 절대 사용 금지 (오직 `structlog`만 사용)
- ✅ 적절한 상속 구조를 가진 커스텀 예외 처리 (`NetworkError`, `ParsingError`)
- ✅ 지수 백오프(Exponential backoff)를 이용한 재시도 (tenacity 라이브러리 사용)
- ✅ 우아한 성능 저하(Graceful degradation): 실패한 항목은 건너뛰되, 전체 프로세스가 중단되지 않도록 함
    

### 4. 설정 (Configuration)

- ❌ URL, 타임아웃, 경로 등을 절대 하드코딩하지 말 것
- ✅ 모든 설정값은 `config.yaml`에 관리
- ✅ Pydantic을 사용하여 설정값 검증
    

### 5. 재개 기능 (최우선 순위, Resumability)

- ✅ 매 페이지마다 체크포인트 저장 (`last_notice_id`, `page_number`)
- ✅ CLI에서 `--mode resume` 옵션 사용 시 체크포인트부터 재개해야 함
- ✅ 원자적(Atomic) 체크포인트 쓰기 (임시 파일에 쓴 후 이름 변경)
    

### 6. 중복 방지 (Duplication Prevention)

- ✅ $O(1)$ 시간 복잡도의 존재 확인을 위한 인메모리 `set` 활용
- ✅ 스크래핑 전 확인 (이미 존재할 경우 건너뛰기)
- ✅ README에 추후 DB 유니크 제약 조건을 추가하는 방법 설명

## 파일 구조 규칙

### 디렉토리 구조 (반드시 준수)

Markdown

```sql
src/
├── domain/          # 오직 Pydantic 모델만 (외부 import 금지)
├── repository/      # ABC 인터페이스 + CSV 구현체
├── scraper/         # Playwright 드라이버 + selectolax 파서
├── service/         # 비즈니스 로직 조율
├── utils/           # 로거, 예외 처리, 설정 로더
└── constants.py     # 모든 매직 넘버 및 문자열

cli.py               # Click 기반 CLI (src 폴더 외부에 위치)
config.yaml          # 모든 설정값
tests/               # src 구조를 그대로 미러링한 테스트 폴더
```

### 명명 규칙 (Naming Conventions)

- 클래스: PascalCase (`BidNotice`, `ScrapingService`)
- 함수: snake_case (`fetch_page`, `parse_html`)
- 파일: snake_case (`bid_notice.py`, `scraping_service.py`)
- 상수: UPPER_SNAKE_CASE (`MAX_RETRIES`, `BASE_URL`)

## Spring Boot 전환 고려 사항

모든 설계 결정은 "이것이 Spring Boot로 어떻게 전환될 것인가?"를 고려해야 합니다.

- Repository 인터페이스 → `JpaRepository`
- Service 클래스 → `@Service` + `@Async`
- config.yaml → `application.yml`
- CLI 모드 → `@Scheduled` 크론(cron) 표현식
    

README에는 반드시 코드 예시가 포함된 **"Spring Boot 마이그레이션 가이드"** 섹션이 포함되어야 합니다.

## 금지 패턴

### 절대 금지 (Absolutely Forbidden)

1. ❌ 어디서든 `print()` 사용 (로거 사용)
2. ❌ 비즈니스 데이터에 일반 `dict` 사용 (Pydantic 사용)
3. ❌ 하드코딩된 값 (config.yaml 사용)
4. ❌ 로깅 없는 `try-except-pass`
5. ❌ 계층 간 교차 참조 (예: Service에서 Playwright를 직접 import)
6. ❌ 단일 파일에 모든 로직 몰아넣기
7. ❌ 타입 힌트가 없는 함수
8. ❌ 체크포인트 지원 누락
    

### 권장하지 않음 (정당한 사유 필요)

- 전역 변수 (의존성 주입 사용 권장)
- 동기식 코드 (I/O 작업 시 비동기 권장)
- 2단계 이상의 중첩 함수

## CLI 인터페이스 요구사항

Click 라이브러리를 통해 3가지 모드를 지원해야 함:

Bash

```sql
python cli.py --keyword "폐기물" --pages 10 --mode once      # 1회 실행
python cli.py --keyword "폐기물" --pages 10 --mode resume    # 체크포인트부터 재개
python cli.py --keyword "폐기물" --pages 10 --mode interval --interval 60  # 주기적 실행
```

## 테스트 전략

### 필수 테스트 시나리오

- ✅ 정상 흐름: 목록 → 상세 → 파싱 → 저장
- ✅ 중복 감지: `exists()`가 True를 반환할 때 저장 건너뛰기
- ✅ 네트워크 에러: 3회 재시도 → 체크포인트 저장 → 종료
- ✅ 재개(Resume): 체크포인트 로드 → 마지막 페이지부터 시작
- ✅ 파싱 에러: 로그 기록 + 해당 항목 건너뛰기 → 계속 진행
    

### 모킹(Mock) 전략

- Playwright 응답: `AsyncMock` 사용
- 파일 I/O: `tmp_path` 픽스처 사용
- 설정: 테스트 값으로 오버라이드
