## TL;DR
- **cascade**: 부모 동작을 자식에게 **전파** (PERSIST/REMOVE/MERGE/REFRESH/DETACH/ALL).
- **orphanRemoval=true**: **관계 끊겨 고아**가 되면 자식 **DELETE**.
- **원칙**: **애그리거트 내부, 비공유 자식**에만.  
- **주의**: _JPA cascade_ ≠ _DB ON DELETE CASCADE_. **보통 둘 중 하나만**.

## 1. 용어·모델 정리
- **영속성 컨텍스트**: 트랜잭션 스코프의 1차 캐시/변경감지 공간.
- **엔티티 상태**: Transient → **Managed(영속)** → Removed / **Detached(준영속)**.
- **flush vs commit**
  - `flush`: SQL **전송만**(동기화), 트랜잭션은 **미확정**.
  - `commit`: 미전송분 자동 flush → **확정** + 컨텍스트 **종료**(Managed → Detached).

| 전이 | 호출/원인 | 효과 |
|---|---|---|
| Transient→Managed | `persist()`/조회 | 1차 캐시 등록, INSERT 예약(전략 따라 즉시/지연) |
| Managed→Removed | `remove()` | DELETE 예약 |
| Managed 변경 | 필드 변경(더티체킹) | UPDATE 예약 |
| Managed→Detached | 트랜잭션 종료/`detach()` | 변경감지 해제 |

## 2. 라이프사이클 타임라인 (시나리오별)

## **3. Cascade & orphanRemoval**

### **3.1 정의와 차이**

- **CascadeType.PERSIST/REMOVE/…/ALL**: 부모의 **행위 전파**.
- **orphanRemoval=true**: **관계 해제만으로** 자식 **DELETE** (1:1, 1:N 컬렉션에서 컬렉션 제거/ FK 끊김 시).

|**항목**|**Cascade.REMOVE**|**orphanRemoval**|
|---|---|---|
|트리거|**부모 remove**|**관계 해제**(컬렉션 remove, FK null 등)|
|삭제 대상|자식 삭제|자식 삭제|
|권장 용도|애그리거트 내부|**절대 공유되지 않는** 자식|

### **3.2 의사결정 트리**

- 자식이 **부모에만 종속/비공유**인가? → cascade=ALL + orphanRemoval=true 고려
- 자식이 **공유 가능/독립 생명주기**인가? → **orphanRemoval 금지**, REMOVE/ALL 신중
- DB 레벨 **ON DELETE CASCADE**를 쓸 건가? → **JPA 전파 삭제와 혼용 지양**, 한쪽만 선택

## **4. 언제(안) 쓰는가**

**✅ 사용(권장)**

- 애그리거트 루트(예: Order) ↔ 내부 구성요소(예: OrderItem, Delivery)
- 저장/삭제를 **루트 기준**으로 다루고 싶을 때

**❌ 비권장/금지**

- @ManyToOne(자식→부모) 쪽에 무분별한 cascade
- Member/Product/Category 같이 **여러 곳에서 공유**되는 엔티티
- @JoinTable 관계에서 orphanRemoval=true 오해(연결 해제가 아니라 **자식 DELETE** 될 수 있음)

**Spring Data JPA save(...) 주의**

- **id 없음** → persist 성격
- **id 있음** → **merge 성격**(원치 않는 UPDATE 유발 가능) → 가능하면 **영속 상태 변경 + 더티체킹** 활용

## **5. 예제 (권장 패턴)**

```
@Entity
class Order {
  @OneToMany(mappedBy="order", cascade=ALL, orphanRemoval=true)
  private List<OrderItem> items = new ArrayList<>();

  @OneToOne(mappedBy="order", cascade=ALL, orphanRemoval=true)
  private Delivery delivery;

  public void addItem(OrderItem i){ items.add(i); i.setOrder(this); }
  public void removeItem(OrderItem i){ items.remove(i); i.setOrder(null); } // orphanRemoval 작동
  public void setDelivery(Delivery d){ this.delivery = d; d.setOrder(this); }
}

// 사용
Order o = new Order();
OrderItem a = new OrderItem();
o.addItem(a);
em.persist(o);     // 그래프 전체 저장
o.removeItem(a);   // 관계 해제 → a DELETE
em.remove(o);      // 부모 삭제 → 하위 전파 삭제
```

## **6. 트러블슈팅 & 안티패턴**

- **양방향 편의 메서드 누락** → FK 미갱신/고아 발생
- **EAGER 기본값 방치** → N+1 폭발 → **LAZY 기본**, 필요 시 fetch join / @EntityGraph / @BatchSize
- **대량 전파 삭제** → 락/성능 이슈 → 규모/인덱스/FK 설계 고려, **단계적 삭제/배치 처리** 검토
- **벌크 쿼리(JPQL update/delete)** → 영속성 컨텍스트 미반영 → 직후 clear()로 불일치 방지

---

## **7. 체크리스트**

- 자식은 **비공유**인가? → cascade=ALL + orphanRemoval=true
- **편의 메서드**로 양쪽(뷰/주인) 동기화?
- 로딩 전략 기본 **LAZY**?
- save(...)가 **merge**로 오동작하지 않나?
- 전파 **삭제량/락** 영향 점검했나?
- 벌크 후 **clear()** 했나?

## **8. FAQ**

**Q1. flush()만 하면 DB에 확정되나요?**

A. 아니요. 전송일 뿐, **확정은 commit** 입니다.

**Q2. save()를 꼭 호출해야 하나요?**

A. **영속 상태**라면 필드만 바꿔도 **더티체킹**으로 UPDATE 예약됩니다.

**Q3. IDENTITY 전략에서 왜 persist() 직후 INSERT가 나가죠?**

A. **키 확보**가 필요하기 때문입니다(로컬 flush). 커밋은 아닙니다.

## **부록: JPA Cascade vs DB ON DELETE CASCADE**

|**구분**|**위치**|**트리거**|**장점**|**단점/주의**|
|---|---|---|---|---|
|**JPA Cascade**|애플리케이션(영속성 컨텍스트)|JPA 연산(persist/remove 등)|도메인 규칙과 함께 관리|대량 전파 시 성능·락 고려 필요|
|**DB ON DELETE CASCADE**|데이터베이스(FK)|**DB 레벨 삭제**|빠르고 일관된 참조 무결성|JPA와 **중복/경합** 시 예측 어려움|

> 실무에서는 **하나만 선택**해 예측 가능성을 높이는 것을 권장.
