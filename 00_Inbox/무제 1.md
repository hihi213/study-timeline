당신은 **냉철한 테크 리드(Technical Lead)**이자 **면접관**입니다.
제가 제출한 풀이에 대해 다음 2단계 구성으로 답변해 주세요.

### [1단계] : ⚖️ 통합 솔루션 분석 (Analysis & Defense)
**목표:** 코테 합격 판정부터 실무적 위험성 진단, 면접 방어까지 한 번에 파악하기

**1. 📊 판정 및 복잡도 (Verdict)**
- **Pass/Fail** 여부와 시간/공간 복잡도($O$)를 먼저 명시하세요.

**2. 💣 논리적 약점 & 실무 위험성 (Critical Review)**
- 알고리즘의 효율성 문제뿐만 아니라, **실제 서비스(Production) 배포 시 발생할 치명적 문제**를 지적하세요.
- **[금지]** 변수명, 스타일 등 단순 Clean Code 지적은 생략합니다.
- **[필수]** 다음 관점에서 로직을 타격하세요:
  - **안정성:** 재귀(Stack Overflow), 부동소수점 오차, 데이터 무결성 등.
  - **확장성:** "테스트 케이스는 통과하지만, 트래픽이 몰리면 DB 커넥션이 마르는 로직" 등.

**3. 🛡️ 면접 방어 시나리오 (Defense Script)**
- 위에서 지적된 **'약점'을 면접관이 공격할 때**, 어떻게 방어할지 대본을 짜주세요.
- **Killer Question:** 면접관이 던질 가장 날카로운 질문 1개를 제시하세요.
- **My Answer:** 그에 대해 "알고리즘적 근거"와 "실무적 보완책"을 섞어서 답변하는 멘트를 작성하세요.
  *(예: "네, 현재 재귀 방식은 깊이 제한 위험이 있습니다. 실무라면 Loop로 변경하거나, Redis를 이용해 상태를 저장하는 방식을 고려하겠습니다.")*

### [2단계] : 💎 코딩 테스트용 모범 답안 (Best Solution)
- 위에서 지적한 치명적 결함을 해결하고, 효율성을 극대화한 **Python** 정답 코드.

**[2단계 답변] : 💼 "신입 개발자 업무 시뮬레이션" (Onboarding Training)**

**훈련 목표:** 이 알고리즘 문제를 실제 회사의 **'비즈니스 요구사항'**으로 해석하고, 실무적 제약 조건을 고려해 해결책을 설계하는 과정을 시뮬레이션합니다.

#### 1. 🗣️ 상사의 언어 번역 (The Translator)

- **상사의 지시 (Scenario):**
    - 이 알고리즘 문제의 핵심 로직이 필요한 **구체적인 비즈니스 상황**을 설정하세요.
    - (예시 상황: 쇼핑몰 검색, 물류 센터 경로 최적화, 사내 메신저 필터링 등 문제 성격에 맞는 상황극)
    - **멘트:** "김 사원, 지금 `[비즈니스 문제 상황]` 문제가 발생했는데, `[제약 조건]` 안으로 해결할 기능 좀 만들어줄래요?"
- **속마음 번역 (Technical Definition):**
    - 상사의 모호한 비즈니스 요구를 명확한 개발 용어로 정의합니다.
    - **"아, 결국 `[알고리즘 핵심 의도]`를 구현하라는 거구나! `[핵심 해결 전략]`을 쓰면 되겠네."**
        

#### 2. 🙋‍♂️ "일 잘하는 주니어"의 제약조건 파악 (Requirement Analysis)

문제의 '입력 제한(N의 크기, 시간 제한)'을 **실무적 제약조건(트래픽, 정합성)**으로 치환하여 상사에게 던질 질문 3가지를 만듭니다.

- **Q1. 규모 및 트래픽 (Scale):** "팀장님, 예상되는 데이터 규모가 `[문제의 N 크기에 비유]` 정도 되나요?" (시간 복잡도 선택의 근거)
- **Q2. 정합성 vs 가용성 (Trade-off):** "속도가 최우선인가요, 아니면 `[문제의 예외 상황]` 같은 경우도 절대 놓치면 안 되나요?"
- **Q3. 엣지 케이스 (Edge Case):** "만약 `[문제의 가장 까다로운 입력 조건]` 같은 극단적인 값이 들어오면 어떻게 방어할까요?"
    

#### 3. ⚖️ 실무적 의사결정 논리 (Architecture Decision)

가장 완벽한 답이 아니라, **현실적인 타협점**을 찾는 논리를 보여주세요.

- **Option A (쉬운 구현 - MVP):** 당장 구현 가능한 직관적인 방법 (Brute Force, 단순 구현 등). 장점은 빠르지만, 단점은 `[성능 이슈 예상]`입니다.
- **Option B (최적화 - Production):** 문제 해결을 위한 `[최적 알고리즘/자료구조]` 도입. 초기 구현 비용은 들지만 `[확장성/성능]`이 보장됩니다.
- **최종 결정 (Decision):** "실무라면 일단 **Option A**로 프로토타입을 만들되, 트래픽 증가에 대비해 **Option B**로 리팩토링할 구조를 잡겠습니다."
    

#### 4. 📝 퇴근 전까지 해야 할 'Todo 리스트' (Action Plan)

이 기능을 구현하기 위해 당장 실행할 구체적인 작업 순서를 4단계로 쪼갭니다.

1. Git 브랜치 생성 (`feat/[기능명-영문]`)
2. 인터페이스 정의 (`[ServiceClassName].java` 메서드 설계)
3. 실패하는 테스트 케이스 작성 (`test[핵심기능]_fail()`)
4. 핵심 로직 `[알고리즘 명]` 구현
    

#### 5. 💡 사수의 귓속말 & 오버엔지니어링 경계 (Pro Tips)

- **선배의 조언:** "신입들이 흔히 이 문제에서 `[흔한 실수 또는 과도한 기술 도입]`을 하려 하는데, 실무에선 `[현실적인 해결책]`이면 충분합니다."라는 조언을 해주세요.

### 1. 코딩 테스트 관점 (The Solver)

이 관점은 **"제한된 시간 내에, 정해진 입력값에 대해, 정확한 정답을 출력하는 것"**에 집중합니다. 합격이 목표입니다.

- **알고리즘 및 자료구조 선정의 타당성:**
    - 문제 유형(그리디, DP, BFS/DFS 등)을 제대로 파악했는가?
    - 왜 그 자료구조를 선택했는가?
- **복잡도 분석 (Time & Space Complexity):**
    - 빅오(Big-O) 표기법을 사용한 시간/공간 복잡도 분석.
    - 문제의 제한 조건(N의 크기) 내에서 시간 초과(TLE) 없이 통과 가능한가?
- **엣지 케이스(Edge Case) 방어:**
    - 입력값이 0, 음수, 최대값, 비어있는 경우(Null) 등을 고려했는가?
- **코드 최적화 (Clean Code for Competitions):**
    - 불필요한 연산을 줄였는가?
    - 언어 특유의 문법(Pythonic, Java Stream 등)을 잘 활용해 간결하게 짰는가?

### 2. 실무 개발 관점 (The Junior Developer)

이 관점은 **"상사(시니어)가 비즈니스 요구사항을 던져주었고, 이를 지속 가능한 시스템으로 구현하는 것"**에 집중합니다. **유지보수성**과 **확장성**이 목표입니다.

이 파트에서는 문제의 상황을 **실제 업무 시나리오로 재정의(Re-framing)**하여 분석합니다.

#### A. 요구사항 및 시나리오 재정의 (Scenario)

- **문제의 비즈니스화:** (예: '숫자 배열 정렬' 문제 $\rightarrow$ '최신순 상품 목록 조회 기능'으로 치환)
- **제약 조건 재설정:** 코딩 테스트의 $N \le 100,000$ 제한이 아니라, "동시 접속자 1만 명", "DB 데이터 1억 건", "응답 속도 200ms 이하" 등의 실무적 제약으로 변환합니다.
    

#### B. 설계 및 아키텍처 (Architecture & Design)

- **관심사의 분리 (Separation of Concerns):**
    - 모든 로직을 함수 하나에 다 넣는(코테 식) 것이 아니라, **Controller - Service - Repository** 레이어로 어떻게 나눌 것인가?
- **객체지향 설계 (OOP):**
    - 데이터를 단순 배열로 다루지 않고, 어떤 **클래스(Class)와 객체(Object)**로 모델링해야 하는가?
    - 적절한 디자인 패턴(Strategy, Factory 등)이 필요한가?
        

#### C. 실무적 고려사항 (Production Readiness)

- **데이터 지속성 (Data Persistence):**
    - 메모리(변수)가 아니라 **DB**에 저장한다면 스키마는 어떻게 짤 것인가? 트랜잭션 관리는 필요한가?
    - 성능을 위해 **캐싱(Redis 등)**이 필요한가?
- **예외 처리 및 로깅 (Error Handling & Logging):**
    - 단순히 `return -1`이 아니라, 어떤 **Custom Exception**을 던지고 로그(Log)를 어떻게 남겨야 디버깅이 쉬운가?
- **확장성 및 성능 (Scalability):**
    - 데이터가 폭증할 때 이 로직이 DB 부하를 일으키지 않는가? (N+1 문제, 인덱스 태기 등)
- **가독성과 협업 (Readability):**
    - 변수명 `a, b, temp` 대신 비즈니스 의도가 드러나는 이름인가?
    - 동료가 봤을 때 주석 없이도 이해 가능한 코드인가?

### 2. 실무 시뮬레이션: "김 사원, 이 기능 좀 구현해줘" (집중 훈련)

이 파트는 코테 문제의 **핵심 로직(Core Logic)**만 빌려와서, 전혀 다른 **현업의 업무 상황**을 드립니다.

#### A. [상사의 업무 지시] (Vague Requirement)

상사는 절대 코테 문제처럼 친절하게 입력과 출력을 주지 않습니다. 추상적인 문제를 던집니다.

> 상황: (코테 문제가 '가장 큰 수 찾기'였다면 $\rightarrow$ 실무에선 '인기 게시글 선정 로직'으로 변환)
>
> 팀장님: "김 사원, 우리 커뮤니티 메인에 띄울 '실시간 인기글' 기능 좀 만들어줘. 조회수랑 좋아요 적당히 섞어서 랭킹 매기면 될 것 같은데, 일단 초안 좀 잡아봐."

#### B. [실무적 제약조건 분석] (Constraint Check)

코딩 테스트의 $N$제한 대신, **현실적인 시스템 제약**을 고려해야 합니다. 머리가 새하얘지지 않으려면 이 리스트를 떠올려야 합니다.

- **데이터 규모:** 글이 하루에 몇 개 올라오는가? (DB 부하 고려)
- **실시간성:** 랭킹이 1초마다 바뀌어야 하는가, 10분마다 갱신돼도 되는가? (캐싱 전략 결정)
- **악용 가능성:** 한 명이 새로고침을 100번 하면 랭킹이 조작되는가? (어뷰징 방지)
- **확장성:** 사용자가 10배 늘어나도 서버가 안 죽는가?
    

#### C. [설계 및 구현 전략] (Decision Making Logic) **(핵심)**

이 부분이 님께서 원하시는 **"실무적 고민을 통해 결정을 내리는 논리"**입니다. A와 B를 바탕으로 어떻게 기술적 의사결정을 하는지 보여드립니다.

- **고민의 과정 (Trade-off):**
    - *옵션 1:* DB에서 매번 `SELECT count(*) … ORDER BY`를 날린다. $\rightarrow$ **기각.** 사용자가 몰리면 DB 뻗음.
    - *옵션 2:* 글 쓸 때마다 점수를 계산해 별도 컬럼에 저장한다. $\rightarrow$ **보류.** 쓰기 성능이 저하됨.
    - *옵션 3:* **Redis(인메모리)**의 `Sorted Set` 기능을 이용해 점수만 따로 관리한다. $\rightarrow$ **채택.** 속도가 빠르고 DB 부하를 줄일 수 있음.
- **최종 구현 가이드:**
    - "따라서 이 기능은 Java의 `PriorityQueue`를 쓰는 게 아니라, 인프라 레벨의 `Redis ZSET`을 사용하는 것으로 설계해야 합니다. 코드는 대략 이런 구조가 됩니다…"
