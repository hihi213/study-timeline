# **JPA 실무 규칙 – 통합 정리본**

## **🔎 TL;DR (한 장 요약)**

- **CQRS Lite**: 쓰기·읽기 분리. **쓰기(커맨드)는 ID만 반환**, 조회는 전용 DTO 경로.
- **트랜잭션**: 쓰기/테스트 필수. 조회는 @Transactional(readOnly=true).
- **연관관계**: **FK 가진 쪽이 주인**. 거울(mappedBy)은 조회 전용. 동일 PK는 동일 엔티티.
- **로딩 전략**: 전부 **LAZY** 기본. N+1은 **fetch join / EntityGraph / BatchSize**로 해결.
- **Enum**: @Enumerated(STRING)만. ORDINAL 금지.
- **엔티티**: **Setter 금지**, 의미 있는 메서드로 변경. **값 타입은 불변**.
- **컬렉션**: 필드에서 즉시 초기화, **재할당 금지**.
- **Cascade/고아 삭제**: **“프라이빗 + 수명 동일”**일 때만 ALL + 필요 시 orphanRemoval=true.
- **DB 설계**: 스네이크 네이밍, 1:1 FK는 **더 자주 보는 쪽**에. **중복 방지는 유니크 인덱스**로 최종 보루.
- **영속성 동작**: **영속 엔티티 변경은 Dirty Checking**(save 불필요). 벌크 후 clear().
- **테스트**: 도메인 단위 테스트가 최고. 통합 테스트는 연결 검증용.
- **폼/API**: 서버 렌더 폼은 엔티티 사용 가능하나 **DTO 권장**. **API 응답에 엔티티 금지**.

---

## **1) 쓰기/읽기 분리 (CQRS Lite)**

- **원칙**: “쓰기와 읽기를 분리한다.”
- **커맨드(쓰기)**: **엔티티 반환 금지, ID만 반환** → 후속 조회는 **쿼리 모델/DTO**로.
- **효과**: 변경 부작용 축소, API 계약 단순화, 테스트 용이.

---

## 쓰기/테스트에 트랜젝션 필수

- JPA는 트랜잭션 경계 안에서만 일관성(쓰기 지연, flush, 1차 캐시)을 보장. 변경은 항상 **@Transactional 내부**에서 하기
- **조회 최적화**: @Transactional(readOnly = true)로 불필요 작업 생략
	- [@Transactional(readOnly)를 키면 일어나는일](../00_Inbox/@Transactional(readOnly)를%20키면%20일어나는일.md)
- **적용 위치**: 서비스 계층에 선언(클래스 단위 기본 + 메서드별 override 가능).
- **테스트**: 트랜잭션으로 격리/롤백 보장.
- 클래스에 @Transactional하고 매서드에 @Transactional(readOnly = true)해서 조회만 옵션을 켜준다거나 그 반대도 가능
- @Transactional은 두가지 있는데 spring이 제공하는걸로 사용하기

## **3) 연관관계 핵심**

- **주인(owner)**: **항상 FK 가진 쪽**을 주인으로 정하기
- 반대편(mappedBy)은 **조회 전용**.
- **동일성**: 같은 트랜직션(영속성 컨텍스트)에서 **동일 PK ⇒ 동일 객체(엔티티)(\==)**로 인식한다.
- **편의 메서드**: 주인 필드 세팅을 **반드시** 포함해 양방향 동기화.

```
public void addOrderItem(OrderItem item) {
  orderItems.add(item);  // 메모리 일관성
  item.setOrder(this);   // 주인 필드(FK) 세팅이 핵심
}
```

## **4) DB 설계 가이드**

- **네이밍:** 소문자 + 스네이크(member_point) 권장.
- **1:1 매핑:** FK 위치는 **접근 빈도 높은 테이블**에 두자.
    예) Delivery보다 Order에서 Delivery를 더 자주 본다 → **Order에 FK(=delivery_id)** 두기
- **상속 매핑**:
	- 추상클래스인 부모를, 자식들이 구현하는것으로 상속 구현
	- 단일 테이블 전략 시 부모에 @Inheritance + @DiscriminatorColumn("dtype")해서 dytpe으로 자식 구분
- **FK vs 가용성**
    - **정합성 최우선(금융/정산)**: FK **건다**.
    - **고트래픽/가용성 우선**: FK 생략 + FK 없이 **인덱스만**으로도 운영 가능
- **중복 최종 방어선**: **유니크 인덱스/제약**으로 레이스 컨디션 차단.
	 - 두 명의 사용자가 거의 동시에 같은 이름으로 가입을 요청할 때, 서비스 로직이 중복을 검사하는 시점(SELECT)과 실제 데이터를 저장하는 시점(INSERT) 사이에 아주 짧은 시간적 틈이 있다. 이 틈 때문에 서비스 로직의 방어는 뚫릴 수 있습니다.
```
ALTER TABLE member ADD CONSTRAINT uk_member_username UNIQUE (username);
ALTER TABLE member ADD CONSTRAINT uk_member_email    UNIQUE (email);
```

## **6) 엔티티 설계 원칙**

### **6-1) Setter 금지 & 의도 드러내기**

- **Setter를 가급적 열지 말자.**
    Setter 남발은 “변경점 추적 불가” 문제를 만든다.
- **의도 드러나는 메서드**로만 상태 변경:
    예) order.cancel(), orderItem.changeQuantity(…)

### **6-2) 값 타입은 불변(Immutable)**
- @Setter 제거
- 생성자/정적 팩토리로만 초기화, 변경은 **통째 교체**. (동시성/사이드이펙트 ↓)

### **6-3) 기본 생성자**

- JPA 스펙: **public/protected 기본 생성자 필수** → **protected 권장**.

### **6-4) 컬렉션 초기화 & 재할당 금지**
- 컬렉션은 필드에서 선언과 동시에 초기화하기
```java
private final List<OrderItem> orderItems = new ArrayList<>();
```
- 이후 orders = new LinkedList<>() 같은 **재할당/Null 할당 금지**.
### **6-5) 의존성 주입**

- **필드 주입 X**. final + 롬복으로 **생성자 주입**.

```java
@RequiredArgsConstructor
@Service
public class MemberService {
  private final MemberRepository memberRepository;
}
```

### **6-6) 도메인 주도 설계 스타일**

- 서비스 계층 같은 외부에서 엔티티의 데이터를 꺼내어 수정하고 다시 저장하는 방식이 아니라, 엔티티 내부에 스스로 자신의 상태를 변경하는 메서드 구현
- 서비스는 **오케스트레이션/트랜잭션**에 집중, 계산/검증은 엔티티 메서드로 위임.

### **6-7) 생성 메서드(정적 팩토리) – 생성 지점 단일화**

- 규칙/검증/연관 세팅을 한 곳에 모아 변경시 메서드 한개만 고치면되게 하자
- 이렇게 임의 new 방지 위해
    @NoArgsConstructor(access = PROTECTED) 활용.

```
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
public class Order {
  public static Order place(Clock clock, Member m, Delivery d, List<OrderItem> items) { ... }
}
```

## **7) 로딩 전략과 N+1**

- **기본**: 모든 연관관계 **LAZY** (특히 @ManyToOne, @OneToOne 기본 EAGER → **반드시 LAZY 지정**).
- **N+1**: 다건 조회 후 연관이 N번 추가 조회되는 현상.
- **해결**:
    - JPQL **fetch join**
    - **@EntityGraph**
    - **@BatchSize**(컬렉션/연관 배치 로딩)

---

## **8) Cascade & 고아 삭제**

### **8-1) 언제 쓰나 (권장 기준)**

- **프라이빗 오너**(자식이 그 부모에서만 사용) + **수명 동일** ⇒

    cascade = ALL + 필요 시 orphanRemoval = true.

체크리스트

- 자식이 **부모 전용**인가?
- 생성/삭제가 **항상 함께** 일어나는가?
- 컬렉션에서 빠지면 **삭제가 규칙**인가?

### **8-2) 언제 피하나**

- 자식을 여러 애그리거트가 공유, 삭제 전파 리스크 큼, @ManyToOne 무지성 전파.

### **8-3) 예시**

```
@OneToMany(mappedBy="order", cascade=ALL, orphanRemoval=true)
private final List<OrderItem> orderItems = new ArrayList<>();

@OneToOne(fetch=LAZY, cascade=ALL) @JoinColumn(name="delivery_id")
private Delivery delivery;
```

- save(order) 한 번으로 자식 INSERT 전파, remove(order) 시 자식 DELETE 전파.
- **주의**: 컬렉션에서 뺀다고 DB 삭제 아님 → orphanRemoval=true일 때만 자동 DELETE.

## **9) persist / remove / flush 동작**

- **persist**: INSERT 예약(커밋/flush 시 실행). **IDENTITY** 전략은 즉시 INSERT로 키 확보.
- **remove**: DELETE 예약(커밋/flush 시 실행).
- **flush**: 1차 캐시 변경을 DB와 동기화(보통 커밋 직전 자동).
- **벌크 연산 후**: 1차 캐시 불일치 방지를 위해 em.clear() 또는 clearAutomatically.

## **10) 테스트 전략**

- **도메인(엔티티) 단위 테스트가 최우선**: 순수 자바/JUnit으로 빠르고 명확.
- **통합 테스트**: 여러 모듈/트랜잭션 **연결 검증**용.
- **예외 검증**: assertThrows(예외.class, () -> { ... });

## **11) 실용 체크리스트 (최종)**

- 커맨드는 **ID만 반환**, 조회는 DTO 전용 경로
- 쓰기/테스트는 **@Transactional**, 조회는 readOnly=true
- **FK 가진 쪽이 주인**, 편의 메서드로 양쪽 동기화
- **LAZY 기본화**, N+1은 **fetch join/EntityGraph/BatchSize**
- **Enum=STRING**, ORDINAL 금지
- **Setter 금지**, 의미 메서드로 변경 / **값 타입 불변**
- **컬렉션 즉시 초기화**, 재할당 금지
- 1:1 FK는 **접근 빈도 높은 곳**
- FK 사용 여부는 **정합성 vs 가용성** 기준으로 결정
- **Cascade는 “프라이빗+수명 동일”에만**. 필요 시 선별 전파(PERSIST/REMOVE)
- orphanRemoval=true는 “컬렉션에서 빠지면 삭제”가 **도메인 규칙**일 때
- **정적 팩토리**로 생성 지점 단일화, 루트 save + Cascade
- **Dirty Checking**으로 영속 엔티티 수정(save 불필요), 벌크 후 clear()
- **유니크 인덱스**로 최종 중복 방어선 구축
- 동시성은 낙관락 @Version 검토
- **API에 엔티티 직접 반환 금지**, DTO 사용
- (선택) **OSIV OFF** + 컨트롤러 앞에서 DTO로 완결

> **실용 메모**

- > “단순 조회만 하는 얇은 API”를 **서비스 레이어 강제 통과**시키느라 의미 없는 위임만 남는다면, 팀 규칙에 맞춰 **실용적으로** 선택(단, 일관성과 횡단 관심사 적용 범위를 고려).
- > 반대로, 규칙/정책이 빠르게 변하는 조직이라면 **서비스 레이어 일관 유지**가 더 안전할 수 있음.

## **12) 폼 검증 & DTO (Spring MVC + Bean Validation)**

- **서버 렌더링(템플릿) 페이지**: 내부 용이라면 엔티티 직접 바인딩도 가능하지만, **요구가 복잡해지면 DTO(폼 객체) 권장**.
- **API(JSON)**: **절대 엔티티를 그대로 반환하지 말 것**. 응답 계약 변화 방지를 위해 **전용 DTO** 사용.
- **검증**: @Valid, BindingResult, @NotEmpty 등 표준 애노테이션 활용.

## **부록) 저장 패턴 예시 (생성 단일화 + 전파)**

```
@Transactional
public Long placeOrder(Member m, Delivery d, List<OrderItem> items) {
  Order o = Order.place(clock, m, d, items); // 검증/초기화/양방향 동기화
  orderRepository.save(o);                   // cascade로 자식까지 persist
  return o.getId();
}
```
