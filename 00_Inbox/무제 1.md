# 0. 수업 개요 - DB보안 1교시_20251027

### 공지사항

- **범위 변경**: 중간고사 이후부터는 지금까지 배운 SQL/PLSQL 문법을 **DB 보안(암호화/난독화/로그 등)**에 적용하는 실습 위주로 진행.
- **교안 추가**: 프로시저 암호화(Wrapping) 관련 내용이 교안에 추가됨.
    

### 오늘의 Workflow

- **Step 1)** 실습 환경 구축 (`userTBL` 생성 및 데이터 적재)
- **Step 2)** 평문 프로시저 작성 (이름 마스킹 로직 구현)
- **Step 3)** Source Code Obfuscation (소스 코드 숨기기/암호화)
    

### 오늘의 실습 연결고리 (Flow Summary)

- 회원 테이블 생성 → 특정 회원의 정보를 조회하되 **이름을 마스킹(Masking)** 하여 출력하는 프로시저 작성 → 그러나 `USER_SOURCE` 뷰를 조회하면 **마스킹 로직이 평문으로 노출**되는 보안 취약점 확인 → **`DBMS_DDL.CREATE_WRAPPED`** 를 사용하여 소스 코드를 난독화(Wrapping)하여 보호.

## Step 2. 데이터 마스킹 프로시저 작성 (Plain) - DB보안 1교시_20251027

### Goal & Preconditions

- 입력받은 ID에 해당하는 회원의 이름을 조회하되, **첫 글자만 노출하고 나머지는 마스킹('00' 또는 '땡땡')** 처리하여 출력하는 프로시저 작성.
- `SET SERVEROUTPUT ON` 설정 필수.
### Concept

- **`%TYPE`**: 테이블의 컬럼 데이터 타입을 그대로 참조. 테이블 스키마가 변경되어도 프로시저 코드를 수정할 필요가 없어 유지보수성이 높음. (면접 빈출)
- **`SUBSTR`**: 문자열 자르기 함수. `SUBSTR(name, 1, 1)`은 첫 글자 추출.
### Build & Execute

#### Logic

1. `CREATE OR REPLACE PROCEDURE`로 프로시저 정의.
2. 입력 파라미터(`p_id`)와 내부 변수(`v_name`, `v_birthYear`) 모두 `%TYPE`을 사용하여 선언.
3. `SELECT … INTO` 절을 사용해 데이터 조회.
4. `DBMS_OUTPUT` 출력 시 `SUBSTR`과 연결 연산자(`||`)를 사용해 마스킹 처리.
#### Code

```SQL
-- SQL Developer 워크시트에서 실행 시 끝에 '/' 필수
CREATE OR REPLACE PROCEDURE view_data_plain (
    p_userId IN userTBL.userID%TYPE  -- 입력: 사용자 ID (%TYPE 참조)
) 
IS
    -- 변수 선언: 테이블 컬럼 타입 참조
    v_userName  userTBL.userName%TYPE;
    v_birthYear userTBL.birthYear%TYPE;
BEGIN
    -- 1. 데이터 조회
    SELECT userName, birthYear 
    INTO v_userName, v_birthYear
    FROM userTBL 
    WHERE userID = p_userId;

    -- 2. 마스킹 및 출력 (예: 이승기 -> 이00)
    DBMS_OUTPUT.PUT_LINE('--------------------');
    DBMS_OUTPUT.PUT_LINE('이름: ' || SUBSTR(v_userName, 1, 1) || '00'); 
    DBMS_OUTPUT.PUT_LINE('생년: ' || v_birthYear);
    DBMS_OUTPUT.PUT_LINE('--------------------');
    
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('존재하지 않는 회원입니다.');
END;
/
```

#### **Pitfalls**

- ⚠️ **컴파일 오류**: SQL Developer 워크시트에서 PL/SQL 블록 실행 시 마지막에 `/`(슬래시)가 없으면 컴파일되지 않거나 버퍼에만 남을 수 있음.
- ⚠️ **`%TYPE` 미사용**: `VARCHAR2(10)` 등으로 하드코딩해도 동작은 하나, 컬럼 사이즈 변경 시 에러 발생 가능성 있음 (유지보수 관점 감점).
    

### 검증

- 프로시저 실행 및 결과 확인

```SQL
SET SERVEROUTPUT ON; -- 출력 결과 보기 위해 필수

-- 실행 예시 (JYP 조용필 -> 조00 확인)
EXEC view_data_plain('JYP');
```

### 💡 Interview

> [!faq]- Q. PL/SQL에서 %TYPE을 사용하는 이유는 무엇인가?
>
> 🗣️ 핵심 답변
>
> 특정 테이블 컬럼의 데이터 타입을 동적으로 참조하기 위해 사용합니다. 이를 통해 DB 스키마(컬럼 크기나 타입)가 변경되더라도 코드를 수정할 필요가 없어 유지보수성과 안전성이 높아집니다.
>
> **📚 꼬리질문 대비**
>
> - **Example**: `v_name userTBL.userName%TYPE` 선언 시, `userName`이 `VARCHAR2(20)`으로 늘어나도 변수는 자동으로 반영됩니다.

## Step 3. 소스 코드 난독화 (Wrapping) - DB보안 1교시_20251027

### Goal & Preconditions

- **Goal**: 앞서 만든 프로시저(`view_data_plain`)는 `USER_SOURCE` 뷰를 통해 누구나 소스 코드를 볼 수 있어, 마스킹 로직(첫 글자만 노출)이 노출되는 취약점이 있음. 이를 **암호화(Wrapping)** 하여 소스 코드를 숨김.
- **Precondition**: `SYS.DBMS_DDL` 패키지 실행 권한 필요 (기본적으로 사용자에게 있을 수 있으나 없다면 `GRANT EXECUTE ON DBMS_DDL TO 사용자` 필요).
    

### Concept

- **`DBMS_DDL.CREATE_WRAPPED`**: PL/SQL 소스 코드를 입력받아 **난독화(Wrapped)** 된 상태로 데이터베이스에 생성하는 프로시저.
- **Wrapping(래핑)**: 소스 코드를 사람이 읽을 수 없는 16진수 형태의 텍스트로 변환하는 과정. 로직은 실행 가능하지만, `SELECT`로 소스를 조회하면 암호문이 보임.
    

### Build & Execute

#### Logic (Dynamic SQL Construction)

1. **변수 선언**: 전체 PL/SQL 소스 코드를 담을 문자열 변수(`v_code`) 선언 (길이에 따라 `VARCHAR2` 또는 `CLOB` 사용).
2. **코드 문자열 생성**: `CREATE OR REPLACE PROCEDURE …` 문장을 문자열로 조립.
    
    - ⚠️ **주의**: PL/SQL 내부에서 SQL 문자열을 만들 때, 문자열 내부의 **작은따옴표(')** 는 **두 번('')** 써서 이스케이프 처리하거나, 연결 연산자(`||`)로 분리해야 함.
        
3. **래핑 실행**: `SYS.DBMS_DDL.CREATE_WRAPPED(v_code)` 호출.
    

#### Code

```SQL
DECLARE
    v_code VARCHAR2(3000); -- 소스 코드를 담을 변수
BEGIN
    -- 소스 코드 문자열 조립 (가독성을 위해 연결 연산자 || 사용)
    v_code := 'CREATE OR REPLACE PROCEDURE view_data_secure ( ' ||
              '    p_userId IN userTBL.userID%TYPE ' ||
              ') IS ' ||
              '    v_userName  userTBL.userName%TYPE; ' ||
              '    v_birthYear userTBL.birthYear%TYPE; ' ||
              'BEGIN ' ||
              '    SELECT userName, birthYear INTO v_userName, v_birthYear ' ||
              '    FROM userTBL WHERE userID = p_userId; ' ||
              
              -- 주의: 문자열 내부의 따옴표 처리에 유의 ('' 또는 연결)
              '    DBMS_OUTPUT.PUT_LINE(''--------------------''); ' ||
              '    DBMS_OUTPUT.PUT_LINE(''이름(Secured): '' || SUBSTR(v_userName, 1, 1) || ''**''); ' ||
              '    DBMS_OUTPUT.PUT_LINE(''생년: '' || v_birthYear); ' ||
              '    DBMS_OUTPUT.PUT_LINE(''--------------------''); ' ||
              
              'EXCEPTION ' ||
              '    WHEN NO_DATA_FOUND THEN ' ||
              '        DBMS_OUTPUT.PUT_LINE(''존재하지 않는 회원입니다.''); ' ||
              'END;';

    -- 래핑된 프로시저 생성 실행
    SYS.DBMS_DDL.CREATE_WRAPPED(v_code);
END;
/
```

#### **Pitfalls**

- ⚠️ **Quoting Hell (따옴표 지옥)**: 동적 SQL 작성 시 `DBMS_OUTPUT.PUT_LINE('Text')`를 문자열 변수에 넣으려면 `'DBMS_OUTPUT.PUT_LINE(''Text'')'` 처럼 따옴표를 이스케이프 해야 함. 강의에서는 이를 해결하기 위해 `||` 연산자를 적극 활용함.
- ⚠️ **컴파일 에러 확인 불가**: `CREATE_WRAPPED`로 생성 시, 소스 코드 문법에 오류가 있어도 "프로시저가 생성되었습니다(컴파일 오류 포함)" 메시지만 뜨고, 구체적인 라인을 찾기 어려울 수 있음. **반드시 평문으로 먼저 테스트 후 래핑할 것.**

## Step 4. 검증 (USER_SOURCE) - DB보안 1교시_20251027

### Goal

- 평문 프로시저와 래핑된 프로시저가 시스템 카탈로그(`USER_SOURCE`)에 어떻게 저장되는지 비교 확인.
    

### Build & Execute

#### Code

```SQL
-- 1. 평문 프로시저 소스 확인 (다 보임)
SELECT text 
FROM user_source 
WHERE name = 'VIEW_DATA_PLAIN'
ORDER BY line;

-- 2. 래핑된 프로시저 소스 확인 (암호화됨)
SELECT text 
FROM user_source 
WHERE name = 'VIEW_DATA_SECURE'
ORDER BY line;

-- 3. 기능 실행 테스트 (동작은 정상적으로 해야 함)
SET SERVEROUTPUT ON;
EXEC view_data_secure('LSG');
```

### 결과 예시

- **Plain**: `SELECT userName …` 코드가 그대로 보임.
- **Secure**: `wrapped 0abcd …` 와 같이 알 수 없는 헥사 코드 덩어리로 보임.
    

### 💡 Interview

> [!faq]- Q. DB에서 소스 코드를 Wrapping(난독화) 하는 이유는 무엇이며, 한계점은?
>
> 🗣️ 핵심 답변
>
> 지적 재산권 보호 및 비즈니스 로직(특히 암호화 키나 민감 알고리즘) 노출을 방지하기 위해 사용합니다. DBMS_DDL.CREATE_WRAPPED 등을 사용하면 USER_SOURCE 조회 시 코드가 난독화됩니다.
>
> **📚 꼬리질문 대비**
>
> - **한계점**: 완벽한 암호화라기보다는 난독화에 가까워, 전문적인 Unwrapper 도구를 사용하면 복호화될 가능성이 있습니다. 따라서 DB 접속 권한 관리 자체가 더 중요합니다.
>

## 기타 핵심 (Etc & Tips) - DB보안 1교시_20251027

- **SQL Developer 새로고침**: 프로시저 생성 후 왼쪽 객체 탐색기(Object Browser)에 바로 안 뜰 경우, '새로고침(Refresh)'을 눌러야 함.
- **`user_source` 뷰**: 내가 만든 PL/SQL 객체의 소스 코드가 저장되는 딕셔너리 뷰. (참고: `all_source`, `dba_source`)
- **문자열 연결(`||`)**: SQL에서 `CONCAT` 함수보다 `||` 연산자가 직관적이며 여러 문자열 연결 시 유리함.
    

### Prof’s Comment

> "관리자(DBA)도 사용자 패스워드 로직이나 민감한 쿼리를 함부로 보면 안 됩니다. 그래서 이렇게 `CREATE_WRAPPED`를 사용해 카탈로그에 저장될 때부터 암호화시켜 저장하는 겁니다."

# 0. 수업 개요 - DB보안 2교시_20251027

### 공지사항

- **Cursor(커서)**: DB 시간에 배웠으므로 실습은 생략하고 개념만 짚고 넘어감. (파일 포인터와 유사하게 한 줄씩 처리하는 방식).
- **Trigger(트리거)**: 오늘 수업의 핵심. 보안(로그 기록, 접근 제어)에서 프로시저보다 더 자주 사용됨.
    

### 오늘의 Workflow

- **Step 1)** Trigger 기초 실습 (Update/Delete 시 알림 출력)
- **Step 2)** Audit(감사) 로그 시스템 구축 (변경 전 데이터 백업)
- **Step 3)** 보안 트리거 (특정 작업 강제 차단 및 예외 처리)
    

### 오늘의 실습 연결고리 (Flow Summary)

- `testTBL`을 생성하여 트리거의 기본 작동 시점(AFTER, FOR EACH ROW)을 확인 → `userTBL`의 데이터 변경(삭제/수정) 발생 시 자동으로 `backup_userTBL`에 **"누가, 언제, 무엇을"** 변경했는지 남기는 로그 시스템 구현 → 마지막으로 INSERT 자체를 막아버리는 보안 정책을 트리거로 구현하여 에러(`RAISE_APPLICATION_ERROR`) 발생시킴.

## Step 1. Trigger 기초 (Basic Syntax) - DB보안 2교시_20251027

### Goal & Preconditions

- `testTBL`을 만들고 UPDATE나 DELETE 이벤트 발생 시, 자동으로 안내 메시지를 출력하는 트리거 작성.
- **Precondition**: `SET SERVEROUTPUT ON` 필수.
    

### Concept

- **Trigger(트리거)**: 테이블에 특정 이벤트(INSERT, UPDATE, DELETE)가 발생했을 때 **DBMS가 자동으로 실행**하는 저장 프로시저의 일종.
- **`FOR EACH ROW`**: 문장 단위(Statement Level)가 아니라 **행 단위(Row Level)**로 동작함을 의미. (100건을 업데이트하면 트리거도 100번 실행됨).
- **`AFTER` vs `BEFORE`**: 동작 수행 '후'에 실행할지, '전'에 실행할지 결정. (로그는 주로 AFTER, 데이터 변조나 검증은 BEFORE).
    

### Build & Execute

#### Logic

1. 테스트용 테이블(`testTBL`) 생성 및 데이터 삽입.
2. 트리거 생성: `testTBL`에 `DELETE` 또는 `UPDATE` 발생 시 동작.
3. 동작 확인: 실제로 지우거나 수정해보고 메시지 출력 확인.
    

#### Code



```SQL
-- 1. 테스트 테이블 생성 및 데이터 준비
DROP TABLE testTBL; -- 기존 거 있으면 삭제
CREATE TABLE testTBL (id NUMBER, text NVARCHAR2(10));

INSERT INTO testTBL VALUES(1, '아이브');
INSERT INTO testTBL VALUES(2, '블랙핑크');
INSERT INTO testTBL VALUES(3, '방탄소년단');
COMMIT;

-- 2. 기본 트리거 생성
CREATE OR REPLACE TRIGGER trg_test
    AFTER DELETE OR UPDATE  -- 삭제 또는 수정 후에 동작
    ON testTBL              -- 대상 테이블
    FOR EACH ROW            -- 각 행마다 실행
BEGIN
    DBMS_OUTPUT.PUT_LINE('트리거가 작동했습니다! (데이터 변경됨)');
END;
/
```

### 검증



```SQL
SET SERVEROUTPUT ON;

-- 업데이트 실행 -> 트리거 메시지 출력 확인
UPDATE testTBL SET text = '뉴진스' WHERE id = 1;

-- 삭제 실행 -> 트리거 메시지 출력 확인
DELETE FROM testTBL WHERE id = 2;
```

## Step 2. Audit Log(감사 로그) 구현 - DB보안 2교시_20251027

### Goal & Preconditions

- 실무 보안의 핵심인 **로그(Log) 기록**.
- `userTBL`의 데이터가 수정되거나 삭제될 때, **변경 전 데이터(Old Value)** 와 **변경자/변경일시**를 `backup_userTBL`에 자동 저장.
    

### Concept

- **`:OLD` vs `:NEW`**: 트리거 내에서 사용하는 가상 레코드(Pseudo-records).
    - **`:OLD`**: 변경/삭제 **전**의 데이터 (UPDATE, DELETE 시 사용).
    - **`:NEW`**: 새로 입력/변경 **될** 데이터 (INSERT, UPDATE 시 사용).
- **Audit Trail(감사 추적)**: 누가(User), 언제(Date), 무슨 짓을(Type) 했는지 기록.
    

### Build & Execute

#### Logic

1. 로그를 담을 `backup_userTBL` 생성 (기존 테이블 구조 + 메타데이터 컬럼).
2. `userTBL`에 `UPDATE` 혹은 `DELETE` 발생 시 동작하는 트리거 작성.
3. `IF UPDATING THEN …` 구문으로 타입을 구분하여 백업 테이블에 `INSERT`.
4. 이때 값은 `:OLD.컬럼명`을 사용하여 변경 전 값을 보존.
    

#### Code



```SQL
-- 1. 백업(로그) 테이블 생성
CREATE TABLE backup_userTBL (
    userID      CHAR(8)       NOT NULL PRIMARY KEY, 
    userName    NVARCHAR2(10) NOT NULL,            
    birthYear   NUMBER(4)     NOT NULL,            
    addr        NCHAR(2)      NOT NULL,            
    mobile1     CHAR(3),                            
    mobile2     CHAR(8),                            
    height      NUMBER(3),                          
    mDate       DATE,                                
    modType     NCHAR(2),       -- 변경 타입 (수정/삭제)
    modDate     DATE,           -- 변경 일시
    modUser     NVARCHAR2(256)  -- 변경 수행자 (계정명)
);

-- 2. 로그 트리거 생성
CREATE OR REPLACE TRIGGER trg_backupUser
    AFTER UPDATE OR DELETE ON userTBL
    FOR EACH ROW
DECLARE
    v_type NCHAR(2); -- 수정/삭제 구분 변수
BEGIN
    -- 작업 타입 구분
    IF UPDATING THEN
        v_type := '수정';
    ELSIF DELETING THEN
        v_type := '삭제';
    END IF;

    -- 백업 테이블에 저장 (변경 전 데이터 :OLD 사용)
    INSERT INTO backup_userTBL VALUES (
        :OLD.userID, 
        :OLD.userName, 
        :OLD.birthYear, 
        :OLD.addr, 
        :OLD.mobile1, 
        :OLD.mobile2, 
        :OLD.height, 
        :OLD.mDate, 
        v_type,             -- 작업 타입
        SYSDATE,            -- 현재 시간
        USER                -- 현재 접속한 DB 사용자(ex: SYSTEM, APP_USER)
    );
END;
/
```

#### **Pitfalls**

- ⚠️ **PK 제약조건 충돌**: 동일한 ID에 대해 수정이 여러 번 일어나면 `backup_userTBL`의 PK(`userID`) 때문에 에러가 날 수 있음. 실무에서는 로그 테이블의 PK를 별도 시퀀스로 따거나 복합키(ID + 시간)로 구성해야 함. (본 실습에서는 단순화를 위해 1회성 백업 가정).
    

### 검증



```SQL
-- 1. 데이터 수정
UPDATE userTBL SET addr = '제주' WHERE userID = 'BBK';

-- 2. 데이터 삭제
DELETE FROM userTBL WHERE userID = 'LSG';

-- 3. 백업 테이블 확인 (로그가 남았는지)
SELECT * FROM backup_userTBL;
-- 결과: BBK는 '수정', LSG는 '삭제' 타입으로 기록되어야 함.
```

### 💡 Interview

> [!faq]- Q. 트리거의 :OLD와 :NEW의 차이점은 무엇이며 언제 사용하는가?
>
> 🗣️ 핵심 답변
>
> :OLD는 변경 전의 기존 데이터를, :NEW는 새로 입력되거나 변경될 데이터를 의미합니다. 주로 UPDATE 시에는 두 값을 모두 사용할 수 있고, INSERT는 :NEW만, DELETE는 :OLD만 존재합니다.
>
> **📚 꼬리질문 대비**
>
> - **Audit Log**: 변경 이력을 남길 때는 주로 `:OLD` 값을 별도 테이블에 저장하여 복구 시점을 확보합니다.
>

## Step 3. 강제 예외 처리 (Prevention Trigger) - DB보안 2교시_20251027

### Goal

- 특정 테이블(`userTBL`)에 새로운 데이터 입력(INSERT)을 시도하면, 경고 메시지를 띄우고 작업을 **강제로 취소(Rollback)** 시킴.
    

### Concept

- **`RAISE_APPLICATION_ERROR(error_code, message)`**: 사용자 정의 에러를 발생시키는 프로시저.
    - Error Code 범위: `-20000` ~ `-20999` 사이의 값 사용.
    - 실행 시 트랜잭션이 중단되고 롤백됨.
        

### Build & Execute

#### Code



```SQL
-- 1. INSERT 차단 트리거 생성
CREATE OR REPLACE TRIGGER trg_blockInsert
    BEFORE INSERT ON userTBL -- 입력하기 '전'에 막는 것이 더 효율적 (강의는 After/Before 혼용이나 로직상 차단 목적)
    FOR EACH ROW
BEGIN
    -- 에러 발생 시켜서 트랜잭션 취소
    RAISE_APPLICATION_ERROR(-20001, '[보안 경고] 새로운 회원은 입력할 수 없습니다.');
END;
/
```

_(참고: 강의에서는 메시지를 출력하고 에러를 낸다고 했으나, 에러를 내면 `DBMS_OUTPUT`은 클라이언트에 따라 안 보일 수 있으므로 `RAISE_APPLICATION_ERROR` 메시지가 핵심임)_

### 검증


```SQL
-- INSERT 시도 -> ORA-20001 에러 발생하며 실패해야 함
INSERT INTO userTBL VALUES ('NEW', '신규', 2000, '서울', NULL, NULL, 180, SYSDATE);

-- 실패 확인 후 트리거 삭제 (실습 종료)
DROP TRIGGER trg_blockInsert;
```

## 기타 핵심 (Etc & Tips) - DB보안 2025.10.27

- **트리거 오버헤드**: 트리거는 이벤트마다 매번 실행되므로 시스템 성능(Performance)에 영향을 줍니다. 불필요한 트리거는 테스트 후 반드시 삭제(`DROP TRIGGER`)해야 합니다.
- **Cursor(커서) 개념**: `DECLARE`(선언) -> `OPEN`(열기) -> `FETCH`(한 줄씩 읽기) -> `CLOSE`(닫기). 파일 입출력과 유사한 흐름을 가집니다.
- **INSERT 시 로그**: INSERT 트리거는 `:OLD` 값이 없으므로 로그 기록 시 주의해야 합니다. (보통 `:NEW` 값을 기록).
    

### Prof’s Comment

> "실무에서 개발할 때 커서 많이 씁니다. 트리거는 보안 쪽에서 로그 남길 때 아주 많이 쓰고요. 특히 정보처리기사에서는 개념 위주로 나오지만, DB 보안 실무에서는 필수입니다."
