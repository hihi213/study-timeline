## 🌐 웹 통신 프로세스 및 인프라 흐름

### 네트워크 경로 및 서버 보안 (접속 경로 계층)

클라이언트와 서버는 각자의 로컬 네트워크를 거쳐 공용 인터넷망(WAN)에서 만납니다.

- **웹 클라이언트의 외부 도달 경로:** 클라이언트의 브라우저에서 출발한 데이터 패킷은 내부망의 **L2 스위치**를 거쳐 게이트웨이 역할을 하는 **라우터**를 통과한 뒤, 공용 **인터넷(WAN)** 망에 도달합니다.
- **웹 서버의 인터넷 연결 및 보호 장치:** 서버 역시 인터넷에 연결되기 위해 라우터를 거치지만, 불특정 접근으로부터 리소스를 보호하기 위해 최소 3가지의 논리적 보안 계층을 추가적으로 둡니다.
    
	1. **방화벽 (Firewall):** 미리 정의된 보안 규칙에 따라 특정 IP와 포트(Port)의 접근을 제어하는 일차적 방어선입니다.
    1. **로드 밸런서 (Load Balancer):** 서버의 실제 IP 주소를 은닉(Private IP)하고, 외부의 대량 접속 요청을 여러 대의 서버로 분산하여 가용성을 보장합니다.
    2. **WAF/IPS (웹 방화벽 및 침입 차단 시스템):** 단순 포트 차단을 넘어, HTTP 메시지 내부의 악성 코드나 해킹 패턴(SQL 인젝션 등)을 실시간으로 분석하고 차단합니다.
        
### 2. 통신 수립 및 데이터 교환 5단계

#### **1단계 [Server Setup] : 서버의 수신 대기

**프로세스 선행:** 통신 성립을 위해 서버 애플리케이션이 클라이언트보다 먼저 구동되어야 합니다.
- **Listen 상태:** 서버는 운영체제로부터 특정 **포트(Port)**를 할당받아 점유하고, 클라이언트의 연결 요청을 수락할 수 있는 **Listen(수신 대기)** 상태를 유지합니다.

#### **2단계 [Addressing] : 브라우저의 주소 식별**

1. **URL 입력:** 사용자가 브라우저 주소창에 URL을 입력합니다.
2. **DNS 조회:** 브라우저는 **DNS(Domain Name System)** 서버에 접속하여, 문자열로 된 도메인 네임을 실제 통신이 가능한 **IP 주소**로 변환합니다.

### 3단계: [Connection] TCP/IP 통로 생성 ()

식별된 IP 주소를 바탕으로 물리적/논리적 연결을 맺는 과정입니다.

* **3-Way Handshake:** 클라이언트가 서버의 IP와 포트로 접속을 시도하면, **TCP/IP** 프로토콜을 통해 서로의 상태를 확인하며 신뢰성 있는 전송 통로를 연결합니다.

### 4단계: [교환] HTTP 메시지 송수신 (Data Exchange)

생성된 통로를 통해 실제 비즈니스 데이터를 주고받습니다.

* **HTTP Request:** 클라이언트는 **HTTP 프로토콜** 규격에 맞춰 필요한 리소스(HTML, JSON 등)를 서버에 요청합니다.
* **HTTP Response:** 서버는 요청을 처리한 후, 결과물을 HTTP 응답 메시지에 담아 클라이언트에게 보냅니다.

### 5단계: [완료] 브라우저 렌더링 (Rendering)

수신된 데이터를 사용자가 볼 수 있게 가공합니다.

* **해석 및 출력:** 브라우저는 서버로부터 받은 **HTML 문서** 데이터를 파싱(Parsing)하고 해석하여 시각적인 화면으로 출력합니다.



## 🌐 1. 웹 통신의 기본: HTTP Read와 브라우저의 본질

웹 통신의 출발은 멀리 떨어진 컴퓨터의 문서를 읽어오는 것입니다.

- **HTTP GET 메서드:** 특정 경로를 지정하여 "문서를 달라"고 요청하는 **Read(읽기)** 작업입니다.
- **서버의 응답:** 요청이 정상적이면 서버는 `200 OK` 상태 코드와 함께 해당 리소스를 전달합니다.
- **브라우저의 본질:** 브라우저는 **'원격 문서 뷰어'**입니다. 서버로부터 받은 HTML을 다음 절차에 따라 화면에 표현합니다.
    
    1. **구문 분석(Parsing):** HTML 태그를 분석하여 데이터 구조를 만듭니다.
    2. **렌더링(Rendering):** 분석된 구조를 시각적인 화면으로 그립니다.

## 🏗️ 2. SW 설계 대원칙: 관심사의 분리와 정적 리소스

소프트웨어 설계의 핵심 목표는 **유지보수성**입니다. 이를 위해 **UI(인터페이스), 로직, 데이터**를 엄격히 분리합니다.

- **문제 인식:** 초기에는 HTML 내부에 꾸밈 정보(디자인)가 섞여 있어, 디자인 하나를 바꾸려면 모든 데이터를 수정해야 하는 강한 의존성 문제가 있었습니다.
- **해결(관심사 분리):** 데이터(**HTML**), 꾸밈(**CSS**), 미디어(**사진/이미지**)를 각각 별도의 파일로 분리했습니다.
- **정적 문서(Static Document):** 서버 하드디스크에 저장된 파일을 가공 없이 그대로 클라이언트에 전송하는 단계입니다. 파일의 내용이 변하지 않으므로 '정적'이라 부릅니다.

## ⚙️ 3. 브라우저의 진화: 자바스크립트 엔진의 등장

문서에 동적인 '움직임'을 주기 위해 스크립트 규칙인 **JavaScript**가 추가되었습니다.

- **실행 위치의 이해:** 서버는 JS 파일을 **저장하고 전달**하는 배달원 역할만 수행합니다. 실제 코드를 해석하고 실행하는 주체는 **클라이언트(브라우저)**입니다. 이를 위해 브라우저 내부에 엔진이 필요해졌습니다.
- **브라우저의 3대 핵심 요소:**
    
    1. **파서(Parser):** HTML/XML 태그 분석.
    2. **렌더링 엔진:** CSS와 결합하여 화면 출력.
    3. **자바스크립트 엔진(예: V8):** 전달받은 코드를 실시간으로 실행.

## 🚀 4. [다음 예고] 문서 송수신에서 '서비스'로의 확장

초기 웹이 단순히 '파일을 주고받는 것'이었다면, 이제는 서버가 직접 일을 하는 **기능(Service)**의 단계로 진화합니다.

- **기능의 호출:** 단순히 저장된 문서를 가져오는 것이 아니라, 서버의 특정 기능을 작동시켜 그 **실행 결과값**을 받아옵니다.
- **로직의 공유:** 이제 실행 로직이 클라이언트(JS)뿐만 아니라 **서버(Back-end)**에도 존재하게 됩니다.
- **CGI(Common Gateway Interface):** 서버가 외부 프로그램을 실행하여 동적으로 결과를 생성하는 기술로, 웹이 '문서 전송 도구'에서 '서비스 플랫폼'으로 확장되는 시작점입니다.

### 💡 학습 정리

- **브라우저**는 원격 HTML을 해석해 보여주는 **뷰어**에서 시작해, 엔진을 탑재한 **실행기**로 발전했다.
- **유지보수**를 위해 내용(HTML)과 꾸밈(CSS)을 분리한 것이 웹 설계의 기초다.
- **초기 웹**은 정적 파일을 전달하는 데 그쳤으나, **현대 웹**은 서버가 직접 로직을 수행하는 **서비스**로 진화했다.
