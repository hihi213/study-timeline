### **VPD 대체 구현 방식 (View + Trigger)**

사용자님께서 정리해주신 대로, VPD 대체 구현 방식은 **조회(View)**와 **수정(Trigger)** 권한을 분리하여 수동으로 보안을 확립하는 것이 핵심입니다.

#### **1. 조회 제어: View를 통한 데이터 필터링**

- **VPD (Native) 방식:** DBMS 엔진이 SQL 실행 시점에 **자동으로 `WHERE` 절을 추가**하여 데이터를 필터링합니다. (동적)
    
- **대체 구현 (View) 방식:** DBMS가 자동으로 `WHERE` 절을 붙여주지 못하므로, 개발자가 **미리 `WHERE` 조건(예: `WHERE login_id = USER`)이 포함된 뷰(View)**를 생성합니다.
    
- **보안 적용:** 사용자에게 원본 테이블 접근 권한을 주지 않고, **이 필터링된 뷰에만 `SELECT` 권한을 부여**하여, 사용자 본인의 데이터만 볼 수 있게 합니다.
    

---

#### **2. 수정 제어: Trigger를 통한 접근 통제**

- **필요성:** 뷰를 통해 데이터를 조회하더라도, DML(Update/Delete) 명령을 통해 타인의 데이터를 변경하려는 시도는 가능할 수 있습니다.
    
- **대체 구현 (Trigger) 방식:** 테이블에 **트리거(`BEFORE UPDATE OR DELETE`)**를 설치하여 방어막을 만듭니다.
    
- **트리거 로직:** 트리거 내부에서 **"현재 접속한 사용자(`USER`)가 변경하려는 데이터의 원래 소유자(`:OLD.login_id`)와 같은가?"**를 비교합니다.
    
- **보안 적용:** 만약 다를 경우, 트리거는 해당 DML 작업을 취소하고 **에러(`RAISE_APPLICATION_ERROR`)를 발생**시켜 무단 수정을 원천적으로 차단합니다.
    

## VPD
- VPD란: 사용자가 SQL을 실행하면 DB가 자동으로 **`WHERE` 절(조건)** 을 추가해 실행하는 보안
- 사용자마다 접근가능한 데이터 즉, 행을 제한하는 기술이다.
- **핵심 패키지:** **`DBMS_RLS`** (RLS = Row Level Security)
### 1. 🔐 VPD 대체 구현: 뷰(조회제한)+트리거(수정제한)

Oracle Enterprise의 VPD(행 단위 보안)의 조회제한, 수정제한을
뷰와 트리거로 "뷰로 내 데이터만 보이게 하고, 트리거로 남의 데이터는 절대 건드리지 못하게 막는"  기능을 대체한다.


#### 사전 작업(기존과 동일)
```SQL
-- 1. 기존 계정이 있다면 삭제 (초기화)
DROP USER 유저이름 CASCADE;
-- 2. 계정 생성 (비밀번호: 1234)
CREATE USER 유저이름 IDENTIFIED BY 비밀번호 ACCOUNT UNLOCK;
-- 3. 기본 접속 권한 부여
GRANT CONNECT TO 유저이름;
-- 4. 테이블생성과 샘플데이터 삽입 
```

#### **① 조회 제한 (View)**

- **원리:** `WHERE` 절에 현재 접속한 사용자(`USER`)와 테이블의 주인 ID(`login_id`)가 같은지 비교합니다.
- **시험 포인트:** `USER` 키워드와 `WHERE` 절 조건.

```SQL
-- 1. 일반 직원용 뷰 (자신의 정보만 조회 가능)
-- 조건: login_id가 현재 접속자(USER)와 같은 행만 필터링
CREATE OR REPLACE VIEW vw_my_profile AS
SELECT * FROM employee2
WHERE login_id = USER;

-- 2. 인사팀용 뷰 (모든 직원 조회 가능, 단 주민번호 제외)
-- 조건: ssn 컬럼을 SELECT 절에서 제외
CREATE OR REPLACE VIEW vw_hr_view AS
SELECT emp_id, name, department, salary 
FROM employee2;

-- 3. 관리자용 뷰 (모든 정보 조회 가능)
CREATE OR REPLACE VIEW vw_admin_view AS
SELECT * FROM employee2;
```
#### **② 수정 제한 (Trigger)**

- **원리:** 뷰를 통해 조회를 막아도, SQL로 직접 `UPDATE`를 시도할 수 있습니다. 이를 막기 위해 **트리거**에서 `:OLD.login_id` (데이터 주인)와 `USER` (접속자)를 비교합니다.
- **시험 포인트:** `IF` 조건문과 `RAISE_APPLICATION_ERROR` (강제 에러 발생).

```SQL
CREATE OR REPLACE TRIGGER trg_emp_self_update
    BEFORE UPDATE OR DELETE ON employee2 -- 수정/삭제 시도 전
    FOR EACH ROW
BEGIN
    -- 접속자(USER)가 데이터 주인(:OLD.login_id)이 아니면 에러 발생
    IF USER <> :OLD.login_id THEN
        RAISE_APPLICATION_ERROR(-20001, '자신의 정보만 수정할 수 있습니다.');
    END IF;
END;
/
```

## FGA
- FGA란?: 특정 컬럼이나 조건에 대해 조회했을때만 기록 (급여처럼 민감)
- **핵심 패키지:** **`DBMS_FGA`**
- **로그 확인 뷰:** **`DBA_FGA_AUDIT_TRAIL
### 2. 🕵️‍♀️ FGA 대체 구현:


**핵심:** Oracle Enterprise의 FGA(정밀 감사)를 **로그 테이블**과 **조건부 트리거**로 흉내 내는 것입니다

#### **① 로그 테이블 (Audit Log)**

- 감사 기록을 담을 그릇입니다.
- **필수 컬럼:** 누가(`username`), 언제(`access_time`), 무슨 짓을(`action_type`), 어떤 데이터를(`accessed_data`) 4.
    

#### **② 조건부 감시 트리거 (Smart Trigger)**

- **원리:** 모든 변경을 기록하면 로그가 너무 커집니다. **"연봉이 10,000을 넘을 때"** 처럼 특정 조건에서만 트리거가 발동하도록 합니다.
- **시험 포인트:** **`WHEN` 절** 사용법 (매우 중요). 트리거 내부 `IF`문이 아니라, 트리거 선언부의 `WHEN`을 써야 성능이 좋습니다.

```SQL
CREATE OR REPLACE TRIGGER trg_audit_salary_update
    AFTER UPDATE OF salary ON users -- 급여 컬럼이 변경된 후에만
    FOR EACH ROW
    WHEN (NEW.salary > 10000)       -- ★ 핵심: 변경 후 급여가 1만 초과일 때만 실행 [cite: 1855]
BEGIN
    -- 로그 테이블에 기록 (이전 값 -> 새로운 값)
    INSERT INTO audit_log (username, access_time, action_type, accessed_data)
    VALUES (USER, SYSDATE, 'UPDATE', :OLD.salary || ' -> ' || :NEW.salary);
END;
/
```

### 📝 시험장 가져갈 체크리스트 (이것만 외우세요!)

1. **VPD 대체 (View):** `WHERE login_id = USER`
2. **VPD 대체 (Trigger):** `IF USER <> :OLD.login_id THEN RAISE_APPLICATION_ERROR…`
3. **FGA 대체 (Trigger):** `WHEN (NEW.컬럼명 > 값)` (괄호 필수!)
4. **변수 구분:**
    
    - `:OLD.컬럼`: 변경 **전** 값 (누가 내 데이터를 건드리기 전 주인 확인용)
    - `:NEW.컬럼`: 변경 **후** 값 (연봉을 1억으로 올리는지 감시용)


### 1. Virtual Private Database (VPD)

VPD는 오라클 엔터프라이즈 에디션에서 제공하는 강력한 보안 기능으로, 사용자가 별도의 `WHERE` 절을 입력하지 않아도 DB가 자동으로 보안 조건을 추가하여 데이터를 필터링하는 기술입니다.

#### **1) 핵심 개념**

- **행 단위 보안 (Row-Level Security):** 뷰(View)보다 강력하고 유연하며, 로그인한 사용자에 따라 자신이 접근 가능한 행(Row)만 조회/수정하도록 제한합니다.
- **동작 원리:** 사용자가 SQL(`SELECT * FROM employee`)을 실행하면, DBMS가 정책 함수(Policy Function)를 통해 자동으로 `WHERE` 조건을 덧붙여 실행합니다
    - _변환 예시:_ `SELECT * FROM employee` → `SELECT * FROM employee WHERE login_id = 'EMP_1001'`
        

#### **2) 구현 요소**

- **정책 함수 (Policy Function):** 현재 사용자(SESSION)에 따라 어떤 조건(Predicate)을 적용할지 결정하는 함수입니다
    - _예:_ 관리자('TEST')는 `1=1`(전체 조회), 일반 직원은 `login_id = USER`(본인만 조회) 반환
- **DBMS_RLS 패키지:** VPD 정책을 관리하는 패키지로, `ADD_POLICY` 프로시저를 통해 테이블에 정책을 등록합니다
    

#### **3) 제약 사항 및 주의점**

- **에디션 제한:** Oracle XE(Express Edition)나 SE(Standard Edition)에서는 사용할 수 없으며, Enterprise Edition 19c 이상에서만 가능합니다
- **주의사항:** 정책 함수가 복잡하면 성능 저하가 발생할 수 있으며, 자동으로 조건이 붙기 때문에 디버깅이 어려울 수 있습니다

### 2. View와 Trigger를 활용한 VPD 대체 구현 [44p ~ 49p]

Oracle XE와 같이 VPD를 사용할 수 없는 환경에서는 **View(조회 제한)**와 **Trigger(수정 제한)**를 조합하여 유사한 보안 효과를 낼 수 있습니다.

#### **1) 구현 전략**

VPD가 자동으로 하던 일을 **수동으로 분리**하여 구현합니다.

- **조회(SELECT) 제어:** 사용자별 맞춤형 **View** 생성
- **수정(UPDATE/DELETE) 제어:** **Trigger**를 사용하여 권한 검증
    

#### **2) 단계별 상세 구현**

Step 1: 사용자별 맞춤형 View 생성 (접근 제어)

사용자의 역할에 따라 서로 다른 뷰를 제공하여 데이터 노출을 최소화합니다.

- 일반 직원용 (본인 정보만 조회):
    
    USER 함수를 사용하여 현재 로그인한 사용자의 ID와 일치하는 데이터만 보여주는 뷰를 생성합니다.
    
    ```SQL
    CREATE OR REPLACE VIEW vw_my_profile AS
    SELECT * FROM employee2
    WHERE login_id = USER; -- 로그인한 사용자의 데이터만 조회 [cite: 853, 854, 855]
    ```
    
- 인사팀용 (민감 정보 제외):
    
    주민번호(SSN) 같은 민감 컬럼을 제외하고 나머지 정보를 조회하는 뷰를 생성합니다
    
- 관리자용 (전체 조회):
    
    모든 데이터에 접근 가능한 뷰를 생성합니다12.
    

Step 3: 권한 부여

테이블에 대한 직접 접근 권한(SELECT 등)은 회수하고, 위에서 만든 View에 대해서만 권한(GRANT SELECT)을 부여합니다13.

Step 4: Trigger를 통한 수정 제한

뷰를 통해 데이터를 조회하더라도, 직접적인 SQL 조작을 통한 데이터 변조를 막기 위해 트리거를 사용합니다.

- 수정/삭제 제한 트리거:
    
    BEFORE UPDATE OR DELETE 트리거를 생성하여, 본인의 데이터가 아닌 경우 에러를 발생시킵니다.
    
    ```SQL
    IF USER <> :OLD.login_id THEN
        RAISE_APPLICATION_ERROR(-20001, '자신의 정보만 수정하거나 삭제할 수 있습니다.');
    END IF; -- [cite: 871, 872]
    ```

### **요약 및 비교**

| **구분**    | **VPD (Enterprise)**         | **View + Trigger (XE 대체)**  |
| --------- | ---------------------------- | --------------------------- |
| **적용 방식** | 정책 함수에 의해 SQL 실행 시 **자동** 적용 | 개발자가 **명시적**으로 뷰와 트리거를 생성   |
| **보안 수준** | DB 커널 레벨에서 강제 적용 (매우 강력)     | 애플리케이션 레벨에서 뷰 사용을 강제해야 함    |
| **장점**    | SQL 수정 없이 일괄 보안 적용 가능        | 모든 에디션에서 구현 가능              |
| **단점**    | 설정이 복잡하고 디버깅이 어려움            | 뷰와 트리거를 사용자/역할별로 일일이 관리해야 함 |
