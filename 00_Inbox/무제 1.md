# 🌐 웹 서비스의 진화: 데이터 조회에서 로직 처리로

## 1. 패러다임의 전환: 단방향 조회에서 양방향 상호작용으로

웹은 단순히 파일을 가져오는 도구에서, 서버의 기능을 작동시키고 생성된 결과값을 획득하는 플랫폼으로 진화했습니다.

- **정적 웹 (GET 중심):** 특정 파일 경로를 요청해 데이터를 수신하는 **조회(Read)** 구조입니다. 서버 내부의 데이터 상태를 변경하지 않는 단방향 상호작용입니다.
- **동적 서비스 (POST 중심):** 매개변수와 함께 기능을 요청하여 서버 로직을 가동시키는 **처리(write/Process)** 구조입니다. 실시간 결과값을 생성하며 시스템의 변화를 유도하는 양방향 상호작용입니다.

## 2. 상호작용의 메커니즘: 절차와 상태 전이

양방향 통신은 단순히 데이터를 주고받는 것이 아니라, 서버 내부의 상태를 변화시키는 과정입니다.

- **절차 발생 (Procedure):** 입력값을 바탕으로 목표 결과를 도출하는 일련의 연산 단계입니다.
	> 예: 로그인의 절차 [데이터 수신 → 유효성 검사 → DB 대조 → 세션 생성]
- **상태 전이 (State Transition):** 절차 완료 후 시스템이 보유한 데이터의 **스냅샷(Snapshot)** 이 업데이트되는 현상입니다.
    - **상태(State):** **특정 시점**, 시스템에 저장된 데이터의 구체적인 값.
    - **전이(Transition):** 로직 결과에 따라 기존 상태(비로그인)가 새로운 상태(로그인)로 바뀌는 것. 
## 3. 기술적 한계: CGI와 플랫폼 의존성

초기 동적 웹(CGI)은 **C언어** 기반의 특성상 물리적 환경의 제약이 매우 컸습니다.

- **컴퓨터의 3계층:**
	- 애플리케이션(소프트웨어)
	- 시스템(소프트웨어)
	- 하드웨어
- **플랫폼(Platform):** 하드웨어의 핵심인 **CPU**와 시스템 소프트웨어의 핵심인 **운영체제**의 결합
	- cpu는 머신, 운영체제는 os라고도 한다.
	- cpu의 코드는 native
	- 플랫폼에 종속적인 코드를 Native Code라 한다.
- C언어는 native code를 생성한다. 그래서 서버 환경(CPU/OS)이 변경되면 코드를 재작성하거나 재컴파일해야 하므로 유지보수성이 낮습니다.

## 4. 현대적 해결책: Java와 WAS (Web Application Server)

이러한 한계를 극복하기 위해 플랫폼 독립성과 역할 분리를 기반으로 한 현대적 아키텍처가 정립되었습니다.

### **Java와 JVM: 플랫폼 독립성**

- **JVM(Java Virtual Machine):** Java는 머신코드 대신 **바이트코드**를 생성합니다. 이를 JVM이 실행 시점에 각 플랫폼에 맞게 해석하므로, 환경에 상관없이 동일한 코드를 실행하는 플랫폼 독립성을 실현했습니다.

### **WAS의 등장: 역할과 책임의 분리**
> 소프트웨어 설계 원칙인 '관심사의 분리'가 서버 아키텍처에도 적용되었습니다.
- **Web Server (Apache 등):** 정적 리소스 송수신 및 클라이언트와의 통신 인프라 담당.
- **WAS (Tomcat 등):** 복잡한 비즈니스 로직 처리 및 애플리케이션 실행 담당.
- **장점:** 통신과 로직을 분리함으로써 대규모 시스템에서도 상태 전이 로직을 안정적이고 효율적으로 관리할 수 있습니다.

## 💡 최종 핵심 요약

1. **동작의 확장:** 웹은 리소스 조회(GET)를 넘어 시스템 상태를 변경하는 **기능 호출(POST)**로 진화했다.
2. **핵심 기제:** 양방향 통신은 서버 내부의 **절차**를 가동하고, 그 결과로 데이터의 **상태 전이**를 일으킨다.
3. **환경의 극복:** 특정 플랫폼(CPU+OS)에 종속적인 **Native Code**의 한계를 **Java(JVM)**가 해결했다.
4. **효율적 설계:** 유지보수를 위해 송수신(Web Server)과 처리(WAS)를 분리하는 **현대적 WAS 구조**가 확립되었다.
