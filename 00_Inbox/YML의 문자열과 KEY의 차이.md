## 정리

### 1) 부족 포인트 스캔
* **데이터 타입의 불일치:** `String`과 `Key`는 완전히 다른 목적과 구조를 가진 데이터 타입이라는 점을 간과하고 있습니다. 하나는 문자 배열, 다른 하나는 암호화 정보를 담은 규격화된 객체입니다.
* **API의 역할:** 라이브러리(Library)가 왜 특정 타입의 객체(`Key`)를 파라미터로 요구하는지, 즉 API 설계의 의도를 파악하지 못하고 있습니다.
* **컴퓨터의 데이터 처리 방식:** 암호화 연산과 같은 저수준(low-level) 처리는 사람이 읽는 '문자'가 아닌, 컴퓨터가 이해하는 '바이트(byte)' 단위로 이루어진다는 기본 원리를 놓치고 있습니다.

### 2) 핵심 개념 요약
* **`String` 객체:** 자바에서 유니코드 문자의 연속을 표현하는 객체입니다. 본질적으로 사람이 읽고 쓰기 위한 '텍스트' 데이터입니다.
* **`byte[]` (바이트 배열):** 8비트(bit) 데이터 단위인 바이트(byte)의 배열입니다. 파일, 네트워크 데이터, 암호화 키 등 컴퓨터 시스템에서 처리되는 모든 데이터의 가장 기본적인 형태입니다.
* **`Key` 객체 (JCA Spec):** 자바 암호화 아키텍처(Java Cryptography Architecture) 명세에 따른 인터페이스입니다. 이 객체는 암호화 키의 원시 데이터(`byte[]`)뿐만 아니라, 해당 키가 어떤 알고리즘(예: "HS256")에 사용될 것인지와 같은 메타데이터를 포함하는 구조체입니다.
* **API 계약 (API Contract):** 라이브러리 제작자가 정한 규칙입니다. JWT 라이브러리의 `signWith()` 메소드는 "나는 서명을 위해 반드시 `Key` 타입의 객체만 받겠다"라고 약속(정의)해 놓은 것입니다.

### 3) 용어 매핑
* `yml의 문자열`: **원시 설정 텍스트 (Raw Configuration Text)**
    * `설명`: `.yml` 파일에 저장된, 아직 아무런 처리가 되지 않은 순수한 문자 데이터입니다.
* `서명에 사용하는 최종 Key 객체`: **JCA `SecretKey` 구현체 (JCA `SecretKey` Implementation)**
    * `설명`: JWT 라이브러리가 요구하는 표준 인터페이스를 구현한, 암호화 연산에 즉시 사용될 수 있는 상태의 객체입니다.

### 4) 사고 틀 & 판단 기준
이 둘이 왜 다른지 데이터가 변환되는 과정을 순서대로 살펴보면 명확해집니다.

1.  **[1단계] 파일 읽기 (File I/O) & 텍스트 로딩**
    * **프로세스:** 스프링 부트 애플리케이션이 시작되면, `application.yml` 파일을 읽습니다. 파일의 내용은 순수한 텍스트이므로, 자바는 `jwt.secret: "..."` 부분의 값을 `String` 타입 객체로 메모리에 올립니다.
    * **이 시점의 데이터:** `String secretString = "Base64EncodedSecretKeyString";`
    * **한계:** 이 `String`은 그저 문자의 나열일 뿐, 암호학적 의미나 속성을 전혀 가지고 있지 않습니다.

2.  **[2단계] 데이터 변환 (Data Transformation)**
    * **프로세스:** 암호화 알고리즘은 텍스트가 아닌 바이너리(binary) 데이터, 즉 `byte[]`를 입력으로 받습니다. 따라서 `String`을 `byte[]`로 변환해야 합니다. 만약 원본 문자열이 Base64로 인코딩되어 있었다면, Base64 디코더를 사용해 원본 `byte[]`로 복원합니다.
    * **이 시점의 데이터:** `byte[] keyBytes = Base64.getDecoder().decode(secretString);`
    * **한계:** 이제 암호화 연산이 가능한 원시 데이터 조각은 확보했지만, 이 데이터가 어떤 알고리즘에 쓰일 것인지, 어떤 형식인지에 대한 정보는 여전히 없습니다.

3.  **[3단계] 객체화 (Object Instantiation)**
    * **프로세스:** JWT 라이브러리는 `byte[]`만 받아서는 어떤 알고리즘으로 서명해야 할지 알 수 없습니다. 그래서 라이브러리는 `byte[]`와 알고리즘 정보를 함께 캡슐화하는 `Key` 객체 생성을 요구합니다.
    * **이 시점의 데이터:** `Key hmacKey = new SecretKeySpec(keyBytes, "HmacSHA256");`
    * **결과:** 드디어 `hmacKey`라는 `Key` 객체가 생성되었습니다. 이 객체 안에는 **(1) 키의 실제 데이터인 `keyBytes`**와 **(2) 이 키가 'HmacSHA256'용이라는 정보**가 함께 들어있습니다.

이제 JWT 라이브러리의 `signWith(hmacKey)` 메소드를 호출하면, 라이브러리는 `hmacKey` 객체에서 키 데이터와 알고리즘 정보를 모두 꺼내 안전하게 서명 연산을 수행할 수 있습니다.

**결론적으로, `yml`의 문자열은 최종 `Key` 객체를 만들기 위한 '재료'에 불과하며, 실제 연산에 사용되기까지는 `String` → `byte[]` → `Key Object` 라는 명확한 데이터 타입 변환 및 객체화 과정을 거쳐야만 합니다.**

### 5) 체크 질문(자가 점검)
* JWT 라이브러리가 `String`이나 `byte[]` 대신 `Key` 객체를 인자로 받도록 설계한 가장 큰 이유는 무엇일까요? (힌트: 타입 안정성, 정보 캡슐화)
* `String`을 `byte[]`로 변환할 때, 어떤 문자 인코딩(예: UTF-8)을 사용할지 결정하는 것이 왜 중요한가요?
	- 같은 글자라도 인코딩에 따라 바이트가 달라지면 **전혀 다른 키**
* `new SecretKeySpec(bytes, "ALGORITHM")` 코드가 실행될 때, `bytes` 외에 알고리즘 이름 문자열을 추가로 받는 이유는 무엇일까요?
	*   **동일 바이트 ≠ 동일 의미**: 같은 bytes라도 **AES 키인지 HMAC 키인지**에 따라 쓰임·제약이 달라서, JCA가 올바른 엔진(Cipher/Mac 등)과 **검증 규칙(길이/패딩/패리티)** 을 적용하려면 알고리즘 식별자가 필요합니다.
