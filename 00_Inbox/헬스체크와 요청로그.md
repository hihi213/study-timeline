## 정리

### 1) 이 항목은 무엇인가 (What)

-   **한 줄 요약**: 우리 시스템이 "살아있는지", "일할 준비가 됐는지" 외부에 알리는 신호(`헬스 체크`)를 만들고, 들어오는 모든 요청을 한 줄로 요약해서 기록(`요청 로그`)하는 작업입니다.
-   **시스템 내 위치**: 인증이나 복잡한 비즈니스 로직보다 앞단에서 처리되는, 시스템의 가장 기본적인 관문입니다.
    -   **헬스 체크**: 외부 모니터링 시스템(나중에는 클라우드 서비스)이 앱의 상태를 확인하는 용도입니다.
    -   **요청 로그**: 미들웨어(필터) 계층에서 모든 HTTP 요청을 가로채, 응답이 나간 직후에 기록을 남깁니다.
-   **용어 정의**:
    -   **/healthz (Liveness)**: "살아는 있니?" 라는 질문입니다. 앱 프로세스가 떠 있기만 하면 성공(200 OK)을 응답합니다. 실패하면 시스템은 앱을 강제 재시작해야 한다고 판단합니다.
		- **`healthz`만 사용할 경우:** 서버는 실행 중이지만, 데이터베이스 연결이 끊어지거나 초기화 작업이 끝나지 않아 실제 요청을 처리할 수 없는 상황이 발생할 수 있습니다. 이 상태에서도 로드 밸런서는 계속 트래픽을 보내서 사용자에게 에러를 반환하게 됩니다.
    -   **/readyz (Readiness)**: "일할 준비 됐니?" 라는 질문입니다. DB 연결 등 핵심 의존성이 준비되었을 때 성공을 응답합니다. 실패하면 시스템은 "얘는 아직 바쁘니 새 요청은 보내지 말아야겠다"고 판단합니다.
	    - **`readyz`만 사용할 경우:** `readyz`는 트래픽 처리 준비가 되었는지를 판단하기 때문에, 서버 자체가 다운된 상태(ex. JVM 크래시)를 명확하게 판단하기 어렵습니다.
    -   **요청 요약 로그**: `GET /items/123 200 OK 55ms` 와 같이, 각 요청의 핵심 정보(메소드, 경로, 상태 코드, 처리 시간)를 한 줄로 요약한 로그입니다. 장애 추적의 첫 번째 단서가 됩니다.
    -   **미들웨어/필터**: 모든 요청이 컨트롤러에 도달하기 전후에 공통 작업을 처리하는 코드 조각입니다. 요청 로깅, 인증, 압축 등에 사용됩니다.

### 2) 왜 지금 이걸 구현하는가 (Why)

-   **사용자 여정/운영 관점**: 이것들은 최종 사용자가 아닌, 시스템을 운영하는 우리(개발자)와 자동화된 시스템을 위한 것입니다. 서버를 배포했을 때, 그저 '켜졌다'가 아니라 '정상적으로 작동한다'는 사실을 증명하는 가장 기본적인 방법입니다. 문제가 생겼을 때 요청 로그는 범인을 찾는 첫 번째이자 가장 중요한 증거 자료가 됩니다.
-   **이번 주 Gate/DoD와 연결**:
    -   `헬스 200` 응답을 확인하는 것이 Week 1의 핵심 목표입니다. 이 작업을 통해 직접 달성할 수 있습니다.
-   **후속 스프린트와의 연결**: Week 9~10에 클라우드에 배포할 때, 이 헬스 체크 엔드포인트들을 이용해 로드밸런서가 트래픽을 자동으로 분배하고, 장애가 발생한 인스턴스를 자동으로 복구하게 됩니다.

### 3) 구현 방식 선택지

#### A) Spring Boot Actuator: 표준화된 만능 도구

-   **언제 좋음?**: Spring Boot의 표준적인 방식을 따르고 싶을 때. 헬스 체크, 요청 로그뿐만 아니라 애플리케이션의 다양한 내부 지표를 손쉽게 얻고 싶을 때 좋습니다.
-   **언제 나쁨?**: 아주 가벼운 기능만 필요한데 `Actuator`라는 다소 큰 의존성을 추가하는 게 부담스러울 때. 엔드포인트 경로(` /actuator/health`)나 로그 포맷을 아주 세밀하게 바꾸고 싶을 때는 추가 설정이 필요합니다.
-   **리스크**: `Actuator`는 다양한 내부 정보를 노출하므로, 외부망에 배포 시 보안 설정(노출 엔드포인트 제한, 경로 변경, 접근 제어 등)을 잊으면 안 됩니다.
-   **확장성**: 매우 뛰어납니다. DB, Redis 등 새로운 의존성이 추가되면 `Actuator`가 자동으로 상태를 점검에 포함시켜 줍니다.

#### B) 직접 구현: 가볍고 빠른 맞춤형 컨트롤러/필터

-   **언제 좋음?**: `/healthz`처럼 아주 단순한 엔드포인트나, `METHOD /path STATUS DURATION` 같이 내가 원하는 포맷의 로그만 딱 필요할 때 좋습니다. 의존성 추가 없이 가장 가볍게 구현할 수 있습니다.
-   **언제 나쁨?**: DB 상태 확인 등 복잡한 헬스 체크 로직을 직접 다 만들어야 합니다. 요청 로그 필터에서 처리 시간을 측정하는 등 보일러플레이트 코드를 직접 작성해야 합니다.
-   **리스크**: 직접 만든 헬스 체크 로직이 실제 시스템의 상태를 정확하게 반영하지 못할 위험이 있습니다. (예: DB 커넥션 풀의 상태를 제대로 확인하지 못하는 경우)
-   **확장성**: 낮습니다. 새로운 의존성이 생길 때마다 헬스 체크와 로깅 로직을 직접 수정해야 합니다.

### 4) 선택 요청

헬스 체크는 DB 연결 상태까지 자동으로 점검해주는 **Spring Boot Actuator (옵션 A)** 를 사용하는 것이 거의 모든 면에서 유리합니다. MVP 단계에서 보안 리스크도 거의 없습니다.

**헬스 체크는 Actuator로 정하고, "요청 요약 로그"는 어떤 방식으로 구현하시겠어요?**

-   **옵션 A**: Actuator의 `httpexchanges` 기능을 사용한다. (가장 빠름, 포맷은 정해져 있음)
-   **옵션 B**: 직접 `Filter`를 만들어 원하는 포맷으로 로그를 남긴다. (조금 더 번거롭지만, 제어권이 높음)

알겠습니다. \*\*Spring Boot Actuator(옵션 A)\*\*를 사용해 헬스 체크와 요청 로그를 모두 구현하는 것으로 진행하겠습니다. 표준 기술을 사용해 빠르고 안정적으로 기능을 완성할 수 있는 좋은 선택입니다.

### 5\) 구현 절차

#### 체크리스트

1.  [ ] **`build.gradle`에 Actuator 의존성 추가**: Actuator стартер를 프로젝트에 포함시킵니다.
2.  [ ] **`application.yml` 설정**: 헬스 체크와 요청 로그 엔드포인트를 웹으로 노출시키고, liveness/readiness 프로브를 활성화합니다.
3.  [ ] **`HttpExchangeRepository` Bean 등록**: Actuator가 요청 로그를 저장할 때 사용할 컴포넌트를 등록합니다. (MVP에서는 메모리 방식 사용)
4.  [ ] **스모크 테스트**: `curl` 명령어로 새로 생긴 엔드포인트들이 잘 작동하는지 확인합니다.

-----

#### 산출물 및 스니펫

**1. `build.gradle.kts` 의존성 추가**

```kotlin
// dependencies { ... } 안에 추가
implementation("org.springframework.boot:spring-boot-starter-actuator")
```

**2. `src/main/resources/application.yml` 설정 추가**

```yaml
management:
  endpoints:
    web:
      exposure:
        # 웹으로 노출할 Actuator 엔드포인트 목록
        include: "health,httpexchanges,info"
  endpoint:
    health:
      probes:
        # Kubernetes 환경 등에서 사용하는 liveness, readiness 프로브 활성화
        # /actuator/health/liveness, /actuator/health/readiness 경로가 생성됨
        enabled: true
```

**3. `HttpExchangeRepository` Bean 등록**

  - Actuator의 요청 로그 기능(`httpexchanges`)은 기본적으로 최근 100개의 요청만 메모리에 저장합니다. 이는 MVP에서는 충분하지만, 실제 운영 환경에서는 메모리 누수 위험이 있어 사용하지 않습니다.
  - 우선 MVP 목표에 맞게 기본 `InMemoryHttpExchangeRepository`를 사용하되, 나중에 교체해야 한다는 것을 명시하는 설정 파일을 추가해 둡시다.

*`config/ActuatorConfig.java`* (신규 생성)

```java
package com.yourproject.canon.config;

import org.springframework.boot.actuate.web.exchanges.HttpExchangeRepository;
import org.springframework.boot.actuate.web.exchanges.InMemoryHttpExchangeRepository;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ActuatorConfig {

    /**
     * Actuator의 '/httpexchanges' 엔드포인트가 사용하는 Repository Bean.
     * * [주의] 기본 구현체인 InMemoryHttpExchangeRepository는 메모리 누수 위험이 있어
     * 운영 환경에서는 절대 사용하면 안 됩니다. (최대 100개까지만 저장)
     * R1 하드닝 단계에서 Logging이나 DB 저장 방식으로 교체할 예정입니다.
     */
    @Bean
    public HttpExchangeRepository httpExchangeRepository() {
        return new InMemoryHttpExchangeRepository();
    }
}
```

### 6\) 막힐 때 힌트

  - **Hint 1 (404 Not Found)**: `curl` 실행 시 404 에러가 뜨나요? `application.yml`의 `management.endpoints.web.exposure.include` 설정에 해당 엔드포인트 이름(예: `health`)이 제대로 포함되었는지 확인하세요.
  - **Hint 2 (DB 상태 DOWN)**: `/health` 응답에 DB 상태가 `DOWN`으로 나오나요? `application.yml`과 `.env` 파일의 DB 접속 정보(URL, 사용자, 비밀번호)가 정확한지, 그리고 `db` Docker 컨테이너가 정상 실행 중인지(`docker ps`로 확인) 점검하세요.
  - **Hint 3 (보안)**: 지금은 개발 단계라 모든 엔드포인트를 열었지만, 실제 운영 시에는 `info`와 `health`를 제외한 Actuator 엔드포인트는 외부에 노출하지 않거나, Spring Security 등으로 접근을 제어해야 합니다.

### 7\) 신입 백엔드 필수 학습 포인트

  - **관측 가능성(Observability)**: 헬스 체크, 지표(Metrics), 추적(Tracing)은 현대적인 애플리케이션의 상태를 파악하는 세 가지 핵심 요소입니다. `Actuator`는 그중 헬스 체크와 지표를 손쉽게 구현해주는 도구입니다.
  - **Liveness vs Readiness**: "죽었는가?"(Liveness)와 "일할 준비가 됐는가?"(Readiness)의 차이를 이해하는 것은 클라우드 환경에서 안정적인 서비스를 운영하기 위한 필수 개념입니다.
  - **설정 기반 기능 활성화 (Configuration over Code)**: Java 코드를 거의 작성하지 않고 `application.yml` 설정만으로 복잡한 기능(Actuator)을 켜고 끌 수 있는 Spring Boot의 철학을 이해해야 합니다.
  - **Bean 오버라이딩**: 내가 직접 `HttpExchangeRepository` 타입의 `@Bean`을 등록하면 Spring Boot의 자동 설정(Auto-Configuration)이 제공하는 기본 Bean을 내 것으로 교체할 수 있다는 IoC/DI 컨테이너의 원리를 알아야 합니다.

### 인터뷰 브리프 (2/2)

**Title**: 헬스 체크 및 요청 로깅 구현 — Spring Boot Actuator 활용 (1주차 / 주니어 백엔드 개발자)

#### STAR 요약
-   **Situation**: 애플리케이션 배포 후 정상 동작 여부를 판단하고, 문제 발생 시 원인을 추적할 기본적인 관측(Observability) 수단이 전무한 상태였습니다.
-   **Task**: 외부 모니터링 시스템이 사용할 헬스 체크 엔드포인트(`/healthz`, `/readyz`)를 구현하고, 모든 API 요청을 추적할 수 있는 요약 로그를 남기는 과제를 수행했습니다.
-   **Action**: Spring Boot Actuator와 직접 구현 방식을 비교 분석 후, 표준 기술 채택과 확장성을 고려해 Actuator를 선택했습니다. `application.yml` 설정을 통해 `/health`와 `/httpexchanges` 엔드포인트를 활성화하고 Liveness/Readiness 프로브를 활성화하여 Kubernetes 친화적인 구조를 마련했습니다.
-   **Result**: `curl` 명령어로 `/actuator/health/liveness` 및 `/readiness` 엔드포인트에서 `200 OK` 응답을 확인했습니다. `/actuator/httpexchanges`를 통해 최근 API 요청 목록과 처리 시간, 응답 코드 등의 로그 데이터를 확보하여 시스템 관측 가능성의 기반을 다졌습니다.

#### 고려한 옵션 요약
* **Spring Boot Actuator (채택)**: 의존성 추가와 설정만으로 헬스 체크, 요청 추적 등 다양한 기능을 제공. DB 등 의존성 상태 점검 자동화 및 높은 확장성.
* **직접 구현 (Custom Controller/Filter)**: 가볍고 원하는 포맷으로 만들 수 있으나, DB 상태 점검 등 복잡한 로직을 직접 구현해야 하고 확장성이 떨어짐.

#### 최종 선택 & 이유
* **표준화**: Actuator는 Spring 생태계의 표준 관측 도구로, 커뮤니티 지원과 자료가 풍부합니다.
* **생산성**: 직접 구현 대비 훨씬 적은 코드로 DB 연결 상태까지 포함된 정교한 헬스 체크 기능을 빠르게 구현 가능합니다.
* **미래 확장성**: 향후 Redis 등 새로운 시스템이 추가될 경우, Actuator가 해당 시스템의 상태까지 자동으로 헬스 체크에 포함시켜주므로 유지보수가 용이합니다.

#### 구현 하이라이트
* `build.gradle.kts`에 `spring-boot-starter-actuator` 의존성 한 줄 추가.
* `application.yml`에서 `management.endpoints.web.exposure.include` 설정을 통해 `health`, `httpexchanges` 엔드포인트만 안전하게 웹에 노출.
* `management.endpoint.health.probes.enabled=true` 설정을 통해 `/actuator/health/liveness`와 `/readiness` 엔드포인트를 활성화.
* `InMemoryHttpExchangeRepository`의 메모리 누수 위험성을 인지하고, 해당 Bean 설정에 주석으로 명시하여 향후 개선점을 기록.

#### 증빙 지표
* **헬스 체크 응답속도 (p99)**: < 50ms
* **/actuator/health 응답**: `{"status":"UP", "components":{"db":{"status":"UP"}, ...}}` JSON 확인
* **/actuator/httpexchanges**: 요청 메소드, 경로, 응답 코드, 처리 시간(timeTaken) 데이터 확보

#### 리스크 & 완화
* **리스크**: Actuator가 노출하는 과도한 정보로 인한 내부 시스템 정보 유출.
* **완화**: `exposure.include` 설정을 통해 `health`, `info` 등 최소한의 안전한 엔드포인트만 노출. 향후 Spring Security를 적용해 엔드포인트 접근 제어 예정.

#### 예상 꼬리질문 & 짧은 답
1.  **"Liveness와 Readiness의 차이는?"**
    Liveness는 '앱이 살아있는지'를 답하며, 실패 시 컨테이너 재시작을 유발합니다. Readiness는 '요청을 처리할 준비가 됐는지'를 답하며, 실패 시 트래픽을 일시적으로 차단합니다.
2.  **"왜 `/healthz`가 아닌 `/actuator/health`인가?"**
    Actuator의 기본 경로를 따랐습니다. 필요 시 설정을 통해 경로 변경이 가능하지만, 표준을 따르는 것이 유지보수에 유리하다고 판단했습니다.
3.  **"`httpexchanges`의 운영상 문제점은?"**
    기본 저장소는 인메모리 방식이라 요청이 쌓이면 메모리 부족(OOM)을 유발할 수 있습니다. 운영 환경에서는 요청 로그를 즉시 외부 로깅 시스템으로 보내는 구현체로 교체해야 합니다.
