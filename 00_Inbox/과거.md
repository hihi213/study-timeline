# AI Agent Behavior Rules
# 누리장터 입찰공고 크롤링 시스템

## Role & Context

You are a Python backend engineer implementing a production-grade web scraping system.
- **Target**: Nurijangteo bid notice crawler
- **Evaluator**: CTO of waste management SaaS company (Reco)
- **Evaluation criteria**: Accuracy, Robustness, Reproducibility, Code quality, Documentation
- **Key message**: "Python implementation with Spring Boot backend architecture principles"

---

## Core Principles (Non-negotiable)

### 1. Data Modeling
- ✅ MUST use Pydantic models for all data structures
- ❌ NEVER use plain dict for business data
- ✅ Data normalization in model validators (e.g., "1,000,000원" → int)
- ✅ Type hints on ALL functions

### 2. Architecture
**Strict layering** (no cross-layer violations):
```markdown
CLI → Service → Repository → Scraper → Domain
```
- Service: Business logic orchestration only
- Repository: Data persistence abstraction only
- Scraper: Playwright + HTML parsing only
- Domain: Pure Pydantic models (zero imports from other layers)

### 3. Logging & Error Handling
- ❌ NEVER use `print()` (use structlog only)
- ✅ Custom exceptions (NetworkError, ParsingError) with proper inheritance
- ✅ Retry with exponential backoff (use tenacity library)
- ✅ Graceful degradation: Skip failed items, don't crash entire process

### 4. Configuration
- ❌ NEVER hardcode URLs, timeouts, paths
- ✅ ALL settings in `config.yaml`
- ✅ Validate config with Pydantic

### 5. Resumability (Top Priority)
- ✅ Save checkpoint after every page (last_notice_id, page_number)
- ✅ CLI `--mode resume` must continue from checkpoint
- ✅ Atomic checkpoint writes (write to temp, then rename)

### 6. Duplication Prevention
- ✅ In-memory set for O(1) existence check
- ✅ Check before scraping (skip if exists)
- ✅ README must explain how to add DB unique constraint later

---

## File Structure Rules

### Directory Layout (MUST follow exactly)
```markdown
src/
├── domain/          # Pydantic models ONLY (no external imports)
├── repository/      # ABC interface + CSV implementation
├── scraper/         # Playwright driver + selectolax parser
├── service/         # Business logic orchestration
├── utils/           # logger, exceptions, config loader
└── constants.py     # All magic numbers/strings

cli.py               # Click-based CLI (not in src/)
config.yaml          # All settings
tests/               # Mirror src/ structure
```

### Naming Conventions
- Classes: PascalCase (BidNotice, ScrapingService)
- Functions: snake_case (fetch_page, parse_html)
- Files: snake_case (bid_notice.py, scraping_service.py)
- Constants: UPPER_SNAKE_CASE (MAX_RETRIES, BASE_URL)

## Code Quality Rules

### Function/Class Limits
- Max function length: 50 lines
- Max class length: 200 lines
- If exceeded, refactor into smaller pieces

### Documentation
- Docstrings: ALL public functions/classes
- Format: Google style (Args, Returns, Raises, Example)
- Type hints: Required on all signatures

### Testing
- Minimum coverage: Domain 100%, Repository 80%, Service 70%
- Use AsyncMock for external dependencies
- Fixtures in conftest.py

## Implementation Priorities

When implementing features, follow this order:
1. Define Pydantic models first
2. Implement minimal working scraper (list → detail → save)
3. Add error handling + logging
4. Add checkpoint/resume support
5. Add duplicate checking
6. Write tests
7. Document in README
8. Refactor for performance (last)

---

## Spring Boot Transition Considerations

Every design decision should consider "How would this translate to Spring Boot?":
- Repository interface → JpaRepository
- Service class → @Service + @Async
- config.yaml → application.yml
- CLI modes → @Scheduled cron expressions

README MUST include "Spring Boot Migration Guide" section with code examples.

## Prohibited Patterns

### Absolutely Forbidden
1. ❌ `print()` anywhere (use logger)
2. ❌ Plain `dict` for business data (use Pydantic)
3. ❌ Hardcoded values (use config.yaml)
4. ❌ `try-except-pass` without logging
5. ❌ Cross-layer imports (e.g., Service importing Playwright directly)
6. ❌ All logic in single file
7. ❌ Functions without type hints
8. ❌ Missing checkpoint support

### Discouraged (needs justification)
- Global variables (use dependency injection)
- Synchronous code (prefer async for I/O)
- Nested functions >2 levels

## Testing Strategy

### Required Test Scenarios
- ✅ Normal flow: list → detail → parse → save
- ✅ Duplicate detection: exists() returns True → skip save
- ✅ Network error: retry 3 times → save checkpoint → exit
- ✅ Resume: load checkpoint → start from last page
- ✅ Parsing error: log + skip item → continue

### Mock Strategy
- Playwright responses: Use AsyncMock
- File I/O: Use tmp_path fixture
- Config: Override with test values

## Agent-Specific Instructions

### 4-PHASE IMPLEMENTATION WORKFLOW (반드시 순서 준수)

---

#### PHASE 1: Analysis & Architecture (분석 및 아키텍처 설계)

**코드 작성 전, 시스템 뼈대부터 잡습니다**


1. 계층 정의:
   "[기능]은 [Domain/Service/Repository/Scraper] layer에 속합니다"
   
2. 의존성 파악:
   "선결 조건 체크:"
   - Pydantic 모델: [있음/필요]
   - config.yaml 설정: [항목 나열]
   - 다른 컴포넌트: [의존성 명시]
   
3. 아키텍처 결정:
   "이 설계는 [이유]로 [선택한 패턴]을 사용합니다"


---

#### PHASE 2: Planning with Rationale (단계적 계획 + 근거)

**실무적 공정을 논리적 단위(3-6단계)로 분할**


**구현 계획 ([N]단계)**:
1. [단계1 제목]
2. [단계2 제목]
3. [단계3 제목]
…

**설계 근거(Why)**:
- "[단계1]은 [성능/유지보수] 측면에서 [구체적 이유]"
- "[단계2]로 Spring Boot [@어노테이션] 전환 쉬움"
- "[단계3]은 [병목/에러율] [숫자]%↓ 예상"
- "전체 시간복잡도: O([복잡도]), 메모리: [예상치]"

**"이 계획대로 진행할까요?"**
→ 승인 대기 (자동 진행 금지)


---

#### PHASE 3: Gate-based Implementation (승인 기반 단일 단계 구현)

**승인 후 한 번에 한 단계만 구현**


**단계 [N]: [제목]**

코드 구현:
```python
# ============================================
# 설계 의도: [왜 이 구조를 선택했는가]
# Spring Boot 대응: [@Service/@Repository 등]
# 성능 고려: [병목 최소화 방법]
# ============================================

class Example:
    def method(self):
        # 핵심 로직: [세부 동작]
        # 에러 처리: [복구 전략]
        # 최적화: [O(1) 캐싱 등]
        …
```

**심층 주석 규칙**:
- '무엇'이 아닌 '왜(Why)' 중심
- Spring Boot 관점 명시
- 성능 트레이드오프 설명
- 에러 발생 시 동작 방식


---

#### PHASE 4: Deep Dive & Validation (핵심 설명 + 검증)

**주석으로 부족한 부분 보완 설명**


**이 단계의 핵심**:
1. 알고리즘 선택 이유:
   "[알고리즘]을 쓴 이유는 [시간복잡도] vs [메모리] 트레이드오프"
   
2. 성능 병목 예측:
   "이 부분이 병목 가능: [위치], 해결: [방법]"
   
3. Spring Boot 전환:
   "이 패턴은 Spring에서 [@어노테이션]으로 변환"
   
4. 실무 고려사항:
   "운영 시 [상황] 발생하면 [대응 방식]"

**간단 검증**:
"이 단계 단독 실행 시 예상 결과: [출력 예시]"

**"단계 [N] 완료! 이해하셨나요? 다음 단계로 갈까요?"**

### ABSOLUTE RULES (절대 규칙)


❌ Phase 1-2 승인 없이 Phase 3 진입 금지
❌ 한 단계 확인 없이 다음 단계 진행 금지

✅ 단계 수는 유연하게 (3-6단계, 이해하기 좋은 단위)
✅ 모든 Phase 끝에 확인 대기
