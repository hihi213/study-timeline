## **2025.10.27, 1교시 — 개선본**

프로시저(Procedure)와 함수(Function)는 시험 범위였습니다. 이전에 프로시저 암호화 실습을 하지 않아서 이 부분을 추가했습니다.

오늘은 `userTBL` 테이블을 하나 만들어서 프로시저로 간단하게 암호화하는 실습을 진행합니다. 교안에 추가된 내용이니 새 교안을 참고하세요. `userTBL` 테이블 생성 및 데이터 삽입 스크립트는 (카톡에) 올렸습니다. (실습)

프로시저에서 사용자가 소스 코드를 알아볼 수 없도록 암호화하는 방법은 보안에서 사용되는 부분입니다. 오늘부터는 배운 것들을 데이터베이스 보안에 적용하는 것을 다룰 것입니다. 이후에는 트리거(Trigger)를 사용한 로그 기록, 뷰(View)와 인덱스(Index)를 활용한 민감한 데이터 숨기기 등을 진행할 것입니다.

(SQL Developer에서) 테스트 계정으로 접속하여 올려준 스크립트를 실행합니다. `CREATE TABLE userTBL`을 실행하고, 10건의 데이터를 `INSERT` 합니다. (실습)

데이터가 10개 들어갔는지 확인해 주세요. (실습)

이 테이블을 가지고 사용자 코드를 알아볼 수 없도록 암호화하는 방법입니다. 예를 들어, 이름의 첫 글자만 남기고 나머지를 '00' 등으로 마스킹(masking) 하거나, 암호화된 코드 값으로 나오도록 할 것입니다.

워크시트에서 바로 코딩해도 됩니다. 프로시저 생성 코드를 워크시트에 모두 입력하고, 제일 끝 `END;` 다음에 슬래시(`/`)를 붙이면 워크시트에서 바로 컴파일됩니다. (실습)

컴파일이 완료되면, 해당 코드는 지우고 `SET SERVEROUTPUT ON` 설정 후 `EXEC`로 프로시저를 실행하여 결과를 테스트합니다. (실습)

JYP를 입력하면 'J00'처럼 이름의 첫 글자만 나오고 뒤에는 '00'이 붙도록 데이터를 숨겨서 처리할 수 있습니다. (실습)

프로시저 코드를 살펴보겠습니다. 프로시저명은 `encryptProc`이고, 입력 매개변수 `pi_userID`는 `userTBL.userID%TYPE`을 사용했습니다. `%TYPE`은 해당 테이블의 컬럼과 동일한 타입을 사용하겠다는 의미입니다.

내부 변수 `v_userName`과 `v_birthYear`도 마찬가지로 `%TYPE`을 사용했습니다.

`BEGIN` 블록에서는 `SUBSTR` 함수를 사용해 `userName`의 첫 글자만 가져오고, 나머지는 '00'을 붙였습니다. 이 값과 `birthYear` 값을 `SELECT … INTO` 구문을 사용해 변수에 할당합니다. 조건은 매개변수로 입력받은 `userID`와 일치하는(`WHERE userID = pi_userID`) 것입니다.

이후 `DBMS_OUTPUT.put_line`을 사용하여 'JYP --> J00(1971)'과 같은 형식으로 결과를 출력합니다. (실습)

이처럼 프로시저를 데이터베이스 보안(암호화) 관련 작업에 활용할 수 있습니다.

SQL Developer의 프로시저 목록을 새로고침하면 생성된 `encryptProc` 프로시저를 확인할 수 있습니다. (실습)

`SELECT` 구문을 활용하여 민감한 데이터를 숨길 때, 뷰(View)를 사용할 수도 있고 지금처럼 프로시저를 통해 `SELECT` 결과 자체를 프로그래밍으로 처리할 수도 있습니다.

이제 기존 프로시저를 `DROP PROCEDURE`로 삭제하고, 소스 코드를 암호화하는 두 번째 실습을 진행합니다. (실습)

`DECLARE` 섹션에 `v_source`라는 긴 문자열 변수를 선언합니다. 이 변수에 이전에 작성했던 `CREATE OR REPLACE PROCEDURE … END;`까지의 전체 코드를 문자열로 할당합니다. (실습)

문자열이 너무 길기 때문에 `||` (연결 연산자)를 사용하여 여러 줄로 나누어 할당합니다. 문자열 내부에 작은따옴표(')를 표현하려면 작은따옴표 두 개('')를 사용해야 합니다.

그다음 `EXECUTE IMMEDIATE` 명령과 `DBMS_DDL.WRAP` 함수를 사용합니다. `DBMS_DDL.WRAP`은 DDL문을 암호화(wrapping)하는 함수입니다. `DDL => v_source` 형태로 암호화할 DDL 코드(문자열)를 전달합니다. (실습)

이 명령을 실행하면 프로시저가 암호화되어 생성됩니다. 이렇게 하면 패스워드 등이 포함된 쿼리 구문을 `SELECT` 하지 못하도록 암호화하여 저장할 수 있습니다.

암호화 처리된 프로시저는 `USER_SOURCE`라는 (데이터 딕셔너리 뷰) 테이블에 저장됩니다.

`SELECT text FROM USER_SOURCE WHERE name = 'ENCRYPTPROC'`로 조회하면, 소스 내용이 암호화되어 저장된 것을 관리자도 확인할 수 있습니다. (실습)

관리자도 사용자 패스워드 같은 민감한 정보를 함부로 알면 안 되므로, 이렇게 암호화하여 저장하는 방법을 사용합니다.

암호화된 프로시저를 실행하면 이전과 동일하게 결과가 출력되지만, 그 내용은 암호화되어 카탈로그에 저장되어 있습니다. (실습)

**2025.10.27, 1교시 — 개념**

1. 한 줄 요약(≤120자)
    
    1교시는 프로시저를 활용한 데이터 마스킹(예: 'JYP'→'J00') 및 DBMS_DDL.WRAP을 이용한 DDL 소스 코드 암호화(래핑) 방법을 다룹니다.
    
2. **핵심 TL;DR**
    
    - 프로시저(Procedure)는 민감한 데이터(예: 이름)를 `SUBSTR` 등으로 마스킹(masking)하여 반환하는 보안 로직을 캡슐화하는 데 활용됩니다.
    - 데이터베이스 보안은 단순 권한 제어를 넘어, 프로시저나 뷰(View)를 통해 `SELECT` 결과 자체를 변형하여 민감 정보 노출을 제어하는 것을 포함합니다.
    - `%TYPE` 속성은 테이블의 특정 컬럼 타입을 그대로 참조하여, 테이블 구조가 변경되어도 프로시저 코드가 유연하게 대응할 수 있도록 합니다.
    - `SELECT … INTO` 구문은 쿼리 결과를 PL/SQL 변수(예: `v_userName`)에 직접 할당할 때 사용됩니다.
    - `DBMS_DDL.WRAP` 패키지는 `CREATE PROCEDURE`와 같은 DDL문의 소스 코드를 읽을 수 없는 난독화된(obfuscated) 형태로 래핑(Wrapping)합니다.
    - 암호화(래핑)된 소스 코드는 DBA(관리자)조차 원본 코드를 볼 수 없도록 하여, 내부에 포함된 중요 로직이나 패스워드 등을 보호합니다.
    - 암호화된 프로시저의 소스 코드는 데이터 딕셔너리 뷰인 `USER_SOURCE` (또는 `ALL_SOURCE`, `DBA_SOURCE`)에 저장됩니다.
    - 동적 SQL(Dynamic SQL)인 `EXECUTE IMMEDIATE`는 문자열 변수(예: `v_source`)에 저장된 DDL문이나 DML문을 실행할 때 사용됩니다.
    - PL/SQL에서 문자열 내부에 작은따옴표(')를 포함시키려면, `''` (작은따옴표 2개)를 사용해야 합니다.
    - SQL Developer 워크시트에서 `END;` 블록 끝에 슬래시(`/`)를 사용하면 해당 PL/SQL 블록을 즉시 컴파일하고 실행할 수 있습니다.
    - `SET SERVEROUTPUT ON`은 `DBMS_OUTPUT.PUT_LINE`의 결과를 화면에 출력하기 위해 필요한 SQL*Plus (또는 SQL Developer) 환경 설정입니다.
        
3. **표현 = 표준 용어**
    
    - `Procedure` (프로시저): 명명된 PL/SQL 블록. 보안 로직(데이터 변형, 접근 제어)을 캡슐화하는 데 사용.
    - `Data Masking` (데이터 마스킹): 민감한 데이터를 식별 불가능한 형태(예: 'J00', '***')로 변형하여 노출하는 기법.
    - `DBMS_DDL.WRAP`: 오라클에서 DDL 소스 코드를 암호화(래핑)하는 데 사용하는 내장 패키지.
    - `Wrapping` (래핑): 소스 코드를 실행 가능하지만 읽을 수 없는 난독화된(obfuscated) 형태로 변환하는 과정.
    - `USER_SOURCE`: 현재 사용자가 소유한 저장 객체(프로시저, 함수, 패키지 등)의 소스 코드가 저장된 데이터 딕셔너리 뷰.
    - `%TYPE`: 변수 선언 시, 특정 테이블 컬럼이나 다른 변수의 데이터 타입을 동적으로 참조하는 속성.
    - `EXECUTE IMMEDIATE`: 문자열에 담긴 SQL문(DDL, DML)을 동적으로 실행하는 명령어.
    - `SELECT … INTO`: 쿼리 결과를 PL/SQL 변수로 가져오는 구문 (결과는 반드시 1개 행이어야 함).
        
4. 정석 보강(canon-std)
    
    프로시저는 민감 데이터 접근 로직을 캡슐화하여 보안 계층을 제공합니다.
    
    사용자에게 테이블 직접 접근 권한 대신 프로시저 EXECUTE 권한만 부여하면, 프로시저 내부 로직(마스킹, 로깅)을 강제할 수 있습니다.
    
    DBMS_DDL.WRAP은 DDL 소스 코드를 난독화(obfuscation)하여 USER_SOURCE 등에서 원본을 숨깁니다.
    
    이는 코드 내 비즈니스 로직(IP)을 보호하기 위한 목적이 강하며, TDE(저장 데이터 암호화)나 TLS(전송 암호화)와는 목적이 다릅니다.
    
5. **실수·함정**
    
    - `SELECT … INTO` 사용 시, 결과가 2건 이상(`TOO_MANY_ROWS`)이거나 0건(`NO_DATA_FOUND`)이면 예외가 발생합니다.
    - `DBMS_DDL.WRAP`은 강력한 암호화(Encryption)가 아닌 난독화(Obfuscation)입니다.
    - `DBMS_DDL.WRAP`으로 래핑된 코드는 되돌릴 수(un-wrap) 있는 비공식 유틸리티가 존재할 수 있으므로, 소스 코드 보호에 절대적이지 않습니다.
    - 프로시저를 통한 마스킹은 `SELECT` 출력만 변형할 뿐, 디스크에 저장된 원본 데이터는 변경하지 않습니다. (Masking vs. Encryption 혼동)
    - 동적 SQL(`EXECUTE IMMEDIATE`) 사용 시, 사용자 입력을 검증 없이 문자열에 결합하면 SQL Injection 공격에 매우 취약합니다.
    - 문자열 연결 시 작은따옴표(') 처리를 잊거나(예: `''` 대신 `'` 사용), `||` 연산자를 누락하기 쉽습니다.
    - `%TYPE`을 사용하지 않고 `VARCHAR2(10)`처럼 타입을 하드코딩하면, 원본 테이블 컬럼 크기가 변경될 때 프로시저 오류가 발생할 수 있습니다.
    - `DBMS_OUTPUT.PUT_LINE`은 버퍼를 사용하므로, `SET SERVEROUTPUT ON` 설정 없이는 클라이언트에서 결과를 볼 수 없습니다.
    - 프로시저 권한 모델(Definer vs. Invoker)을 명시하지 않으면 기본값(Definer)으로 실행되어, 의도치 않은 권한 상승이 발생할 수 있습니다.
    - `USER_SOURCE`는 현재 스키마의 객체만 보여줍니다. 다른 스키마의 객체 소스를 보려면 `ALL_SOURCE`나 `DBA_SOURCE` (권한 필요)를 조회해야 합니다.

**[Q1] 프로시저를 사용하여 민감한 데이터(이름 등)를 마스킹(Masking)하는 방법은? | 태그: 마스킹, 프로시저**

- **모범답(강의 기준):** `SELECT` 문에서 `SUBSTR` 함수로 첫 글자만 취하고, '00' 같은 고정 문자열을 `||` (연결 연산자)로 붙여서 변수에 `INTO` 한 뒤, 이 변수를 출력합니다.
- **정석체크(면접 30초):** 데이터 마스킹(Masking)은 원본 데이터를 변경하지 않고 출력(presentation) 단계에서 민감 정보를 가리는 기법입니다. 프로시저는 `SUBSTR(col, 1, 1) || '***'`처럼 복잡한 마스킹 로직을 캡슐화합니다. 사용자에게 테이블 직접 조회를 `REVOKE`하고 프로시저 `EXECUTE` 권한만 `GRANT`하여, 마스킹 로직 실행을 강제할 수 있습니다.
    

**[Q2] PL/SQL에서 `%TYPE` 속성을 사용하는 이유는? | 태그: PL/SQL, %TYPE**

- **모범답(강의 기준):** 변수를 선언할 때, 참조할 테이블의 특정 컬럼과 동일한 데이터 타입을 사용하도록 지정하여 코드 유연성을 높이고 유지보수를 용이하게 하기 위해 사용합니다.
- **정석체크(면접 30초):** `%TYPE`은 '앵커드(anchored) 타입' 선언입니다. `v_name userTBL.userName%TYPE;`처럼 선언하면, `userTBL.userName` 컬럼의 타입(예: `NVARCHAR2(10)`)을 그대로 가져옵니다. 향후 원본 컬럼의 타입이나 길이가 변경되어도, 프로시저 코드를 수정 없이 재컴파일만 하면 되므로 유지보수성이 크게 향상됩니다.
    

**[Q3] 민감 데이터 은닉 시, 뷰(View)와 프로시저(Procedure) 방식의 차이는? | 태그: 뷰, 마스킹, 접근제어**

- **모범답(강의 기준):** 뷰(View)를 사용해서 민감 데이터를 숨길 수도 있고, (1교시 실습처럼) 프로시저를 통해 `SELECT` 결과 자체를 프로그래밍으로 변형(마스킹)하여 처리할 수도 있습니다.
- **정석체크(면접 30초):** 뷰(View)는 `CREATE VIEW v_user AS SELECT SUBSTR(name,1) …`처럼 마스킹 로직을 뷰 정의에 포함시켜 사용자에게 뷰 접근 권한만 줍니다. 프로시저는 `EXECUTE` 권한으로만 접근하며, 파라미터(예: ID)를 받아 특정 행만 마스킹하는 등 더 복잡한 로직 구현이 가능합니다. 뷰는 SQL 접근에 유용하고, 프로시저는 캡슐화된 로직 실행에 유리합니다.
    

**[Q4] PL/SQL 문자열 리터럴(literal) 내부에 작은따옴표(')를 포함시키는 방법은? | 태그: PL/SQL, 구문(Syntax)**

- **모범답(강의 기준):** 문자열 안에서 작은따옴표(')를 표현하려면, 작은따옴표를 두 번 연속(`''`)으로 씁니다. (예: `v_text := 'JYP''s data';`)
- **정석체크(면접 30초):** SQL과 PL/SQL에서 문자열 리터럴은 작은따옴표(`'`)로 감쌉니다. 리터럴 내부에 `'` 기호 자체를 포함하려면, 이스케이프(escape) 문자로 `''` (두 개)를 사용합니다. 대안으로 `q` (quote) 연산자(예: `q'[JYP's data]'`)를 사용하면 `''` 처리 없이 내부 문자열을 그대로 인식시킬 수 있습니다.

- **모범답(강의 기준):** DDL문(프로시저 생성 코드 등)을 암호화(래핑)하는 함수입니다. 암호화된 코드는 `USER_SOURCE` 딕셔너리 뷰에 저장되며, 관리자도 암호화된 내용으로만 조회가 가능합니다.
- **정석체크(면접 30초):** `DBMS_DDL.WRAP`은 PL/SQL 소스 코드를 난독화(obfuscation)하여 `USER_SOURCE` 등에 저장합니다. 이는 디스크 데이터 암호화(TDE)와 달리, 코드 내의 비즈니스 로직(IP)이나 하드코딩된 패스워드를 숨기기 위한 목적입니다. 강력한 암호화는 아니며, 비공식적인 un-wrapper로 복호화될 가능성에 유의해야 합니다.
    

**[Q6] PL/SQL 블록 실행 시 `END;` 뒤에 `/` (슬래시)를 사용하는 이유는? (보완됨) | 태그: PL/SQL, SQL*Plus**

- **정석체크(면접 30초):** `/` (슬래시)는 SQL_Plus 및 SQL Developer의 버퍼 실행 명령어입니다. PL/SQL 블록은 내부에 여러 개의 세미콜론(`;`)을 포함하므로, 블록의 끝을 명확히 구분하기 위해 `END;` 다음 줄에 `/`를 사용합니다. 이는 PL/SQL 엔진의 문법이 아니라, 클라이언트 도구(SQL_Plus)의 명령어입니다.

2. **핵심 TL;DR**
    
    - 스토어드 프로그램(Stored Program)은 프로시저, 함수, 트리거 3가지가 있으며, 보안 처리에는 트리거가 많이 활용됩니다.
    - 트리거(Trigger)는 `INSERT`, `UPDATE`, `DELETE` 등 DML 이벤트 발생 시 DBMS에 의해 자동으로 실행되는 캡슐화된 로직입니다. (`SELECT`는 제외)
    - 트리거의 주요 용도는 감사 로그(Audit Log) 기록, 데이터 변경 로직 강제, 또는 특정 DML(예: `INSERT`) 작업 방지입니다.
    - 트리거 동작 시점은 `BEFORE` (이벤트 전) 또는 `AFTER` (이벤트 후)로 지정하며, 보통 `AFTER`를 많이 사용합니다.
    - `FOR EACH ROW` 옵션은 DML에 의해 영향받는 _모든 행_에 대해 개별적으로 트리거 로직을 적용하도록 지정합니다.
    - `INSTEAD OF` 트리거는 테이블이 아닌 뷰(View)에 대해 DML(주로 복합 뷰의 `INSERT`)이 시도될 때, 지정된 로직으로 '대신' 실행됩니다.
    - 트리거 로직 내에서 `:OLD`와 `:NEW`라는 특수 레코드(pseudo-record)를 사용하여 데이터 변경 전/후 값에 접근할 수 있습니다.
    - `:OLD`는 `UPDATE`나 `DELETE` 시 _이전 값_을 참조하며, `:NEW`는 `INSERT`나 `UPDATE` 시 _새 값_을 참조합니다.
    - 로그 기록 시, `:OLD` 레코드의 값, `SYSDATE` (현재 시각), `USER` (현재 계정)를 별도 백업 테이블에 `INSERT` 합니다.
    - `RAISE_APPLICATION_ERROR([에러 번호], '[메시지]')` 함수는 사용자 정의 예외를 강제로 발생시켜, 트랜잭션을 롤백(Rollback)시킵니다.
    - 트리거는 DML 이벤트마다 실행되므로, 불필요한 트리거는 시스템 성능에 오버헤드(Overhead)를 유발하므로 테스트 후 삭제하는 것이 좋습니다.
    - (참고) 커서(Cursor)는 응용 프로그램에서 `SELECT` 결과를 행 단위로 처리(OPEN, FETCH, CLOSE)하기 위한 객체입니다.
        
3. **표현 = 표준 용어**
    
    - `Trigger` (트리거): DML/DDL 이벤트 발생 시 자동 실행되는 스토어드 프로그램.
    - `DML (Data Manipulation Language)`: `INSERT`, `UPDATE`, `DELETE` 등 데이터 조작어.
    - `Audit Log` (감사 로그): 데이터 변경 이력(누가, 언제, 무엇을)을 기록하는 로그.
    - `BEFORE` / `AFTER`: 트리거 실행 시점 (DML 실행 전/후).
    - `INSTEAD OF`: 트리거 실행 시점 (주로 View에 대한 DML을 대체).
    - `FOR EACH ROW`: 행(Row) 레벨 트리거. DML이 영향을 미치는 모든 행에 대해 각각 실행.
    - `:OLD` / `:NEW`: 행 레벨 트리거에서 사용하는 의사 레코드(pseudo-record) (변경 전/후 값 참조).
    - `RAISE_APPLICATION_ERROR`: 사용자 정의 예외(오류)를 강제로 발생시키는 PL/SQL 함수.
    - `Overhead` (오버헤드): DML 실행 시 트리거 호출로 인해 추가로 발생하는 시스템 부하.
    - `Cursor` (커서): `SELECT` 결과 집합을 행 단위로 탐색(fetch)하기 위한 포인터.
        
4. 정석 보강(canon-std)
    
    트리거는 INSERT, UPDATE, DELETE 같은 DML 이벤트와 테이블을 연결하여 자동 실행되는 객체입니다.
    
    보안(Security) 관점에서 트리거는 (1) 감사 로그(Audit Log)를 백업 테이블에 기록하거나 (2) RAISE_APPLICATION_ERROR를 호출하여 특정 DML을 금지하는 데 사용됩니다.
    
    FOR EACH ROW로 지정된 행 레벨 트리거는 :OLD (변경 전 값)와 :NEW (변경 후 값) 의사 레코드(pseudo-record)에 접근할 수 있습니다.
    
    트리거는 트랜잭션의 일부로 실행되므로, 트리거 로직이 실패(예: RAISE_APPLICATION_ERROR)하면 원본 DML 문(예: INSERT)도 롤백(Rollback)됩니다.
    
5. **실수·함정**
    
    - 트리거에서 `SELECT` 이벤트를 사용하려 시도. (트리거는 DML/DDL 이벤트에만 반응함, `SELECT` 제외)
    - `FOR EACH ROW`를 지정하지 않아, DML이 100행을 수정해도 트리거가 1번만 실행(문장 레벨)되게 만듦.
    - `DELETE` 트리거에서 `:NEW` 값을 참조하거나, `INSERT` 트리거에서 `:OLD` 값을 참조하려 시도. (존재하지 않음)
    - `INSTEAD OF` 트리거를 일반 테이블(Table)에 적용하려 시도. (`INSTEAD OF`는 뷰(View) 전용)
    - 트리거가 너무 많거나 로직이 복잡하면 DML 성능에 심각한 오버헤드(Overhead)를 유발할 수 있습니다.
    - 트리거 A가 테이블 B를 수정하고, 테이블 B의 트리거 B가 테이블 A를 수정하는 '순환 트리거'(Mutating Trigger) 오류 발생.
    - `RAISE_APPLICATION_ERROR` 사용 시, 에러 번호는 반드시 -20000 ~ -20999 사이의 사용자 정의 범위를 사용해야 합니다.
    - 트리거 로직에서 `COMMIT`이나 `ROLLBACK` (TCL)을 사용하려 시도. (트리거는 DML 트랜잭션의 일부이므로 단독 트랜잭션 제어 불가)
    - 트리거를 테스트 용도로만 생성하고 `DROP`하지 않아, 운영 환경에 불필요한 부하를 누적시킴.

**2025.10.27, 3교시 — 개선본**

뷰(View)에 대해 알아보겠습니다. 이전에 배운 함수, 프로시저, 트리거를 활용하여 뷰와 인덱스에서 데이터베이스 보안을 어떻게 관리하는지 적용해 볼 것입니다.

뷰는 데이터베이스 보안, 특히 민감한 데이터를 숨기는 데이터 마스킹(Masking)에 사용됩니다. (1교시 프로시저 마스킹과 유사) 또한 접근 권한을 분리하여, 뷰 단위로 접근 권한을 관리하여 보안 설정을 할 수 있습니다.

쿼리가 매우 복잡할 때(예: 3중 조인) 뷰를 미리 만들어 두면, 쿼리문이 간단해지고 처리 속도에도 이점이 있을 수 있습니다. 감사 로깅(Audit Logging) 관련해서도 트리거와 연동하여 사용할 수 있습니다.

뷰를 `WITH CHECK OPTION` 같은 제한을 두어 읽기 전용(Read-only) 테이블처럼 활용하여 `UPDATE`를 막을 수도 있습니다.

사용자에게는 최소한의 정보만, 필요한 정보만 오픈하고 민감한 데이터는 숨기는 형태로 뷰를 활용합니다. 예를 들어, 같은 사원 테이블이라도 인사팀(급여액), 기획실(부서/직무), 사내 복지팀(생일/주소) 등 각 팀에 필요한 정보만 선별하여 뷰로 제공합니다.

뷰는 실제적인 물리적 공간을 가지고 있지 않은 가상의, 논리적인 테이블입니다. 원본 테이블(예: `employees`)은 그대로 있고, 뷰는 `SELECT` 한 결과를 가상으로 보여줍니다. 실제 물리적 데이터를 건드리지 않습니다.

뷰 생성(`CREATE VIEW`)은 시스템 권한이므로 아무나 만들 수 없습니다. `SYSTEM` 계정으로 접속하여, 뷰를 생성할 계정(예: 테스트 계정)의 편집(사용자 편집)에 들어가, [시스템 권한] 탭에서 `CREATE VIEW` 권한을 체크하고 적용해야 합니다. (실습)

권한 설정이 완료되면, 해당 계정에서 `CREATE VIEW`를 할 수 있습니다. `CREATE VIEW [뷰 이름] AS [SELECT 문]` 형식으로 생성합니다. 이는 `SELECT` 결과를 기반으로 물리적 테이블을 생성하는 `CREATE TABLE … AS SELECT …`와 다릅니다. (실습)

SQL Developer에서 GUI (뷰 목록 우클릭 > 새 뷰)로 생성할 수도 있으나, 워크시트에서 스크립트로 직접 입력하는 것이 더 빠릅니다. (실습)

GUI로 생성 시 뷰 이름(예: `EMP_HIGH_SALARY`)과 `SELECT` 문을 입력하고 테스트 후 확인하면, 뷰 목록에 선글라스 모양의 아이콘으로 생성됩니다. (실습) 이는 실제 데이터가 아닌 가상 데이터(보여지는 것)임을 의미합니다.

생성된 뷰는 마치 일반 테이블처럼 `SELECT` 문에서 사용할 수 있습니다. `SELECT * FROM EMP_HIGH_SALARY WHERE department_id = 90;` 처럼 조회하면 됩니다. (실습)

뷰를 호출하면, 실제로는 뷰에 정의된 `SELECT` 문과 사용자가 입력한 `SELECT` 문이 (인라인 함수처럼) 병합되어 실행됩니다. (예: `WHERE` 조건이 `AND`로 추가됨)

뷰는 수정(DML)도 가능하지만, 보통은 `SELECT`용(조회용)으로 많이 씁니다.

뷰와 일반 테이블 간의 조인(Join)도 가능합니다. `SELECT … FROM EMP_HIGH_SALARY v JOIN departments d ON …` 처럼 일반 테이블처럼 사용하면 됩니다. (실습)

단, 뷰 생성 시 `SELECT` 절에 포함하지 않은 컬럼(예: `job_id`, `hire_date`)은 해당 뷰를 통해서 접근하려 하면 오류가 발생합니다. 각 팀에 꼭 필요한 컬럼을 잘 맞춰 뷰를 생성해야 합니다.

복잡한 조인 쿼리를 미리 뷰로 만들어 두면(예: `v_emp_dept`), 사용자는 조인 없이 해당 뷰에서 필요한 컬럼만 간단히 `SELECT` 할 수 있습니다. 실무에서 자주 쓰는 방식입니다. (실습)

뷰에 `INSERT`, `DELETE`, `UPDATE` (DML)도 가능하지만, 항상 되는 것은 아니고 원본 데이터에 문제가 없는 경우(예: 조인 뷰가 아님)에 한해 케바케(Case-by-case)로 실행됩니다. 웬만하면 뷰는 조회용으로만 사용하는 것을 권장합니다(비추천).

이제 보안 관점에서 뷰를 활용하는 실습을 하겠습니다. `employee2`라는 새 테이블을 사용합니다. (테이블 생성 및 `INSERT` 스크립트 제공) (실습)

보안 요구 사항은 다음과 같습니다:
1.  일반 직원: 자신의 정보만 조회 가능
2.  인사팀: 주민번호(ssn)를 제외한 모든 정보 조회 가능
3.  관리자: 주민번호 포함 모든 정보 조회 가능

(로직 설명) `USER` 키워드는 현재 접속한 계정 ID를 반환하는 시스템 변수입니다. 일반 직원의 뷰는 `WHERE emp_id = SUBSTR(USER, 4, 4)` (계정 ID가 'EMP_1001'일 경우 '1001'을 추출)과 같은 조건을 사용합니다.

(실습 절차)
1.  **(SYSTEM 계정)**: 일반 직원(`EMP_1001`), 인사팀(`HR_USER`), 관리자(`ADMIN_USER`) 계정을 생성하고 `CONNECT` 권한(관리자는 `DBA` 권한 추가)을 부여합니다. (스크립트 제공) (실습)
2.  **(테스트 계정)**: `employee2` 테이블을 생성하고 데이터를 `INSERT` 합니다. (스크립트 제공) (실습)
3.  **(테스트 계정)**: 각 요구 사항에 맞는 뷰 3개(`vw_my_profile`, `vw_hr_view`, `vw_admin_view`)를 `CREATE VIEW`로 생성합니다. (코드는 비슷하므로 복사/붙여넣기 후 수정) (실습)
    * `vw_my_profile`: `WHERE emp_id = SUBSTR(USER, 4, 4)` (자기 정보만)
    * `vw_hr_view`: `SELECT emp_id, name, … salary` (ssn 컬럼 제외)
    * `vw_admin_view`: `SELECT * FROM employee2` (모든 컬럼)
4.  **(테스트 계정)**: `employee2` 테이블의 소유자인 테스트 계정에서, 생성한 뷰에 대한 `SELECT` 권한을 각 사용자 계정에 부여(`GRANT`)합니다. `GRANT` 설명은 다음 시간에 하겠지만, 일단 실행합니다. (스크립트 제공) (실습)
    * `GRANT SELECT ON vw_my_profile TO EMP_1001;`
    * `GRANT SELECT ON vw_hr_view TO HR_USER;`
    * `GRANT SELECT ON vw_admin_view TO ADMIN_USER;`

(설명) 원래는 사용자(사원)가 많으므로, 한 명 한 명 권한을 주는 대신 '롤(Role)'(그룹)을 만들어 롤에 권한을 부여하고, 사용자를 롤에 포함시킵니다.

1.  **(커맨드 라인)**: 접속 테스트를 합니다. SQL Developer에서 계정을 추가하면 불편하므로, 커맨드 라인(CMD)에서 테스트합니다. (실습)
    * `CONNECT emp_1001/1234` (아이디/비밀번호 동시 입력)
    * `SELECT * FROM [테스트계정].vw_my_profile;` (자기 정보만 나오는지 확인)
    * `CONNECT hr_user/1234`
    * `SELECT * FROM [테스트계정].vw_hr_view;` (주민번호 제외하고 나오는지 확인)
    * `CONNECT admin_user/1234`
    * `SELECT * FROM [테스트계정].vw_admin_view;` (모두 나오는지 확인)

이처럼 뷰를 보안 관점에서 활용하여, 부서나 역할에 따라 필요한 데이터만 제공하고 민감한 데이터는 숨길 수 있습니다. (커맨드 라인 결과 캡처)

**2025.10.27, 3교시 — 개념**

1. 한 줄 요약(≤120자)
    
    3교시는 뷰(View)를 활용한 데이터베이스 보안(민감 데이터 마스킹, 역할별 접근 제어)의 개념, 생성/권한 부여(CREATE VIEW, GRANT), 동작 원리(가상 테이블)를 다룹니다.
    
2. **핵심 TL;DR**
    
    - 뷰(View)는 `SELECT` 쿼리문 자체를 저장하는 가상의, 논리적인 테이블(Logical Table)이며 물리적 데이터를 저장하지 않습니다.
    - 보안 목적으로 뷰를 사용하여 민감한 정보(예: 주민번호 `ssn`)를 `SELECT` 절에서 제외하여 숨기거나(Data Masking), 특정 컬럼만 노출시킬 수 있습니다.
    - 역할(Role)에 따라 다른 뷰를 제공하여(예: 인사팀 뷰, 일반 직원 뷰), 필요한 정보만 선별적으로 접근하도록 접근 권한을 분리(Separation of Duty)합니다.
    - 복잡한 조인(Join) 쿼리를 뷰로 미리 정의하여, 사용자가 복잡한 쿼리문 대신 뷰를 단순 조회하도록 쿼리문을 단순화하는 용도로도 사용됩니다.
    - 뷰를 생성하려면 `CREATE VIEW` 시스템 권한이 필요하며, 이는 기본 권한이 아니므로 `SYSTEM` 관리자가 사용자 계정에 부여해야 합니다.
    - 뷰에 대한 접근은 테이블 소유자가 `GRANT SELECT ON [뷰 이름] TO [사용자/롤];` 명령으로 객체 권한(Object Privilege)을 부여해야 합니다.
    - `USER` 키워드는 현재 접속한 계정 ID를 반환하며, 뷰의 `WHERE` 절에서 '자신의 정보만' 보도록 제한하는 데 사용됩니다. (예: `WHERE emp_id = SUBSTR(USER, 4, 4)`)
    - 뷰에 대한 DML(`INSERT`, `UPDATE`, `DELETE`)은 단순 뷰 등 일부 경우에만 가능하지만, 원본 데이터 무결성 문제로 권장되지 않으며(비추천), 뷰는 주로 조회용(Read-only)으로 씁니다.
    - 뷰 쿼리 시, DBMS는 뷰의 `SELECT` 문과 사용자의 `SELECT` 문을 병합(Merge)하여 실행합니다. (인라인 확장)
    - 뷰는 `SELECT` 절에 정의된 컬럼만 접근할 수 있으며, 뷰에 없는 원본 테이블 컬럼을 조회하려 하면 오류가 발생합니다.
    - 권한 관리는 사용자 개개인보다 롤(Role)을 생성하여 그룹 단위로 `GRANT`하는 것이 효율적입니다.
        
3. **표현 = 표준 용어**
    
    - `View` (뷰): 하나 이상의 테이블에서 유도된 가상 테이블(Logical/Virtual Table).
    - `Data Masking` (데이터 마스킹): 뷰의 `SELECT` 절에서 민감한 컬럼을 제외하거나 `***` 등으로 변형하여 노출하는 기법.
    - `Access Control` (접근 제어): 뷰를 통해 사용자/역할별로 데이터 접근 범위(행/열)를 제한하는 것.
    - `CREATE VIEW`: 뷰를 생성하기 위한 시스템 권한(System Privilege).
    - `GRANT SELECT ON [view] TO [user]`: 특정 뷰에 대한 `SELECT` 권한(Object Privilege)을 부여하는 SQL 명령어.
    - `SYSTEM` (계정): 데이터베이스 최고 관리자 계정 (시스템 권한 부여/회수 담당).
    - `USER` (키워드): 현재 세션의 사용자 계정 이름을 반환하는 SQL 함수.
    - `Role` (롤): 권한의 집합(Group)을 의미하며, 사용자에게 롤을 부여하여 권한을 효율적으로 관리.
    - `Logical Table` (논리적 테이블): 뷰와 동의어. 물리적 저장 공간을 갖지 않음.
        
4. 정석 보강(canon-std)
    
    뷰(View)는 저장된 SELECT 쿼리로, 데이터 독립성과 보안을 제공합니다.
    
    보안 측면에서 뷰는 (1) 열(Column) 수준 보안 (민감 컬럼 제외) 및 (2) 행(Row) 수준 보안(RLS의 고전적 방식) (예: WHERE user = USER)을 구현하는 데 사용됩니다.
    
    사용자에게는 원본 테이블 접근 권한을 REVOKE하고, 뷰에 대한 GRANT SELECT 권한만 부여하여 최소 권한 원칙(Least Privilege)을 준수합니다.
    
    조인 뷰나 집계 함수를 포함한 뷰는 DML이 제한되며, 단순 뷰라도 WITH CHECK OPTION을 사용하여 뷰의 WHERE 조건을 위배하는 DML을 방지하는 것이 좋습니다.
    
5. **실수·함정**
    
    - 뷰가 실제 데이터를 복사하여 저장한다고 오해. (뷰는 쿼리 정의만 저장)
    - `CREATE VIEW` 권한이 기본적으로 사용자에게 있다고 착각. (`SYSTEM` 관리자가 부여해야 함)
    - 뷰를 생성한 후, 다른 사용자에게 `GRANT`하는 것을 잊어 접근이 안 됨.
    - 뷰를 통해 원본 테이블의 모든 컬럼에 접근할 수 있다고 오해. (뷰의 `SELECT` 절에 포함된 컬럼만 가능)
    - `USER` 키워드를 `WHERE` 절에 사용하여 행 수준 보안을 구현할 때, 사용자 계정 ID(예: `EMP_1001`)와 테이블의 ID 컬럼(예: `1001`) 간의 매핑 로직(`SUBSTR` 등)을 잘못 설계.
    - 복잡한 조인 뷰(Join View)에 `INSERT`나 `UPDATE`를 시도. (대부분 실패하거나 의도대로 동작하지 않음)
    - 뷰의 목적이 쿼리 성능 향상이라고 오해. (뷰는 쿼리 _단순화_가 목적. 성능 향상은 주로 'Materialized View'(구체화된 뷰)의 역할임)
    - 테이블 소유자가 아닌 `SYSTEM` 계정으로 뷰에 대한 `GRANT`를 시도. (객체 권한 `GRANT`는 기본적으로 객체 소유자(Owner)가 수행)
    - `GRANT` 시 `SELECT ON [TABLE]` (원본 테이블) 권한을 부여. (보안 목적상 `SELECT ON [VIEW]`를 부여해야 함)

**2025.10.27, 3교시 — 질문**

**[Q1] 뷰(View)를 보안 목적으로 사용하는 주요 용도 2가지는? | 태그: 뷰, 마스킹, 접근제어**

- **모범답(강의 기준):** 민감한 데이터(예: 주민번호 `ssn`)를 `SELECT` 절에서 제외하여 숨기는 마스킹(Masking) 용도와, 팀/역할별(인사팀, 일반직원)로 필요한 정보만 선별하여 접근 권한을 분리하는 용도로 사용합니다.
- **정석체크(면접 30초):** 뷰는 (1) 열(Column) 수준 보안(민감 컬럼 제외/마스킹)과 (2) 행(Row) 수준 보안(예: `WHERE user = USER`)을 구현하는 데 사용됩니다. 사용자에게 원본 테이블 대신 뷰 접근 권한만 `GRANT`하여, 최소 권한 원칙(Least Privilege)을 만족시킵니다.
    

**[Q2] 뷰(View)는 물리적 데이터를 저장하는가? | 태그: 뷰, 가상테이블**

- **모범답(강의 기준):** 아니요, 물리적 공간을 갖지 않는 가상의, 논리적인 테이블입니다. `SELECT` 쿼리문 자체만 저장하고, 호출 시 원본 테이블에서 데이터를 가져와 보여줍니다.
- **정석체크(면접 30초):** 뷰는 `SELECT` 쿼리 정의(Definition)만 데이터 딕셔너리에 저장하는 논리적 객체입니다. 실제 데이터는 원본 테이블에만 존재합니다. (단, 'Materialized View'(구체화된 뷰)는 예외적으로 데이터를 물리적으로 저장합니다.)
    

**[Q3] 뷰를 생성(`CREATE VIEW`)하고, 타인에게 조회 권한을 주기(`GRANT`) 위해 어떤 권한이 필요한가? | 태그: 권한(Privilege), GRANT, 시스템권한**

- **모범답(강의 기준):** 뷰를 생성하려면 `SYSTEM` 관리자로부터 `CREATE VIEW` 시스템 권한을 받아야 합니다. 뷰 생성 후(소유자가 된 후), `GRANT SELECT ON [뷰 이름] TO [사용자]` 명령으로 다른 사용자에게 조회(객체) 권한을 부여해야 합니다.
- **정석체크(면접 30초):** 뷰 생성은 `CREATE VIEW` (시스템 권한)이 필요합니다. 뷰 조회는 `SELECT ON [뷰]` (객체 권한)이 필요합니다. 객체 소유자(Owner)가 `GRANT SELECT ON [뷰] TO [사용자];`를 실행하여 권한을 위임합니다.
    

**[Q4] `USER` 키워드를 뷰의 `WHERE` 절에 사용하는 이유는? | 태그: 뷰, RLS, USER**

- **모범답(강의 기준):** '일반 직원은 자기 정보만 조회'하도록 만들기 위해 사용합니다. `USER` 키워드가 현재 접속한 계정 ID를 반환하므로, `WHERE emp_id = SUBSTR(USER, 4, 4)`처럼 사용하여 접근을 제한합니다.
- **정석체크(면접 30초):** 이는 RLS(Row-Level Security) 또는 VPD(Virtual Private Database)의 고전적인 구현 방식입니다. `USER` 함수를 `WHERE` 조건에 사용하여, 동일한 뷰(`SELECT * FROM v_my_info`)를 조회하더라도 접속한 사용자에 따라 다른 행(Row)만 볼 수 있도록 동적(Dynamic)으로 데이터를 필터링합니다.
    

**[Q5] 보안 권한을 개별 사용자(User)가 아닌 롤(Role)로 관리하는 이유는? | 태그: RBAC, Role(역할)**

- **모범답(강의 기준):** 사원이 많을 때 한 명 한 명에게 권한을 주면(예: `GRANT … TO EMP_1001;`, `GRANT … TO EMP_1002;`) 관리가 복잡합니다. '인사팀' 같은 롤(그룹)을 만들고 롤에 권한을 부여하면 효율적으로 관리할 수 있습니다.
- **정석체크(면접 30초):** 이는 RBAC(역할 기반 접근 제어)의 핵심입니다. 권한(Privilege)은 롤(Role)에 부여하고, 사용자(User)는 롤을 상속받습니다 (`GRANT [priv] TO [role];`, `GRANT [role] TO [user];`). 사용자의 직무(Role) 변경 시 롤만 바꾸면 되므로, 권한 관리가 단순해지고 최소 권한 원칙 준수가 용이해집니다.
    

**[Q6] 뷰를 사용하는 보안 외적인 장점은 무엇인가요? | 태그: 뷰, 쿼리단순화**

- **모범답(강의 기준):** 복잡한 쿼리(예: 3중 조인)를 미리 뷰로 만들어 두면, 사용자는 복잡한 조인 없이 뷰를 단순 조회하여 쿼리문을 간단하게 만들 수 있습니다.
- **정석체크(면접 30초):** 뷰는 복잡성(Complexity)을 숨겨 쿼리 단순화(Query Simplification)를 제공합니다. 자주 사용되는 조인이나 계산식을 뷰로 추상화하면, 사용자는 원본 테이블 구조를 몰라도 쉽게 데이터를 활용할 수 있어 개발 생산성이 향상됩니다.
    

**[Q7] 뷰에 DML(INSERT, UPDATE) 사용을 권장하지 않는(비추천) 이유는? | 태그: 뷰, DML, 무결성**

- **모범답(강의 기준):** 항상 가능한 것은 아니며(케바케), 원본 데이터에 문제가 생길 수 있으므로 웬만하면 조회용(SELECT)으로만 사용하는 것을 권장합니다.
- **정석체크(면접 30초):** 복잡한 뷰(조인 뷰, 집계 뷰 등)는 DML이 불가능합니다. 단순 뷰(Single-Table View)는 DML이 가능하지만, 뷰의 `WHERE` 조건(예: `salary > 5000`)을 위배하는 데이터가 `INSERT`되는 등 데이터 무결성이 깨질 수 있습니다. 이를 방지하려면 `WITH CHECK OPTION`을 명시해야 합니다.
