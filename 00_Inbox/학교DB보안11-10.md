### 🛡️ 보안 맥락 및 이론 (Context & Theory)

#### 1. 권한 관리의 효율화 (Role-Based Access Control)

- **배경:** 사용자별로 `CREATE TABLE`, `CREATE SESSION` 등 개별 권한을 반복적으로 `GRANT` 하는 것은 관리 비용이 높고 보안 실수를 유발합니다.
- **정책:** 권한을 직무나 기능 단위의 **Role(롤)**로 그룹핑하여 관리합니다.
    - _(예: 신규 입사자에게 개별 권한 10개를 주는 대신 `T1_TEAM_ROLE` 하나만 부여)_
- **검증:** `DBA_ROLE_PRIVS` 등의 메타데이터를 통해 부여된 롤을 확인합니다.
    

#### 2. 보안 감사 (Database Auditing)

- **배경:** 권한이 부여된 사용자라 하더라도, "누가, 언제, 어떤 데이터"를 조회하거나 변경했는지 추적(Trace)할 필요가 있습니다.
- **구현:** `AUDIT` 명령어를 사용합니다.
    - **활성화:** `ALTER SYSTEM SET AUDIT_TRAIL = DB` 설정 후 DB 재시작(`SHUTDOWN` -> `STARTUP`)이 필수입니다.
    - **범위 설정:**
        - **Statement Audit:** 특정 명령어(`CREATE TABLE` 등) 사용 감시.
        - **Object Audit:** 특정 객체(`SELECT ON HR.EMPLOYEES`) 접근 감시.
        - **조건부 감사:** `WHENEVER SUCCESSFUL` (성공 시 기록) vs `WHENEVER NOT SUCCESSFUL` (실패 시 기록 - 침입 시도 탐지).
    - **사후 관리:** `NOAUDIT`으로 감사를 해제하고, 주기적으로 로그(`DBA_AUDIT_TRAIL`)를 백업/삭제하여 성능 저하를 방지해야 합니다.
        

#### 3. 데이터 암호화 (Column Encryption via DBMS_CRYPTO)

- **배경:** 주민등록번호 등 민감 정보는 평문(Plain Text)으로 저장되면 안 됩니다.
- **구현:** 오라클 내장 패키지인 `DBMS_CRYPTO`를 활용한 **AES-256** 대칭키 암호화를 적용합니다.
    - **Data Type:** 암호화된 데이터는 바이너리 형태이므로 `RAW` 타입(최대 2000 byte)으로 저장해야 합니다.
    - **알고리즘:** `AES256` + `CBC`(Block Chaining) + `PKCS5`(Padding) 조합을 사용하여 보안 강도를 높입니다.
    - **자동화 전략 (Trigger & View):**
        - **입력(INSERT):** **Trigger**가 동작하여 평문을 암호문으로 자동 변환 후 저장.
        - **조회(SELECT):** **View**를 생성하여 암호문을 복호화 함수(`DECRYPT`)를 거쳐 평문으로 보여줌.
        - _참고: 트리거 내부에서는 `SELECT` 처리가 불가능하므로 조회는 뷰를 활용함._
            
## 개념 - DB보안 1교시_2025.11.10

### 1. **핵심 용어 (Terminology)**

- **RBAC (Role-Based Access Control):**
    - 개별 사용자에게 권한을 일일이 부여하는 **DAC(Discretionary Access Control)** 방식의 비효율성을 개선하기 위해, **'역할(Role)'** 단위로 권한을 그룹핑하여 부여하는 정책입니다.
    - _(예: `CONNECT`, `RESOURCE` 롤은 오라클 설치 시 기본 제공되는 대표적인 롤)_
- **Database Auditing (보안 감사):**
    - 데이터베이스 사용자의 행동(로그인, DDL, DML 등)을 감시하고 기록하는 메커니즘입니다.
    - **System Audit:** 데이터베이스 수준의 시스템 명령어(예: `CREATE TABLE`) 감시.
    - **Object Audit:** 특정 객체에 대한 작업(예: `SELECT ON HR.EMPLOYEES`) 감시.
    - **Fine-Grained Auditing (FGA):** (이번 실습에선 제외되었으나) 조건 기반의 정밀 감사.
- **Symmetric Key Encryption (대칭키 암호화):**
    - 암호화와 복호화에 **동일한 키(Key)**를 사용하는 방식입니다.
    - **AES-256:** 이번 수업에서 사용한 알고리즘으로, 256비트 길이의 키를 사용하는 고급 암호화 표준입니다.
    - **Padding (PKCS5):** 암호화 블록 크기(예: 16byte)를 맞추기 위해 빈 공간을 특정 값으로 채우는 작업.

### 2. **SQL 패턴 (Syntax Pattern)**

#### **A. 감사(Audit) 설정**



```SQL
-- 1. 감사 활성화 (시스템 파라미터 변경 후 DB 재시작 필요)
ALTER SYSTEM SET AUDIT_TRAIL = DB SCOPE=SPFILE;

-- 2. 감사 정책 수립 (누가, 무엇을, 언제)
-- 문법: AUDIT [명령어|객체] [ON 객체명] BY [사용자] WHENEVER [SUCCESSFUL|NOT SUCCESSFUL];
AUDIT SELECT ON hr.employees BY hr WHENEVER SUCCESSFUL; -- 성공한 조회만 기록
AUDIT SESSION WHENEVER NOT SUCCESSFUL; -- 로그인 실패 기록 (Brute Force 탐지)

-- 3. 감사 해제
NOAUDIT [명령어];
```

#### **B. 암호화 함수 (DBMS_CRYPTO)**



```SQL
-- 기본 뼈대
DBMS_CRYPTO.ENCRYPT(
    src => UTL_RAW.CAST_TO_RAW([평문]), -- 입력값은 반드시 RAW 타입이어야 함
    typ => [알고리즘_상수],             -- 예: AES256 + CBC + PKCS5
    key => [암호화_키_RAW]              -- 32Byte(256bit) 키
)
```

#### **C. 자동화 로직 (Trigger & View)**

- **Insert 시:** `Trigger`가 `:NEW.컬럼` 값을 가로채 암호화 함수 적용.
- **Select 시:** `View`가 암호화된 컬럼을 복호화 함수로 감싸서 출력.

### 3. **Standard Check 보안성 검증**

|**항목**|**강의/실습 방식**|**실무 권장 (Best Practice)**|
|---|---|---|
|**키 관리**|소스 코드(`Function`) 내부에 키 값 하드코딩 (String Literal)|**KMS(Key Management System)** 또는 **Oracle Wallet**에 키를 분리 저장하여 소스 유출 시에도 키를 보호해야 함.|
|**알고리즘**|`DBMS_CRYPTO` 패키지 직접 호출|오라클 엔터프라이즈의 **TDE (Transparent Data Encryption)** 기능을 사용하여 엔진 레벨에서 투명하게 암호화(애플리케이션 수정 불필요).|
|**감사 범위**|`AUDIT SELECT ON …` (전수 조사 가능성)|모든 `SELECT` 감사 시 **성능 저하(Performance Degradation)** 및 디스크 고갈 위험. 개인정보 등 **Compliance(규제)** 대상 데이터에 한해 최소한으로 설정.|
|**권한 분리**|`SYSTEM` 계정으로 암호화/감사 모두 수행|**SoD(Segregation of Duties)** 원칙에 따라, 보안 관리자(Auditor)와 DB 관리자(DBA)의 계정 및 권한을 분리해야 함.|

### 4. Oracle XE 환경의 감사 제한 및 대안 (FGA Limitation)
- **제약 사항:** Oracle XE(Express Edition) 버전에서는 `DBMS_FGA`(Fine-Grained Auditing) 패키지를 사용할 수 없습니다.
- **대안 (Trigger-based Audit):**
    - 특정 컬럼(예: 급여, 주민번호)의 변경(`UPDATE`, `DELETE`)을 감시하기 위해 **별도의 감사 로그 테이블**(`audit_log`)을 만들고, **트리거**를 통해 변경 전/후 데이터를 직접 `INSERT` 하는 방식을 사용해야 합니다.
    - _참고: `SELECT` 트리거는 공식 지원되지 않아 조회를 완벽히 감시하기는 어렵습니다._

### S#0. 계정 프로파일(Profile) 보안 설정

#### **1. Scenario & Goal**
- **목표:** 무차별 대입 공격(Brute Force) 방지를 위해 로그인 실패 횟수를 제한하고, 유휴 세션(Idle Time)을 자동 종료시키는 보안 정책을 수립합니다.
- **대상:** `prof_security` 프로파일을 생성하여 `HR` 계정에 적용합니다.

#### **2. SQL Implementation**
```sql
-- 1. [SYSDBA] 리소스 제한 기능 활성화 (기본값 FALSE일 경우)
ALTER SYSTEM SET RESOURCE_LIMIT = TRUE;

-- 2. 보안 프로파일 생성 (PDF Source 88, 113)
-- FAILED_LOGIN_ATTEMPTS: 5회 실패 시 계정 잠금
-- PASSWORD_LOCK_TIME: 30일간 잠금
-- IDLE_TIME: 15분 동안 활동 없으면 접속 해제
CREATE PROFILE prof_security LIMIT
    FAILED_LOGIN_ATTEMPTS 5
    PASSWORD_LOCK_TIME 30
    PASSWORD_LIFE_TIME 90
    IDLE_TIME 15;

-- 3. 사용자에게 프로파일 적용
ALTER USER hr PROFILE prof_security;

-- 4. 적용 확인 (PDF Source 121)
SELECT username, profile 
FROM dba_users 
WHERE username = 'HR';
```

- **목표:** 데이터베이스 감사를 활성화하고, `HR` 계정이 `EMPLOYEES` 테이블을 조회(`SELECT`)할 때 기록을 남깁니다.
- **대상:** 성공한 접근(`WHENEVER SUCCESSFUL`)만 기록하여 정상적인 업무 수행 내역을 모니터링합니다.

```SQL

-- 현재 상태 확인 (VALUE가 'DB'여야 함)

-- SHUTDOWN IMMEDIATE;
-- STARTUP;

-- 2. [SYSTEM] 감사 정책 수립
-- HR 사용자가 EMPLOYEES 테이블을 조회할 때, 성공한 경우만 감사

-- 로그인 실패 시 감사 (Brute Force 공격 탐지용)

-- 3. [HR] 동작 수행 (로그 남기기)
CONN hr/hr;
SELECT * FROM employees WHERE ROWNUM <= 5;

-- 4. [SYSTEM] 감사 로그 확인
CONN system/oracle;

-- 표준 감사 로그 조회 (누가, 언제, 무엇을)
SELECT username, 
       timestamp, 
       obj_name, 
       action_name, 
       sql_text, -- [Fix] EXTENDED 옵션으로 저장된 실제 SQL 문장 확인
       returncode  -- 0이면 성공, 그 외는 실패 에러코드
FROM dba_audit_trail
WHERE username = 'HR'

NOAUDIT SELECT ON hr.employees;
NOAUDIT SESSION;
``` 

### S#2. 암호화 시스템 (AES-256) 자동화

#### **1. Scenario & Goal**

- **목표:** 민감 정보(예: 이름, 주민번호)를 테이블에 저장할 때 **평문이 아닌 암호문**으로 저장합니다.
- **전략:**
    - **저장(INSERT):** **Trigger**가 자동으로 암호화 함수를 호출하여 평문을 암호문(Hex String)으로 변환 후 저장.
    - **조회(SELECT):** **View**를 통해 암호문을 복호화하여 사용자에게 평문으로 표시.
- **알고리즘:** AES-256 + CBC Mode + PKCS5 Padding.
    

#### **2. SQL Implementation**

STEP A: 암호화/복호화 함수 생성 (Provided by Professor)

(※ SYS 계정에서 GRANT EXECUTE ON DBMS_CRYPTO TO system; 선행 필요)


```SQL
-- [SYSTEM 계정]

-- 1. 암호화 함수 (Plain Text -> Encrypted RAW)
CREATE OR REPLACE FUNCTION encrypt_aes(p_plain IN VARCHAR2) RETURN RAW IS
    -- 32Byte(256bit) 키 설정 (실무에선 별도 관리 필수)
    l_key RAW(32) := UTL_RAW.cast_to_raw('01234567890123456789012345678901'); 
BEGIN
    IF p_plain IS NULL THEN RETURN NULL; END IF;
    
    RETURN DBMS_CRYPTO.encrypt(
        src => UTL_RAW.cast_to_raw(p_plain),
        typ => DBMS_CRYPTO.encrypt_aes256 
             + DBMS_CRYPTO.chain_cbc 
             + DBMS_CRYPTO.pad_pkcs5,
        key => l_key
    );
END;
/

-- 2. 복호화 함수 (Encrypted RAW -> Plain Text)
CREATE OR REPLACE FUNCTION decrypt_aes(p_raw IN RAW) RETURN VARCHAR2 IS
    l_key RAW(32) := UTL_RAW.cast_to_raw('01234567890123456789012345678901');
BEGIN
    IF p_raw IS NULL THEN RETURN NULL; END IF;
    
    RETURN UTL_RAW.cast_to_varchar2(
        DBMS_CRYPTO.decrypt(
            src => p_raw,
            typ => DBMS_CRYPTO.encrypt_aes256 
                 + DBMS_CRYPTO.chain_cbc 
                 + DBMS_CRYPTO.pad_pkcs5,
            key => l_key
        )
    );
END;
/
```

**STEP B: 테이블 및 자동화 객체(Trigger/View) 생성**

```SQL
-- 1. 테이블 생성 (암호문 저장을 위해 넉넉한 크기 할당 - PDF Source 846 참조)
CREATE TABLE t_user_secure (
    user_id NUMBER PRIMARY KEY,
    user_name VARCHAR2(2000) -- [Fix] 200 -> 2000 (암호화 시 길이 증가 및 16진수 변환 대비)
);

-- 2. 입력/수정 자동화 트리거 (BEFORE INSERT OR UPDATE)
CREATE OR REPLACE TRIGGER trg_encrypt_user
BEFORE INSERT OR UPDATE ON t_user_secure -- [Fix] UPDATE 이벤트 추가 (PDF Source 849)
FOR EACH ROW
BEGIN
    -- 입력된 평문(:NEW.user_name)이 있을 때만 암호화 수행
    IF :NEW.user_name IS NOT NULL THEN
        :NEW.user_name := RAWTOHEX(encrypt_aes(:NEW.user_name));
    END IF;
END;
/

-- 3. 복호화 뷰 생성 (편의성 함수 활용 권장 - PDF Source 859, 868)
-- (선행) 16진수 문자열 처리를 위한 래퍼 함수 생성 필요
CREATE OR REPLACE FUNCTION decrypt_aes_hex(p_hex IN VARCHAR2) RETURN VARCHAR2 IS
BEGIN
    IF p_hex IS NULL THEN RETURN NULL; END IF;
    RETURN decrypt_aes(HEXTORAW(p_hex));
END;
/

CREATE OR REPLACE VIEW v_user_plain AS
SELECT user_id,
       decrypt_aes_hex(user_name) AS user_name_plain -- 래퍼 함수 사용
FROM t_user_secure;
WITH CHECK OPTION; -- 뷰의 조건(WHERE절 등)을 위반하는 INSERT/UPDATE 차단
```

#### **3. Verification (Test)**



```SQL
-- 1. 평문 입력 (트리거 동작 확인)
INSERT INTO t_user_secure VALUES (101, 'HongGilDong');
COMMIT;

-- 2. 물리적 저장 상태 확인 (암호화 여부)
-- 결과가 읽을 수 없는 16진수 문자열(예: 3F4A…)이어야 성공
SELECT * FROM t_user_secure; 

-- 3. 복호화 뷰 조회 (정상 복원 여부)
-- 결과가 'HongGilDong'으로 보여야 성공
SELECT * FROM v_user_plain;
```

### ⚠️ Error Case & Troubleshooting

1. **`ORA-00904: "DBMS_CRYPTO": invalid identifier`**
    
    - **원인:** 현재 사용자(`SYSTEM`)에게 `DBMS_CRYPTO` 패키지 실행 권한이 없음.
    - **해결:** `SYS` 계정(SYSDBA)으로 접속하여 권한 부여.
        
        SQL
        
        ```Java
        CONN sys/oracle as sysdba;
        GRANT EXECUTE ON dbms_crypto TO system;
        ```
        
2. **트리거/함수 컴파일 오류**
    
    - **원인:** `DBMS_CRYPTO` 상수가 인식되지 않거나 `UTL_RAW` 함수 오타.
    - **해결:** 위 제공된 코드 블록을 그대로 복사하여 재컴파일(오타 수정됨).
        
3. **데이터 길이 오류 (`ORA-12899`)**
    
    - **원인:** 암호화 시 평문보다 길이가 늘어나는데, 컬럼 사이즈가 너무 작음.
    - **해결:** `VARCHAR2(20)` 대신 `VARCHAR2(200)` 등으로 넉넉하게 설정.

## 질문 - DB보안 1교시_2025.11.10

<summary>Q1. 권한 회수 시 WITH GRANT OPTION과 WITH ADMIN OPTION의 차이는 무엇인가?</summary>
<br>
[🗣️ 핵심 요약]

객체 권한의 WITH GRANT OPTION은 회수 시 **연쇄 회수(Cascade)**가 발생하지만, 시스템 권한의 WITH ADMIN OPTION은 연쇄 회수되지 않고 개별적으로 회수해야 합니다.
<br><br>
[📚 상세 설명]

- **WITH GRANT OPTION (객체 권한):** A가 B에게, B가 C에게 권한을 줬을 때 A가 B의 권한을 `REVOKE`하면, C의 권한도 함께 사라집니다. (종속성 존재) <br>
- **WITH ADMIN OPTION (시스템 권한/롤):** A가 B에게 관리자 옵션을 줬고, B가 C에게 권한을 줬더라도, A가 B를 `REVOKE` 한다고 해서 C의 권한이 사라지지 않습니다. (독립성 존재)<br>
- 시험 포인트: 시스템 권한 회수 시 찌꺼기(Orphan Privilege)가 남지 않도록 주의해야 함을 시사합니다.
    
</details>
    

<details>

<summary>Q2. DB 감사(Audit) 기능을 활성화했는데 로그가 쌓이지 않습니다. 무엇을 확인해야 하나요?</summary>
<br>
[🗣️ 핵심 요약]

AUDIT_TRAIL 파라미터가 NONE이 아닌 DB 등으로 설정되었는지 확인하고, DB 인스턴스를 재시작(Shutdown/Startup) 했는지 확인해야 합니다.
<br><br>
[📚 상세 설명]
- **필수 조치:** `AUDIT_TRAIL`은 정적 파라미터이므로 `ALTER SYSTEM` 명령 수행 후 반드시 DB를 **재시작(SHUTDOWN -> STARTUP)**해야만 로그가 쌓이기 시작합니다. 재시작하지 않으면 설정이 적용되지 않습니다.<br>
- **정적 파라미터(Static Parameter):** `AUDIT_TRAIL`은 `SCOPE=SPFILE`로 설정 후 DB를 재부팅해야만 메모리에 반영되는 파라미터입니다.<br>
- **설정 확인:** `SHOW PARAMETER AUDIT_TRAIL` 명령어로 현재 값이 `DB`(데이터베이스 테이블 저장)인지 확인합니다.<br>
- 활성화 명령: ALTER SYSTEM SET AUDIT_TRAIL = DB SCOPE=SPFILE;
    
</details>
    

<details>

<summary>Q3. 암호화된 데이터를 저장할 때 VARCHAR2 대신 RAW 타입을 권장하는 이유는?</summary>
<br>
[🗣️ 핵심 요약]

암호화 알고리즘(AES 등)의 결과물은 바이너리(Binary) 데이터이므로, 문자셋(Character Set) 변환 이슈가 없는 RAW 타입에 저장하는 것이 데이터 무결성에 안전합니다.
<br><br>
[📚 상세 설명]

- **데이터 변형 위험:** 암호화된 바이너리 값을 `VARCHAR2`에 강제로 넣으면, DB의 문자셋(예: UTF-8 -> EUC-KR) 변환 과정에서 비트 값이 깨져 복호화가 불가능해질 수 있습니다.<br>
- 실무 팁: 만약 반드시 문자열로 저장해야 한다면 RAWTOHEX 등을 사용하여 16진수 문자열로 변환하여 저장해야 합니다. (오늘 실습 코드의 방식)
    
</details>
    

<details>

<summary>Q4. 애플리케이션 수정 없이 DB 내부에서 암호화를 자동화(Transparent)하려면?</summary>
<br>
[🗣️ 핵심 요약]

**트리거(Trigger)**를 사용하여 INSERT 시 자동 암호화하고, **뷰(View)**를 사용하여 SELECT 시 자동 복호화하여 보여주는 구조를 사용합니다.
<br><br>
[📚 상세 설명]

- **Trigger 역할:** 사용자가 평문을 입력하면 `:NEW` 값을 가로채 암호화 함수를 적용한 뒤 테이블에 넣습니다. (입력 투명성)<br>
- **View 역할:** 테이블 직접 조회를 막고, 뷰를 통해서만 조회하게 하여 복호화 함수가 적용된 결과를 보여줍니다. (조회 투명성)<br>
- 한계: 트리거는 성능 부하가 크므로, 대량 데이터 처리 시에는 오라클 TDE(Transparent Data Encryption) 기능을 사용하는 것이 권장됩니다.
    
</details>
