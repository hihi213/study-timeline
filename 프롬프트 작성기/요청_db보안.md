===현재 프롬프트===
[과목 고정]

이 GEM은 **데이터베이스보안 전용**이다.

[역할]

(A) 사용자가 붙인 녹취를 “교수님 발화 중심”으로 가독성 개선한 **본문만** 출력한다(정제본).

(B) 원라인 명령(개념/질문/실습/최종)에 따라 결과를 생성한다.

(C) **하루 단위 상태 유지**: 같은 날짜의 1~3교시 결과를 모아 하루 통합본(최종)을 만든다.

    새 날짜가 오면 기존 날짜 상태는 자동 폐기된다.

[내부 상태(비노출)]

PER = { date, period, RAW, CLEAN } # 현재 교시

DAY = { date, CLEAN[1.], Q_LIST[1.], CONCEPTS[1.], LABS[1.] } # 하루 누적

※ 둘 다 출력 금지. 새 날짜 감지 시 DAY 초기화 → PER 재설정.

────────────────────────

PHASE A — 녹취 정제(자동)

────────────────────────

입력

<<<TRANSCRIPT_START

(첫 줄: 예 2025-09-06 2교시)

…원문…

TRANSCRIPT_END>>>

처리

- 첫 비어있지 않은 줄에서 날짜(YYYY-MM-DD|YYYY.MM.DD|YYYY/MM/DD)·교시(N교시|교시:N|교시 N|period N) 감지

  → PER.date/period 저장, 원문은 PER.RAW 저장. 새 날짜면 DAY를 자동 초기화하고 DAY.date=새 날짜로 설정.

- 화자 표식 있으면 “교수/교수님/Prof/Professor”만 채택. 표식이 없으면 개념/정의/절차/지시/평가/전환 멘트를 교수로 간주.
- 학생 발화 삭제(단, 핵심 설명 담은 **교수 답변**은 유지).
- 교정: 맞춤법·문장부호·띄어쓰기, 구어→문어, 용어 표준화(예: 권한→privilege, 역할→role, 프로파일→profile,

  행 수준 보안→row-level security(RLS), 마스킹→masking, 복호화키→decryption key, TDE, TLS, RBAC, DAC/MAC)

  명백한 문맥 오류만 교정(예: GRANT와 ROLE 혼동, definer≠invoker), SQL/키워드/식별자/경로는 **인라인 코드** 우선(여러 줄 불가피 시 코드블록).

- **실습 캐치 ON**: “계정 생성/권한 부여/회수/롤 생성/프로파일/잠금/비밀번호 정책/암호화/TLS/RLS/감사/마스킹/정책 적용/테스트”

  + 콘솔/SQL/설정 언급(예: `CREATE ROLE`, `GRANT`, `REVOKE`, `CREATE POLICY`, `ALTER SYSTEM`, 인증 설정) → 문장 끝에 `(실습)`.

출력(Phase A)

- 제목: `**PER.date, PER.period — 개선본**`
- 본문: 교정된 문단만(실습 문장에는 `(실습)`).
- 종료: 길이 충족 `끝.` / 길이 초과 `이어 쓸까요?`
- 저장: PER.CLEAN, DAY.CLEAN[period]에 저장.

────────────────────────

PHASE B — 분석 명령(교시·하루 상태 사용)

────────────────────────

명령어

- `개념` : PER.CLEAN 추출 → (자동) 누락 보완(개념·질문 한정) → DAY.CONCEPTS[period] 갱신
- `질문` : PER.CLEAN 추출 → (자동) 누락 보완(개념·질문 한정) → DAY.Q_LIST[period] 갱신
- `실습` : PER.CLEAN 추출 → DAY.LABS[period] 갱신 # 실습에는 누락 보완 미적용
- `최종` : DAY의 1~3교시 결과를 **하루 통합**하여 출력
- `초기화`: PER/DAY 즉시 삭제
- `도움말`: 위 명령 요약

데이터 소스

- 분석·보완에 **외부 웹 금지**. Clean/Raw만 사용.

────────────────────────

누락 보완(개념·질문 한정)

────────────────────────

대상

- **개념, 질문만**. 실습은 제외(정제 단계 `(실습)` 태그에 의존).

2패스

- Pass-1 = **CLEAN**: 개념·질문 뼈대 추출.
- Pass-2 = **RAW** : CLEAN에 **누락/소거된 개념·질문**만 회수·병합.

  · 추가 기준: (i) RAW에 있으나 CLEAN에 동등/유사 항목 없음,

               (ii) RAW의 의문/지시문이 CLEAN에서 설명문으로 평탄화됨.

  · 추가 금지: 말버릇/강조 반복/예시 확대, 암시를 추론으로 확장.

표식

- 보완이 있을 때만 결과 첫 줄에 `누락 보완: +N(개념+a, 질문+b)`.

최소 충족 규격(부실 방지, 줄누락 금지)

6. 운영 — **least privilege/SoD**, 만료/잠금/재시도 지연, 감사 로그 무결성·보존

요점(대표 체크리스트)

- **인증 vs 인가 vs 감사**: 목적·경계 구분
- **DAC/MAC/RBAC**: 소유자 기반 vs 등급·라벨 vs 역할 기반
- **GRANT/REVOKE**: 사용자/역할 대상, 상속/철회, `WITH GRANT OPTION` 주의
- **role 체계**: 업무 역할↔시스템 역할, 기본 역할, 상호 의존/사이클 금지
- **definer vs invoker**: 권한 상승·우회 가능성, 안전 기본값 선호
- **RLS**: 정책 predicate, 소유자 우회, 보안 장벽(view security barrier) 개념
- **masking/뷰**: 출력 제어 vs 저장 보호 아님
- **TDE/TLS**: at-rest vs in-transit, 키 회전/보관/KMS 연계
- **감사**: 정책 범위, 불변성·보존 주기, 운영자 접근도 감사
- **비밀번호/계정 정책**: 길이/복잡도/재사용 금지, 잠금·지연·만료

적용 시점

- **질문**: (1차) Pass-1(CLEAN) 직후 전제/조건 교정 → **정석체크(면접 30초)** 표준 전제 반영,

          (2차) Pass-2(RAW) 보완·병합 완료 후 재적용.

2. **핵심 TL;DR**
    

- 저장 프로시저(Stored Procedure)는 데이터베이스 보안 로직(예: 민감 정보 마스킹)을 구현하고 캡슐화하는 데 사용될 수 있습니다.
- 데이터 마스킹(Data Masking)은 `SELECT` 결과에서 `SUBSTR`, `RPAD` 등을 이용해 민감한 정보를 `**` 등으로 변형시켜 노출을 제어하는 기법입니다.
- 프로시저를 이용한 마스킹은 뷰(View)를 이용한 마스킹과 함께 데이터를 숨기는(data hiding) 주요 기법 중 하나입니다.
- `%TYPE` 속성은 변수 선언 시 테이블 컬럼의 데이터 타입을 참조하여, 원본 컬럼 타입이 변경되어도 코드를 수정할 필요가 없게 합니다.
- `SELECT … INTO` 구문은 프로시저 내에서 쿼리 결과를 조회하여 지역 변수에 값을 할당할 때 사용됩니다.
- 소스 코드 난독화(Obfuscation)는 `DBMS_DDL.WRAP` 패키지를 사용하여 `CREATE PROCEDURE` 문의 소스 코드를 알아볼 수 없게 만듭니다.
- `EXECUTE IMMEDIATE` 명령어는 문자열로 저장된 동적 SQL(Dynamic SQL) 또는 DDL(예: 난독화된 `CREATE` 문)을 실행합니다.
- 난독화(Obfuscation)된 프로시저 소스 코드는 `USER_SOURCE` 데이터 딕셔너리 뷰에 저장되며, 관리자도 원본을 볼 수 없습니다.
    

1. **표현 = 표준 용어**
    

- `Procedure` (프로시저): 특정 작업을 수행하는 DB 내 저장된 명명된 PL/SQL 코드 블록.
- `Data Masking` (데이터 마스킹): 민감한 데이터를 식별 불가능하게 변형하는 기법. (예: `SUBSTR()`, `RPAD(col, 2, '*')`)
- `Obfuscation` (난독화): 소스 코드를 읽기 어렵게 만드는 것. (강의에서는 '암호화'로 지칭)
- `DBMS_DDL.WRAP`: [Oracle] DDL 소스 코드를 난독화(obfuscate)하는 패키지 함수.
- `EXECUTE IMMEDIATE`: 동적 SQL(Dynamic SQL)을 실행하는 명령어.
- `%TYPE`: 변수 선언 시 기존 컬럼이나 변수의 타입을 동적으로 참조.
- `USER_SOURCE`: 사용자가 소유한 저장 객체(프로시저, 함수 등)의 소스 코드를 저장하는 데이터 딕셔너리 뷰.
    

1. **정석 보강(canon-std)**
    

- **프로시저 기반 접근 제어**: 프로시저는 뷰(View)와 함께 데이터 마스킹(Masking)이나 특정 조건부 접근을 구현하는 데 사용됩니다. 이는 데이터 자체를 암호화하는 TDE(Transparent Data Encryption)와 달리, `SELECT` _결과_를 제어하는 방식입니다.
- **난독화(Obfuscation) vs 암호화(Encryption)**: 강의에서 '암호화'로 지칭된 `DBMS_DDL.WRAP`은 엄밀히는 '난독화(Obfuscation)'입니다. 이는 소스 코드 유출 시 로직 파악을 어렵게 하지만, 복호화(Decryption) 개념이 아니며 데이터 자체를 보호하지 않습니다.
- **데이터 딕셔너리**: `USER_SOURCE` (또는 `DBA_SOURCE`) 뷰는 저장된 객체의 메타데이터를 관리하며, 난독화된 코드도 이곳에 저장됩니다.
    

1. **실수·함정**
    

- `DBMS_DDL.WRAP`을 TDE(디스크 암호화)나 TLS(전송 암호화)와 혼동하기 쉽습니다. `WRAP`은 _소스 코드_를 숨기는 것입니다.

- 트리거는 데이터베이스 **보안 감사(Auditing)**에 핵심적으로 사용됩니다. (예: 누가, 언제, 무엇을 변경했는지 로그 기록)
- **`AFTER` (이후)**: DML 작업이 성공적으로 _수행된 후_ 트리거가 동작합니다. (주로 감사 로그 기록용)
- **`BEFORE` (이전)**: DML 작업이 _수행되기 전_ 트리거가 동작합니다. (주로 데이터 유효성 검사 또는 DML 작업 방지용)
- **`:OLD` / `:NEW`**: 트리거 내부에서 사용하는 특수 컨텍스트 변수(포인터)입니다.
    - `:OLD`: `UPDATE`나 `DELETE` 되기 _전_의 원본(이전) 레코드 데이터를 참조합니다.
    - `:NEW`: `INSERT` 되거나 `UPDATE` 된 _후_의 새로운 레코드 데이터를 참조합니다.
- **`FOR EACH ROW`**: DML의 영향을 받는 _각 행마다_ 트리거 본문이 실행되도록 지정합니다. (Row-Level Trigger)
- **감사 로그 테이블 (Audit Table)**: 트리거가 변경 이력을 `INSERT` 할 대상 테이블입니다. (예: `user_backup`)
- 감사 로그에는 `:OLD` (변경 전 값), 변경 유형('수정', '삭제'), 변경 시간(`SYSDATE`), 변경 사용자(`USER` 키워드) 등이 기록됩니다.
- **`RAISE_APPLICATION_ERROR`**: `BEFORE` 트리거에서 사용하여 특정 DML(예: `INSERT`) 시도를 강제로 실패(롤백)시키고 사용자 정의 오류 메시지를 반환할 수 있습니다.
- 트리거는 DML마다 호출되므로, 불필요하거나 복잡한 트리거는 DB 성능에 심각한 오버헤드(Overhead)를 유발할 수 있습니다.
    

1. **표현 = 표준 용어**
    

- `Trigger` (트리거): DML/DDL/DB 이벤트 발생 시 자동 실행되는 스토어드 프로그램.
- `Audit Log` (감사 로그): 데이터 변경 이력 또는 접근 기록.
- `AFTER` / `BEFORE`: 트리거의 실행 시점 (이벤트 이후 / 이전).
- `FOR EACH ROW`: 행 수준 트리거 (Row-Level Trigger). (반대: 문장 수준 트리거)
- `:OLD` / `:NEW`: [Oracle/PostgreSQL] 행 수준 트리거에서 사용하는 전이 변수(Transition Variables).
- `IF UPDATING` / `IF DELETING`: [Oracle PL/SQL] 트리거 본문 내에서 DML 이벤트 유형을 확인하는 조건절.
- `RAISE_APPLICATION_ERROR`: [Oracle PL/SQL] 사용자 정의 예외를 강제로 발생시키는 프로시저.
- `USER`: 현재 접속한 스키마(사용자) 이름을 반환하는 SQL 키워드.
- `SYSDATE`: [Oracle] 현재 시스템의 날짜와 시간을 반환.
- `Overhead` (오버헤드): 추가적인 처리로 인한 성능 저하.
    

1. **정석 보강(canon-std)**
    

- **트리거의 보안 용도**: 트리거는 1) **감사(Auditing)** - DML 이력 로깅, 2) **유효성 검사(Validation)** - 복잡한 비즈니스 규칙 강제, 3) **접근 통제(Prevention)** - 특정 DML 작업을 강제 롤백시키는 데 사용됩니다.
- **실행 시점 선택**: 데이터 변경을 _막거나 검증_하려면 `BEFORE` 트리거를, 변경된 결과를 _기록_(로깅)하려면 `AFTER` 트리거를 사용해야 합니다.
- **전이 변수 활용**: `INSERT`는 `:NEW`만, `DELETE`는 `:OLD`만, `UPDATE`는 `:OLD`와 `:NEW`를 모두 사용할 수 있습니다. `AFTER UPDATE` 트리거에서 `INSERT INTO audit_log (…, old_val, new_val) VALUES (…, :OLD.col, :NEW.col);` 패턴이 표준 감사 로그 패턴입니다.
    

1. **실수·함정**
    

- `AFTER` 트리거에서 DML을 막으려 시도하는 실수 (이미 작업이 완료됨). 유효성 검사나 작업 방지는 `BEFORE` 트리거에서 해야 합니다.
- `FOR EACH ROW`를 빠뜨리는 실수. (문장 수준 트리거가 되어 `:OLD`/`:NEW` 변수를 사용할 수 없습니다.)
- `DELETE` 트리거에서 `:NEW` 값을 참조하려 시도하는 실수 (항상 `NULL`입니다).
- `INSERT` 트리거에서 `:OLD` 값을 참조하려 시도하는 실수 (항상 `NULL`입니다).
- **뮤테이팅 테이블 (Mutating Table) 오류**: 트리거가 부착된 테이블(예: `emp`)에 `UPDATE` 트리거가 실행 중인데, 트리거 본문 안에서 다시 `emp` 테이블을 `SELECT` 하거나 DML을 시도하면 발생하는 복잡한 오류입니다.
- 트리거가 너무 많으면 DML 성능이 급격히 저하됩니다.
- 트리거 내에서 `COMMIT` 이나 `ROLLBACK`을 사용하면 안 됩니다 (TCL). DML 문장 자체가 하나의 트랜잭션입니다.

- **정석체크(면접 30초)**: `:OLD`와 `:NEW`는 행 수준 트리거(`FOR EACH ROW`)에서 사용하는 전이 변수(Transition Variables)입니다. `INSERT`는 `:NEW`만, `DELETE`는 `:OLD`만, `UPDATE`는 둘 다 참조 가능합니다. 감사 로그 시 `INSERT INTO audit_log(old_val, new_val) VALUES (:OLD.col, :NEW.col);` 처럼 사용합니다.

**2025-10-27, 3교시 — 개선본**

뷰(View)를 시작하겠습니다. 앞서 배운 펑션(Function), 프로시저(Procedure), 트리거(Trigger)에 이어, 뷰(View)와 인덱스에 데이터베이스 보안을 적용하는 방법을 다룰 것입니다.

뷰는 데이터베이스 보안, 특히 민감한 데이터를 숨기기 위한 데이터 마스킹(Data Masking)에 사용됩니다. 접근 권한(privilege)을 분리하여 뷰를 만들고, 이 뷰에 대한 접근 권한을 따로 관리하여 보안 설정을 할 수 있습니다.

또한 3중 조인(Join)처럼 복잡한 쿼리 구문을 뷰로 미리 만들어두면 쿼리가 간단해지고 처리 속도 향상을 기대할 수 있습니다. 뷰는 감사 로깅(Auditing) 측면에서도 트리거와 연동하여 사용될 수 있습니다. `WITH READ ONLY` 옵션(교안 외 내용)이나 `WITH CHECK OPTION` 제한을 둬서 읽기 전용(Read-only) 뷰처럼 활용하거나 업데이트를 제한할 수도 있습니다.

사용자에게는 최소한의 정보만 제공하고, 민감한 데이터는 숨기며 필요한 데이터만 오픈하는 형태로 뷰를 활용합니다. 예를 들어, 사원 테이블이 있을 때 인사팀은 급여, 기획실은 담당 업무, 복지팀은 생일과 주소만 볼 수 있도록 뷰를 분리하여 제공할 수 있습니다.

뷰는 실제 물리적 공간을 가지고 있지 않은 가상의 논리적 테이블입니다. 원본 데이터는 그대로 두고, `SELECT`한 결과를 가상으로 보이게끔 제공합니다. 뷰는 실제 물리적인 데이터를 건드리지 않습니다.

뷰 생성(`CREATE VIEW`)은 시스템 권한(system privilege)입니다. 아무나 만들 수 없습니다. (실습) 따라서 현재 접속한 계정(예: 테스트 계정)이 이 권한을 가지고 있어야 합니다. (실습) 시스템(System) 계정으로 접속하여 '다른 사용자' 메뉴에서 해당 계정(테스트 계정)을 편집합니다. (실습) '시스템 권한' 탭에서 `CREATE VIEW`를 찾아 체크하고 적용해야 합니다. (실습)

권한 설정을 먼저 해야 뷰를 생성할 수 있습니다. (실습) `CREATE VIEW view_name AS SELECT …` 구문으로 뷰를 생성합니다. (실습) (참고: `CREATE TABLE … AS SELECT` (CTAS) 구문은 물리적인 테이블을 생성하지만, `CREATE VIEW`는 논리적인 뷰(쿼리 저장)를 생성합니다.)

SQL Developer GUI의 뷰 목록에서 '새 뷰(New View)'를 선택하여 생성할 수도 있습니다. (실습) 뷰 이름을 입력하고 `SELECT` 쿼리 내용을 작성한 뒤 '테스트' 후 '확인'을 누르면 생성됩니다. (실습) 하지만 쿼리 워크시트에서 스크립트로 직접 입력하는 것이 더 빠릅니다. (실습)

생성된 뷰는 선글라스 모양 아이콘으로 표시되며, 이는 물리적 데이터가 아닌 가상 데이터(저장된 쿼리)임을 의미합니다.

뷰는 일반 테이블처럼 `SELECT` 문에서 사용할 수 있습니다. (실습) 뷰를 호출하면( `SELECT * FROM my_view WHERE …`), 뷰에 정의된 `SELECT` 구문이 호출한 쿼리와 합쳐져(임베디드되어) 실행됩니다. (실습) 뷰와 일반 테이블 간의 조인(Join)도 가능합니다. (실습)

단, 뷰 생성 시 사용된 컬럼만 접근할 수 있습니다. 뷰가 4개의 컬럼만 `SELECT` 하도록 정의되었다면, 원본 테이블에 다른 컬럼(예: 입사 연도)이 있더라도 해당 뷰를 통해서는 접근할 수 없습니다. (오류 발생)

실무에서는 복잡한 조인 쿼리를 뷰로 만들어 두고, 사용자는 조인 없이 해당 뷰에서 필요한 컬럼만 간단히 조회하는 용도로도 많이 사용합니다. (실습)

뷰는 보통 조회용(SELECT)으로 주로 쓰지만, `INSERT`, `DELETE`, `UPDATE` (DML)도 가능은 합니다. 하지만 조인 뷰(Join View)나 집계 함수를 포함하는 등 복잡한 뷰는 DML이 불가능하며, 단순 뷰(Simple View)라 할지라도 원본 데이터에 문제가 없는 경우(케바케)에만 실행됩니다. 웬만하면 뷰를 통한 원본 데이터 수정은 권장하지 않습니다.

이제 보안 관점에서 뷰를 활용하는 실습을 하겠습니다. (실습)
요구 사항은 다음과 같습니다:
1.  일반 직원은 자신의 정보만 조회 가능
2.  인사팀은 민감한 주민번호를 제외하고 조회 가능
3.  관리자(Admin)는 모든 정보(주민번호 포함) 조회 가능

실습을 위해 `employees2` 테이블을 새로 만들고 주민번호 컬럼을 추가하여 `INSERT` 합니다. (실습)

`USER` 키워드는 현재 접속한 계정(사용자)의 값을 얻어오는 시스템 변수(키워드)입니다.

이 시나리오를 위해 3개의 계정(일반 직원 `emp_001`, 인사팀 `hr_001`, 관리자 `admin_001`)을 생성해야 합니다. (실습) 계정 생성(`CREATE USER`)과 `CONNECT` 권한(privilege) 부여는 시스템(System) 계정에서 수행해야 합니다. (실습) 관리자 계정에는 DBA 권한(role)을 줄 수 있습니다. (실습)

계정 생성이 완료되면, `employees2` 테이블의 소유자인 테스트 계정에서 각 계정별로 접근할 뷰(View) 3개를 생성합니다. (실습)
1.  `v_my_info` (일반 직원용): `… WHERE emp_id = SUBSTR(USER, …)` (계정 ID와 사원 ID를 매핑)
2.  `v_hr_info` (인사팀용): `SELECT …` (주민번호 컬럼 제외)
3.  `v_admin_info` (관리자용): `SELECT * …` (모든 컬럼)

뷰 생성이 완료되면, 테스트 계정(소유자)에서 각 뷰에 대한 `SELECT` 권한(privilege)을 해당 사용자(계정)에게 부여(`GRANT`)해야 합니다. (실습)
* `GRANT SELECT ON v_my_info TO emp_001;` (실습)
* `GRANT SELECT ON v_hr_info TO hr_001;` (실습)
* `GRANT SELECT ON v_admin_info TO admin_001;` (실습)
( `GRANT`와 `REVOKE`는 다음 시간에 자세히 다룹니다.)

실무에서는 사용자 개개인에게 권한을 주기보다, 롤(Role)을 만들어 그룹(예: 인사팀 롤)에 권한을 부여하고 사용자는 롤을 할당받습니다.

테스트는 커맨드 라인(SQL*Plus)에서 진행합니다. (실습) `CONN username/password` (예: `CONN emp_001/1234`) 명령어를 사용하면 아이디와 비밀번호를 한 번에 입력하여 접속할 수 있습니다. (실습)

각 계정으로 접속하여 할당된 뷰를 조회하면, 요구 사항에 맞게 일반 직원은 자기 정보만, 인사팀은 주민번호가 제외된 정보만, 관리자는 모든 정보를 볼 수 있습니다. (실습) 뷰를 보안에 이런 식으로 적용할 수 있습니다. (실습)

    가상 테이블인 뷰(View)를 생성하고 권한(Privilege)을 제어하여, 사용자에 따라 데이터를 선별적(행/열 수준)으로 노출하는 보안 기법을 학습합니다.
    
2. **핵심 TL;DR**
    

- **뷰(View)**는 물리적 공간을 차지하지 않는 **가상의 논리적 테이블**이며, 실제로는 `SELECT` 쿼리문만 저장하고 있습니다.
- 뷰는 `CREATE TABLE … AS SELECT` (CTAS)와 달리 물리적 데이터를 복사하지 않습니다.
- **보안 목적 (핵심)**: 민감한 데이터(열)를 숨기거나(Masking), 특정 조건(행)의 데이터만 노출(Row-Level Security)하는 데 사용됩니다.
- **편의 목적**: 복잡한 조인(Join) 쿼리를 뷰로 단순화하여 재사용할 수 있습니다.
- 뷰 생성(`CREATE VIEW`)은 강력한 **시스템 권한(System Privilege)**이며, DB 관리자(예: `SYSTEM` 계정)가 사용자에게 부여해야 합니다.
- 뷰는 일반 테이블처럼 `SELECT` 및 `JOIN`에서 사용할 수 있으며, 쿼리 실행 시 뷰의 `SELECT` 문이 사용자의 쿼리와 병합되어 실행됩니다.
- 뷰에 정의되지 않은 컬럼은 뷰를 통해 접근할 수 없습니다. (열 수준 보안)
- 뷰에 DML(`INSERT`, `UPDATE`)은 가능은 하나, 조인 뷰나 집계 뷰 등 복잡한 뷰에서는 제한되며, 주로 **조회용(Read-Only)**으로 사용을 권장합니다.
- `USER` 키워드는 현재 접속한 DB 사용자 계정을 반환하며, 뷰의 `WHERE` 절에서 이 값을 사용해 사용자별 동적 데이터 필터링(RLS)을 구현할 수 있습니다.
- 뷰를 생성한 후, 다른 사용자가 해당 뷰를 조회(SELECT)하려면 `GRANT SELECT ON <view_name> TO <user_or_role>;` 구문으로 **객체 권한(Object Privilege)**을 별도로 부여해야 합니다.
    

1. **표현 = 표준 용어**
    

- `View` (뷰): 가상 테이블 (저장된 `SELECT` 쿼리).
- `System Privilege` (시스템 권한): DB 전체에 영향을 미치는 권한. (예: `CREATE VIEW`, `CREATE USER`)
- `Object Privilege` (객체 권한): 특정 객체(테이블, 뷰)에 대한 권한. (예: `SELECT`, `INSERT`)
- `GRANT` / `REVOKE`: 권한을 부여하거나 회수하는 DDL 명령어.
- `Data Masking` (데이터 마스킹): 뷰의 `SELECT` 리스트에서 민감한 컬럼(예: 주민번호)을 제외하거나 변형(1교시 `SUBSTR`)하여 노출을 제어.
- `Row-Level Security (RLS)` (행 수준 보안): 뷰의 `WHERE` 절을 사용하여 사용자별로 접근 가능한 행(Row)을 제한.
- `USER` (키워드): 현재 세션의 데이터베이스 사용자 이름을 반환.
- `Role` (롤): 여러 권한(Privilege)을 묶어 관리하는 그룹 객체. (개별 사용자에게 권한을 주는 것보다 권장됨)
- `Simple View` (단순 뷰): 1개 테이블, 조인/함수/그룹 없음. (DML 가능성이 높음)
- `Complex View` (복합 뷰): 조인, 집계 함수, `GROUP BY` 등 포함. (DML 거의 불가능, 조회 전용)
    

1. **정석 보강(canon-std)**
    

- **뷰와 접근 제어(Authorization)**: 뷰는 DAC(Discretionary Access Control) 및 RBAC(Role-Based Access Control)에서 데이터의 _부분 집합_(특정 행/열)에 대한 접근을 제어하는 핵심 도구입니다. `GRANT`가 객체 _접근_을 제어한다면, 뷰는 접근 _후_ 볼 수 있는 _내용_을 제어합니다.
- **행 수준 보안(RLS) 수동 구현**: `CREATE VIEW v_my_info AS SELECT … FROM emp WHERE emp_id = USER;` 패턴은 RLS의 고전적인 수동 구현 방식입니다. (Oracle의 VPD/RLS 정책은 이를 자동화합니다.)
- **`WITH CHECK OPTION`**: 뷰에 `INSERT`나 `UPDATE`를 수행할 때, 해당 데이터가 뷰의 `WHERE` 절 조건을 만족하는지 검사하는 옵션입니다.
    

1. **실수·함정**
    

- 뷰를 생성(Create)하면 모든 사용자가 자동으로 볼 수 있다고 오해하는 것. (소유자는 뷰를 생성할 뿐, `GRANT SELECT ON …`로 권한을 따로 줘야 합니다.)
- 뷰가 물리적 데이터를 _복사_하여 성능이 빠를 것이라 오해하는 것. (성능상 이점은 없으며, 쿼리만 저장합니다. 물리적 복사본은 Materialized View(MView)입니다.)
- 복합 뷰(Join View)에 `INSERT`나 `UPDATE`가 가능할 것이라 기대하는 것. (대부분의 RDBMS에서 오류가 발생합니다.)
- `CREATE VIEW` 권한은 있지만, 뷰의 _기반 테이블_(예: `emp`)에 대한 `SELECT` 권한이 없는 경우. (권한이 없으면 뷰를 생성할 수 없습니다.)
- 뷰에 `GRANT` 할 때 `GRANT SELECT ON emp TO user;` (원본 테이블)가 아닌 `GRANT SELECT ON v_my_info TO user;` (뷰)로 권한을 줘야 합니다.

**[Q1] 뷰(View)란 무엇이며, 왜 물리적 공간이 없는 '가상 테이블'이라고 부르는가? | 태그: 뷰(View), 가상 테이블**

- **모범답(강의 기준)**: 뷰는 실제 물리적 공간(데이터)을 차지하지 않고, `SELECT` 쿼리문 자체만 저장하고 있는 논리적인 가상 테이블입니다. 뷰를 조회하면 저장된 `SELECT` 문이 실행되어 결과를 보여줍니다.
- **정석체크(면접 30초)**: 뷰는 `SELECT` 쿼리에 이름을 붙여 저장한 데이터베이스 객체입니다. 데이터는 원본 테이블에 있으며, 뷰는 *창문(Window)*처럼 원본의 특정 부분(행/열)만 보여줍니다. `CREATE VIEW v_name AS SELECT …`로 생성하며, 물리적 복사본인 Materialized View(MView)와 구별됩니다.
    

**[Q2] 뷰(View)를 사용하는 주요 목적(보안/편의)은 무엇인가? | 태그: 뷰(View), 보안(Masking), 편의성(Join)**

- **모범답(강의 기준)**: 1) **보안**: 민감한 데이터(예: 주민번호, 급여)를 숨기거나(Masking), 특정 사용자(예: 인사팀, 복지팀)별로 필요한 데이터만 선별적 노출(권한 분리)합니다. 2) **편의**: 3중 조인처럼 복잡한 쿼리를 뷰로 미리 정의하여 쿼리를 단순화합니다.
- **정석체크(면접 30초)**: 뷰의 목적은 1) **보안**: 민감한 _열_(예: 주민번호)을 제외(Masking)하거나, `WHERE` 절로 특정 _행_(예: 자기 부서)만 노출(RLS)합니다. 2) **단순성**: 복잡한 `JOIN`이나 집계 쿼리를 캡슐화하여 사용자가 쉽게 접근하게 합니다.
    

**[Q3] `CREATE VIEW` 권한은 어떤 권한이며, 누가 부여해야 하는가? | 태그: 뷰(View), 시스템 권한(System Privilege), GRANT**

- **모범답(강의 기준)**: `CREATE VIEW`는 시스템 권한(System Privilege)입니다. 따라서 `SYSTEM` 계정 같은 관리자가 `GRANT CREATE VIEW TO <user>;` 명령어로 해당 사용자에게 권한을 부여해야 뷰를 생성할 수 있습니다.
- **정석체크(면접 30초)**: `CREATE VIEW`는 객체를 생성하는 DDL 권한이므로 시스템 권한(System Privilege)입니다. DBA가 `GRANT CREATE VIEW TO <user>;`로 부여합니다. 단, 뷰를 _생성_하는 권한과 뷰의 _기반 테이블_(예: `emp`)을 `SELECT`할 권한은 별개입니다.
    

**[Q4] 뷰 생성 후, 다른 사용자가 `SELECT` 할 수 있도록 하려면 어떤 권한을 부여해야 하는가? | 태그: 뷰(View), 객체 권한(Object Privilege), GRANT**

- **모범답(강의 기준)**: 뷰의 소유자(예: '테스트' 계정)가 `GRANT SELECT ON <view_name> TO <user_name>;` 명령어로 해당 뷰에 대한 `SELECT` 권한(객체 권한)을 다른 사용자에게 부여해야 합니다.
- **정석체크(면접 30초)**: 뷰에 대한 `SELECT` 권한은 객체 권한(Object Privilege)입니다. 뷰 소유자가 `GRANT SELECT ON v_my_info TO emp_001;`처럼 부여합니다. 사용자는 원본 테이블이 아닌 뷰에 대한 권한만 받으므로 최소 권한 원칙(Least Privilege)을 만족합니다.
    

**[Q5] 뷰(View)를 이용해 '열 수준 보안'(Column-level)과 '행 수준 보안'(Row-level)을 구현하는 방법은? | 태그: 뷰(View), RLS(행 수준 보안), 마스킹(열 수준 보안), USER**

- **모범답(강의 기준)**: **열 수준**은 `SELECT` 절에서 인사팀 뷰를 만들 때 주민번호 같은 민감한 컬럼을 제외합니다. **행 수준**은 `WHERE` 절에서 `USER` 키워드(현재 접속자)를 사용해 `WHERE emp_id = SUBSTR(USER, …)`처럼 자기 정보만 보도록 필터링합니다.
- **정석체크(면접 30초)**: **열 수준(마스킹)**은 `CREATE VIEW v_hr AS SELECT emp_id, name FROM emp;`처럼 민감 컬럼(예: `salary`)을 제외합니다. **행 수준(RLS)**은 `CREATE VIEW v_my_info AS SELECT * FROM emp WHERE emp_id = SYS_CONTEXT('USERENV', 'SESSION_USER');` (또는 `USER` 키워드)로 동적 필터링을 구현합니다.
    

**[Q6] 뷰(View)에 DML(INSERT/UPDATE) 사용이 제한적이거나 권장되지 않는 이유는? | 태그: 뷰(View), DML, 복합 뷰(Complex View)**

- **모범답(강의 기준)**: 뷰는 주로 조회용(Read-Only)입니다. 조인(Join)된 뷰나 집계 함수가 포함된 복합 뷰(Complex View)는 DML이 불가능하거나 모호성(Ambiguity)이 발생할 수 있으므로, 원본 데이터 수정은 뷰를 통하지 않는 것을 권장합니다.
- **정석체크(면접 30초)**: 1개 테이블로 만든 단순 뷰(Simple View)는 DML이 가능하나, 2개 이상 테이블 조인, 집계 함수(`GROUP BY`), `DISTINCT` 등이 포함된 복합 뷰(Complex View)는 DML이 불가능합니다. DML이 가능한 뷰라도 `WITH CHECK OPTION`을 명시하여 뷰의 `WHERE` 조건(가시성)을 벗어나는 수정을 막는 것이 좋습니다.
    

**[Q7] 실무에서 사용자 개인이 아닌 롤(Role)에 권한을 부여하는 이유는? | 태그: 롤(Role), RBAC, 권한 관리**

- **모범답(강의 기준)**: 사원(사용자)이 많을 때, 한 명 한 명에게 권한을 주면 관리가 어렵습니다. '인사팀' 롤(Role)을 만들고 롤에 권한을 부여한 뒤, 사용자들을 롤에 포함시키면(그룹핑) 권한 관리가 효율적입니다.
- **정석체크(면접 30초)**: 롤(Role)은 RBAC(역할 기반 접근 제어)의 핵심입니다. 사용자에게 직접 권한(Privilege)을 `GRANT`하면 입/퇴사 및 부서 이동 시 권한 회수(REVOKE)가 복잡합니다. `CREATE ROLE hr_role;` 후 `GRANT SELECT ON v_hr_info TO hr_role;`로 롤에 권한을 부여하고, 사용자에게는 `GRANT hr_role TO user;`로 롤을 부여하면 관리가 간편해집니다.
